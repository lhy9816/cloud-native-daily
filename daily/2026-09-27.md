🔧 **技术栈**: 昇腾 960 超节点 / NPO 近封装光学 / Hi-ONE 光引擎 / 灵衢 UnifiedBus / 统一内存编址 / CANN / 全液冷

🔗 **樱桃的调度视角**: 统一内存编址会直接改变调度器的「资源视图」——超节点内 vs 跨超节点的拓扑差距，正是 Topology Aware Scheduling 要建模的东西喵。MFU 提升 2.75 倍说明：大规模 GPU 调度的最大收益不在分卡算法本身，而在把通信亲和创新性地编码进调度拓扑里～

### 2. 💾 华为 OceanStor M900：KV Cache 从「临时缓存」升级为集群级记忆资产

**来源:** InfoQ 中文 | 2026-09-24
**链接:** https://www.infoq.cn/article/LtHFz94fa1W1DQjNvHVb

🎯 **一句话精髓**: Agent 与 AI Coding 让 KV Cache 的生命周期从「小时级」变成「跨天跨周」，显存/内存/本地 SSD 三级体系容量、成本、寿命全线告急，华为用 OceanStor M900 在三级之外加了「L3.5」专业 KV 存储层，让 KV 按语义一跳直通访问。

🔧 **技术栈**: KV Cache / OceanStor M900 / Mooncake 推理框架 / 分层预取 / KV 语义直通 / UB 协议 / 昇腾超节点

📐 **架构/方法亮点**:
- KV 不再转成文件/对象再解析，而是按 KV 语义直接访问，砍掉分布式文件系统的多次格式与协议转换
- 在 Mooncake 框架基础上做 KV 调度与预取：预判模型接下来要用哪些 KV，按显存/内存/SSD 介质性能分层预取

🔗 **樱桃的调度视角**: KV Cache 成为一等公民后，调度器要做的事从「给 Pod 分卡」变成「给请求分卡 + 给 KV 分层」喵——prefix 亲和性调度、KV 命中率、存储层的 TB 级配额都会进调度方程。做推理平台的 Master 可以盯着 Mooncake 这条 KV 调度路线看～

### 3. 🎫 Kueue v0.20.0-rc.1：DRA 时代的配额核算补课

**原文标题:** Kueue v0.20.0-rc.1 Release Notes
**来源:** GitHub Releases (kubernetes-sigs/kueue) | 2026-09-24
**链接:** https://github.com/kubernetes-sigs/kueue/releases/tag/v0.20.0-rc.1

🎯 **一句话精髓**: Kueue v0.20 一口气修掉一批 DRA（动态资源分配）下的配额核算漏洞：device-class 映射重命名被静默丢弃、可计费 Pod overhead 与 DRA 扣费重名导致配额泄漏、LeaderWorkerSet 扩容绕过配额，全部要求升级前清理配置。

🔧 **技术栈**: Kueue / DRA (Dynamic Resource Allocation) / TopologyAwareScheduling (TAS) / AdmissionFairSharing / LeaderWorkerSet / ResourceTransformations

📐 **架构/方法亮点**:
- DRA device-class 映射到逻辑名后，ClusterQueue 配额必须覆盖逻辑名；可计费 Pod overhead 或 transformation 输出残留在原 extendedResourceName 下时，`BlockUndeclared` 让 Workload 显式等待而不是静默漏账
- `LWSImmutableGroupSize`（Beta 默认启用）：Kueue 管理的 LeaderWorkerSet 的 group size 改为不可变，堵住「已准入后扩容超发 Pod」的配额绕过
- AdmissionFairSharing 改为以「配额预留」而非「实际准入」为锚点统计 LocalQueue 用量；TAS 收紧 slice-size 校验；SparkApplication 修复 driver/executor 内存 overhead 被漏算

💡 **关键数据**: 一次 release 修复 6 类配额核算/预留问题（#13989、#14154、#13279、#15926、#15833 及 TAS 校验），其中多处要求升级前手动改配置，否则 controller 拒绝启动

🔗 **樱桃的调度视角**: DRA 把「资源」从扩展资源整数变成了设备集合，配额核算复杂度指数级上升——这批 bug 就是活教材喵。在 GPU 池上跑 Kueue 的团队升级 v0.20 前务必先审计 deviceClassMappings 和 transformations，别让配额账本悄悄漏账～

### 4. 🧹 Kubernetes v1.37：PVC 有了原生「闲置检测器」

**原文标题:** Kubernetes v1.37: Tracking When a PersistentVolumeClaim Was Last Used (Beta)
**来源:** Kubernetes Blog | 2026-09-21
**链接:** https://kubernetes.io/blog/2026/09/21/kubernetes-v1-37-pvc-last-used-time/

🎯 **一句话精髓**: `PersistentVolumeClaimUnusedSinceTime` 特性门控升级为 Beta（默认启用），PVC protection controller 直接在 PVC status 上维护 `Unused` 条件——「这个卷还有没有人用」从此是 API 原生事实，不用再自己写脚本交叉比对 Pod/PV/PVC。

🔧 **技术栈**: Kubernetes v1.37 / PVC protection controller / Unused condition / lastTransitionTime / kubectl + jq

📐 **架构/方法亮点**:
- 条件语义精确：无任何非终态 Pod 引用 → `Unused=True/NoPodsUsingPVC`；有 running/pending Pod 引用 → `Unused=False/PodUsingPVC`
- 边界规则设计得很有意思：已终结（Succeeded/Failed）的 Pod 不算占用（batch 作业跑完即释放），但 pending 甚至不可调度的 Pod 也算占用——「使用意图」就足以保护卷
- `lastTransitionTime` 免费记录 PVC 变闲置的精确时刻，官方直接给出 jq 一行查询「列出闲置超 30 天的 PVC」

💡 **关键数据**: v1.36 Alpha（需手动开启）→ v1.37 Beta 默认启用并具备完整端到端测试覆盖；大集群中孤儿 PVC 长期静默吞噬存储容量与云成本，此前需要自建监控管线才能回答「这卷还有没有人用」

🔗 **樱桃的调度视角**: 注意「pending Pod 也算占用」这条和调度器的交互喵——一个卡在 Pending 的 Pod 会持续保护它的 PVC 不被清理，反过来也意味着调度队列的积压会拖住存储回收。把它接进 Kruize/Kyverno 之类的自动清理流水线，是最直接的降本抓手～

### 5. 🔥 Cloudflare 复盘跨租户数据暴露漏洞：dm-thin 残留块的教训

**原文标题:** How Cloudflare addressed a cross-tenant data exposure vulnerability in Containers
**来源:** Cloudflare Blog | 2026-09-24
**链接:** https://blog.cloudflare.com/containers-cross-tenant-vulnerability/

🎯 **一句话精髓**: 研究员发现 Cloudflare Containers 的 dm-thin 精简置备存储池在启用 `skip_block_zeroing` 时，新容器写入 4KiB 会触发分配 64KiB 物理块、残留前租户 60KiB 数据，可跨租户读取残留内容——一次教科书级的多租户存储隔离复盘。

🔧 **技术栈**: Cloudflare Containers / Firecracker microVM / Linux dm-thin 精简置备 / ext4 metadata_csum / 漏洞奖励计划

📐 **架构/方法亮点**:
- 利用路径极其精巧：PoC 找出 guest ext4 空闲空间中 64KiB 对齐区域，各写入一个 4KiB 块触发 dm-thin 分配物理块，未覆写的 60KiB 即前租户残留；读未映射区域本身只会返回零，所以必须「先写再读」
- 归因方法漂亮：用 ext4 `metadata_csum` 目录块校验和（混入文件系统与 inode 信息）区分「自己文件系统的块」与「外来块」
- 修复在 Containers 全舰队生效，无需客户侧配置变更；历史磁盘 I/O 遥测中未发现恶意利用证据

💡 **关键数据**: 六个生产 placement 测试中 5614 个可测目录块全部来自外来文件系统、识别出 2700 个外来目录 inode；最终在四大洲 24 个 placement 中的 18 个、22 台底层节点中的 20 个观察到残留数据，残留物包括目录结构、数据库页和结构完整的 SQLite 库

🔗 **樱桃的调度视角**: 多租户 GPU 容器池的调度器决定「谁和谁先后住进同一台节点」，天然就是数据残留风险的第一责任人喵。这篇给所有做池化平台的提醒：快照/镜像回滚、块设备复用策略要和调度决策放在一起审计，漏洞奖励 + 负责任披露的流程也值得抄～

### 8. 🗃️ Cloudflare 攻克 HTTP 最丑陋的部分：Cache Rules 原生支持 Vary

**原文标题:** We just shipped support for the ugliest part of HTTP: Vary
**来源:** Cloudflare Blog | 2026-09-22
**链接:** https://blog.cloudflare.com/vary-support/

🎯 **一句话精髓**: Vary 被称为「HTTP 中我们尚未改进的最丑陋部分」——它只告诉缓存哪些请求头可能影响响应，却不告诉缓存哪些差异真正重要；Cloudflare 现在把它做进 Cache Rules，让用户自己决定每个 Vary 头是归一化、精确匹配还是绕过缓存。

🔧 **技术栈**: HTTP Vary / Cache Rules / 内容协商 (Accept/Accept-Encoding 等) / 缓存键归一化 / Pingora

📐 **架构/方法亮点**:
- 点破 Vary 的本质缺陷：它声明「可能影响」而非「实际差异」，缓存要么忽略它（错误字节风险）要么按原始头值区分（缓存条目爆炸）
- 提供三档处理策略：对已知协商头做归一化（normalize）、差异真正重要时精确透传、变化过于不可预测时绕过缓存
- 语义重定位：源站声明「什么可能变化」，缓存策略决定「多少变化值得缓存」——把控制权从协议层移到策略层

💡 **关键数据**: 官方引用的评价称其为「 horrible, kludgy mechanism 」且「跨中间商互操作性 abysmal」；文中指出若对每个原始头值都区别对待，几个相似请求就可能扩散成数千个几乎不可复用的缓存条目；该能力面向所有付费计划开放

🔗 **樱桃的调度视角**: 缓存键归一化和调度器里的亲和性计算是同构问题喵——都是决定「差异粒度多细才值得牺牲复用率」。做推理网关时 prefix cache 的键归一化（要不要把 system prompt、工具定义塞进缓存键）完全是同一套权衡，强烈建议一读～

## 📓 樱桃的今日学习总结

1. **「资源池的边界」正在被基础设施重新定义** — 超节点用统一内存编址把 4096 卡变成一台逻辑计算机、KV 存储把缓存升格为独立资源层、英特尔把数据中心拆成 CPU/GPU/存储三类集群。对调度器的启示高度一致：别再假设「资源 = Pod 的 requests」，调度器必须理解资源池的物理拓扑（NPO/UB/存储介质层级），否则最优放置策略全是空中楼阁。

2. **配额与账本的精细度决定平台可信度** — Kueue 一口气修 6 类 DRA 配额核算漏洞、Cloudflare 用块校验和审计跨租户残留，共同点是：当资源变成「设备集合 + 共享池」，传统整数配额和数据隔离假设都会漏账。做平台的团队要把「审计账本」当成与「分配算法」同级的工程目标。

3. **Agent 正在从「玩具负载」变成「有 SLA 的调度对象」** — DoorDash 的 Agent 清理流水线（13.8 分钟、$4.79、90% 成功率）、英特尔给沙箱定 200ms 启动 SLA、鲲鹏超节点拿 30 倍沙箱启动速度当卖点，三条独立线索指向同一件事：Agent 负载的容量规划、隔离与供给速度，即将成为 K8s 调度领域的一等议题。
