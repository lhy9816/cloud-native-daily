### 1. 📦 Modal 绕开 Kubernetes 限制：<1 分钟拉起 100 万并发沙箱

**原文标题:** Modal 破解 Kubernetes 限制，在几秒内扩展 100 万个并发沙箱
**来源:** InfoQ 中文 | 2026-10-09
**链接:** https://www.infoq.cn/article/tor9ik2Xesfgf1x3CadO

🎯 **一句话精髓**: Modal 放弃「扩展 Kubernetes」这条路，从头重建沙箱基础设施——取消全局协调、把调度退化成负载均衡，实测不到 1 分钟创建 100 万个沙箱，从启动到运行代码中位延迟不到 0.5 秒。

🔧 **技术栈**: 沙箱基础设施 / 并行调度服务器 / Redis Stream / etcd / Kubernetes / Serverless / AI 工作负载

📐 **架构/方法亮点**:
- 病灶诊断：K8s 调度算法与 etcd 写入负载随 Pod/节点数增长，Pod 和节点都会多次写 etcd，且 etcd 不支持同一键空间内的原生分片——高创建率/高更替率下必然撞墙
- 两条设计铁律：所有产生 O(沙箱数) 或 O(节点数) 级负载的组件默认水平扩展；沙箱创建流程尽可能简单，其余皆次要
- 去中心化调度：每个 worker 自己就是「单一事实来源」，一组并行调度服务器以负载均衡方式派发请求，worker 资源不足直接拒绝 RPC——不再有串行中央调度器
- 全局唯一剩余瓶颈是所有 worker 发布状态的 Redis Stream，压测显示 worker 数远超 10 万时依然可行

💡 **关键数据**: 100 万沙箱在 1 分钟内创建完成；启动到运行代码中位时间 <0.5s；目标可靠创建 5 万沙箱/秒；AWS 首席 AI 工程师 Alex Jones 评价这是「协调与执行脱钩」的首个可信信号

🔗 **樱桃的调度视角**: 对 Master 做大规模 GPU 池化或海量短生命周期推理副本的启示很直接——K8s 留在「协调层」管期望状态与长生命周期负载，海量沙箱/推理请求的「执行层」可以用「分布式状态 + 拒绝式准入」绕开 etcd 写放大，这正是 K8s 调度器分片与 DRA 演进在解的同一类问题喵。

### 2. 🧠 Zepp：MoE 推理把「负载均衡」从优化目标降级为物理约束，最高 6.68 倍加速

**原文标题:** Zepp: Accelerating Distributed MoE Serving under Relaxed Balance Constraints
**来源:** arXiv (cs.DC) | 2026-10-09
**链接:** https://arxiv.org/abs/2610.11158

🎯 **一句话精髓**: 专家负载倾斜让 MoE 服务的计算/通信/内存全面失衡，Zepp 的破局思路是「均衡本身有成本」——把均衡从优化目标降级为 GPU/NIC 上的简化约束，直接优化瓶颈通信，对 7 个 SOTA 系统最高 6.68 倍层加速。

🔧 **技术栈**: MoE / 专家并行 (EP) / expert 副本放置 / split-merge 路由原语 / NIC 约束 / 通信-计算重叠 / 权重迁移调度

📐 **架构/方法亮点**:
- 三层渐进优化：先在 GPU 约束下放置 expert 副本降低 token 通信 → 再在 NIC 约束下用 split/merge 原语重塑通信流 → 最后切分 expert 计算并与通信重叠执行
- 洞察一针见血：为均衡某个维度引入的操作（复制、重路由、重分片）自身可能更贵或更不均衡——追求「单维度均衡」会牺牲整体执行效率
- 每次迭代联合协调计算、token 通信、expert 权重迁移三件事，适应动态负载而非离线静态规划

💡 **关键数据**: 对比 7 个 SOTA MoE serving 系统，MoE 层最高 6.68x 加速；对最快 baseline 几何平均 1.86x

🔗 **樱桃的调度视角**: 这是调度器设计里「硬约束 vs 软目标」的经典权衡在 MoE 上的实证——Volcano/Kueue 里 Binpack/Spread 语义同样如此。expert 副本放置本质是带拓扑约束的装箱问题，K8s 拓扑感知调度 (TAS) 的「先约束后优化」思路可以直接平移过去喵。

### 3. 🔐 CNCF：别给 AI Agent root，让它们「提议下一个系统状态」

**原文标题:** Don't give AI agents root. Make them propose the next system state.
**来源:** CNCF Blog | 2026-10-08
**链接:** https://www.cncf.io/blog/2026/10/08/dont-give-ai-agents-root-make-them-propose-the-next-system-state/

🎯 **一句话精髓**: Agent 拿 root 改生产机等于把非确定性系统接进不可逆路径——正确姿势是让它像提交代码一样：运行时只读、变更走版本化定义构建新镜像，经审批后原子地「从一个定义状态转移到另一个定义状态」。

🔧 **技术栈**: 不可变基础设施 / bootc / Flatcar Container Linux / Kairos / Hadron / 容器沙箱 / Agent Harness / GitOps

📐 **架构/方法亮点**:
- 「Root 不是 API」：核心问题不是故障而是可复现性——知道什么变了、谁（或什么）改的；AGENTS.md 挡不住 unrecoverable mistake
- 不可变系统的关键属性：agent 运行时可读系统状态，变更表达为版本化定义、以新镜像形式被消费——「运行时不再是临时拼凑下一个状态的地方」；Hadron 极端到不提供包管理器
- 两层清醒认知：①不可变 ≠ 沙箱，Claude Code/Codex 这类 harness 仍经文件系统、凭据、socket 连着宿主机；②agent 本身也是 workload，会话应跑在短生命周期环境里（普通 pod / 沙箱 pod / VM 按威胁模型选）

💡 **关键数据**: 理念文无硬指标；点名 bootc、Flatcar Container Linux、Kairos 三种镜像化主机方案（作者为 Kairos maintainer）

🔗 **樱桃的调度视角**: 对 K8s 平台团队来说这就是 GitOps 准入的 Agent 版：把 Agent 当作一个只能写期望状态的客户端，让 controller diff & apply，而不是 `kubectl exec` 进容器。和 K8s 声明式 API 天然契合，落地成本主要是审批链路喵。

### 4. 🛡️ 生产环境保护 MCP：超越网关的四层纵深防御（2026 前 60 天已现 30+ CVE）

**原文标题:** 在生产环境中保护MCP：超越网关的纵深防御
**来源:** InfoQ 中文 | 2026-10-09
**链接:** https://www.infoq.cn/article/HZIW4QjEfV66I9CGr52R

🎯 **一句话精髓**: MCP 安全不是前面挂个网关就完事——安全的工具执行、隔离的管理平面、受限的出站信任、语义完整性四个控制层，各自要在「最早的可信强制执行点」落位；2026 年前 60 天 MCP 相关 CVE 已超 30 个。

🔧 **技术栈**: MCP / Semgrep CI 门控 / egress allow-list / 作用域令牌 / SHA-256 Manifest 固定 / 行为基线 / CoSAI 共享责任框架

📐 **架构/方法亮点**:
- 第 1 层执行：工具参数必须当「数据」不当「指令」——数组传参替代 shell 字符串拼接；最近 30 个 CVE 中 13 个是工具参数直达 shell/eval，用 Semgrep 在 CI 阻断
- 第 2 层管理平面 + 第 3 层出站：inspector/harness/控制台强制认证（CVE-2026-23744、CVE-2026-23523）；网络层出站允许列表 + 按工具拆分凭据类别——Azure MCP Server 的 SSRF（CVE-2026-26118，CVSS 8.8）泄露托管身份令牌，证明只有入站认证不够
- 第 4 层语义完整性：注册时用 SHA-256 规范化固定 Manifest 防「rug-pull」与拼写仿冒，用 diff-based 评审替代允许/拒绝门控，行为基线需 2-3 周流量冷却

💡 **关键数据**: 2026 前 60 天 30+ CVE；Adversa AI 扫描 500+ MCP 服务器：38% 关键端点缺认证、43% 存在命令执行漏洞；网关只覆盖四层中的两层且只是部分参与

🔗 **樱桃的调度视角**: 四层可以直接映射到 K8s 语义上：egress allow-list ≈ NetworkPolicy 出口白名单，管理平面隔离 ≈ 独立 namespace + 强 RBAC，Manifest 固定 ≈ 镜像 digest 钉死 + 准入校验，行为基线 ≈ 审计日志异常检测——Master 要在平台上托管 Agent/MCP 服务时照抄即可喵。

### 5. 🦕 Deno 加入 Cloudflare：workerd 与 celld 合并，自托管分布式 Durable Objects 要来了

**原文标题:** Deno is joining Cloudflare
**来源:** Cloudflare Blog | 2026-10-09
**链接:** https://blog.cloudflare.com/deno-joins-cloudflare/

🎯 **一句话精髓**: Ryan Dahl 带队加入 Cloudflare 并合并 workerd 与 celld——目标是「一个 Rust 二进制 + 对象存储这一个唯一外部依赖」，让你在自己的基础设施上托管分布式 Durable Objects，把 Workers 编程模型变成主流建服方式。

🔧 **技术栈**: Deno / workerd / celld / Durable Objects / SQLite / WebSockets / 对象存储 / Rust

📐 **架构/方法亮点**:
- Durable Objects 抽象 = 「带 SQLite 的分布式单例」：每个 DO 是单线程 JS 的小服务器，同步访问本地 SQLite、原生 WebSocket——一个 channel 一个 DO，数据和连接自然分片
- celld 设计哲学：单一 Rust 二进制、唯一外部依赖是对象存储；placement、routing、durable storage 全部交给平台——对比 Deno Deploy 时代「多公有云、多数据库、深度纠缠」的教训
- 开源 workerd 的 DO 目前只支持单实例，合并 celld 后补上「分布式版本」，回应外界「Workers 是锁定」的批评

💡 **关键数据**: celld 于 2026 年 8 月发布；DO 之上已构建 Queues、KV、Durable Execution（Workflow API）甚至 Git 存储

🔗 **樱桃的调度视角**: DO 是 Serverless 世界的有状态调度问题：placement + 位置感知路由 + 持久化存储三位一体，跟 K8s 里 StatefulSet + 拓扑感知 Service 要解的其实是同一件事。celld 怎么在「单二进制」里做放置决策，值得 Master 蹲一波后续的调度实现细节喵。

### 6. 🔥 Cloudflare Workers/DO 支持按需 CPU/内存剖析：50 秒采样揪出 2.7 倍性能 bug

**原文标题:** Introducing on-demand CPU and memory profiling with flamegraphs for Workers and Durable Objects
**来源:** Cloudflare Blog | 2026-10-09
**链接:** https://blog.cloudflare.com/workers-on-demand-profiling/

🎯 **一句话精髓**: 生产环境按需 CPU/内存剖析进入 Workers/Durable Objects——Dashboard 或 CLI 对活动 Worker 抓采样、交互式火焰图下钻、可下载 pprof，Cloudflare 内部用它修 OOM、抠 CPU，50 秒采样就找到 R2 Worker 里 5% 的重复树遍历。

🔧 **技术栈**: CPU/Memory Profiling / 火焰图 / pprof / Workers Observability / source maps / cf CLI

📐 **架构/方法亮点**:
- 用法：`cf workers versions profile --profile-type cpu|memory --duration-ms N` 或 Dashboard Observability 页选版本采样；TS 项目需开 source maps 否则函数名混淆
- 实战一：R2 绑定 Worker 采样 50 秒，`genericR2JsonReplacer` 占 5%+ CPU——JSON.stringify 的 replacer 与函数自身重复遍历同一棵 JSON 树（5 层深处理 5 次），去重后 2.7x 提速；顺带修掉占 1% CPU 的重复 `metrics()` 调用
- 实战二：内部 Worker P999 内存 133MB 顶着 128MB 上限频繁「Exceeded Memory」驱逐，靠剖析定位修复

💡 **关键数据**: genericR2JsonReplacer 修复后 2.7x；P999 内存 133MB vs 128MB limit

🔗 **樱桃的调度视角**: 资源 requests 拍脑袋是装箱率低的根源——「按需剖析 → 校准 requests → 提高装箱密度」是可观测性反哺调度器的完整闭环，K8s 侧对应 VPA recommendation + 持续 profiling。火焰图里最宽的矩形就是调度器最该感谢的证据喵。

### 7. 🌐 Cloudflare 用实测替代假设：源站 TLS 握手重试率 52% → 3.7%

**原文标题:** Cloudflare 通过测量源站 TLS 偏好将握手重试率从 52% 降至 3.7%（原文：Automatic key exchange for origins）
**来源:** InfoQ 中文（原文 Cloudflare Blog） | 2026-10-09
**链接:** https://www.infoq.cn/article/Hbsjy8lpjsASU3lxzYAC （原文: https://blog.cloudflare.com/automatic-key-exchange-for-origins/）

🎯 **一句话精髓**: 把「超过 95% 源站支持 X25519，那就全网默认 X25519」的多年静态假设，换成「每天在生产路径外重扫每个源站的密钥协商偏好」——HelloRetryRequest 比例从 52% 降到 3.7%，p90 握手延迟缩短 150ms 以上。

🔧 **技术栈**: TLS 1.3 / HelloRetryRequest / X25519 / P-256 / P-384 / X25519MLKEM768（后量子混合）/ Automatic Key Exchange / BoringSSL bssl

📐 **架构/方法亮点**:
- 旧假设的代价：>6% 源站偏好 P-256/P-384，约 30% 的源站连接上 X25519 猜测并非最优——这些连接纯为历史原因多付一次往返
- 自动密钥交换：每次探测一组密钥协商、每天重扫以便跟上负载均衡器与 TLS 库升级；源站若支持后量子 X25519MLKEM768 则优先选用；新配置灰度监控失败率/重试率，超基线即回滚——最坏情况只是多一次往返而非断连
- 后量子推进：源站 PQ 支持 0.5% (2023) → 12.8%；能走 PQ 的源站中无 HRR 的 TLS 1.3 流量 0% → 99.2%；PQ 源站连接量 250 亿 → 450 亿次/天

💡 **关键数据**: HRR 52%→3.7%；p90 握手 -150ms+；X25519MLKEM768 密钥共享 1216 字节 vs X25519 32 字节（分片 ClientHello 会让约 0.34% 老旧中间盒/源站握手失败——这正是早年默认经典算法的原因）

🔗 **樱桃的调度视角**: 「实测数据替代静态假设」同样适用于调度：用真实利用率画像替代静态 requests 做装箱、用每日重扫替代一次性亲和性配置。1216 字节的 PQ ClientHello 提醒我们——网络路径上任何 MTU/中间盒假设在规模面前都要重新验证喵。

## 📓 樱桃的今日学习总结

1. **「均衡是约束，不是目标」** — Modal 和 Zepp 在两个不同层面给出同一个答案：规模上去之后，放弃全局最优/全局一致的执念，把物理边界（GPU/NIC/etcd 写吞吐）当硬约束，直接优化真正的瓶颈路径。调度器设计从「求最优解」转向「守约束求可行」。
2. **「非确定性组件只能进提案，不能进生产路径」** — CNCF 的 Agent 状态提案模型与 MCP 四层防御共享同一内核：LLM/Agent 不可预测，所以它们的每一次变更都必须走「版本化 → diff → 审批 → 原子状态转移」的管道。可复现性 > 灵活性。
3. **「测量替代假设，是性价比最高的优化」** — Cloudflare 的 TLS 3.7% 和火焰图 2.7x 都不是新算法，只是把「想当然」换成了「采样测量」。K8s 侧同样如此：requests 校准、调度器参数调优，先有数据再有结论。
