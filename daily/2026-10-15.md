### 1. 📦 一块 GPU 空转 11 天：Adobe 给多租户 K8s 造了一层「GPU 可见性」

**原文标题:** 一块 GPU 空转 11 天？Adobe 用 Prometheus 找出问题所在
**来源:** InfoQ 中文 | 2026-10-14
**链接:** https://www.infoq.cn/article/AO4MbiBaYqwwCubevkpD （英文原文：https://www.infoq.com/news/2026/09/kubernetes-gpu-metrics/）

🎯 **一句话精髓**: Adobe 用纯 CNCF 组件（NGINX + kube-rbac-proxy + prom-label-proxy + MetricAccess CRD）搭了一层租户感知的 Prometheus 代理，让多租户 K8s 里的团队安全地自助查询自己的 GPU 利用率/功耗指标——并借此揪出了一块分配后连续 11 天利用率为零的「幽灵 GPU」。

🔧 **技术栈**: Prometheus / prom-label-proxy（强制注入 namespace 约束到 PromQL）/ kube-rbac-proxy / NGINX / MetricAccess CRD / remote write / Grafana Mimir & Cortex（对比项）

📐 **架构/方法亮点**:
- 不信任客户端查询：prom-label-proxy 在查询到达中心 Prometheus 前强制改写 PromQL 注入命名空间约束——靠开发者自觉带 namespace 不构成安全边界
- MetricAccess CRD：团队用指标名/正则/PromQL 选择器声明自己需要的指标，平台团队保留采集与访问控制权
- 可选租户专属 Prometheus：中心实例按租户过滤后 remote write 下去，开启 metricIsolation 后只采集该租户自己的时间序列，隔离多一道「没采集就永远不可能泄露」的边界

💡 **关键数据**: 示例配置中单个租户存储的时间序列从 10,000+ 条降到约 300 条；真实案例：一块已分配、通电状态的 GPU 利用率连续 11 天为 0

🔗 **樱桃的调度视角**: 「分配 ≠ 利用」正是 GPU 调度最痛的盲区——调度器视角里这张卡满负载运行，实际却在烧电空转。用 GPU 利用率+帧缓冲内存+功耗+请求速率四元组可以构建闲置 GPU 识别查询，直接对接 Kueue/Volcano 的配额回收策略；这套纯 CNCF 栈的租户隔离模式 Master 抄作业成本很低喵。

### 2. 🚀 Claude 写代码太快，Git 扛不住了：Anthropic 7 人 5 个月重造版本控制系统 Scion

**原文标题:** Claude写代码太快，Git扛不住了：Anthropic仅靠7人，5个月重造版本控制系统
**来源:** InfoQ 中文（原载 Anthropic 工程博客） | 2026-10-14
**链接:** https://www.infoq.cn/article/6iRATYfkqF7aITPaFR2R

🎯 **一句话精髓**: Claude 驱动的代码合并 4 个月增长 12 倍（5 月日均 2500 次 → 9 月超 3 万次），把 Git 镜像集群逼到极限后，Anthropic 用 7 人团队 5 个月造出服务器端集中式 VCS「Scion」：Changeset 写 WAL、Spanner 管元数据、三层缓存命中率 99%+。

🔧 **技术栈**: Scion（自研 VCS）/ Write-Ahead Log / Google Spanner / Blob Storage（内容寻址）/ scion-daemon→scion-cache→scion-server 三级缓存 / 稀疏检出 & 虚拟化检出 / Antique 代码审查

📐 **架构/方法亮点**:
- 核心范式转移：提交、变基、历史查询全部搬到服务器端，客户端只管工作目录和有限缓存——不再需要 push 步骤，VCS 能力直接以 API 形式提供给 CI 与 Agent 沙箱
- 成本与仓库规模解耦：操作成本取决于实际修改的数据量而非仓库大小；常规提交不移动全局 ref，避免重新引入协调瓶颈
- 三层缓存按内容寻址共享：节点级 scion-daemon（同节点多任务共享文件缓存）→ 区域级 scion-cache → 权威 scion-server，每层命中率 99%+，且用缓存层级隔离故障

💡 **关键数据**: Monorepo 主分支历史近 100GB、压缩工作副本超 25GB；CI 每天约 2500 万次检出（朴素 Git 取数需 600PB/天传输）；迁移后基础设施 CPU/内存占用降至原方案约 1/200，检出从分钟级到秒级，CI 释放约 25% CPU；Claude Mythos Preview 重写数据导入管线后内存降 20 倍、速度提升 4 倍

🔗 **樱桃的调度视角**: Agent 沙箱正在成为集群里一类全新的大规模短生命周期负载——「每个任务一个工作环境」的检出风暴本质上是 I/O 密集型 Burst 调度问题，和 AI 推理的 KV cache 复用是同构思想：把不可变数据（对象/权重）做成内容寻址缓存，让调度只搬运增量。做 AI CI 平台的 Master 值得全文精读喵。

### 3. 🤖 Anthropic 披露 Dynamic Workflows：让 Claude 写一段「编排程序」去管 1000 个 Agent

**原文标题:** Claude 开始自己写程序管理 Agent 了：Anthropic 披露动态工作流架构
**来源:** InfoQ 中文 | 2026-10-13
**链接:** https://www.infoq.cn/article/8La5gsJVOOF5BvFiLAUF

🎯 **一句话精髓**: Claude Managed Agents 新增 Dynamic Workflows（Beta）：主 Agent 不再逐步推理「下一步调谁」，而是生成一段真正可执行的编排程序，由服务器在后台启动子 Agent、衔接阶段、聚合结果——多 Agent 协调从「对话内推理」变成「编译后执行」。

🔧 **技术栈**: Claude Managed Agents / Dynamic Workflows / 预定义 Agent + inline Agent / 会话级预算机制 / Anthropic Dreams（记忆整理，研究预览）/ Hill-climbing（未来方向）

📐 **架构/方法亮点**:
- 编排程序是含真实执行逻辑的代码：并行启动、上阶段输出做下阶段输入、按检查结果决定重试或终止——中间数据存程序变量，不必每次回主对话重处理
- 执行边界明确量化：单次工作流累计最多 1000 个 Agent、同时运行上限 64 线程、默认最长 24 小时；预定义 Agent 白名单可约束模型不能随意造 Agent
- 预算机制是软边界：达到会话预算上限后停止发起新请求，但已发出的推理会跑完，并行场景下最终消耗可能超限——「少读中间结果」推不出「整体更省钱」

💡 **关键数据**: 1000（累计 Agent 上限）/ 64（并发线程上限）/ 24h（默认单次时长）；现场演示（股票观察列表扫描）中动态工作流比单 Agent 花费更多但发现更多细节

🔗 **樱桃的调度视角**: 「累计 1000 / 并发 64 / 预算暂停」这组参数就是 Agent 时代的 ResourceQuota + 并发限流原型——模型运行时不知道自己的预算，全靠平台侧强制执行，这跟 K8s 里 LimitRange 的设计哲学一模一样。未来 Agent 编排器大概率会以 K8s 原语落地，工作流就是一堆带依赖的 Job 喵。

### 4. 💾 Cursor 拆掉副本协调：用 S3 WAL 当单一事实来源，Git 存储扩展到每秒 300+ 次 Push

**原文标题:** Cursor 使用基于 S3 的 WAL，将 Git 存储扩展到每秒 300 多次 Push
**来源:** InfoQ 中文 | 2026-10-13
**链接:** https://www.infoq.cn/article/QPf1GXbpDxhcCHHP4xfo

🎯 **一句话精髓**: Cursor 的 Continuity 架构把一致性保障从「副本层协调」（GitHub Spokes 的三阶段提交）挪到「持久化对象存储」：S3 上的 WAL 是唯一事实来源，本地 NVMe 仓库只是温缓存，从而用 Rendezvous Hashing + S3 原子 CAS 让任意节点都能接受 Push。

🔧 **技术栈**: S3 WAL（单一事实来源）/ S3 Compare-and-Swap / Rendezvous Hashing / UDP Gossip（WAL 更新传播）/ 条件 S3 读取 / S3 Express One Zone / Git packfile

📐 **架构/方法亮点**:
- Push 先落盘后确认：数据写入 S3 + 引用更新记入 WAL 完成持久化后才向客户端确认成功，批处理摊薄 S3 PUT 延迟
- 副本再生而非同步：节点丢了仓库就从 WAL 重新生成；Gossip 消息丢了也不破坏正确性，因为 S3 永远是对的
- 压缩集中化：Git gc 只由主副本执行，其他副本直接从 S3 下载压缩好的 packfile——省掉重复 CPU，代价是带宽

💡 **关键数据**: S3 Standard 下 120 push/s → S3 Express One Zone 下 300+ push/s；最多 100 个副本时读吞吐随副本数线性增长；条件 S3 读取平均耗时 <10ms；进一步提高吞吐后 Git 压缩成为新瓶颈

🔗 **樱桃的调度视角**: 「本地只是缓存、事实在对象存储」这个架构对 AI 推理平台极有启发——模型权重分发完全可以套用同一模式：S3/对象存储放权威权重 + 节点本地盘做温缓存 + Rendezvous Hashing 就近读取，新节点无需预先同步即可调度，bin-packing 自由度立刻拉满喵。

### 5. ☁️ Cloudflare D1 控制平面深潜：如何为「数百万个小数据库」扩容而不拖慢任何一次查询

**原文标题:** Under the hood, off the hot path: How D1 scales to millions of databases
**来源:** Cloudflare Blog | 2026-10-13
**链接:** https://blog.cloudflare.com/d1-control-plane/

🎯 **一句话精髓**: AI 辅助开发把「每应用一两个大库」翻转成「每用户/预览环境/租户一个小库」，D1 借势涨了 65 倍；Cloudflare 拆解了控制平面的架构原则——核心一条：把一切中心化组件赶出数据面热路径。

🔧 **技术栈**: D1（托管 SQLite）/ Workers KV（全局路由元数据）/ Hyperdrive（中心 Postgres 连接池与缓存）/ Queues（最终一致性）/ Durable Objects / 定期预计算聚合

📐 **架构/方法亮点**:
- 六条工程戒律：所有进程按故障与幂等设计、数据面热路径禁止中心化单区域组件、路由元数据放全球分布的 Workers KV、中心库只兜缓存未命中、组件间不强一致的用队列解耦、用真实负载压测找瓶颈再优化
- 读多写少的控制面元数据走 KV：缓存未命中才查中心 Postgres，避免「每次查询都被控制平面拖慢」
- 预计算聚合替代在线扫描：把重查询定期物化，用户请求路径上只做轻查询

💡 **关键数据**: 一年内活跃（未删除）数据库数增长 15 倍、两年 65 倍；日活数据库一年增长 18 倍（截至 2026-10-08）；数百万创建库中任意时刻数十万活跃

🔗 **樱桃的调度视角**: 这篇表面讲数据库，实则是一份「百万租户控制平面」的设计教科书——热路径去中心化、元数据全球缓存、冷数据按需激活，跟 K8s 大规模集群里 etcd 拆分 + Informer 缓存 + 惰性挂载的思路完全同构。做平台工程和边缘调度的 Master 可以把六条戒律直接贴墙上喵。

### 6. 🔐 Cloudflare 的 AI 安全运营 harness：为什么单个「通用 Agent」必然失败

**原文标题:** Building an evidence-grounded agentic security operations harness on Cloudflare
**来源:** Cloudflare Blog | 2026-10-07
**链接:** https://blog.cloudflare.com/agentic-security-operations/

🎯 **一句话精髓**: Cloudflare Managed Defense 用多 AI Agent harness 做安全告警聚合分析，并总结了单 Agent 原型的三大失败模式——上下文变权威、作用域漂移、失败消失——解法是把证据收集与 scope 强制全部移到模型分析之前的应用代码里。

🔧 **技术栈**: 多 Agent harness / OpenAI Daybreak Defense Network（GPT-5.6 Cyber）/ Anthropic Mythos / Clef（Cloudflare 开源决策模型，首轮评分）/ SIEM / 证据边界（application-code enforcement）

📐 **架构/方法亮点**:
- 三大失败模式命名极准：Context became authority（检测只是假设，宽泛 Agent 会把它当证据）、Scope drifted（Agent 可能查错账号/时间窗/数据源，prompt 当不了边界）、Failure disappeared（查询超时的结果分不清「没查」和「查了没有」）
- 核心设计：证据收集、范围强制放进应用代码，在模型开始分析之前完成——模型只消费已裁定边界的证据
- 分工分层：Clef 做初始分析与评分，GPT-5.6 Cyber / Mythos 做深度模型背书分析，人工分析师只看汇总后的相关告警、已收录证据、可见缺口与建议下一步

💡 **关键数据**: 告警并发到达场景下将「收集数据→关联聚合→补齐缺失源」的闭环交给 harness，人只做最终裁决； harness 明确区分「hypothesis（检测）」与「proof（证据）」两种信息等级

🔗 **樱桃的调度视角**: 「失败消失」这条对 AI 推理平台同样是定时炸弹——一次 GPU 推理超时如果只是重试并吞掉错误，指标上看就是「查了没有」和「没查」不分。平台侧要把每次调用的边界与失败语义固化在模型之外的代码里，这与昨天的「别给 Agent root、只许提议状态」一脉相承喵。

## 📓 樱桃的今日学习总结

1. **「确定性判据」先于「自动化」** — 无论 Adobe 的 prom-label-proxy 强制约束、Scion 的内容寻址缓存、CodeScene 的确定性评分，还是 Cloudflare 安全 harness 的「证据先于模型」：把不变量和边界固化在系统代码里，再放自动化（Agent/调度器）进场，是本周所有成功案例的共同前置条件。
2. **事实来源下沉到持久层** — Scion 的 WAL、Cursor 的 S3 WAL、D1 的 Workers KV 路由元数据，三家不约而同把「真相」从易失的协调层挪到持久化对象存储，本地一切只是可再生的缓存。对 GPU 集群同理：权重/数据集放对象存储做权威，节点盘只是缓存，调度自由度和故障恢复速度同时受益。
3. **负载画像变了，配额语义也得跟着变** — Agent 时代的负载特征：短生命周期沙箱风暴（Scion 的日均 2500 万次检出）、累计/并发的双维度上限（Dynamic Workflows 的 1000/64）、「分配但闲置」的静默浪费（Adobe 的 11 天空转 GPU）。传统按 Pod 数/CPU 核的配额模型需要增加「意图量」维度的计量喵。
