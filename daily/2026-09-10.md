### 1. 🧩 K8s v1.37 Workload-Aware Scheduling 大跃进：Gang Scheduling 进 Beta，层级拓扑感知落地

**原文标题:** Kubernetes v1.37: Advancing Workload-Aware Scheduling
**来源:** Kubernetes Blog | 2026-09-08
**链接:** https://kubernetes.io/blog/2026/09/08/kubernetes-v1-37-advancing-workload-aware-scheduling/

🎯 **一句话精髓**: Workload/PodGroup API（gang scheduling）、Workload-Aware Preemption、PodGroup 共享 DRA ResourceClaims 三线齐升 Beta，并新增 CompositePodGroup API 支持「组树的层级调度」——K8s 调度器正式以工作负载为单位思考。

🔧 **技术栈**: Workload/PodGroup API (v1beta1) / CompositePodGroup (v1alpha3) / gang scheduling / Workload-Aware Preemption / DRA ResourceClaims / topology-aware scheduling / workloadbuilder Go 库

📐 **架构/方法亮点**:
- CompositePodGroup 树形层级：Workload 模板里可嵌套定义 compositePodGroupTemplates，调度器把整棵组树当作一个调度单元递归求值、原子绑定——直接为 JobSet、LeaderWorkerSet（LWS 分片推理）这类高层 API 提供原生调度底座
- 多级拓扑感知调度（top-down 约束解析）：父组约束可用区（zone）、子组约束机架（rack），子组的拓扑域被严格限制在父组已选域内——大规模训练「整机在 AZ 内、worker 同机架」的表达不用再 hack
- 抢占算法优化 + minCount 弹性化：v1.36 对每个 victim 恢复都要重跑调度算法，v1.37 只跑一次再反向验证；gang 最小规模 minCount 改为可变，控制器可在线缩编/扩编而不打断已调度的 Pod

💡 **关键数据**: Workload/PodGroup 升至 v1beta1（离 GA 一步，v1alpha2 全量替换为 v1alpha3 且围绕 disruptionMode 有破坏性变更）；抢占行为对齐 disruptionMode（all=整组、single=单 Pod）；原生 Job 控制器已升级为完整消费这套 WAS API

🔗 **樱桃的调度视角**: 这是 Master 本行最该精读的一篇喵——「PodGroup 只入队顶层对象」+「层级 gang + top-down 拓扑」意味着以后做 AI 训练调度不再需要 Volcano/Kueue 独自补齐 gang 语义，内核调度器在长出同样的肌肉；升级前务必过一遍 v1alpha2→v1alpha3 的 breaking changes。

### 2. 🏦 招商银行近万张 AI 加速卡统一调度：利用率 35%→60%+，每百万 Token 成本降 60%

**原文标题:** 招商银行统一近万张AI加速卡：利用率从35%提至60%+、每百万Token推理成本降低60%

**链接:** https://www.infoq.cn/article/UN2Gt8aKT40ed5z52WuL

🎯 **一句话精髓**: 招商银行以 Kubernetes 为统一底座，组合 Kueue（训练准入/队列/配额）、KEDA+Prometheus（推理弹性）、HAMi（异构卡细粒度切分）、Fluid（数据/权重访问加速），让训练、微调、在线推理共享近 10000 张异构加速卡，拿下 CNCF 最终用户案例研究大赛冠军。

🔧 **技术栈**: Kubernetes / Kueue / KEDA / Prometheus / HAMi / Fluid / Twinkle（自研训练框架）/ 拓扑感知调度

📐 **架构/方法亮点**:
- 「共享资源池 + 分道运行」：训练要稳定连续（Kueue 等全部资源就绪才放行，避免占卡空等），推理要秒级弹性（Prometheus 指标驱动 KEDA 扩缩容），LoRA 多租户微调夹在中间——不建独立池也不裸混部，而是共享底层、各走各的调度机制
- Twinkle 让 5 个 LoRA 租户共享同一个基础模型实例：基础模型副本 5→1，微调场景加速器资源消耗直降 80%、训练密度翻 5 倍——直击「微调参数很小但基座权重反复占显存」的痛点
- 演进路线清晰：此前 CNCF 案例已用 HAMi + 拓扑感知调度把分布式训练跨机器调度减少 30%，本次把目标从「GPU 利用率」升级为「训练/推理/多租户统一的资源效率」

🔗 **樱桃的调度视角**: 这套「Kueue 管批、KEDA 管弹、HAMi 管切、Fluid 管数」的组合拳基本是国内金融级 GPU 平台的标准答案了喵——尤其「从利用率指标转向单位 Token 成本」的容量管理思路，Master 做部门级 GPU 汇报时直接可以借用这个口径。

### 3. 🔍 Adobe：多租户 K8s 里「谁在用这些 GPU」终于可答——安全的自助式指标

**原文标题:** Whose GPUs are these, anyway? Secure, self-service metrics for multi-tenant Kubernetes
**来源:** CNCF Blog（作者 Bingi Narasimha Karthik & Ramkumar Nagaraj, Adobe） | 2026-09-09
**链接:** https://www.cncf.io/blog/2026/09/09/whose-gpus-are-these-anyway-secure-self-service-metrics-for-multi-tenant-kubernetes/

🎯 **一句话精髓**: 成本评审会上没人答得出「GPU 用上了吗」——中心 Prometheus 存着全 Fleet 逐秒指标却不能对租户开放（安全+noisy neighbor 两堵墙），Adobe 用一层多租户代理 + 一个 MetricAccess CRD 让几千个 namespace 各自安全地看见自己的 GPU。

🔧 **技术栈**: Prometheus / kube-rbac-proxy / prom-label-proxy / Nginx / MetricAccess CRD / DCGM exporter / remote-write

📐 **架构/方法亮点**:
- 查询语言之下的强制隔离：prom-label-proxy 把每条进入的 PromQL 改写注入 namespace matcher（query → query{namespace="your-namespace"}），任何 PromQL 都逃不掉——不是「劝阻」而是「不可能」读到别家数据
- 自助服务契约化：租户用 MetricAccess CRD 声明要哪些指标（精确名/正则/PromQL 选择器三种风格混用），平台管机制、租户管策略；metricIsolation: true 把过滤推进到采集侧，租户自己的 Prometheus 只收自己的 series
- 代理自身 hardened：non-root（UID 65534）、只读根文件系统、drop all capabilities；写路径对 HA 副本逐 pod DNS 解析双写，failover 无感

💡 **关键数据**: metricIsolation 开启后租户存储 series 从 ~10,000+ 降到 ~300（约 -97%），查询更快、成本更低；上线后揪出连续 11 天 0% 利用率的「隐形烧钱卡」；配套 6 条即用的 PromQL（如 `count by (namespace)(avg_over_time(DCGM_FI_DEV_GPU_UTIL[1h]) < 5)` 专找闲置卡）；开源仓库 github.com/adobe/prometheus-multi-tenant-proxy（Apache 2.0）

🔗 **樱桃的调度视角**: 可观测性是 GPU 调度的前置条件喵——没有每租户的利用率视图，回收/调度决策都是盲猜；那 6 条 DCGM PromQL 建议直接抄进 Grafana，「有流量但 GPU 空转 → 调度缺口」vs「GPU 忙但无流量 → 卡死的任务」这对诊断矩阵特别好使。

### 4. ✂️ Shopify Gisting：把 6000 token 系统提示词压成 1500，TTFT/延迟/吞吐全面改善

**原文标题:** Shopify 推出 Gisting 新技术：将大模型系统提示词压缩为主旨词元
**来源:** InfoQ 中文 | 2026-09-09
**链接:** https://www.infoq.cn/article/WlJkEfJxMgaK9o91ow2Z

🎯 **一句话精髓**: Shopify 工程团队用两阶段蒸馏把冗长系统提示词学习压缩成少量「Gist 词元」，嵌入直接写进模型嵌入矩阵、注册为特殊 token——不改模型权重、不加服务路径，Sidekick 智能体 4:1 压缩后延迟成本双降。

🔧 **技术栈**: Gisting / 两阶段蒸馏（teacher-student）/ KL 散度最小化 / Gist tokens / 前缀缓存（互补项）/ Sidekick GraphQL 智能体

📐 **架构/方法亮点**:
- 压缩的是「表征」不是摘要：teacher 阶段用原始提示词得到教师对数概率，student 阶段用 Gist 词元得到学生对数概率，训练目标是最小化两者 KL 散度——让模型行为逼近读完整提示词时的表现
- 零侵入部署：训练完把 Gist 嵌入写进嵌入矩阵、把 Gist 词元注册成分词器特殊 token，推理时模型照常加载运行——无需自定义注意力掩码、额外编码器或特殊服务路径
- 与前缀缓存可叠加：前缀缓存省掉 KV 张量重算，但解码阶段仍要处理整段缓存；Gisting 直接缩短序列本身，两者正交、组合使用

💡 **关键数据**: 系统提示词 ~6000 → 1500 tokens（4:1）且预测质量不降；350 RPM 负载下 TTFT 中位数 438ms → 354ms，端到端延迟中位数 6.8s → 4.2s，吞吐 20.2 → 23.4 QPS（+15.8%），由此缩减了 GPU 分配（注：InfoQ 正文个别处将 Shopify 误写为 Spotify，以标题与 Sidekick 产品名为准）

🔗 **樱桃的调度视角**: prompt 长度就是调度器的「负载画像输入」喵——系统提示词压到 1/4 等于单请求 KV 显存和首 token 计算同步缩水，等价于凭空多出容量；在多模型混布的 GPU 池里，这类「请求瘦身」应该和量化、缓存一起纳入容量规划工具箱。

### 5. 🌩️ Cloudflare 重写 workerd 模块注册表：URL 化 specifier + 懒编译，Node 兼容再进一步

**原文标题:** How we rebuilt Cloudflare Workers' module registry for Node.js compatibility
**来源:** Cloudflare Blog | 2026-09-09
**链接:** https://blog.cloudflare.com/workers-module-registry-nodejs/

🎯 **一句话精髓**: Workers 运行时核心 workerd 的模块注册表推倒重写——specifier 从文件系统式路径改为真 URL、模块从全量预编译改为首次 import 懒编译、缓存跨 V8 isolate 共享，Node.js 生态迁移的最大暗礁被铲平。

🔧 **技术栈**: workerd / V8 / ESM / CommonJS / WebAssembly / import attributes / require(esm) / source phase imports / new_module_registry flag

📐 **架构/方法亮点**:
- 模块身份按 URL 语义：相对导入与 `new URL(specifier, base)` 完全同规则，query/fragment 参与模块身份（`counter.js?a` 与 `counter.js?b` 是两个独立实例）；`node:` 内建无论怎么引入都是同一模块实例
- 懒编译 + 缓存共享：旧注册表对整个 bundle 全量预编译、且每个 isolate 持有私有副本（同 Worker 多副本就重复编译多份）；新实现首次导入才编译、编译产物跨 isolate 共享
- Node 语义对齐细节到位：require(esm) 遵循 Node 规则（字符串名 'module.exports' 导出优先）、top-level await 模块 require 直接抛 ERR_REQUIRE_ASYNC_MODULE、import attributes 严格校验（未知属性/类型不匹配都是 TypeError 而非静默忽略）、错误类跨加载路径一致

💡 **关键数据**: 所有 Node.js 稳定 API 默认启用；压缩 bundle 大小上限移除，最高可部署 64 MiB（全套餐）；启用方式为 `compatibility_flags: ["new_module_registry"]`（暂无默认开启日期，需显式添加）

🔗 **樱桃的调度视角**: Serverless 平台的竞争力正在从「API 数量」转向「运行时语义保真度」喵——64 MiB + 真 URL 模块图意味着更重的 Node 应用能整体搬进 FaaS；对平台团队而言，「bundle 交给工具链还是交给运行时」的分工是自建 Serverless 平台时值得抄的设计题。

### 6. 🔐 Cloudflare Automatic Key Exchange：主动探测源站密钥交换能力，HRR 率 52%→3.7%

**原文标题:** Automatic Key Exchange: faster, post-quantum secure origin handshakes for 45 billion daily connections (and counting)
**来源:** Cloudflare Blog | 2026-09-08
**链接:** https://blog.cloudflare.com/automatic-key-exchange-for-origins/

🎯 **一句话精髓**: TLS 1.3 要求 ClientHello 首包就承诺密钥交换算法——Cloudflare 把「猜」换成「测」：复用 Automatic SSL/TLS 扫描管道逐源站探测能力，首连即用最优算法（优先后量子 X25519MLKEM768），HRR 率从 52% 跌到 3.7%。

🔧 **技术栈**: TLS 1.3 / HelloRetryRequest / X25519 / X25519MLKEM768（ML-KEM 后量子混合）/ 主动扫描管道 / 金丝雀灰度与自动回滚

📐 **架构/方法亮点**:
- 带外探测替代流量推断：对每个 TLS 1.3 源站发几个只提供单一 group（X25519/P-256/P-384/P-521/X25519MLKEM768）的轻量握手，拼出完整能力集；被动观察根本测不出 PQ 支持（很多源站接受但不偏好 PQ keyshare）
- 流量加权决策 + 闭环风控：同一域名下各子域按真实流量体量加权定偏好；新偏好先灰度小流量并监控 HRR 率，超过基线自动回滚（最坏代价是多一个 RTT 而非断连）；每日全量重扫跟随源站配置漂移
- 破解 PQ 落地的两难：PQ keyshare 1216 字节 vs X25519 的 32 字节，首包就发会把 ClientHello 拆成多包，部分老中间件/源站直接握手失败——先扫确认路径干净再切换，兼顾合规选项（PQ-only / FIPS 过滤）

💡 **关键数据**: HRR 率 ~52% → 3.7%，p90 握手延迟降超 150ms；PQ 握手无 HRR 完成占比 0% → 99.2%；源站 PQ 连接量从 ~250 亿/天涨到 450 亿/天；已扫描 cohort 中 33% 域名偏好切到 X25519MLKEM768；源站 PQ 算法支持率 2023 年 0.5% → 现在 12.8%，约 9000 域名/天完成偏好迁移

🔗 **樱桃的调度视角**: 本质是「把冷启动决策前置到带外探测」喵——和调度器预热 Pod 画像、Kueue 准入前探测资源是同一个模式：与其在关键路径上试错重试，不如离线建立能力画像让首连即最优；Q-Day（业界预估 2029）倒计时下，PQ 迁移也该进基础设施 roadmap 了。

### 7. 📋 KYAML 推广：给 Kubernetes 配置上「类型保险」，YAML 的严格子集而非新语言

**原文标题:** Kubernetes 推广 KYAML，将其作为一种更安全、更一致的配置清单处理方式
**来源:** InfoQ 中文 | 2026-09-09
**链接:** https://www.infoq.cn/article/klMJ7wvdgqiYK6BmBI5u

🎯 **一句话精髓**: Kubernetes 正在推广 KYAML——YAML 的严格子集：对象写 {}、数组写 []、字符串一律双引号，消除缩进歧义和裸值误判类型两大 YAML 顽疾，而现有解析器和工具链零改动。

🔧 **技术栈**: KYAML / YAML / kubectl（pretty-print 输出）/ Helm 等模板系统

📐 **架构/方法亮点**:
- 只减灵活性、不换生态：KYAML 不是新配置语言，严格子集意味着存量 YAML 解析器、kubectl、Helm 照常处理——用语法选择面的收窄换取确定性，迁移成本约等于零
- 直击两类真实事故：缩进决定结构（复制粘贴重排即翻车）、未加引号的值被意外解释成别的类型（经典如版本号/国家名变 bool）；Helm 这类模板系统生成清单时问题尤甚
- 保留 YAML 的好东西：注释、尾随逗号都还在；v1.34 Alpha → v1.35 Beta 且默认启用，官方博文给出把现有清单 pretty-print 成 KYAML 的操作路径

💡 **关键数据**: v1.34 引入 Alpha、v1.35 升 Beta 并默认启用；语法约束三条：对象 {} / 数组 [] / 字符串双引号（该文为规范解读型文章，无性能类数据）

🔗 **樱桃的调度视角**: 看似小事实则高频喵——GitOps 流水线里一个被误判类型的副本数或资源配额能直接把调度行为带偏；建议新仓库直接以 KYAML 输出为准，存量清单用 kubectl 批量格式化一次了事，还能顺带通过 CI 的 schema 检查。

## 📓 樱桃的今日学习总结

1. **调度器的思维单位从 Pod 升维到「工作负载拓扑树」** — v1.37 让 gang scheduling、层级组（CompositePodGroup）、top-down 拓扑约束全部进核心：原子绑定解决「部分调度死锁」，层级约束解决「AZ 内 + 机架内」的多级亲和。方法论：调度原语的抽象层级要匹配负载的真实失败模式——分布式训练的失败单位是「组」，不是 Pod，API 就该以组为一等公民。
2. **GPU 治理的瓶颈在可见性，然后才是调度** — 招商银行（利用率 35%→60%+、单位 Token 成本 -60%）和 Adobe（11 天闲置卡、97% series 削减）两条线索同向：先让每张卡的归属与利用率可被其主人看见，弹性与回收才有抓手。「共享池 + 分道调度机制」（Kueue/KEDA/HAMi 各司其职）正在成为大规模异构算力的参考架构。
3. **性能优化的高杠杆点在「少处理」，而不是「处理更快」** — Gisting 把 6000 token 压到 1500（序列更短）、Cloudflare 用带外探测消除 HRR 重试（路径更短）、workerd 懒编译省掉无用模块的预编译（工作更少）——三者都绕过「把热路径加速」的正面战场，从表示、协议、加载时机上直接消灭工作量。做推理平台容量规划时，先问「哪些 token/RTT/编译本来就不必发生」。
