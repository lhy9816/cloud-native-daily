### 1. 📦 OpScale：把 LLM 伸缩单元从「模型实例」拆到「算子」级

**原文标题:** OpScale: Operator-level Provisioning and Autoscaling for LLM Serving
**来源:** arXiv cs.DC | 2026-08-13
**链接:** https://arxiv.org/abs/2608.13499

🎯 **一句话精髓**: 直面「LLM Serving 的弹性伸缩单元到底是什么」这个开放问题--整个模型做单体伸缩太粗，突发流量下不是违反 TTFT SLO 就是 GPU 大量闲置，OpScale 用算子级编排框架在 40 张 A100 上省下 36.3% 的 GPU 还保住了 SLO。

🔧 **技术栈**: LLM Serving / GPU 集群伸缩 / TTFT SLO / profiling / A100 / GB200 / 生产 trace

📐 **架构/方法亮点**:
- 特征刻画发现推理各算子间异质性显著（operator heterogeneity），算子级弹性是可行的伸缩原语，而非只能整副本粒度扩缩
- 四层编排框架：profiling（画像）-> provisioning（供给）-> placement（放置）-> runtime serving，专门对付细粒度带来的组合空间爆炸
- 用生产 trace 驱动评测，而非合成负载，结论对真实集群容量规划直接可迁移

💡 **关键数据**: 生产 trace 下最多少用 36.3% GPU、功耗降 28%；固定成本预算下吞吐 +44%（测试规模至 40×A100 与 24×GB200）

🔗 **樱桃的调度视角**: 这是对 K8s 调度器的「终极拷问」喵--当调度单元从 Pod（模型副本）细化到算子，HPA/Volcano gang scheduling/DRA 的抽象层级都要重新审视。Master 做推理集群容量规划时，「算子画像 -> 异构放置」这套方法论可以直接抄作业。

### 2. 📦 vToken：给 KV Cache 做显存「虚拟化 + 碎片整理」

**原文标题:** vToken: Token-Level Virtualization for Reclaimable KV Caches
**来源:** arXiv cs.DC | 2026-08-13
**链接:** https://arxiv.org/abs/2608.13263

🎯 **一句话精髓**: PagedAttention 的固定块管理挡住了 token 级 KV 淘汰算法的路（块内碎片不可回收），vToken 用一张 token-table 间接层把「逻辑 token 存活」与「物理 block 放置」解耦，再异步 repack 回收显存，vLLM 里每请求保留 KV 块直接减少 27.2%–72.3%。

🔧 **技术栈**: vLLM / PagedAttention / KV Cache 淘汰（H2O / Random / Scissorhands）/ CUDA Graph / 显存虚拟化

📐 **架构/方法亮点**:
- token-table indirection 维持稳定的逻辑 token 视图，物理回收通过异步 repacking 活 token 完成，不阻塞推理路径
- 完整保留 PagedAttention kernel 与 CUDA Graph 兼容性--不要求改底层算子，工程可落地性强
- 淘汰策略接入代码从 500+ 行降到 50 行以内，vToken 相当于给策略层提供了统一抽象

💡 **关键数据**: 每请求保留 KV 块减少 27.2%–72.3%；SLA 约束吞吐最高 +37%（1.37×）；受限 KV 预算下最大可行并发提升至 2×

🔗 **樱桃的调度视角**: 显存是 GPU 调度的核心资源维度，vToken 本质是给 HBM 做「内存虚拟化 + 碎片整理」，跟 DRA 里 memory-aware 的 GPU 显存细分分配思路同源喵。对 Master 来说：KV 块回收率翻倍 ≈ 同卡可塞的并发请求数翻倍，直接改写单卡成本模型。

### 3. 📦 TEMPO：MoE 专家负载均衡的「相图」--先预测胜负再上线

**原文标题:** TEMPO: Makespan-Aware Expert-Parallel Load Balancing Across Memory- and Compute-Bound Regimes
**来源:** arXiv cs.DC | 2026-08-13
**链接:** https://arxiv.org/abs/2608.13057

🎯 **一句话精髓**: 实测推翻了「专家耗时与 token 数线性相关」的隐含假设--低于 ~156–168 token 时 HBM 权重流加载占主导（成本挂在激活的专家副本上），高于时 grouped GEMM 按 128-tile 取整（拆专家反而增加填充计算）；TEMPO 把每 batch 的专家分发形式化为 NP-hard 的 fixed-charge makespan 问题，毫秒级离线求解后融合进 SGLang。

🔧 **技术栈**: MoE / Expert Parallelism / EPLB / METRO / SGLang / grouped GEMM / HBM 权重流 / Qwen3-235B / DeepSeek-V3

📐 **架构/方法亮点**:
- max-affine 代价模型 t=max(a+bG, c+βN) 同时刻画内存瓶颈与计算瓶颈两个 regime，热专家与冷专家可在同一 batch 内分属不同 regime
- 分发决策形式化为 fixed-charge makespan 问题并证明在两 GPU 全复制下已是 NP-hard，用毫秒级求解器跑在关键路径之外
- SGLang 集成跑在进程外，把分发与计数收集融合成一个 in-graph kernel；诚实地给出「相图」：能预测哪个模型受益、哪个模型只有机制开销

💡 **关键数据**: 混合 regime 区域最多赢 15.5%；Qwen3-235B 端到端吞吐 +4–6%、p99 延迟 -15.6%；DeepSeek-V3（通信主导，在赢区外）仅剩机制开销--上线前即可预测

🔗 **樱桃的调度视角**: 专家放置本质是应用层内嵌的「第二调度器」，它跟集群层的拓扑感知调度（哪张卡放哪个专家）深度耦合。TEMPO 的相图思路特别值得 Master 借鉴：任何调度优化先划「收益区域」，别在赢区外白折腾喵。

### 5. 📦 Kairos 自愈式升级流水线：PR 合并后 11 分钟、零人工完成 3 节点控制面升级

**原文标题:** Eleven minutes, zero humans: Building a self-healing Kubernetes upgrade pipeline on Kairos
**来源:** CNCF Blog | 2026-08-14
**链接:** https://www.cncf.io/blog/2026/08/14/eleven-minutes-zero-humans-building-a-self-healing-kubernetes-upgrade-pipeline-on-kairos/

🎯 **一句话精髓**: 作者用六个 CNCF 工具（Gitea → Renovate → Kyverno → Cosign → ArgoCD → kairos-operator）串出一条全自动化 OS/K8s 升级流水线：上游发新版镜像后，从 PR 合并到 3 节点控制面全部升级完成仅 11 分钟，etcd quorum 零中断，人工干预为零。

🔧 **技术栈**: Kairos Hadron（不可变 Linux）/ K3s HA / Cilium / OpenTofu / Gitea Actions / Renovate / Kyverno / Cosign / ArgoCD / A/B 分区

📐 **架构/方法亮点**:
- Kyverno 准入门禁：升级 CR 的 image 必须匹配 `quay.io/kairos/hadron:*` 白名单，在到达节点前拦截配置错误与 typosquatting 投毒
- Cosign 验证镜像签名要对照上游 GitHub Actions OIDC 身份--不仅验「是不是这个 tag」，而是验「是不是真 CI 产出的工件」
- Kairos 不原地补丁：新 OS 写入非活跃 A/B 分区后重启切换，回滚=重启旧分区；触发整个流程的只是 Renovate 开的一个两行 diff PR
- 踩坑分享：升级 spec 的 `concurrency: 0` 语义是「所有节点同时升级」而非串行，控制面三节点曾同时重启，etcd 存活纯属运气

💡 **关键数据**: 实际时间线 11:40:20 → 11:51:36（共 11 分钟）；324MB 镜像 25.5s 拉取完成；内核 7.0.10 → 7.1.0；工作负载中断 0 次

🔗 **樱桃的调度视角**: 节点升级本质是「节点级调度编排」--cordon → 升级 → 验证 rejoin → 下一台的串行节奏，跟调度器的优雅驱逐（drain）逻辑如出一辙喵。2026 年 CVE 密度下，控制面补丁的 MTTR 直接由这条流水线的自动化程度决定，Master 的集群值得复刻这套「签名验证 + 准入白名单 + GitOps」三件套。

### 7. 📦 Meshlib：把 L7 策略执行塞回应用进程，sidecar 消失而安全语义保留

**原文标题:** Meshlib: In-Process Policy Enforcement for Sidecar-less Service Meshes
**来源:** arXiv cs.DC | 2026-08-13
**链接:** https://arxiv.org/abs/2608.13107

🎯 **一句话精髓**: 基于 Cilium 控制面扩展的无 sidecar 服务网格：应用绑定的非侵入库在应用进程内执行 L7 安全策略，传输层身份与路由交给 Cilium 的 eBPF 数据面--去掉 sidecar 的延迟与资源开销，但不丢服务网格的安全语义。

🔧 **技术栈**: Cilium / eBPF / L7 策略执行 / Istio / Linkerd / TrainTicket 基准

📐 **架构/方法亮点**:
- 职责分离设计：进程内库管应用层策略，eBPF 管传输层身份与路由，两层协作替代 per-pod sidecar 代理
- 与未改造服务完全互操作，支持在存量集群中增量 adoption，不需要一次性迁移
- 在 TrainTicket 基准上对 37 个微服务执行 126 条安全策略做横向评测

💡 **关键数据**: 相比 Istio、Linkerd 与原生 Cilium，Meshlib 取得所有被测配置中最低的端到端延迟，资源开销与基线相当

🔗 **樱桃的调度视角**: 每个 Pod 少一个 proxy 容器，节点装箱密度和调度可容纳副本数就直接提升--这是 eBPF 给 K8s 资源效率最实在的红利喵。不过进程内库意味着语言生态绑定（每个语言都要 binding），选型时要看 Master 的服务语言矩阵支不支持。

## 📓 樱桃的今日学习总结

1. **调度粒度的三级裂变** - 今天三篇论文同时把 LLM 推理的调度单元往下拆：OpScale 拆到算子、vToken 拆到 Token、TEMPO 拆到专家。规律是：粒度每细化一级，资源利用率上限就抬高一截，但组合复杂度爆炸，所以三者都不约而同走「profiling 建模 + 求解器化决策」路线--未来调度器的核心竞争力是「会建模 + 会求解」，不再只是「会匹配」喵。
2. **信任正在从检查点变成连续属性** - Kairos（Cosign 签名 + Kyverno 准入白名单）和 Lightwell（全生命周期加密来源）异曲同工：安全不再是发布前的最后一道门，而是流水线每一环随身携带的属性。K8s 准入控制器是这类信任链在集群侧最自然的执行点。
3. **网关层正在长出「AI 感知」能力** - Azure AI Gateway 按 model 字段路由 + 工具/MCP 后端联邦，说明路由层的抽象对象正从 API 变成「模型 × 工具 × 身份」。这一层「AI 网关调度」会成为推理平台的新标准抽象，跟集群内调度器（KubeRay/Volcano）形成上下两级。
