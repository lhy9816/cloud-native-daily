### 1. 📦 将 Pod 作为 Worker 而非智能体：K8s 上重新思考 AI Agent 的部署单元

**原文标题:** Pods as Workers, Not Agents: Rethinking the Deployment Unit for AI Agents on Kubernetes
**来源:** InfoQ 中文（原文 CNCF Blog） | 2026-08-20
**链接:** https://www.infoq.cn/article/u2O9k3QiZkeIbqJ7GsPw

🎯 **一句话精髓**: Google kagent 项目提出将 Pod 降级为"执行 Worker"而非 AI 智能体的部署/身份/生命周期单元，引入 Agent Substrate 控制平面在 K8s 之上管理 Actor 的调度与迁移。

🔧 **技术栈**: Kubernetes / kagent / Agent Sandbox / Agent Substrate / WorkerPool / ActorTemplate

📐 **架构/方法亮点**:
- 引入 Agent Substrate 控制平面：WorkerPool 类比 NodePool、Worker 对应 Node、ActorTemplate 对应 Pod 声明式规范，Actor 在工作到来时调度到 Worker 上，可挂起/恢复/迁移
- 每个智能体不再独占 Pod：固定池内长期运行的 Pod 可支撑远超其容量的逻辑智能体，Pod 成为执行 worker 而非部署模型
- 身份标识从 Pod/Service 级迁移到 ActorTemplate/命名空间/租户级别，访问控制和网络策略需在模板级表达

💡 **关键数据**: 传统"每智能体一 Pod"模式为每个潜在 Agent 保留专用 Pod，造成资源浪费；Actor 模型允许一个 Worker Pod 承载多个逻辑 Agent

🔗 **樱桃的调度视角**: 这直接触及 Master 关注的 K8s 调度核心问题——当 AI 推理工作负载从"持续运行的服务"变为"短时突发的任务"，传统 Pod 调度粒度太粗。Agent Substrate 的 Actor/Worker 分离模式，与 Volcano 的 Job 级调度、Kueue 的排队思路异曲同工，未来 K8s 调度器可能需要原生支持 Actor 级别的弹性调度。

### 2. 📦 GPU 算力期货化：华尔街开始交易"未来的 H100"

**原文标题:** AI Infra 正在诞生自己的石油期货？GPU 不够买之后，华尔街开始交易算力
**来源:** InfoQ 中文 | 2026-08-20
**链接:** https://www.infoq.cn/article/qaWyth5P4tZE1CQhhaGq

🎯 **一句话精髓**: CFTC 就算力衍生品征求意见，CME Group 联合 Silicon Data 计划推出 H100/B200 GPU 租赁价格期货，AI 算力正从"有没有"走向"值多少"的商品化阶段。

🔧 **技术栈**: GPU 期货合约 / 永续算力期货 / GPU 远期价格曲线 / Silicon Data benchmark / CME Group

📐 **架构/方法亮点**:
- 标准化路径：GPU → 算力商品 → 价格指数 → 期货合约 → 金融资产，Silicon Data 扮演类似 Platts/Bloomberg 的价格基准角色
- 远期价格曲线覆盖未来 36 个月，市场已开始对"三年后的 H100 值多少钱"形成定价
- 核心难题：与石油不同，"一小时 H100 算力"包含 GPU × 网络 × 集群规模 × 可用率 × 软件栈 × 地理位置 × 时间，标准化极其困难

💡 **关键数据**: H100 现货约 $2.72/GPU·h，36 个月远期约 $2.38；B200 从 $5.62 降至 $5.17；A100 从 $1.65 降至 $1.40。三种 GPU 远期价格均低于现货，反映供应扩大预期。

🔗 **樱桃的调度视角**: 算力期货直接影响 GPU 调度策略——如果未来可以通过期货锁定 GPU 成本，K8s 上的 GPU 调度器需要考虑"算力合约到期"与"实际负载需求"之间的匹配，类似于 Volcano 的 Gang Scheduling 需要配合金融层面的算力预算管理。

### 5. 📦 用 OpenTelemetry 将慢查询变为可观测的可靠性指标

**原文标题:** How to turn slow queries into actionable reliability metrics with OpenTelemetry
**来源:** CNCF Blog | 2026-08-21
**链接:** https://www.cncf.io/blog/2026/08/21/how-to-turn-slow-queries-into-actionable-reliability-metrics-with-opentelemetry/

🎯 **一句话精髓**: 通过 OTel Collector 的 spanmetrics 连接器将数据库 Span 蒸馏为可告警的指标，三层渐进式分析从简单排序到流量加权再到异常检测。

🔧 **技术栈**: OpenTelemetry Collector / spanmetrics connector / TraceQL / Grafana Tempo / Loki / Mimir / docker-otel-lgtm

📐 **架构/方法亮点**:
- 三层渐进式仪表盘：按耗时排序 → 流量加权 Impact = Avg Duration × Count → 基于 baseline 的异常检测
- spanmetrics 连接器检查每个 DB Span 并生成延迟直方图，按 service_name / db_system / db_query_text 标签化
- 将异常检测从"当前是否慢"升级为"是否比正常慢"，区分已知行为与新问题

💡 **关键数据**: 示例中复杂报表查询 2.3s/5 次但搜索查询 150ms/10000 次——按平均耗时排序会误导，流量加权 Impact 揭示搜索查询对用户影响远大于罕见慢查询

🔗 **樱桃的调度视角**: spanmetrics 方法可直接应用于 K8s 上 AI 推理服务——将推理请求的 Trace Span 蒸馏为延迟指标，按模型版本/GPU 节点/Pod 分维度异常检测，能在调度层面快速发现"某个 GPU 节点上的推理突然变慢"。

**来源:** CNCF Blog | 2026-08-19
**链接:** https://www.cncf.io/blog/2026/08/19/kyverno-is-a-platform-primitive-not-a-security-tool/

🎯 **一句话精髓**: 资深实践者认为 Kyverno 被错误归类为"安全工具"，其 validate/mutate/generate/verify 四大能力中三个是建设性的，应被视为与 Pod、Service 同级的平台构建块。

🔧 **技术栈**: Kyverno / CEL (Common Expression Language) / Pod Security Standards / 策略驱动平台工程 / 准入控制

📐 **架构/方法亮点**:
- 四大能力中只有 validate 符合"安全门"模型，mutate（变更资源）、generate（生成新资源）、verify images（建立信任）三个动词都是建设性的
- 大多数组织只部署 validation 策略（阻断不安全配置），浪费了 75% 的能力
- 平台团队用 Kyverno 实现自助式平台：自动注入 sidecar、生成 NetworkPolicy、基于标签自动配置资源

💡 **关键数据**: 作者三年前首次 Kyverno 会议演讲标题是"Securing Your Kubernetes Workloads"，三年后全部转向治理、CEL 和平台自助服务

🔗 **樱桃的调度视角**: Kyverno 的 mutate/generate 能力可用于 AI 推理工作负载的自动化——比如基于模型标签自动注入 GPU 资源配额、生成 NodeAffinity 规则将大模型调度到有 NVLink 的节点，实现策略驱动的 GPU 调度。

🔗 **樱桃的调度视角**: Buildpacks 的 rebase 机制对 K8s 安全调度有直接价值——当新的 CVE 出现时，平台团队可以在构建器层一次性修补，配合 K8s 滚动更新策略快速替换所有受影响 Pod，而不需要每个应用团队各自修改 Dockerfile 重新构建。

## 📓 樱桃的今日学习总结

1. **AI Agent 的部署单元正在脱离 Pod 粒度** - kagent 的 Actor/Worker 分离模式表明，K8s 原生的 Pod/Service/ServiceAccount 抽象是为持续运行的微服务设计的，而 AI Agent 的短时突发、子 Agent 派生、等待审批暂停等行为需要新的生命周期抽象。调度器未来可能需要原生支持 Actor 级别的弹性调度，而非仅以 Pod 为最小单位。

2. **算力正在金融化，GPU 调度需要考虑"价格"维度** - 从 CFTC 征求意见到 CME 期货合约，GPU 算力的商品化将影响基础设施决策。K8s 上的 GPU 调度器可能需要扩展一个新维度：不仅考虑"哪个节点有 GPU"，还要考虑"当前算力期货价格"和"合约到期时间"，实现成本感知的调度策略。

3. **可观测性的"蒸馏"趋势** - OpenTelemetry 的 spanmetrics 连接器代表了一个重要趋势：不是收集更多遥测数据，而是从海量 Trace 中蒸馏出可操作的指标。对于 K8s 上的 AI 推理服务，这意味着可以将推理延迟、GPU 利用率、模型版本等维度从 Trace 自动转化为告警规则，无需人工设置阈值。
