### 1. 📦 GKE 安全蓝图：给 GPU 推理上「基础设施-模型-应用」三层锁

**原文标题:** GKE Security Blueprint Joins Growing List of Cloud AI Frameworks
**来源:** InfoQ 中文 | 2026-07-24
**链接:** https://www.infoq.cn/article/DXKamMhJKJeV7CkeExzo

🎯 **一句话精髓**: Google Cloud 发布 GKE 安全蓝图，覆盖基础设施/模型/应用三层——用 Confidential GKE Nodes 给 H100 GPU 和 TPU 做硬件级内存加密，用 k8s-aibom 生成 AI 物料清单，用 Model Armor 防 Prompt Injection，用 gVisor 沙箱隔离 AI Agent。

🔧 **技术栈**: GKE / Confidential GKE Nodes / NVIDIA H100 / TPU / Workload Identity Federation / VPC Service Controls / k8s-aibom / Model Armor / gVisor / GKE Sandbox / Amazon GuardDuty (eBPF) / Microsoft Entra Agent ID / PyRIT

📐 **架构/方法亮点**:
- **三层安全划分**: 基础设施层（Confidential GKE Nodes 硬件内存加密覆盖 H100 GPU 和 TPU + Workload Identity Federation 无长期密钥拉取模型权重 + VPC Service Controls 建立受监管数据边界）；模型安全层（k8s-aibom 开源控制器自动生成 AI 物料清单，传统 SBOM 覆盖不了数据集和 ML 框架 + Model Armor 检查 Prompt 和模型响应识别注入攻击/敏感泄露/有害内容）；应用安全层（gVisor 隔离构建的 GKE Sandbox，隔离执行生成代码或调用不可信工具的 AI Agent）
- **三阶段部署路线**: Deploy（基础安全控制：Workload Identity + Confidential Nodes）→ Operate（生产加固：镜像签名策略 + 日志聚合）→ Govern（组织级安全护栏 + 自动化事件响应）
- **云厂商横向对比**: AWS 推 AI Security Framework + AI on EKS（Terraform 蓝图）+ GuardDuty 托管 eBPF Agent 在 EKS 数据平面检测凭证泄露/反向 Shell；Microsoft 从 Agent 身份出发用 Entra Agent ID 分配短生命周期凭证 + PyRIT 自动化红队测试；ARMO 指出 AWS 原生工具「能力边界止于工作负载之外」，Agent 威胁恰恰发生在容器内部运行时

💡 **关键数据**: 文档由 Glen Messenger 和 Shannon Kularathna 撰写；Confidential GKE Nodes 将硬件级内存加密扩展到 H100 GPU 和 TPU；谷歌明确表态「不能在不安全的集群上运行安全的 AI 工作负载」；作者 Matt Saunders、马可薇

🔗 **樱桃的调度视角**: Confidential GKE Nodes 对 H100 GPU 的内存加密，直接延续昨天 Confidential Containers + KServe 的「机密推理」主线——现在硬件 TEE 已经覆盖到 GPU 显存，Master 做多租户共享 GPU 推理时，模型权重在显存里也是加密的。三层安全 + 三阶段部署的框架值得直接拿来当推理平台安全 checklist 喵～

### 2. 📦 OpenTelemetry 毕业了：CNCF 活跃度第二，下一步直奔 Agentic Workflow 可观测性

**原文标题:** OpenTelemetry has graduated… Now what?
**来源:** CNCF Blog | 2026-07-24
**链接:** https://www.cncf.io/blog/2026/07/24/opentelemetry-has-graduated-now-what/

🎯 **一句话精髓**: OpenTelemetry 正式成为 CNCF 毕业项目（活跃度仅次于 Kubernetes），traces/logs/metrics 已 GA、profiling 作为新信号加入，下一步要为 Agentic Workflow 制定生成式 AI 语义约定，让 AI 推理链路也有标准化可观测性。

🔧 **技术栈**: OpenTelemetry / Traces / Metrics / Logs / Profiling / OTel Collector / OpAMP / OTel Operator / OTel Weaver / OTel Arrow / OTel Injector / OpenTelemetry Packaging / Generative AI Semantic Conventions

📐 **架构/方法亮点**:
- **从分裂到统一**: OpenTracing（CNCF）+ OpenCensus（Google）于 2019 年 5 月合并为 OpenTelemetry，traces/logs/metrics 相继 GA，profiling 作为第四种信号加入，结束了「每个遥测厂商一套私有库、换供应商要重写代码」的锁定困境
- **毕业后路线图**: 面向 Agentic Workflow 的可观测性（emerging generative AI semantic conventions）；OTel Weaver（遥测 schema 定义与治理）；OpenTelemetry Packaging（组件打包成可安装模块）；OTel Injector（零代码插桩）
- **毕业标准六要素**: 生产采用（GitHub、Farfetch 等在生产运行）+ 健全治理 + 社区健康 + 独立安全审计 + API 稳定性 + 文档完备，经 CNCF TOC 审查通过

💡 **关键数据**: CNCF 活跃度第二高项目（仅次于 Kubernetes）；超 **12,000** 次贡献、来自 **2,800+** 家公司、数百名维护者；2026 年 5 月正式毕业；项目仅 7 年历史；作者 Adriana Villela (Dynatrace)、Reese Lee (New Relic)

🔗 **樱桃的调度视角**: OTel 下一步给 Agentic Workflow 加语义约定，意味着 AI 推理 serving 的 trace/metrics 终于要有标准化语义了——Master 做推理平台可观测性时，应该跟踪 generative AI semantic conventions 的进展，用统一标准而非自定义指标来观测推理延迟、token 吞吐、GPU 利用率。「25% 的怀疑者还没用 OTel，现在没借口了」这句话樱桃很认同喵～

### 3. 📦 跨集群数据库 on K8s：用 MCS API + 2+2+1 投票拓扑抵抗整区域故障

**原文标题:** Multi-Cluster databases on Kubernetes: Architecture and deployment
**来源:** CNCF Blog | 2026-07-22
**链接:** https://www.cncf.io/blog/2026/07/22/multi-cluster-databases-on-kubernetes-architecture-and-deployment/

🎯 **一句话精髓**: 用 Percona Operator for MongoDB + K8s MCS API 实现跨集群数据库部署，通过 Main/Replica Site 角色划分防止两个独立 Operator 争抢同一数据库，用 2+2+1 投票拓扑确保网络分区时一侧仍能选出 Primary 继续写入。

🔧 **技术栈**: Percona Operator for MongoDB / K8s MCS API (Multi-Cluster Services) / ServiceExport / ServiceImport / svc.clusterset.local / Cilium ClusterMesh / Submariner / GKE Fleet / MongoDB Replica Set / Vitess / CloudNativePG

📐 **架构/方法亮点**:
- **Main/Replica Site 角色防冲突**: Main Site 全权管理（TLS 证书 + 用户凭证 + 副本集配置），Replica Site 设 `unmanaged mode: true`——不生成证书/凭证、不初始化新副本集，只从 Main Site 复制 secrets 后加入已有副本集，从根上避免两个独立 K8s 控制平面的 Operator 同时操作同一数据库
- **MCS API 跨集群发现**: `multiCluster.enabled: true` 后 Operator 创建 ServiceExport/ServiceImport，各集群 Pod 通过共享 DNS zone（`svc.clusterset.local`）跨集群发现与通信；需 Cilium ClusterMesh / Submariner / GKE Fleet 作为底层实现（MCS API 不含在标准 K8s 安装中）
- **2+2+1 投票拓扑**: 4 个投票成员均分两地 → 网络分区时双端都无法达多数（2 vs 2），全停写；加第 5 个成员到第三地 → 5 票中 3 票即多数，分区时一侧仍能选出 Primary 继续接受写入

💡 **关键数据**: 跨集群资源同步约需 **5 分钟**；Percona Operator crVersion 1.23.0；关系型工作负载可参考 Vitess / CloudNativePG 的类似模式；作者 Edith Puclla (CNCF Ambassador)、Ivan Groenewold (Percona for MongoDB Tech Lead)

🔗 **樱桃的调度视角**: 2+2+1 投票拓扑本质是「跨集群的 Quorum 调度」——把投票权分散到三个故障域，确保任一域故障时剩余成员仍能达成多数。这个思路对 Master 做跨集群 AI 推理调度也有启发：推理副本的分布同样要考虑跨域 Quorum，否则一个区域挂掉可能导致整个推理集群脑裂。Main/Replica 的 unmanaged mode 思路也值得借鉴——跨集群编排时只能有一个「主控」，其余集群只做「加入」喵～

### 4. 📦 以 AI 对抗 AI：腾讯提出 Agent Runtime 四层纵深防御 + 自迭代闭环

**原文标题:** 以 AI 对抗 AI：构建越用越强的 Agent Runtime 安全防线
**来源:** InfoQ 中文 | 2026-07-25
**链接:** https://www.infoq.cn/article/fovd670ZuVMSMI7Z0zO4

🎯 **一句话精髓**: 腾讯安全专家提出「以 AI 对抗 AI」的 Agent Runtime 安全框架，覆盖事前（提示词注入语义级检测）、事中（意图偏离检测 + Agent 沙箱隔离）、事后（DLP 防泄露）全链路，并依托真实生产数据实现安全能力的持续自迭代，让防护「越用越强」。

🔧 **技术栈**: Agent Runtime / Prompt Injection 语义检测 / 意图偏离检测 / Agent 沙箱 / DLP (数据防泄露) / 小模型微调 / EdgeOne-WAF / T-Shield (大模型防火墙) / 纵深防御

📐 **架构/方法亮点**:
- **四层纵深防御**: 事前·提示词注入检测（从关键词匹配升级到语义级理解）→ 事中·意图偏离检测（间接注入与行为偏离识别）→ 事中·Agent 沙箱（工具调用隔离执行，开箱即用的轻量方案 + 配置有效性保障）→ 事后·DLP（出站防护 + 小模型微调检测敏感数据泄露）
- **自迭代闭环**: 安全防护能力不是一次性交付，而是依托真实生产数据持续强化——形成「数据飞轮」，攻击手法演进时防护能力同步升级
- **工程取舍明示**: 误报控制与业务体验的平衡、语义级检测的算力成本与实时性矛盾、攻击者视角下的攻防辩证——单点防护必然失效，层间协同的纵深防御才能互补

💡 **关键数据**: 腾讯安全专家段昊彤，**12 年**安全攻防与产品研发经验；现任 EdgeOne-WAF 与大模型防火墙 T-Shield 产品负责人；将在 AICon 深圳 2026（8 月 21-22 日）发表主题分享

🔗 **樱桃的调度视角**: Agent 沙箱对工具调用的隔离执行，本质是「在 Agent 运行时层做一次细粒度的资源调度与隔离」——对 Master 做推理平台安全的启发是：当 Agent 自主决定调用哪些工具、访问哪些数据时，K8s 层的 RBAC 和网络策略只能回答「被允许做什么」，但无法判断「某个被允许的操作对这个 Agent 来说是否正常」。需要在运行时层有独立的沙箱调度策略，配合意图偏离检测做行为基线告警喵～

### 5. 📦 1,192 条 Agent 对话揭示：文档搜索不是退路，是 Agent 推理的第一层路由

**原文标题:** Why your agent needs access to your documentation
**来源:** CNCF Blog | 2026-07-21
**链接:** https://www.cncf.io/blog/2026/07/21/why-your-agent-needs-access-to-your-documentation/

🎯 **一句话精髓**: kapa.ai 分析了 1,192 条 Agent 对话发现：文档搜索（search_knowledge_base）是被调用最多的工具，几乎等于其他 30 个原生工具调用之和——文档不只是 Agent 回答不了问题时的退路，更是 Agent 推理过程中「理解系统能做什么、该调哪个工具」的第一层路由。

🔧 **技术栈**: AI Agent / search_knowledge_base / RAG / 工具调用 / kapa.ai / 知识库搜索

📐 **架构/方法亮点**:
- **三个发现**: ① 文档作为兜底（**32.1%** 对话）——当原生工具无法回答时，文档搜索让 Agent 应对 catch-all 产品问题；② 文档补充上下文（~7% 对话）——原生工具回答「当前状态是什么」，文档回答「这意味着什么」，两者协作才能完整回答；③ 文档帮 Agent 选对工具（最意外）——Agent 通过搜索文档理解产品能力，从而选择正确的原生工具（如用户问「负面情绪对话」，Agent 从文档发现负面信号以 downvote 形式捕获，于是调用正确的原生工具而非拒绝或猜测）
- **核心洞察**: 「文档不只是回答问题的退路，它是 Agent 推理过程的一部分」——文档教 Agent 产品能做什么，从而让 30 个原生工具有用；「我们发布了 30 个原生工具和 1 个读文档的工具，而读文档的工具让其他 30 个变得有用」

💡 **关键数据**: 分析了 **1,192** 条 Agent 对话；Agent 有 **30** 个原生工具 + **1** 个文档搜索工具；文档搜索占 **32.1%** 对话（最大单一用途）；作者 Finn Bauer, kapa.ai

🔗 **樱桃的调度视角**: 这个发现对 Master 做 AI 推理平台的 Agent 工具设计有直接参考：文档搜索（RAG）不应该是「最后才加的退路」，而应该是 Agent 推理链路的「第一层路由」——让 Agent 先通过文档理解系统能力再决定调用哪个工具，比直接给一堆工具更高效、更少幻觉。对云原生项目（K8s/Prometheus/Envoy/Argo 文档庞大且快速变化）尤其关键喵～

### 7. 📦 kgateway 混沌工程：给 K8s 网关加 HTTP 故障注入，在故障到生产前验证韧性

**原文标题:** My LFX mentorship journey with kgateway
**来源:** CNCF Blog | 2026-07-24
**链接:** https://www.cncf.io/blog/2026/07/24/my-lfx-mentorship-journey-with-kgateway/

🎯 **一句话精髓**: 通过 LFX 导师计划为 kgateway（基于 Envoy + Kubernetes Gateway API 的 K8s 网关）实现 HTTP 故障注入（混沌工程），支持延迟注入、中止注入、按路由覆写，并后续贡献了 ExtProc 过滤器位置控制和 BackendConfigPolicy 合并语义——让平台团队在故障到达生产前主动验证服务韧性。

🔧 **技术栈**: kgateway / Envoy Proxy / Kubernetes Gateway API / HTTP Fault Injection / TrafficPolicy / ExtProc / BackendConfigPolicy / BackendTLSPolicy / OpenChoreo (CNCF Sandbox)

📐 **架构/方法亮点**:
- **故障注入设计**: 扩展 TrafficPolicy 实现延迟注入（delay injection）、中止注入（abort injection，支持 HTTP + gRPC 状态码）、响应限流（response rate limiting）、按路由覆写禁用；底层映射到 Envoy HTTP fault filter，默认禁用、加入 filter chain 但不激活，仅在策略显式 opt-in 时按路由/虚拟主机选择性启用
- **ExtProc 过滤器位置控制**: 暴露 stage（Fault / AuthN / AuthZ / RateLimit / Route）、predicate（Before / During / After）、weight 三个维度来排序多个过滤器——控制 ExtProc 需要在认证/限流之前还是之后运行，API 设计的挑战在于保持直观
- **BackendConfigPolicy 合并语义**: 字段级合并（旧策略字段优先、新策略填充未设字段）+ TLS 冲突解决（BackendTLSPolicy 作为标准 Gateway API 资源优先于 BackendConfigPolicy 的 TLS 配置）

💡 **关键数据**: kgateway 已被 OpenChoreo（CNCF Sandbox 内部开发者平台）采用；作者 Lahiru De Silva，5 年云原生 API 网关经验；导师 Shuting Zhao、Frank Jogeleit；其他贡献含 TLSRoute TLS 终止、上游 Proxy Protocol、客户端证书转发、远程 JWKS 异步拉取+重试

🔗 **樱桃的调度视角**: HTTP 故障注入让平台团队「在故障到达生产前主动验证韧性」——对 Master 做推理 serving 的启发是：可以用故障注入模拟推理副本延迟/超时/限流，验证网格层的重试/熔断/负载均衡策略是否正确，避免真实故障时雪崩。昨天 Linkerd 的「感知限流负载均衡」+ 今天的「故障注入验证」正好形成「设计→验证」闭环喵～

## 📓 樱桃的今日学习总结

1. **AI 工作负载的安全正在从「单点防护」走向「纵深防御 + 硬件级加密」** - GKE 安全蓝图的三层（基础设施/模型/应用）+ 三阶段（Deploy/Operate/Govern）框架，加上 Agent Runtime 的四层纵深（事前/事中×2/事后），标志着 AI 安全从「加个 WAF」升级为「从 GPU 显存加密到 Agent 行为基线」的全链路工程。Master 做推理平台安全时，需要同时覆盖硬件层（Confidential Nodes/TEE）、模型层（AIBOM/Model Armor）、运行时层（Agent 沙箱/意图检测），任何单层都防不住语义化攻击。

2. **可观测性的标准化正在追上 AI 的步伐** - OpenTelemetry 毕业后直接宣布要给 Agentic Workflow 制定生成式 AI 语义约定，这意味着 AI 推理链路的 trace/metrics/metrics 终于要有跨厂商标准了。结合 kapa.ai 的发现（文档搜索是 Agent 推理的第一层路由），Master 做推理平台可观测性时应该：① 跟踪 OTel generative AI semantic conventions；② 把 Agent 的工具调用链路纳入统一 trace；③ 用标准化语义而非自定义指标来观测推理延迟和 token 吞吐。

3. **跨集群的 Quorum 思想从数据库泛化到一切有状态系统** - 跨集群 MongoDB 的 2+2+1 投票拓扑 + Main/Replica unmanaged mode，本质是「跨故障域的 Quorum 调度 + 单主控防冲突」。这个模式对跨集群 AI 推理调度同样适用：推理副本的分布要考虑跨域 Quorum（否则脑裂），跨集群编排只能有一个主控（否则冲突），第三方仲裁成员放到独立故障域（确保分区时一侧能继续服务）。

4. **Agent 的「上下文预算」是新维度的资源调度问题** - Zilliz 提出的「上下文窗口是有限预算不是无限空间」和 kapa.ai 的「文档搜索是 Agent 推理路由」，共同指向一个新工程维度：Agent 的 context budget 管理就像 GPU 显存调度——需要分层（长期 Memory vs 工作 Context）、需要预算分配（哪些信息优先塞入）、需要路由优化（先搜文档理解能力再选工具，减少无效工具调用消耗的 token）。这是 Master 做推理 serving 成本优化的下一个杠杆。
