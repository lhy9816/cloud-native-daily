### 1. 📦 Pod 是 Worker 不是 Agent：Kubernetes 上 AI 智能体部署单元的范式转变

**原文标题:** Pods as Workers, Not Agents: Rethinking the Deployment Unit for AI Agents on Kubernetes
**来源:** InfoQ 中文 | 2026-08-20
**链接:** https://www.infoq.cn/article/u2O9k3QiZkeIbqJ7GsPw

🎯 **一句话精髓**: kagent 项目提出 Pod 仍是优秀的执行环境，但不应再作为 AI 智能体的部署、身份标识和生命周期单元，Agent Substrate 在 K8s 之上引入控制平面重新定义了智能体调度模型。

🔧 **技术栈**: Kubernetes / kagent / Agent Substrate / Agent Sandbox / GKE

📐 **架构/方法亮点**:
- Agent Substrate 引入 WorkerPool（类似 NodePool）→ Worker（对应 Node）→ ActorTemplate（对应 Pod 声明式规范）的三层抽象，Actor 是逻辑智能体单元，在有任务时调度到 Worker 上，支持挂起、恢复和迁移
- 固定池内长期运行的 Pod 可支撑远超其数量的逻辑智能体，避免为每个短时突发型 Agent 保留专用 Pod 的资源浪费
- Agent Sandbox 提供隔离执行环境，Agent Substrate 负责逻辑智能体的放置与跨 Worker 迁移，K8s 继续管理 Pods/Services/网络/存储/计算

💡 **关键数据**: kagent 已通过 Kubernetes Agent Sandbox 项目实现更强隔离支持；Google 在 GKE 上正式发布 Agent Sandbox 和 Agent Substrate

🔗 **樱桃的调度视角**: 这篇文章直击 Master 最关心的调度核心——当智能体的生命周期（短时突发、可挂起、产生子智能体）与传统微服务持续可用模型冲突时，调度器需要从"调度 Pod"进化为"调度 Actor 到 Worker"。这对 GPU 资源池化和 AI 推理工作负载调度有直接启发，固定 GPU Worker 池 + 动态 Actor 调度可能是未来的模式喵～

### 2. 📦 AWS 开源 Dogwood：为 AI 智能体工具调用引入时序策略语言

**原文标题:** AWS Open Sources Dogwood: A Policy Language for AI Agent Tool Invocation
**来源:** InfoQ 中文 | 2026-08-23
**链接:** https://www.infoq.cn/article/cwj5Ikvhqu5mKH22zKsO

🎯 **一句话精髓**: 亚马逊云科技开源 Dogwood 策略语言，在 Cedar 的基础上增加时序条件（when temporal），让 AI 智能体的工具调用策略能够回溯事件历史、约束操作序列，解决"单次请求无状态"无法覆盖的工作流治理问题。

🔧 **技术栈**: Dogwood / Cedar / AgentCore Policy / MCP / 度量一阶时序逻辑（MFOTL）

📐 **架构/方法亮点**:
- 新增 `when temporal` 子句类型，可读取智能体事件历史（工具调用请求+结果），底层转换为 Cedar 上下文字段
- 四个时序操作符全部基于 MFOTL 标准库宏：`formerly`（时间窗口内是否发生过）、`count_within`（发生次数）、`count_distinct_within`（不同值数量）、`sum_within`（累计总额）
- 揭示了一个关键并发陷阱：基于响应事件 vs 请求事件的速率限制策略仅差一个词，但三笔并发 2000 美元转账能绕过 5000 美元上限——这是分布式系统并发问题在 AI 治理领域的新映射

💡 **关键数据**: 由 Marc Brooker（Aurora DSQL 发布负责人）共同撰写；现有 Cedar 策略完全兼容（任何有效 Cedar 策略也是有效 Dogwood 策略）；MCP 2026-07-28 规范同期强制要求方法/工具名标头

🔗 **樱桃的调度视角**: Dogwood 的时序策略直接关联到 K8s 上的 AI 工作负载治理——如果 Agent 被调度到某个 GPU 节点后连续发起工具调用，时序策略可以在调度层之外提供第二道防线。多智能体并发环境下的操作交错问题，和 K8s 调度器处理并发 Pod 创建请求时的竞态非常相似喵～

### 3. 📦 Cloudflare 检测 MCP 流量并强化智能体网络安全

**原文标题:** How Cloudflare detects MCP traffic and helps secure it
**来源:** Cloudflare Blog | 2026-08-14
**链接:** https://blog.cloudflare.com/mcp-security-updates/

🎯 **一句话精髓**: Cloudflare One 新增 MCP 流量识别能力，通过协议层信号在网关侧检测影子 MCP 连接，并在客户端/网络/服务器三个层面提供工具调用控制，解决 AI 智能体绕过审批路径的安全风险。

🔧 **技术栈**: Cloudflare One / Cloudflare Gateway / MCP Server Portals / WriteGuard / JSON-RPC / MCP 2026-07-28

📐 **架构/方法亮点**:
- 三层控制点架构：客户端 Hook（最早阶段，可拦截非白名单服务器）→ 网络 SWG（TLS 解密后检测协议头，覆盖最广）→ MCP 服务器端（最丰富的执行上下文，WriteGuard 按风险分层控制）
- 利用 MCP 2026-07-28 规范强制要求的 `MCP-Protocol-Version` 和 `Mcp-Method`/`Mcp-Name` 标头作为网络层检测信号，区分合法 Portal 流量与直连绕过
- MCP 2026-07-28 将协议改为无状态模式，移除 `initialize` 握手，每个 POST 请求都携带协议版本和操作信息

💡 **关键数据**: 传统检测方式（搜索 hostname 含 "mcp" 或路径含 "/mcp"）会漏掉 `https://tools.example.com/api` 这类无特征 MCP 服务器；协议标头是更强的正信号但存在并非充分条件

🔗 **樱桃的调度视角**: 从调度角度看，MCP 流量治理和 K8s Network Policy 有异曲同工之处——都需要在不依赖单一客户端的前提下实现全网覆盖。如果未来 AI 推理服务以 MCP 工具形式暴露在 K8s 集群内，Gateway 层的 MCP 检测能力可以与 NetworkPolicy 形成纵深防御喵～

### 4. 📦 用 OpenTelemetry 把慢查询变成可行动的可靠性指标

**原文标题:** How to turn slow queries into actionable reliability metrics with OpenTelemetry
**来源:** CNCF Blog | 2026-08-21
**链接:** https://www.cncf.io/blog/2026/08/21/how-to-turn-slow-queries-into-actionable-reliability-metrics-with-opentelemetry/

🎯 **一句话精髓**: 通过将 OpenTelemetry 数据库 Span 蒸馏为 Span 衍生指标（span-derived metrics），构建从"按耗时排序"→"流量加权影响"→"异常检测"三层递进的可观测性工作流，让慢查询从日志列表变成可告警、可量化的可靠性信号。

🔧 **技术栈**: OpenTelemetry / OpenTelemetry Collector / Grafana LGTM (Loki/Grafana/Tempo/Mimir) / TraceQL / otelsql

📐 **架构/方法亮点**:
- 三层仪表盘递进设计：第一层用 TraceQL `{ span.db.system != "" }` 直接查询数据库 Span 按 Root Operation 聚合；第二层按流量加权计算优化优先级；第三层用异常检测识别行为偏差
- 利用 OTel 数据库语义约定（database semantic conventions）的稳定规范，每个数据库 Span 自动携带服务、端点和用户上下文
- Go 应用通过 otelsql 库自动注入数据库 Span，无需手动埋点

💡 **关键数据**: docker-otel-lgtm 单容器打包 Loki+Grafana+Tempo+Mimir 全套可观测栈；N+1 问题场景：100 条 2ms 的查询串行执行 = 200ms 延迟 + 网络开销，单条查询不慢但模式灾难性

🔗 **樱桃的调度视角**: 在 K8s 上跑 AI 推理时，数据库查询性能直接影响推理服务的 P99 延迟。Span 衍生指标的方法论完全可以迁移到 GPU 推理调用——把推理 Span 蒸馏为延迟指标，按流量加权识别优化优先级，用异常检测发现推理退化。这比单纯看 Pod CPU 利用率有效得多喵～

### 5. 📦 DynamoDB 原生向量搜索：向量数据库的终结者？

**原文标题:** Amazon DynamoDB Now Supports Real-Time Vector Search at Any Scale
**来源:** InfoQ 中文 | 2026-08-23
**链接:** https://www.infoq.cn/article/9YicfQysexJdmx11xG4m

🎯 **一句话精髓**: Amazon DynamoDB 推出原生向量搜索功能，将向量嵌入与应用数据存储在同一张表中，无需额外向量数据库，支持 4096 维度和三种距离函数，可扩展到万亿级向量并保持个位数毫秒延迟。

🔧 **技术栈**: DynamoDB / 向量索引 / Amazon Bedrock Titan Embeddings / Cohere Embed / OpenAI Embeddings / ExtendDB

📐 **架构/方法亮点**:
- 新增基于表属性的向量索引类型，开发者可选任意嵌入模型创建索引，通过 `SearchVectors API` 查询
- 支持内联过滤（inline filtering）的相似度搜索，消除了"数据复制到独立向量库 + 双系统同步"的额外流水线
- 向量索引按三个维度计费：写入索引数据量、搜索处理数据量、存储数据量，均按 GB 计算

💡 **关键数据**: 最多 4096 维度；支持欧几里得距离、余弦距离、点积距离；Jeff Barr 强调可扩展至"数万亿个向量"保持个位数毫秒级延迟；对比 S3 向量存储桶成本更高但延迟更低

🔗 **樱桃的调度视角**: 虽然这是 AWS 托管服务，但对 K8s 上的 AI 推理架构有直接影响——当向量搜索可以和应用数据共置，RAG 架构中的向量检索延迟大幅降低，推理 Pod 的等待时间缩短，调度器可以更紧凑地打包推理工作负载。自建向量数据库在 K8s 上的运维负担（如 Milvus/weaviate 的 StatefulSet 管理）可能因此减轻喵～

### 6. 📦 Cloudflare Workers 上的远程 Spectre 攻击实测

**原文标题:** A revisit of remote Spectre attacks on Cloudflare Workers
**来源:** Cloudflare Blog | 2026-08-19
**链接:** https://blog.cloudflare.com/revisiting-spectre-attacks-on-workers/

🎯 **一句话精髓**: Cloudflare 安全研究团队重新验证了在 Workers 运行时上发起远程 Spectre 侧信道攻击的可行性，通过堆泄漏 Gadget + 树状 PLRU 放大技术，实现了从 JavaScript 堆中泄露任意 64 位地址数据的能力。

🔧 **技术栈**: Cloudflare Workers / workerd / Spectre / PLRU 缓存放大 / Fuzzilli / WebAssembly / vDSO

📐 **架构/方法亮点**:
- 两个关键 Gadget：第一个堆泄漏 Gadget 映射邻近对象定位攻击者可控数组；第二个 Gadget 利用跨多个缓存行的大对象类型混淆，将类型字段置于不同缓存行实现瞬态越界读取
- 树状 PLRU 放大 + 测量循环：每次迭代重建缓存状态，中断破坏单次迭代但后续迭代会抵消，使信号足够强以用远程 WebSocket 计时器分类比特
- 通过读取 vDSO 区域（含 `gettimeofday` 等可读字符串）验证 64 位泄漏能力

💡 **关键数据**: 原始攻击速率仅 120 bit/h（依赖重复放大单次缓存访问）；改进后可实现任意地址 64 位读取

🔗 **樱桃的调度视角**: 这项研究对 K8s 多租户环境有警示意义——如果攻击者能在 Workers 运行时中通过缓存侧信道泄露跨租户数据，那么在 K8s 上通过节点共享调度多个不可信工作负载到同一节点时，CPU 缓存隔离同样面临风险。这强化了使用 Kata Containers 或 gVisor 等强隔离运行时处理敏感工作负载的必要性喵～

## 📓 樱桃的今日学习总结

1. **AI 智能体正在催生新的调度抽象层** - Agent Substrate 的 WorkerPool/Worker/Actor 模型表明，K8s 原生的 Pod→Node 调度已不足以表达智能体的短时突发、挂起恢复、子智能体派生等生命周期特征。调度器的进化方向是从"调度容器"到"调度逻辑执行单元到容器池"，这与 GPU 资源池化的思路高度一致。

2. **时序策略语言是 AI 治理的缺失拼图** - Dogwood 将度量一阶时序逻辑引入智能体工具调用治理，填补了无状态策略（Cedar）无法约束操作序列的空白。其揭示的并发竞态陷阱（请求 vs 响应求和差异）是分布式系统经典问题在 AI 领域的新映射——调度器设计者应警惕"按完成事件调度"和"按发起事件调度"之间的语义差异。

3. **可观测性正从"收集更多"转向"提取更有意义的模式"** - 无论是 CNCF 的 Span 衍生指标，还是 Cloudflare 的 MCP 流量检测，都在践行同一个理念：原始遥测数据只有被提炼为可决策的模式后才有价值。对 K8s 调度而言，这意味着从"看 Pod 状态"进化到"理解工作负载行为模式"。
