### 1. 📦 GPU 弹性伸缩的预测式控制器：用 Bi-LSTM 抢在流量洪峰前预热算力

**原文标题:** Scale before the spike: Predictive autoscaling for GPU workloads on Kubernetes
**来源:** CNCF Blog | 2026-08-28
**链接:** https://www.cncf.io/blog/2026/08/28/scale-before-the-spike-predictive-autoscaling-for-gpu-workloads-on-kubernetes/

🎯 **一句话精髓**: Adobe 工程师构建了一个 K8s 控制器，用 Bi-LSTM 模型分析过去 1 小时的 Prometheus 指标，提前 10 分钟预测 GPU 需求并预配容量，把「被动式 HPA」升级为「预测式弹性伸缩」。

🔧 **技术栈**: Bi-LSTM (TensorFlow Lite) / Prometheus / NVIDIA DCGM / HPA v2 / Go Controller / Kubernetes Deployment API

📐 **架构/方法亮点**:
- 三段式架构：Predict（Bi-LSTM 预测）→ Provision（预配 GPU 节点）→ Absorb（吸收流量），控制器每 60 秒运行一次推理，模型直接嵌入 Go 二进制文件
- 突发检测器（Burst Detector）作为安全网并行运行，基于预测值与实际值的滚动标准差自适应阈值，检测模型未学到的异常流量
- 渐进式缩容器（Graduated Scaler）限速 20 pods/min，防止「惊群效应」导致 etcd 抖动、调度器过载和镜像拉取风暴

💡 **关键数据**: 预测准确率 85%（±10% 范围内）；突发检测精度 9/10 实际峰值，2 次误报；500+ 小时影子模式验证；23/23 验证检查全部通过；GPU 节点启动比 CPU 慢 3-5 倍（固件加载/驱动初始化/CUDA 就绪）

🔗 **樱桃的调度视角**: 这篇文章直击 Master 关注的 GPU 调度痛点——GPU 节点启动延迟使得传统 HPA 在流量到达时才下单已经太晚。Bi-LSTM 预测 + 渐进式调度限速的思路，对 K8s 上 AI 推理服务的弹性伸缩非常有参考价值。关键启发是：不需要完美预测，只需要在 80% 的情况下比 HPA 快 10 分钟就够了。

### 2. 📦 在 K8s 上构建 AI 工厂：从裸金属到推理服务的全栈组装指南

**原文标题:** Building an AI factory on Kubernetes
**来源:** CNCF Blog | 2026-08-27
**链接:** https://www.cncf.io/blog/2026/08/27/building-an-ai-factory-on-kubernetes/

🎯 **一句话精髓**: 系统性地梳理了在 K8s 上构建「AI 工厂」的完整技术栈——从裸金属供应到多租户 GPU 隔离再到推理服务，核心论点是「瓶颈在利用率而非模型服务本身」。

🔧 **技术栈**: Metal3/Ironic / Cluster API / Argo CD / DRA (K8s 1.34 GA) / NVIDIA MIG / vCluster / HAMi / KAI Scheduler / Volcano / Kueue / vLLM / KServe / llm-d / Cilium / SR-IOV / RDMA

📐 **架构/方法亮点**:
- 全栈分层设计：硬件生命周期（Metal3/Ironic）→ 集群生命周期（Cluster API/Argo CD）→ 节点清单（NFD/GPU Operator）→ 租户隔离（vCluster + 沙箱运行时）→ GPU 分配（DRA/MIG/HAMi/时间片）→ 推理服务（vLLM/KServe/llm-d）
- 明确区分两种 GPU 利用率杀手：资源模型问题（device-plugin 独占整卡）和隔离模型问题（每团队专属集群/专属 GPU 段），DRA GA 在 K8s 1.34 让调度器感知 GPU 属性/内存/拓扑
- 多种调度器选择：KAI Scheduler（拓扑感知调度）、Volcano（批调度）、Kueue（队列管理），适配训练/推理/HPC 不同场景

💡 **关键数据**: SemiAnalysis ClusterMAX 以安全/网络/存储/可靠性/支持维度评估 GPU 云而非纯吞吐量；DRA 在 K8s 1.34 正式 GA；AI 工厂还集成 Slinky（SLURM on K8s）和 KubeVirt（租户虚拟机）

🔗 **樱桃的调度视角**: 这是 Master 应该收藏的一份架构参考图。文章把 AI 工厂定义为「组装问题」而非「新发明」——大多数组件是 K8s 原生或 CNCF 项目。对调度方向的启发是：GPU 利用率才是核心 KPI，DRA + MIG + HAMi 的组合可以让多个 Pod 共享一张 GPU，但真正的多租户安全隔离还需要 vCluster 或 DPU 级别保障。

### 3. 📦 你的 K8s 平台能跑容器了，但它准备好跑 AI 了吗？

**原文标题:** Your Kubernetes platform is ready for containers. Is it ready for AI?
**来源:** CNCF Blog | 2026-08-28
**链接:** https://www.cncf.io/blog/2026/08/28/your-kubernetes-platform-is-ready-for-containers-is-it-ready-for-ai/

🎯 **一句话精髓**: 指出「在 K8s 上跑 AI」和「K8s 平台为 AI 做好运维准备」是两件事，从资源模型、模型生命周期 CI/CD、调度拓扑三个维度提出了平台团队需要做出的转变。

🔧 **技术栈**: DRA (Dynamic Resource Allocation) / GitOps / KServe / Containerd / GPU Operator

📐 **架构/方法亮点**:
- 资源模型需超越 CPU/内存：AI 管线是异构的——数据预处理跑 CPU，推理用 GPU/加速器，单一工作负载可能依赖多种资源类型，DRA 提供声明式方式请求专用硬件
- CI/CD 需扩展到模型生命周期：模型不是镜像，模型有版本、有评测指标、有漂移检测需求，传统 CI/CD 管线需增加模型注册和模型质量门禁
- 调度需感知加速器类型与拓扑：平台团队需同时考虑加速器类型、可用性、拓扑和工作负载特征

💡 **关键数据**: CNCF 2025 年度调查显示 66% 托管生成式 AI 模型的组织使用 K8s 做推理，但仅 7% 每日部署 AI 模型；2025 State of AI in Platform Engineering 报告显示 35% 平台团队仍不编排 AI 工作负载

🔗 **樱桃的调度视角**: 66% vs 7% 的差距很说明问题——大家都在 K8s 上「跑」AI，但「持续运营」AI 的能力远未成熟。对 Master 来说，DRA 是需要重点关注的能力——它让调度器从「给 Pod 分一张 GPU」进化为「理解 GPU 的型号/显存/拓扑/ fractional 切分」。

### 4. 📦 Flux Mirror 插件：构建 Kubernetes 供应链的「单向二极管」

**原文标题:** Flux 推出 Mirror 插件：只让可信制品进入 Kubernetes 集群
**来源:** InfoQ 中文 | 2026-08-27
**链接:** https://www.infoq.cn/article/p8qELFuWcdBic11PXG72

🎯 **一句话精髓**: Flux CD 推出 Mirror CLI 插件，可声明式地在注册表间镜像容器镜像/Helm Chart/OCI 制品，并通过 Cosign 签名验证和「最短存续时间」策略构建供应链安全边界。

🔧 **技术栈**: Flux CD v2.9 / OCI Registry / Cosign / Helm / SBOM / GitHub Actions / Kubernetes CronJob

📐 **架构/方法亮点**:
- 「供应链二极管」概念：制品只能从上游流入私有注册表，通过身份策略 + 证明 + 最短存续时间三重防护，确保只镜像可信制品
- Cosign 签名验证 + SBOM + 构建来源信息一并传输，集群内 Flux 可重新检查证据；新签名制品会被暂缓，只有公开足够长时间后才镜像
- 支持多架构清单列表逐字节复制、HTTP Helm Chart 转 OCI 制品、正则/语义版本/前 N 项选择器管线，避免镜像不使用版本

💡 **关键数据**: Docker Hub 速率限制和 Bitnami 冻结免费镜像事件驱动了该工具的诞生；制品提交量较 2023 年增长约 7 倍

🔗 **樱桃的调度视角**: 虽然不是直接的调度话题，但供应链安全是 K8s 运维的基础。Mirror 插件的「最短存续时间」策略很有启发——对抗供应链投毒，新发布的制品即使签名合法也要等「冷静期」过后才被信任。对 Master 的集群安全策略设计有参考价值。

### 5. 📦 Cloudflare 如何用 5 次 Rust 优化省下 100TB 内存

**原文标题:** How we saved 100 terabytes of memory by optimizing 1.1.1.1's DNS cache
**来源:** Cloudflare Blog | 2026-08-27
**链接:** https://blog.cloudflare.com/dns-cache-memory-optimization-1111/

🎯 **一句话精髓**: Cloudflare 对 Big Pineapple DNS 平台的缓存条目结构进行了 5 次连续 Rust 内存优化，每条目内存减少 56%，全集群释放约 100TB 内存，同时插入吞吐量提升 43%、查询延迟下降 19%。

🔧 **技术栈**: Rust / Box<[T]> / Box<str> / 自定义 GlobalAlloc / DNS (EDNS Client Subnet) / Parquet

📐 **架构/方法亮点**:
- Vec→Box<[T]> 替换：DNS 响应缓存后不再修改，Vec 的 capacity 字段（8 字节/条）和预分配的堆空间完全浪费；Box<[T]> 去掉 capacity 字段和多余分配
- String→Box<str> 同理：去掉 String 的 capacity 开销，每条目有 8 个 Vec/String 字段，累计节省可观
- 自定义分配器封装 Rust System allocator 记录每次分配的字节数，用 56% A / 25% AAAA / 19% TXT 的生产流量分布做基准测试

💡 **关键数据**: 全集群存储 2500 亿条 DNS 缓存条目；每条目内存减少 56%；释放约 100TB（相当于 130 台 Gen 13 服务器内存）；插入吞吐量 +43%，查询延迟 -19%；每浪费 1 字节 = 全集群浪费 250GB

🔗 **樱桃的调度视角**: 这篇文章对 Master 的启发是系统层面的——「每浪费 1 字节 × 2500 亿条 = 250GB」这个算法展示了规模放大效应。在 K8s 中也是如此：每个 Pod 的 annotation 浪费、每个镜像层的冗余，在万级节点集群上会被放大到 TB 级。资源效率意识是调度的底层能力。

### 6. 📦 Qwen3.8-Flash MoE 架构：Token 消耗减少 75% 的推理经济学

**原文标题:** Token消耗减少75%，千问办公创造了新的"省钱模式"
**来源:** InfoQ 中文 | 2026-08-28
**链接:** https://www.infoq.cn/article/70zHFKxwRRGIjBO8EUtC

🎯 **一句话精髓**: 阿里千问发布 Qwen3.8-Flash 多模态 MoE 模型（125B 参数/每 Token 激活 6B），通过 GDN+Attention 混合架构和模型-Agent 双向协同，在保证质量前提下将办公 Agent 的 Token 消耗减少 75%、速度提升约 100%。

🔧 **技术栈**: MoE (Mixture of Experts) / GDN (Gated Delta Network) / Qwen Sparse Attention / N-gram Embedding / Agent Harness

📐 **架构/方法亮点**:
- GDN + Attention 混合架构：每 4 层中 3 层用 GDN 将历史信息压缩到固定大小状态，1 层保留全局 Attention 做精确检索——大幅降低长上下文的 KV Cache 访存成本
- Qwen Sparse Attention (QSA)：通过压缩式轻量 Indexer 在 micro-block 粒度上筛选重要上下文，GDN 负责压缩记忆，QSA 做粗筛找到最相关区域，避免每次全量重算
- 125B 总参数但每 Token 只激活 6B，另加 51B N-gram Embedding（存于 Host Memory 异步 Prefetch），实现「高智能密度」；Gated Residual 将单一残差流扩展为 4 条动态门控分支

💡 **关键数据**: Token 消耗平均减少 75%，速度提升约 100%；1M Token 上下文下 QSA 的 Attention Kernel 在 Prefill/Decode 阶段最高加速 7.6 倍/4.9 倍；Prefix Cache 90% 命中率下 Prefill 吞吐达 Qwen3.7-Plus 的 8.6 倍；输入 0.8 元/百万 Token，输出 2.7 元/百万 Token，缓存命中 0.1 元/百万 Token

🔗 **樱桃的调度视角**: 对 K8s 上 AI 推理服务来说，Token 成本和速度直接决定了 GPU 调度策略。Qwen3.8-Flash 的 MoE 架构意味着推理时实际 GPU 计算量远小于参数量——这对推理服务的 HPA 阈值设定和 GPU 显存规划有直接影响。GDN 压缩 KV Cache 的思路也适用于推理服务的并发度规划。

### 7. 📦 DuckDB v2.0 预览：从嵌入式分析引擎迈向分布式架构

**原文标题:** DuckDB v2.0 重磅预览：从嵌入式数据库迈向分布式架构
**来源:** InfoQ 中文 | 2026-08-28
**链接:** https://www.infoq.cn/article/9YLW3ZxLvrqxOVzSh9Y1

🎯 **一句话精髓**: DuckDB Labs 发布 v2.0 预览版「Cyanoptera」，引入原生客户端/服务器模式（quack 协议）、版本化 C API、VARIANT 类型和自定义扩展仓库，在不牺牲单二进制简洁性的前提下将运行范围扩展到分布式拓扑。

🔧 **技术栈**: quack 协议 / CONNECT SQL / MVCC / Parquet / PEG Parser / VARIANT 类型 / 异步 I/O (S3)

📐 **架构/方法亮点**:
- 原生 C/S 模式：通过 quack 协议和 CONNECT SQL 语句，任意 DuckDB 实例可作为守护进程通过网络接受连接，支持挂载远程 DuckDB 端点或 PostgreSQL/MySQL，通过下推优化路由查询
- 版本化 C API + 稳定 ABI：此前扩展需针对不稳定内部 C++ API 编译、每个版本重新构建；v2.0 引入 YAML 定义规范和 ABI 保证，一次构建多版本运行，支持加密固定自托管扩展仓库
- 自定义 PEG 语法解析器替代 PostgreSQL 衍生解析器，允许扩展注册自定义 SQL 语法；VARIANT 类型可自动检测半结构化模式并分解为列式表示

💡 **关键数据**: 自 v1.5 以来超 10000 次提交；正式版计划秋季发布；存储格式引入 ART 索引延迟列元数据加载和增量检查点空间回收

🔗 **樱桃的调度视角**: DuckDB 从嵌入式走向分布式是一个值得关注的基础设施演进。在 K8s 上，DuckDB 的 C/S 模式可以作为轻量级 OLAP 分析层嵌入 Pod，quack 协议的多连接事务隔离和 MVCC 也使其适合作为多租户分析服务的后端。对 Master 的数据平台选型有参考价值。

## 📓 樱桃的今日学习总结

1. **GPU 调度正在从「被动响应」走向「主动预判」** - Adobe 的预测式控制器证明：对 GPU 这种启动延迟 3-5 倍于 CPU 的资源，传统 HPA 的「等流量来了再扩容」已经不够用。Bi-LSTM + 突发检测 + 渐进式缩容的组合，在 85% 准确率下就能避免级联故障。核心启发是：预测不需要完美，只需要比反应快一个时间窗。

2. **AI 工厂是「组装问题」而非「新发明」** - CNCF 的 AI 工厂一文最有价值的是那张全栈分层表：从 Metal3 到 vLLM，每一层都有成熟工具。瓶颈不在任何单点，而在利用率——DRA/MIG/HAMi 解决资源模型问题，vCluster 解决隔离模型问题，KAI Scheduler/Volcano/Kueue 解决调度策略问题。Master 可以按这张表自检团队的 AI 工厂完整度。

3. **MoE 架构改变了推理资源规划的底层假设** - Qwen3.8-Flash 的 125B 参数/6B 激活意味着：模型大小不再等于推理计算量。这对 K8s GPU 调度有深远影响——推理服务的资源规划不能只看参数量，必须看活跃参数量。GDN 压缩 KV Cache 的思路也意味着长上下文服务的并发度可能比预期更高。
