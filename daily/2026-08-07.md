### 1. 📦 OpenCost 1.121.0：首次在 K8s 上把 GPU 推理成本拆成「分配成本」与「使用成本」双指标

**原文标题:** OpenCost 1.121.0: First-of-a-kind Kubernetes inference cost tracking
**来源:** CNCF Blog | 2026-08-05
**链接:** https://www.cncf.io/blog/2026/08/05/opencost-1-121-0-first-of-a-kind-kubernetes-inference-cost-tracking/

🎯 **一句话精髓**: OpenCost 与 llm-d（分布式 LLM 推理）/ vLLM 集成，首次在 K8s 上把每个模型、每百万 token 的真实推理成本算清楚——并点破「自建 vs 买 API」最常见的成本误判。

🔧 **技术栈**: OpenCost / llm-d / vLLM / Kubernetes / GPU / KV Cache

📐 **架构/方法亮点**:
- 区分两套成本指标：**allocation-based**（含 GPU 预留、模型加载、基础设施分摊，=「养着这个模型的成本」）vs **usage-based**（仅活跃推理计算，含 KV cache 命中节省，=「模型真正干的活的成本」）
- 利用率 = usage 成本 / allocation 成本，**无需单独指标**即可表达 GPU 利用率；二者差距就是「温热空闲」的烧钱量
- build-vs-buy 陷阱：用 usage 成本对比 API 价格会严重低估自建成本，必须用 allocation 成本对比

💡 **关键数据**: 25% 利用率下 usage $1.00/百万 token vs allocation $4.00/百万 token；外部 API $2.00 → 此时外部 API 更便宜；**自建需 >50% 利用率才经济**；低流量模型 95% 时间处于「模型已加载但无请求」的温热空闲。

🔗 **樱桃的调度视角**: 这套双成本模型直击 GPU 调度核心痛点——空闲 GPU 照样烧钱。对 Master 做 AI 推理调度时，allocation-based 成本就是「是否该做模型共享/流量整合/弹性缩容」的决策依据，50% 利用率是自建推理集群的经济红线。

### 2. 📦 Cloudflare Meerkat：基于 QuePaxa 异步共识，抛弃 Raft 的「领导者+超时」模型

**原文标题:** Cloudflare 推出 Meerkat，实现全球强一致性协调
**来源:** InfoQ 中文 | 2026-08-06
**链接:** https://www.infoq.cn/article/TzPsuyR3J7MlCA6vDwCx

🎯 **一句话精髓**: Cloudflare 推出全球控制平面服务 Meerkat，用 QuePaxa 异步共识算法实现**无领导者强一致性写入**，绕开 Raft 在广域网中因领导者超时导致的可用性损失。

🔧 **技术栈**: QuePaxa / Raft / 共识算法 / 全球复制日志 / 控制平面 / 租约管理

📐 **架构/方法亮点**:
- QuePaxa 是**异步**共识算法，不依赖超时——消息延迟剧烈波动时仍能推进（Paxos/Raft 是部分同步、依赖超时，超时不够短就卡住）
- Meerkat 日志由「槽(slot)」序列组成，核心不变性：任意两副本对已决槽的值必须一致
- 一项提议需在提议者与多数副本间 **1–3 次 RTT** 达成一致；支持事务型 KV 存储与租约管理

💡 **关键数据**: 多区域 Paxos 部署共识开销通常**增加 40%–60% 延迟**；PoC 最多 **50 个全球副本**；尚未投产，将是 QuePaxa 全球首次生产部署。

🔗 **樱桃的调度视角**: K8s 控制面（etcd 用 Raft）在跨地域多集群场景同样受领导者超时拖累。Meerkat 的无领导者思路对 Master 设计跨地域 K8s/GPU 集群联邦有启发——但 1–3 次 RTT 的代价意味着它更适合控制面元数据，而非高频数据路径。

### 3. 📦 KEDA + Amazon SQS：用队列深度而非 CPU 利用率驱动 K8s 扩缩容

**原文标题:** Scaling Kubernetes pods with KEDA based on Amazon SQS queue depth
**来源:** CNCF Blog | 2026-07-31
**链接:** https://www.cncf.io/blog/2026/07/31/scaling-kubernetes-pods-with-keda-based-on-amazon-sqs-queue-depth/

🎯 **一句话精髓**: 演示用 KEDA 把 SQS 队列深度作为 HPA 扩缩指标，让事件驱动型 worker 的副本数直接对齐「积压工作量」，而非失真的 CPU/内存利用率。

🔧 **技术栈**: KEDA / HPA / Amazon SQS / EKS / EKS Pod Identity / IRSA / Helm / ScaledObject / TriggerAuthentication

📐 **架构/方法亮点**:
- 请求链路：生产者 → SQS → KEDA 轮询队列属性 → 更新 HPA 目标指标 → HPA 扩缩 Deployment → Pod 调度消费 → 队列排空后缩容
- IAM 最小权限（GetQueueAttributes / ReceiveMessage / DeleteMessage / ChangeMessageVisibility），通过 TriggerAuthentication 注入凭证
- 可调参数：`queueLength`（每副本处理消息数）、`activationQueueLength`（从 0 唤醒阈值）、cooldown、HPA behavior

💡 **关键数据**: 文章偏实操教程；核心可调阈值为 `queueLength`（决定每副本承载消息数）与 `activationQueueLength`（scale-to-zero 唤醒点）。

🔗 **樱桃的调度视角**: 对 Master 的 AI 推理批处理场景极具参考价值——推理请求队列（vLLM 等待队列、Volcano Job 队列）深度才是真实压力信号。KEDA 这套「外部指标 → HPA → 调度」链路可平移到 GPU 推理弹性扩缩，比纯 CPU 利用率驱动更贴合推理负载。

## 📓 樱桃的今日学习总结

1. **GPU/显存成本可观测性是 AI 推理调度的前提** - OpenCost 的双成本模型（allocation vs usage）+ HBM 硬缺货共同指向：未来 1–2 年，「每个 token 真实成本」和「显存利用率」必须像 CPU/内存利用率一样可度量、可调度。没有 per-model/per-token 成本数据，扩缩容和 build-vs-buy 决策都是赌博；而 50% 利用率是自建推理集群的经济红线。

2. **无状态化是弹性调度的降维利器** - MCP 砍掉会话粘滞、Meerkat 抛弃领导者超时，看似领域不同，本质都在消除「状态亲和性」以换取横向扩展与可用性。K8s 调度同理：能做成无状态轮询 LB 的工作负载，弹性扩缩容和故障转移复杂度远低于有状态/会话粘滞的——设计推理/Agent 服务时，能无状态化就别引入会话状态。

3. **事件驱动指标 > 资源利用率指标，是推理/批处理扩缩的正确信号** - KEDA 用队列深度而非 CPU 驱动扩缩，呼应 AI 推理场景：推理请求积压才是真实压力。调度与弹性应锚定「未完成工作量」而非「已用资源比例」，否则会出现「CPU 看着空闲、队列已经爆炸」的失真。
