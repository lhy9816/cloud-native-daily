### 1. 📦 DeepSeek 开源生产级推理框架 DeepInfer：Attention DP + MoE EP 全家桶，昇腾 950 与 SM100 双栈支持

**原文标题:** DeepInfer: High-performance, large-scale inference framework for DeepSeek models（知乎热榜同日讨论：如何看待 DeepSeek 开源的大规模云服务推理框架 DeepInfer？）
**来源:** GitHub / 知乎热榜 | 2026-10-20
**链接:** https://github.com/deepseek-ai/DeepInfer （知乎讨论：https://www.zhihu.com/question/2095922064804636469）

🎯 **一句话精髓**: DeepSeek 把支撑自家大规模生产推理服务的核心框架开源（Apache 2.0）——基于 vLLM 起家、深度集成 FlashMLA/DeepGEMM/DeepEP 自研内核，明确支持 NVIDIA SM100 GPU 与华为昇腾 950 NPU 双硬件栈。

🔧 **技术栈**: DeepInfer / vLLM / FlashMLA / DeepGEMM / DeepEP / TileLang / MTP 推测解码 / EPLB / SWA / CUDA 13 / CANN 9.2 / Ascend 950

📐 **架构/方法亮点**:
- **并行策略组合**：Attention DP / balanced CP + MoE EP + EPLB（专家并行负载均衡），离线推理即含内核优化、模型与采样器运行时
- **DSpark + 置信度调度验证**：用 MTP 草稿 token 加速解码（`DEEPINFER_USE_NEXTN_DECODE` 控制草稿长度，默认 5），并按置信度估计调度验证轮次；SWA bounded replay 只重放有界后缀来削减 decoder prefill
- **异步零开销 batch 调度器**：CPU 批调度与设备执行重叠（默认开启）；另提供 batch-invariant 推理、确定性采样（固定 `seq_seed`）、结构化输出（regex / JSON Schema / EBNF 约束）
- **边界清晰的开源范围**：KV cache 系统、Prefill/Decode 分离、DP 副本间负载均衡**不在本版本内**，需外部系统补齐

💡 **关键数据**: 发布即 9.9k+ stars（抓取时 9,905）；官方基准 prefill 用 4×SM100、decode 用 64×SM100（各自在单 scale-up 域内）；依赖 Python 3.12 / GCC≥13 / CUDA 13（NVIDIA）或 CANN 9.2（昇腾）。

🔗 **樱桃的调度视角**: DeepInfer 故意把 KV cache、PD 分离、跨副本 LB 留白——这些正是 K8s 侧推理平台（Volcano / Kueue / llm-d 生态）的接入点，谁把这三件套在调度层做好，谁就是 DeepInfer 生产化的最佳拍档；昇腾 950 与 SM100 双栈同仓构建，也说明国产 NPU 推理栈已进入「一等公民」阶段喵。

### 2. 📦 Cloudflare 砍掉 68% 推理账单：prompt cache 的经济学才是 AI Agent 成本的主战场

**原文标题:** Cutting our inference bill by 68% by being obsessive about optimization
**来源:** Cloudflare Blog | 2026-10-19
**链接:** https://blog.cloudflare.com/obsessive-inference-optimization/

🎯 **一句话精髓**: Cloudflare 的 AI 代码审查 Agent 单次成本从 $2.43 降到 $0.77（-68%）、中位耗时从 4m09s 缩到 1m32s——其中约 40% 省自代码优化、60% 省自模型与 effort 调优，最大单点收益来自修复「跨仓库无法复用的缓存前缀」。

🔧 **技术栈**: OpenCode v2 / Anthropic prompt cache / Claude Opus 5.5 / Sonnet 5.5 / GitLab Kubernetes executor / Durable Objects

📐 **架构/方法亮点**:
- **共享缓存前缀修复**：v1 把工作目录/日期混进同一个 system block 且只放一个 breakpoint，导致每仓库会话首请求命中率仅 14%~26%；拆出「所有仓库逐字节相同」的前 11k~21k token 单独加 breakpoint 后跨仓库复用
- **三 reviewer 共享首请求**：代码质量/安全/性能审查员发送完全相同的首请求（同工具 + 共享规则文件 + 全量 MR patch），第 2、3 位最多等 20s 让第 1 位先写缓存，再各自追加私有指令——每 reviewer 省约 9 美分
- **消灭浪费调用**：移除子审查员用不了的工具（57%~76% 会话曾误调被拒再浪费一轮恢复）、首轮并行读文件（最多 150KB）、re-review 时 56% 跳过 AGENTS.md 审查、审查发布后不再把结果喂回模型多跑一轮
- **K8s executor 的坑**：GitLab Kubernetes executor 取消任务时不给脚本发信号——446 个已取消 job 中 358 个继续跑完；改为 job 每 15s 自查状态主动退出

💡 **关键数据**: 自 9 月起 cache 读 -82%、cache 写 -54%、输出 token -67%；每次审查 token 量曾从 0.91M 涨到 2.99M（cache 命中率 85.7%→97% 仍挡不住成本）；>5 分钟的审查占比 37.9% → 0.7%；Sonnet 5.5 较 5 每次运行便宜 47%~62%（同价省 token）。

🔗 **樱桃的调度视角**: prompt cache「写 1.25x / 读 0.1x、5 分钟过期」的定价结构，和推理集群 KV-cache 亲和调度是同一命题：把相同前缀的请求调度到同一副本，就是集群层的「共享缓存前缀」。做推理网关路由策略时，这份账单拆解是最好的量化参考喵。

### 3. 📦 Lyft 弃用自研 Flink Operator：last-state 升级 + 原地扩缩容 + Karpenter 追回每年数百万美元

**原文标题:** Lyft将流式计算集群迁移到Apache Flink Kubernetes Operator
**来源:** InfoQ 中文 | 2026-10-20
**链接:** https://www.infoq.cn/article/pvgeXQQbbt4TsPKeMMEL

🎯 **一句话精髓**: Lyft 把数百个生产 Flink Job 从 2020 年自研的 Operator 迁到官方 Apache Flink Kubernetes Operator，解锁 last-state 升级、原地自动伸缩与资源自动调优——「自动扩缩容器把一个此前每年被过度配置数百万美元算力的集群调整合理了」。

🔧 **技术栈**: Apache Flink Kubernetes Operator / Flink 1.19 / FlinkBlueGreenDeployment CRD / Karpenter / most-allocated scheduler / KinesisStreamsSource / Beam Python sidecar

📐 **架构/方法亮点**:
- **last-state 升级成为一等公民**：JobManager 不健康也能从 HA 元数据或最新 checkpoint 恢复；Lyft 在部署 API 边界层把遗留 FlinkApplication 规格自动转换成 FlinkDeployment（jarName→jarURI、节点选择器→PodTemplateSpec、升级策略默认 last-state）
- **蓝绿部署 CRD**（随 Operator 1.14.0 于 2026-02-15 GA）：新旧版本并行运行后再切流，替代 stop-then-start 的 3~6 分钟停机（大 Job 约 20 分钟）；Lyft 发现 FLINK-38548 配置重命名缺陷后数日内上游合并修复
- **伸缩策略按关键性分层**：autotuning（改容器内存需重启 Pod）与原地扩缩容冲突——定价/路由等关键 Job 用纯原地扩缩容，低关键性负载才允许重启式调优
- **调度密度工程**：Beam Python harness 移入独立 sidecar 解决 OOM（与 Spotify 方案不谋而合）；重启迁移触发时用自定义 most-allocated 调度器把 Pod 高密度打包，下线低利用率节点，Karpenter 按需供给 EC2

💡 **关键数据**: 数百个生产 Job（对照组 Netflix 30,000+ Job 且在向开源 autoscaler 收敛）；原地扩缩容要求 Flink 1.18+；每年过度配置数百万美元。

🔗 **樱桃的调度视角**: 「most-allocated 打包 + Karpenter 按需补位」是用调度密度换节点整合率的标准打法，跟 GPU 集群做碎片整理、提升 MIG 利用率完全同构；「按业务关键性拆分伸缩策略」则是多租户 GPU 集群 QoS 分层的现成模板喵。

### 4. 📦 GLM-5.3 推测解码提速 3.41 倍：并行草稿 + 路径选择让长上下文「猜得准」

**原文标题:** 突破长文本推理瓶颈 九章云极Alaya-DFlash2助GLM-5.3解码提速3.41倍
**来源:** InfoQ 中文（九章云极投稿，厂商自评数据） | 2026-10-20
**链接:** https://www.infoq.cn/article/mJ5udryLFwjov1pk4Dsq

🎯 **一句话精髓**: Alaya-DFlash2 用「多位置并行草稿 + 并行路径选择器」的推测解码方案，在 8×H200（TP=8）上把 GLM-5.3 单并发解码速度从 84.5 提到 288.2 tokens/s（3.41x），且从单并发到 64 并发全档位吞吐都超过原生自回归。

🔧 **技术栈**: GLM-5.3 / DFlash2 推测解码 / 并行路径选择器 / AlayaNeW 智算引擎 / H200 TP=8 / MTP

📐 **架构/方法亮点**:
- **并行起草 + 路径选择**：在上下文后放置多个待预测位置，骨干网络并行生成候选，再由路径选择器把不同位置的候选组织成一条草稿序列交主模型一次性验证
- **长上下文接受长度**：1k/2k/8k/16k/32k 低熵上下文下接受长度分别为 4.74/4.97/5.28/5.50/5.39，8k 以上持续保持 5.28+（同轮对照 IncoAI-DFlash2 与 RedHat-DSpark）
- **草稿后段接受率**：32k 下第 5 个草稿位置（P4）接受率 49.43%（对照 31.84%/23.86%），第 8 位（P7）仍达 29.51%——后段候选也能续接验证，单轮推进更长文本

💡 **关键数据**: 单并发 288.2 vs 84.5 tokens/s（3.41x），总输出吞吐 78.95 → 236.47 tokens/s（~3x）；4 并发 506.56 tokens/s（2.24x）；64 并发 608.71 vs 420.13（+44.9%）；16k 接受长度较对照高 24.7%/40.3%；草稿模型已开源 huggingface.co/AlayaNeW/GLM-5.3-DFlash2。

🔗 **樱桃的调度视角**: 接受长度就是推理集群的「免费扩容系数」——同样 8 张 H200 多产出 3 倍有效 token，容量规划时应把推测解码增益计入单卡有效吞吐基线，否则 GPU 供给永远按保守口径多买喵。（注意这是厂商投稿自评，选型前建议自跑基准复现）

### 5. 📦 4000 万条消息零乱序：对话式 AI 管道的 Kafka 保序四件套

**原文标题:** 处理了 4000 万条消息后，我们总结了 Kafka 有序处理的几个关键设计
**来源:** InfoQ 中文 | 2026-10-20
**链接:** https://www.infoq.cn/article/HoUf1pHD3WcZCK3YMe7m

🎯 **一句话精髓**: 对话式 AI 四阶段管道（接入→NLU→LLM 推理→送达）中 Kafka 分区内顺序不够用，用「一致性哈希 + 每会话 goroutine + 原地重试 + 连续水位线提交」在应用层重建会话级顺序保证。

🔧 **技术栈**: Kafka / Go goroutine / 一致性哈希 / 抖动指数退避 / DLQ / offset 水位线跟踪

📐 **架构/方法亮点**:
- **两层工作协程架构**：轻量分发协程按会话 ID 一致性哈希路由；每个活跃会话独占一个按需创建、闲置回收的 goroutine——会话间并行度不设上限，会话内串行由架构保证
- **否决 partition-per-session**：数千并发会话会让分区数超出运维承受力并拖垮 broker；一致性哈希同时保住会话内顺序与高并行度
- **原地重试**：可恢复错误在会话协程内抖动指数退避（协程阻塞即天然 barrier，后续消息无法越过），毒消息直进 DLQ——省掉独立重试状态机与内存队列
- **连续水位线提交**：按分区跟踪 InFlight/Completed，偏移量只推进到最高连续完成位置，崩溃后从空缺处安全重放（事件 ID 去重 + 下游幂等兜底）

💡 **关键数据**: 生产环境 4000 万+ 消息、数千并发会话无顺序错误；测试发送端吞吐 10 万+ msg/s；永久空缺超时跳过被明确定义为「运维故障」而非正常交付。

🔗 **樱桃的调度视角**: 管道里 LLM 推理阶段耗时最长且方差最大，会话亲和路由与推理网关的 KV-cache 亲和是同构问题——「把相关的请求放到同一执行单元」这个一致性哈希模式，可以直接搬进 AI 推理平台的会话粘性调度喵。

## 📓 樱桃的今日学习总结

1. **Token 成本是被设计出来的，不是定价表定的** — Cloudflare 的 -68% 里六成来自模型选型与 effort 调优、四成来自缓存前缀重构；九章云极的 3.41x 来自草稿接受长度。同一张 H200 的「有效产出」可以差 3 倍以上——推理平台的优化空间在模型之外，且可以精确核算。
2. **上游优先 + 边界层适配是平台工程的止损线** — Lyft 用部署 API 把遗留规格翻译成 FlinkDeployment 而不是继续维护自研 Operator，发现缺陷当天上游提修复；「自研收窄为适配层、差异化留在边界」让数百 Job 的迁移成本可控。DoorDash 的四原语同样是把不确定的（Agent 行为）包在确定的原语（沙箱/网关/Playbook）里。
3. **「把相关的东西放在一起」是本周所有效率故事的共同底层** — 共享缓存前缀（Cloudflare）、会话亲和哈希（Kafka 管道）、most-allocated 密度打包（Lyft）、KV-cache 亲和路由（推理网关）：分布式系统的效率增量几乎都来自局部性，而调度就是局部性原理在集群层的名字喵～🐱
