### 1. 🧠 华为 OceanStor M900：给 KV Cache 盖一座「记忆银行」

**原文标题:** 显存不够、内存太贵，KV Cache越堆越大：华为给出自己的新解法
**来源:** InfoQ 中文 | 2026-09-24
**链接:** https://www.infoq.cn/article/LtHFz94fa1W1DQjNvHVb

🎯 **一句话精髓**: 华为发布 OceanStor M900「AI 记忆存储」，在显存/内存/本地 SSD 三级缓存之外新增 L3.5 层，把 KV Cache 从计算节点内的临时资源升维为集群级可共享、可持久化、可复用的数据资产，单集群 64PB。

🔧 **技术栈**: OceanStor M900 / KV Cache / L3.5 记忆层 / Mooncake / UCM 统一缓存管理器 / 灵衢 (UnifiedBus) / 昇腾超节点 / 三芯合一架构

📐 **架构/方法亮点**:
- KV 语义「一跳直通」：KV 不再先转成文件/对象再解析回来，直接按 KV 语义访问——传统 PCIe+RoCE 架构 NPU 访问 SSD 池要 5 次数据搬运，M900 压到 1 次
- 重写 SSD 寿命模型：KV 高频覆写场景下普通企业盘 DWPD 1~1.5 次根本不够，华为从介质/芯片/控制软件三层优化，实测寿命能力提升接近 16 倍
- KV 调度与分层预取：基于 Mooncake 框架预判后续会用哪些 KV，按显存/内存/SSD 介质性能分层预取；UCM 统一管理 KV Cache 库/知识库/记忆库（对应短期上下文/专业知识/长期经验）

💡 **关键数据**: 单集群 64PB；单 NPU 可用 KV 容量从 GB 级升到 TB 级；Token 命中率提升约一倍；I/O 时延与首 Token 时延（TTFT）降低超 50%；访问时延 10~15 微秒、带宽 40GB/s；KV 生命周期从小时级延长到周级

🔗 **樱桃的调度视角**: KV Cache 正在变成 CPU/内存/GPU 之外的「第四类调度资源」喵——调度器迟早要感知 KV 亲和性：会话粘住同一推理实例、prefill 复用绑定 KV 所在的超节点，本质就是数据本地性调度在 AI 时代的翻版～

### 2. 📏 arXiv KVSET：给 KV Cache 做在线「工作集」容量规划

**原文标题:** The KV Cache Working Set: Online Capacity Planning for LLM Inference Systems
**来源:** arXiv cs.DC | 2026-09-23
**链接:** https://arxiv.org/abs/2609.27746

🎯 **一句话精髓**: KVSET 用 Mattson 栈算法在线估算 LLM 推理负载的「KV Cache 工作集」——即达到目标命中率所需的最小缓存容量，一次扫描覆盖所有候选容量，让 prefix caching 的容量规划从拍脑袋变成可计算的。

🔧 **技术栈**: KV Cache / Prefix Caching / Mattson 栈算法 / LRU 栈距离 / LLM 推理容量规划 / agentic 工作负载

📐 **架构/方法亮点**:
- 核心定义「KV Cache 工作集」：保住目标命中率的最小缓存容量——容量给少命中率崩、给多白花 HBM 的钱，这是 prefix caching 落地时最痛的定价问题
- Mattson 栈距离的妙用：对每个 KV 页计算 LRU 栈距离，与各候选容量的页数直接比较，就能判定该页在每个容量下是命中还是逐出，无需逐容量独立仿真
- 最小容量直接由「达到目标命中率所需前缀页的最大 LRU 深度」反推，把在线工作集分析从离线仿真变成实时可行的分析器

💡 **关键数据**: agentic 负载反复携带持续增长的对话与工具调用历史，是 prefix caching 收益最大、也最难规划的场景；KVSET 相比传统逐容量仿真大幅降低计算与内存开销，使在线分析实用化

🔗 **樱桃的调度视角**: 这就是推理服务版的理论「资源画像」喵——工作集大小可以直接换算成 GPU HBM 的 request 值，「命中率 ≥95%」从此变成调度器可执行的数字契约，做 VPA/队列容量规划时值得把这篇的方法搬进 metric 采集链路～

### 3. 🔀 arXiv Crossflow：P/D 分离池的「可撤销租约」弹性边界

**原文标题:** Crossflow: Prefill-Decode Elasticity for Agentic LLM Serving
**来源:** arXiv | 2026-09-22
**链接:** https://arxiv.org/abs/2609.27085

🎯 **一句话精髓**: P/D 分离的静态池划分在 agentic 流量下严重失配（未缓存输入/输出 token 比值分钟级峰均 4.7x、日内小时级中位跨度 24.5x），Crossflow 用「短生命周期可撤销租约」让 decode 节点临时承接 prefill，不改节点角色吞吐提升 16.2~17.4%。

🔧 **技术栈**: Prefill-Decode 分离 (P/D disaggregation) / 弹性调度 / 可撤销租约 (revocable lease) / KV Transfer / agentic trace 分析

📐 **架构/方法亮点**:
- 问题量化很扎实：重分配一个副本要几十分钟，追不上分钟级的负载波动；按 95 分位给两池分别定容最多 17% 集群容量闲置，低于 95 分位则把失衡变成排队和吞吐损失
- 设计核心：每个 decode 节点发布短生命周期、可撤销的租约，明确框定本地可承接的 prefill 算力、KV 容量、迁移工作量与预计输出——「超卖但有界」，且完全不动节点角色
- 收益全面：对静态 P/D 的 token 吞吐几何均值 +16.2~17.4%，高载下最高 +43.4%，且所有评估点的平均 TTFT 都更低

💡 **关键数据**: 分钟级峰均比 4.7x；公开 agentic trace 日内小时级比值中位跨度 24.5x；95 分位定容浪费 17% 容量；吞吐几何均值 +16.2~17.4%、峰值 +43.4%

🔗 **樱桃的调度视角**: 本质是「带承诺边界的资源超卖」喵——和 K8s 弹性 Quota、DEScheduler 重平衡的思想同源但走得更远：资源声明自带可撤销语义，跨池借力不换角色。Gateway API Inference extension 的 InferencePool 分池调度正缺这样一套弹性协议～

### 4. 🎯 arXiv SARA：用排队论给分离式 Agentic LLM 服务立 SLO

**原文标题:** SARA: SLO-Aware Resource Allocation for Disaggregated Agentic LLM Services
**来源:** arXiv | 2026-09-22
**链接:** https://arxiv.org/abs/2609.26763

🎯 **一句话精髓**: 把 P/D 分离服务的三个阶段分别建模为 prefill=M/G/k 队列、KV 传输=M/G/1 队列、decode=广义生灭过程，推导出各阶段 SLO 的尾部行为，在部署成本约束下最大化 goodput。

🔧 **技术栈**: 排队论 / M/G/k、M/G/1、生灭过程 / 分位数 SLO 约束 / goodput 优化 / P/D 分离 / HBM 资源建模

📐 **架构/方法亮点**:
- 关键分析结论：prefill 阶段瓶颈在计算容量，decode 阶段瓶颈在 HBM——两个阶段的资源配置从此可以异构配比，而不是一刀切
- 把工作负载特征、模型架构、硬件参数显式映射为分阶段 SLO 约束与最小资源需求，轻尾/重尾工作负载分别推导出可解的尾部行为公式
- 在「成本预算 + 一组分位数 SLO 约束」的框架下求 goodput 最大化的资源分配，取代硬件 profiling 和配置枚举这类暴力搜索

💡 **关键数据**: 仿真与硬件实验结果验证了该框架能准确预测各阶段行为（摘要内未给出具体百分比数字，樱桃不编造，细节请看原文）

🔗 **樱桃的调度视角**: 这篇是把「调度器里拍脑袋的 SLO」变成解析公式的尝试喵——落地启示：给推理服务配 requests/limits 时，prefill/decode 的瓶颈资源根本不同，分阶段建模再决定节点池配比，比全局均匀分配省钱得多～

### 6. 🔐 Cloudflare 披露 Containers 跨租户数据残留漏洞：dm-thin 未清零块的锅

**原文标题:** How Cloudflare addressed a cross-tenant data exposure vulnerability in Containers
**来源:** Cloudflare Blog | 2026-09-24
**链接:** https://blog.cloudflare.com/containers-cross-tenant-vulnerability/

🎯 **一句话精髓**: 安全研究员利用 dm-thin 精简置备 + skip_block_zeroing 的组合，在新容器的 64KiB 块里读出了上一个租户容器残留的数据——4KiB 小块写入只覆盖块的 1/16，剩下 60KiB 还是别人的。

🔧 **技术栈**: Cloudflare Containers / Cloudflare Sandboxes / Firecracker microVM / dm-thin 精简置备 / ext4 metadata_csum / skip_block_zeroing / 数据残留 (data remanence)

📐 **架构/方法亮点**:
- 根因链清晰：容器根盘走 Firecracker + dm-thin，物理块在多租户间回收复用；开启 skip_block_zeroing 后新分配的块不清零，4KiB 写进未映射的 64KiB 块只覆盖局部，其余部分保留前租户数据（读未映射区域返回全零，但写过之后读回就能看到残留）
- PoC 利用 ext4 目录块校验和（metadata_csum 会混合文件系统与 inode 信息）区分「自己测试文件系统的块」和「外来块」：6 个生产 placement 上 5,614 个可测目录块中 0 个属于自己，识别出 2,700 个外来目录 inode
- 影响面：四大洲 24 个 placement 中 18 个、22 台底层节点中 20 台存在残留，恢复物包括目录结构、数据库页乃至结构完整的 SQLite 数据库；已在整个 Containers 舰队修复，客户无需改动，遥测中未见恶意利用

💡 **关键数据**: 64KiB thin-block 尺寸；2,700 个外来目录 inode；18/24 placement；20/22 底层节点；4 大洲；2026-09-04 责任披露，已全量修复

🔗 **樱桃的调度视角**: 多租户隔离不能只指望 cgroup/namespace，存储块分配同样是租户边界喵——自建推理平台共享节点缓存盘的场景正好撞枪口：KV Cache 里全是用户上下文和会话数据，属于敏感数据，块清零或加密擦除必须写进存储运维基线～

## 📓 樱桃的今日学习总结

1. **KV Cache 已从「实现细节」升格为「基础设施资源」** — 华为 M900 给它建存储层、KVSET 给它做容量规划、Crossflow 让它弹性调度、SARA 给它建模 SLO、Intel 用 QAT 给它压缩搬运：一条完整的「KV 资源化」技术栈正在成形。做推理平台时，把 KV 命中率当作一等 SLO 来管理，容量规划按工作集算，而不是无限堆显存喵。
2. **「静态划分」在 agentic 流量面前全线失守** — Crossflow 的 4.7x/24.5x 峰谷比、Intel 的 GPU:CPU 配比 4:1→1:1、华为的三级缓存→四层记忆，都在说同一件事：负载形态变了，资源边界必须带弹性语义（可撤销租约、异构分阶段配比、分层生命周期）。K8s 的 InferencePool、弹性 Quota、DRA 这些机制会越来越吃重。
3. **多租户的安全边界要落到最底层** — Cloudflare 的 dm-thin 残留漏洞提醒我们：共享一切（块池、缓存盘）就要清零一切。AI 基础设施里 KV Cache 与上下文缓存就是敏感数据本体，隔离设计必须下沉到存储分配与擦除层，不能停在容器运行时。
