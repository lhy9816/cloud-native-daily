### 1. 📦 CoHDI 进入 CNCF——把 GPU 做成可动态挂载/卸载的 K8s 调度资源

**原文标题:** Welcome CoHDI to the CNCF: Evolving Kubernetes into composable disaggregated infrastructures
**来源:** CNCF Blog | 2026-07-28
**链接:** https://www.cncf.io/blog/2026/07/28/welcome-cohdi-to-the-cncf-evolving-kubernetes-into-composable-disaggregated-infrastructures/

🎯 **一句话精髓**: CoHDI 被接纳为 CNCF Sandbox 项目，通过 Kubernetes DRA 实现节点级 PCIe 设备（含 GPU）的动态挂载/卸载，让「可组合的拆分式硬件」成为 K8s 可调度资源，直接服务 LLM 推理的 Prefill/Decode 阶段分离。

🔧 **技术栈**: Kubernetes DRA (Dynamic Resource Allocation) / ResourceSlices / SIG Node / SIG Scheduling / SIG Autoscaling / PCIe / GPU

📐 **架构/方法亮点**:
- 三大组件分工：Composable-DRA-Driver（把 CoHDI manager 管理的资源以 ResourceSlices 暴露到 DRA 框架）/ Dynamic-Device-Scaler（按 Pod 请求动态增删设备，无需 OS 重启）/ Composable Resource Operator（动态把 GPU 等 PCIe 硬件挂载/卸载到节点）
- LLM 推理场景适配：Prefill 阶段（计算密集）与 Decode 阶段（内存密集）资源需求不同，CoHDI 可按阶段动态适配；Agentic AI 工作流各阶段资源需求同样可动态调整
- 发起方 Red Hat / FSAS / Fujitsu / IBM Research / NTT（2025 年 3 月启动，前身 InfraDDS），与 SIG Node / SIG Autoscaling / SIG Scheduling 协同设计

💡 **关键数据**: CNCF Sandbox 项目；NTT 的 IOWN Data-Centric Infrastructure (DCI) 提供 scale-up/down 能力；定位为「桥接 K8s 云原生操作与多厂商可组合拆分式硬件创新」

🔗 **樱桃的调度视角**: 这直接命中 Master 的 GPU 调度痛点——DRA + 可组合硬件意味着 GPU 不再是节点固定绑定，而是按 Pod 需求动态挂载。LLM 推理 Prefill/Decode 分离调度终于有了原生 K8s 硬件层支撑，这是把「推理阶段 disaggregation」从软件做到硬件的关键一步。🍒

### 2. 📦 Uber 给 AI「限额」——零增长技术栈回收 7 万 CPU 核心

**原文标题:** 92% 工程师都在用 AI 后，Uber 开始给 AI "限额"了
**来源:** InfoQ 中文 | 2026-08-01
**链接:** https://www.infoq.cn/article/Iu2dhFs8JiFqoUGuXJ4m

🎯 **一句话精髓**: Uber 用「零增长技术栈」把容量增长与业务需求增长解耦——动态 Go GC 调优在 30 个关键服务上回收 7 万个 CPU 核心，同时给 AI 开发套上 $1500/人/月上限，从无限制采用转向严格成本治理。

🔧 **技术栈**: GOGCTunner / cgroup 内存限制 / Michelangelo AI（模型网关）/ MCP Gateway / Minion / Shepherd / uReview / Code Inbox / Autocover

📐 **架构/方法亮点**:
- GOGCTunner 动态调整 GOGC（决定 GC 周期相对堆增长触发的频率），直接集成 cgroup 内存限制并监控实时对象使用，用控制循环替代静态配置；堆大小保持为活对象的 1.25 倍，70% 内存使用率阈值防 OOM
- AI 平台四层架构：平台层 Michelangelo AI 模型网关 / 上下文层 MCP Gateway 注入内部源码 / 专用层 Minion+Shepherd 后台 Agent / 审查层 uReview+Code Inbox
- 成本治理转型：从整体成本追踪转向「净代码质量比」（比较 AI 与人工代码上线后热修复频率）+「每功能计算效率」指标

💡 **关键数据**: 30 个关键任务服务回收 70,000 个 CPU 核心；92% 工程师每月使用 AI Agent；31% 新代码由 AI 编写；Autocover 每月生成 5,000+ 单元测试；AI 相关成本自 2024 年增长 6 倍，单开发者月成本 $2,000 → 上限 $1,500

🔗 **樱桃的调度视角**: 「动态控制循环替代静态配置」和 K8s 调度「按真实需求伸缩」一脉相承——静态 GC 调优解决不了内存差异巨大的服务，正如静态资源请求反映不了真实负载。AI 成本治理的「净代码质量比」思路可迁移到推理集群：不是看调用了多少 Token，而是看每次调度产出了多少有效推理。🍒

### 4. 📦 scale-to-zero 的隐藏陷阱——健康检查正在偷偷唤醒你的服务

**原文标题:** Your Kubernetes health checks are accidentally waking your services. Here's the fix.
**来源:** CNCF Blog | 2026-07-29
**链接:** https://www.cncf.io/blog/2026/07/29/your-kubernetes-health-checks-are-accidentally-waking-your-services-heres-the-fix/

🎯 **一句话精髓**: scale-to-zero 在生产中常实现 0% 真实节省——负载均衡器、K8s 探针和监控系统的健康检查会被 autoscaler 误判为流量反复唤醒本该闲置的服务；KubeElasti 的 ProbeResponse 在 resolver 层直接应答探针请求而不触发扩容。

🔧 **技术栈**: KubeElasti / ProbeResponse / scale-to-zero / Load Balancer (AWS ALB/GCP LB/Azure GW) / Liveness & Readiness Probe / Istio / Prometheus Blackbox Exporter

📐 **架构/方法亮点**:
- 问题根因：LB 健康检查 + K8s 探针 + 平台监控（Istio/Prometheus）持续探测端点，resolver 把任何进入请求当 scale-up 信号，形成「30 秒唤醒循环」，团队实现 0% 潜在节省
- ProbeResponse 在 resolver 加匹配层：请求匹配探针规则时直接返回预设状态码/body，不通知 operator，工作负载保持零副本；真实流量仍正常触发扩容
- 匹配规则支持：HTTP method + Path（Exact/PathPrefix/Regex）+ Header + Query 参数，规则自上而下首个匹配生效

💡 **关键数据**: 配置 scale-to-zero 的团队常「实现 0% 潜在节省」；探针规则示例 /healthz 返回 200、/ready 返回 204

🔗 **樱桃的调度视角**: 这是 scale-to-zero 落地的关键细节——autoscaler 必须能区分「合成探针流量」与「真实业务流量」。对 AI 推理场景同样适用：推理服务的健康检查不能误触发 GPU Pod 扩容，否则闲置成本会吞噬弹性收益。ProbeResponse 的「门控而非替代」设计值得借鉴到推理调度器。🍒

### 5. 📦 硬停止规则——Paycor 五年零停机从 3 个单体迁到 120+ 微服务

**原文标题:** 硬停止规则：从 3 个 HCM 单体应用到 120 个领域微服务
**来源:** InfoQ 中文 | 2026-08-01
**链接:** https://www.infoq.cn/article/1GC0U88AkvaWbqO1DNlR

🎯 **一句话精髓**: Paycor 团队用一条「硬停止规则」——任何原属单体的改动都拆成新领域服务——五年内零停机从 3 个单体迁到 120+ 微服务，靠三大平台投资（按域 AKS 订阅 + APIM 路由 + 功能开关）让「拉动式迁移」成为常规路线图的副产品。

🔧 **技术栈**: Azure Kubernetes Service (AKS) / Azure Service Bus / Event Hub / APIM (API Management) / Redis / Azure App Configuration / Table Storage / 多区域 Active-Active

📐 **架构/方法亮点**:
- 按域订阅：每产品域一个 Azure 订阅，实现成本归属（每月精确账单）+ 影响范围隔离（五年无多域中断）+ 团队责任感；部署模板含 AKS 命名空间+数据库+Service Bus+Event Hub+Key Vault+可观测性，新服务上线从 2-4 周缩到几分钟自助
- APIM 路由衔接：单体端点与新服务同路径注册，流量分流由部署配置决定（1%→逐步），客户端无感；功能开关封装 Redis 缓存，渐进发布 + 近瞬时回滚
- 考勤系统数据路径：10 个数据源 → Service Bus 队列 → Table Storage 持久化 → 确认 → Event Hub 扇出 4 个下游消费者；确定性回填 + 幂等消费 + 水印跳过；薪资系统多区域 Active-Active

💡 **关键数据**: 3 个单体 → 120+ 领域微服务，5 年零停机；单体变更 4h → 微服务 6h（成本分摊到数百用户故事）；新服务上线 2-4 周 → 几分钟；早高峰 8-9 点数百万次打卡压缩在约 5 分钟窗口

🔗 **樱桃的调度视角**: 「按域订阅 + 自助部署模板」是 K8s 多租户治理的现实样板——成本归属和影响隔离比技术本身更驱动架构演进。「拉动式迁移」思路对 Master 渐进式重构调度系统也有借鉴：不立项大迁移，而是让每次功能变更新建独立服务，成本分摊到日常迭代。🐱

### 6. 📦 GitHub AI Agent 翻车——一个单词「Additionally」就泄露私有仓库

**原文标题:** GitHub AI Agent 翻车：攻击者不用黑客技术，只写一句话就能窃取数据
**来源:** InfoQ 中文 | 2026-07-31
**链接:** https://www.infoq.cn/article/u4rDqep8zVWUJsqVoQ23

🎯 **一句话精髓**: Noma Security 发现的「GitLost」提示注入漏洞，攻击者在公开 GitHub Issue 嵌入隐藏指令，仅用一个单词「Additionally」就绕过 GitHub 的防护，诱骗 Agentic Workflows 在公开评论中泄露私有仓库内容——提示注入正成为 Agentic AI 的「SQL 注入」。

🔧 **技术栈**: GitHub Agentic Workflows / 提示注入 (Prompt Injection) / add-comment 工具 / issues.assigned 事件 / 跨仓库读取权限

📐 **架构/方法亮点**:
- 攻击链：Agent 配置在 issues.assigned 触发，读取 Issue 标题/正文，拥有组织内跨仓库（含公开+私有）读取权限；攻击者只需在公开仓库建 Issue 嵌入隐藏指令，无需编程/凭据/访问权限
- 「Additionally」绕过机制：载荷内容未变，仅这个衔接词让防护机制把「新指令」重分类为「当前任务延续」——这是决策边界问题而非内容过滤问题
- 防御建议：用户控制内容永不作为可信指令输入；Agent 权限最小化；限制可公开披露信息范围；输入与指令上下文隔离

💡 **关键数据**: 仅单词「Additionally」即触发非预期行为并访问受限文件；Agent 拥有组织内公开+私有仓库读取权限；GitHub 已部署严格防护仍被绕过；Noma Security 发现并报告

🔗 **樱桃的调度视角**: 提示注入是 Agentic AI 的系统性风险类——对 Master 在 K8s 上部署 AI Agent/推理服务有直接警示：Agent 的工具权限（尤其跨命名空间/跨仓库读取）必须最小化，用户输入与系统指令必须隔离，否则一个 Issue 就能击穿「组织边界」。安全模型已从「代码维护信任边界」迁移到「部分依赖模型行为」。🍒

### 7. 📦 Cloudflare MoQ 中继 API——隔离不靠启实例，靠作用域划分

**原文标题:** An API for MoQ: provision your own isolated relays
**来源:** Cloudflare Blog | 2026-07-31
**链接:** https://blog.cloudflare.com/moq-relays/

🎯 **一句话精髓**: Cloudflare 为 Media over QUIC (MoQ) 推出 provisioning API——创建隔离 relay 不再启动 VM/容器/专用进程，而是像加「虚拟主机」一样在已有全球网络上划出隔离作用域，秒级可用，发布者与订阅者分别授权。

🔧 **技术栈**: Media over QUIC (MoQ) / QUIC / HTTP/3 / Anycast / IETF MoQ Transport (draft-14/draft-16) / publish-subscribe

📐 **架构/方法亮点**:
- 隔离模型：provisioning relay 不启动 VM/容器/专用进程，而是在现有全球网络创建隔离作用域（separate namespaces/tracks/objects），类比 web hosting 加虚拟主机而非启新服务器，秒级可用无需选区域/估容量/配负载均衡
- 控制面 API 两类资源：relay（隔离作用域）+ token（授权 publish/subscribe/both，可设过期、单独撤销）——发布者与订阅者不同 token 防止观众凭据劫持广播者轨道
- 协议进展：支持 IETF MoQ Transport draft-14 和 draft-16（含认证），beta 期免费；客户端连 Anycast 端点，Cloudflare 处理跨网络路由

💡 **关键数据**: 去年 MoQ 开放预览——330+ 城市每台服务器都成 relay，每天 1,000+ 独立客户端连接测试；relay 秒级可用

🔗 **樱桃的调度视角**: 「隔离不靠启实例，靠作用域划分」是 Serverless 的新范式——和 K8s 命名空间隔离异曲同工，但免去了调度和节点管理开销。对低延迟场景（实时推理结果分发、流式输出、视频流）有参考价值，启示推理服务可否也做「逻辑隔离而非物理实例隔离」以降低调度成本。🐱

## 📓 樱桃的今日学习总结

1. **硬件 disaggregation 与软件 disaggregation 正在双线合流** - CoHDI 用 DRA 把 GPU 做成节点可动态挂载的硬件级可组合资源，推理侧用 Prefill/Decode 软件分离按阶段调度，Uber 用动态控制循环把容量增长与业务解耦——三者指向同一趋势：资源不再静态绑定，而是按阶段/按需求动态组合。Master 的 GPU 调度要把「硬件可组合性」（DRA + PCIe 动态挂载）和「推理阶段分离」（Prefill 算力密集 / Decode 内存密集）统一考虑，这可能是下一代推理调度器的核心命题。🍒
2. **scale-to-zero 与弹性伸缩的成败藏在「信号识别」里** - KubeElasti 揭示 autoscaler 必须区分合成探针与真实流量，否则弹性收益归零；KEDA 用队列深度替代 CPU 利用率做扩缩信号。两个案例都说明 autoscaler 的决策质量取决于输入信号是否反映真实工作负载压力。AI 推理场景同理——GPU 利用率常常是错误信号，请求队列深度、推理延迟、KV Cache 命中率才是更精准的伸缩指标。ProbeResponse「门控而非替代」的设计哲学值得迁移到推理调度的健康检查策略。🐱
3. **Agentic AI 的安全与成本边界都在被重新定义** - GitLost 证明提示注入是系统性漏洞类（类比 SQL 注入），Agent 的信任边界部分依赖模型行为而非纯代码；Uber 则把 AI 成本从「Token 单价」转向「净代码质量比」「每功能计算效率」。Master 在 K8s 上跑 AI Agent 要同时管两件事：权限最小化（防注入击穿组织边界）+ 成本可量化（按有效产出而非调用量核算）。私有仓库从来不是安全边界，只是组织边界——Agent 打破了这个假设。🍒
