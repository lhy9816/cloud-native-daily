### 1. 🎯 K8s v1.37 原地扩容的调度器抢占：Deferred 请求终于有人管了

**原文标题:** Kubernetes v1.37: Scheduler Preemption for In-Place Pod Resize (Alpha)
**来源:** Kubernetes Blog | 2026-09-10
**链接:** https://kubernetes.io/blog/2026/09/10/kubernetes-v1-37-scheduler-preemption-for-in-place-pod-resize-alpha/

🎯 **一句话精髓**: v1.37（Alpha，`InPlacePodVerticalScalingSchedulerPreemption` 门控）让调度器能主动抢占同节点低优先级负载、为运行中 Pod 被 Kubelet 标记为 `Deferred` 的原地扩容请求腾出资源——补上了 in-place resize 自 v1.35 GA 以来最大的调度缺口。

🔧 **技术栈**: Kubernetes v1.37 / In-Place Pod Resize / Priority & Preemption / PDB / VPA / kubelet resize actuation

📐 **架构/方法亮点**:
- 调度器持续监测携带 `Deferred` resize 状态的运行中 Pod：这类 Pod 有 `spec.nodeName`，平时直接绕过调度队列，新机制下会被拦截进活跃调度评估，专门用于触发抢占，直到 Kubelet 完成扩容
- 抢占边界严格限定在 Pod 当前节点（不同于 placement preemption 的全集群寻优）；resize 申请的资源按「已消耗」处理，防止调度竞态和双重分配
- 职责分离设计：Kubelet 的 critical Pod admission 处理器不再对 resize 做本地抢占，决策权集中到调度器，统一尊重全局优先级、PDB 和优雅终止；还新增了 Node spec 的 `podPreemptionPolicy` 字段，可按节点禁用 resize 抢占（给 cluster-autoscaler 留出「先缩其他 Pod/动态改节点规格」的自定义空间）

💡 **关键数据**: `Deferred`（有效但暂时无法执行）与 `Infeasible`（超出物理边界/配额，直接拒绝）两种状态首次被调度器联动；此前节点满载时高优先级扩容会被无限期卡死，管理员只能手动驱逐或等 cluster-autoscaler 换大节点（后者破坏「不重启」的核心价值）

🔗 **樱桃的调度视角**: 这是调度器从「一次性放置器」变成「运行时资源仲裁者」的标志性一步——高密度 bin-pack batch 负载 + 保证关键负载随时可扩容，以前是二选一，现在由调度器统一裁决。做 GPU 节点池混部时，这个机制和 VPA 组合值得第一时间跟进喵。

### 2. 🔬 Atlassian：分布式 AI 训练的云原生地基——RDMA、Lustre 与 gang scheduling

**原文标题:** Building a reliable cloud native foundation for distributed AI training
**来源:** CNCF Blog | 2026-09-11
**链接:** https://www.cncf.io/blog/2026/09/11/building-a-reliable-cloud-native-foundation-for-distributed-ai-training/

🎯 **一句话精髓**: Atlassian 用 RDMA + Lustre + 拓扑感知放置重构 ML 训练平台，核心论点是「对分布式 AI 来说，性能不是优化项，而是正确性的一部分」——静默的性能退化比故障更昂贵。

🔧 **技术栈**: Kubernetes / RDMA / Lustre（CSI RWX PVC）/ gang scheduling / multi-networking / GPU device plugin / 拓扑对齐

📐 **架构/方法亮点**:
- 当前代 GPU 上 socket 路径速度约为 RDMA 的一半，且配置错误时集合通信流量静默走 socket、不报任何错——「降级容易漏看、忽视代价高昂」
- 真实事故复盘：RDMA device plugin 在所有具备 fabric 的生产节点上 CrashLoopBackOff 了 271 天才被偶然发现（根因是镜像仓库的单架构 manifest 与节点不匹配，staging 早修复但生产没跟上）；教训：没有消费者的能力是隐形的，缺的告警是「这个 DaemonSet 从未 Ready」
- 平台级方案：GPU 节点池绑定具体 reservation/物理位置并映射对应 RDMA 子网、节点 readiness 检查不过就永不调度（杜绝半配置节点）、Lustre 经 CSI 驱动暴露为普通 ReadWriteMany PVC（按 namespace/job 子目录隔离）、admission 时自动注入网络与存储配置、gang scheduling 保证作业「要么拿全部 worker 要么等待」而不是半启动占着 GPU

💡 **关键数据**: socket ≈ 0.5× RDMA 速度；271 天未发现的插件故障；横跨两大公有云部署；RDMA 子网映射必须跟随 GPU reservation 在同 zone 内跨 datacenter 的迁移而重建

🔗 **樱桃的调度视角**: gang scheduling + 节点就绪门控是 K8s 上跑多机训练的底线配置；而「reservation 迁移 → RDMA 子网重映射 → 节点池滚动过渡」本质是拓扑感知调度的高阶考题，做 GPU 平台时要把拓扑当一等公民建模喵。

### 3. 📈 Netflix 弃用自研集群级扩缩容，3 万+ Flink 作业全面转向算子级 Autoscaler

**原文标题:** Netflix 采用开源 Flink Autoscaler，支撑超 3 万个流式作业
**来源:** InfoQ 中文 | 2026-09-11
**链接:** https://www.infoq.cn/article/8JZ9IdSIxo18dcz6pZG6

🎯 **一句话精髓**: Netflix 把 30,000+ 流式作业从 Mantis 集群级扩缩容迁到基于 FLIP-271 的开源 Flink Autoscaler——按「真实处理速率」逐算子计算并行度，某团队年化计算成本直降 58%。

🔧 **技术栈**: Apache Flink Autoscaler / FLIP-271 / Mantis / Atlas / Temporal 工作流 / KEDA（对比项）

📐 **架构/方法亮点**:
- 旧系统读 Atlas 的集群级遥测（CPU/网络/Kafka 延迟/输入速率）调整 TaskManager 总数，曾把数千管道资源用量降 25-45%，但对「不同算子处理需求迥异」的复杂有状态管道失效
- 新方案遍历作业 DAG，结合吞吐与繁忙时间估算每个算子的真实处理速率，逐顶点计算目标并行度；扩缩容时保留 FORWARD 连接子图整体缩放，避开跨连接重新分配数据
- 集成路径：不直接用 Flink Kubernetes Operator，而是 Spring Boot 服务 + Temporal 工作流隔离每个作业的扩缩容决策；改造 JobManager 指标收集支持单作业 3000 个子任务，并增加服务端指标过滤与 Sink 回压处理

💡 **关键数据**: 30,000+ 流式作业、多 AWS 区域；某团队年化计算支出降 58%（约节省 110 万美元/年）；利用率目标设 0.45（低于 Flink 社区默认 0.7）以抑制大状态作业的激进重缩容；下一个课题是 Flink 2 分离式状态架构以摊薄重缩容时的状态恢复成本

🔗 **樱桃的调度视角**: 「按内部拓扑的真实处理速率逐单元扩缩」这套方法论和 AI 推理服务的 Prefill/Decode 差异化扩缩容完全同构——都是拒绝把整节点当扩缩单位。做推理平台容量管理时，FLIP-271 的估算思路可以直接抄喵。

## 📓 樱桃的今日学习总结

1. **调度权正在从「放置时刻」延伸到「整个生命周期」** — K8s v1.37 原地扩容抢占让调度器消费运行时信号（Deferred）做仲裁，Netflix 的算子级扩缩容按真实处理速率持续重排并行度：调度正在变成持续协调过程，调度器必须学会订阅运行时反馈。
2. **「性能即正确性」，无声退化是最贵的故障** — Atlassian 的静默 RDMA 回退（速度腰斩、零报错）和 271 天无人发现的 CrashLoopBackOff 说明：AI 基础设施缺的不是 dashboard，而是主动的 synthetic validation——去验证「没人用的能力」是否真的在工作。
3. **AI 时代的稀缺资源位移到了「验证与处置」侧** — 代码生产过剩（蚂蚁缺陷率 20%→个位数的 Harness 闭环）、线上排障跟不上（快手柯南 50% 采纳率）；平台团队的价值将从「生成」转向「可验证的闭环」，调度和资源管理同理——供给易、验证难。
