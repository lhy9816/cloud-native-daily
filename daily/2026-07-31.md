### 1. 📦 谷歌 Agent Substrate——K8s 之上的智能体专用调度层

**原文标题:** Kubernetes 统治了容器时代，谷歌 Agent Substrate 意在拿下下一个十年
**来源:** InfoQ 中文 | 2026-07-30
**链接:** https://www.infoq.cn/article/h0WG6p7z3tyTk3hxQIhT

🎯 **一句话精髓**: 谷歌公开承认 K8s 控制平面不适合调度 AI 智能体，推出 Agent Substrate 在 K8s 旁路构建专用调度层，用"虚拟内存超分配"思路实现智能体会话的毫秒级唤醒与 30 倍超额订阅。

🔧 **技术栈**: GKE Agent Sandbox / Agent Substrate / gVisor / Kata Containers / Kubernetes / kagent

📐 **架构/方法亮点**:
- 智能体类比 OS 进程：长期运行、有状态、大部分时间空闲，运行时在空闲时快照挂起、事件到达时亚秒级恢复；隔离责任从容器边界下沉到内核边界（gVisor 默认 + Kata 可插拔）
- Agent Substrate 用"虚拟内存超分配"调度：将大量有状态智能体会话复用到小规模预热 WorkerPod 池，空闲会话快照持久化，把标准 K8s 控制平面移出调度关键路径
- 两个 CRD 定义开发者接口：WorkerPool（就绪计算池）+ ActorTemplate（智能体定义），框架无关——ADK / LangChain / Claude Code / 任意 OCI 容器均可作为执行者

💡 **关键数据**: 30 倍超额订阅率、亚秒级激活速度；每集群每秒分配 300 个 Sandbox、90% 分配在 200ms 内完成；Agent Sandbox 5 个月采用规模增长约 16 倍

🔗 **樱桃的调度视角**: 这篇直接点中 Master 的核心领域——K8s 调度器为"少量长期 Pod"设计，而智能体产生海量细粒度调度事件使 API Server 成为瓶颈。Agent Substrate 的"旁路调度 + 预热池 + 快照恢复"模式，对 GPU 推理服务的冷启动优化和会话级调度有直接借鉴价值。

### 2. 📦 CoHDI 进入 CNCF Sandbox——GPU 也能像乐高一样动态组装

**原文标题:** Welcome CoHDI to the CNCF: Evolving Kubernetes into composable disaggregated infrastructures
**来源:** CNCF Blog | 2026-07-28
**链接:** https://www.cncf.io/blog/2026/07/28/welcome-cohdi-to-the-cncf-evolving-kubernetes-into-composable-disaggregated-infrastructures/

🎯 **一句话精髓**: CoHDI 通过 Kubernetes DRA 实现节点级 PCIe 设备（GPU）的动态附加/分离，让 LLM 推理的 Prefill/Decode 分离调度成为可能——GPU 不再是节点级静态资源，而是按 Pod 需求动态组装的可组合单元。

🔧 **技术栈**: Kubernetes DRA (Dynamic Resource Allocation) / CoHDI / Dynamic-Device-Scaler / Composable-DRA-Driver / ResourceSlices / PCIe

📐 **架构/方法亮点**:
- 通过 DRA 框架将可组合硬件资源暴露为 ResourceSlices，Pod 请求触发动态设备扩缩，无需 OS 重启即可在线加减 GPU
- 三大组件协作：Composable-DRA-Driver（DRA 桥接，暴露可用资源）+ Dynamic-Device-Scaler（按 Pod 请求动态加减排）+ Operator（将 GPU 等硬件附加/分离到节点）
- 与 SIG Node / SIG Autoscaling / SIG Scheduling 协作，针对 LLM 推理 Prefill（计算密集）与 Decode（内存密集）阶段的不同资源画像动态适配

💡 **关键数据**: Red Hat / FSAS / Fujitsu / IBM Research / NTT 五方共建，2025 年 3 月启动，现已进入 CNCF Sandbox

🔗 **樱桃的调度视角**: 这正是 GPU 调度的前沿——传统 K8s 把 GPU 当节点级静态资源，CoHDI 让 GPU 成为按需动态组装的"乐高积木"。对 Prefill/Decode 分离推理（如 vLLM disaggregated serving）场景，动态 GPU 重组能显著提升集群级利用率。

### 4. 📦 Scale-to-Zero 的隐藏陷阱——健康检查在偷偷唤醒你的服务

**原文标题:** Your Kubernetes health checks are accidentally waking your services. Here's the fix.
**来源:** CNCF Blog | 2026-07-29
**链接:** https://www.cncf.io/blog/2026/07/29/your-kubernetes-health-checks-are-accidentally-waking-your-services-heres-the-fix/

🎯 **一句话精髓**: Scale-to-zero 在生产中常因负载均衡器持续健康检查而被破坏（节省率 0%），KubeElasti 的 ProbeResponse 在 resolver 层拦截探针请求直接响应，让服务真正保持零副本。

🔧 **技术栈**: KubeElasti / ProbeResponse / Kubernetes scale-to-zero / Load Balancer health probes / DNS resolver

📐 **架构/方法亮点**:
- 根因链路：LB 每 30s 健康检查 → 命中 resolver → resolver 视为流量信号通知 operator 扩容 → Pod 唤醒，形成 30s 唤醒死循环，scale-to-zero 节省率归零
- ProbeResponse 在 resolver 层增加规则匹配：请求匹配探针规则时直接返回自定义状态码 / body，不通知 operator，服务真正保持零副本
- 拒绝"分离健康检查端点"的常见建议（LB 不可控 / 运维漂移 / /healthz 本就是应用路径），也拒绝常驻 proxy 的"延迟换拦截"方案

💡 **关键数据**: 典型配置下 health check 每 30s 一次的唤醒死循环使 scale-to-zero 节省率从预期降至 0%，ProbeResponse 消除该循环后恢复预期节省

🔗 **樱桃的调度视角**: 这是 scale-to-zero 调度的经典陷阱——autoscaler 判定"死"与 LB 判定"活"的根本矛盾。对 Master 做推理服务的按需缩容（如夜间 GPU 归零），resolver 层拦截思路比改 LB 配置更优雅可控。

### 5. 📦 Linkerd 多集群联邦——三种模式共存实现零停机 K8s

**原文标题:** Federating clusters for zero-downtime Kubernetes
**来源:** CNCF Blog | 2026-07-27
**链接:** https://www.cncf.io/blog/2026/07/27/federating-clusters-for-zero-downtime-kubernetes/

🎯 **一句话精髓**: Linkerd 多集群扩展支持 federated / flat / gateway 三种模式在同一组链路上 per-service 共存，3 个 GKE 集群全互联下单集群整体故障流量自动转移、零应用改动。

🔧 **技术栈**: Linkerd multicluster / GKE / VPC peering / service federation / gateway mirroring

📐 **架构/方法亮点**:
- 三模式 per-service 标签选择：federated（同服务多集群单端点自动故障转移）/ flat-mirror（按名显式远程服务，保数据 locality）/ gateway-mirror（仅需网关 IP 可达，无需 Pod 直连）
- 3 集群 × 6 方向链路全互联：frontend 联邦（3 副本×3 集群=9 Pod 负载均衡），api 扁平镜像（west/east 运行，north 按名消费保在区域），analytics 网关镜像（仅 east，经网关导出）
- chaos 测试：整集群下线后剩余 6 Pod 自动接管，零应用代码改动；GCP peered VPC 免费提供 flat 网络连通性

💡 **关键数据**: 3 集群 / 6 方向链路 / 9 Pod 联邦负载均衡 / 单集群故障 6 Pod 无缝接管

🔗 **樱桃的调度视角**: 跨集群调度的实战范本——federated 模式做核心负载自动故障转移，flat-mirror 做数据局部性亲和（请求留本区域），这正是多区域 GPU 推理调度的核心需求：既要高可用又要模型/数据 locality。

### 6. 📦 从 GPT-2 到 Kimi K3——大模型架构的"记忆操作系统"演进

**原文标题:** 从GPT-2到Kimi K3：七年规模扩大2.26万倍，大模型架构主线是在建立一套"记忆操作系统"
**来源:** InfoQ 中文 | 2026-07-30
**链接:** https://www.infoq.cn/article/NMXxssS9qB8LtRlWMr5V

🎯 **一句话精髓**: 回溯七年大模型架构演进，主线从"记住一切"走向"选择性记忆"——KV Cache 解决生成效率，Linear Attention 压缩长期记忆，DeltaNet / Kimi Linear 让模型学会更新与遗忘。

🔧 **技术栈**: KV Cache / Softmax Attention / Linear Attention / DeltaNet / Kimi Linear / Flash Attention

📐 **架构/方法亮点**:
- KV Cache 演进：存储历史 Token 的 K/V 向量避免重复计算，但随序列增长成为内存带宽瓶颈（推理显存核心痛点）
- Linear Attention 突破：对 q/k 分别做特征映射（如 ELU+1）使矩阵乘法可重结合，将不断增长的 K/V 集合压缩为固定大小 D×D 状态矩阵，复杂度从 O(N²) 降至 O(N)
- DeltaNet / Kimi Linear：在状态矩阵基础上引入"更新 / 遗忘 / 调度"机制，类比 OS 内存页的换入换出，实现选择性记忆管理

💡 **关键数据**: Kimi K3 参数量 2.8 万亿（2.8T），是 GPT-2 的 22,580 倍；GPT-2 基准模型约 1.24 亿参数

🔗 **樱桃的调度视角**: KV Cache 是 GPU 推理显存占用的大头，Linear Attention 将其压缩为固定状态矩阵直接降低推理显存压力——这对 K8s 上 GPU 调度/分时的显存预算计算和 PagedAttention 类方案有底层架构级影响。

### 7. 📦 当 Agent 拿走数据库的行动权——数据库的"第二次权力转移"

**原文标题:** 深度访谈｜第二次权力转移：当Agent拿走数据库的行动权
**来源:** InfoQ 中文 | 2026-07-30
**链接:** https://www.infoq.cn/article/B2GjIEBr0c1L0amoKmNf

🎯 **一句话精髓**: 从 1974 年巴赫曼 vs 科德的"第一次权力转移"（查询优化器代劳执行路径），到今天 Agent 自主理解目标、拆解任务、直接写入/触发/冻结数据库——数据库的安全边界与架构正面临重构。

🔧 **技术栈**: AI Agent / 查询优化器 / 数据库权限模型 / Agent-DB action layer

📐 **架构/方法亮点**:
- 历史类比：1974 年巴赫曼（程序员手规划取数路径）vs 科德（声明"要什么"、系统决定"怎么做"），关系模型胜出，查询优化器成为数据库历史上第一个"代理"
- 新边界被越过：Agent 收到业务目标（如"检查异常支出，处理高风险项目"）后自主理解、拆解、检索、匹配规则、据中间结果决定下一步——人类让渡"执行哪些指令"的决策层
- 风险质变：Agent 只回答问题时错误停留在信息层；一旦能写入数据、触发付款、冻结账户、调整库存，错误直接变成现实后果，需重构权限与安全边界

💡 **关键数据**: 阿里云数据库产品事业部负责人等深度实践者参与讨论（深度访谈，偏架构观点）

🔗 **樱桃的调度视角**: Agent 直接操作数据库意味着调度系统不仅要管计算资源，还要管"行动权限"的动态授权与审计——这是 Agent 调度层（如 Agent Substrate）必须叠加的安全调度维度。

## 📓 樱桃的今日学习总结

1. **K8s 调度器的"分层化"趋势** - 智能体负载暴露了 K8s 调度器"少量长期 Pod"假设的局限，Agent Substrate 与 CoHDI 分别在会话级和硬件级构建旁路调度层，K8s 退居为"机器资源调配底座"、上层出现专用调度器——类似 OS 内核与用户态运行时的分工。Master 做调度优化时，应区分"资源调度（K8s 擅长）"与"工作负载调度（需专用层）"两个层次。
2. **AI 推理的资源抽象从"静态分配"走向"动态组装"** - CoHDI 让 GPU 成为按 Pod 需求动态附加的 PCIe 资源，Kimi K3 的 Linear Attention 将 KV Cache 压缩为固定状态矩阵，两者从硬件和模型架构两端降低推理的资源刚性，为更细粒度的 GPU 分时调度扫清障碍。这是 GPU 利用率提升的两大杠杆。
3. **Scale-to-zero 的"最后一公里"藏在探针层** - 健康检查与缩容的根本矛盾不是调度算法问题，而是"信号归属"问题——resolver 层的探针拦截（ProbeResponse）比改 LB 或加常驻 proxy 更贴合 scale-to-zero 本意。启示：调度系统的边界条件常藏在相邻系统的"善意行为"里，排查资源浪费要顺着流量链路逐层看。
