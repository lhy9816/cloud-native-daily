### 1. 🤖 谷歌开源 AX：把 AI Agent 当「有状态 Actor」编排的 K8s 风格运行时

**原文标题:** 谷歌开源面向自主 AI 代理的 Kubernetes 风格编排器 AX
**来源:** InfoQ 中文 | 2026-09-30
**链接:** https://www.infoq.cn/article/M6BRTrsyJvUg8y0M0kyh

🎯 **一句话精髓**: Google 开源 Apache 2.0 编排器 AX（github.com/google/ax），把自主 Agent 视为「有状态的 Actor」而非微服务或批处理任务，提供 Task/Workspace/Gateway/Model 四个声明式原语，支持亚秒级任务暂停与恢复。

🔧 **技术栈**: AX / Agent Substrate / Actor 多路复用 / 声明式运行时 / K8s 编排模型

📐 **架构/方法亮点**:
- 工作负载语义重定义：Agent 是「状态性 + 突发性 + 长时运行」的混合体——推理/工具执行/本地代码评估的高强度计算，穿插等待模型响应、外部 API、人工干预的长空闲期，两类传统模型（无状态微服务 / run-to-completion 批任务）都覆盖不了
- 直击 K8s 两难：空闲期保活专用沙箱 → 利用率不足；容器冷启动 → 交互式 Agent 循环延迟抬升。AX 用专为密集 Actor 多路复用设计的 Agent Substrate 执行运行时在中间走出第三条路
- 架构基线来自 Google 与 Google DeepMind 各团队的系统研究，四个声明式基本组件：Task、Workspace、Gateway、Model

💡 **关键数据**: 亚秒级任务暂停/恢复；Apache 2.0 许可开源；四核心原语 Task/Workspace/Gateway/Model

🔗 **樱桃的调度视角**: 这是「Agent 原生调度」的标志性信号喵——suspend/resume 正在成为一等公民调度动作，Master 关注调度器的话，值得跟踪 AX 这类声明式原语未来与 K8s 的对接方式：Agent 的「空闲但不释放」语义会直接冲击现有资源配额与利用率模型～

### 2. ⚡ Cloudflare 重构 Containers：durable_object 调度策略让沙箱启动快 6 倍

**原文标题:** Cloudflare Containers, rebuilt to scale agent sandboxes
**来源:** Cloudflare Blog | 2026-09-30
**链接:** https://blog.cloudflare.com/faster-agent-sandboxes/

🎯 **一句话精髓**: 为 Agent「按需创建、立即就绪、可暂停恢复」的沙箱模式，Cloudflare 从底层重构 Containers——新增 durable_object 调度策略把镜像/实例类型的选择权从部署时下沉到运行时应用代码，启动中位时间从 4 秒降到 648 毫秒。

🔧 **技术栈**: Cloudflare Containers / durable_object scheduling policy / Durable Objects / 文件系统快照 / Sandbox SDK 1.0 / ctx.container API

📐 **架构/方法亮点**:
- 配置单元翻转：旧模型「应用 = 部署时统一镜像与资源的 rollout 单元」→ 新模型「任务决定镜像、资源、工具与起始文件系统」，配置决策随任务代码走
- 每个 Container 绑定一个常驻 Durable Object 作为可编程控制器，管生命周期与出站流量；原生 ctx.container API 免掉中间包装类
- 文件系统快照公测：工作区可保存后在数天后恢复，编码 Agent（Cursor Cloud Agents、Devin Outposts、OpenAI Agents API、Claude Managed Agents）、评测、RL 环境批量创建/评分/重置都被列为目标场景

💡 **关键数据**: ComputeSDK 独立基准中位启动 4s+ → 648ms（>6 倍）；burst 测试秒级创建数十万容器；快照公测上线

🔗 **樱桃的调度视角**: 和昨天阿里云 Agent Sandbox 的发布互为印证喵——「沙箱 = 短生命周期、任务级、状态可挂起」正在成为跨厂商共识。运行时选择镜像本质上是把调度决策 API 化，K8s 生态里对应的痛点（冷启动、镜像拉取、状态卷挂载）还没被这么优雅地解掉～

### 3. 📐 768 组仿真实证：MoE 推理完成时间被「拓扑 × 并行度 × 拥塞控制」联合决定

**原文标题:** Joint Effects of GPU Server Topology, Parallelism, and Congestion Control on MoE Inference: A Controlled Simulation Study
**来源:** arXiv (cs.DC) | 2026-09-29
**链接:** http://arxiv.org/abs/2609.37828v1

🎯 **一句话精髓**: 用 ASTRA-sim + NS-3 构建 32 GPU rank 的受控仿真矩阵，系统性量化服务器拓扑、TP/EP 划分、集合通信算法与拥塞控制对 MoE 推理完成时间的联合影响——暴露通信占总完成时间的 89.9%–95.8%。

🔧 **技术栈**: ASTRA-sim / NS-3 离散事件仿真 / MoE 推理 / TP·EP / Ring vs DBT 集合通信 / HPCC / DCQCN / RoCE / InfiniBand

📐 **架构/方法亮点**:
- 实验矩阵设计：6 种服务器拓扑 × 4 种 TP/EP 划分 × 2 种 TP 集合通信算法 × 4 种网络/拥塞控制模式 = 768 组确定性仿真；固定 DP=PP=1，4096-token prefill 型 Chakra 合成轨迹，4 种 MoE 配置
- 并行度压倒一切：TP16EP2 的平均完成时间是 TP2EP16 的 3.68–4.35 倍——EP 度越高、TP 度越低越快（在该工作负载下）
- 拓扑效应是条件性的：Topology~6 在低 TP 度时领先、高 TP 度时优势消失；加 GPU/NIC 只有在 rank 映射能均衡各注入路径流量时才有收益
- 拥塞控制差距显著：RoCE+DCQCN 比 RoCE+HPCC 慢 23.8%–35.7%；固定 rank 映射下 DBT 比 Ring 慢 28.3%–83.2%

💡 **关键数据**: 暴露通信占完成时间 89.9%–95.8%；TP16EP2 = 3.68–4.35× TP2EP16；DCQCN 慢 23.8%–35.7%；每 rank 最大 checkpoint 权重分片 ~48.75 GB（64 GB 显存约束全配置满足）

🔗 **樱桃的调度视角**: 对 Master 的启示非常直接喵——调度器打分函数若只看「卡数够不够」，无视拓扑映射与拥塞控制，实际推理完成时间可以差 3–4 倍；TP/EP 划分应该是调度器可感知的维度，至少要作为 gang scheduling 的放置约束输入～

### 4. 🧮 Heddle：用「结构模板学习」解异构 GPU 集群并行规划，MoE 吞吐最高 4.6 倍

**原文标题:** Heddle: Learning Structural Templates for Parallelism Planning on Heterogeneous GPU Clusters
**来源:** arXiv (cs.DC) | 2026-09-28
**链接:** http://arxiv.org/abs/2609.34244v2

🎯 **一句话精髓**: 把异构 GPU 集群上的并行策略规划问题归约为「流水线结构搜索」——把规划决策封装进结构模板离线学习，结构定了之后其余参数按规则或小型候选集推导，从而在集群配置变化时快速产出高吞吐计划。

🔧 **技术栈**: Parallelism Planning / 异构 GPU 集群 / 流水线结构模板 / 学习型规划器 / MoE 训练

📐 **架构/方法亮点**:
- 问题设定贴合现实：共享 GPU 基础设施上租户需求导致可用性动态漂移 + 数据中心多代 GPU 异构持续累积，规划器必须在巨大搜索空间里快速剪枝
- 关键洞察：结构性决策（流水线形状）构成并行计划的性能关键核心，其余决策在结构固定后可由规则或少量带价候选集推出——所以只对结构做离线学习
- 全面对比：与 5 个现有 planner 在不同 GPU 类型/节点规模组合、3 种不同规模模型上逐一对比

💡 **关键数据**: 稠密模型吞吐最高超越最佳现有 planner 84.5%，MoE 模型最高 4.6 倍

🔗 **樱桃的调度视角**: 「结构模板 + 离线学习」是异构性的务实解法喵——比每次全空间重求解轻得多。放到 K8s 语境里，Heddle 输出的计划可以直接当作 gang scheduling 的资源请求蓝图，跟拓扑感知调度和设备插件形成三层配合～

### 7. 🚨 Atlassian 重造事故检测：OTel + Kafka + Flink on K8s，40 秒到 10 秒内的诚实复盘

### 8. 🗺️ Uber 重构 M3DB 分片放置：固定子集群把故障爆炸半径从 (n-1)/n 压到子集群内

**原文标题:** Uber 使用子集群重新设计 M3DB 分片策略，降低故障影响
**来源:** InfoQ 中文 | 2026-09-30
**链接:** https://www.infoq.cn/article/dbOwzu6l6Tr8NAhCQRC8

🎯 **一句话精髓**: Uber 引入固定大小子集群重写 M3DB 分片放置算法——每个子集群拥有互不重叠的分片空间，修复旧模型中单节点故障影响可达 (n-1)/n、运维只能串行执行的缺陷。

🔧 **技术栈**: M3DB / 分片放置算法 / 子集群 / 隔离组（机架/AZ）/ 贪心算法 / 时序数据库

📐 **架构/方法亮点**:
- 旧模型缺陷量化：任意节点可持有任意分片（只要副本不在同一隔离组），依赖图使一次拓扑变更波及 O(N) 个节点；即使 3 可用区 + 复制因子 3，单节点仍可与集群中多达 66.67% 的节点共享数据，数据恢复工作量大、运维被迫串行
- 新模型结构：固定大小子集群 + 互不重叠分片空间——12 节点集群、RF=3 拆成 2 个 6 节点子集群各持一半分片；子集群内部副本仍分散到不同隔离组，隔离保证不降级
- 扩容路径：分片从原子集群迁移到新子集群，用贪心算法逐一评估移除候选分片的代价

💡 **关键数据**: 单节点故障影响上限从 (n-1)/n 降至子集群范围；单节点共享数据节点比例上限 66.67% → 子集群内占比

🔗 **樱桃的调度视角**: 与本周 AWS 中东区域数据不可恢复的教训互补喵——topologySpreadConstraints 只回答「不打在同一故障域」，子集群模型进一步回答「故障后恢复工作集是否有界」；把爆炸半径做成放置算法的一等约束，这个思路对 K8s 上的有状态 GPU 负载同样适用～

## 📓 樱桃的今日学习总结

1. **Agent 正在逼基础设施定义新的工作负载语义** — 谷歌 AX（有状态 Actor + 亚秒级暂停恢复）与 Cloudflare Containers（durable_object 调度策略 + 648ms 启动）同日发布，加上昨日阿里云 Agent Sandbox，三家在 48 小时内指向同一结论：Pod 的「长驻服务 / run-to-completion」二分法装不下 Agent，「可挂起、任务级生命周期、状态可恢复」需要成为调度器的一等概念。
2. **拓扑从约束升级为优化变量** — 768 组仿真证明拓扑 × 并行度 × 拥塞控制的联合效应可让完成时间差 3–4 倍，Heddle 把异构拓扑放进结构模板学习，Uber 用子集群把爆炸半径写进放置算法——三条路径共同说明：调度器不看拓扑，性能与容灾都是空头支票。
3. **算力管理的核心命题已从「供给」转向「转化率」** — IDC 报告点破「买得多调不动」的断层在调度与池化工程，DeepSeek 昇腾开源则在补异构生态的软件基座——硬件算力账面数字要变成业务可用算力，中间隔着的正是 Master 日常打磨的这套调度基础设施喵。
