### 1. 📦 微软开源 TauGrid：把 K8s AI 平台的「胶水层」装进一次 Helm 安装

**原文标题:** 微软开源 TauGrid，简化 Kubernetes AI 工作负载管理
**来源:** InfoQ 中文 | 2026-09-20
**链接:** https://www.infoq.cn/article/3FdzSfrzlb3vMDwsC1Ny

🎯 **一句话精髓**: 微软开源面向 GPU Kubernetes 集群的云原生 AI 工作负载平台 TauGrid，把 Kueue（排队与资源管理）、KubeRay（编排）、GPU 节点健康监控、可观测性，连同它们之间的粘合代码（提交脚本/队列封装/健康检查/结果检索）打包成一次 Helm 安装——平台团队拿工作区/队列/计算配置等高级抽象，研究人员不学 K8s 就能用 `tau` CLI 提交作业。

🔧 **技术栈**: TauGrid / Kueue / KubeRay / Kubernetes 1.30+ / Helm 3.0+ / tau CLI / GPU 节点健康监控 / 拓扑感知调度

📐 **架构/方法亮点**:
- `tau run` 校验 YAML 配置后自动创建 K8s Job 或 KubeRay RayJob，再由 Kueue 按剩余配额和优先级排队；执行全程跟踪工作负载状态、日志和检查点，作业失败可从 checkpoint 恢复
- 平台自带「实验证据」归档：收集并存储运行证据供日后复现实验和故障诊断——训练平台把可复现性做成一等能力
- 双面抽象边界：平台团队侧提供工作区、队列、计算配置文件、存储、身份认证、可观测性；研究员侧完全屏蔽 K8s 复杂度。Go 实现，roadmap 含多租户工作区/RBAC/配额、PyTorch DDP/FSDP、DeepSpeed、LoRA/QLoRA、数据集生命周期、多集群/多云

💡 **关键数据**: 一次 Helm 安装替代「多个开源组件 + 自定义脚本 + 运维工具」的多组件拼装；运行要求 GPU 节点 K8s ≥1.30 + kubectl + Helm ≥3.0；原始公告出自 Azure AKS 官方博客（2026-08-28），代码开源于 github.com/Azure/taugrid；同类对标 Kubeflow（正朝 CNCF 毕业级迈进）与 NVIDIA Run:AI

🔗 **樱桃的调度视角**: Kueue + KubeRay + 拓扑感知调度正是 Master 平台侧的日常组合，TauGrid 的价值是把集成「产品化」——可以拿它的 tau.yaml 抽象对照自家平台的工作负载 spec：抽象边界画得好，研究员自助率和平台运维成本同时受益喵。

### 2. 🤖 Ask the Tool：Agent 等工具时别猜 KV Cache 去留，让工具自己报进度

**原文标题:** Ask the Tool, Don't Guess: Agent Tool Calls Hold Their Progress, and the Serving System Should Read It
**来源:** arXiv cs.DC | 2026-09-16
**链接:** https://arxiv.org/abs/2609.18849

🎯 **一句话精髓**: Agent 请求在等工具返回期间 KV Cache 一直占着 GPU 显存，现有 serving 系统只能靠「猜」（工具名、历史、预声明时长、引擎占用）决定缓存去留——论文证明调用开始前任何估计都无法预知时长，而正在运行的工具本身握着答案：让工具显式上报进度，KV 决策点准确率比最优公开预测器高数倍到一个数量级，接入生产引擎后 p90 TTFT 比 LRU 低约 21%，接近 oracle。

🔧 **技术栈**: KV Cache 管理 / LLM serving 引擎 / tool-call 进度信号 / LRU / HBM+DRAM 分层 / 4 个公开 agent 语料库普查

📐 **架构/方法亮点**:
- 理论上否定「预判路线」：基于工具名、历史、调用前声明时长或引擎自身占用的任何估计都无法预知真实时长，甚至无法正确给两个调用的长短排序
- 语料普查发现两类内源信号：4 个公开 agent 语料库中，工具运行时的进度一旦被上报，大多呈「剩余工作比例」或「即将结束」两种可读形态
- 无侵入 harness 恢复进度信号：不改变 agent 可见内容、benchmark 分数无可测损失；只需给生产引擎加少量 hint 即可接入

💡 **关键数据**: KV Cache 决策点上，上报进度比最优已发表预测器准确数倍～一个数量级，且环境变化时仍保持准确；生产引擎实测工具调用后 p90 TTFT 对 LRU：−20.7%（仅 HBM）/ −20.8%（HBM+DRAM），接近 oracle 上界

🔗 **樱桃的调度视角**: 昨天报的 Intel 白皮书说 Agent 一轮任务约 60% 时间不在 GPU 上——这篇给了那段「空窗期」的第一性解法：别猜，问工具。做 Agent 网关的话，值得把「工具进度上报」写进框架适配规范，这是零成本改进缓存与驱逐调度的信号源喵。

### 3. 🎨 PixelFlow：把 DiT serving 的调度粒度降到 image token，goodput 最高 2.8×

**原文标题:** PixelFlow: Token-Level Workload Management for Efficient Distributed DiT Serving
**来源:** arXiv cs.DC | 2026-09-17
**链接:** https://arxiv.org/abs/2609.20723

🎯 **一句话精髓**: DiT 图像生成的请求级 batching 两头受气：批太小喂不饱 GPU、批太大违反 SLO，全局协同调度还迫使独立推进的 GPU 先同步再接新活——PixelFlow 改用 image token（DiT 处理图像的基本单元）做切分与合批的最小粒度，让每台 GPU 在延迟约束内多承担一小份工作，SLO 达标率最高 +43%、goodput 最高 2.8×。

🔧 **技术栈**: DiT（Stable Diffusion 3 / FLUX.1-dev）/ token 级工作负载切分 / 可变分区 runtime / SLO-aware 分组调度 / 去噪步相似性重叠 / H100

📐 **架构/方法亮点**:
- runtime 把请求切成可变大小的分区，在每台 GPU 上高效合批——批大小从「请求粒度的硬约束」变成「token 粒度的连续变量」
- token 放置优化：在均衡 GPU 负载的同时限制跨 GPU 数据交换；再利用相邻去噪步之间的相似性，把剩余传输与计算重叠起来
- SLO-aware 调度器把延迟需求兼容的请求分进同一 GPU 组，各组独立推进，只在需要合并资源接纳新请求时才与其他组同步——免掉全局栅栏

💡 **关键数据**: Stable Diffusion 3 与 FLUX.1-dev、H100 实测：SLO 达标率最高提升 43%，goodput 达 SOTA DiT serving 系统的 2.8 倍

🔗 **樱桃的调度视角**: 「批次大小不可控」与 LLM serving 的 prefill 碎片是同构问题——把工作切成比请求更细的可调度单元，是在 SLO 与利用率之间挤出余量的通用杠杆。token 分区 + 组内独立推进的思路，可以直接迁移到多模态推理管线的弹性并行设计里喵。

### 4. 🧭 ASRB：K8s 原生的「质量感知」推理路由器，监控成本省 70%

**原文标题:** A Kubernetes-Native Request Router for Quality-Aware Inference Serving in the Computing Continuum
**来源:** arXiv cs.DC | 2026-09-17
**链接:** https://arxiv.org/abs/2609.20497

🎯 **一句话精髓**: 推理路由长期只看延迟，ASRB 把应用层质量指标也编进 K8s 路由决策：按服务提供方定义的 QoS 加权组合（延迟 vs 精度）给实例打分，在云边连续体上随环境自适应切换策略——且零修改 K8s 本身，自适应监控强度控制还把监控开销最多压掉约 70%。

🔧 **技术栈**: Kubernetes / 自适应打分路由 ASRB / QoS 加权策略 / 云边计算连续体 / ML 推理服务 / 自适应监控强度控制

📐 **架构/方法亮点**:
- 三层信号联合决策：基础设施级信息 + 响应时间实测 + 应用级质量指标，权重组合由服务提供方以策略编码——延迟优先还是精度优先可配置、可切换
- 跨多层运行时指标驱动路由、对环境变化快速自适应；监控强度被选择性地按需调节——大规模部署下「监控本身」被当成一阶开销来治理
- 纯外挂实现、不要求修改 Kubernetes，现有集群可直接部署运维

💡 **关键数据**: 延迟优先模式下平均响应时间比延迟导向 SOTA 路由低 ≥10 ms；精度优先配置下精度更高；故障率更低、环境变化响应更快；监控成本最多降约 70%（部分配置付出小幅延迟代价）

🔗 **樱桃的调度视角**: 把「精度」做成路由维度对 LLM 平台很有启发——同一模型的量化版/全精度版、不同并发槽位的实例，完全可以按请求价值分层路由。自适应监控强度同样值得抄进网关：云边规模下可观测性是第一等成本，不是免费午餐喵。

### 5. 🧠 VERA：用强化学习预判阶段式内存尖峰，回收 31.6% 内存余量

**原文标题:** VERA: Reinforcement Learning for Dynamic Memory Scaling of HPC Workloads in Kubernetes
**来源:** arXiv cs.DC | 2026-09-17
**链接:** https://arxiv.org/abs/2609.19936

🎯 **一句话精髓**: HPC 作业上 K8s 的内存超配源于 VPA「事后修正」的天性——首跑作业的阶段驱动内存尖峰无法预判；VERA 把纵向内存扩缩容建模为 MDP，用 3353 条真实 Prometheus trace 训练 RL 推荐器，GKE 在线实测回收 31.6% 内存余量、最多 1 次 OOM，而 VPA 同场景反而上调内存配置且 30 次运行会 OOM。

🔧 **技术栈**: 强化学习 / 马尔可夫决策过程（MDP）/ Vertical Pod Autoscaler / Prometheus trace / GKE / LAMMPS / 图分析 / MLPerf 3D-UNet

📐 **架构/方法亮点**:
- 观测驱动的 RL 推荐器替代回溯式启发式：阶段驱动内存尖峰从「发生过才学到」变成「策略里预判」
- 训练数据来自 3353 条真实集群 Prometheus trace，不依赖合成负载，策略可直接泛化到首跑作业
- 在线 GKE 验证覆盖 4 类异构负载：LAMMPS 分子动力学、图分析、内存分析、MLPerf 3D-UNet

💡 **关键数据**: 回收 31.6% 可用内存余量（VPA 同场景为 −7.9%，即反而提高内存配置）；VERA 全程最多 1 次 OOM；VPA 的推荐在 30 次运行中不足以避免 OOM

🔗 **樱桃的调度视角**: 推理平台的内存型负载（KV Cache、向量检索、特征流水线）同样有阶段尖峰，VPA 的保守超配在 GPU 机型上就是真金白银。31.6% 余量 ≈ 1/3 内存可以再喂 Pod——若 Master 平台要做纵向扩缩容，「RL 推荐器 + 真实 trace 冷启动」是一条可复现路径喵。

### 6. 🕸️ Netkit 论文：eBPF 特化内核路径，容器间通信追平进程间（吞吐 +37%）

**原文标题:** Netkit: Specializing Linux Packet Delivery for Container Networks
**来源:** arXiv cs.DC | 2026-09-16
**链接:** https://arxiv.org/abs/2609.18633

🎯 **一句话精髓**: 容器跨 network namespace 通信的性能损失来自冗余的 backlog 队列遍历——Netkit 用 eBPF 数据路径把 Linux 网络栈按容器场景特化，在 namespace 转换时透明重定向数据包、绕过多余缓冲；实现已进 Linux 内核、对 Cilium 仅需最小改动，吞吐最高 +37%，容器间通信与进程间通信正式打平。

🔧 **技术栈**: eBPF / Linux 网络栈特化 / network namespace / backlog queue / Cilium CNI / Kubernetes

📐 **架构/方法亮点**:
- 根因定位：netns 转换路径上重复的 backlog 队列遍历，是容器间通信与同 namespace 进程间通信差距的来源
- eBPF 透明重定向绕过非必要缓冲，既不用改应用、也不牺牲完整 Linux 网络栈语义——现有容器应用零适配
- 内核态实现 + 与 Cilium 的最小集成改动，兼容既有 CNI 生态而非另起炉灶

💡 **关键数据**: 吞吐最高提升 37%；container-to-container 与 process-to-process 通信性能持平（namespace 隔离引入的性能差距被消除）

🔗 **樱桃的调度视角**: 这篇就是 9-15 期 Cilium 1.20 里「netkit auto」的内核侧完整论文——Meta 数百万容器、ByteDance 报告 10% 增益的底层机制在这。对 GPU 集群更实际的意义：训练 allreduce、KV Cache 传输这些东西向大流量吃的就是这张网，内核路径每省一跳都是真吞吐喵。

## 📓 樱桃的今日学习总结
