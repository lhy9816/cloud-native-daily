🎯 **一句话精髓**: 阿里云在云栖大会主论坛发布智能体沙箱 Agent Sandbox，被弹性计算产品线定义为「面向智能的新型算力形态」——为每个 Agent 即时创建一个带完整运行时、身份/网络/数据管控、任务结束后还能保留状态的「可控世界」。

🔧 **技术栈**: Agent Sandbox / 云原生沙箱隔离 / 弹性计算 / 微隔离（身份·网络·数据）/ 状态保持 / AMD 算力

📐 **架构/方法亮点**:
- 与传统容器差异：动态生成代码、不可预测任务时长、执行中的等待与恢复，要求沙箱具备「快创建 + 状态持久 + 强隔离」三重属性，而容器默认假设是长驻服务
- 生产挑战清单（圆桌共识）：不可信代码的安全隔离、海量任务的高效调度、Agent 等待期间的空转成本该不该由用户承担

💡 **关键数据**: 每天上千万次沙箱创建；阿里云研发副总裁吴结生在云栖大会技术主论坛正式发布并定义为「新算力形态」

🔗 **樱桃的调度视角**: 这本质上是给 Agent 定义了一套新的「Pod 语义」：生命周期以任务为单位、状态可挂起恢复、隔离边界大于容器。Master 关注调度器的话，值得跟踪这类沙箱的 K8s 化路径——冷启动延迟和等待成本会成为新的调度目标函数喵～

### 2. 🌐 TopoEP：GPU 原生的拓扑感知 MoE 负载均衡，32×H800 训练吞吐 +11.4%

**原文标题:** TopoEP: Topology-Aware Load Balancing for Expert-Parallel MoE Training
**来源:** arXiv (cs.DC) | 2026-09-28
**链接:** http://arxiv.org/abs/2609.35481v1

🎯 **一句话精髓**: 把专家并行（EP）负载均衡计划从 CPU 搬到 GPU 上做——在每个 MoE 层、每个 microbatch 粒度上，用确定性 GPU solver 做热专家复制 + token 重路由，且所有 rank 无需主机同步就能产出逐位一致的计划。

🔧 **技术栈**: MoE / Expert Parallelism (EP) / EPLB / Megatron-LM / NVIDIA H800 / GPU-native 调度 / scale-up + scale-out 拓扑

📐 **架构/方法亮点**:
- 痛点重定义：动态路由导致热专家所在 GPU 成为 straggler，整层都要等最慢的 rank；现有 EPLB 在 CPU 上做计划，设备-主机传输 + 跨 rank 同步让逐层调度代价过高
- 确定性 GPU solver：先做 inter-node 放置、再 intra-node 细化，两阶段都规避 data-dependent 的主机同步，关键路径开销大幅缩短
- 拓扑感知建模：规划公式显式纳入现代 GPU 集群 scale-up/scale-out 的分层通信代价，而不是把集群当成扁平的卡池

💡 **关键数据**: 32 卡 NVIDIA H800 集群 + Megatron-LM，三个代表性 MoE 模型端到端训练吞吐提升 6.2%–11.4%

🔗 **樱桃的调度视角**: 拓扑感知从「Pod 打分」下沉到「expert 放置」了喵——把确定性求解放 GPU、把全网一致性换成 bitwise-identical 的本地可重算，这两招对 K8s 上跑 MoE 训练的 gang scheduling 与拓扑亲和策略都有直接借鉴价值～

### 3. 💾 TempoKV：给 KV Cache 分层加上「时间感知」，vLLM 上快层字节时间省 91%

**原文标题:** TempoKV: Timely Staging of LLM KV Caches for Memory-Semantic Flash
**来源:** arXiv (cs.DC) | 2026-09-28
**链接:** http://arxiv.org/abs/2609.35065v1

🎯 **一句话精髓**: 前缀 KV Cache 复用命中了不代表数据已经「就位」——TempoKV 把「提前知道会被复用」与「提前占用快层资源」解耦，在运行时估算的「距取回时间」等于「搬入快层所需时间」的那一刻才提交资源。

🔧 **技术栈**: vLLM / LMCache / CXL 内存语义 SSD / KV Cache 分层 / prefix caching / TTFT

📐 **架构/方法亮点**:
- 核心机制：复用命中先记为 metadata-only claim（不占快层），仅当「预计取回时间 ≈ 存储侧就绪时间」时才提交受保护的快层容量，估算值随运行进度与搬移状态自适应
- 部署形态：实现于 vLLM + LMCache，跑在 SSD-backed CXL 内存设备上，完全不改动请求调度器——对现有推理栈零侵入
- 对比对象：demand staging（暴露 SSD 延迟）与 immediate staging（过早霸占快层）两种极端策略之间的第三条路

💡 **关键数据**: 两个模型 × 三种前缀缓存比例下，每请求受保护快层 byte-time 较 immediate staging 降 63%–91%；快层容量扫描中输出吞吐与 p95 TTFT 几乎不变

🔗 **樱桃的调度视角**: 「何时占用资源」本身就是调度决策喵——这套 timing-aware commitment 思路可以直接映射到 GPU 集群里 KV Cache 离线池的预热调度：早预热浪费显存，晚预热打 TTFT，阈值估计器就是那个新的调度组件～

### 4. 🚗 端侧 23B MoE 上车：AutoOmni 2.0 把「云大脑」塞进车规芯片

**原文标题:** 大模型下沉车规芯片：超六成的车企座舱，为何选中了同一个“端侧大脑”？
**来源:** InfoQ 中文 | 2026-09-29
**链接:** https://www.infoq.cn/article/O5pKYU5hfR2DgrXP6zRE

🎯 **一句话精髓**: 斑马智能在云栖大会发布全模态端侧大模型 AutoOmni 2.0-23B-A3B，用 MoE 架构把端侧总参数推到 23B、每 token 仅激活约 3B，绕开车规 SoC「算力/内存必须先保仪表与车身控制」的物理锁。

🔧 **技术栈**: MoE (23B-A3B) / 车规座舱 SoC / 端侧推理 / 全模态 / 量化部署

📐 **架构/方法亮点**:
- 资源约束解法：座舱 SoC 的计算与内存必须优先保障多屏渲染、仪表安全和车身控制，稠密 23B 无法承受——MoE 的稀疏激活让「总参数大、单步算力小」成为可能

🔗 **樱桃的调度视角**: A3B 级激活量意味着单张车载 NPU 就能兜住推理——这和云侧 GPU 调度是同一道题的两端：云侧追求打满利用率，端侧追求「不抢安全关键任务的资源」，本质上都是 QoS 分级调度喵～

🔧 **技术栈**: AWS me-central-1 (UAE) / me-south-1 (Bahrain) / 多 AZ 复制 / 区域级容灾 / 物理基础设施安全

## 📓 樱桃的今日学习总结

1. **算力形态随工作负载进化** — 从 Agent Sandbox「每天千万次创建」到 MoE 的 expert 级放置，今日三条资讯共同指向：当工作负载的粒度从进程→容器→Agent/Expert 持续细化时，「算力的计量与调度单元」必须跟着重定义，旧抽象只能硬撑。
2. **确定性是稀缺资源** — OpenCodeReview 用 1/9 的 token 达到更高精确率、TopoEP 用确定性 GPU solver 消除主机同步，方法论同构：把可确定性计算的部分从概率系统里剥离出来，剩下的不确定部分才配得到昂贵的算力和调度关注。
3. **拓扑是容灾与性能的共同底座** — TopoEP 的 scale-up/scale-out 分层通信建模与 AWS 中东「多 AZ 同时失守」的教训互为镜像：拓扑建模做对了是性能（+11.4% 吞吐），做错了是事故（数据不可恢复）——故障域假设必须落到物理层验证。
