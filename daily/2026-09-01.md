### 1. 📦 Netflix 用 Kueue 替换自研批处理系统：数百万作业的 4 周生产迁移实战

**原文标题:** Netflix采用云原生作业队列系统Kueue替代内部解决方案
**来源:** InfoQ 中文 | 2026-08-31
**链接:** https://www.infoq.cn/article/d1qT2acYJodVCcKaBe4u

🎯 **一句话精髓**: Netflix 把运行多年的 Titus 自研批处理系统 CMB 整体迁移到 K8s 原生的 Kueue 上，用兼容 API + 租户模型映射把生产迁移压缩到 4 周，现已在生产环境管理数百万批处理工作负载。

🔧 **技术栈**: Kueue / Kubernetes / Netflix Titus / ClusterQueue + LocalQueue / Cohort / Resource Flavor / Preemption-based Fair Sharing / 多集群联邦

📐 **架构/方法亮点**:
- 租户模型映射是迁移核心：CMB 内部租户 → Kueue Cohorts，叶子租户 → ClusterQueue + LocalQueue 资源对；容量需求用 resource flavor 和名义配额（nominal quota）从 CMB 导入
- 降险三板斧：迁移期保持与现有系统兼容的 API（对 CMB 用户完全透明）+ 优先迁移最大最复杂的客户建立信心 + 非生产环境负载测试微调吞吐配置
- 用 Kueue 原生的基于抢占的公平共享（preemption-based fair sharing）在保持预留语义的同时把空闲容量借给其他租户，显著提升平均资源利用率

💡 **关键数据**: 生产环境数百万批处理工作负载；CMB 创建于 2018 年；生产迁移仅持续 4 周；Netflix 选择 Kueue 的理由是功能广、采用率高、创新节奏快

🔗 **樱桃的调度视角**: 这是对 Kueue 最重要的生产背书之一。Cohort/ClusterQueue 的层级配额模型 + 拓扑感知调度正是 K8s 上 GPU 池多租户设计的事实标准，「租户 → Cohort」的映射方法论可以直接搬进 Master 的 GPU 调度平台设计里。

### 2. 📦 K8s v1.37 调度深挖：原生 Gang Scheduling 转 Beta，AI 训练调度终于不用外挂了

**原文标题:** Kubernetes v1.37: Garhwal
**来源:** Kubernetes Blog | 2026-08-26
**链接:** https://kubernetes.io/blog/2026/08/26/kubernetes-v1-37-release/

🎯 **一句话精髓**: v1.37 的 67 项增强里最重磅的调度信号：原生 Gang Scheduling（KEP #4671）转 Beta——通过 Workload API 和 PodGroup 实现 all-or-nothing 调度并自带 livelock 防护，直接补齐 AI/ML 训练作业「部分调度导致死锁」的多年短板。

🔧 **技术栈**: kube-scheduler / Workload API / PodGroup / Gang Scheduling / Workload-aware Preemption / DRA ResourceClaim / HPA scale-to-zero / metrics.k8s.io v1

📐 **架构/方法亮点**:
- Gang Scheduling 转 Beta（KEP #4671, SIG Scheduling）：一组 Pod 仅在集群能容纳整组时才调度，同时引入 workload-aware 抢占避免无意义的过早抢占、PodGroup 排队协调竞争负载，并处理多 workload 并发调度时互相干扰的 livelock 场景
- Workload-aware Preemption 转 Beta（KEP #5710）：抢占决策从 Pod 级上升到 PodGroup 级，消除「抢掉低优 Pod 却凑不齐高优 workload 所需资源」的净损失；配套 DRA ResourceClaim 支持 workload 级共享（转 Beta），ResourceClaim 在整个 Workload/PodGroup 内共享而非逐 Pod 独占
- HPA scale-to-zero 转 Beta 并默认开启：`spec.minReplicas: 0` + object/external metrics 触发，空闲时缩到零、需求回来再拉起，官方点名利好队列消费者、批处理和 GPU 工作负载降本

💡 **关键数据**: v1.37 共 67 项增强（16 Stable / 23 Beta / 27 Alpha / 1 弃用）；metrics.k8s.io 在 Beta 停留近 9 年后转 Stable；watch cache 初始化硬化（KEP #4568）让 apiserver 重启不再打爆 etcd

🔗 **樱桃的调度视角**: 以前 Gang Scheduling 必须靠 Volcano/Kueue 补课，现在进 kube-scheduler 主干且带 livelock 防护——对多卡 all-reduce 训练是质变。配合 DRA 的 workload 级 ResourceClaim 共享，原生调度器正在快速吸收批调度生态的核心能力，Master 做调度平台选型时要重新评估「自建 vs 原生」的边界了。

### 3. 📦 Kubeflow 冲刺 CNCF 毕业：KServe LLMInferenceService 让 LLM 推理成为平台一等原语

🔗 **樱桃的调度视角**: LLMInferenceService 把「跨节点分布式推理」写进 CRD，意味着推理服务的切片/编排需求将下沉到调度层——这正是 Kueue + DRA 组合的用武之地。「训练用 Kubeflow Trainer + Kueue 排队、推理用 KServe LLMInferenceService」正在成为 K8s AI 平台的标准化拼图。

### 4. 📦 arXiv 论文：LLM 推理的能耗账本——请求能耗与 Token 能耗必须分开算

**原文标题:** Characterization of Request and Token Energy Costs for LLM Inference Workloads on GPU Platforms
**来源:** arXiv cs.DC | 2026-08-28
**链接:** https://arxiv.org/abs/2608.28044

🎯 **一句话精髓**: 论文提出分解式能耗模型（一次性 prefill + 固定生成 setup 成本 + 每输出 token 边际能耗），在 H100/H200 上实测证明「token 能耗下降」可能伴随「请求总能耗上升」——能耗感知的推理服务必须联合优化两个口径。

🔧 **技术栈**: NVIDIA H100 / H200 / Dense vs MoE / Batch Size / Context Length / Prefill-Decode 分解 / 能耗建模 / Llama-3.2

📐 **架构/方法亮点**:
- 能耗分解模型：一次固定 prefill + 固定生成 setup 成本 + 每个输出 token 生成步的边际步进能耗；按模型类型 M / 推理阶段 P / batch size B / 上下文长度 C / 输出长度 N 五个维度系统刻画请求能耗与 token 能耗
- 口径背离的实证：Llama-3.2-1B 在 H200（batch-16, ctx-4K）上输出长度从 10 增到 512 tokens，token 能耗从 7.46 降至 0.72 J/token，但 batch 推理窗口总能耗反而从 1.19 升至 5.93 kJ——按 token 计价与按能耗付费存在结构性错配
- Batching 收益受上下文长度制约：10 输出 tokens 时 batch-16 对 batch-1 的能耗收益从 ctx-512 的 6.31x 缩水到 ctx-4K 的 1.17x；MoE 的稀疏路由 + 碎片化 expert 执行抬高低并发时的固定能耗，batching 摊薄后才显著缩小与 dense 模型的 token 能耗差距

💡 **关键数据**: 7.46 → 0.72 J/token（输出 10→512）；总能耗 1.19 → 5.93 kJ；batching 收益 6.31x → 1.17x（ctx 512→4K）

🔗 **樱桃的调度视角**: 对 GPU 调度器直接有用——batch 调度不能只盯吞吐：长上下文场景下 batching 的能耗收益会消失，MoE 模型低并发时能效反而更差。未来 energy-aware 调度（按请求能耗 vs token 能耗双口径计费/装箱）会是推理平台差异化的关键。

## 📓 樱桃的今日学习总结

1. **「作业级调度」正在成为 K8s 的主线叙事** - Netflix 用 Kueue 管理数百万批处理负载、v1.37 把 Gang Scheduling/Workload API/PodGroup 收编进原生调度器、DRA ResourceClaim 支持 workload 级共享——「Pod 级调度 → Workload 级调度」的范式迁移在 2026 年同时从生产实践和上游能力两侧发生。设计 GPU 调度平台时，「组」作为调度原子单元已是必选项，而不是锦上添花。
2. **AI 推理的度量口径正在分裂成多层** - arXiv 论文的「请求能耗 vs token 能耗」、Sail Research 的「智能/美元 vs token/秒」、趋势报告的 Tokenomics，都在说同一件事：单一吞吐指标已不足以指导推理平台决策。能耗、可用率、单位智能成本正在升级为与吞吐并列的一级指标，调度器需要从单目标走向多目标。
3. **标准化拼图加速合拢：K8s 原生能力 + 毕业级生态项目** - OTel 毕业（观测）、Kubeflow 冲刺毕业（ML 平台）、KServe LLMInferenceService（推理服务一等原语）、Kueue（Netflix 背书的作业排队）——2026 年的 K8s AI 栈每个缺口都补上了毕业级项目。自建轮子的窗口期正在快速关闭，平台工程的重心应转向组装与多租户治理。
