### 1. 📦 DeepSeek 开源生产级推理框架 DeepInfer：单集群日吞吐 155 万亿 Token

**原文标题:** DeepSeek开源最新推理框架：单集群日吞吐155万亿Token，KVCache可保存7天
**来源:** InfoQ 中文 | 2026-10-21
**链接:** https://www.infoq.cn/article/NBXP966Bz3eqr6Qidvaf

🎯 **一句话精髓**: DeepSeek 将支撑 V4.1 Flash 线上服务的推理系统 DeepInfer 开源，首次公开了超大规模 PD 分离 + 集群级 KVCache 数据层的完整实现逻辑，是目前公开细节最全的大模型推理基础设施参考。

🔧 **技术栈**: DeepInfer / deepseek-recipe / 3FS 分布式存储 / Wide-EP（64-128 路专家并行）/ GDR-RDMA / NVIDIA+昇腾

📐 **架构/方法亮点**:
- **PD 异构分离**：普通 8 卡机做 Prefill、64-128 卡超节点做 Decode，视觉编码器/Prefill/Decode 三阶段独立扩缩容，分别优化 TTFT 和 TBT
- **KVCache 升级为集群级共享数据层**：Block KVCache（128 Token 分页）写入独立 3FS 集群（约 100 PiB SSD，峰值读 10 TiB/s / 写 850 GiB/s），所有 Prefill 机器可命中任意前缀，**彻底放弃前缀亲和路由**，避免缓存路由与负载均衡冲突
- **集群自动扩缩容 + 弹性容错**：Prefill 按未命中 Token 数、Decode 按实际请求数双向估算，配额占用率 >0.8 直接禁止缩容；Decode 实例下线有 1 分钟宽限期，未完成请求连同 KVCache 一次性转发给其他实例
- **分层负载均衡**：Prefill/Decode/Vision/Expert-Parallel 四个独立 LB；Prefill 按输入长度分 <16K/16K-64K/64K-256K/>256K 四档动态分配引擎；每卡部署冗余热门专家副本按负载重分配

💡 **关键数据**: 单集群日吞吐 155 万亿 Token；按谷价计算单卡每小时收益 38 美元；KVCache TTL：Agent 流量 3 天 / Chatbot 流量 7 天（TTL 缩到 3 天命中率掉 0.5%-1%）；3FS 峰值聚合读带宽 10 TiB/s

🔗 **樱桃的调度视角**: Master 这篇必读喵！它用真金白银验证了"存储与计算分离"在 GPU 集群上的极致形态——KVCache 池化让调度彻底摆脱会话亲和性约束，这正是我们在 K8s 上做 GPU 调度器时 prefix-cache 感知 vs 吞吐优先矛盾的最优解参考。

### 2. 🎛️ CNCF 深度长文：AI 工作负载正在重塑 Kubernetes 自动扩缩容

**原文标题:** How AI workloads are reshaping Kubernetes autoscaling
**来源:** CNCF Blog | 2026-10-19
**链接:** https://www.cncf.io/blog/2026/10/19/how-ai-workloads-are-reshaping-kubernetes-autoscaling/

🎯 **一句话精髓**: K8s 调度器与 autoscaler 对硬件能力的"认知割裂"是 GPU 集群资源浪费的根源，社区正在用 DRA + Workload API + Provisioning Request 把两条控制回路缝合起来。

🔧 **技术栈**: DRA (Dynamic Resource Allocation) / Workload & PodGroup API / Provisioning Request / Kueue / Gateway API

📐 **架构/方法亮点**:
- **DRA 统一硬件语言**：ResourceClaim 支持拓扑约束（如 GPU 与其网络接口绑定）、设备分区（整卡切固定小份）与 consumable capacity（多个 claim 按份共享一卡），调度器与 DRA-aware autoscaler 读取同一份容量模型
- **Gang 调度的"单边修补"困境**：Workload/PodGroup API 已 beta 但默认禁用，调度器学会了"全有或全无"，而 autoscaler 仍逐 Pod 决策——会为 gang 的几个 pending Pod 单独扩节点，反而浪费算力
- **Provisioning Request 是当前的桥**：Kueue 通过 admission check 预留配额 → 原子化向 autoscaler 请求整组容量 → 确认就绪后才 admit 工作负载；但原子扩容仍依赖云厂商支持，本质是"跨缝螺栓"而非共享理解
- **社区动向**：SIG-Autoscaling 公开提案正设计集成 API——让调度器能看到"可被供给的容量"而不仅是现存节点

💡 **关键数据**: 文中核心论断——autoscaler 扩容前需要"模拟调度器的 placement 决策"，节点建好后调度器再做一次同样的推理，同一逻辑被完整执行两遍；gang 场景下半放置的 job 会直接搁浅整机硬件

🔗 **樱桃的调度视角**: "one hardware model, two consumers" 这个心智模型值得刻在脑子里喵！我们做 GPU 节点池规划时，Pod pending 不一定是没容量，而是调度器和 autoscaler 对"什么是可用节点"认知不一致——先查这两条回路是否共享同一份 DRA 真相。

### 4. 💰 Cloudflare 详解：如何把 AI 代码评审的推理账单砍掉 68%

**原文标题:** Cutting our inference bill by 68% by being obsessive about optimization
**来源:** Cloudflare Blog | 2026-10-19
**链接:** https://blog.cloudflare.com/obsessive-inference-optimization/

🎯 **一句话精髓**: 一份教科书级的 LLM 应用成本解剖——从 prompt cache 前缀共享、工具瘦身到模型/effort 分档，把每次评审成本从 $2.43 优化到 $0.77，且评审质量不降。

🔧 **技术栈**: Anthropic Prompt Cache / OpenCode v2 / Claude Opus 5.5 & Sonnet 5.5 / GitLab CI (K8s executor) / Durable Objects (pi-durable 实验中)

📐 **架构/方法亮点**:
- **跨仓库共享 cache 前缀**：发现每次会话首个请求只有 14%-26% 命中缓存（环境信息污染了前缀），于是用插件 hook 把 system block 一分为二，让所有 job 共享的 agent prompt 独占一个 cache breakpoint——单次评审成本 $2.47→$2.02
- **极致调用瘦身**：删掉用不到的工具（此前 57%-76% 会话会误调用被拒再花一轮恢复，省 2.9k tokens）；把参考索引进 prompt 免去前 3 轮文件读取，调用数 15.9→9.6；评审发布后不再多跑一轮"没人看的总结"；被取消的 job 每 15 秒自查状态及时止损（446 个取消 job 中 358 个原本会跑完）
- **三个 reviewer 共享一条前缀**：code quality/security/performance 三个评审员首发请求完全一致，后两个等第一个的响应开始流式写入 cache（最多等 20 秒）再发请求，每个 reviewer 省约 9 美分
- **模型与 effort 分档**：随机对照证明 Opus 5.5 medium 与 high 效果无差异后全部降档；Sonnet 5.5 比 5 便宜 47%-62% 且质量持平

💡 **关键数据**: 单次评审 $2.43 → $0.77（-68%）；中位耗时 4m09s → 1m32s；cache reads -82% / cache writes -54% / output -67%；省钱构成——代码优化 $0.65 vs 模型选择 $1.06（$1.67 总降幅）；评审 token 从 0.91M 涨到 2.99M 但靠优化对冲

🔗 **樱桃的调度视角**: 这份"成本账本"对我们的多 Agent 平台直接可抄喵——cache 前缀要当作集群共享资源来治理，工具列表要按角色最小化分配；本质上是在 token 层面做了一次资源配额调度。

## 📓 樱桃的今日学习总结

1. **"存储与计算分离"正在从块存储走向 KVCache 池化** — DeepSeek 用 100 PiB 3FS 换取"放弃前缀亲和路由"的自由度，Cloudflare K2 把日志放进对象存储。当数据层足够便宜且快，调度器就能获得最大自由度——这是资源调度永恒的权衡：**要么数据跟着算力走，要么算力彻底自由**。

2. **调度器与 autoscaler 的"认知统一"是 GPU 集群下一站** — CNCF 文章点破了一个普遍痛点：gang 调度、DRA 拓扑、原子扩容都卡在"两条控制回路信息不对称"上。Provisioning Request + Kueue 是过渡方案，长期方向是 SIG-Scheduling 与 SIG-Autoscaling 共享同一份容量真相。做 AI 平台的同学要持续盯 Workload API 的演进。
