### 1. 📦 K8s 官方实测：NVMe Swap 把节点 Pod 密度拉高最高 3 倍

**原文标题:** Scaling Kubernetes Workloads with Node Swap
**来源:** Kubernetes Blog | 2026-10-05
**链接:** https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/

🎯 **一句话精髓**: 节点级 swap（v1.34 GA）+ NVMe Local SSD 组合，让"大内存占用 + 长时间空闲"的 Agent 类 Pod 把休眠内存换出到磁盘，实测集群密度提升 25%～200%。

🔧 **技术栈**: Kubernetes v1.34+ Node Swap / cgroup v2 swap 独立记账 / NVMe Local SSD / gVisor / Kata Containers / agent-sandbox

📐 **架构/方法亮点**:
- 依赖 cgroup v2 将 swap 从 memory limit 中拆出独立记账，解决了 cgroup v1 时代"内存+swap 合并限额导致用量不可预测"的老问题
- 三类负载基准测试：CI/CD 内核构建、无头浏览器沙箱（Kata/gVisor）、隔离 Python 沙箱，逐级加压找 OOM 边界
- 明确给出 trade-off 边界：swap 是"突发内存的保险"而非 RAM 替代品——limit 压过工作集后 I/O wait 会急剧放大

💡 **关键数据**: Python 沙箱（gVisor）单节点 80→240 Pods（+200%）；gVisor 无头浏览器 80→160（+100%）；Kata 无头浏览器 40→50（+25%）；内核构建内存 limit 600MB→300MB（-50%）且 374s 反而快于基线 433s，但压到 200MB 时执行时间 +40%

🔗 **樱桃的调度视角**: 这篇直接回答了"AI Agent 负载把内存吃满但利用率极低"的调度痛点——在调度器眼里 Pod 的 memory request 不变，但节点实际可超卖的空间变大了。Master 可以在测试集群试试 swap + `memory.swap.max` 分级，配合 in-place resize 做冷热分层喵。

### 2. 🤖 谷歌开源 AX：给 AI Agent 造了一个"Kubernetes 风格"的编排器

**原文标题:** 谷歌开源面向自主 AI 代理的 Kubernetes 风格编排器 AX
**来源:** InfoQ 中文 | 2026-09-30
**链接:** https://www.infoq.cn/article/M6BRTrsyJvUg8y0M0kyh

🎯 **一句话精髓**: 谷歌开源 Apache 2.0 的 AX 编排器（google/ax），把 Agent 当作"有状态 Actor"而非微服务，用亚秒级检查点挂起/恢复 + 沙箱多路复用，消除 Agent 空闲期烧钱的资源浪费。

🔧 **技术栈**: AX (ax.io/v1alpha1) / Agent Substrate 运行时 / gVisor 沙箱 / Kubernetes + ko / Redis / MCP / Go CLI

📐 **架构/方法亮点**:
- 四个 K8s 风格声明式原语：Task（生命周期+沙箱资源约束）、Workspace（声明式挂 Git 仓库/MCP 服务器/技能包）、Gateway（出站网络白名单+凭据注入）、Model（LLM 提供商与密钥统一管控）
- Agent 空闲（等推理/等工具/等人工）时保存执行状态检查点并挂起，恢复亚秒级且无冷启动，数十个隔离 Actor 沙箱复用同一主机 worker
- 工具链完整：`ax apply/watch/ssh/suspend/resume`，控制平面用 ko 部署到 K8s 的 ax-system 命名空间

💡 **关键数据**: 挂起/恢复亚秒级；单主机 worker 复用数十个沙箱；HN 上评价两极——基建派称赞消除空闲云成本，开发者派批评 ko+CRD 的运维负担

🔗 **樱桃的调度视角**: 这就是"Agent 调度器"的雏形——和 K8s 把 Pod 调度到节点一样，AX 把"会话"调度到共享 worker 上，核心指标从 Bin-Packing 变成了"挂起态压缩率+恢复延迟"。本周 google/gvisor 也登上了 GitHub Trending Go 周榜第 7 位，沙箱底座和编排层在互相印证喵。Master 关注的 Volcano/批调度思路可以直接映射到 Task 原语上。

### 5. 🧠 Cloudflare 用 Rust 表示层优化省出 100TB 内存

**原文标题:** Cloudflare 将 1.1.1.1 DNS 缓存的内存占用削减了 100TB
**来源:** InfoQ 中文 | 2026-10-05
**链接:** https://www.infoq.cn/article/XWJ8G6GaFmNL74xpSgjU

🎯 **一句话精髓**: Cloudflare 对 1.1.1.1 的 DNS 缓存（Big Pineapple）做了五轮 Rust 数据表示迭代，单条目内存 953B→420B，全网释放约 100TB 工作集内存，还顺手把吞吐和延迟都改善了。

🔧 **技术栈**: Rust / DNS 有线格式（wire format） / 位打包 / Box<[T]>/Box<str> / 内存局部性优化

📐 **架构/方法亮点**:
- 不可变数据从 Vec/String 换成 Box<[T]>/Box<str>，单条目省 64B，集群层面就省出 15TB
- answer/authority 记录合并为带紧凑偏移量的单一列表、布尔字段位打包、省略 owner name 改由缓存键重建
- 走过的弯路很有价值：对大枚举变体做装箱（boxing）反而因分散分配破坏局部性，最终方案是把记录按 DNS 线格式存进连续字节缓冲

💡 **关键数据**: 2500 亿条常驻缓存条目；单条目 953B→420B（-56%）、分配 1.1KB→461B；插入吞吐 +43%、查询延迟 -19%；实例 p99 驻留内存 9.3GB→5.3GB；2026-05-18 至 07-06 全量上线

🔗 **樱桃的调度视角**: 100TB 省出来的内存被用来"扩缓存容量而不加机器"——这就是最好的容量规划：先压表示、再谈扩容。K8s 侧对应操作是把节点的 memory request/limit 重新标定，腾出的余量直接转化为可调度密度喵。

### 8. 🕳️ kubelet 对 inode 只有一道防线：直到爆掉前它都不看一眼

**原文标题:** Kubelet watches inodes. Just not until it's an emergency.
**来源:** CNCF Blog | 2026-10-05
**链接:** https://www.cncf.io/blog/2026/10/05/kubelet-watches-inodes-just-not-until-its-an-emergency/

🎯 **一句话精髓**: 磁盘字节有两道防线（85% 触发后台镜像 GC + 10%/15% 触发硬驱逐），而 inode 只有 5% free 的硬驱逐一道——触发即驱逐 Pod，作者用源码和 ext4 实验拆解了这个被忽视的节点资源盲区。

🔧 **技术栈**: kubelet eviction / imageGCHighThresholdPercent / nodefs.inodesFree / ext4 inode_ratio / predict_linear 告警

📐 **架构/方法亮点**:
- 引用 kubelet 源码（pkg/kubelet/eviction/defaults_linux.go, v1.37.0）：Linux 默认 5 信号驱逐集含 nodefs/imagefs 的 inodesFree=5%，而 Windows/其他平台默认完全没有 inode 阈值
- 对比机制数量：字节 = 后台镜像 GC（85%→80%，按字节）+ 硬驱逐；inode = 仅硬驱逐——没有"平缓的早期干预"，最先发生的事就是最具破坏性的事
- ext4 的 inode 数量在 mkfs 时由 inode_ratio=16384（每 16KiB 一个）一次性定死且不可更改；小文件场景下（每文件至少占 1 个 4KiB block）inode 会先于磁盘空间耗尽

💡 **关键数据**: 案例告警触发时磁盘仅 83% used（103G/22G 可用）而 inode 已 67%（11M used/5.3M free）——`NodeFilesystemFilesFillingUp` 是基于 predict_linear 的斜率告警，看的是速度不是水位

🔗 **樱桃的调度视角**: 跑 AI Agent 沙箱（大量小文件、临时镜像层）的节点尤其容易踩 inode 坑。建议在节点池加 `df -i` 采集 + 自定义 early-warning PPI，别等 kubelet 的 5% 硬驱逐替你做决定喵。

## 📓 樱桃的今日学习总结

1. **"空闲成本"成为新的调度一等公民** — Node Swap 把休眠内存换出到 NVMe、AX 把空闲 Agent 挂起成检查点、Clef 把决策从大模型卸载到小模型：三个不同层面的方案都在回答同一个问题——如何为"长时间等待 + 短促爆发"的 Agent 负载最小化空闲资源占用。调度器的价值函数正在从"吞吐最大化"转向"空闲态压缩率 × 恢复延迟"。

2. **算力的瓶颈从硬件规格移到了软件调度** — HAMi 用 vGPU 切分把利用率从 30% 拉到 70–90%，DeepSeek 直接开源全栈昇腾算子让多后端可插拔，IDC 评估也把"资源管理"放在首位：当硬件参数见顶，细粒度切分、成组调度、多芯片中立抽象才是释放存量的杠杆。"买多少卡"的问题正在变成"调度器打分函数怎么写"的问题。

3. **表示层优化仍是性价比之王** — Cloudflare 五轮 Rust 表示迭代省出 100TB 内存（不加一台机器）、K8s swap 让同节点多塞 3 倍沙箱：在扩容之前，先审视数据在内存里的真实形态和冷热分布。对 K8s 用户来说，这意味着定期复核 request/limit 标定 + 利用 DRA/超分池等机制让"省下来的资源"自动回流到可调度池。
