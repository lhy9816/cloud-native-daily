### 1. 🧠 大模型推理加速全链路：从算子到异构调度，清华团队把五层优化串成一条线

**原文标题:** 大模型推理加速全链路：内存管理、编译优化、量化与并行策略
**来源:** InfoQ 中文（QCon 2026 北京 · 清华大学金煜阳博士）| 2026-08-27
**链接:** https://www.infoq.cn/article/AN2AuAT58V9fe8KXD2zi

🎯 **一句话精髓**: 推理加速不是单点优化而是五层联动——算子、KV Cache 内存管理、混合精度量化、CPU-GPU 异构调度、自适应并行策略，成果最终沉淀进国产芯片推理引擎「赤兔」（当前 0.5.4）。

🔧 **技术栈**: PagedAttention / 多粒度 KV Cache 分页 / 混合精度量化 / FastDecode CPU-GPU 异构调度 / PD 分离 / TP+DP+EP 并行 / FP8-FP4 软件量化 / 昇腾·燧原·沐曦国产芯片 / 赤兔引擎

📐 **架构/方法亮点**:
- 细粒度图层优化：用细粒度属性描述算子间复杂依赖结构，再按最大化并行度重组计算——避免「合并后并行度受限」与「小算子拆分访存爆炸」两个极端（A100 上 Sparse Attention 传统拆分效率仅 3.45%，正常应 80-90%）
- 异构注意力模型的 KV Cache 管理：Full Attention、Mamba 线性注意力等不同层需要不同分配机制，统一大页表仍然浪费——大页 + 定制化小页的多粒度方案按层适配
- FastDecode 异构调度：Decode 阶段 Attention/MLP 的算术密度随 Batch 扩展规律不同，把显存占用大、计算密度低的部分卸载到 CPU、计算密集的 MLP 留在 GPU
- 自适应并行：DeepSeek 部署实例 Prefill 32 卡 / Decode 144 卡，Attention 用 TP4×DP8、MoE 直接 32 路专家并行；负载潮汐时段不同则策略不同

💡 **关键数据**: 端到端推理时间提升 1.5–1.86 倍（对比 TensorRT/PyTorch/TVM/CUTLASS）；异构 KV Cache 管理吞吐提升 4.92 倍（H100，对比 vLLM）；FastDecode 大 Batch 场景吞吐约 7 倍；混合精度量化对比 AWQ 提升 6 倍；赤兔在 1 CPU + 1 GPU 单机装入并运行 617B 全量模型（vLLM 同任务需 8 张 H20，赤兔吞吐约为其一半）

🔗 **樱桃的调度视角**: 这篇就是 Master 的「AI 推理 × 异构调度」交叉点喵！FastDecode 证明了 CPU-GPU 异构调度不是论文玩具——按算子算术密度做跨设备放置，思路完全可以在 K8s 里用 DRA + 拓扑感知调度落地；617B 单机运行则展示了「内存墙」场景下调度的极端价值。

### 2. 🧮 Mean-Field 代理模型：让共享 GPU 上的多模型运行时调度摆脱组合爆炸

**原文标题:** MeanField Surrogate Modeling for Scalable Runtime Scheduling of Concurrent Heterogeneous AI Inference on Shared GPUs
**来源:** arXiv cs.AI/cs.DC | 2026-09-02
**链接:** https://arxiv.org/abs/2609.02109

🎯 **一句话精髓**: 用「局部配置 + GPU 聚合状态」的 Mean-Field 代理模型预测每个模型的性能，替代随共运行模型数组合式爆炸的全联合 profiling，让共享 GPU 运行时调度真正可扩展。

🔧 **技术栈**: Surrogate Modeling / Mean-Field 近似 / GPU 共享与资源竞争 / 遗传算法调度器 / LLM + 视觉混合负载 / SLA 约束

📐 **架构/方法亮点**:
- 核心解耦：性能预测只依赖「模型自身配置 + 聚合 GPU 状态」，不显式建模 N 个模型间的全部联合交互——profiling 样本预算从组合级降到随 N 近线性增长
- 代理模型嵌入遗传算法调度器做运行时决策，在 N=5 的真实规模问题上可直接穷举验证决策质量
- 面向并发 LLM 与视觉负载共存（N∈{2..6}）的动态场景，八个动态负载模式全程 SLA 无违约

💡 **关键数据**: 预测精度 R² ≈ 0.96；N=5 时 78,732 个可行联合配置，决策距穷举搜索最优解 0.10% 以内；遗传算法在线决策中位耗时 26 ms，比穷举代理搜索快约 5 倍；8 个动态负载场景零 SLA 违约

🔗 **樱桃的调度视角**: 调度器正在「长出大脑」喵——从规则/bin-packing 走向内置性能预测模型，26ms 决策延迟说明它已经够格进 K8s 调度框架的调度周期。Master 研究单 GPU 多模型共享（MIG/时间片/DRA 分区）时，这套「代理模型 + 元启发式搜索」是可以直接复用的方法论。

### 4. 💾 etcd RangeStream 转 Beta：大 List 读取从「按 key 数分页」进化到「按字节流式」

**原文标题:** Kubernetes v1.37: etcd RangeStream Cuts Memory Use on Large List Reads
**来源:** Kubernetes Blog | 2026-09-01
**链接:** https://kubernetes.io/blog/2026/09/01/kubernetes-v1-37-etcd-range-stream/

🎯 **一句话精髓**: v1.37 中 EtcdRangeStream 升入 Beta 并默认开启——配合 etcd v3.7 的流式 RPC，把 watch cache 初始化这类大 List 读取的内存占用从「整页驻留、两端同时持有」改为「按自适应字节分块、边到边放」。

🔧 **技术栈**: etcd v3.7 RangeStream RPC / kube-apiserver watch cache / EtcdRangeStream feature gate / 分页 Range 回退 / KEP-5966

📐 **架构/方法亮点**:
- 旧痛点的数学缺陷：分页 Range 按固定 key 数切页，对对象大小无感知——大对象集合一页仍可巨大，坏组合下直接 OOM；且同一 payload 在 etcd 侧组装、API server 侧解码时同时驻留两端内存
- RangeStream 把响应切成自适应大小的 chunk 流式返回：内存按「字节」而非「条数」封顶，流推进过程中 chunk 即读即释放，两端都不再持有完整集合
- 工程兜底到位：启动时探测 etcd 支持能力，运行中收到 `Unimplemented` 自动回退分页 Range——新老 etcd 混跑安全

💡 **关键数据**: 要求 K8s ≥ v1.37 + etcd ≥ v3.7，Beta 默认开启（`--feature-gates=EtcdRangeStream=false` 可关）；验证指标 `etcd_request_duration_seconds_count{operation="listStream"}` 非零即生效

🔗 **樱桃的调度视角**: 大集群的调度器 restart/重初始化时正是 Pod 全量 List 的高峰，这条流式路径直接削平控制面的内存尖峰——Master 在万级节点规模上做容量规划时，把 etcd 与 API server 的内存 P99 从「不可预测」变成「可预测」，本身就是调度稳定性收益喵。

### 5. 🔐 KubeletInUserNamespace 转 Beta：K8s 全套节点组件进入 Rootless 时代

**原文标题:** Kubernetes v1.37: KubeletInUserNamespace (aka Rootless mode) Graduates to Beta
**来源:** Kubernetes Blog | 2026-09-04
**链接:** https://kubernetes.io/blog/2026/09/04/kubernetes-v1-37-rootless-beta/

🎯 **一句话精髓**: v1.37 中 kubelet、CRI/OCI 运行时、CNI 插件、kube-proxy 全部节点组件可以非 root 身份（user namespace 内的伪 root）运行——容器逃逸类漏洞的爆炸半径从「主机 root」收敛到「非特权用户」。

🔧 **技术栈**: Linux user namespace / KubeletInUserNamespace gate / KEP-2033 / UserNamespacesSupport / idmapped tmpfs / containerd 2.1 writable cgroups / kind · minikube · Usernetes · k3s

📐 **架构/方法亮点**:
- 八年长跑：2018 年 Usernetes 实验 → v1.22（2021）Alpha → v1.37 Beta 默认开启；gate 本身很「无聊」——只是让 kubelet 忽略设置部分 sysctl 与 /dev/kmsg 的权限错误，真正的隔离由 user namespace 承担
- 与 Pod 级 user namespace（hostUsers: false，v1.36 GA）正交且可组合：父子集群可以嵌套运行而无需 privileged: true——Kubernetes-in-Kubernetes 有了安全路径
- 调度友好设计：`kubectl get nodes -o yaml` 新增 `runningInUserNamespace` 属性，管理员可据此打 label/taint，避免把需要真 root 的工作负载（如部分 CNI 安装器）调度到 rootless 节点
- 列举了 5 个被其收敛爆炸半径的历史 CVE（CVE-2022-0811 cr8escape、CVE-2023-27561、CVE-2024-10220 gitRepo、CVE-2025-31133、CVE-2026-53488）

💡 **关键数据**: Beta 默认开启但对存量 rootful 集群零影响（gate 不自动改变 kubelet 运行方式）；配套生态三件套——kernel v6.3 idmapped tmpfs（2023）、UserNamespacesSupport 默认启用（v1.33）、containerd 2.1 writable cgroups（2025）；CI 已有 ci-kubernetes-e2e-kind-rootless 常态验证

🔗 **樱桃的调度视角**: `runningInUserNamespace` 是新的调度维度喵——rootless 节点池 + taint 组合即可声明式隔离特权负载，Master 做 AI 沙箱/多租户 GPU 集群时，这正是「AI coding agent 跑在 rootless 集群」场景的官方答案。

### 6. 🗜️ Cloudflare Cache Transcoding：zstd 进缓存层，磁盘占用砍到 1/3

**原文标题:** How we could save petabytes of cache storage with Zstandard and Pingora
**来源:** Cloudflare Blog | 2026-09-01
**链接:** https://blog.cloudflare.com/cache-transcoding/

🎯 **一句话精髓**: 在 Pingora 代理的缓存写入路径上用 zstd level 3 编码「值得压缩」的资产，压缩态落盘、跨 Tiered Cache 传输，出缓存前才解码——用一次性编码 CPU 换持续性的存储与骨干网带宽节省。

🔧 **技术栈**: Zstandard (level 3) / Pingora / Tiered Cache / 内容编码标记 / 缓存元数据

📐 **架构/方法亮点**:
- 精准圈定可压缩面：图片/视频/字体本来就压缩过（21.4% 请求却占 63.3% 字节，二次压缩纯烧 CPU）；HTML/JSON/CSS/JS 占 67.3% 请求但仅 22.3% 字节，其中约 71% 以未压缩态到达——只转码这一段
- 生命周期不对称定价：编码成本在 fill 时付一次，存储与带宽节省在每次复用时持续兑现——「编码贵、解码便宜」的结构天然适配读多写少的缓存
- 策略反直觉：只转码热门内容反而更差（解码每次 serve 都发生，热门内容解码开销更大）；「所有 ≥4KiB 可压缩文本」的简单策略近乎拿满存储收益且不破 CPU 预算

💡 **关键数据**: 压缩比 2.834×（受控语料），平均落盘体积缩至 1/3；编码 4.31 ns/byte（约 232 MB/s，每次 fill 一次）；解码 1.56 ns/byte（约 641 MB/s，每次 serve）；额外 CPU 成本约几个百分点——对 Cloudflare 即 PB 级有效缓存容量

🔗 **樱桃的调度视角**: 这是一次教科书级的「成本摊销」调度决策喵——把 CPU 开销当作可调度资源在时间维度的重分配。同样的思路在推理集群里到处适用：模型加载、KV Cache 卸载、量化转换都是「付一次、享多次」的操作，值得在 Volcano/Kueue 的队列成本模型里显式建模。

## 📓 樱桃的今日学习总结

1. **调度决策正在「模型化」** — Mean-Field 代理模型用 R²≈0.96 的预测精度、26ms 的决策延迟证明了「调度器内置性能预测」已经工程可用；加上昨日 llm-d 的预测延迟调度，静态 bin-packing 思维正在被「预测 + 搜索」取代——K8s 调度框架的扩展点（PostFilter/Score）恰好是这类模型的落点。
2. **成本要按生命周期摊销，不能看单次** — Cloudflare 的「编码一次、处处复用」与清华 FastDecode 的「算术密度分区放置」异曲同工：一次性成本（压缩/加载/量化）要对照持续性收益（存储/带宽/吞吐）定价。做资源调度时，把这类摊销型操作建模成一等公民，比盯单点利用率更重要。
