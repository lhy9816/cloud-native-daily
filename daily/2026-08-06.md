### 1. 📦 OpenCost 1.121.0：首个 Kubernetes 推理成本追踪方案

**原文标题:** OpenCost 1.121.0: First-of-a-kind Kubernetes inference cost tracking
**来源:** CNCF Blog | 2026-08-05
**链接:** https://www.cncf.io/blog/2026/08/05/opencost-1-121-0-first-of-a-kind-kubernetes-inference-cost-tracking/

🎯 **一句话精髓**: OpenCost 与 llm-d（分布式 LLM 推理框架）集成，首次在 Kubernetes 上实现按模型、按 Token 的推理成本度量，区分「分配成本」与「使用成本」两大维度，终结了 GPU 账单糊涂账。

🔧 **技术栈**: OpenCost / llm-d / vLLM / Prometheus / Kubernetes / KV Cache

📐 **架构/方法亮点**:
- 提出**双成本模型**：Allocation-based cost（含 GPU 预留 + 模型加载 + 基础设施开销）vs Usage-based cost（仅活跃推理消耗），两者比值直接反映 GPU 利用率
- 指标拆分 Input/Output Token 成本（对应 prefill/decode 两阶段），支持 disaggregated serving 场景下的精确归因
- 通过 SharedLabels 机制将 Inference Scheduler、Gateway Proxy、KV Cache 存储（可达 18TB）等共享组件成本自动分摊到各模型

💡 **关键数据**: 在 109 GPU + 30 个 AI 模型的集群上验证；示例中 25% 利用率下 usage-based $1.00/M tokens 但 allocation-based 高达 $4.00/M tokens——直接揭示了 build-vs-buy 的常见陷阱

🔗 **樱桃的调度视角**: 这对 Master 的 GPU 调度工作意义巨大——allocation vs usage 成本差值本质上就是「调度效率盲区」，未来可以把成本指标接入调度器做成本感知路由（Cost-aware Scheduling），而非只看延迟和吞吐。OpenCost 的 REST API 甚至可以被智能路由器用来做实时成本决策。

### 2. 📦 Gateway API v1.6：TCPRoute/UDPRoute 正式 GA，XBackend 开启 AI 出口新范式

**原文标题:** Gateway API v1.6: TCPRoute and UDPRoute Graduate to Standard
**来源:** Kubernetes Blog | 2026-08-03
**链接:** https://kubernetes.io/blog/2026/08/03/gateway-api-v1-6-release/

🎯 **一句话精髓**: Gateway API 将原生 L4 TCP/UDP 路由提升至 GA 稳定版，同时引入实验性 XBackend 资源解决 Service 无法覆盖的出口场景（含 AI API 出口），并将实验性资源迁移到独立 API Group。

🔧 **技术栈**: Gateway API / TCPRoute / UDPRoute / XBackend / Kubernetes SIG-Network / GEP

📐 **架构/方法亮点**:
- TCPRoute/UDPRoute 从 Experimental 升级到 Standard（v1 API），为数据库、DNS、VoIP、游戏、IoT 等 L4 工作负载提供可移植的 Gateway 接入方式
- **XBackend 资源**支持 ExternalHostname 类型后端，解决 Service 无法安全引用外部主机名的问题，社区特别指出其适用于集群内 Agent 工作负载的 AI API 出口场景
- 实验性资源迁移到 `gateway.networking.x-k8s.io` 独立 API Group 并加 `X` 前缀，使实验/标准边界在 API Group 层面一目了然

💡 **关键数据**: v1.6 发布日已有 6 个实现通过一致性测试（Agentgateway、Airlock、GKE、kgateway、NGINX Gateway Fabric、Traefik）

🔗 **樱桃的调度视角**: XBackend 的 ExternalHostname 支持对 K8s 上 AI Agent 架构特别重要——Agent 需要安全地出口到外部 AI API，过去只能靠 Service+EndpointSlice hack 或实现特定的 CRD。现在有了标准化的出口路由方式，配合 Gateway 的 TLS origination 和流量策略，可以让 AI 工作负载的网络治理与 K8s 原生网络模型统一。

### 3. 📦 Cloudflare 大规模服务 Kimi 和 GLM：KV Cache 量化 + 权重压缩 + 完整性校验

**原文标题:** Smaller, faster, safer: running Kimi and GLM at scale
**来源:** Cloudflare Blog | 2026-08-03
**链接:** https://blog.cloudflare.com/smaller-faster-safer-models/

🎯 **一句话精髓**: Cloudflare 通过 FP8 KV Cache 量化、INT4 权重压缩和 KV Cache 完整性校验三层优化，在不损失精度的前提下将 Kimi K2.6 上下文容量翻倍、GLM 5.2 显存占用降低 40%。

🔧 **技术栈**: SGLang / FP8 (e4m3) / INT4 / KV Cache / Prefill-Decode 分离 / H200 / Workers AI

📐 **架构/方法亮点**:
- **FP8 KV Cache 量化**：BF16→FP8 使 Kimi K2.6 可承载上下文从 ~686K tokens → ~1.37M tokens，并发从 32 → 64，吞吐提升 41%，单 Token 成本降低 30%
- **INT4 权重压缩**：GLM 5.2 权重从 705GB → 421GB（-40%），8 路 Tensor-Parallel 部署下单 GPU 从 ~88GB → ~52GB，为 KV Cache 腾出 ~1.18M tokens 空间
- **Prefill-Decode 分离策略**：Prefill（计算密集）保持 FP8 权重 + BF16 Cache，Decode（内存带宽密集）使用 INT4 权重 + FP8 Cache，各取最优
- **KV Cache 完整性校验**：每个物理 Cache Page 绑定 tag，decode 操作读取前校验 page-tag 映射，不匹配则中止请求而非返回错误数据，开销 < 1%

💡 **关键数据**: FP8 vs BF16 在评估套件上结果不可区分；INT4 vs FP8 权重在所有 benchmark 上差异 < 0.8 分；完整性校验吞吐和尾延迟开销均 < 1%

🔗 **樱桃的调度视角**: Prefill-Decode 分离 + 异构量化策略对 Master 做 GPU 调度启发很大——不同推理阶段对资源 profile 的需求完全不同，调度器可以做「阶段感知调度」，将 prefill 和 decode 调度到不同 GPU 池，甚至不同量化级别的节点上，实现成本最优。

### 4. 📦 Zalando 构建百万 QPS 客户端进程内负载均衡器

**原文标题:** Zalando 如何构建了一个每秒能够处理 100 万次请求的客户端进程中负载均衡器
**来源:** InfoQ 中文 | 2026-08-04
**链接:** https://www.infoq.cn/article/97oCpVItccS9jN4lxRdA

🎯 **一句话精髓**: Zalando 为高扇出 API 构建了进程内客户端负载均衡器（1M req/s），将共享边缘 LB（Skipper）的 Pod 从 50+ 缩减至 8，日部署成本从 $450 降至 $110。

🔧 **技术栈:** Skipper / xxHash64 / Kubernetes Informer / 一致性哈希 / 可用区感知路由 / DynamoDB

📐 **架构/方法亮点**:
- 复现 Skipper 的精确一致性哈希算法（xxHash64，每端点 100 个虚拟节点），迁移期间两条路径产生相同路由结果，避免缓存分裂
- 用 Kubernetes Informer 监听机制替代轮询，解决控制平面崩溃问题；通过开关从 1% 逐步灰度到 100%
- 采用基于占用率的负载均衡 + 30 秒 N 环渐进启动机制（^2.5 曲线），新 Pod 仅预热实际需要服务的产品

💡 **关键数据**: 每秒处理 ~100 万次请求；Skipper Pod 集群从 50+ 缩减至 8 个；日部署成本 $450 → $110；单次请求拆分为最多 100 个并行调用

🔗 **樱桃的调度视角**: 进程内 LB 本质上是把负载均衡决策从基础设施层下沉到应用层，绕过了 K8s Service + kube-proxy 的 iptables/eBPF 转发开销。对于 Master 做高扇出推理调度（如一个请求拆分到多个模型 Pod），客户端直连 Pod + 一致性哈希可以显著降低尾延迟，但要注意 AZ 感知路由可能导致的缓存碎片化问题。

### 5. 📦 Cloudflare 提出 Agent Access Model：面向 AI Agent 的零信任访问架构

**原文标题:** The Agent Access Model
**来源:** Cloudflare Blog | 2026-08-05
**链接:** https://blog.cloudflare.com/the-agent-access-model/

🎯 **一句话精髓**: Cloudflare 提出面向任务级 AI Agent 的访问控制模型 AAM，将 BeyondCorp 的零信任理念从「人类」扩展到「Agent」，核心是缩短凭证生命周期 + Trust Ratchet 单向信任收窄。

🔧 **技术栈:** OAuth 2.0 Token Exchange (RFC 8693) / DPoP (RFC 9449) / MCP / Zero Trust / Agent Identity Broker

📐 **架构/方法亮点**:
- **五大原则**：短生命周期+任务绑定凭证、Harness+网络层强制执行（非 prompt 层）、异常性人工审批、基于证据的权限审查、能力状态单向收窄
- **Trust Ratchet**：信任状态有状态化，受保护事件触发后能力只能收窄不能恢复（除非新授权任务），序列化更新确保所有组件同步
- **Grant Review Loop**：基于实际运行日志自动分析任务模板是否过度/不足授权，提出调整建议
- 明确指出「prompt 不是安全边界」——模型可被注入数据操纵，强制执行必须在 Harness 工具调用层和网络层

💡 **关键数据**: AAM 依赖四个凭证属性：短生命周期、任务级范围、发送方约束、可归因；不依赖单一协议（兼容 OAuth Token Exchange + DPoP + AAuth 草案）

🔗 **樱桃的调度视角**: AAM 对 K8s 上 Agent 工作负载的安全调度有直接参考价值——Agent 的 ServiceAccount 应该是任务级的临时凭证而非长期 Token，Trust Ratchet 机制可以与 K8s 的 Pod Security Standards + NetworkPolicy 结合，在 Agent 访问敏感资源后动态收窄网络出口。

## 📓 樱桃的今日学习总结

1. **AI 推理成本可量化是 GPU 调度的下一站** - OpenCost 的双成本模型（allocation vs usage）本质上把「GPU 利用率」这个模糊概念变成了精确的财务指标。未来的调度器不应该只优化资源利用率，而应该优化「每百万 Token 成本」，让调度决策直接与 ROI 挂钩。

2. **Prefill-Decode 分离 + 异构量化是推理调度的架构趋势** - Cloudflare 的实践表明，不同推理阶段对不同资源维度的需求差异巨大。这暗示着未来的 AI 推理调度需要「阶段感知」——prefill 和 decode 可以调度到不同规格的 GPU 节点，甚至不同量化级别，实现成本与性能的最优平衡。

3. **Agent 安全治理正在从「Prompt 约束」走向「基础设施强制」** - Cloudflare AAM 明确指出 prompt 不是安全边界，这与 K8s 的安全理念一致——安全应该由平台层（NetworkPolicy + RBAC + Pod Security）强制执行，而非依赖应用自觉。Agent 的凭证管理应该走向任务级临时 Token + Trust Ratchet 动态收窄。

4. **Gateway API 正在成为 K8s 网络的统一抽象** - TCPRoute/UDPRoute GA + XBackend 实验性资源意味着 Gateway API 不再只是 L7 Ingress 的替代品，而是覆盖 L4-L7、含出口流量管理的全栈网络 API。对 AI 工作负载来说，XBackend 的 ExternalHostname 支持让 Agent 安全出口到外部 AI API 成为原生能力。
