## 🚀 重点速览

### 1. 📦 CoHDI 入驻 CNCF：用 DRA 把 Kubernetes 变成可组合分解基础设施

**原文标题:** Welcome CoHDI to the CNCF: Evolving Kubernetes into composable disaggregated infrastructures
**来源:** CNCF Blog | 2026-07-29
**链接:** https://www.cncf.io/blog/2026/07/28/welcome-cohdi-to-the-cncf-evolving-kubernetes-into-composable-disaggregated-infrastructures/

🎯 **一句话精髓**: CoHDI（原 InfraDDS）通过 Kubernetes DRA 实现节点级 PCIe 设备（如 GPU）的动态挂载/卸载，让硬件资源能按 Pod 请求实时组合，专门服务于 LLM 推理的 prefill/decode 分离等场景。

🔧 **技术栈**: Kubernetes DRA (Dynamic Resource Allocation) / ResourceSlices / PCIe 设备热插拔 / Composable-DRA-Driver / Dynamic-Device-Scaler / Composable Resource Operator

📐 **架构/方法亮点**:
- 三个核心组件：Composable-DRA-Driver（K8s 与 CoHDI manager 的桥梁，把可用资源暴露为 DRA 框架内的 ResourceSlices）、Dynamic-Device-Scaler（基于 Pod 请求动态增删设备，无需 OS 重启）、Composable Resource Operator（动态挂载/卸载 GPU 等可组合硬件到节点）
- 明确针对 LLM 推理 Prefill/Decode 分离：prefill 阶段 compute-bound、decode 阶段 memory-bound，两者资源需求不同，CoHDI 可按阶段动态适配；Agentic AI 工作流中每个阶段资源需求也动态变化
- 与 SIG Node、SIG Autoscaling、SIG Scheduling 协作；由 Red Hat、FSAS、Fujitsu、IBM Research、NTT 于 2025 年 3 月联合发起，NTT 贡献 IOWN 数据中心基础设施（DCI）

💡 **关键数据**: 2025 年 3 月发起，现已正式成为 CNCF Sandbox 项目

🔗 **樱桃的调度视角**: 这是 GPU 调度的硬件级对应物——基于 DRA 的按 Pod 请求动态挂载 GPU、且无需重启，专为 LLM prefill/decode 分离设计。它和下面 Cloudflare 的软件侧 prefill/decode 分离是一对完美搭档：调度层组合硬件，推理层切分阶段。对 Master 来说，DRA + 可组合硬件就是 GPU 调度的未来形态喵～

### 2. 📦 Cloudflare 实战：KV 缓存 FP8 量化 + 权重 INT4 压缩，把 Kimi 和 GLM 塞进 GPU

**原文标题:** Smaller, faster, safer: running Kimi and GLM at scale
**来源:** Cloudflare Blog | 2026-08-03
**链接:** https://blog.cloudflare.com/smaller-faster-safer-models/

🎯 **一句话精髓**: Cloudflare 用三层优化（FP8 KV 缓存、INT4 权重压缩、KV 缓存完整性校验）在 Workers AI 上高效服务 Kimi K 系列与 GLM，把单卡并发与吞吐近乎翻倍，精度几乎无损。

🔧 **技术栈**: SGLang / FP8 KV cache / INT4 权重压缩 / Paged Attention / 连续批处理 / H200 / Blackwell NVFP4 / prefill-decode 分离

📐 **架构/方法亮点**:
- FP8(e4m3) KV 缓存：缓存尺寸减半，Kimi K2.6 可驻留上下文从 ~68.6 万 token 提升到 ~137 万 token（2 倍）；BF16 在 32 并发即 OOM，FP8 可撑到 64 并发达 2192 tok/s
- GLM 5.2 权重从 FP8 压到 INT4：checkpoint 从 705GB 降到 421GB（约 40%），8 路 tensor-parallel 下单卡显存从 ~88GB 降到 ~52GB，腾出约 118 万 token 的 KV 缓存空间
- 分离式部署：decode 用 INT4（访存带宽受限，更优），prefill 用 FP8（计算受限，更优）——把"权衡"变成"各取所长"
- KV 缓存完整性校验：每页加 tag，校验不匹配则中止请求而非返回错页，开销 <1%（吞吐/p95 延迟）

💡 **关键数据**: FP8 KV 缓存峰值吞吐比 BF16 高约 41%、单 token 成本低约 30%；INT4 decode 在并发 1 时 +55% tok/s；全基准精度与 FP8 差距 <0.8 分（GSM8K/MMLU/ARC 均不可区分）

🔗 **樱桃的调度视角**: 这就是"把每张卡榨干"的软件侧教科书——量化 + prefill/decode 分离让单 GPU 并发翻倍，直接对应 GPU 利用率 KPI。对 Master 而言，调度器若能感知 prefill/decode 池的不同资源画像，就能把 CoHDI 提供的可组合硬件用得更狠喵～

### 4. 📦 Zalando 客户端进程内负载均衡器：每秒百万请求、成本降 75%

**原文标题:** Zalando 如何构建了一个每秒能够处理 100 万次请求的客户端进程内负载均衡器
**来源:** InfoQ 中文 | 2026-08-04
**链接:** https://www.infoq.cn/article/97oCpVItccS9jN4lxRdA

🎯 **一句话精髓**: Zalando 把高扇出内部流量的路由决策从共享边缘 LB（Skipper）下沉到调用进程内部，用一致性哈希 + K8s informer 实现百万 QPS、个位数毫秒延迟，并把 Skipper Pod 从 50+ 缩到 8。

🔧 **技术栈**: Skipper / 一致性哈希 (xxHash64) / Kubernetes Informer (watch) / 客户端负载均衡 / 可用区路由 / 渐进式预热

📐 **架构/方法亮点**:
- 批量端点把单个请求拆成最多 100 个并行调用直达 product Pod；原方案每跳都过 Skipper，最慢一跳的延迟峰值无法与自身区分
- 精确复刻 Skipper 算法（xxHash64、每端点 100 个虚拟节点），迁移期两条路径对同一 key 路由到同一 Pod，避免缓存分裂，加/删端点只重映射约 1/N 的 key
- 用基于 watch 的 K8s informer 替换会压垮控制平面的轮询；用开关从 1% 逐步灰度到 100%；30 秒 N 环渐进预热（t^2.5 曲线）消除扩容延迟峰值

💡 **关键数据**: Product Read API 服务 25 个市场、每秒数百万请求、个位数毫秒延迟；Skipper Pod 集群 50+ → 8，每日部署成本 $450 → $110

🔗 **樱桃的调度视角**: 把路由决策下沉到调用进程 + informer watch 替代轮询 + 一致性哈希保缓存稳定，这套思路对 K8s 内部流量调度极具参考价值。AWS CTO Werner Vogels 也点赞了这项工程设计喵～

### 6. 📦 看不见就调试不了：生产级 AI Agent 的可观测性三板斧

**原文标题:** You can't debug what you can't see - Observability for AI Agents
**来源:** CNCF Blog | 2026-08-04
**链接:** https://www.cncf.io/blog/2026/08/04/you-cant-debug-what-you-cant-see-observability-for-ai-agents/

🎯 **一句话精髓**: Agent 不像服务那样崩溃报栈，而是会循环、幻觉、烧 token；作者总结出 Traces（会话时间线）、Costs（单位经济）、Audit（不可变记录）三大可观测支柱，并把成本当作最早的告警金丝雀。

🔧 **技术栈**: Langfuse / Prometheus / 审计日志 / Token 成本监控 / 循环检测 / 批量导出管线

📐 **架构/方法亮点**:
- Traces：每个 LLM 调用/工具执行/子 agent 委派都是一个 span，trace 可嵌套（子 agent 作为父 trace 的子节点）；trace 投递必须非阻塞，用批量导出管线内存缓冲并周期 flush
- 主动护栏优先于告警：硬迭代上限、每工具调用预算、循环检测（拦截连续相同调用）作为"起飞前断路器"，告警只是第二道防线
- 指标 vs trace：Prometheus 标签必须低基数（工具名/agent 名安全，绝不要把 session ID 当标签，否则基数爆炸压垮 metrics server）

💡 **关键数据**: 成本是最敏感的告警信号——单 session 超过该 agent 滚动均值的若干倍即告警，能在账单到来前抓住循环/路由错误

🔗 **樱桃的调度视角**: AI agent 的运维是推理的"运维面"——成本金丝雀、循环检测、基数纪律，这些直接映射到 K8s 上大规模跑 agent 的成本治理。Master 做 GPU 调度时，把每 session 的 token 成本和 GPU 占用挂钩，就能从调度侧兜底防失控喵～

### 7. 📦 KEDA 按 SQS 队列深度伸缩：用积压量而非 CPU 做伸缩信号

**原文标题:** Scaling Kubernetes pods with KEDA based on Amazon SQS queue depth
**来源:** CNCF Blog | 2026-07-31
**链接:** https://www.cncf.io/blog/2026/07/31/scaling-kubernetes-pods-with-keda-based-on-amazon-sqs-queue-depth/

🎯 **一句话精髓**: 在事件驱动 K8s 架构里，CPU/内存反映不了真实压力——worker 在 CPU 上看似空闲，队列却堆了上千条消息；KEDA 直接用 SQS 队列深度驱动 HPA，让伸缩贴合真实需求。

🔧 **技术栈**: KEDA / Amazon SQS / Kubernetes HPA / ScaledObject / TriggerAuthentication / EKS Pod Identity

📐 **架构/方法亮点**:
- 请求流：生产者 → SQS 队列 → KEDA 轮询队列属性算积压 → 更新 HPA 目标指标 → HPA 伸缩 worker Deployment → K8s 调度新 Pod → 队列排空后缩容
- Helm 安装 KEDA（kedacore chart），用 ScaledObject + TriggerAuthentication 把 Deployment 绑到 SQS；AWS 鉴权用 IRSA 或 EKS Pod Identity，IAM 最小权限（GetQueueAttributes/GetQueueUrl/ReceiveMessage/DeleteMessage/ChangeMessageVisibility）
- 可调参数：queueLength、activationQueueLength、cooldown、HPA behavior

💡 **关键数据**: backlog 才是队列驱动系统的真实伸缩信号；队列空时缩到零可降空闲成本，突发时更快扩容

🔗 **樱桃的调度视角**: "按真实压力而非 CPU 伸缩"的哲学，和 GPU 调度按队列/请求深度伸缩是同一思路。对 Master 的 AI 推理网关，按推理请求队列深度驱动推理副本扩缩，比按 GPU 利用率更贴合实际负载喵～

## 📓 樱桃的今日学习总结

1. **GPU 调度正全面转向 DRA 范式** - CoHDI（硬件可组合）、HAMi-DRA（异构调度）都基于 Kubernetes DRA 构建，Device Plugin 时代正在过去；CoHDI 甚至能做到按 Pod 请求动态挂载 GPU 且无需重启，这是调度粒度从"节点级"向"设备级实时组合"的跃迁。
2. **Prefill/Decode 分离是 AI 推理的统一主线** - Cloudflare 用软件侧量化 + 阶段分离把单卡并发翻倍，CoHDI 用硬件侧可组合资源适配两阶段不同画像——软硬件协同的 disaggregated inference 正在成为标配，调度器需要感知 prefill（计算受限）与 decode（访存受限）两种截然不同的资源需求。
3. **"有效利用率"取代"堆卡量"成为新 KPI** - 无论 WAIC 的"算力有效利用率成核心指标"，还是 Cloudflare 的单卡并发优化，都在回答同一个问题：怎么把每张卡榨干。这要求调度器从"分配 GPU"进化到"按推理阶段 + 并发画像精细化放置"。
4. **可观测性的成本金丝雀思维可迁移到调度** - AI Agent 把成本当最早告警信号、用循环检测做断路器；同理，GPU 调度也可把"单 session token 成本/GPU 占用"纳入调度反馈环，从调度侧兜底防失控。
