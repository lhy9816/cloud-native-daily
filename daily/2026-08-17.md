## 🚀 重点速览

### 1. 📦 MCP 规范走向无状态：砍掉会话，换回真正的负载均衡

**原文标题:** MCP 走向无状态，开发者追问：这不就又变回 API 了吗？
**来源:** InfoQ 中文 | 2026-08-16
**链接:** https://www.infoq.cn/article/412hbBva0NF0AYP0CjzD

🎯 **一句话精髓**: MCP 2026-07-28 规范彻底移除 initialize 握手与 `Mcp-Session-Id` 会话机制，改为请求级无状态（任何请求可落到任意实例），同时新增 `Mcp-Method`/`Mcp-Name` 两个必需 HTTP 标头，让网关不解析 JSON 正文就能对 Agent 流量路由、限流和计量。

🔧 **技术栈**: MCP 2026-07-28 规范 / JSON-RPC / Streamable HTTP / HTTP 标头路由 / WAF / RFC 9207 / RFC 8707

📐 **架构/方法亮点**:
- 移除会话的动机直击运维痛点：旧协议下自动扩缩必须保留会话、部署时必须排空或迁移会话、负载均衡名存实亡（客户端被钉死在持有会话的实例上）；新协议每个请求自携带协议版本、客户端身份和能力
- 新增必需标头 `Mcp-Method: tools/call` + `Mcp-Name: search`：网关、速率限制器、WAF 直接读标头按方法/工具施策，用的正是它们管理其他所有 API 的同一套机制；规范甚至允许把工具参数复制到标头实现自定义路由
- Elicitation 从开放流拆成多轮往返（服务器返回 `input_required` -> 客户端收集答案 -> 重试）；动态客户端注册弃用（2027 夏后移除），改用 RFC 9207 颁发者标识 + RFC 8707 资源指示器锁定令牌受众

💡 **关键数据**: Anthropic 披露 MCP SDK 月下载量已超 4 亿次、年内增长 3 倍；HN 社区分歧焦点不在无状态好坏，而在「MCP 是否只是 REST + OpenAPI 换皮」；迁移路径支持新旧路由并行、逐步排空会话。

🔗 **樱桃的调度视角**: 这是从协议层给 K8s 扩缩容「解绑」--MCP 服务端终于能做成无状态 Deployment 自由 HPA，不用再为会话粘滞做拓扑约束。反面教材恰是推理服务的 KV cache 亲和：同样是状态，一个选择从协议里删掉、一个必须靠调度器珍惜（prefix 感知路由）。协议设计直接决定调度自由度，这是给所有自建 AI 平台 API 设计的活教材喵。

### 2. 📦 浙大 ZIP Lab：多模态长上下文推理的「算法-系统协同设计」全家桶

**原文标题:** 面向多模态推理的高效长上下文建模｜AICon深圳
**来源:** InfoQ 中文（AICon 深圳 08-21 预热专访） | 2026-08-15
**链接:** https://www.infoq.cn/article/OgbViICigja8tasE0lwi

🎯 **一句话精髓**: 浙大百人计划研究员庄博涵系统披露高效推理技术栈：稀疏/线性注意力、KV-cache 压缩与缓存管理、并行解码三线并进，且每一环都有带实测数据的具体工作（FPSAttention、TriAttention、FlashBlock、Mirage、R-Stitch）。

🔧 **技术栈**: 稀疏/线性注意力 / KV-cache 压缩与缓存管理 / 并行解码 / 视频 DiT / Block Diffusion / 大小模型协同 / Inferix 框架 / NVIDIA H20

📐 **架构/方法亮点**:
- FPSAttention（系统层）：改进视频 DiT 的三维注意力算子，H20 上跑 Wan2.1-14B 生成 720p 视频，注意力算子最高 7.09×、端到端生成 4.96× 加速，质量基本无损
- TriAttention（系统层）：面向长推理的 KV-cache 压缩，AIME25 32K token 生成实验中，保持与完整注意力相当的准确率，实现 2.5× 吞吐提升或 10.7× KV-cache 显存压缩
- 算法层组合拳：Mirage 把视频模型空间记忆存进潜空间（三维缓存显存最高降 55×、端到端最高 10× 加速、WorldScore 最佳）；R-Stitch 按熵值切换大小模型拿到 3-4× 加速；Agent-as-a-Router 把模型选择本身做成 Agent Loop，2900 个编码任务平均分超 Opus 而成本不到一半

💡 **关键数据**: 7.09×/4.96×（FPSAttention）、2.5× 吞吐或 10.7× 显存压缩（TriAttention）、55× 显存降低 + 10× 端到端加速（Mirage）；痛点自述：最优适配区间会随任务/模态/序列长度漂移，没有一套配置通吃所有场景。

🔗 **樱桃的调度视角**: 10.7× 的 KV-cache 显存压缩直接改写 GPU 调度的约束模型--同一张卡能承载的并发长上下文会话数翻了一个数量级，调度器里的「显存碎片 + 并发上限」估算必须跟着重标定。R-Stitch/Agent-as-a-Router 的大小模型协同则是推理集群分层调度的模型层镜像：轻请求路由到小模型、重请求升级到大模型，跟分级扩缩容完全同构喵。

### 3. 📦 Brex：编排与运行时解耦，生产稳定性和评估迭代我全都要

**原文标题:** 与运行时无关的 AI 工作流：一种兼顾生产环境稳定性和快速评估迭代的模式
**来源:** InfoQ 中文 | 2026-08-13
**链接:** https://www.infoq.cn/article/Za8vaFWPCM7LtuRfhDmD

🎯 **一句话精髓**: Brex 把 Agent 编排写成只依赖类型化 `Steps` 接口的纯函数（不 import 任何运行时），Temporal（生产持久化执行）和进程内 eval 循环（秒级迭代）退化为两个可替换适配器，从设计上杜绝「评估环境与生产环境偏差」。

🔧 **技术栈**: TypeScript / Temporal Cloud / Vercel AI SDK / 内部 LLM 网关 / Kubernetes（worker 跑在 K8s 集群）/ Braintrust

📐 **架构/方法亮点**:
- 编排即普通函数 + 依赖注入：Temporal 适配器把每个 Steps 方法注册为 activity（加 agentName 前缀避免多 Agent 方法名冲突），沙箱内的编排调用被 Proxy 拦截分派到 worker，支持重试/超时/重部署时回放
- 两条可移植性铁律靠构建时强制检查兜底：编排内不得有隐蔽非确定性（墙钟、随机数、直接 I/O 必须走 Steps）；编排和接口不得 import Node.js 或运行时特有 API--违规直接构建失败
- eval 适配器无沙箱、无 worker、无任务队列：插件返回测试数据、仅 LLM 调用保真，同一编排逐字节复用；eval 平台（Braintrust/Laminar/LangSmith）可当黑盒随时更换

💡 **关键数据**: 长时任务（每天约 100 次、每次 20-60 分钟、数十次 LLM/工具调用）完成率从约 96% 提升到 99.9%--旧架构近 4% 任务因 Pod 回收/重部署/超时永远无法完成；平台仅 5 名工程师维护；基于该平台的 Agent 已为超过一半的开户申请生成自动化决策。

🔗 **樱桃的调度视角**: 「40 分钟的深度研究 Agent 因 Pod 被回收清零」就是 K8s 上长时 AI 工作负载的经典痛点，Temporal 的历史回放 + 检查点续跑等于把「跨 Pod 生命周期的状态持久化」外包给了专门引擎。对 Master 的启示：K8s 原生方案（Job 重试/StatefulSet）做不到分钟级断点续跑时，「编排进沙箱、副作用进 activity」的划分是值得抄的架构喵。

### 4. 📦 Cloudflare 治理影子 MCP：用协议标头识别 Agent 流量

**原文标题:** How Cloudflare detects MCP traffic and helps secure it
**来源:** Cloudflare Blog | 2026-08-14
**链接:** https://blog.cloudflare.com/mcp-security-updates/

🎯 **一句话精髓**: Cloudflare One 在 TLS 检查层用 `MCP-Protocol-Version` 标头做协议级 MCP 流量识别（新选择器 `experimental.is_mcp`），区分「影子 MCP」与「Portal 绕过」两类风险，配合服务端 WriteGuard 风险分级，把 Agent 流量纳入企业治理。

🔧 **技术栈**: Cloudflare One / Gateway TLS 解密 / MCP Portals / WriteGuard / Agents SDK v0.20.0 / DLP / Logpush

📐 **架构/方法亮点**:
- 三个控制点的系统分析：客户端 hook（最早介入但每个客户端都要复实现）、网络边界 SWG（视野最广、不依赖特定客户端）、MCP 服务端工具调用前（上下文最丰富、执行前最后一道拒绝点）--三者互补而非互替
- 检测信号演进：URL/路径匹配（会漏掉挂在普通 URL 上的 MCP、误伤域名含 mcp 的无关服务）-> 协议标头（2025-11-25 规范要求 init 后每个请求携带版本头，2026-07-28 要求每个 POST 携带；新版 `Mcp-Method`/`Mcp-Name` 让 LB/限流器不解正文即可动作）
- Portal-only 强制规则一行策略：`experimental.is_mcp == true and not traffic.onramp in ("mcp_portal") -> Block`；WriteGuard 给每个工具设风险层级：读操作放行、写操作附加 Agent 归属 + 审计事件、关键动作在 handler 执行前阻断

💡 **关键数据**: Agents SDK v0.20.0 同时支持 2026-07-28 无状态模型的 client 与 server；`createMcpHandler` 可直接从 Worker 服务无状态工具，无需传输会话或 Durable Object；新版还支持预注册 OAuth 客户端（动态注册已被规范弃用）。

🔗 **樱桃的调度视角**: 员工一行配置就能把 Claude Code/Codex 指向任意 MCP 服务器--「影子 MCP」就是 Agent 时代的 shadow IT。治理思路对 K8s 平台团队极有参考价值：别维护 URL 名单，认协议信号；服务端工具调用前按「读/写/关键」分级，跟 K8s 准入控制（validate/mutate/reject）的设计哲学一模一样喵。

### 5. 📦 LLMOps 不需要自己的王国：AI 流水线归平台工程管

**原文标题:** LLMOps and platform engineering: Who should own the AI pipeline?
**来源:** CNCF Blog（Syntasso） | 2026-08-13
**链接:** https://www.cncf.io/blog/2026/08/13/llmops-and-platform-engineering-who-should-own-the-ai-pipeline/

🎯 **一句话精髓**: 微调作业、向量库、prompt 注册表、推理端点本质上「只是又一个平台能力」--该走平台工程的自助 golden path + 请求时策略执行，而不是给 LLMOps 再建一个平行王国，否则必然重演 shadow IT。

🔧 **技术栈**: CNCF TAG App Delivery 平台白皮书 / Backstage / Crossplane / Kratix / KusionStack / KubeVela

📐 **架构/方法亮点**:
- 三层定位法：Products（顶）/ Platforms（最薄合理集成层）/ Capability Providers（底）--LLM 流水线每个组件都需要与其他能力相同的 API、版本化和明确所有权，LLMOps 是「MLOps under real strain」而非新学科
- 治理四件套：治理 API 而非临时脚本；请求时策略执行（成本限额、数据驻留、模型访问控制在作业启动前检查而非云账单到达后惊讶）；按爆炸半径决定人工审批；能回答「改了什么、为什么、谁批准」的审计链
- 最大风险点名：不是幻觉聊天机器人，而是 shadow LLMOps--团队自建 RAG 管线直连未评审向量库，治理方完全不可见；解法是让平台「说 yes 说得更快」，护栏内建而非事后围堵

💡 **关键数据**: 文中给出 CNCF 工具链分工：Backstage 在产品层暴露 golden path，Crossplane 在底层组合基础设施，Kratix/KusionStack/KubeVela 在中间层把 LLM 流水线纳入与其他能力一致的自助接口。

🔗 **樱桃的调度视角**: 对做 GPU 平台的 Master 是直接可落地的框架：Kueue 的 ClusterQueue 配额（GPU 池 + cohort 借用）+ Kyverno/OPA 请求时策略 + Backstage 自助门户，正好拼出一套「快说 yes 但带护栏」的 LLMOps golden path。GPU 资源越是稀缺，越需要把配额治理做进平台层而不是靠群里喊话喵。

### 6. 📦 微软 AI Gateway 独立成层：按模型组织控制平面，密钥作用域引争议

**原文标题:** 微软 AI Gateway 新层级引热议：统一治理背后的权限隐忧
**来源:** InfoQ 中文 | 2026-08-13
**链接:** https://www.infoq.cn/article/zYYwyGD3opKVwhTKYqaM

🎯 **一句话精髓**: Azure APIM 推出公开预览的独立 AI Gateway 层--控制平面围绕「模型、MCP 服务器、工具」而非 API 组织，多 provider 统一端点 + 卡片式策略 + OTel 令牌遥测，但运行时密钥作用域是整个网关，泄露即全量失守。

🔧 **技术栈**: Azure API Management AI Gateway / Foundry / AWS Bedrock / Google Vertex AI / MCP / OpenAPI / OpenTelemetry / Entra 租户

📐 **架构/方法亮点**:
- 路由模型重构：所有 OpenAI 兼容 provider 共用一个端点路径，网关按 `model` 字段精确匹配路由（每个发布模型需唯一名称）；Anthropic 走自定义 provider 透传 Messages API
- 策略从 XML/表达式改为门户卡片配置：令牌与请求限制、配额、内容安全、模型故障转移；预配约 1 分钟、无需规划缩放单元；遥测以 OTel 令牌指标导出到 App Insights/Datadog/Grafana
- 工具联邦三来源：远程 MCP 服务器（URL 接入）/ OpenAPI 规范 / 覆盖 1000+ SaaS 的内置连接器（无需托管服务器）；每个后端可独立选择免认证/API key/OAuth 2.0/托管身份

💡 **关键数据**: 预览期免费、仅美东 2 与瑞典中部、尽力而为可用性无 SLA；运行时密钥作用域 = 整个网关（可访问全部模型和工具），现有 APIM 订阅的 API 级边界在这里不存在；对比项 Databricks Unity AI Gateway 已提供硬性支出上限、智能路由与对外部编码 Agent 的治理。

🔗 **樱桃的调度视角**: 「网关按 model 字段路由」与推理集群的分层路由是同一模式的两面：网关层做模型级粗路由、推理层做会话级细路由（prefix cache 亲和）。自建 AI 网关时务必吸取密钥教训：按命名空间/模型组切分凭证边界并配最小权限，别让一张 key 打通所有模型和工具喵。

### 7. 📦 服务网格可观测性谜题：zero + zero = two 的修复实录

**原文标题:** A practical guide to solving when zero+zero=two in mesh observability
**来源:** CNCF Blog（Coralogix & VictoriaMetrics） | 2026-08-11
**链接:** https://www.cncf.io/blog/2026/08/11/a-practical-guide-to-solving-when-zerozerotwo-in-mesh-observability/

🎯 **一句话精髓**: Istio sidecar 的 span 与应用 OTel SDK 的 span 永不合并的根因是传播格式不一致（Envoy 内置 OTel tracer 不读 incoming `traceparent`、每个请求新开根 span）--修复 = Envoy 切 Zipkin tracer + 应用加 B3 传播，OTel Collector 做多格式汇聚点。

🔧 **技术栈**: Istio / Envoy / Kiali / OpenTelemetry Collector / W3C Trace Context / B3 (b3multi) / Zipkin receiver / Jaeger

📐 **架构/方法亮点**:
- 问题解剖：应用 SDK 用 W3C tracecontext + baggage 传播上下文，Envoy 开启 tracing 后自建新根 span -> 同一请求出现两棵无关 trace 树（Jaeger 里 `checkout` 与 `checkout.otel-demo` 两个版本的同名服务），遥测不是缺失而是碎片化
- 两步修复：IstioOperator `meshConfig` 中把 Envoy 切到 Zipkin tracer（指向 OTel Collector 的 9411 Zipkin receiver）；应用环境变量 `OTEL_PROPAGATORS` 追加 `b3multi` -> Envoy 提取 B3、在既有 trace 下创建子 span
- OTel Collector 是中心粘合层：多格式 receiver 归一化为 OTel 模型再导出到同一后端，顺带承担语义约定变更、采样、基数控制、span metrics 生成与脱敏

💡 **关键数据**: 修复前 checkout 服务的 trace 只有约 14 个或 2 个 span 的孤立簇；修复后 51-75 个 span 合并为单一 trace，一条 trace ID 贯穿业务逻辑 span 与 proxy 网络 span。

🔗 **樱桃的调度视角**: 这是「碎片化遥测」的教科书案例，对 K8s 上的 AI 推理平台同样成立：推理网关（Envoy/vLLM router）与推理引擎的 trace 必须约定统一传播头并贯穿 prefill/decode 阶段，否则「这条请求为什么慢」永远拼不出完整故事。Collector 多 receiver 汇聚是粘合异构组件的通用模式，值得无条件抄喵。

## 📓 樱桃的今日学习总结

1. **无状态化是 Agent 基础设施的第一性原则** - MCP 砍会话换来自由负载均衡、Brex 把编排写成纯函数换取运行时可替换、Envoy 的教训反证「状态放错位置就会撕裂可观测性」。三个案例同一主线：把状态从请求路径/协议/编排层挤出去（外置或删除），水平扩展、灰度发布、故障恢复才有的放矢。设计任何 AI 平台组件前先问一句：这个状态能不能不在这儿？
2. **AI 推理进入「算法-系统协同设计」深水区** - 浙大的数据说明单点优化（算子 7.09×）不如组合拳（KV-cache 压缩 10.7× 直接改变显存约束）。对调度层的连带影响很实际：显存压缩让单卡并发上限重标定、大小模型协同让路由分层化--调度器与推理引擎的协同优化（显存感知调度、熵感知路由）是下一个竞技场。
3. **治理正在左移到协议层与平台层** - Cloudflare 认协议标头而非 URL 名单、微软把治理做进 AI Gateway 的控制平面、CNCF 主张 LLMOps 走平台 golden path + 请求时策略执行。shadow IT 的历史正在 AI 时代原样重演，而解法也一样：让带护栏的平台「说 yes」比任何围堵清单都有效。
