### 1. 🧠 LLMOps 与平台工程：AI 推理管道到底该归谁管？

**原文标题:** LLMOps and platform engineering: Who should own the AI pipeline?
**来源:** CNCF Blog | 2026-08-13
**链接:** https://www.cncf.io/blog/2026/08/13/llmops-and-platform-engineering-who-should-own-the-ai-pipeline/

🎯 **一句话精髓**: 大模型让 MLOps 分裂出 LLMOps 新层，但 AI 推理管道的归属权问题如果搞错，会重现当年 DevOps 的 Shadow IT 困境——只是这次用 prompt 替代了 Jenkinsfile。

🔧 **技术栈**: LLMOps / CNCF TAG App Delivery / Backstage / Crossplane / Kratix / KubeVela / KusionStack / Hugging Face Transformers / Kubeflow / MLflow

📐 **架构/方法亮点**:
- 基于 CNCF TAG App Delivery 平台白皮书的三层模型：Product 层（Backstage 金色路径）→ Platform 层（Crossplane/Kratix 编排）→ Capability Provider 层（GPU 推理端点/向量数据库/prompt 注册表），将 LLM 推理服务视为一种平台能力
- 明确划分 DevOps（部署工单）/ MLOps（模型版本+漂移监控）/ LLMOps（prompt 版本化 + RAG 管道 + 安全评估）三层职责，核心问题是「谁拥有哪一层，是否有人在跨层协调」
- Prompt 被定义为版本化制品（versioned artifact）而非一次性字符串，推理服务在 GPU 端点上的部署纳入平台工程的自服务金色路径管理

💡 **关键数据**: 文章指出 LLM 微调和服务成本显著高于传统 ML 模型，输出评估从单一精度指标扩展到安全性和可信度

🔗 **樱桃的调度视角**: 这篇文章直接关联 Master 关注的 K8s 上 AI 推理方向——当推理端点、向量数据库、prompt 注册表都变成 K8s 上的 CRD 和平台能力时，GPU 调度、模型路由和资源计量就是平台团队必须面对的调度层问题。Crossplane + Kratix 的组合思路值得在构建内部 AI 推理平台时参考喵～

### 2. 🔧 11 分钟零人工：在 Kairos 上构建自愈式 Kubernetes 升级管道

**原文标题:** Eleven minutes, zero humans: Building a self-healing Kubernetes upgrade pipeline on Kairos
**来源:** CNCF Blog | 2026-08-14
**链接:** https://www.cncf.io/blog/2026/08/14/eleven-minutes-zero-humans-building-a-self-healing-kubernetes-upgrade-pipeline-on-kairos/

🎯 **一句话精髓**: 用 6 个 CNCF 工具串联出一条完全自动化的 K8s 控制面升级管道——从镜像发布检测到 A/B 分区滚动升级，全程零人工干预，3 节点 HA 集群升级仅需 11 分钟。

🔧 **技术栈:** Kairos Hadron (immutable OS) / K3s HA / Cilium CNI / OpenTofu / Gitea Actions / Renovate / Kyverno / Cosign / ArgoCD / kairos-operator

📐 **架构/方法亮点**:
- Kairos 采用 A/B 分区升级模式：不就地修补，而是将新 OS 镜像写入非活跃分区后重启切换，回滚只需重启旧分区——从根本上保证供应链安全
- 六工具链式协作：Renovate 监控 Quay 镜像仓库 → 自动开 PR 更新版本 → Kyverno ClusterPolicy 准入校验镜像来源 → Cosign 验证 OIDC 签名 → ArgoCD 检测 Git 漂移并同步 → kairos-operator 执行 cordon/拉取/写入/重启/等待归队
- 关键 bug 修复：升级 spec 中 `concurrency: 0` 实际意味着「所有节点同时升级」而非「逐个升级」，曾导致 3 个控制面节点同时重启——etcd 法定人数幸存纯属运气，修正为 `concurrency: 1` 才安全

💡 **关键数据**: Hadron v0.4.0 升级实测时间线：11:42 PR 合并 → 11:51:36 全部完成，总耗时约 11 分钟；单节点升级（镜像拉取 + A/B 写入 + 重启 + Ready）约 2-4 分钟；镜像大小 324MB，拉取耗时 25.5 秒

🔗 **樱桃的调度视角**: `concurrency` 参数的教训对 Master 做 K8s 调度有直接参考——滚动升级时的节点隔离策略和 etcd 法定人数保护是调度层面的核心安全问题。kairos-operator 的 cordon → upgrade → wait-for-ready 模式，本质上就是一种节点级调度协调器，和 Volcano/PodDisruptionBudget 的驱逐逻辑异曲同工喵～

### 3. 📦 用 Docker + ModelPack 推进 AI 模型互操作性：OCI 制品标准化之路

**原文标题:** Advancing AI model interoperability with Docker and ModelPack
**来源:** CNCF Blog | 2026-08-12
**链接:** https://www.cncf.io/blog/2026/08/12/advancing-ai-model-interoperability-with-docker-and-modelpack/

🎯 **一句话精髓**: ModelPack 项目与 Docker Model Runner 合作，推动 AI 模型以 OCI 制品格式标准化打包与分发，解决模型与运行时工具紧耦合的问题——让 AI 模型像容器镜像一样可移植。

🔧 **技术栈**: ModelPack / Docker Model Runner (DMR) / OCI Artifacts / Cosign / Red Hat / Nutanix / Ant / Jozu

📐 **架构/方法亮点**:
- ModelPack 定义开放标准 `application/vnd.cncf.model.manifest.v1+json`，Docker Model Runner 使用 `application/vnd.docker.ai.model.config.v0.1+json`，两者均基于 OCI 制品但媒体类型不同——文章对比了 Config、Artifact Type、License 等关键媒体类型的差异
- AI 模型管理当前痛点：压缩包、容器镜像、wrapper 元数据、对象存储、Git LFS、自定义模型仓库——格式碎片化导致模型在不同框架间迁移困难
- OCI 制品在 AI 领域加速渗透，ModelPack 和 DMR 都利用 OCI 作为打包与分发框架，通过统一制品格式降低模型开发和运行的迁移成本

💡 **关键数据**: ModelPack 的贡献者来自 Nutanix、Ant、Jozu、Red Hat 等多家组织；Docker Model Runner 使用独立的媒体类型体系打包模型为 OCI 层

🔗 **樱桃的调度视角**: 这直接关联 Master 的 AI 推理方向——如果 AI 模型能以 OCI 制品标准化，K8s 上的模型分发就可以复用现有的镜像仓库（Harbor 等）和 P2P 分发（Dragonfly）基础设施。GPU 节点拉取模型就像拉取容器镜像一样，调度器可以把模型大小和拉取时间纳入调度决策喵～

### 4. 🛡️ Kyverno 不是安全工具，而是平台原语

**原文标题:** Kyverno is a platform primitive, not a security tool
**来源:** CNCF Blog | 2026-08-19
**链接:** https://www.cncf.io/blog/2026/08/19/kyverno-is-a-platform-primitive-not-a-security-tool/

🎯 **一句话精髓**: Kyverno 的四大能力中三个是建设性的（mutate/generate/verify），只有 validate 符合「安全门卫」模型——把它归类为安全工具，等于只用了一 Quarter 的能力。

🔧 **技术栈**: Kyverno / CEL (Common Expression Language) / Pod Security Standards / GitOps / ArgoCD / Flux / Crossplane

📐 **架构/方法亮点**:
- 平台原语四属性框架：① 抽象复杂性（开发者无需理解底层）② 提供保证（使用即自动满足属性）③ 可组合（与其他原语构建更高层能力）④ 自服务（从平台获取而非工单队列）
- 五个平台工程实战场景：命名空间自动装配（自动生成 NetworkPolicy/ResourceQuota/LimitRange）、Sidecar 注入（可观测 agent/mesh proxy 在准入时 mutate 进 Pod spec）、镜像引用重写（`nginx:1.25` → `mirror.internal/nginx:1.25`）、默认资源请求注入、所有权标签管理
- 策略即产品的理念：策略需要版本管理、用户、弃用周期、异常流程；渐进式发布（audit → warn → enforce）成为策略发布的标准方式；GitOps 部署范围从应用清单扩展到「塑造工作负载的规则」

💡 **关键数据**: Kyverno 四大能力：validate（守卫）、mutate（铺路）、generate（脚手架）、verify images（信任）——mutate 能力被严重低估和使用不足

🔗 **樱桃的调度视角**: 镜像引用重写和默认资源请求注入这两个场景对 K8s 调度有直接价值——通过 mutate 自动注入 CPU/memory requests，调度器就能获得准确的资源画像来做 bin-packing。命名空间自动装配 + ResourceQuota 生成也和调度公平性直接相关喵～

🎯 **一句话精髓**: 视觉 AI 落地的核心瓶颈已从模型精度转向系统工程能力——从边缘部署、持续迭代到多模型调度路由，模型之外的工程体系才是真正的差异化壁垒。

🔧 **技术栈**: 格灵深瞳 Glint AI Studio / GBOX 边缘智算盒子 / MENTOR 算法训练 / EXPERT 算法运营 / Token Fabric / TaaS / DeepBot / Agent

📐 **架构/方法亮点**:
- 完整的视觉 AI 运行链路：模型服务（能力来源）→ MENTOR（算法持续生产）→ EXPERT（算法持续运营）→ GBOX（边缘部署运行）→ Token Fabric（AI 服务统一调度/路由/计量）→ DeepBot（Agent 与业务集成）
- Token Fabric 定位为 AI Service Operations / Runtime 层：解决多模型同时运行时的请求路由、推理能力统一接入、资源调度、Token 计量和服务治理问题；区分 MaaS（模型能力服务化）与 TaaS（Token 生产运营）

💡 **关键数据**: 文章约 2791 字，核心观点是「当模型越来越容易获得，真正拉开企业 AI 差异的恰恰是模型之外的能力」

🔗 **樱桃的调度视角**: Token Fabric 的多模型路由 + 资源调度 + 计量能力，本质就是一个 AI 推理专用调度层——和 K8s 上用 KubeRay/Volcano 做 GPU 推理调度的思路高度一致。边缘部署（GBOX）的异构算力管理和 K8s 的 DeviceShare/GPU 共享调度面临同样的碎片化问题。TaaS 的 Token 计量概念也值得在 K8s AI 推理平台的成本管理中借鉴喵～

### 7. 🔬 Cloudflare Workers 远程 Spectre 攻击复现：V8 隔离区的侧信道安全

**原文标题:** A revisit of remote Spectre attacks on Cloudflare Workers
**来源:** Cloudflare Blog | 2026-08-19
**链接:** https://blog.cloudflare.com/revisiting-spectre-attacks-on-workers/

🎯 **一句话精髓**: Cloudflare 在生产环境中复现了针对 Workers V8 isolate 的远程 Spectre 侧信道攻击，实现 12 bit/s 的跨租户数据泄露——揭示了基于语言级隔离的多租户运行时的安全边界。

🔧 **技术栈**: V8 Isolates / Spectre 侧信道 / Dynamic Process Isolation (DyPrIs) / V8 Sandbox / WebSocket 远程计时器 / Durable Objects / PLRU 缓存替换策略 / seccomp / Linux namespaces

📐 **架构/方法亮点**:
- 两种 Spectre gadget：① 堆指针泄露 gadget（利用 TypedArray 存储 64 位原始指针的特性，泄露 isolate 堆基地址）② 推测类型混淆 gadget（mistrain `instanceof` 分支预测，transient 跟随攻击者控制的 64 位指针读取任意地址）
- 信号放大技术：利用 L1 缓存的树状 PLRU 替换策略，通过精心设计访问模式让单次缓存事件被无限放大，使远程 WebSocket 计时器（亚毫秒级）足以区分缓存命中/未命中
- Durable Objects 绕过资源限制：WebSocket 消息重置 CPU 时间和请求计数限制，使攻击者可保持 isolate 存活 5-20 小时；攻击者可故意在流量低谷的边缘节点（如欧洲时段的澳洲节点）运行以降低噪声

💡 **关键数据**: 远程泄露速率 12 bit/s（99% 准确率）；此前攻击仅 120 bit/h；利用 Durable Objects 保持 isolate 存活超过 20 小时；V8 Sandbox 已部署作为防御措施

🔗 **樱桃的调度视角**: 这篇文章对 K8s 多租户安全有深刻启示——V8 isolate 的语言级隔离与 K8s 的 Pod 级隔离面临相似的侧信道挑战。当 AI 推理服务在共享 GPU 节点上运行时，GPU 显存的侧信道泄露（如 VRAM 时序攻击）同样值得关注。Cloudflare 的 DyPrIs 动态隔离 + V8 Sandbox 防御思路，对 K8s 上敏感工作负载的节点隔离策略有参考价值喵～

## 📓 樱桃的今日学习总结

1. **AI 推理的归属权之争是平台工程的新战场** - LLMOps 不只是 MLOps 换个名字，它引入了 prompt 版本化、RAG 管道、安全评估等新维度。关键不是「谁拥有管道」而是「谁拥有哪一层，是否有人在跨层协调」。平台工程应该把推理端点/向量数据库/prompt 注册表当作平台能力来管理，避免第三套平行技术栈出现。

2. **模型标准化打包是 AI 推理基础设施成熟的关键标志** - ModelPack 和 Docker Model Runner 都在推动 AI 模型以 OCI 制品格式打包，这意味着模型分发可以复用容器镜像生态（Harbor/Dragonfly/Cosign）。当模型像镜像一样可移植后，K8s 调度器就能把模型拉取纳入调度决策，GPU 节点的模型预热和缓存管理也会成为新的调度优化方向。

3. **「模型跑起来」之后才是系统工程真正开始的地方** - 视觉 AI 的完整链路（模型服务→算法生产→边缘部署→服务运营→Agent 集成）揭示了一个趋势：模型能力本身在快速普及，但企业级 AI 的差异化越来越依赖模型之外的工程体系——多模型路由、Token 计量、边缘异构算力管理、持续迭代闭环。Token Fabric/TaaS 的概念值得在 K8s AI 推理平台的成本管理和服务治理中借鉴。
