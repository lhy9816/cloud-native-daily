### 1. 📦 Intel 白皮书：一个机柜能跑多少 Agent，瓶颈不在 GPU

**原文标题:** 单个机柜到底能跑多少个 Agent？答案不在 GPU 身上
**来源:** InfoQ 中文 | 2026-09-19
**链接:** https://www.infoq.cn/article/brH7TRcHB9evl32KQJkY

🎯 **一句话精髓**: Agent 一轮任务里模型调用只占 40% 时间，剩下 60% 全在主机端（工具执行 35%、数据服务 10%、状态搬运 8%、编排调度 7%）；Intel 提出机柜级公式「可交付智能体数 = 理论值 × 调度有效性 × 资源平衡度 × 计算卸载效益」，数据中心该优化的是满足延迟承诺下的实际交付量，不是理论算力上限。

🔧 **技术栈**: Agent 工作负载建模 / 沙箱快照与恢复 / KV Cache / CXL Flat Memory / AMX·QAT·DSA·IAA 硬件卸载 / p99 膝点分析

📐 **架构/方法亮点**:
- 对 739 次匿名化 Claude Code 对话实测：单请求时主机端 CPU 仅占端到端延迟 0.4~0.6%，并发到 32 会话时跳到 11%~15%，其中 94% 的增长来自调度与排队而非实际计算，单请求占用主机 CPU 时间放大 20 倍以上
- 三因子优化：调度器按节点实时采样（CPU/内存/I/O/KV 状态位置）「跟着状态走」；CXL 扩展内存与 DDR5 合一地址空间（Flat Memory）免掉 OS 搬数据；IAA 卸载沙箱快照压缩，恢复时延降 38~42%
- 定义「膝点」：p99 延迟在某并发临界点前平稳、之后失控，所有优化本质是把膝点右移

💡 **关键数据**: 自适应运行时优化后膝点从 235 推到 300 并发 Agent（同 p99 目标下 +28%）；理论容量高 33% 的机柜，综合三因子后实际交付反而落后 23%（1.1 vs 0.85 单位）；编码 Agent 场景 GPU 估算仅 50%~60% 时间在真正干活；英特尔与 SAP 联测中 Flat Memory 跑出全 DDR5 性能的 96%、内存成本降 25%

🔗 **樱桃的调度视角**: 这篇等于给「调度有效性」定了价——94% 的 CPU 开销增长来自排队，意味着沙箱调度、KV 亲和这些软件层手段比换芯片更能提升机柜交付量。Master 做推理平台容量规划时，建议把「每节点并发 Agent 膝点」纳入压测指标，只看峰值吞吐会被理论值骗喵。

### 2. 🛠️ 阿里 Atrex Kernel Agent：从生产 Trace 到算子上线的全自动优化闭环

**原文标题:** 从算子调优到推理自治：构建 MaaS 场景下的 AI Inference 自动优化闭环｜QCon上海
**来源:** InfoQ 中文 | 2026-09-19
**链接:** https://www.infoq.cn/article/G4tlQvg2IsabE0v1RDOE

🎯 **一句话精髓**: MaaS 的模型/卡型/请求工况变化太快，人工「需求分析→性能定位→算子开发→验证上线」跟不上——阿里把整条链做成自动闭环：从生产 Trace 挖热门算子生成 Benchmark，由 Atrex Kernel Agent 在 Loop 里完成优化，再回接推理框架做端到端回归和灰度。

🔧 **技术栈**: Atrex Kernel Agent / Agent Loop / FlashInfer / vLLM 类推理框架 / 生产 Trace 清洗泛化 / ABBA 测量 / Git worktree 隔离

📐 **架构/方法亮点**:
- 优化任务不从人工需求来，而是从真实运行 Trace 识别热门算子、归并动态 Shape、脱敏泛化成可复现 Benchmark，并建立正确性/数值容差/性能三重评测标准与优先级
- Agent Loop 内自动做 profile→瓶颈分析→方案生成→代码修改→验证复盘；外围 Loop 管实验预算、正确性门禁、状态恢复和终止控制，用完整 workload + 同卡 ABBA 测量防测量波动误判
- 「Kernel 局部变快 ≠ 端到端有收益」被列为流程必检项：优化后必须回接推理框架做算子级 + 模型端到端回归，再灰度发布并保留回滚

💡 **关键数据**: 相关实践支撑阿里百炼 MaaS 大规模 GPU 集群优化，并支撑 Qwen3.8 拿下 NVIDIA SOL-ExecBench FlashInfer 算子优化榜首；QCon 上海 10 月 22-24 日演讲（阿里高级技术专家杨林枫，昇腾算子编译器 SWFT 前设计者）

🔗 **樱桃的调度视角**: 这条和昨天智谱 Infra Agent 是同一趋势的两面：一个调「集群参数」，一个调「算子代码」，推理平台的优化闭环正在从 CI 工具进化成自主体。他们自曝的坑很值得抄进 checklist：Agent 会过拟合公开 Shape、把 GPU 测量波动当成收益——自动化必须配正确性门禁和 ABBA 复测喵。

### 3. 🧩 COMPASS-ABS：不依赖历史负载的 GPU 集群碎片化度量，SIF 有 2/N 上界

**原文标题:** COMPASS-ABS: Reducing Fragmentation in Shared GPU Clusters for Deep Learning Training Workloads
**来源:** arXiv cs.DC | 2026-09-16
**链接:** https://arxiv.org/abs/2609.18519

🎯 **一句话精髓**: 共享 GPU 集群被碎片化拖垮利用率、DLT 任务被迫长排队，但现有碎片度量在没有负载分布先验时会失效——论文提出 Scheduler-Induced Fragmentation（SIF）指标（基于 partial-nodes、与历史负载无关），并用 COMPASS 算法把集群状态压进 Anchor-Based Space，证明 SIF ≤ 2/N。

🔧 **技术栈**: GPU 集群调度 / SIF 碎片化度量 / partial-nodes / COMPASS-ABS / DLT 训练负载 / 物理集群 + 仿真双验证

📐 **架构/方法亮点**:
- partial-nodes 视角：度量「因碎片而被浪费的部分空闲节点」，不依赖任何历史工作负载分布知识，可以直接内嵌进在线调度器的打分函数
- COMPASS（COMPact-ASSured）算法利用主导负载规模与节点容量之间的拓扑对齐来构造 Anchor-Based Space，把集群状态约束在紧凑区域
- 理论与实践双线：在匹配理论假设与生产负载构成的条件下证明 SIF 被 2/N 上界约束；物理集群 + 模拟集群实验验证利用率提升、任务完成时间缩短

💡 **关键数据**: SIF 上界 2/N（N 为集群节点数）；物理与仿真集群实验显示碎片下降带来资源利用率提升与 DLT 任务完成时间缩短（论文以图表形式给出，无统一单值）

🔗 **樱桃的调度视角**: K8s 默认 bin-packing 对「整机申请」的 GPU 训练负载一直缺好用的碎片指标，gang scheduling 也只能事后补救。SIF 的「无需历史负载」特性让它适合做在线反馈信号，Master 如果自建 GPU 平台，可以照 partial-nodes 的定义给自己集群算一版碎片基线喵。

### 4. 📊 PrefixBench-H100：prefix 复用什么时候值钱？分界线在「缓存压力」

**原文标题:** PrefixBench-H100: Characterizing Prefix Reuse and Time-to-First-Token in H100 LLM Serving
**来源:** arXiv cs.DC | 2026-09-17
**链接:** https://arxiv.org/abs/2609.19657

🎯 **一句话精髓**: vLLM 和 TensorRT-LLM 都支持跨请求复用 KV Cache 前缀，但没人说清它何时显著改善 TTFT、何时被调度/缓存粒度/并发/内存压力吃掉——这个可复现基准在单卡 H100 上系统扫参，画出了 prefix 复用的实际工作包络。

🔧 **技术栈**: vLLM / TensorRT-LLM / KV Cache prefix reuse / TTFT·ITL·E2E 时延 / cache-hit 统计 / H100

📐 **架构/方法亮点**:
- 受控合成 trace + chat/RAG 风格真实负载，双运行时同条件对比；变量覆盖共享前缀长度、后缀多样性、到达模式、并发、输出长度、缓存配置
- 全维度采集：TTFT、token 间延迟、端到端延迟、吞吐、缓存命中率、GPU 显存与剖析 trace
- 两个定性结论很关键：缓存效果本身对并发和输出长度基本不敏感；剩余的跨运行时差异出现在缓存之上的调度层

💡 **关键数据**: 明确划出「前缀复用大幅降低首 token 延迟」与「缓存压力侵蚀收益」两个 regime 的边界，并验证缓存命中率对并发规模与输出长度几乎不敏感（具体数值在论文图表中）；不引入新缓存算法，纯测量框架

🔗 **樱桃的调度视角**: 既然差异出在「缓存之上的调度层」，那把同前缀请求路由到同一实例就不该靠引擎内缓存碰运气，prefix-aware routing 应该升格为调度器/网关的一等公民。做 Agent 网关的话，可以按这个基准补一套 prefix 命中率监控喵。

### 5. 🔁 AccelPact：训练故障恢复做到「零 I/O」，每 update 一次 checkpoint 的代价是 +656% 延迟

**原文标题:** Zero-I/O Fault Recovery for Sharded Deep Learning via Dynamic Framework Dependency Rebinding
**来源:** arXiv cs.DC | 2026-09-16
**链接:** https://arxiv.org/abs/2609.18178

🎯 **一句话精髓**: 瞬时网络故障迫使集群回滚到 checkpoint，而高频 checkpoint 本身就是灾难（实测 +656.7% 延迟开销、3.39TB/h 存储流量）——AccelPact 发现故障时显存其实完好，失效的只是框架缓存的通信 handle，于是用非侵入式引用重绑定 + 带外 Gloo 共识，在显存里直接完成恢复，跳过全部 checkpoint 回放。

🔧 **技术栈**: PyTorch FSDP / Gloo 带外共识 / RTX 5880 ×16 / Mistral-7B 全参训练 / torch.compile / 分片训练容错

📐 **架构/方法亮点**:
- 根因洞察：通信在已提交的 optimizer step 失败时，设备内存静止且未损坏；恢复失败是因为 FSDP 跨模块包装器和参数层级缓存了内部通信 handle——要修的是依赖，不是数据
- 非侵入式 reference rebinding 修复依赖失效，由带外 Gloo 共识协调；应用代码零修改，torch.compile 下不产生 graph break
- 重绑定执行时间在 4~16 GPU 拓扑下为常数（0.493~0.518 ms）

💡 **关键数据**: 每 update 异步 checkpoint 实测：延迟开销最高 +656.7%、占用 32.5 GiB 主机内存、产生 3.39 TB/h 存储流量（1.216B 参数模型）；AccelPact 全程 goodput 比 cold restart 高 1.197×，比 NVRx checkpoint 恢复高 1.194×（checkpoint 龄期 5）至 1.698×（龄期 18）；连续 10 次故障注入 16 个 rank 保持位级一致零数值漂移

🔗 **樱桃的调度视角**: 这篇把「故障域」和「恢复域」解耦得很干净——K8s 重拉 Pod 只解决进程存活，不解决通信组失效。对长训练任务，调度器值得感知框架级恢复能力，把「checkpoint 间隔 vs 瞬断恢复」做成策略开关，冷恢复的排队预算能省一大截喵。

### 6. 💾 Cloudflare 用数学 + Rust 再省 100TB 内存：一致性哈希虚节点砍 90%

**原文标题:** Saving another 100TB of RAM with math (and Rust)
**来源:** Cloudflare Blog | 2026-09-18
**链接:** https://blog.cloudflare.com/saving-100-tb-of-ram-with-math/

🎯 **一句话精髓**: 内部负载均衡服务 Pingora Backend Router 里的一致性哈希库 pingora-ketama 内存超标——两招解决：Rust 结构体去对齐填充直接省 25%，再靠精确推导的标准差公式证明 2048 节点机房在 1万~10万 hash/节点之间碰撞误差才开始爬升，于是把每节点 hash 数砍掉 90%，合计回收 100TB RAM。

🔧 **技术栈**: Rust / pingora-ketama / 一致性哈希 / 变异系数（CV）/ 生日悖论 / 双环灰度迁移

📐 **架构/方法亮点**:
- Point 结构体（hash+index）因 Rust 对齐规则被迫 8 字节起，改成 raw byte array + getter（编译结果等价于 packed 但安全），哈希内存立省 25%
- 作者嫌近似公式不够，直接推导出 k hash/节点时标准差的精确表达式；结合 32-bit 哈希碰撞（生日悖论）随 hash 数快速增长的现象，确定砍 90% 也无感知误差
- 迁移方法论教科书级：新旧双环并行驻留、按请求 hash 稳定选环（可即时回滚）、机房粒度分层放量，同时独立控制「流量比例」和「迁移地域」两个维度，全程盯 origin 流量防缓存雪崩

💡 **关键数据**: 每节点 hash 数默认 160（NGINX 遗产），100 台服务器场景 CV 从约 99% 降到约 8%；hash 数削减 90% 后误差无感；最终 PBR 内存下降 100TB——这是继上个月 DNS 团队省下 100TB 之后的又一笔

🔗 **樱桃的调度视角**: 负载均衡器的哈希环本质是一笔「调度数据结构的内存税」：160×节点数的虚节点在数万台规模就是 PB 级浪费，同样的税 K8s 里的一致性哈希路由、sidecar 路由表也在交。经验可以照抄：先推精确误差公式，再定削减比，最后双版本灰度防缓存失效喵。

## 📓 樱桃的今日学习总结

1. **「理论容量 → 实际交付」的转换效率成为新战场** — Intel 用三因子公式把「机柜交付量」定价，Cloudflare 用精确数学把哈希环内存税砍掉九成，COMPASS-ABS 把碎片损耗证明出 2/N 上界。三件事的共同点：不新增硬件，只压缩调度、排队、搬运、冗余数据结构里的转换损耗。考核指标正在从峰值吞吐换成 p99 交付量、膝点位置和碎片上界。
2. **优化闭环自动化从「调参数」走向「写代码」，门禁是底座** — Atrex Kernel Agent 让 Agent Loop 直接改算子代码，智谱 Infra Agent 在 10 万卡上调集群（昨日报道）。但两边都强调同一件事：可复现 Benchmark、正确性门禁、ABBA 复测缺一不可，否则自动优化就是自动翻车。
3. **「状态」是 Agent 时代的一等公民** — KV Cache（PrefixBench 的包络、华为 PB 级分层）、沙箱快照（Intel 的 IAA 卸载、Docker VMM 内存返还）、训练通信 handle（AccelPact 的零 I/O 恢复）——谁管好这些易失状态，谁就有密度和恢复速度。调度器设计的重心正在从「算力分配」滑向「状态放置」喵。
