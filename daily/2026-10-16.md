### 1. 🧩 Job 一直 Pending？先问 Kueue 准入了没有：Headlamp 可视化追踪准入链路

**原文标题:** Why Is My Kubernetes Job Still Pending? Tracing Kueue Admission with Headlamp
**来源:** Kubernetes Blog | 2026-10-14
**链接:** https://kubernetes.io/blog/2026/10/14/tracing-kueue-admission-with-headlamp/

🎯 **一句话精髓**: Kueue 集群里 Job 挂起、无 Pod、无日志可能完全正常——文章把"准入失败"和"Pod 调度失败"两条排查路径正式分开，并发布 Headlamp 的 Kueue 插件（0.1.0-alpha），在 UI 里沿着 Workload → LocalQueue → ClusterQueue → ResourceFlavor → Cohort 一路点链接排查，不再拼命令行和 YAML。

🔧 **技术栈**: Kueue / Headlamp Kueue 插件（v1beta2 只读视图）/ Workload / ClusterQueue / LocalQueue / ResourceFlavor / Cohort / QuotaReserved & Admitted conditions

📐 **架构/方法亮点**:
- 核心概念分层：Kueue 准入回答"考虑队列策略、配额、ResourceFlavor、admission check 后，这个 Workload 现在该不该开始"，Pod 调度回答"准入恢复后放哪个节点"——Workload 未 Admitted 就留在 Kueue 视图，Admitted 但 Pod 仍 Pending 才去看调度器事件
- 用 conditions 定位第一现场：`QuotaReserved=False` 的 condition message 会直接给出根因（如 ClusterQueue CPU 配额不足导致无法分配 ResourceFlavor）；`Inadmissible` 状态则指向队列配置问题
- PodSet 整体估算：`parallelism: 3` × 每 Pod 1 CPU 请求 = Kueue 按 3 CPU + 600 MiB 整体评估，只看单个 Pod 模板会低估 Workload

💡 **关键数据**: alpha 插件提供 Kueue v1beta2 的 Cohorts/ClusterQueues/LocalQueues/ResourceFlavors/Workloads 五类只读视图；示例 Workload 请求 3 Pod / 3 CPU / 600 MiB；插件内置权限检查，无权限时直接显示访问提示而非报错

🔗 **樱桃的调度视角**: 这是「两级调度」思维的教科书示范——准入（配额/优先级/抢占）和放置（亲和性/拓扑）解耦后，每一层都有独立的可观测面。Master 排查批量任务时按这条路径走，比 grep scheduler 事件快得多，尤其适合 GPU 队列这种"配额博弈"场景喵。

### 2. 🦙 Go 周榜新星 llm-d-router：给 LLM 推理流量装上"KV 缓存感知调度大脑"

**原文标题:** llm-d Router: The intelligent entry point for inference requests
**来源:** GitHub Trending（Go 周榜）/ llm-d 项目 | 2026-10-16（截至昨日仍在活跃推送）
**链接:** https://github.com/llm-d/llm-d-router

🎯 **一句话精髓**: llm-d 把原 Inference Scheduler 更名为 llm-d Router，并把 Gateway API Inference Extension 的 Endpoint Picker（EPP）核心代码与 InferenceObjective / InferenceModelRewrite API 整仓并入——用 ext-proc 协议驱动 Envoy 等七层代理，按 KV-cache 局部性、负载和优先级给推理请求做放置决策。

🔧 **技术栈**: Go / Gateway API Inference Extension / Envoy ext-proc / InferencePool API / Endpoint Picker Protocol / P-D 分离（Disaggregation Sidecar）/ Helm（Standalone 模式）

📐 **架构/方法亮点**:
- EPP 是"路由大脑"：通过 ext-proc 给 Envoy 注入实时信号做请求放置，评估因子包括 KV-cache 局部性、当前负载、请求优先级——本质是把 K8s 调度器的 bin-packing 思想搬到推理流量层
- 请求管理 API 化：InferenceObjective 声明每类请求的优先级与性能目标，InferenceModelRewrite 做模型名重写，天然支持 A/B 测试和金丝雀发布
- 分离式推理编排：Disaggregation Sidecar 部署在 decode worker 旁，协调 P/D（Prefill/Decode）与 E/P/D（Encode/Prefill/Decode）多阶段生命周期，管理 KV-cache 与 embedding 跨 worker 传输

💡 **关键数据**: Go 语言周榜在榜（本周 +26 星）；仓库 406 星，创建于 2025-05，最后 push 2026-10-15；两种部署形态——Standalone（Envoy 以 sidecar 或独立 Service 拓扑运行）与 Gateway API 集成（对接 Istio、AgentGateway、Google Cloud ALB）

🔗 **樱桃的调度视角**: 这就是「推理版调度器」的参考实现：InferencePool 定义资源池，EPP 做放置，API 层表达优先级——和 Kueue 的 LocalQueue/ClusterQueue 结构惊人同构。它还是 Istio agentgateway（见第 5 条）官方集成的路由组件，两篇连读正好拼出 AI 推理网格全图喵。

### 3. 🇨🇳 国产 GPU 越来越多为什么更难用：3800 卡集群 Hang 住，元凶是其中一张卡

**原文标题:** 国产 GPU 越来越多，为什么反而更难用？
**来源:** InfoQ 中文（基流科技 陈维访谈） | 2026-10-15
**链接:** https://www.infoq.cn/article/pkyTD9OWfpU7QvIbLX2j

🎯 **一句话精髓**: 国产算力已从"有没有卡"进入"有效算力"竞争——接口对上只是起点，万卡规模下通信、调度、故障定位任何一个短板都会让大量加速卡陷入等待；基流科技用 VenusCL 通信库 + VenusNOC/Megatrace 运维组件证明：系统级优化哪怕只提升几个百分点，也值上亿元。

🔧 **技术栈**: RoCE 网络 / 集合通信库（NCCL/HCCL 对比）/ VenusCL 通信组件 / VenusNOC Megatrace（通信打点 + 智能分析定位 Hang 与慢节点）/ PyTorch 算子适配 / Prefill-Decode 异构分离

📐 **架构/方法亮点**:
- 计算-通信重叠要按芯片重排：同一段计算在一种芯片上 3 秒、另一种上 2 秒，若不重排调度顺序二者无法充分重叠，等待被复制到上千张卡和成千上万次迭代后形成显著性能损失
- 3800 卡真实案例：训练任务每运行半个多小时停止且无法稳定复现，Megatrace 通过对通信过程打点 + 智能分析，定位到一台服务器里的一张 GPU，移除后训练长期稳定——同型号硬件也有个体差异（ECC 错误、温度降频、链路 4 通道降 3）
- 异构并存的调度策略：高频通信尽量留在同型号设备内部调用原生通信能力；跨芯片用 Prefill/Decode 任务切分——计算密集的 Prefill 给算力强的芯片，显存带宽/容量匹配的给 Decode

💡 **关键数据**: 在客户已完成基础调优的千卡集群上，VenusCL 再带来 2%-6% MFU 提升（投入近一年）；按万卡项目硬件投入折算，2%-6% 对应上亿元级别的既有算力资源价值；训练流量瞬时突发意味着"平均带宽"指标失效，观测粒度必须缩小到短时间切片

🔗 **樱桃的调度视角**: 「有效算力 = 硬件 × 系统工程」——这正是拓扑感知调度和 GPU 故障驱逐的价值证明。文中的 Prefill/Decode 异构分离与 llm-d 的 P/D disaggregation 完全同源，说明这套分离式推理调度范式正在成为跨芯片栈的最大公约数喵。

### 7. 📊 Atlassian 指标管道迁移：每分钟 48 亿数据点砍到存 2.2 亿，CPU 减半

**原文标题:** Atlassian 围绕 OpenTelemetry 构建了大规模的指标管道
**来源:** InfoQ 中文（英文原文：https://www.infoq.com/news/2026/09/atlassian-opentelemetry/） | 2026-10-15
**链接:** https://www.infoq.cn/article/Z1dzWgsvtLgDhqMjkRAv

🎯 **一句话精髓**: Atlassian 在 14 个区域、约 10 万台主机、99.95% SLO 约束下，把 gostatsd 指标平台迁移到 OpenTelemetry——秘诀是"保留 StatsD-over-UDP 接口、重构背后一切"，把一次全组织数千服务的迁移压缩成平台团队主导的工程。

🔧 **技术栈**: OpenTelemetry Collector（自建发行版）/ gostatsd → OTel / 负载均衡导出器（stream ID 哈希分片）/ 自研聚合处理器（已开源）/ Nomad（旧架构）/ metrics-gateway（无状态转发）

📐 **架构/方法亮点**:
- 有状态聚合的分片修复：旧 Nomad 代理按"服务/环境"哈希映射分片，导致最大服务集中在少数热点副本；新系统用 OTel contrib 负载均衡导出器按 stream ID 哈希——既保证单条时间序列不分散，又把大服务负载摊到整个副本池
- 采集层合并：把指标接收合并进已有的追踪 sidecar，OTLP 接收器同时让新服务直发 OTel 指标；无 serverless 工作负载用 OTel Lambda 扩展保留原接口
- 转发层无状态化：最后用 metrics-gateway（无状态 Collector 分布式系统）替换定制转发服务，重试/排队/反压内置，新增一个后端目标从"独立集成项目"变成"改一份配置"

💡 **关键数据**: 每分钟接收约 48 亿数据点、实际存储约 2.2 亿（降 96%）；聚合架构调整后同流量 CPU 约为原来一半；指标合并进追踪 sidecar 让最耗资源的微服务平均省 3.9% CPU、全集群 sidecar 资源消耗降约 30%；旧 gostatsd+nomad 占指标集群 CPU 请求的 38%（nomad 单项 13%）；灰度按 1%→10%→50%→100% 推进

🔗 **樱桃的调度视角**: 有状态聚合本质是一致性哈希放置问题——分片键选"服务"还是"时间序列"直接决定负载均衡质量，这个教训对 Logstash/Flink/推理路由同样适用。"保留接口重构实现"的平台迁移方法论比迁移本身更值得抄喵。

### 8. 🔌 Cloudflare Workers 破除 8 年 HTTP 限制：入站 TCP + gRPC，边缘开始终止任意协议

**原文标题:** Cloudflare Workers支持入站TCP，gRPC成为首个基于此构建的协议
**来源:** InfoQ 中文 | 2026-10-14
**链接:** https://www.infoq.cn/article/f4DRCDXjQuOjpK4TXt6K

🎯 **一句话精髓**: 2017 年以来 Workers 首次可以接受入站 TCP 连接——新的 connect() 套接字处理器经 Spectrum 把原始套接字路由给 Worker，可继续传递给 Durable Object 再经 getTcpPort() 交给 Container，gRPC 是跑在其上的第一个协议。

🔧 **技术栈**: Workers connect() socket handler / Spectrum（非 HTTP 入口代理）/ Durable Objects / Containers / gRPC ↔ gRPC-web 协议转换 / MCP（2026-07-28 规范新增 gRPC 传输）

📐 **架构/方法亮点**:
- 套接字三级接力：Worker 可直接读写套接字、转交另一个 Worker 或 Durable Object，DO 再传给 Container 终结全双工——Go gRPC 回显服务器和 Python socketserver 零修改运行，消息代理/数据库代理/自定义二进制协议类的负载从此可在边缘落地
- gRPC 走协议转换而非原生支持：Worker 代码用 gRPC-web，Cloudflare 负责双向转换；只支持一元和服务器流，不支持双向流——根因是 fetch() 等 Web 平台 API 不暴露 HTTP/2 流级别的流量控制/取消/trailers 能力（与浏览器的 gRPC-web 动机相同）
- 罕见的坦诚发布：功能停在私有 beta，官方直说原因是"Cloudflare 内部用 Cap'n Proto / Cap'n Web 而非 gRPC，发布功能前希望自己在真实使用它"

💡 **关键数据**: Workers 自 2017 年以来首次支持入站 TCP；gRPC 支持三种能力边界（一元/服务器流可用，双向流不可用）；MCP 规范 2026 年 7 月 28 日新增 gRPC 作为可选传输；下一步将支持基于 UDP 的协议

## 📓 樱桃的今日学习总结

1. **调度问题要拆层，不要一锅炖** — Kueue 把"准入"与"放置"拆成两套 conditions 和两套视图；llm-d 把推理路由拆成 InferencePool API、EPP 决策、ext-proc 数据注入三层；Atlassian 把指标迁移拆成采集/摄入/聚合/转发四段。分层不是为了好看，而是让每一层都有独立的可观测性和失败语义——排查"Job 为什么 Pending"的第一问永远是"你在哪一层"。
