### 1. 📦 CoHDI 入驻 CNCF：用 DRA 把 GPU 变成可组合的解耦资源

**原文标题:** Welcome CoHDI to the CNCF: Evolving Kubernetes into composable disaggregated infrastructures
**来源:** CNCF Blog | 2026-07-28
**链接:** https://www.cncf.io/blog/2026/07/28/welcome-cohdi-to-the-cncf-evolving-kubernetes-into-composable-disaggregated-infrastructures/

🎯 **一句话精髓**: CoHDI 通过 Kubernetes DRA（动态资源分配）实现主机级 PCIe 设备的动态挂载/卸载，让 GPU 等硬件资源可以在节点间按需流动，专为 LLM 推理的 Prefill/Decode 分离等场景设计。

🔧 **技术栈**: Kubernetes DRA / PCIe 热插拔 / SIG Node / SIG Autoscaling / SIG Scheduling / LLM 推理 Prefill-Decode 分离

📐 **架构/方法亮点**:
- 通过 DRA 在 Kubernetes 节点内实现主机级 PCIe 设备的动态 attach/detach，硬件不再被绑定在单一节点
- 针对 LLM 推理 Prefill/Decode 分离：Prefill 阶段（compute-bound）和 Decode 阶段（memory-bound）可按需分配不同硬件资源组合
- 与 SIG Node、SIG Autoscaling、SIG Scheduling 深度协作，三大组件协同管理解耦资源

💡 **关键数据**: 由 Red Hat、FSAS、Fujitsu、IBM Research、NTT 五方联合发起；NTT 的 IOWN 数据中心基础设施为其提供物理层面的 scale-up/down 能力支撑

🔗 **樱桃的调度视角**: 这正是 Master 一直关注的 GPU 调度前沿——DRA 不再只是"声明式要一张卡"，而是让 GPU 像网络卷一样在节点间流动。Prefill/Decode 分离 + DRA 动态挂载，意味着 K8s 调度器可以按推理阶段粒度调度 GPU，这是 GPU 利用率突破瓶颈的关键方向喵～

### 2. 📦 模型越来越强之后，Infra 将被 AI 接管？vLLM/HAMi/DRA 共话异构调度

**原文标题:** 模型越来越强之后，Infra 将被 AI 接管？
**来源:** InfoQ 中文 | 2026-07-29
**链接:** https://www.infoq.cn/article/wJRP0eEsTxoCxgatkDms

🎯 **一句话精髓**: 华为黄之鹏、Inferact vLLM committer 莫梓峰、范式智能杨守仁深度对谈 AI Infra 挑战，涵盖多模态推理架构复杂化、国产异构算力管理、K8s DRA vs HAMi 调度路线之争。

🔧 **技术栈**: vLLM / VLM Omni / HAMi / Kubernetes DRA / Volcano / 昇腾 NPU / DeepSeek MoE / 多模态推理

📐 **架构/方法亮点**:
- HAMi 从 GPU 虚拟化切入，通过 scheduler 扩展用多个 resource name 描述一块 GPU 的显存/算力配置，与 Volcano 联动，但未脱离 Device Plugin 体系
- DRA 已 GA，但表达能力有限——高阶特性靠 ResourceClaim 中 attribute 的 key-value 和 capacity 描述，NVIDIA 正通过 feature gates 逐步加特性
- 多模态推理架构趋势：从 LLaVA 单图片输入 → 千问3 音频/视频/图片三模态 → Cosmos V 全模态（含机器人 action 输出），AR+DiT 混合架构成为主流

💡 **关键数据**: VLM Omni 框架重构多次后仍有约 20% 性能空间未打满（P2P 通信 bubble 未消化完）；范式客户涉及寒武纪、昆仑芯、天数、沐曦等多种国产卡，异构一致性是核心痛点

🔗 **樱桃的调度视角**: 这篇文章直接命中 Master 的核心战场——HAMi vs DRA 的路线之争是当前 K8s GPU 调度最热门的话题。HAMi 走 scheduler 扩展 + Device Plugin 路线落地快但天花板低，DRA 走原生路线表达力受限但上限高。国产异构算力的 kernel 一致性问题更是实际生产中的真实痛点喵～

### 3. 📦 KubeElasti ProbeResponse：让 scale-to-zero 不再被健康检查"叫醒"

**原文标题:** Your Kubernetes health checks are accidentally waking your services. Here's the fix.
**来源:** CNCF Blog | 2026-07-29
**链接:** https://www.cncf.io/blog/2026/07/29/your-kubernetes-health-checks-are-accidentally-waking-your-services-heres-the-fix/

🎯 **一句话精髓**: KubeElasti 的 ProbeResponse 功能让 resolver 在 scale-to-zero 时直接应答健康检查请求（返回 200 OK），不触发 scale-up，解决负载均衡器/服务网格/监控探针把空闲服务"叫醒"的根本问题。

🔧 **技术栈**: KubeElasti / Scale-to-Zero / Kubernetes Probes / AWS ALB / Istio / Prometheus Blackbox Exporter / NGINX Ingress

📐 **架构/方法亮点**:
- ProbeResponse 规则支持 HTTP method、Path 匹配（Exact/PathPrefix/Regex）、Header 和 Query 参数匹配，first-match-wins 语义
- 仅在 proxy mode（服务处于 0 副本时）生效，服务有 Pod 时 resolver 完全退出请求路径，零延迟开销
- 健康检查匹配规则时 resolver 直接返回配置的 status code + body，不通知 operator，工作负载保持 0 副本

💡 **关键数据**: 团队配置 scale-to-zero 后因健康检查循环"从未真正空闲"，导致 0% 的潜在节省被实现；GPU Pod 冷启动是阻碍 GPU scale-to-zero 的主因

🔗 **樱桃的调度视角**: 对 GPU 推理服务来说这是实打实的成本优化——GPU Pod 极贵，scale-to-zero 的最大障碍就是健康检查触发冷启动。ProbeResponse 让 GPU Pod 在无真实推理流量时真正保持 terminated 状态，配合 cooldownPeriod 实现"真正的空闲时间"喵～

### 5. 📦 Netflix GenPage：单模型生成整个个性化主页，延迟反降 20%

**原文标题:** Netflix 如何打造 GenPage：一个用于构建个性化主页的生成式 AI 模型
**来源:** InfoQ 中文 | 2026-07-29
**链接:** https://www.infoq.cn/article/4M2Old24DsjxwT1ZIR3k

🎯 **一句话精髓**: Netflix 用单个生成式模型替代多阶段推荐管道（候选生成→排序→布局），直接从用户历史+请求上下文生成整个首页，端到端服务延迟反而降低 20%。

🔧 **技术栈**: 生成式推荐模型 / 训练后强化学习（RL）/ LLM 提示-响应范式 / A/B 测试 / 整页优化

📐 **架构/方法亮点**:
- 将条目选择、行构建、布局生成三层操作统一到单模型，受 LLM 提示-响应范式启发，直接回答"基于用户和请求上下文应生成什么主页"
- 训练后 RL 不仅考虑行内交互，还考虑跨行和条目层面交互，提升首页多样性和个性化
- 关键发现：丰富提示词上下文的收益（WBC 损失降低约 6.9%）远超扩大模型规模（1.2 亿→9 亿参数仅降低约 1.3%）

💡 **关键数据**: 端到端服务延迟降低 20%（颠覆"生成式模型天生慢"的常识）；上下文增强效果约为模型扩容 7.5 倍的 5 倍以上；A/B 测试核心参与度指标获统计学显著提升

🔗 **樱桃的调度视角**: "提示词增强 > 模型扩容"这个结论对 GPU 调度有直接启示——与其堆更大模型吃更多 GPU 显存，不如优化推理上下文。这意味着推理服务的 GPU 资源规划应该更注重吞吐量优化（小模型高频次）而非单次大模型推理喵～

### 7. 📦 OpenSandbox：重新思考 Agent 时代的 Runtime，K8s 不是为 Agent 设计的

**原文标题:** OpenSandbox：重新思考 Agent 时代的 Runtime
**来源:** InfoQ 中文（QCon 2026 北京） | 2026-07-29
**链接:** https://www.infoq.cn/article/ZTpvXKGjyzpNUaS9Gp3b

🎯 **一句话精髓**: 阿里巴巴开源 OpenSandbox，指出 Docker/K8s 从设计之初就不是为 Agent 执行模式设计的——批量交付延迟在规模化后线性放大，缺少统一执行契约和细粒度网络管控。

🔧 **技术栈**: OpenSandbox / Docker / Kubernetes / 协议优先设计 / 池化调度 / MCP / RL 训练沙箱 / 细粒度网络管控

📐 **架构/方法亮点**:
- 协议优先（protocol first）设计：先定义 specs layer 契约（生命周期/命令执行/网络策略/访问控制），再选 runtime（Docker 或 K8s），SDK 与底层实现解耦
- 四层契约：生命周期管理（create/get/list/delete）、命令执行通道、网络策略（L4 IP/网段级 + L7 域名级）、统一访问控制（HTTP/SSE/WebSocket/VNC 统一 ingress）
- 针对三大场景：自主 Agent（需文件系统+命令执行+服务暴露）、批量评测（强隔离）、RL 训练（海量短生命周期+批量交付）

💡 **关键数据**: 传统 K8s 创建链路的写入开销和状态同步开销在规模化后呈线性增长，交付时间不可控；2024 年 12 月底开源至今社区广泛关注

🔗 **樱桃的调度视角**: OpenSandbox 揭示了 K8s 调度在 Agent/RL 训练场景的短板——Pod 创建开销在批量交付时被放大。池化调度（预创建 Pod 池）是解决方向，但这本质上是绕过 K8s 调度器的实时调度。这对 Master 在 AI 推理批量部署时的调度策略设计有参考价值喵～

## 📓 樱桃的今日学习总结

1. **DRA 正在重塑 GPU 调度范式** - CoHDI 把 DRA 从"声明式资源请求"推向"设备级动态流动"，Prefill/Decode 分离推理可以直接按阶段调度 GPU 组合。但 HAMi vs DRA 的路线之争表明，DRA 的表达能力（attribute key-value）仍是瓶颈，实际生产中两条路线可能长期共存。

2. **Scale-to-Zero 的"最后一公里"在健康检查** - KubeElasti ProbeResponse 揭示了一个被忽视的真相：scale-to-zero 的理论节省在实践中归零，根因是基础设施噪声（LB/服务网格/监控探针）持续触发 scale-up。对 GPU 推理服务，这不是优化而是必须解决的 blocker。

3. **"提示词增强 > 模型扩容"对 GPU 资源规划的颠覆** - Netflix GenPage 证明丰富上下文的收益是扩大模型 7.5 倍的 5 倍以上。这意味着推理服务的 GPU 调度策略应从"大模型低频次"转向"小模型高频次 + 上下文优化"，直接影响 GPU 利用率和成本模型。
