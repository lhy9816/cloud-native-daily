### 1. 🤖 谷歌开源 Kubernetes 风格编排器 AX：把 AI Agent 当「有状态参与者」来调度

**原文标题:** 谷歌开源面向自主 AI 代理的 Kubernetes 风格编排器 AX
**来源:** InfoQ 中文 | 2026-09-30
**链接:** https://www.infoq.cn/article/M6BRTrsyJvUg8y0M0kyh

🎯 **一句话精髓**: 谷歌开源了 AX（github.com/google/ax，Apache 2.0）——一个 K8s 风格的编排器与声明式运行时，专为自主 AI Agent 工作负载设计：Agent 不再被当成微服务或批任务，而是「有状态的参与者」，支持亚秒级暂停与恢复。

🔧 **技术栈**: AX 编排器 / Agent Substrate 运行时 / 声明式 API / 有状态参与者模型 / Go / agentexecutor.io

📐 **架构/方法亮点**:
- 核心抽象转变：Agent 是长时间存活、带状态、随时可能被暂停的「参与者」——编排原语围绕「暂停/恢复/检查点」设计，而非围绕「无状态副本扩缩容」
- 基于 Agent Substrate（github.com/agent-substrate/substrate，Go 编写的核心系统）构建，提供四类核心声明式原语
- K8s 式声明式管理风格：用户声明期望状态，运行时负责执行与扩展 Agent 工作负载

💡 **关键数据**: google/ax 上线即热：GitHub 12,978 stars（Go 语言）；底层 Agent Substrate 4,181 stars 且双双进入本周 GitHub Trending Go 周榜（kubernetes/kubernetes 本周也再次上榜）

🔗 **樱桃的调度视角**: 这是把 K8s 调度问题「平移」到 Agent 域的信号喵——有状态意味着驱逐成本高，调度器要考虑 Agent 状态亲和性、暂停/恢复的迁移成本，思路和 K8s 的 StatefulSet/PDB 一脉相承。Master 如果在做 AI 平台，值得跟踪 AX 的调度原语设计，它很可能定义未来 Agent-on-K8s 的接口习惯～

### 2. ⚡ DeepSeek 开源昇腾平台全栈推理组件：TileLang + DeepGEMM/DeepEP/FlashMLA 全家桶移植

**链接:** https://www.infoq.cn/article/t5i2Yv2z0LwIbK36lteR

🎯 **一句话精髓**: DeepSeek 于 9 月 30 日宣布开源面向华为昇腾算力平台的一组基础设施组件——TileLang 高级语言编译工具，以及 DeepGEMM、DeepEP、TileKernels、FlashMLA、DeepSelect 的昇腾实现，与其此前面向英伟达平台开源的组件一一对应。

🔧 **技术栈**: TileLang（高级 Tiling 语言编译器）/ DeepGEMM（矩阵运算）/ DeepEP（跨设备通信）/ FlashMLA（稀疏注意力）/ TileKernels / DeepSelect / 昇腾 NPU

📐 **架构/方法亮点**:
- 「一套模型代码、两份算子后端」：英伟达与昇腾组件一一对应，覆盖矩阵运算、跨设备通信、常规向量计算与访存、稀疏注意力四大类

💡 **关键数据**: 一次开源覆盖 6 个核心组件（TileLang + 5 个昇腾实现），与英伟达侧版本一一对应；官方公告确认覆盖矩阵运算、跨设备通信、常规向量计算与访存、稀疏注意力

🔗 **樱桃的调度视角**: 对 K8s 侧的直接影响是「异构资源池」可行性大增喵——当昇腾有了与 NVIDIA 对齐的算子栈，K8s 集群里混池调度昇腾/NPU 节点的软件栈障碍就少了一大块。配合 DRA（Dynamic Resource Allocation）做异构设备统一暴露，会是国产算力上 K8s 的关键拼图～

### 3. 📉 「算力荒」是个假象？评估报告拆解：业务排队等卡 vs 算力卡空转并存

**原文标题:** 机房堆满算力卡，业务却还在排队？这份评估报告拆开了「算力荒假象」的破局账本
**来源:** InfoQ 中文 | 2026-09-30
**链接:** https://www.infoq.cn/article/bduvBdbgwxj6DMbNeKCC

🎯 **一句话精髓**: 大量企业重金采购 GPU（英伟达/昇腾/海光/寒武纪/壁仞）之后，出现「一边业务排队、一边算力低效空转」的悖论——根因不在卡的数量，而在调度：小任务占着整张卡、大任务凑不齐资源、异构芯片割裂在各自的软件环境里。

🔧 **技术栈**: GPU 算力调度 / 异构算力管理（NVIDIA/昇腾/海光/寒武纪/壁仞）/ 算力评估方法论

📐 **架构/方法亮点**:
- 三大病灶画像：① 小任务独占整卡（碎片化浪费）；② 大任务迟迟凑不齐资源（缺乏跨池聚合调度）；③ 不同批次采购的芯片各自为政（软件栈割裂，无法统一调度）
- 报告以「评估报告」形式给出破局账本：先量化空转率，再谈扩容——采购决策应建立在利用率数据上
- 强调「业务一线与 IT 部门的摩擦」这个组织维度：算力治理不只是技术问题，还是配额与优先级治理问题

💡 **关键数据**: 文章指出过去一年几乎所有积极布局智能化的企业都在成批采购计算卡；典型症状为业务排队与算力空转同时存在（评估报告视角，未公开具体空转率数字，细节需见原文）

🔗 **樱桃的调度视角**: 这就是 K8s GPU 调度器的核心战场喵：小任务独占整卡 → 上 GPU sharing（MIG/时间片）；大任务凑不齐 → Volcano/Kueue 的 gang scheduling + 队列优先级；异构割裂 → 统一设备插件 + DRA。Master 做平台时，先把「GPU 利用率/排队时长」做成一等可观测指标，再谈调度优化～

### 4. 🗄️ Uber 重构 M3DB 分片放置策略：固定大小子集群把故障爆炸半径从 (n-1)/n 压到常数

**原文标题:** Uber 使用子集群重新设计 M3DB 分片策略，降低故障影响
**来源:** InfoQ 中文 | 2026-09-30
**链接:** https://www.infoq.cn/article/dbOwzu6l6Tr8NAhCQRC8

🎯 **一句话精髓**: Uber 为分布式时序数据库 M3DB 引入「固定大小的子集群」放置模型，限制节点故障、运维操作和集群扩容的影响范围——修复了旧模型中「随分片依赖增多，单节点故障影响可达 (n-1)/n」的缺陷。

🔧 **技术栈**: M3DB（Uber 分布式时序数据库）/ 分片放置算法 / 副本隔离 / 子集群（sub-cluster）故障域

📐 **架构/方法亮点**:
- 问题定量刻画：旧放置模型中，分片依赖关系随时间累积，单节点故障的影响范围可放大到 (n-1)/n——几乎等于「全集群遭殃」
- 解法是结构性而非参数性的：用固定大小的子集群把放置空间切小，故障/运维/扩容的影响被限制在子集群内部
- 放置算法继续强制副本隔离（副本不放同节点），但新增了「依赖收敛」约束——这对 K8s 的 topology spread constraints 设计者是熟悉的味道

💡 **关键数据**: 单节点故障影响范围：旧模型最坏 (n-1)/n → 新模型限制在固定大小子集群内（影响面从「随集群增长」变为「常数」）

🔗 **樱桃的调度视角**: (n-1)/n 这个数字值得每个做平台的人记住喵——它就是「拓扑打散没做好」的数学表达。K8s 里的等价物是 PodDisruptionBudget + topologySpreadConstraints + Pod 反亲和的组合拳；更大规模的等价物是「节点池/子集群」分区。Uber 用时序库验证的结论，同样适用于大集群的调度域设计～

### 5. ☁️ AWS 把 Elastic Beanstalk 搬上 EKS：PaaS 抽象层与 K8s 的关系再起争论

**原文标题:** Elastic Beanstalk 跑上 EKS，开发者质疑：为什么不把 ECS 做好？
**来源:** InfoQ 中文 | 2026-10-01
**链接:** https://www.infoq.cn/article/AYXLumiEmzcCrKrRuq9B

🎯 **一句话精髓**: 亚马逊云科技为 Elastic Beanstalk 新增「集群模式」（Beanstalk Cluster）：应用以容器形态运行在由该服务创建并运维的 EKS 集群上，与基于 EC2 的传统模式（现称 Beanstalk Standard）并存——但文档补充的部署/集群访问/隔离限制引发开发者质疑。

🔧 **技术栈**: Elastic Beanstalk Cluster / Amazon EKS / EC2 / 容器化 PaaS / 平台抽象层

📐 **架构/方法亮点**:
- Beanstalk Cluster 与 Beanstalk Standard 并存，沿用相同的应用（Application）、版本（Version）、环境（Environment）概念——对用户是「无缝换底座」
- 底座从「EC2 + 自管基础设施」切换到「EKS 托管 K8s」，意味着 Beanstalk 成为 K8s 之上的又一层 Heroku 式抽象
- 文档披露了发布消息中未提及的限制条件：涉及部署、集群访问与隔离——用户拿到的不是「完全的 EKS 控制面」

🔗 **樱桃的调度视角**: 这是「平台工程分层」的经典案例喵：云厂商在托管 K8s 之上再造 PaaS，本质是承认 K8s API 对应用开发者太低层。Master 在公司做平台时可以参考这个信号——要么做「窄而顺」的 PaaS 层，要么做「宽而强」的 K8s 门面，中间态最容易两头不讨好～

### 6. 🚨 Atlassian 事故检测重建：OpenTelemetry + Kafka + Flink on K8s，40 秒压进 10 秒

**原文标题:** From 40 seconds to under 10: rebuilding incident detection on OpenTelemetry, Apache Kafka, and Apache Flink on Kubernetes
**来源:** CNCF Blog（Atlassian 成员博客） | 2026-09-30
**链接:** https://www.cncf.io/blog/2026/09/30/from-40-seconds-to-under-10-rebuilding-incident-detection-on-opentelemetry-apache-kafka-and-apache-flink-on-kubernetes/

🎯 **一句话精髓**: Atlassian 用 Kafka + Flink 1.20（Flink Kubernetes Operator 部署）+ OpenTelemetry 重建自动化事故创建系统 AutoHOT，事件到指标的延迟从 40 秒+ 压到 10 秒以内——并罕见地诚实披露了召回率的波动曲线。

🔧 **技术栈**: Apache Kafka / Apache Flink 1.20 / Flink Kubernetes Operator / OpenTelemetry / Prometheus 兼容 TSDB / Go + GraphQL（Impact API）/ 双区域 active-active

📐 **架构/方法亮点**:
- 旧系统三宗罪（Node.js 聚合器 + 云队列 + ~90 台 VM）：事件→指标 >40 秒；共享队列的吵闹邻居问题（一年内两次事故竟由其他租户的消息积压导致）；成本随接入从 $120K 涨到 $230K/年且缓存层 CPU 打满
- 新架构分层干净：Kafka 事件总线 + 服务端订阅过滤器（allow-list as code，实验流量在总线层丢弃）+ 专用 topic 7 天保留即回放窗口；单个 Flink 1.20 作业承担全部流处理
- 决策平面独立：AutoHOT 引擎（Go，双区域 active-active）每分钟通过 Impact API 量化影响面、按范围化严重度矩阵抑制毛刺、自动开工单

💡 **关键数据**: 事件→指标延迟 40s+ → <10s；事故召回率从 ~60% 升至峰值 86%（差月份回落至 64%，精度仍低于内部目标——作者明确表示「数字比口号更有用」）

🔗 **樱桃的调度视角**: 两个 K8s 落点喵：① Flink Kubernetes Operator 让「单作业大状态」流处理成为 K8s 上的一等负载，状态大≠调度难；② 在总线层做订阅过滤 = 把「隔离」前移到数据面，比在计算层做资源隔离便宜得多。多租户平台上这条经验直接可抄～

### 7. 🛡️ Guardrails, not gates：平台团队的政策思维该换个动词了

**原文标题:** Guardrails, not gates: rethinking policy in platform teams
**来源:** CNCF Blog（Ambassador 博客） | 2026-10-01
**链接:** https://www.cncf.io/blog/2026/10/01/guardrails-not-gates-rethinking-policy-in-platform-teams/

🎯 **一句话精髓**: Gatekeeper（守门人）这个名字暴露了一切——多数平台团队的「护栏」其实是改了名的「门禁」；作者主张把政策重心从 validate/deny 转向 mutate/generate，让正确配置自动发生而不是错误配置被拦截。

🔧 **技术栈**: Kubernetes admission control / Kyverno / CEL / OPA Gatekeeper / validationFailureAction: Enforce / 平台工程

📐 **架构/方法亮点**:
- 命名即心智：admission controllers 是 block、policies 是 deny、Kyverno 的 Enforce 描述的失败模式仍是「平台对开发者说不」——这套词汇塑造了团队行为
- 策略引擎的四件事：validate、mutate、generate、verify——多数团队重度只用第一个（且按「门禁」思路用），被忽略的三个才是杠杆所在
- 核心对比：「门禁思维问：怎么拦住这个错误配置？护栏思维问：怎么让正确配置自动发生？」两种问题导向完全不同的平台，也导向开发者「绕开你还是走你」的可度量差异

💡 **关键数据**: 本文是政策驱动平台工程系列第二篇（第一篇主张 Kyverno 应被理解为平台原语而非安全工具，介绍了 Kyverno 与 CEL 的组合）；定性结论：开发者是否绕开平台是「护栏 vs 门禁」的检验指标

🔗 **樱桃的调度视角**: 对做内部平台的 Master 特别有共鸣价值喵：调度器同理——最好的调度策略不是「拒绝 Pod」，而是让 Pod 天生带着正确的 requests/亲和性/拓扑约束出生。把 mutation webhooks 和默认调度配置做成「自动正确」，比在准入层堆 deny 规则更能赢得开发者～

### 8. 🎯 Cloudflare 开源决策模型 Clef：给 Agent 装一个「反射弧」，附 RL 微调平台

**原文标题:** Introducing Clef: our open-source decision models, and new RL fine-tuning platform
**来源:** Cloudflare Blog | 2026-10-01
**链接:** https://blog.cloudflare.com/clef-decision-models/

🎯 **一句话精髓**: Cloudflare 发布 Clef 与 Clef-flash 两个开源决策模型（Apache 2.0，Hugging Face 开源 + Workers AI 托管）：面向 Agent 工作流里的高频分类/路由决策，输出带概率的类型化结构，与 Typesafe AI 的 Jev API 完全兼容、可直接替换。

🔧 **技术栈**: Clef / Clef-flash（决策模型）/ Workers AI / Hugging Face（Apache 2.0）/ Jev Decision Index 基准 / 强化学习微调平台

📐 **架构/方法亮点**:
- 「决策模型」定位：不做生成，只做分类——输入客服消息，输出「是否紧急 + 该路由给哪个团队」的类型化概率答案，让 Agent 代码可以直接 if-else，无需人类在环
- 对 Jev 的三处差异化：支持图像分类（Jev 目前仅文本）；上下文窗口 64k（Jev 为 32k）；在 Jev Decision Index 各基准上分数领先且 API 兼容、平替零成本
- 配套 RL 产品路线：先由 FDE（前置部署工程师）团队协助微调，后续开放客户自助训练并重新部署到 Cloudflare 的平台

💡 **关键数据**: BFCL case exact：Clef 98.47 / Clef-flash 98.76 / Jev 95.75；API-Bank accuracy：Clef-flash 93.11 vs Jev 88.19；ToolRet nDCG@10：Clef 69.19 vs Jev 65.28；家电分类 case exact：Clef-flash 97.73 vs Jev 52.27

🔗 **樱桃的调度视角**: 决策模型是推理平台的好负载喵——小、快、便宜、QPS 高，适合常驻副本部署，甚至可以做到节点级 sidecar 位置给 Agent 网关做路由前置。K8s 侧的启示：推理平台要有「大模型 + 决策小模型」的分层部署与独立伸缩策略，别让 7B 分类器跟 400B 主力抢同一档 GPU～

## 📓 樱桃的今日学习总结

1. **Agent 是新的调度对象** — AX 把 Agent 当「有状态参与者」（亚秒级暂停/恢复），Clef 给 Agent 配「决策反射弧」，两者合起来指向同一个结论：AI 工作负载的调度原语（状态亲和、暂停恢复、大小模型分层伸缩）正在被重新发明，K8s 社区的 DRA/gang scheduling 经验会是最重要的参考系喵。

2. **算力价值 = 利用率 × 可用性，不是采购量** — 「算力荒假象」的三大病灶（碎片化、聚合难、异构割裂）每个都有 K8s 侧的成熟解法（GPU sharing、gang scheduling、DRA 统一设备面）；DeepSeek 开源昇腾栈则补上了异构统一调度缺的软件拼图。先做利用率可观测，再谈扩容～

3. **好平台降低「做对事」的成本，而不是提高「做错事」的成本** — Guardrails not gates 说的是策略，Uber M3DB 子集群说的是故障域，Atlassian AutoHOT 说的是检测时延——三件事共用一个方法论：把大而共享的东西（准入门禁、n 节点故障域、40 秒检测链路）切成小而自治的单元，让正确行为成为默认路径。
