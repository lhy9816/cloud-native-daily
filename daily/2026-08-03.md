### 1. 📦 Uber「零增长技术栈」：用动态控制循环回收 7 万 CPU 核，AI 开销从无限走向限额

**原文标题:** 92% 工程师都在用 AI 后，Uber 开始给 AI "限额"了
**来源:** InfoQ 中文 | 2026-08-01
**链接:** https://www.infoq.cn/article/Iu2dhFs8JiFqoUGuXJ4m

🎯 **一句话精髓**: Uber 将容量增长与业务增长解耦，用动态运行时优化 + AI 成本治理实现「零硬件增长」下持续扩容，是从资源管理到 FinOps 的完整工程范式。

🔧 **技术栈**: Go runtime / GOGC / cgroups / Michelangelo AI（模型网关）/ MCP Gateway / 多层 Agent 架构

📐 **架构/方法亮点**:
- **GOGCTunner**：自动调整 GOGC 值，直接集成 cgroup 内存限制并监控实时对象，将堆大小控制在实时对象的 1.25 倍、内存使用率卡在 70% 阈值以下避免 OOM——用控制循环替代静态 GC 配置
- **AI 生命周期分层治理**：平台层（Michelangelo AI 网关）→ 上下文层（MCP Gateway 注入内部源码）→ 专用层（Minion/Shepherd 后台 Agent）→ 审查层（uReview/Code Inbox）
- **成本治理转向**：从无限制采用 → 每人 $1,500 月度上限，并提出「净代码质量比」和「每功能计算效率」两个新指标衡量 AI 产出的真实 ROI

💡 **关键数据**: GOGCTunner 在 30 个关键任务服务中回收了 **70,000 个 CPU 核心**；92% 工程师每月使用 AI Agent，31% 新代码由 AI 编写，Autocover 月生成 5,000+ 单元测试；AI 成本自 2024 年增长 **6 倍**，单开发者月成本从飙升至 $2,000 后被限额至 $1,500

🔗 **樱桃的调度视角**: 这对 Master 太有参考价值了——GOGCTunner 本质上就是一个「运行时层面的调度器」，用 cgroup 感知动态调节 GC 频率，和 K8s HPA 用自定义指标驱动扩缩容是同一种思维：**不要静态配置，要闭环反馈**。AI 成本治理的「净代码质量比」也值得在 GPU 调度场景借鉴。

### 2. 📦 KEDA + SQS 队列深度驱动 K8s 扩缩容：让积压量而非 CPU 成为扩容信号

**原文标题:** Scaling Kubernetes pods with KEDA based on Amazon SQS queue depth
**来源:** CNCF Blog | 2026-07-31
**链接:** https://www.cncf.io/blog/2026/07/31/scaling-kubernetes-pods-with-keda-based-on-amazon-sqs-queue-depth/

🎯 **一句话精髓**: 事件驱动架构中 CPU/内存利用率无法反映真实系统压力，KEDA 用 SQS 队列深度作为 HPA 扩缩容指标，让副本数精确对齐未处理工作量。

🔧 **技术栈**: KEDA / Amazon SQS / EKS / HPA / AWS Pod Identity / Helm

📐 **架构/方法亮点**:
- **请求流闭环**：生产者发消息 → KEDA 轮询队列属性 → 更新 HPA 目标指标 → HPA 扩缩 Deployment → K8s 调度新 Pod 消费 → 队列排空后副本缩回
- **关键调参**：`queueLength`（每个副本处理的队列消息数，决定目标副本数）、`activationQueueLength`（从零扩容的触发阈值）、cooldown 和 HPA behavior 策略，分别控制扩容速度和缩容保守度
- **认证方案**：支持 IRSA 和 EKS Pod Identity 两种 AWS 身份注入，ScaledObject + TriggerAuthentication CRD 声明式配置

💡 **关键数据**: 文章强调「backlog is the true scaling signal」——队列积压量才是真实扩容信号；架构将扩缩容决策直接绑定到未完成工作量，实现更快突发处理和队列空时更低闲置成本

🔗 **樱桃的调度视角**: 这正是 Master 关注的调度信号选择问题——**用什么指标驱动扩缩容**。对 AI 推理场景同理：GPU 利用率低不代表没有请求积压，用推理队列长度 / token 吞吐量做 KEDA trigger 比 CPU 指标靠谱得多。scale-to-zero + activationQueueLength 的组合也值得参考。

### 3. 📦 NRI 运行时层供应链校验：把镜像签名验证下沉到 admission webhook 之下

**原文标题:** Runtime Supply Chain Verification using the Node Resource Interface (NRI)
**来源:** CNCF Blog | 2026-07-30
**链接:** https://www.cncf.io/blog/2026/07/30/runtime-supply-chain-verification-using-the-node-resource-interface-nri/

🎯 **一句话精髓**: Admission webhook 存在静态 Pod、kubelet 直连等绕过路径，NRI 插件把供应链校验下沉到容器运行时层，实现无论怎样调度都必须经过的强制校验。

🔧 **技术栈**: NRI / CRI-O / containerd / Kyverno / OPA Gatekeeper / Sigstore

📐 **架构/方法亮点**:
- **Admission Webhook 的盲区**：静态 Pod 由 kubelet 直接管理（镜像 Pod 即使 admission 失败容器仍运行）、命名空间选择器配置错误会静默跳过验证、fail-closed webhook 在节点恢复时可能死锁导致集群锁死
- **NRI 插件方案**：长驻守护进程（非一次性 hook）订阅 `CreateContainer` 生命周期事件，在 CRI-O 1.28+ 和 containerd 1.7+（2.0 起默认启用）上运行，独立发布周期
- **纵深防御定位**：Admission webhook 是必要的第一层但非充分层，NRI 在「无法被跳过的点」强制策略执行

💡 **关键数据**: 已披露利用 mutating webhook 操纵来迷惑 validating webhook 的技术（验证可被静默绕过）；OPA Gatekeeper 文档记录了 fail-closed webhook 阻止集群范围节点删除后恢复的死锁场景

🔗 **樱桃的调度视角**: 这个对 GPU 集群安全很关键——AI 推理镜像通常体积巨大且含专有模型权重，一旦被篡改后果严重。NRI 保证了即使有人通过 static pod 或 kubelet API 绕过调度器直接起容器，镜像签名校验仍然生效，是 GPU 节点的安全兜底层。

## 📓 樱桃的今日学习总结

1. **「闭环反馈」正在取代「静态配置」成为资源管理主流** - Uber 的 GOGCTunner（动态调 GC）和 KEDA（队列深度驱动扩缩容）都是同一范式：用实时指标 + 控制循环替代静态阈值配置。K8s 调度器、GPU 调度、运行时优化都在往这个方向走——**配置是死的，反馈是活的**。

2. **安全防御正在从 API 层下沉到运行时层** - NRI 把供应链校验放到容器运行时，补上了 admission webhook 的静态 Pod/kubelet 绕过盲区。趋势很明确：纵深防御不能只靠 API server 一层，运行时层是「无论怎么调度都必须经过」的强制点。GPU 节点的镜像完整性校验尤其需要这个兜底。

3. **AI Infra 的投资逻辑要从「为模型建」转向「为调度建」** - WAIC 圆桌点出的矛盾很现实：模型迭代太快，绑定特定模型能力的基建会被覆盖。但调度、弹性、成本治理、资源配额这些底层能力是模型无关的——**把钱投在抽象层够低、够通用的位置，才能穿越模型代际更替**。Kubeflow 用 CRD 驱动 Notebooks 也是这个思路：让平台能力声明式可调度，而非绑定特定 ML 流程。
