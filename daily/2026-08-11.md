### 1. 📦 华为提出 G3.5 上下文记忆存储：推理规模上升后存储进入实时数据路径

**原文标题:** AI推理规模上升后，华为开始重新定义"存储"的位置
**来源:** InfoQ 中文 | 2026-08-10
**链接:** https://www.infoq.cn/article/qBHKWa0AabfP0Fs8rGrk

🎯 **一句话精髓**: 华为提出 AI 数据中心五层基础设施架构（数据湖→数据平台→算力→模型→Agent），并在 G3（本地 SSD）与 G4（共享存储）之间新增 G3.5 上下文记忆存储（CMS）--当推理集群进入千卡/万卡规模、需要构建 PB 级共享 KV Cache 池时，这种外置高速共享缓冲层比继续堆 HBM/DRAM 更有成本和容量优势。

🔧 **技术栈**: G1(HBM) / G2(DRAM) / G3(本地 SSD) / G3.5(CMS 上下文记忆存储) / G4(共享存储) / OceanStor Pacific / Omni-Dataverse / OceanStor A800 / OceanStor Dorado / ModelEngine / Nexent / KV Cache / Agent Memory

📐 **架构/方法亮点**:
- **五层 AI DC 架构**：底层 AI 数据湖（OceanStor Pacific + Omni-Dataverse 统一纳管多源异构数据，支撑清洗/标注/检索的 AI 就绪处理）→ AI 数据平台层（UCM 推理记忆数据管理 + CMS 上下文存储）→ 算力层 → 模型层 → Agent 平台，数据安全与韧性贯穿全栈
- **G3.5 的定位逻辑**：不是简单用 SSD 代替显存，而是在 G3 与 G4 之间增加高速、容量更大、可共享的中间缓冲层--把不需要始终驻留显存的数据（KV Cache、Agent 上下文）保存下来减少重复计算；当 HBM 和内存在价格/容量上不能满足 Token 数量和序列长度要求时才产生优势
- **渐进式改造而非重建**：已部署 OceanStor Dorado 的客户可通过增加数据引擎节点在保留原有存储投资的基础上增加 AI 能力；ModelEngine 覆盖模型部署和 GPU/NPU 资源调度，Nexent 进入 Agent 开发运行环境

💡 **关键数据**: G3.5 在推理集群进入**超节点及千卡/万卡规模**、需要构建 **PB 级共享 KV Cache 池**时收益最明显；华为判断这一轮存储周期可能持续至 **2028 年上半年**；五层架构中数据安全与韧性贯穿始终。

🔗 **樱桃的调度视角**: 这条直接关联 Master 的 AI 推理调度--G3.5 共享上下文存储意味着 KV Cache 可以从单机 GPU 显存外溢到集群级共享池，推理调度的资源模型需要再扩展一层：不仅要调度 GPU 算力和本地显存，还要调度共享 CMS 的 KV Cache 容量和带宽。关键洞见是：**当 KV Cache 可共享外置时，推理 Pod 的调度不再受限于「同一 GPU 上的历史上下文」**--Prefill 和 Decode 可以分离到不同节点，Session 路由可以更灵活。这和昨天日报里的 Mooncake 分离式推理、NVIDIA CMX 是同一趋势：存储从被动持久化设备进入推理的实时数据路径，调度器必须感知这个新层级。

### 2. 📦 DeepSeek 涨价 30 倍仍最便宜：KV Cache 命中率是推理成本经济的隐藏变量

**原文标题:** 涨价30倍仍是最便宜的模型，DeepSeek可能有这个底气
**来源:** InfoQ 中文 | 2026-08-10
**链接:** https://www.infoq.cn/article/FEcOI8kYoGuFYq39acEo

🎯 **一句话精髓**: DeepSeek 拟涨价 30 倍仍可能是最便宜的模型，核心护城河不是模型本身而是 KV Cache 命中率--官方 100% 缓存命中率（12 小时不失效）+ V4 的 Token-wise Compression + DeepSeek Sparse Attention 把百万 Token 的 KV Cache 压缩 8.7 倍，使缓存读取价格低至 $0.0028/M tokens，而第三方平台（DeepInfra 等）虽然标价更低但缓存命中率差导致实际支出反而更高。

🔧 **技术栈**: KV Cache / DeepSeek Sparse Attention (DSA) / Token-wise Compression / Common Prefix Detection / FP4 Indexer Cache / FP8 Attention Cache / vLLM / Cache Hit pricing / OpenRouter / OpenCode Go

📐 **架构/方法亮点**:
- **三种缓存前缀落盘机制**：①每次请求的输入/输出结束位置自动生成缓存前缀；②公共前缀检测（Common Prefix Detection）--系统发现多次请求存在共同前缀时主动把公共部分单独落盘，直接提高实际命中概率；③针对超长输入/输出按固定 Token 间隔主动生成缓存前缀单元，不必等超长请求结束才能形成可复用缓存
- **V4 架构的 KV 压缩**：不仅共享 Key/Value，还跨 Token 进一步压缩 KV Cache--一种模式约压缩 4 倍，另一种可达约 128 倍；百万 Token 上下文下 BF16 KV Cache 约为 9.62 GiB（V3.2 约 83.9 GiB，缩小约 8.7 倍），实际部署用 FP4 保存 Indexer Cache、FP8 保存 Attention Cache 再压低约一半
- **缓存命中率决定真实成本**：第三方平台标价更低但实际支出更高--OpenCode Go 在长会话中消费金额平均约为官方 API 的 4 倍（部分超 10 倍），因为会话越长缓存未命中越多；「每百万 Token 多少钱」正在变得不准确，缓存命中率才是真实成本变量

💡 **关键数据**: DeepSeek 缓存命中率在两万次实验中始终保持 **100%**（间隔 12 小时仍不失效）；缓存价格 **$0.0028/M tokens**（列表最低）；V4 KV Cache 约 **9.62 GiB** vs V3.2 约 **83.9 GiB**（缩小 **8.7 倍**）；DeepInfra 标价约为官方的 **64%**（FP4）；GLM 2 分钟后命中率降至约 80%，5 分钟仅剩 25%。

🔗 **樱桃的调度视角**: 这条对 Master 的 K8s 推理平台有直接的经济学指导--**KV Cache 命中率是推理成本的第一变量，比模型定价更重要**。DeepSeek 的三种缓存前缀落盘机制（per-request、common prefix detection、interval-based）是分布式推理 KV Cache 管理的蓝图：如果 Master 的推理平台能实现共享 KV Cache 池（配合上一条华为 G3.5 的方向），缓存命中率可以跨 Pod/跨节点复用，直接把 per-token 成本压到接近「缓存读取价」。反过来说，如果 K8s 上每个推理 Pod 独立管理 KV Cache（不共享），缓存命中率会随 Pod 扩缩容而清零--这正是调度器和缓存系统需要协同设计的地方。

### 3. 📦 AI Agent 可观测性三板斧：Traces + Costs + Audit，传统 APM 看不懂 Agent 的循环

**原文标题:** You can't debug what you can't see - Observability for AI Agents
**来源:** CNCF Blog | 2026-08-04
**链接:** https://www.cncf.io/blog/2026/08/04/you-cant-debug-what-you-cant-see-observability-for-ai-agents/

🎯 **一句话精髓**: 传统 APM 回答「服务是否存活、响应多快、有无错误」，而 Agent 监控需要回答「为什么这个任务成本异常高、为什么 agent 反复调用同一工具、agent 是否真的做了它说做的事」--文章基于生产环境实战提出 Traces（会话时间线）+ Costs（单位经济学）+ Audit（不可变审计记录）三板斧，并强调成本是 Agent 故障的金丝雀信号。

🔧 **技术栈**: Langfuse / Prometheus / Grafana / batch exporter / per-tool call budgets / loop detection / PII redaction / automated session review / cardinality management

📐 **架构/方法亮点**:
- **Traces 不是 APM trace 而是 Agent trace**：每个 Agent session 产出一条完整决策历史 trace--每次模型调用、工具执行、子代理委派都是一个 span，子代理工作作为父 trace 的子节点嵌套；trace 交付必须非阻塞（batch exporter 管道，内存缓冲 + 定期 flush），trace 后端不可达时丢失的是遥测不是可用性
- **成本是第一信号**：Agent 循环（因无法推进而反复调用同一工具）会几何级烧 token--仅靠 reactive alerting 不够快（并行 Agent 的紧密循环可在 webhook 触发前几秒烧穿预算），需要硬性迭代上限、per-tool call 预算、循环检测（阻断完全相同的连续调用）作为 pre-flight 断路器；告警是第二道防线不是第一道
- **Prometheus 标签低基数警告**：工具名和 Agent 名是安全的（有界值），绝不能把 session ID 等唯一标识放进 Prometheus 标签--日跑数千 session 的系统会导致基数爆炸压垮 metrics server；per-session 细节留给 tracing 后端或结构化日志

💡 **关键数据**: Agent 循环会**几何级烧 token**；并行 Agent 紧密循环可在**几秒内**烧穿预算；成本异常几乎总是指向 bug（循环/模型路由错误/无界上下文累积）；异常 session 通过自动化分析标记（duration/cost/tool count/loop detection/token efficiency flags）而非人工逐条审查。

🔗 **樱桃的调度视角**: 对 Master 的 K8s AI 推理平台有直接架构参考--Agent 可观测性三板斧可以映射到 K8s 可观测性栈：Traces = 分布式追踪（Langfuse/Tempo），Costs = GPU 成本监控（OpenCost 已在 Aug 9 日报覆盖），Audit = K8s audit log。关键洞见是**成本监控不是财务工具而是故障检测器**--Agent 的成本突增几乎总是 bug 信号，这和 GPU 利用率突降/突增是同类信号。Prometheus 基数警告也直接适用：在 K8s 上监控 Agent 时，用 agent_name/tool_name 做标签（有界），session_id 留给 tracing。per-tool call 预算和循环检测可以做成 K8s 准入控制或 sidecar 代理的策略。

### 4. 📦 Agent 安全第一次换轨：从「内容对不对」到「行为可不可控」，HITL 正在退化为安慰剂

**原文标题:** 当 human in the loop 变成"闭着眼睛点确认"，企业Agent 安全还能靠谁？
**来源:** InfoQ 中文 | 2026-08-10
**链接:** https://www.infoq.cn/article/5qWsLD6JV8N2zDgGuhK9

🎯 **一句话精髓**: 腾讯/百度/Cloudflare 三位安全专家在 AICon 直播中指出 Agent 安全发生了两次换轨--从「内容风险」到「行为风险」（Agent 有了工具/记忆/执行权限后，恶意指令可以藏在网页/文档/邮件里让 Agent 真去删库/转发数据/转账），从「守住静态入口」到「约束动态行为」（已知入口模糊了，传统 WAF 靠特征拦截而攻击已变成语义）；human-in-the-loop 正在成为最大安慰剂，弹窗越多越退化为「闭着眼睛点确认」。

🔧 **技术栈**: Prompt Injection / MCP / OWASP LLM Top 10 / WAF / DLP / sandbox 隔离 / 临时 token / API gateway / audit log / 语义引擎 / OpenClaw / Hermes

📐 **架构/方法亮点**:
- **Agent 的三个换轨变量**：身份（Agent 有了自己的 channel/skill/MCP，可以远距离控制并进入公司内网）+ 思考（大模型 + harness 工程让 Agent 有自主规划能力）+ 行动（基于工具和自主编码执行现实操作）--从「Agent 说错话」到「Agent 干错事」，传统 AI 是业务流中的一个环节而 Agent 本身就是业务流全生命周期
- **工具 = 钥匙分发**：每接入一个工具就等于给 Agent 和黑客多发了一把钥匙，多数企业发出去的是万能钥匙而非用完即焚的临时门禁；上下文压缩导致约束丢失的极端案例--skill 用真实上传地址做示例，上下文被压缩后唯一留存的就是示例地址，数据直接 post 到示例网址
- **三板斧：可视、可管、可追溯**：可视（看到企业整体风险面）+ 可管（保底策略 + 最小权限 + 沙箱隔离 + 临时 token + gateway + DLP）+ 可追溯（即便所有防御失效也要在各个层面加 log 可溯源）；核心判断：安全不是刹车是护栏--有了护栏在山路上反而敢开得更快

💡 **关键数据**: Prompt Injection 高居 **OWASP LLM 01** 安全风险榜首；OpenAI 已发布工具滥用和过度授权警告，将其列为**高危漏洞类别**；Agent 从 demo 走向台前的标志是 OpenClaw/Hermes 爆火；安全方法论三板斧覆盖**可视/可管/可追溯**三个维度。

🔗 **樱桃的调度视角**: 对 Master 的 K8s Agent 平台有直接操作价值--「每接入一个工具 = 发一把钥匙」这个判断意味着 Agent 平台的每个 MCP/tool/skill 连接都应该有独立的 ServiceAccount + 最小权限 RBAC + 临时 TokenRequest（短 TTL）+ 网络策略隔离 + audit log。上下文压缩导致约束丢失的案例特别值得警惕：Agent 在 K8s 上执行操作时，prompt 中的约束（「不要访问生产环境」）不是边界--能被 talk past 的边界不是边界，真正的 enforcement 要在 harness 层（准入控制/Kyverno）和网络层（NetworkPolicy）做。「三板斧」可直接映射到 K8s：可视 = 监控面板，可管 = RBAC + NetworkPolicy + 准入控制，可追溯 = audit log。

### 5. 📦 Cloudflare Agent Access Model：不信任运行，授权每个动作--Agent 版 Zero Trust

**原文标题:** The Agent Access Model
**来源:** Cloudflare Blog | 2026-08-05
**链接:** https://blog.cloudflare.com/the-agent-access-model/

🎯 **一句话精髓**: Cloudflare 提出 Agent Access Model（AAM）--正如 BeyondCorp 把隐式信任从网络层移除，AAM 把隐式信任从「任务执行图」中移除，核心规则是「不信任运行，针对任务及其累积状态授权每个动作」；核心思路不是让每个访问决策更聪明，而是让 Agent 的能力范围更小，从源头减少需要判断的量。

🔧 **技术栈**: BeyondCorp / Zero Trust / Agent Access Model (AAM) / task execution graph / capability ceiling / trust level / identity brokering / continuous mediation / inline preventive controls / least privilege

📐 **架构/方法亮点**:
- **人类模型不适配 Agent 的四个属性**：①Agent 是短暂的但凭证是持久的（service account 的长期密钥/宽范围/低频轮换 outlive 了任务本身）→ 凭证生命周期应匹配任务生命周期（通常几分钟）；②Agent 以机器速度行动（人类调优的异常检测/限流/DLP 反应太慢，Agent 有数据库连接和出站网络路径就能在人类控制采样完之前把表读出来 POST 到外部）→ 预防性控制必须 inline 运行在动作点；③prompt 不是边界（模型可被注入内容操纵或自行产出不安全动作，推断的意图可被攻击者通过文本塑造）→ enforcement 属于中介工具调用的 harness 和中介数据包的网络层；④Agent 跨跳组合权限（Agent 调工具调另一个 Agent 调 API，「这是为谁做的、允许做什么」在链路中消失）
- **AAM 的核心规则**：「不信任运行，针对任务及其累积状态授权每个动作」--授权一个动作不授权后续动作；每次动作都重新评估当前任务状态和已累积的信任/风险；capability ceiling 限定单个任务执行图内所有动作的权限上限
- **让能力更小而非让判断更聪明**：当前工作多在让每个访问决策更智能（更好的上下文分析/风险评分），AAM 采取不同方向--缩小 Agent 的能力范围使需要判断的量更少；通过 identity brokering（身份代理）+ continuous mediation（持续中介）+ stateful trust（有状态信任）实现

💡 **关键数据**: Agent 任务生命周期通常**几分钟**；Agent 有数据库连接和出站网络路径时可在**人类控制采样完成前**读取并外传整张表；AAM 的 capability ceiling 限定单个任务执行图的所有动作权限；凭证应匹配任务生命周期而非 service account 的长期密钥。

🔗 **樱桃的调度视角**: AAM 对 Master 的 K8s Agent 平台是架构级指导--「不信任运行，授权每个动作」意味着 K8s 的 RBAC 需要从「Pod/ServiceAccount 级别」细化到「Agent task/action 级别」。具体实现路径：每个 Agent 任务创建独立的短生命周期 ServiceAccount（TokenRequest with short TTL），capability ceiling 通过 RBAC Role 限定该任务可访问的 K8s 资源类型和操作，continuous mediation 通过 admission webhook 在每个 API 调用时重新评估任务状态。Agent 跨跳组合权限的属性意味着 K8s 需要支持跨 ServiceAccount 的委托链追踪（类似 AWS role chaining 的审计链）。「让能力更小」的思路也适用于 GPU 调度：不是给 Agent 一个能访问所有 GPU 的凭证，而是按任务粒度分配特定 GPU 的临时访问权限。

### 6. 📦 Cloudflare 行为评估：从点状 Risk 到持续 Trust，Agentic Internet 的流量治理

**原文标题:** Unveiling good and bad behaviors on the Agentic Internet
**来源:** Cloudflare Blog | 2026-08-07
**链接:** https://blog.cloudflare.com/good-and-bad-agentic-behaviors/

🎯 **一句话精髓**: Cloudflare 把 bot 治理从「点状 Risk 评估」转向「持续 Trust 评估」--Risk 是短暂的（某个请求/动作有多大可能有害），Trust 是基于声誉随时间积累的；在人类与 bot 界限越来越模糊的混合流量时代（同一 session 从人类切换到 Agent 再切回来），关键是评估行为而非身份，用 BotBase 目录追踪所有已知 bot/agent 的行为是否符合声明。

🔧 **技术栈**: BotBase / Precursor / Risk assessment / Trust evaluation / Web Bot Auth / CDN-injected JavaScript detection / continuous client-side detection / Verified bots / behavioral baseline

📐 **架构/方法亮点**:
- **Risk 与 Trust 是独立但互惠的值**：Risk = 某个请求/动作有多大可能有害（短暂的、瞬时的）；Trust = 基于声誉随时间积累的（持续的）--不能只看「这个行为风险高不高」，还要看「这个访问者基于历史行为是否值得信任」（深夜疯狂按门铃的如果是你最好的朋友，你会开门）
- **混合流量挑战**：同一 session 可能从人类浏览切换到 Agent 结账再切回来--传统的「人类 = 好、bot = 坏」二分法失效；需要分析连续行为模式来评估 Trust，而非静态的点状检查
- **BotBase 目录 + Precursor 持续检测**：BotBase 不只是「好 bot」目录而是所有已知 bot/agent 的行为事实数据库（verified = 诚实声明自己 + 不滥用信任）；Precursor 是 CDN 注入的持续客户端检测系统，在整个 session 期间持续评估用户行为（而非仅入口检查），能检测到网络信号无法发现的细微非人类行为

💡 **关键数据**: 超过**一半**的 HTML 页面请求已不再来自人类；Verified bot 的定义简化为两个条件：①诚实声明自己 ②不滥用已获得的信任；Precursor 在整个 session 期间**持续**评估行为而非入口单次检查。

🔗 **樱桃的调度视角**: Risk vs Trust 的分离对 Master 的 K8s 推理平台有流量治理启发--当推理 API 同时服务人类用户和 Agent 时，不能只按身份（人类 vs Agent）做限流和资源分配，而要按行为模式做持续评估。Agent 流量的特征（高并发、短会话、不渲染 CSS、每次请求有 token 成本）和人类流量完全不同，需要差异化的 rate limiting 和调度策略。Precursor 的持续客户端检测思路可以内化到推理平台的 API gateway：不是在入口做一次认证就放行，而是在整个 session 期间持续评估调用模式（频率/工具链/数据访问量），异常模式（循环调用/大量数据读取）触发动态限流或降级--这和第 3 条的可观测性三板斧中的「循环检测」是同一思路的不同实现。

## 📓 樱桃的今日学习总结

1. **AI 推理的存储分层正在从「HBM/DRAM」扩展到「G3.5 共享上下文存储」，调度器需要感知新的存储层级** - 华为 G3.5 CMS（介于本地 SSD 和共享存储之间的高速共享缓冲层）和昨天日报里的 Mooncake/NVIDIA CMX 指向同一趋势：当推理集群进入千卡/万卡规模，KV Cache 和 Agent 上下文需要 PB 级共享池。这意味着调度器的资源模型从「GPU 算力 + 本地显存」扩展到「GPU 算力 + 本地显存 + 共享 CMS 容量/带宽」的三层协同。关键设计决策是：KV Cache 可共享外置时，Prefill 和 Decode 可以分离到不同节点，Session 路由不再受限于同一 GPU 上的历史上下文。

2. **KV Cache 命中率是推理成本的第一变量，比模型定价更重要--缓存策略即调度策略** - DeepSeek 涨价 30 倍仍最便宜的底气来自 100% 缓存命中率（12 小时不失效）+ V4 的 8.7 倍 KV 压缩。三种缓存前缀落盘机制（per-request、common prefix detection、interval-based）是分布式推理 KV Cache 管理的蓝图。对 K8s 推理平台的核心启示：如果每个推理 Pod 独立管理 KV Cache，Pod 扩缩容会导致缓存清零；需要把 KV Cache 管理从 Pod 级提升到集群级，让缓存跨 Pod/跨节点复用。缓存命中率应该成为调度决策的输入变量：高命中率 session 优先路由到有缓存的节点，缓存淘汰策略与 Pod 调度策略协同设计。

3. **Agent 安全正在经历从「内容风险」到「行为风险」的换轨，治理框架需要从身份认证升级到行为约束** - 三篇文章共同指向同一趋势：InfoQ 的 HITL 安慰剂论（弹窗越多越退化为闭眼点确认）、Cloudflare AAM 的「不信任运行、授权每个动作」、Cloudflare 行为评估的「持续 Trust vs 点状 Risk」都在说同一件事--Agent 有了工具/记忆/执行权限后，能被 talk past 的边界不是边界。治理框架的映射：K8s 的 RBAC 从 ServiceAccount 级细化到 task/action 级，凭证生命周期匹配任务生命周期（TokenRequest short TTL），enforcement 放在 harness 层（admission webhook/Kyverno）和网络层（NetworkPolicy）而非 prompt 层。「每接入一个工具 = 发一把钥匙」意味着 Agent 平台需要按工具粒度做权限管理和沙箱隔离。成本监控（第 3 条）和行为评估（第 6 条）是同一思路的两种实现：持续监控异常模式而非仅入口认证。
