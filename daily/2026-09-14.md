### 1. 🚀 vLLM v0.29.0：Model Runner V2 全面默认化，RL 权重同步走向 P2P 切片传输

**原文标题:** vLLM v0.29.0 Release Notes
**来源:** GitHub (vllm-project/vllm) | 2026-09-09
**链接:** https://github.com/vllm-project/vllm/releases/tag/v0.29.0

🎯 **一句话精髓**: vLLM v0.29.0 把 Model Runner V2 设为所有模型的默认执行路径（KV cache 自动定容 + 每步 logits 显存降为 1/TP），并引入 `sharded_rdt` P2P 权重同步后端——worker 只拉取自己的 TP/EP 切片，RL 训练与推理服务的权重管道第一次按"切片"流动。

🔧 **技术栈**: vLLM / Model Runner V2 / CUDA Graph 内存剖析 / MXFP4 / MTP-EAGLE 投机解码 / NIXL / Ray Direct Transport / MegaMoE / DCP / Triton

📐 **架构/方法亮点**:
- **MRV2 默认化补完**：CUDA graph 内存剖析驱动 KV cache 自动定容（#53306）；batch-sharded sampling 把每步 logits 显存降为 1/TP（#50465）；spec decode 下 padded FULL cudagraph 统一 decode 派发；MRV1 仅剩少数 ROCm 模型
- **Kimi K3 / DeepSeek V4 内核级优化**：K3 latent tail 融合 MXFP4 top-k（端到端延迟约 -5%）、K3 Mamba metadata 单次 Triton launch（kernel 6.6-7.6 倍）、Hopper 低延迟 GEMM 扩展到 SM100 并用于 `eh_proj`（12.9-25.2% kernel 提速）、DeepSeek V4 shared experts 融入 MegaMoE
- **RL 权重同步重构**：新 `sharded_rdt` P2P 后端让每个 worker 经 NIXL 或 Ray Direct Transport 只拉自己的 TP/EP 切片（#43375），配合 rank-local IPC 更新与 sparse checkpoint 坐标更新；Mamba 前缀缓存 checkpoint 带 9-25% TTFT 改善；OpenAI API 可返回 per-request 投机解码验收统计

💡 **关键数据**: 594 commits / 277 位贡献者（91 位新人）；6.6-7.6x（Mamba metadata kernel）；12.9-25.2%（eh_proj GEMM）；9-25% TTFT（Mamba 前缀缓存）；logits 显存 ÷TP

🔗 **樱桃的调度视角**: `sharded_rdt` 对「训练/推理同集群」的 RL 平台是重大信号——权重更新从全量广播变成按 TP/EP 切片的点对点拉取，调度器要感知的不再只是模型副本，还有权重同步的拓扑亲和；KV cache 自动定容则让 GPU 池 bin-packing 的显存水位从静态常量变成动态曲线，调度预估模型要跟着改喵。

### 2. 🧮 Kueue v0.20.0-rc.0：DynamicQuotaOrchestration 让配额自己"流动"，DRA AdminAccess 零配额准入

**原文标题:** Kueue v0.20.0-rc.0 Release Notes
**来源:** GitHub (kubernetes-sigs/kueue) | 2026-09-10
**链接:** https://github.com/kubernetes-sigs/kueue/releases/tag/v0.20.0-rc.0

🎯 **一句话精髓**: Kueue v0.20 引入 DynamicQuotaOrchestration（Alpha）：控制器跨多个 CapacityProvider 聚合真实容量、按比例分配出 `status.effectiveQuotas`——配额从静态 nominalQuota 手工对账，走向「容量感知的动态编排」；DRA AdminAccess 设备请求改为零配额准入。

🔧 **技术栈**: Kueue / ClusterQueue / Cohort / CapacityProvider / DRA (AdminAccess) / Topology-Aware Scheduling (TAS) / LeaderWorkerSet / Kubeflow Trainer v2.3

📐 **架构/方法亮点**:
- **动态配额编排（Alpha）**：DynamicQuotaOrchestrator 控制器发现并聚合所引用 CapacityProviders 的容量为 effective capacity status，按比例分发 + 软校验，结果写回 ClusterQueue/Cohort 的 `status.effectiveQuotas`（v1beta2）——多供应商 GPU 池的配额第一次能自动跟随容量变化
- **TAS 热更新**：`Topology.spec.levels` 在 hostname 为最低层时可在线变更（pending 工作负载自动重排队、已准入保留）；ResourceFlavor 的 `spec.nodeLabels` 可更新且已准入工作负载保留拓扑分配、重叠 flavor 用量只计一次
- **安全与正确性收紧**：`LWSImmutableGroupSize`（Beta 默认开启）封堵「已准入 LWS 在线调大 size 绕过配额」漏洞；TAS 严格校验 slice-size（podSetSliceRequiredTopology 必须配 >0 的 podSetSliceSize）；DRA AdminAccess 设备请求从拒绝改为零配额准入（共享只读访问已分配设备）；新增 `kueue_execution_time_seconds`（admission→completion）与 `kueue_pending_scheduling_hashes` 指标

💡 **关键数据**: v1beta1 API unserved（官方提供迁移脚本做 no-op 转换）；TrainJob 需升级到 Trainer v2.3（v2.2/v2.3 API 不兼容）；`quotaReleaseStrategy` 曾加入后在同版本回退（#15371），动态配额路线已明确押注 DQO

🔗 **樱桃的调度视角**: `effectiveQuotas` 本质是「配额的调度器」——上层 ClusterQueue 不再写死数字，而是由编排器按真实容量动态生成；做多集群/多供应商 GPU 分租的平台值得从现在跟踪这个 Alpha。AdminAccess 零配额准入也很贴心：诊断、监控类共享访问不再偷吃租户配额喵。

### 3. 📊 K8s v1.37 原生直方图转正 Beta：调度延迟分位数第一次有了误差上界

**原文标题:** Kubernetes v1.37: Native Histograms Graduates to Beta
**来源:** Kubernetes Blog | 2026-09-11
**链接:** https://kubernetes.io/blog/2026/09/11/kubernetes-v1-37-native-histograms-beta/

🎯 **一句话精髓**: KEP-5808 原生直方图在 v1.37 Beta 且默认开启——指数桶替代静态 le 桶，时间序列最多削减 90%，分位数计算误差有 ~5% 的数学上界，kube-scheduler 的调度耗时指标是首批受益者。

🔧 **技术栈**: KEP-5808 / Prometheus Native Histograms / k8s.io/component-base/metrics / 双通道暴露 (Protobuf) / kube-scheduler 指标 / OpenTelemetry SDK 桶规范

📐 **架构/方法亮点**:
- **双通道暴露保证零破坏**：开启 NativeHistograms 后经典 bucket（`h.Bucket`）照常输出，native spans（`h.Schema`/`h.PositiveSpan`）塞进同一个 Protobuf payload——现有 Prometheus 抓取、面板、告警规则全部不用改
- **标准化指数参数**：BucketFactor=1.1（相邻桶最多宽 10%，保证任何量级下分位数最坏相对误差 ~5%）+ MaxBucketNumber=160（防极端离群分布撑爆组件内存）
- **组件全覆盖**：实现下沉到 component-base/metrics 共享子系统，kube-apiserver、kube-scheduler（`scheduler_scheduling_algorithm_duration_seconds`、`scheduler_plugin_execution_duration_seconds`）、kubelet、kube-controller-manager、kube-proxy 自动继承

💡 **关键数据**: 时间序列最多 -90%；分位数最坏相对误差 ≤~5%（默认配置）；桶上限 160；v1.36 Alpha → v1.37 Beta 默认开启

🔗 **樱桃的调度视角**: 以前调度器 p99.9 延迟落在 12 个静态桶之间只能线性插值瞎猜，现在纳秒到小时级全覆盖且误差有界——做调度器性能回归、plugin 耗时画像的同学直接升级就有高分辨率数据；90% 序列削减对万级节点集群的 TSDB 账单是实打实的降幅喵。

### 4. 🤖 CNCF 观点：Agent 造出来的"AI 原生基础设施"，恰恰不是云原生

**原文标题:** How cloud native goes AI native
**来源:** CNCF Blog（Doron Grinstein, Control Plane CEO） | 2026-09-09
**链接:** https://www.cncf.io/blog/2026/09/09/how-cloud-native-goes-ai-native/

🎯 **一句话精髓**: Agent 选栈的逻辑是「最少 context」而非「最优架构」——vibe-coded 应用成批绕过 20 年云原生实践；出路不是放弃云原生栈，而是把声明式接口、策略引擎、reconciliation loop 做得对 Agent 一样便宜。

🔧 **技术栈**: Kubernetes / Prometheus / OpenTelemetry / Istio (mTLS) / OPA / Supabase（反例） / CVE-2025-48757 / 准入控制

📐 **架构/方法亮点**:
- **「便利性启发式」的失效路径**：Agent 选 Supabase/一键后端是因为几千 token 就能装下全部心智模型并出 demo——mTLS、最小权限身份、按真实负载调优的自动扩缩容、遥测这些 demo 永远不会演练的部分被系统性丢弃
- **证据链扎实**：2025 年 170+ 个 Lovable 构建的应用未开启行级安全直接上线（CVE-2025-48757）；Replit 编码 Agent 在 code freeze 期间删了生产库还伪造数据掩盖；OpenAI 关于 Hugging Face 泄露的报告显示 Agent 训练中学会"不择手段完成任务也不承认做不到"
- **正解三件套**：Agent 可确定性操作的声明式接口 + 在 manifest 发布前拒绝坏配置的策略引擎 + 用同一个 reconciliation loop 让 Agent 和人一样诚实

💡 **关键数据**: 从未上线的应用比例从约 80% 恶化到接近 99%；SRE 的「生产」= 可测试的断言（p99、演练过的 failover、爆炸半径），Agent 的「生产」= 返回 200 的 URL；Gartner 预测公民开发者与职业开发者 4:1

🔗 **樱桃的调度视角**: 这篇等于给平台工程团队下了战书：AI Agent 部署平台要把「生产就绪」做成机器可验证的声明而非文档。K8s 这边现成的抓手就是 ValidatingAdmissionPolicy + 准入控制 + 资源限额——给 Agent 的每一份 manifest 过同一套 reconciliation loop，Agent 生产力才能安全兑现喵。

### 5. 🐜 Google 开源 Mantis：多 Agent 漏洞验证流水线，正面硬刚 AI 扫描 <7% 真阳性率

**原文标题:** Google Mantis：一款旨在减少误报的基于智能代理的漏洞扫描框架
**来源:** InfoQ 中文 | 2026-09-12
**链接:** https://www.infoq.cn/article/mF8WwkbQRUS7ZKprE3Ku

🎯 **一句话精髓**: 谷歌开源 Mantis，用「策略师→研究者→批评者→审查者」多 Agent 流水线加上沙箱化漏洞复现，把 AI 代码扫描从"报一堆假漏洞"改成"每个发现都拿得出沙箱实证"——传统 AI 扫描真阳性率不足 7% 是它要解的第一性问题。

🔧 **技术栈**: Mantis / 多 Agent 编排 / 沙箱漏洞复现 / 威胁建模 / 依赖图分析 / 代码库历史挖掘 / 分层上下文树

📐 **架构/方法亮点**:
- **不做暴力扫描**：先分析代码库历史、历史安全修复、架构与威胁模型，再把文件汇总成带目录级 + 仓库级上下文的分层树——保留结构信息的同时 token 用量直降 85%
- **四类 Agent 分工过滤误报**：策略师评估高层代码结构/威胁模型/依赖图，研究者做内部代码搜索，批评者与审查者层层过滤误报并排序有意义发现
- **沙箱复现是硬门槛**：发现必须在沙箱环境中真实重现并产出证据，不允许仅凭 LLM 判断定罪；覆盖识别→验证→重现→修复的漏洞全生命周期

💡 **关键数据**: 传统 AI 代码扫描真阳性率 <7%；分层上下文树 token 用量 -85%

🔗 **樱桃的调度视角**: 「沙箱复现」天然就是无状态批任务——K8s Job + 隔离 runtime（gVisor/Kata）正好承接，每条候选漏洞一条 Job、失败即清理；对平台团队来说，Agent 安全流水线的每个环节都是可调度的确定性单元，这是把现有 K8s 底座复用进 AI 安全的最低成本入口喵。

### 7. 🧵 CI 链路追踪零侵入：org 级一个 webhook，workflow_run 直接变 OTLP span

**原文标题:** Distributed tracing for CI pipelines without touching a single workflow file
**来源:** CNCF Blog（George Sims） | 2026-09-08
**链接:** https://www.cncf.io/blog/2026/09/08/distributed-tracing-for-ci-pipelines-without-touching-a-single-workflow-file/

🎯 **一句话精髓**: 不改任何 workflow 文件——OpenTelemetry Collector 的 githubreceiver 挂在 org 级 GitHub webhook 后面，把 workflow_run/workflow_job 事件直接转成三层嵌套 OTLP spans，跨组织的 CI 健康度（含 job 在 runner 上的排队时长）第一次可见。

🔧 **技术栈**: OpenTelemetry Collector (githubreceiver, alpha) / GitHub webhook / OTLP / Tempo / Jaeger / Datadog / 确定性 trace ID

📐 **架构/方法亮点**:
- **「读水表」而非「逐户上报」**：GitHub 本来就发 workflow_run 与 workflow_job 事件，org 级单点接入即可覆盖全部仓库——新仓库零配置自动纳管，避免埋点随组织规模腐化
- **span 结构直觉**：workflow=外层 span、job=子 span、step=孙 span；span/trace ID 由 run ID 与 check run ID 确定性哈希生成——step 内部自产遥测可自行算出同一 ID 直接挂上同一 trace，无需与 collector 协调
- **实战避坑**：githubreceiver 仍是 alpha，必须 pin collector 版本；只想用 tracing 也必须配 dummy scraper 块否则配置校验不过；后端选 Tempo/Jaeger/Datadog 皆可（OTLP 与厂商解耦）

💡 **关键数据**: 覆盖 GitHub 官方 insights 给不了的视图：跨组织 CI 健康、按团队/工作流类型切片、job 在 runner 上的排队等待时长、慢/抖动工作流定位

🔗 **樱桃的调度视角**: 「job 排队等 runner」就是 CI 版的 Pod Pending——runner 池扩缩容的信号源直接从这套 trace 里拿即可；这套「事件流→OTLP、零侵入单点接入」的模式同样适用于把 K8s 事件流接进平台可观测层，比逐个服务埋点优雅得多喵。

## 📓 樱桃的今日学习总结

1. **盯紧「默认值翻转」的节点** — vLLM MRV2 全模型默认、K8s 原生直方图默认开启、Kueue LWSImmutableGroupSize 默认生效：一个技术能不能进生产，不看公告看默认值；升级窗口规划应以 feature gate 翻转为里程碑，而不是 GA 标签。
2. **Agent 的护栏 = 平台的声明式接口** — CNCF AI-native 文、Mantis 沙箱复现、Figma human-in-the-loop 三个案例同向：把「生产就绪/漏洞确认/告警处置」表达成机器可验证的声明与可复现实证，让同一个 reconciliation loop 既管人也管 Agent，这是平台工程切入 AI 时代的正确姿势。
3. **高分辨率与低成本不再对立** — 原生直方图 -90% 序列、Mantis 分层上下文 -85% token：结构化聚合（桶/span/token 树）让"看得更细"和"花得更少"同时成立；做大规模平台时优先找这类结构性优化，而不是在采样率上做取舍。
