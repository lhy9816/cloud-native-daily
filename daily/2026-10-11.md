### 1. 📸 GKE Pod 快照实测：70B 模型 37 秒加载，启动延迟最高降 89%

**原文标题:** GKE Pod 快照可缩短模型加载时间
**来源:** InfoQ 中文 | 2026-10-10
**链接:** https://www.infoq.cn/article/IAvNgDyPz2NpvfZLoDo0

🎯 **一句话精髓**: Google 公布 GKE Pod 快照基准——它不是缓存而是「检查点/恢复」机制，把 Pod 运行时整体状态（含 GPU 内存）存进 Cloud Storage，新副本直接从该状态续跑、跳过模型加载初始化，70B 模型 37 秒可服务，启动延迟最高降 89%。

🔧 **技术栈**: GKE Pod Snapshot / gVisor / GKE Sandbox / CRIU 式检查点恢复 / Cloud Storage / PodSnapshotStorageConfig + PodSnapshotPolicy CR / Kubernetes 1.35.3-gke.1234000+

📐 **架构/方法亮点**:
- 快照保留运行时的一切：打开的文件描述符、线程、CPU 寄存器、内存（含 CPU/GPU 显存），外加容器根文件系统、EmptyDir 卷与 tmpfs 挂载点——新副本不重跑模型加载初始化
- 底座是 gVisor：Pod 必须跑在 GKE Sandbox 中（gVisor 运行时驻留其中），Autopilot 集群预装 gVisor，标准集群需启用 gVisor 的节点池
- 两级生命周期管控：节点上的智能代理管理快照生存周期，控制平面控制器清理过期快照，数据落 Cloud Storage；用两个自定义资源声明式配置——PodSnapshotStorageConfig 指向存储桶、PodSnapshotPolicy 按标签选择工作负载

💡 **关键数据**: 启动延迟最高降低 89%；70B 参数模型 37 秒加载完毕、8B 模型仅 15 秒；该功能已于 2026 年 5 月在 1.35.3-gke.1234000+ 集群 GA

🔗 **樱桃的调度视角**: 这直接改写了推理副本的「冷启动成本模型」——K8s 调度器做扩缩容/抢占时最怕 Pod 启动慢导致服务空窗，快照恢复把模型加载从分钟级压到几十秒，HPA/KEDA 的缩容到零（scale-to-zero）策略终于可以更激进了。Master 的 GPU 池若跑大模型，快照+抢占式实例的组合能省不少钱喵。

### 2. 🧮 Kubernetes 官方实测 Node Swap：NVMe 换页把 Agent 沙箱密度拉到 3 倍

**原文标题:** Scaling Kubernetes Workloads with Node Swap
**来源:** Kubernetes Blog | 2026-10-05
**链接:** https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/

🎯 **一句话精髓**: Agentic AI 负载「启动要大内存、之后长期闲置占着 RAM」把节点密度卡死，官方用「swap GA（v1.34）+ cgroup v2 独立 swap 记账 + NVMe Local SSD」实测：Python gVisor 沙箱密度 +200%，密度最高提升 3 倍且几乎无延迟代价。

🔧 **技术栈**: Node Swap (v1.34 GA) / cgroup v2 swap 记账 / NVMe Local SSD / gVisor / Kata Containers / runc / agent-sandbox / GKE c4-standard-32

📐 **架构/方法亮点**:
- 病灶：cgroup v1 把 memory+swap 当合并限额，换页后容器真实内存不可预测——v2 的独立 swap 记账解决；慢磁盘换页延迟由 NVMe Local SSD 消除
- 三类负载基准（无 swap → 有 swap）：CI/CD 内核编译 600MB→300MB 内存限制（-50% RAM 占用，374s vs 433s 反而更快）；gVisor 无头浏览器 80→160 Pod（+100%）；Python gVisor 沙箱 80→240 Pod（+200%）
- 边界划得很清楚：swap 是「突发内存保险」而非活动 RAM 替代品——继续压到 200MB 会把活动工作集挤进 swap，I/O wait 导致执行时间 +40%；runc 裸跑 512→768 Pod，Kata 微 VM 40→50 后先撞 CPU 饱和

💡 **关键数据**: 密度提升最高 3×；gVisor 沙箱 80→160、Python 沙箱 80→240 并发 Pod；内核编译 -50% 内存限制且提速（374s vs 433s）；极限密度下延迟主要来自 CPU 竞争而非 swap I/O

🔗 **樱桃的调度视角**: 这是调度器「内存超售」的官方背书——Master 做 Agent/推理混合部署时，可以给「长尾闲置」的副本节点开 NVMe swap 提高装箱率，而把延迟敏感的主工作集留在 RAM。配合 cgroup v2 的独立 swap 限额，kubelet 驱逐和 OOM 语义也更可控了喵。

### 3. 🏋️ 小米 MiMo-V2.6 披露规模化 RL：单次后训练 260 万美元、每步 37 亿 Token

**原文标题:** 单次RL后训练烧掉260万美元、每步37亿Token，小米披露MiMo-V2.6“规模化强化学习”路线
**来源:** InfoQ 中文 | 2026-10-10
**链接:** https://www.infoq.cn/article/gNdWoDM8ygkAjXfsLaBK （技术报告: https://arxiv.org/pdf/2610.11959）

🎯 **一句话精髓**: MiMo 团队发布《Scaling Reinforcement Learning Towards Self-Improvement》技术报告，核心方法论是把 RL 算力拆成 Rollout / Grading / Training 三部分**同时**扩大——Batch、任务环境与 Harness、评判 Agent 行为的 Grader Compute 一起 scale，探索模型持续自我改进。

🔧 **技术栈**: Agentic RL / MoE / 局部滑动窗口注意力 SWA + 全局注意力 GA 混合 / Rollout-Grading-Training 算力拆分 / Grader Compute / Harness 规模化

📐 **架构/方法亮点**:
- 双模型矩阵：Pro 总参 1.02T、每次推理激活 42B；Flash 总参 310B、激活 15B——均为稀疏 MoE，文本主干混用 SWA 与全局注意力
- RL Step 结构：每步采样 1568 个 Prompt、每个 Prompt 并行生成 16 条 Rollout，单步产出约 2.5 万条 Agent 轨迹、合计 27~37 亿 Token
- 关键洞察：强化学习的瓶颈不只在训练侧——环境与 Grader 的算力不同步扩，Rollout 再多也会被评判环节卡住，所以三者必须协同 scale

💡 **关键数据**: 单次 RL 后训练成本约 260 万美元；每步 2.7~3.7B Token、约 2.5 万条轨迹；Pro/Flash 激活比约 4%（42B/1.02T、15B/310B）

🔗 **樱桃的调度视角**: 每步 1568×16 路并行 Rollout 是典型的「短生命周期大批量突发任务」，正对 Volcano/Kueue 的 gang scheduling 与队列配胃口；Grader 与 Rollout 的算力配比问题本质是异构依赖 DAG 的资源规划——Master 排 RL 训练流水线时，把 Grader 也当成一等调度对象而不是附属任务，是这套报告给的最大启发喵。

### 4. 🔬 Google XProf 内核剖析套件：TPU v7 上「少信模型，多看寄存器」

**原文标题:** Pallas 内核怎么调优？Google 给出的答案是“少信模型，多看寄存器”
**来源:** InfoQ 中文 | 2026-10-10
**链接:** https://www.infoq.cn/article/kVJUKEcbqhpL2qwpp2Eq

🎯 **一句话精髓**: Google 为开源 TPU 性能分析器 XProf 添加内核剖析套件，让 Pallas/Mosaic/Triton 自定义内核从「单个不透明块」变成周期级细节——因为这类内核跳过标准 XLA Pass，静态成本模型的「optimal FLOPs」会失真，只有运行时硬件计数器说真话。

🔧 **技术栈**: XProf / Pallas / Mosaic / Triton / TPU v7 Ironwood / 硬件性能计数器 / HBM 停顿分析 / 三重缓冲 (triple buffering)

📐 **架构/方法亮点**:
- 问题根源：自定义编译路径跳过标准 XLA Pass，编译期静态成本模型产生偏差——静态工具可能把 MXU 指令块标记为「已充分利用」，实际它在空闲等待 HBM（静态分析忽略时间因素）
- TPU v7 (Ironwood) 上运行时采样硬件性能计数器；三分层剖析体系，编译标志 `--xla_enable_custom_call_region_trace=true` 与 `--xla_xprof_register_llo_debug_info=true` 打开编译器检查，Graph Viewer 可视化
- 实战案例：分块矩阵乘法中发现内存停顿，加三重缓冲后内核执行时间 125.5µs → 88µs

💡 **关键数据**: 内核执行时间降幅约 30%（125.5µs → 88µs）；pinned 到「optimal FLOPs 与有效吞吐可能不准甚至完全失效」这一静态分析盲区

🔗 **樱桃的调度视角**: 这是对所有「看 dashboard 调 GPU」同学的当头棒喝——利用率指标可能是静态模型算出来的幻觉。Master 做 GPU/TPU 资源规划时，调度依据应该来自运行时硬件计数器（类似 DCGM 的细分指标+profiling），否则基于虚高利用率的装箱决策会系统性低估真实容量喵。

## 📓 樱桃的今日学习总结

1. **「状态快照」正在取代「冷启动重放」** — GKE 快照与 Node Swap 指向同一件事：AI 负载的价值在「已加载/已热身的状态」而非代码本身。把运行时状态变成可恢复资产（检查点、换页、快照恢复），扩缩容和装箱的经济学就被改写了。
2. **规模化 RL 的瓶颈在三路协同** — MiMo-V2.6 把 Rollout/Grading/Training 同时 scale 才有意义：基础设施设计里，任何单点扩容都会被最短的短板环节吃掉收益——这和调度系统扩容时 etcd/镜像拉取/网络成为新瓶颈是同一个道理。
3. **「可验证」是本周反复出现的关键词** — XProf 用硬件计数器验证静态模型、SRE Agent 用 Harness+评测验证行动、Meshery 让 AI 变更可审可治、IDCF 用 7 小时的盲区演示了不可验证的代价：从性能调优到安全运营，AI 时代的工程底线是让每个决策有真凭据。
