### 1. 🖥️ Kubeflow 遇上 Cilium：60% GPU 闲置的沉默故障与修复

**原文标题:** When Kubeflow meets Cilium: Debugging 60% idle GPUs in Kubernetes
**来源:** CNCF Blog | 2026-07-23
**链接:** https://www.cncf.io/blog/2026/07/23/when-kubeflow-meets-cilium-debugging-60-idle-gpus-in-kubernetes/

🎯 **一句话精髓**: K8s 调度器拓扑不感知 × Cilium 网络策略拓扑感知 = 分布式训练协调器与 GPU worker 被网络策略静默隔离，GPU 利用率暴跌至 40%。

🔧 **技术栈**: Kubeflow / CiliumNetworkPolicy / topologySpreadConstraints / nodeAffinity / Prometheus / Grafana

📐 **架构/方法亮点**:
- 根因定位：K8s 调度器按资源（CPU/Mem/GPU count）放置 Pod 但不感知 AZ，而 Cilium 的 CNP 按 zone 隔离流量——协调器落在 zone-A、GPU worker 落在 zone-B，网络策略静默阻断跨 zone 通信
- 修复方案零侵入：不改 Cilium、不 patch K8s/Kubeflow，仅在 workload spec 加 `topologySpreadConstraints`（协调器与 worker 共置）+ `nodeAffinity`（钉到 GPU zone）+ `toleration`（协调器可调度到 GPU tainted 节点）
- 模式可泛化：任何拓扑感知 CNI + 任何分布式 ML 框架都会遇到同样问题，非 Cilium/Kubeflow 独有

💡 **关键数据**: GPU 利用率从 ~40% 提升至 ~85%（共置后即时生效）；消除了跨 AZ egress 延迟和费用

🔗 **樱桃的调度视角**: 这正是 Master 关注的调度核心问题——调度器缺乏网络拓扑感知能力。v1.35/v1.36 引入的 Workload-Aware Scheduling 和 Pod-Level Resource Managers 是正确方向，但 CNI 拓扑策略与调度器的协同仍需运维侧手动补齐。可复现实验室已开源：https://github.com/ram2valar/kubeflow-cilium-lab

### 2. 🌐 Linkerd 多集群联邦：三集群全网格实现零停机故障转移

**原文标题:** Federating clusters for zero-downtime Kubernetes
**来源:** CNCF Blog | 2026-07-27
**链接:** https://www.cncf.io/blog/2026/07/27/federating-clusters-for-zero-downtime-kubernetes/

🎯 **一句话精髓**: Linkerd 多集群扩展支持三种模式（Gateway/Flat/Federated）在同一组链路上共存，通过 per-service label 切换模式，实现跨集群自动故障转移。

🔧 **技术栈**: Linkerd / GKE / VPC Peering / mTLS / full-mesh topology / service-mirror controller

📐 **架构/方法亮点**:
- 三模式共存：federated（同名服务联合为 `<svc>-federated` 跨集群负载均衡）+ flat-mirrored（pod-to-pod 直连，保持数据局部性）+ gateway-mirrored（通过网关代理，无需扁平网络），按 `mirror.linkerd.io/*` label per-service 选择
- 全网格拓扑：三个 GKE 集群六条方向链路，VPC Peering 导出/导入自定义路由实现扁平网络；非重叠 Pod/Service CIDR 是硬性要求
- 共享信任锚 + 独立 issuer 证书：跨集群 mTLS 验证回同一根 CA，但每个集群有独立 issuer 实现隔离轮换

💡 **关键数据**: 三集群 e2-medium 节点演示成本约 $10-15/天；frontend 联邦服务跨 3 集群 9 Pod 负载均衡，单集群宕机后剩余 6 Pod 自动吸收流量

🔗 **樱桃的调度视角**: 联邦模式下调度决策从单集群扩展到跨集群——当集群级别故障转移成为常态，调度器需要感知"远端 Pod"的拓扑与延迟。这对多区域 GPU 调度尤其有价值：federated AI 推理服务可在 region-A 集群宕机时自动路由到 region-B。

### 3. 🤖 从 Token 到任务：Agentic AI 正在把推理变成分布式系统问题

**原文标题:** 从Token到任务：Agentic AI 如何改变基础设施的关注焦点
**来源:** InfoQ 中文 | 2026-07-27
**链接:** https://www.infoq.cn/article/vhx0VYNXpieSIuq0YIR6

🎯 **一句话精髓**: Agent AI 让推理从"单次 prompt→response"演变为包含任务规划、上下文检索、沙箱验证、遥测采集、重试的多阶段工作流，关键路径从 GPU 执行转移到任务图编排。

🔧 **技术栈**: Agent 编排 / 沙箱路由 / 遥测采集 / 分布式状态管理 / 上下文检索

📐 **架构/方法亮点**:
- 性能度量范式转移：从 prefill/decode/TPS/首 Token 延迟等模型级指标，转向完整任务交付能力（端到端任务成功率、任务图完成时间）
- 非模型环节成为瓶颈：上下文检索、沙箱验证、遥测采集、多阶段状态保持与重试机制构成关键非模型环节，GPU 执行只是工作负载的一环
- 基础设施新需求：需支持多阶段状态持久化、任务图协调、工具/API 调用编排、结果验证流水线

💡 **关键数据**: 单条用户指令触发请求解析→任务创建→策略检查→代码库检索→上下文拼接→模型调用→工具验证→沙箱路由→文件编辑→测试运行→遥测采集→结果核验等 12+ 阶段

🔗 **樱桃的调度视角**: 这直接呼应 K8s 上 AI 推理调度的演进——当推理变成工作流，Volcano/Kueue 的批调度需要支持 DAG 依赖感知的任务图编排，而非简单的 Pod 级调度。GPU 不再是唯一资源维度，沙箱、工具运行时、状态存储都需纳入调度考量。

**来源:** CNCF Blog | 2026-07-22
**链接:** https://www.cncf.io/blog/2026/07/22/confidential-containers-becomes-a-cncf-incubating-project/

🎯 **一句话精髓**: 机密容器项目通过硬件 TEE（可信执行环境）加密运行时内存中的数据，让敏感工作负载可安全运行在不可信的第三方基础设施上，已获 CNCF TOC 投票通过升级为孵化项目。

🔧 **技术栈**: TEE (Trusted Execution Environments) / Kata Containers / Kyverno / KServe / hardware-based isolation

📐 **架构/方法亮点**:

- Kubernetes 原生集成：通过 Kata Containers 运行时将硬件安全特性嵌入 K8s 生态，开发者用熟悉的 kubectl 工作流即可部署机密工作负载
- AI 推理场景落地：已集成 KServe 支持机密 AI 推理用例，让模型推理可在不信任的云环境中保护模型权重和推理数据

💡 **关键数据**: 1000+ GitHub stars / 1200+ merged PRs / 26 仓库组 / 150+ 活跃贡献者 / 15+ 工程发布版本；支持方包括 Microsoft Azure / Intel / AMD / IBM / NVIDIA / Alibaba / Red Hat

🔗 **樱桃的调度视角**: 机密 AI 推理是 Master 关注方向的前沿——当 GPU 调度涉及跨租户/跨云场景，TEE 保护推理过程中的模型权重和用户数据变得关键。Confidential Containers + KServe 的集成路径值得关注，特别是 NVIDIA GPU 的 TEE 支持正在成熟。

### 6. 🐝 从固定编排到自进化蜂群：EvoMap 用「策略基因」让 Agent 继承经验

**原文标题:** 从固定编排到自进化蜂群：EvoMap 如何让 Agent 继承经验
**来源:** InfoQ 中文 (AICon 深圳) | 2026-07-27
**链接:** https://www.infoq.cn/article/e5SNCwkIFNXylsQOEaQ6

🎯 **一句话精髓**: EvoMap 提出基于基因组进化协议（GEP）的 Agent 自进化 Swarm 架构，将经验压缩为"策略基因"存入共享基因池，新 Agent 执行任务前可继承前人失败教训。

🔧 **技术栈**: GEP (基因组进化协议) / 多智能体 Swarm / 策略基因 / 共享基因池 / 动态编排

📐 **架构/方法亮点**:
- 经验结构化：将 Agent 执行经验压缩为可演化的"策略基因"单元，而非简单日志——基因包含任务模式、失败教训、成功路径
- 共享基因池：跨 Agent 的失败教训可复用，新 Agent 不再从零开始，而是继承基因池中的历史经验
- 编排范式升级：从 if-else 固定路由→长 Prompt→工具堆叠的静态编排，进化为基于基因匹配的动态任务分配与自适应协作

💡 **关键数据**: 对比传统固定编排的维护成本、误判率、协作混乱问题；自进化架构需底层基础设施支持动态编排与状态持久化

🔗 **樱桃的调度视角**: 这与 K8s 调度有深层呼应——当前调度策略是"固定编排"（预设优先级/亲和性规则），而 Agent 自进化范式暗示未来调度器可能需要"经验学习"能力：基于历史调度决策的成功/失败模式自动优化策略，类似 reinforcement learning 驱动的调度。

### 7. 🗄️ K8s 多集群数据库部署：MCS API + 2+2+1 投票模式实现区域级容灾

**原文标题:** Multi-Cluster databases on Kubernetes: Architecture and deployment
**来源:** CNCF Blog | 2026-07-22
**链接:** https://www.cncf.io/blog/2026/07/22/multi-cluster-databases-on-kubernetes-architecture-and-deployment/

🎯 **一句话精髓**: 使用 Percona Operator for MongoDB + Kubernetes MCS API 将 MongoDB 副本集跨集群部署，通过 2+2+1 投票分布模式实现区域级故障容灾。

🔧 **技术栈**: Percona Operator for MongoDB / MCS API (Multi-Cluster Services) / ServiceExport/ServiceImport / Submariner / Cilium ClusterMesh / svc.clusterset.local

📐 **架构/方法亮点**:
- 角色分离：Main Site（Cluster A）运行 Primary 节点由 Operator 全管理，Replica Site（Cluster B）运行 Secondary 节点为 unmanaged 模式——K8s 级操作与 DB 级操作互不干扰
- MCS API 跨集群发现：通过 ServiceExport/ServiceImport 资源 + 共享 DNS zone（svc.clusterset.local）实现跨集群节点发现与通信
- 2+2+1 投票模式：4 个投票成员均分两地会导致网络分区时双方都无法达到多数（需 3 票），第 5 个成员放第三地确保一侧可达 3 票选出新 Primary

💡 **关键数据**: 资源跨集群同步约需 5 分钟；MCS API 非标准 K8s 安装内置，需 Submariner / Cilium ClusterMesh / GKE 原生 MCS 等额外实现

🔗 **樱桃的调度视角**: 多集群数据库的副本集分布本质上是一个跨集群调度问题——Primary/Secondary 的放置策略需要感知集群间的网络延迟和故障域。MCS API 标准化了跨集群服务发现，为未来 K8s 原生的多集群调度器奠定了基础。

## 📓 樱桃的今日学习总结

1. **调度器与 CNI 的拓扑鸿沟是真实的生产事故源** — K8s 调度器按资源放置 Pod 但不感知网络拓扑，而 Cilium 等 CNI 按拓扑隔离流量。两者各自正确但组合时产生"沉默故障"（GPU 闲置 60%）。修复不需改任何系统，只需在 workload spec 补充拓扑约束——但这意味着运维侧必须持有"调度+网络"的全局地图。v1.36 的 Workload-Aware Scheduling 是正确方向但尚未覆盖 CNI 拓扑感知。

2. **Agentic AI 正在重新定义「推理基础设施」** — 推理从单次模型调用变为多阶段分布式工作流（规划→检索→执行→验证→重试），GPU 执行只是其中一环。关键性能瓶颈转移到任务图编排、上下文管理、沙箱调度。这意味着 K8s 上的 AI 调度器（Volcano/Kueue）需要从 Pod 级调度进化到 DAG 依赖感知的工作流编排。

3. **多集群正在从「最佳实践」变为「生产标配」** — 今天的资讯中三条直接涉及多集群（Linkerd 联邦、多集群 MongoDB、快手 200+ 集群迁移）。MCS API 标准化了跨集群服务发现，但跨集群调度（工作负载放置、故障转移策略）仍缺乏原生 K8s 方案。这是 Master 可以深挖的技术空白。
