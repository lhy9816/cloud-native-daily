### 1. 📦 多个 AI 智能体「同住」一台 EC2：AgentCore 推出持久计算

**原文标题:** Runtime instances: Persistent compute for production AI agents on Amazon Bedrock AgentCore
**来源:** InfoQ 中文 | 2026-08-24
**链接:** https://www.infoq.cn/article/2IBWc7BuB2qoGao5tlQT

🎯 **一句话精髓**: AWS 为 Bedrock AgentCore 新增了基于 EC2 的「运行时实例」计算选项，支持多智能体共享同一主机、持久会话最长 14 天，并提供 GPU 加速，弥补了原有 microVM 8 小时会话上限的不足。

🔧 **技术栈**: AWS Bedrock AgentCore / EC2 / microVM / CrewAI / LangGraph / LlamaIndex / Strands / 容器镜像

📐 **架构/方法亮点**:
- 运行时实例运行在客户账户内的托管 EC2 上，复用现有 AgentCore API、身份控制和可观测性模型，无需改变打包方式（@app.entrypoint 装饰器 + ZIP/容器镜像）
- 引入「容量提供程序」原语：定义实例系列、OS、网络和存储，AgentCore 代为预置/修补/扩缩，团队设置实例数上下限和目标利用率即可，免去直接管理 ASG/启动模板/AMI 流水线
- 推荐混合拓扑：microVM 上的编排智能体分派长时任务给实例上的工作智能体；多智能体通过共享会话目录在同一主机协作，无需 API 互调

💡 **关键数据**: 运行时实例与 microVM 的成本盈亏平衡点约为 24% 持续 CPU 利用率；会话最长 14 天（microVM 为 8 小时）；Savings Plans/预留实例折扣适用于计算费用但不适用于管理费

🔗 **樱桃的调度视角**: 这和 K8s 上的 GPU 调度问题高度同构——短时突发任务用 Serverless/microVM，长时有状态任务用持久实例，本质上就是「调度器需要感知工作负载的生命周期特征和资源亲和性」。AgentCore 的容量提供程序概念与 K8s 的 ResourceQuota + 节点亲和性异曲同工，值得 Master 在设计 GPU 调度策略时参考。

### 2. 📦 Atlassian 自动化根因分析：多信号关联的云原生故障诊断

**原文标题:** Automating root cause analysis at scale: Multi-signal correlation for cloud native incident response
**来源:** CNCF Blog | 2026-08-24
**链接:** https://www.cncf.io/blog/2026/08/24/automating-root-cause-analysis-at-scale-multi-signal-correlation-for-cloud-native-incident-response/

🎯 **一句话精髓**: Atlassian 构建了基于多信号关联（指标/日志/链路）的自动化 RCA 系统，通过时间对齐 + 服务拓扑图遍历生成排序的根因假设，让响应者跳过假设生成直接进入验证和修复阶段。

🔧 **技术栈**: OpenTelemetry / 服务依赖图 / RED 信号（Rate/Error/Duration）/ 嵌入式日志聚类 / MAD（中位数绝对偏差）/ BFS 图遍历

📐 **架构/方法亮点**:
- 五步流水线：① 基于 OpenTelemetry span 亲子关系构建实时服务依赖图、限定爆炸半径 → ② 每种信号独立异常检测（MAD + 百分位带、TraceQL 结构异常、嵌入聚类日志）→ ③ 滑动窗口时间关联（时间内聚度评分 S_temporal）→ ④ 图遍历因果方向分析（路径评分 S_path）→ ⑤ 假设生成 + 人类可读叙述
- 序列指纹去重：同一因果链在故障期间重复回放时，通过有序服务列表指纹折叠为单个 bundle 并记录回放次数，避免 100 次相同故障模式产生 100 个假设
- 模块化设计：每个异常检测器是可插拔组件，产出统一 schema 的事件，可在不重建管道的前提下从统计模型升级为 ML 模型

💡 **关键数据**: 服务依赖图将分析范围从数百服务缩减至数十服务；时间关联窗口默认 ±5 分钟；假设叙述示例中支付服务错误率 4 倍增长（基线 0.2%→观测 0.8%），p99 延迟从 340ms 飙升至 2100ms，置信度 0.87

🔗 **樱桃的调度视角**: 这里的服务依赖图遍历思路对 K8s 调度有直接启发——调度器的优先级和抢占决策如果能感知服务间拓扑关系（哪些 Pod 是上下游），就能在故障传播时做出更智能的重调度决策。Master 可以思考将 OpenTelemetry 的服务拓扑数据接入调度器的可行性。

### 3. 📦 Dogwood：给 AI 智能体工具调用立规矩的时序策略语言

**原文标题:** Amazon Open-Sources Dogwood: A Policy Language for AI Agent Tool Calls
**来源:** InfoQ 中文 | 2026-08-23
**链接:** https://www.infoq.cn/article/cwj5Ikvhqu5mKH22zKsO

🎯 **一句话精髓**: AWS 开源了 Dogwood——一种支持时序条件的智能体工具调用策略语言，可回溯查看 Agent 已执行操作的历史，弥补了 Cedar 只能逐次评估单请求、无法描述操作序列约束的缺陷。

🔧 **技术栈**: Dogwood / Cedar（CNCF 沙箱项目）/ AgentCore Policy / 度量一阶时序逻辑（MFOTL）/ MCP 工具清单 / Apache 2.0

📐 **架构/方法亮点**:
- 双子句类型：`when` 条件写 Cedar 标准策略，`when temporal` 条件读取 Agent 事件历史（工具调用请求+结果），底层将时序条件转换为 Cedar 上下文字段再决策
- 四个核心操作符基于 MFOTL 子集：`formerly`（时间窗口内是否发生过）、`count_within`（发生次数）、`count_distinct_within`（不同值计数）、`sum_within`（累计总额），通过 `bind` 命名聚合结果与当前请求比较
- 关键正确性陷阱演示：三笔并发 $2000 转账在任一笔完成前到达——对响应求和的速率限制看不到在途金额而全部放行，对请求求和的相同策略则拒绝第三笔，仅一词之差

💡 **关键数据**: 任何有效 Cedar 策略都是有效 Dogwood 策略（向后兼容）；时序条件不支持 Cedar 自动推理分析工具（形式化分析能力丢失）；由 Aurora DSQL 发布者 Marc Brooker 等人共同撰写

🔗 **樱桃的调度视角**: Dogwood 解决的「操作序列约束」问题与 K8s 准入控制的痛点完全一致——Kyverno/OPA 目前也是逐请求评估，无法表达「同一命名空间在过去 5 分钟内已创建超过 10 个 Pod 就拒绝」这类时序约束。Dogwood 的时序逻辑思路对 K8s 策略引擎演进有参考价值。

### 4. 📦 Netflix 开源因果推理智能代理工作流

**原文标题:** Netflix Open-Sources Agentic Workflow for Causal Inference
**来源:** InfoQ 中文 | 2026-08-24
**链接:** https://www.infoq.cn/article/4h2jb2eOcBrP5AG5hLYt

🎯 **一句话精髓**: Netflix 开源了一个用于观察性因果推断（OCI）的智能代理工作流，采用「执行者-评审者」双代理循环，自动完成敏感性分析等重复性任务，将问题构建和结果评估留给人类。

🔧 **技术栈**: Python / Jupyter Notebook / 因果推断（目标试验仿真）/ Actor-Critic 循环 / Claude LLM / ACIC 竞赛数据集 / GitHub 开源

📐 **架构/方法亮点**:
- 工作流设计：人类分析师创建基于模板的 Jupyter Notebook + 分析计划 → 执行代理生成规格说明、填参数、运行 Notebook → 评审代理审查输出、评级（not_satisfactory / satisfactory_with_caveats / fully_satisfactory）、提出修改建议 → 循环迭代
- 案例研究：评估新型娱乐内容对用户留存率的影响，干预变量为「接触天数」、结果指标为「2 个月留存率」；OCI 代理估算效果值仅为基线（Claude 直接做线性回归）的 25%，评审代理发现早期采用者偏差和安慰剂测试失败
- 流程审计 + 人工监督：代理发布计划、规格说明、流程图和手册供人类检查，两个代理分工（一个运行分析、一个评审），在没有真实标注数据的情况下评估代理表现

💡 **关键数据**: OCI 代理估算效果值为基线的 25%（基线为 Claude 直接线性回归）；在大西洋因果推断会议（ACIC）竞赛数据集上评估，与基准系统「非常具有竞争力」

🔗 **樱桃的调度视角**: 「执行者-评审者」双代理模式对 K8s 运维自动化有启发——可以设想一个调度审计代理定期评审调度决策（如抢占选择、 bin-packing 结果），输出改进建议。Netflix 的流程审计思路（每步留痕、可复查）也适用于调度器的决策日志设计。

### 5. 📦 Kyverno 是平台原语，而非安全工具

**原文标题:** Kyverno is a platform primitive, not a security tool
**来源:** CNCF Blog | 2026-08-19
**链接:** https://www.cncf.io/blog/2026/08/19/kyverno-is-a-platform-primitive-not-a-security-tool/

🎯 **一句话精髓**: 作者 argues Kyverno 应被重新定义为 K8s 平台原语（类似 Pod/Service 的构建块），而非仅用于安全的策略引擎——其 validate/mutate/generate/verify-images 四大能力中三个是构造性的，但多数组织只用了 validate（拦截）。

🔧 **技术栈**: Kyverno / K8s 准入控制 / CEL（通用表达式语言）/ Pod Security Standards / NetworkPolicy / ResourceQuota / Crossplane

📐 **架构/方法亮点**:
- 平台原语四属性框架：① 抽象复杂度（开发者无需理解底层机制）② 提供保证（使用即满足特定属性）③ 可组合（与其他原语构建更高级抽象）④ 自助服务（从平台获取而非提工单）
- 实战用例：Namespace 自动配置（创建 ns 即生成默认 NetworkPolicy/ResourceQuota/LimitRange/RoleBinding）、Sidecar 注入（观测 Agent/Mesh Proxy 在准入时 mutate 进 Pod spec）、镜像引用重写（nginx:1.25 → mirror.internal/nginx:1.25 在准入时自动完成）、默认资源请求注入
- 核心论点：当心智模型是「策略=拒绝」时，只用了工具 1/4 的能力；mutation 和 generation 是构造性动词，能「让正确的事情自动发生」

💡 **关键数据**: Kyverno 四大能力中 3/4 是构造性的（mutate/generate/verify-images），但多数组织部署的全是 validate 策略

🔗 **樱桃的调度视角**: 这篇文章对 K8s 调度/资源管理的启示在于——调度策略不应只是「拒绝坏 Pod」，更应主动「构造好 Pod」。比如通过 mutate 注入合理的 resource requests/limits、通过 generate 为关键工作负载自动创建 PriorityClass 和 PodDisruptionBudget，让调度器在做决策时有更完整的上下文。

### 6. 📦 Cloudflare 重新评估 Workers 上的远程 Spectre 攻击

**原文标题:** A revisit of remote Spectre attacks on Cloudflare Workers
**来源:** Cloudflare Blog | 2026-08-19
**链接:** https://blog.cloudflare.com/revisiting-spectre-attacks-on-workers/

🎯 **一句话精髓**: Cloudflare 在 2024-2025 年重新评估了针对 Workers 的远程 Spectre 攻击，在生产环境中可靠地以 12 bit/s、99% 准确率泄露数据，随后通过改进 DyPrIs、集成 V8 Sandbox 和进程内隔离机制来加固防御。

🔧 **技术栈**: V8 Isolates / Spectre / 推测执行 / V8 Sandbox / Dynamic Process Isolation (DyPrIs) / Linux namespaces / seccomp / Cap'n Proto RPC

📐 **架构/方法亮点**:
- 新攻击原语：推测类型混淆 Spectre gadget——通过 `obj instanceof ObjP` 类型检查的分支预测训练，在 CPU 推测执行时跟随攻击者控制的 64 位指针进行越界读取，将单个 bit 编码到 cache 中
- 远程计时器 + 共置：Workers 运行时冻结了 `Date.now()` 和 `performance.now()`、禁用 SharedArrayBuffer，但研究者通过远程计时原语和共置策略绕过限制
- 防御纵深：发现 DyPrIs 实现缺陷后，集成 V8 Sandbox（指针压缩下 TypedArray 仍存储原始 64 位指针的漏洞被修补）+ 进程内隔离机制，将内存泄露攻击风险降至最低

💡 **关键数据**: 生产环境中可靠泄露速率达 12 bit/s，准确率 99%；论文已在 arXiv 发表（arXiv:2608.17043）；过去三年未发现实际利用迹象

🔗 **樱桃的调度视角**: 这对 K8s 多租户隔离有警示意义——容器运行时（containerd/CRI-O）共享内核，类似 V8 Isolates 共享进程内存。如果 Master 在设计 GPU 共享调度（如时间片/MPS），需要考虑侧信道攻击风险，特别是在多租户场景下。

### 7. 📦 DynamoDB 原生支持向量搜索：向量数据库要被取代？

**原文标题:** Amazon DynamoDB introduces native vector search for AI applications
**来源:** InfoQ 中文 | 2026-08-23
**链接:** https://www.infoq.cn/article/9YicfQysexJdmx11xG4m

🎯 **一句话精髓**: Amazon DynamoDB 推出原生向量搜索功能，允许开发者将嵌入向量与应用数据存储在同一张表中，直接运行近似最近邻查询，无需部署独立的向量数据库。

🔧 **技术栈**: Amazon DynamoDB / 向量嵌入 / 近似最近邻查询（ANN）/ SearchVectors API / Amazon Bedrock Titan Embeddings / Cohere Embed / OpenAI Embeddings

📐 **架构/方法亮点**:

🔗 **樱桃的调度视角**: 向量搜索内嵌到 OLTP 数据库是 AI 推理基础设施的一个趋势——如果 Master 在 K8s 上部署 RAG 系统时可以考虑减少一个微服务依赖，直接用 DynamoDB 的向量搜索替代独立向量数据库组件，降低调度和运维复杂度。

### 8. 📦 Cloudflare Agent Tracing：Agent 可观测性的新范式

**原文标题:** Cloudflare Adds Agent Tracing, with Truncation Limits and Uneven Payload Defaults
**来源:** InfoQ 中文 | 2026-08-22
**链接:** https://www.infoq.cn/article/IBYDTeu3rse9tH3549wf

🎯 **一句话精髓**: Cloudflare 推出 Agent Tracing——在 Workers Tracing 基础上增加 Agent 级别 Span（调用/模型/工具/审批），解决「Agent 返回 HTTP 200 但行为异常」的观测盲区，并遵循 OpenTelemetry GenAI 语义约定。

🔧 **技术栈**: Cloudflare Workers / OpenTelemetry GenAI 语义约定 / Workers Custom Spans API / OTLP Endpoint / Think / Flue / AI SDK (wrapAISDK)

📐 **架构/方法亮点**:
- Trace 瀑布流结构：每轮交互生成一条 Trace `invoke_agent → chat(model) → execute_tool(tool) → tool_approval(tool)`，Subagent 工作嵌套在父操作下，覆盖多层级
- 三字段关联：Agent name（逻辑实现）+ Agent ID（具体实例）+ Conversation ID（会话），Cloudflare 特别提醒不要根据请求/用户 ID 动态生成 Agent name，否则 Dashboard 会出现大量不同 Agent
- Session Replay：跨多轮交互重组已记录的会话（消息/推理/工具调用/Subagent 活动），但明确指出只重放不重新执行 Agent

💡 **关键数据**: Beta 期间免费；2026-10-01 起 Workers Free 每天 20 万次 Event（保留 3 天），Workers Paid 每月 2000 万次（保留 7 天），超出部分 $0.60/百万次；Payload 受 Span 大小限制可能被截断

🔗 **樱桃的调度视角**: Agent Tracing 遵循 OpenTelemetry GenAI 语义约定并支持导出到任意 OTLP Endpoint——这意味着 Master 在 K8s 上部署的 AI 推理服务也可以采用同样的 Span 结构，将模型调用、Token 消耗、工具执行纳入统一可观测性体系，为调度器提供更丰富的负载画像。

## 📓 樱桃的今日学习总结

1. **AI Agent 基础设施正在分化为两层架构** - AgentCore 的 microVM + EC2 混合拓扑与 K8s 的 Serverless + 长时实例分层调度如出一辙。核心设计原则是：短时突发任务用快速启动的轻量级运行时，长时有状态任务用持久计算资源，通过共享文件系统/会话目录实现多 Agent 协作。这对 Master 设计 GPU 调度策略时区分「推理请求」和「推理会话」有直接参考价值。

2. **时序策略是从「拦截」走向「治理」的关键** - Dogwood 的时序条件和 Kyverno 的「平台原语」论实际上指向同一个趋势：策略引擎正在从单次请求的二元拦截（allow/deny）进化为能感知历史上下文、能构造性变更资源的智能治理层。K8s 准入控制的未来不是更严格地「拒绝」，而是更聪明地「让正确的事情自动发生」。

3. **Agent 可观测性需要自己的遥测层** - Cloudflare Agent Tracing 和 Atlassian RCA 都揭示了一个共同教训：基础设施层遥测（HTTP 200、CPU 利用率）无法解释应用层行为（选错工具、过时上下文、Token 浪费）。OpenTelemetry GenAI 语义约定正在成为标准，Master 在 K8s 上部署 AI 推理服务时应尽早采用这套规范，为调度优化和故障诊断积累数据基础。
