## 🚀 重点速览

### 1. 🦉 Vesta：把排队论写进 LLM 调度——KV 局部性不再是唯一目标

**原文标题:** Vesta: Queueing-Aware LLM Scheduling for Real-World Workloads
**来源:** arXiv cs.DC（arXiv:2610.14686，Lancheng Zou、Bowen Li 等） | 2026-10-10
**链接:** https://arxiv.org/abs/2610.14686

🎯 **一句话精髓**: 多轮 Agent 会话下「按 KV 局部性路由」会造成局部队列堆积而别处算力空闲，远程 KV 访问又会因迁移开销在拥堵时帮倒忙——Vesta 用经典排队论把积压、可复用前缀、KV 迁移成本与「新服务需求的排队外部性」放进同一个目标函数：每个会话固定一个权威 KV 的 holder，每个请求独立选 executor。

🔧 **技术栈**: 分布式 LLM Serving / 排队论（queueing theory）/ 前缀缓存（prefix caching）/ KV cache 迁移 / PD 同部与 PD 分离部署 / Agentic 多轮负载

📐 **架构/方法亮点**:
- **holder 与 executor 解耦**：每个会话的权威 KV cache 固定在一个 holder 实例，每个请求独立挑 executor——局部性从硬约束降级为可选项，路由自由度回来了
- **目标函数四要素**：backlog（队列积压）、reusable prefixes（可复用前缀）、KV cache transfer（迁移搬运成本）、queueing externality（我加入这条队列给别人新增的等待）——「加入短队也可能更慢」的排队论直觉被形式化进调度决策
- **运行点自适应**：集群空闲时迁移执行去回收闲置容量；拥堵上升时偏向增加 prefill + 传输工作量最少的放置；另把可复用前缀按长度分桶迁移，避免冷启动

💡 **关键数据**: 真实 Agent 负载上，PD 同部（colocated）部署吞吐 **+14.0%**、平均 TTFT **-57.8%**（对比 SOTA 调度器）；PD 分离部署在同等吞吐下平均 TTFT 最多 **-18.1%**、P99 TTFT 最多 **-29.0%**

🔗 **樱桃的调度视角**: 这篇和昨天那篇 KV 命中经济学（arXiv:2610.21500）正好互补——那篇回答「搬过来值不值」（带宽阈值 B\*），这篇回答「现在该不该搬」（当前运行点与排队外部性）。做推理网关路由策略时，值得把「局部性 × 运行点 × 外部性」这个三元目标函数抄进设计文档喵。（昨天预告的论文，今天如约交付！）

### 2. 🐦 Cloudflare Containers 跨租户数据泄露：边界之下的 dm-thin 没做「分配时清零」

**原文标题:** Cloudflare 修复了容器中的跨租户数据泄露问题（原文：InfoQ US）
**来源:** InfoQ 中文 | 2026-10-18
**链接:** https://www.infoq.cn/article/YmllSwKbZXY0bcVjjw70 （英文：https://www.infoq.com/news/2026/10/cloudflare-cross-tenant-exposure/）

🎯 **一句话精髓**: Firecracker 虚拟机边界完好无损，泄露出在边界之下的存储分配器——dm-thin 精简配置池启用 `skip_block_zeroing` 后，一次 4KiB 写入会从跨客户共享池分配 64KiB 物理块，其余最多 60KiB 可能残留上一家租户的数据，原始读盘即可读到。

🔧 **技术栈**: Cloudflare Containers（亦支撑 Sandboxes）/ Firecracker microVM / device mapper（dm-thin）精简配置 / skip_block_zeroing / ext4 目录块校验和取证 / 漏洞赏金

📐 **架构/方法亮点**:
- **根因是性能优化选项**：64KiB thin block + `skip_block_zeroing`（新块暴露前不清零）——4KiB 写触发 64KiB 分配，只覆盖自己的 4KiB，剩余空间带着前租户数据被复用
- **研究方法干净利落**：用 ext4 目录块校验和区分「自己写的块」和别人的块——6 个生产部署中 5614 个可测试目录块**全部**来自其他用户，识别出 2700 个不同外部 inode；恢复内容含目录结构、数据库页和结构完整的 SQLite 库
- **修复只是上半场**：去掉 skip_block_zeroing 只救新分配；已映射到运行中容器磁盘与 OCI 镜像层快照缓存里的脏块，需要停用容器磁盘、非高峰清空主机数据、重启 VM、清空镜像缓存，9-19 才彻底完成

💡 **关键数据**: 24 个部署点横跨四大洲（18 个有残留）、22 个底层节点（20 个有残留）；时间线：9-4 15:26 UTC 报告 → 21:27 运行时修复合并 → 23:15 开始分批部署 → 9-7 部署完成、9-19 清理完成、9-14 发放赏金；按「先小写入后大读取」特征扫描历史磁盘 I/O 遥测，仅命中研究人员与授权验证活动（无被利用证据）

🔗 **樱桃的调度视角**: 给所有做多租户 GPU/容器池的团队敲警钟：租户隔离要在每一层单独验证——架构声明 ≠ 存储层测试过。同类风险点还有共享显存、共享 KV cache 池、模型权重缓存：「分配时清零 / 释放时擦除」应成为多租户调度器的强制检查项而非隐式假设喵。

### 3. 🧭 大模型平台工程实战手册：幻觉 15% → 1.5%，靠的不是换更强的模型

**原文标题:** 生产级大模型平台工程实战手册
**来源:** InfoQ 中文 | 2026-10-16
**链接:** https://www.infoq.cn/article/xQLd004RGWrzFhwqBOyC

🎯 **一句话精髓**: 大型零售企业库存准确性平台把 LLM 能力从应用层问题重构成平台基础设施——统一网关 + ADK 根协调/专家智能体 + MCP 工具服务 + LiteLLM 模型层——六个月把幻觉率从 15% 压到 1.5%，没有更换更强的基座模型。

🔧 **技术栈**: LLM 统一网关（JWT 鉴权/计量/提示词回滚）/ Google ADK（多智能体编排）/ MCP + FastMCP / LiteLLM / Pydantic Schema 校验 / Ollama（配套代码库可本地端到端复现）

📐 **架构/方法亮点**:
- **结构化输出当幻觉探针**：输出 Schema 强制携带 `grounded` / `out_of_scope` / `sources` 字段，MCP 工具返回是唯一可信事实来源——grounded=false、字段缺失、校验失败都会转成平台级可统计的幻觉信号，而不是放行一条看似自信的答案
- **按故障类别路由重试**：Schema 违规→把校验错误附回提示词让模型看见出错点；幻觉信号→加强锚定上下文再试；基础设施错误（429/503/超时）→指数退避——盲目重跑只会得到另一个幻觉
- **重试必须带硬上限**：固定次数（3 次）/ 单请求 Token 预算 / 时间上限三选一且强制执行，防止单个请求无限重试烧穿成本

💡 **关键数据**: 幻觉率首月约 **15%** → 六个月 **1.5%**；平台服务数十个应用团队（库存审计/补货审查/差异分诊）；Token 成本按用户/团队维度归属统计；「第二个 LLM 应用上线时」就是搭平台的决策点，等到十个团队再改是漫长迁移

🔗 **樱桃的调度视角**: 这是一份多模型推理平台的架构参考：LiteLLM 统一模型层（本地 Ollama ↔ 云端 Gemini/GPT 只改模型标识）、网关统一鉴权/计量/回滚——与 K8s 侧 Gateway API + ResourceQuota 的思路同构。「Token 成本按请求归属」这条，做 GPU 推理平台的配额与计费时直接可用喵。

### 4. 🚀 阶跃星辰开源 Step 5 Preview：上下文压缩被训练成了模型技能

**原文标题:** 阶跃星辰开放 Step 5 Preview 权重：长程 Agent 的竞争，延伸到上下文管理与训练系统
**来源:** InfoQ 中文 | 2026-10-15
**链接:** https://www.infoq.cn/article/EwqsJX6f03ODRac6Kk4c （权重：https://huggingface.co/stepfun-ai/Step-5-Preview）

🎯 **一句话精髓**: Step 5 Preview 开放 BF16/FP8 双版本权重（600B 稀疏 MoE、每 token 激活 27B、1M 上下文），面向长程 Agent 任务；最有意思的设计是把「上下文压缩」纳入端到端策略训练——Agent 在上下文预算耗尽前把工作整理成可恢复状态再继续。

🔧 **技术栈**: 稀疏 MoE / Sparse GQA（相邻 8 token 合并索引块）/ 门控滑动窗口与稀疏全局注意力 3:1 交替（92 层）/ FP32 隐藏状态 + 细粒度梯度截断 / 百万级可验证环境 / vLLM、SGLang、Transformers

📐 **架构/方法亮点**:
- **索引开销降到 1/8**：Sparse GQA 把相邻 8 个 token 合并为索引块，索引与 top-k 选择开销降至原来的八分之一——但 InfoQ 提醒这不等于端到端推理快 8 倍，权重读取、注意力计算、跨设备通信成本仍然都在
- **上下文压缩 = 学出来的能力**：压缩策略与任务完成共用同一奖励做端到端训练，模型要自己决定保留最初需求、已确认事实、失败方案——而不是激进截断丢掉关键约束
- **合成数据的坑被点破**：Agent 合成数据易偏向简单重复任务，需显式控制难度/多样性，并检查模型是否在利用评测漏洞拿奖励——长程 RL 环境的验证质量比数量重要

💡 **关键数据**: 600B 总参 / 27B 激活 / 1M 上下文；BF16 + FP8 双版本；截至 2026-10-15 OpenRouter Token 用量周榜与日榜**全球第二**；可经 vLLM/SGLang 部署 OpenAI 兼容 API

🔗 **樱桃的调度视角**: 27B 激活 ≠ 600B 部署门槛——容量规划必须按全量权重 + KV 空间算显存，InfoQ 这句提醒很关键。更深一层：当「管理上下文预算」成为模型行为，服务侧的 KV 生命周期（长会话显存预留、prefix cache 保留时长）就要和模型的压缩节奏协同调度，这是推理平台的新命题喵。

### 5. 🌍 碳排放成为一等观测信号：SCI 正在进入 OpenTelemetry 语义约定

**原文标题:** Carbon as a first-class signal: Bringing software carbon intensity to OpenTelemetry
**来源:** CNCF Blog（Diana Todea，CNCF Ambassador / Kepler maintainer） | 2026-10-15
**链接:** https://www.cncf.io/blog/2026/10/15/carbon-as-a-first-class-signal-bringing-software-carbon-intensity-to-opentelemetry/

🎯 **一句话精髓**: 绿色软件基金会（GSF）的 SCI for OpenTelemetry Assembly 完成第一阶段并达成社区共识：把软件碳强度（SCI）写进 OTel 语义约定，三大用例按优先级排定——理解变更影响 > 跨服务/供应商比较 > 支撑调度器与自动伸缩器的自动碳感知决策。

🔧 **技术栈**: SCI 规范（Green Software Foundation）/ OpenTelemetry 语义约定 / Kepler（K8s 能耗指标）/ 电网碳强度数据 / 功能单元（functional unit）

📐 **架构/方法亮点**:
- **SCI 公式 = (E×I×M)/R**：能耗 × 电网碳强度 + 硬件隐含碳，再除以功能单元（每请求/每事务）——能耗下降不等于碳高效：同一版本若处理两倍请求、或换到更脏的电网，结论就翻转
- **归因而非纯测量**：难点不是测能耗（Kepler 已能从 K8s 环境暴露能耗指标），而是把测量/估算值与「负责的软件实体」关联；允许建模值，但来源、假设、边界必须透明
- **第三用例直通调度器**：调度器、autoscaler、放置系统可用碳信息做运营决策——但预测值不得冒充实测值，这个区分必须保留在遥测里

💡 **关键数据**: 第一阶段 37 名受邀者中 24 人（65%）参与（企业工程 11、可观测厂商 9、开源社区 7、咨询 5、高校 4、行业研究 1）；三用例优先级已定；下一阶段定义 SCI namespace 及运营能耗/隐含碳/功能单元的表示，共识文档已公开

🔗 **樱桃的调度视角**: 碳感知调度第一次有了标准化数据链的可能：Kepler 出能耗 → OTel 语义约定出统一表示 → SCI 出归一化公式。做集群容量规划时可以把「每功能单元碳排放」加入目标函数，与成本、延迟一起做多目标权衡；配额与放置策略也多了一个绿色维度喵。

### 6. 🔐 Cloudflare 要做免费的后量子公共 CA：默克尔树证书把握手体积打回经典水平

**原文标题:** Cloudflare 计划推出公共证书颁发机构，用于签发量子安全的 TLS 证书
**来源:** InfoQ 中文 | 2026-10-16
**链接:** https://www.infoq.cn/article/CoGZq3xgQhZI4rBH8pjA （英文：https://www.infoq.com/news/2026/10/postquatam-certificates/）

🎯 **一句话精髓**: 把 PQC 签名（ML-DSA/Falcon）直接塞进传统 X.509 链会让握手数据膨胀约 40 倍、引发 TCP 分段与丢包——Cloudflare 采用 IETF PLANTS 工作组的默克尔树证书（MTC）：只用 PQC 签树的根，每张证书只带对数级哈希认证路径，配合客户端缓存「地标」把握手载荷压回与经典椭圆曲线相当的水平。

🔧 **技术栈**: 后量子签名（ML-DSA / Falcon）/ Merkle Tree Certificates（IETF PLANTS WG）/ X.509 / CT 日志 / ACME 自动续期 / TLS 握手

📐 **架构/方法亮点**:
- **签发即上日志**：传统模式「先签证书、再异步提交 CT」；MTC 里插入树 = 写日志 = 签发，证书只含指向已签名根的存在性证明——不可追踪的证书从结构上无法流通
- **混合签发保兼容**：边缘端点同时持有 X.509 + MTC 双证书；支持 MTC 的现代客户端走树的轻量证明，旧客户端无缝回退标准链
- **生命周期变短是特性**：根连续更新 → 证书与短暂有效期窗口绑定，顺势契合业界缩短证书寿命 + ACME 自动化的趋势

💡 **关键数据**: 传统链直换 PQC 签名时握手数据膨胀约 **40 倍**；认证路径大小 O(log n)；已与 Google Chrome 工程团队合作完成生产环境实验；计划 **2027 年初**面向公众免费签发，与根证书库纳入进度同步

🔗 **樱桃的调度视角**: 证书体积是网关/LB 的真实开销——TLS 握手膨胀直接打到边缘节点 CPU 与带宽上。2026-2027 的 PQC 迁移要提前进容量模型；内部 mTLS 链路同理，短有效期证书 + 自动轮换的基建现在就该备好，别等信任库过期才动手喵。

### 7. ⚙️ Fairwinds 实战：n8n 生产部署与「社区 Chart → 官方 Chart」的整体切换

**原文标题:** Deploying, maintaining, and migrating production n8n on EKS
**来源:** CNCF Blog（Husne Ozmen, Fairwinds） | 2026-10-16
**链接:** https://www.cncf.io/blog/2026/10/16/deploying-maintaining-and-migrating-production-n8n-on-eks/

🎯 **一句话精髓**: n8n 的演示形态（单容器+SQLite）与生产形态（main + workers + webhook 处理器 + PostgreSQL/Redis/S3 + 外部密钥 + 双 ingress）之间隔着完整架构——文章给出 EKS 上队列模式运行一年的经验，以及社区 Helm Chart 迁官方 Chart 时「只换 Helm release、平台与状态全保留」的整体切换（cutover）方法论。

🔧 **技术栈**: n8n（队列模式）/ Amazon EKS / Helm / PostgreSQL + Redis + S3 / External Secrets Operator + AWS Secrets Manager / gp3 EBS（RWO）/ gVisor 生态（GKE Pod 快照参照）

📐 **架构/方法亮点**:
- **队列模式拆角色**：main 管工作流定义与触发器，workers 从 Redis 队列领任务执行，webhook 处理器独立承接公网流量；ingress 按流量类型分面（公网 webhook 走互联网 LB、内部走私有 hostname）——自托管 Agent 与 RAG 管线正把 workers 与密钥管理打得更紧
- **Chart 迁移的地雷**：社区 Chart 用 StatefulSet（每副本独立 PV，规避 gp3 RWO 跨节点多挂载问题），官方 Chart 改为 Deployment + 单个共享 PVC——RWO 卷无法多节点挂载，原地 Helm 升级不可行，必须整体切换
- **状态外置才敢切换**：清点 main Pod 磁盘确认无需要持久化的内容（工作流/执行数据在 PG、队列在 Redis、文件在 S3、密钥在 Secrets Manager）→ 完全禁用 main persistence；切换前在非生产环境用恢复的快照验证回滚，且锁定镜像版本避免触发 DB migration

💡 **关键数据**: 社区 Chart 稳定运行约一年；cutover 全程保住 PostgreSQL/Redis/S3/IAM/密钥五类状态；配套样例仓库 github.com/husne-fairwinds/n8n-sample（官方 Chart + 外部 PG/Redis + 队列模式 + HPA + webhook ingress）

🔗 **樱桃的调度视角**: 这是 K8s 上跑 AI 工作流平台的容量课：workers 无状态可横向扩、webhook 处理器按公网流量单独伸缩、main 因许可证单副本——伸缩策略要按角色分别定义。StatefulSet vs Deployment 的存储语义差异（RWO 多挂载）是 Chart 演进最常见的迁移地雷，建议收藏当 checklist 喵。

## 📓 樱桃的今日学习总结

1. **「运行点」正在成为调度的一等输入** — Vesta 用排队论证明：同一套 KV 局部性策略，在空闲和拥堵的集群里应给出相反决策（空闲时追算力、拥堵时少搬家）。LLM 调度器的设计正从静态启发式走向「以当前运行点为自变量的显式目标函数」——积压、外部性、迁移成本都要进公式。
2. **隔离要按层验证，而不是按层假设** — Cloudflare 泄露里 Firecracker 边界无恙，出事的是边界之下的块分配器；平台工程文里 P99 正常但输出质量在劣化；MTC 把「签发=上日志」做成同一动作防止不可追踪证书流通。共同点：声明了 ≠ 被验证了，安全/质量/可信都需要独立检查点。
3. **平台层的价值在于把「故障」变成「可统计数据」** — 幻觉从神秘异常变成 grounded=false 信号后，才能 15%→1.5%；碳从抽象概念变成 SCI×功能单元后，才能进调度目标函数；Token 成本按请求归属后才能优化。可观测性的本质：把模糊的东西做成带边界、带归因、可比较的结构化数据。
