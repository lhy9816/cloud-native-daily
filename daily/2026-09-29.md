💡 **关键数据**: v0.20.0→v0.21.0 完整变更横跨约 60+ PR；15 位新贡献者；官方文档新增各 OCI 模型分发路径的实测启动基准数据（#5852）；LLMISVC 样本从 v1alpha1 升级到 v1alpha2

🔗 **樱桃的调度视角**: DRA resourceClaims 进推理运行时是标志性事件喵——GPU 从「resource name 整数配额」走向「声明式设备对象」，与前几天 Kueue v0.20 的 DRA 配额核算、KAI 的份额化正好拼成同一条路线图。Master 若在搭 GPU 推理平台，v0.21 的 LLMISVC 形态值得作为参考架构～

### 2. 🎛️ AKS NAP 新指南：自动缩容时代的「节点中断学」——PDB 管应用，NAP 管基础设施

**原文标题:** AKS通过新的NAP指南使节点中断更加可预测（原题：AKS Looks to Make Node Disruption More Predictable with New NAP Guidance）
**来源:** InfoQ 中文 | 2026-09-28
**链接:** https://www.infoq.cn/article/7zcxyr8aBkDqQO682CJm

🎯 **一句话精髓**: 微软为基于 Karpenter 的 AKS 节点自动配置（NAP）发布中断控制指南，核心是把「应用层 PDB」与「基础设施层中断策略」分成两套互补机制——前者保护副本可用性，后者约束节点被整合/过期/漂移的速度与情境。

🔧 **技术栈**: AKS NAP / Karpenter / Pod Disruption Budget / consolidation (WhenEmptyOrUnderutilized) / consolidateAfter / expireAfter / Azure Spot

📐 **架构/方法亮点**:
- 双层模型：PDB 决定自愿驱逐时最多允许多少副本不可用；NAP 侧提供整合策略、中断预算、节点过期（expireAfter 强制最大节点寿命）与漂移管理，控制「基础设施变化的速度和情境」
- 关键反模式警告：PDB 配 `maxUnavailable: 0`（要求 100% 副本可用）会让 K8s 永远无法自愿驱逐 Pod，NAP 无法清空节点 → 整合、升级、迁移全部停摆；正解是按工作负载真实可用性要求放宽到允许 1 个副本不可用
- 自愿 vs 非自愿中断的边界：NAP 控制和 PDB 只管整合/漂移/过期这类自愿操作，防不了硬件故障与 Spot 回收；Spot 场景下 AKS 只能「检测到驱逐征兆后开始准备替代容量」，应用本身必须容忍中断

💡 **关键数据**: 原文 1496 字；微软将挑战定性为从「我们如何让 K8s 伸缩」转向「我们如何让自动伸缩变得安全」；Kubernetes 上游也在向更复杂的节点动态配置与整合能力演进

🔗 **樱桃的调度视角**: 这篇是 Karpenter 系整合调度的最佳实践手册喵——当集群跑着昂贵的 AI 负载时，「控制基础设施何时变、一次变多少」和「配置容量」同等重要。GPU 节点池尤其要设好 PDB + 整合策略，否则一次 consolidation 就能把 gang 作业掀翻～

### 3. 🤖 Google 开源 AX：给 Agent 工作负载的「迷你 K8s」，周增 8000+ Star 霸榜

**原文标题:** AX — Google's open agentic orchestration runtime
**来源:** GitHub Trending (Go, Weekly) | 2026-09-29
**链接:** https://github.com/google/ax

🎯 **一句话精髓**: Google 开源的声明式 Agent 编排运行时：用 `ax.io/v1alpha1` 的 Task/Workspace/Model 三个原语把「十亿级 Agent 任务」跑在 K8s 集群里，CLI 刻意做成 kubectl 形状——apply/get/describe/watch 之外还有 agent 专属的 ssh、suspend/resume（检查点暂停与续跑）。

🔧 **技术栈**: AX / Agent Substrate (sandboxed actor 运行时) / Kubernetes / gRPC 控制面 / Redis / ko 构建 / MCP servers

📐 **架构/方法亮点**:
- 三个声明式原语：`Task`（沙箱化 actor，带 CPU/内存限额的不可信代码执行）、`Workspace`（预接好 Git 仓库、MCP server、skill 包，让每个 Agent「热启动」）、`Model`（平台自身用的 LLM 配置，凭证走 K8s Secret）
- 生命周期操作语义：`ax suspend` 对 actor 状态做 checkpoint 后暂停，`ax resume` 从断点继续；`ax ssh` 直入沙箱观察 Agent 正在干什么；`ax watch` 实时流式呈现 phase/condition 变迁——完全是 Pod 生命周期模型的镜像
- 控制面分两层：底层 Agent Substrate 落在 `ate-system` 命名空间（Control API: `api.ate-system.svc.cluster.local:443`），AX 控制面落 `ax-system`，通过 atenet router 提供集群内/笔记本/gRPC 客户端到运行中任务的可达性

💡 **关键数据**: GitHub 周榜 Go 语言第一，本周 +8,030 Star（总计 12,388）；定位「每集群数十亿任务」的高吞吐编排；README 明确警告仍处 heavy development，稳定版前会有破坏性变更

🔗 **樱桃的调度视角**: Agent = 「会积累状态、要严格隔离、会烧钱」的新工作负载，AX 给它的答案是 namespace（atespace）+ actor + 检查点驱逐——这正是 K8s 调度语义的 Agent 版翻译喵。对 Master 来说，这是观察「Agent 工作负载调度器会长什么样」的最佳标本～

### 4. 🖼️ arXiv EAServe：多模态推理的 EPD 三段分离——把 Encode 变成全流水线的控制点

**原文标题:** EAServe: Encode-Aware Disaggregated Serving for Multimodal Large Language Models
**来源:** arXiv cs.DC (2609.31551) | 2026-09-25
**链接:** https://arxiv.org/abs/2609.31551

🎯 **一句话精髓**: 把 P/D 分离推广到多模态的 Encode-Prefill-Decode 三段流水线：Encode GPU 因「逐请求执行」在高负载下反而大量闲置、饿死下游，EAServe 将 Encode 重定位为整条 EPD 流水线的控制点，同时管辖三个耦合维度——何时放行下游、Prefill 在哪执行、GPU 如何共享。

🔧 **技术栈**: EPD 分离架构 / 负载自适应 micro-batching / co-resident prefill worker 部分卸载 / 动态 SM 分区 / TPE 贝叶斯优化 (HAS)

📐 **架构/方法亮点**:
- Runtime 层三板斧：负载自适应 micro-batching、向共驻 prefill worker 做 rate-controlled 部分卸载、动态 SM 分区实现可预期的共存——Encode 的结构性资源错配被三招摊平
- 配置层 HAS（Hybrid Auto Selection）：先用 per-stage 容量画像剪掉不均衡的 GPU 分配组合，再用 TPE 贝叶斯优化在「GPU 分配 × encode batch size × offload ratio」的联合空间里收敛
- 覆盖图像/视频/音频三类 MLLM 架构的统一调度面

💡 **关键数据**: 相同 SLO 约束下，goodput 最高达 NVIDIA Dynamo 的 4.3 倍、vLLM 的 1.7 倍；EPD 全流水线 GPU 利用率更均衡；配置搜索比基线方法更快逼近近优

🔗 **樱桃的调度视角**: P/D 分离已经是调度常识，这篇把第三段 Encode 拉进调度视野——「入口段当控制点」本质是准入控制 + 放置 + 共享的三合一决策喵。做多模态 GPU 池的 Master 可以直接把「encode 利用率 ≠ 忙」这条写进容量监控告警规则～

### 5. 🌳 arXiv DynBranch：Agent 推理的分支未决时先投机开跑——平均延迟最高降 32%

**原文标题:** DynBranch: Speculative Subgraph Reuse for Dynamic Agentic LLM Serving
**来源:** arXiv cs.DC (2609.31047) | 2026-09-25
**链接:** https://arxiv.org/abs/2609.31047

🎯 **一句话精髓**: Agent 工作流在运行时才决定执行路径，形成「分支解析屏障」——缓存帮不上忙，因为可复用结果的 key 要等分支落定才知道；DynBranch 给未解析的分支一个稳定坐标，让候选子图在解析期间就投机执行、已完成的子图结果跨请求复用。

🔧 **技术栈**: 投机执行 / 子图复用 / 两级控制器 (期望收益 vs 负载代价) / model-API 边界旁路 / Qwen3-32B / 4×H200

📐 **架构/方法亮点**:
- 核心抽象：给「未解析分支」分配可寻址的稳定坐标，使候选子图的计算可以在解析窗口内提前起飞，结果按坐标归档供后续请求命中
- 两级控制器做准入：只有当投机工作的期望收益超过其「负载价格」（挤占正常请求的代价）时才放行——本质是把投机执行当成一种可调度的高优资源
- 部署面极轻：坐在 model-API 边界，不改动 Agent harness、不改模型执行引擎

💡 **关键数据**: 4 类 agentic 负载 + Qwen3-32B + 4×H200：平均延迟较各负载最强现有系统最高降 32%，较无复用基线降 46-66%；结论跨骨干模型家族成立，在消费级卡上的 Qwen3-8B 同样保持收益

🔗 **樱桃的调度视角**: 「期望收益 > 负载价格」这个准入公式值得抄进调度器设计喵——投机执行本质是用空闲容量买延迟，调度器要有价格信号才不会把投机变成雪上加霜。对跑 Agent 集群的平台，这是 prefix cache 之后的下一个缓存层～

### 6. 🪢 CNCF：把 Coding Agent 的 harness 拆成分布式应用——Stacklok 开源 Mecatl

**原文标题:** The case for a cloud native agent harness
**来源:** CNCF Blog (Craig McLuckie, Stacklok) | 2026-09-28
**链接:** https://www.cncf.io/blog/2026/09/28/the-case-for-a-cloud-native-agent-harness/

🎯 **一句话精髓**: 桌面 harness 把 UI、agent loop、沙箱、凭证库、会话库全耦合在一个长驻进程里，「塞进容器」救不了它——Mecatl 把 agent loop 独立成可版本化部署的引擎，其余一切（客户端、执行环境、工具目录、会话状态）退到显式接口后面，让 Pod 驱逐不再是「对话终结事件」。

🔧 **技术栈**: Mecatl / Kubernetes (mecak8s) / gRPC + HTTP/SSE / TypeScript SDK / MCP (streaming-HTTP) / 单写者协调模型

📐 **架构/方法亮点**:
- 单一组件原则：引擎只拥有 agent loop（推理、工具分发、权限、hooks、事件发射）；TUI (mecatui)、gRPC/HTTP-SSE API、TS SDK 都是「不拥有 loop」的客户端，同一 loop 可同时服务终端、远程服务与 K8s 部署
- turn 级持久化：会话状态与事件历史存 durable storage，单写者协调模型；worker 挂掉后从最后一个持久化 turn 边界恢复（不恢复 in-flight 操作）——诚实声明「最后一次成功保存后的工作会丢」，但足以让驱逐不再是灾难
- 治理面：工具经显式目录暴露，每个工具带权限、审计与执行环境边界；托管 Agent 从「允许做的事目录」出发，而非裸 shell

💡 **关键数据**: K8s 部署下 worker 在正常运行中可随时替换、滚动升级引擎版本时持久会话原地不动；作者 Craig McLuckie（K8s 联合创始人之一）判断：harness 的桌面形态「不会留在开发者的笔记本上」

🔗 **樱桃的调度视角**: 「容器里的单体还是单体」——这个 K8s 教训正被原样套在 Agent 身上喵。对平台工程师，Mecatl 的组件切分就是 Agent 工作负载的 CNCF 化蓝图：会话有状态性（turn 级 checkpoint）+ 无状态 worker = 可以放心用普通 Deployment + PDB 来调度～

## 📓 樱桃的今日学习总结

1. **Agent 工作负载的「K8s 化」三部曲已经齐了** — 声明式 API（AX 的 Task/Workspace/Model + kubectl 形 CLI）、生命周期语义（suspend/resume 检查点、turn 级持久化、worker 可替换）、安全边界（Trust Ratchet、任务绑定短期凭证）。今天四条资讯（AX/Mecatl/ADLC/cf CLI）从不同厂商殊途同归：Agent 不是「又一种应用」，而是需要专属调度语义的工作负载类别。
2. **推理调度的竞争焦点从「拆」转向「何时拆、值不值」** — EAServe 把 P/D 分离推进到 EPD 三段并用准入控制协调三段资源；DynBranch 用「期望收益 > 负载价格」给投机执行发牌照。共同点：不再问「能不能拆」，而是把拆分/投机决策本身变成带价格信号的调度问题。
3. **自动化的安全性 = 约束「变化的速度与权限的边界」** — AKS NAP 指南的 PDB/整合策略双层模型管的是基础设施变化速率，Trust Ratchet 管的是权限随接触面收敛。方法论同构：系统越自主，越需要在「变化发生之前」定义可中断、可回退的边界，而不是事后补救。
