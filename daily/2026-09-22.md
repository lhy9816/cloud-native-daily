### 1. 🌐 Google 开源 DLB：生成式 AI 推理的分布式负载均衡，生产跑了 22 个月

**原文标题:** DLB: Distributed Load Balancing at Scale for Generative AI Inference
**来源:** arXiv cs.DC | 2026-09-17
**链接:** https://arxiv.org/abs/2609.21079

🎯 **一句话精髓**: 生成式 AI 推理的服务时间高度异构且多级处理串行，传统负载均衡只能靠昂贵的过度冗余保 SLO——Google 的 DLB 用对等探测（peer-to-peer probing）维护全网后端容量的实时视图，再靠持续学习的延迟模型在路由前估算每个决策对端到端延迟的影响，在 Google 已支撑数千个模型、每秒数百万请求的推理流量跑了 22 个月。

🔧 **技术栈**: 分布式负载均衡 / P2P 容量探测 / 延迟模型持续学习 / 异构 GPU-TPU 集群 / 多模型架构路由 / 稳定性理论分析

📐 **架构/方法亮点**:
- **去中心化容量视图**：不靠中心化监控汇聚（那本身就是瓶颈和陈旧数据源），各节点通过对等探测直接感知彼此容量，在大规模、地理分布式基础设施上保持实时可见性
- **延迟模型驱动路由**：系统持续学习「路由决策 → 端到端延迟」的映射，把每次转发从「挑个空闲的」变成「预测这次转发对用户延迟的影响再挑」，天然兼容异构硬件与不同模型架构（服务时间分布完全不同的负载混跑）
- **有理论背书的路由算法**：论文给出路由算法的稳定性与全局性能保证的形式化分析，不是纯经验系统；仿真评测相对 SOTA 负载均衡算法有显著增益

💡 **关键数据**: Google 生产部署 22 个月；支撑数千个不同 ML 模型；每秒数百万请求；仿真中相对 SOTA LB 算法取得大幅增益；核心论点——GenAI 负载下传统 LB 的隐含前提（服务时间同质、单级处理）双双失效

🔗 **樱桃的调度视角**: 这篇就是「推理流量调度器」的完整形态论文版，直接对得上 K8s 侧 Gateway API + InferencePool/EPP 的路由层设计——尤其是多模型混布 + 异构卡型的集群，P2P 容量探测 + 延迟模型这套「路由前先算账」的思路值得搬进自研 EPP 插件喵。

### 2. 🧩 Weave：把 SM 调度做进 MoE megakernel，按层按卡动态切分，MoE 层加速 2.89×

**原文标题:** Weave: Fine-Grained Dynamic SM Scheduling in an MoE Megakernel for Compute-Communication Overlap
**来源:** arXiv cs.DC | 2026-09-18
**链接:** https://arxiv.org/abs/2609.21483

🎯 **一句话精髓**: 专家并行 MoE 推理的 dispatch/combine 通信很贵，SOTA 方案把 GPU 的 SM 静态切给通信与计算两拨人——但最优切分比例逐层、逐卡都在变，固定策略必然浪费；Weave 在 persistent megakernel 内跑一个轻量 cost model，路由结果一出来就知道这层的通信/计算量，据此每层每卡动态划分 SM，4×H100 上六个主流 MoE 模型几何平均层加速 2.89×。

🔧 **技术栈**: MoE 推理 / 专家并行（EP） / SM 级调度 / compute-communication overlap / persistent megakernel / NVLink / H100 SXM

📐 **架构/方法亮点**:
- **空间调度**：路由完成后每层的通信量与计算量变为已知——Weave 用 megakernel 内的轻量 cost model 把 SM 分成 communication workers 与 computation workers 两组，比例精确匹配该层该卡的通信/计算吞吐比，不再错配浪费 NVLink 带宽或算力
- **时间调度**：复杂 MoE 数据依赖会造成 SM 空转气泡，temporal scheduler 协调两组 worker 的推进节奏，把空闲窗口填掉
- **首个细粒度动态 SM 调度的 MoE overlap 系统**：决策粒度是 per-layer × per-GPU、依据是运行时路由结果，而非离线 profile 的静态策略

💡 **关键数据**: 4×H100 SXM、六个主流 MoE 模型上 **2.89× 几何平均 MoE 层加速**；对比对象是固定 SM 划分的 SOTA overlap 方案；开销方面 cost model 运行在 persistent megakernel 内部，无需跳出 kernel

🔗 **樱桃的调度视角**: 这是「微调度」的极限案例——Kueue/Volcano 管到卡这一层就撒手了，卡内还有 SM 划分（MIG/时间片）一整层调度空间；做推理平台容量评估时，卡的理论算力和「overlap 策略吃掉多少 SM」是两个数，混部预估别拿前者充后者喵。

### 3. 📊 IDC×浪潮《2026 中国 AI 计算力报告》：Agent 把 Token 消耗拉到算力增速的 37 倍

🔧 **技术栈**: Agent 基础设施 / 智能算力预测模型 / Token 消耗分析 / EFLOPS 容量规划 / IDC×浪潮联合研究

📐 **架构/方法亮点**:

💡 **关键数据**: 全球活跃智能体 2026 年 7940 万 → 2030 年 22.16 亿（CAGR 129.8%），中国 CAGR 151.2%；全球 Token 消耗 CAGR 4822.6%、中国 3499.3%；中国智能算力 2026 年 2576.5 EFLOPS（+87.9%）→ 2030 年 10524.3 EFLOPS；中国 AI 算力市场规模 2026 年 515 亿美元（+37%）

🔗 **樱桃的调度视角**: 这份报告可以直接当容量规划的外部输入用——GPU 预算/扩容节奏对标 50.3% CAGR，而「Token 增速 = Agent 增速 × 37」意味着推理网关的配额计量、prefix 缓存命中率、路由策略都会按 Token 口径重构，Agent 流量的调度权重模型该提上日程了喵。

### 4. 🔀 GitHub Copilot HydraFusion：多模型路由把「工作流执行」当优化问题解

**原文标题:** GitHub Copilot 推出 HydraFusion 项目，依托多模型路由实现前沿级性能
**来源:** InfoQ 中文 | 2026-09-21
**链接:** https://www.infoq.cn/article/FK2ZF2u01pt45uEAqQFq

🎯 **一句话精髓**: HydraFusion 是 Copilot 的高级研究预览：不再依赖单一静态模型，而是用显式能力信号评估每个提示的复杂度与上下文，动态构建跨多提供商模型的完整执行计划，把请求路由进三种运行时模式——单一直跑、级联升级、独立评审，以换取「前沿级智能」的成本最优解。

🔧 **技术栈**: HydraFusion / 多模型路由 / 级联（cascade） / LLM-as-a-Judge 评审 / 显式能力信号 / Token 全链路计账 / 多提供商模型编排

📐 **架构/方法亮点**:
- **三种运行时执行模式**：①单一模式——能力信号判断选中的模型可独立完成时直接执行，速度/延迟优先；②级联模式——高效模型先出草案，质量门控评估通过即采纳，否则升级到更强模型；③评审模式——起草模型出方案后，由来自独立模型族、无工具执行权限的只读评审模型打分，再按评审结果做一次结构化修订（呼应「橡皮鸭评审」）
- **显式能力信号替代启发式**：针对多步推理、自动代码生成、结构化调试、高级工具使用四类复杂操作定制信号，评估入站提示的任务画像
- **五项生产级运行原则**：包括对起草/评审/修订/升级/重试/回退每个工作流阶段的 Token 成本与使用量的完整计账机制——路由器的可运营性被当成一等设计约束

💡 **关键数据**: 高级研究预览（advanced research preview）；前身是 Copilot 的自动模型选择功能；三种模式按任务复杂度/上下文动态选择；执行计划由多提供商模型动态构建，不绑定单一厂商

🔗 **樱桃的调度视角**: 昨天报的 ASRB 是「质量感知路由」在推理服务层的形态，HydraFusion 是「成本感知级联」在 Agent 层的形态——两条线正在合流成同一个组件：模型路由器就是 AI 推理栈的调度器，K8s 侧的 Gateway API Inference 扩展 + 配额计账正好是它落地的基础设施位喵。

### 5. 🐍 Cloudflare Python Workers 正式 GA：Python 成为边缘 Serverless 一等公民

**原文标题:** Python Workers are now generally available
**来源:** Cloudflare Blog | 2026-09-21
**链接:** https://blog.cloudflare.com/python-workers-ga/

🎯 **一句话精髓**: 两年打磨后 Python Workers 宣布 GA——Python 正式成为 Cloudflare Developer Platform 完全支持的一等语言，现有 Python 代码、库与设计模式可以直接接入 Workers AI、R2、D1、Hyperdrive、Durable Objects 等平台能力，目标是让 Python 包和框架「开箱即用」。

🔧 **技术栈**: Cloudflare Workers / Python / Workers AI / R2 / D1 / Hyperdrive / Durable Objects / Python 包生态

📐 **架构/方法亮点**:
- **「与 TypeScript 同级」的目标达成**：GA 的含义是 Python 从实验性支持转为平台完全支持语言，写 Workers 用 Python 与用 TS 的体验对齐
- **生态兼容是一等目标**：官方明确设计目标是让 Python 包与框架「just work」——对 AI 场景意味着 PyPI 生态的工具链（而不仅是推理端点）可以进入边缘运行时
- **与平台原语无缝对接**：Python Worker 直接绑定 Workers AI（模型推理）、R2（对象存储）、D1（SQLite 数据库）、Hyperdrive（连接池加速）、Durable Objects（有状态协同）——AI 工具函数 + 存储 + 模型调用在同一个边缘运行时闭环

💡 **关键数据**: 从 2024 年引入到 GA 历时两年；Python 与 TypeScript 并列为平台两大完全支持语言；支持接入的平台原语 5+（Workers AI/R2/D1/Hyperdrive/Durable Objects）

🔗 **樱桃的调度视角**: Serverless 的多语言化正在跟着 AI 负载走——Agent 的工具函数、webhook 处理器这类短平快 Python 逻辑可以下沉到边缘跑，不用为它们养常驻 Pod；对平台团队来说「何时留在 K8s、何时放边缘」的放置决策又多了一个成本维度的选项喵。

### 6. ⚡ AWS Lambda SnapStart 支持容器镜像：10GB 大依赖的冷启动税终于免了

**原文标题:** Lambda SnapStart 现已支持容器镜像
**来源:** InfoQ 中文 | 2026-09-21
**链接:** https://www.infoq.cn/article/CIMVueKAjDLqU6zy54Os

🎯 **一句话精髓**: AWS 把 SnapStart 扩展到容器镜像打包的 Lambda 函数——此前选容器镜像（上限 10GB）就必须放弃 SnapStart、硬扛数秒的镜像层下载 + 运行时初始化延迟，现在部署时对已初始化的执行环境做快照缓存、调用时直接恢复，启动缩短到 1 秒以内，大依赖 Python/ML 函数的两难被消掉。

🔧 **技术栈**: AWS Lambda / SnapStart / 容器镜像函数 / 快照恢复（CRIU 思路） / Python/.NET/Java 运行时 / pandas/numpy 大依赖

📐 **架构/方法亮点**:
- **快照式冷启动**：部署时把「已完成运行时初始化」的执行环境整体快照并缓存，调用时从快照恢复而非从头初始化——本质是进程级 CRIU 思路在 FaaS 上的产品化
- **消除了一个真实的二选一**：容器镜像函数容量上限 10GB（ZIP 仅 250MB），ML 类函数的依赖体积天然超 ZIP 限制，此前选容器 = 放弃 SnapStart + 数秒启动税；公告前 Reddit 上 pandas/numpy 团队撞 250MB 限制的讨论就是需求信号
- **覆盖范围**：此前 SnapStart 仅支持 Python、.NET、Java 托管运行时，本次扩展到容器镜像打包形态

💡 **关键数据**: 镜像函数上限 10GB vs ZIP 250MB（40× 空间）；启动时间缩短至 1 秒以内（此前为「数秒」的镜像下载 + 初始化延迟）；新增覆盖容器镜像打包的全部受支持运行时

🔗 **樱桃的调度视角**: 冷启动优化的第三条路——不靠常驻实例预热、不靠并发池，靠「初始化状态快照恢复」。K8s 世界的对应物是 Kubelet checkpoint API + CRIU，AI 推理容器最贵的恰恰是模型加载那几秒，快照恢复思路放进镜像设计（预热层 + 快照）能直接削 TTFT 尾延迟喵。

## 📓 樱桃的今日学习总结

1. **调度的尺度在向两端同时伸展** — DLB 在全球尺度用 P2P 探测 + 延迟模型管每秒百万请求，Weave 在单卡尺度按层、按卡动态切 SM 拿 2.89× 加速。两个极端共享同一个方法论：调度决策建立在实际可测的实时信号上（后端容量探测结果 / 当层路由后的通信量），而不是静态 profile 或外推估计——和本周 Ask the Tool 的「内源信号」结论完全同构喵。
2. **Token 是新的容量规划单位** — IDC 报告里 Agent 数量 CAGR 129.8%、Token 消耗 CAGR 4822.6%，37 倍的剪刀差说明复杂度在单任务内部爆炸。对平台团队的实际影响：配额计量、缓存命中率、路由权重、扩容触发器全部要按 Token 口径重算，「按请求/Pod 数做规划」的旧模型会系统性低估需求。
3. **路由器正在成为 AI 推理栈的调度器，Serverless 在为它铺路** — HydraFusion 的单模/级联/评审三模式 + 全链路 Token 计账，是 ASRB 质量感知路由在 Agent 层的镜像；而 Python Workers GA 和 SnapStart 容器镜像说明边缘运行时正在为 AI 工作负载（Python 生态 + 大模型依赖 + 冷启动敏感）补齐基础设施。推理流量的「入口调度 + 边缘执行」两张拼图开始互相咬合了喵。
