### 1. 📦 Agent 时代，为什么有人开始重新造 Google？

**原文标题:** Agent 时代，为什么有人开始重新造 Google？
**来源:** InfoQ 中文 | 2026-08-29
**链接:** https://www.infoq.cn/article/KbbHdAQFxQM7AJIYMLqR

🎯 **一句话精髓**: 前Yandex搜索负责人创办Keenable，从底层重新爬取互联网、建立独立Web Index，专为AI Agent提供搜索基础设施，揭示了"搜索infra和模型infra出现在同一张账单里"的新趋势。

🔧 **技术栈**: Web Crawl / Index / Retrieval / Ranking / MCP Server / REST API / CLI / Token Efficiency

📐 **架构/方法亮点**:
- Keenable从底层重建Crawl→Index→Retrieval→Ranking全链路，不套壳Google/Bing API，通过REST API、MCP Server和CLI把搜索能力交给Agent
- Agent搜索vs人类搜索的反馈飞轮完全不同：传统搜索优化点击/排序/用户满意度，Agent Search关心Recall、Freshness、Latency、QPS、机器可读性、Token Efficiency、Provenance
- 新成本链条浮现：Search Quality → Context Quality → Token Consumption → Agent Cost，搜索层先删广告/导航/推荐、只送最相关Passage进上下文，同时降低Search成本和后续模型输入Token

💡 **关键数据**: Keenable索引覆盖1000亿+文档，p95延迟<250ms（美东），$1/千次请求(>100 RPS)，$4/千次(普通)，15人团队$2600万种子轮(Accel领投)；竞品Exa 1000亿文档/1.4万亿URL/50万+开发者/$2.5亿C轮/$22亿估值

🔗 **樱桃的调度视角**: 这篇直击AI推理的一个隐形成本--Agent完成任务可能搜索几十到上百次，搜索调用成本正在成为推理成本的重要组成部分。对K8s上的AI推理服务，把搜索层和模型层的成本合并考量是新的架构决策点。

### 2. 📦 Atlassian 的多信号关联自动根因分析：RCA 本质是关联问题

**原文标题:** Automating root cause analysis at scale: Multi-signal correlation for cloud native incident response
**来源:** CNCF Blog | 2026-08-24
**链接:** https://www.cncf.io/blog/2026/08/24/automating-root-cause-analysis-at-scale-multi-signal-correlation-for-cloud-native-incident-response/

🎯 **一句话精髓**: Atlassian将根因分析重新定义为跨「信号类型×时间×拓扑」三维关联问题，自动化假设生成让响应者跳过最耗时的关联步骤直接验证和修复。

🔧 **技术栈**: OpenTelemetry / RED metrics / Embedding-based log clustering / Service dependency graph / Median Absolute Deviation

📐 **架构/方法亮点**:
- 三步流水线：① 用OTel span级parent-child关系构建服务依赖图缩小爆炸半径（从数百服务到几十个）；② 每信号独立异常检测（RED metrics用MAD+百分位带，trace结构异常分析，embedding聚类日志发现新错误簇）；③ 滑动窗口时间关联，用时间聚合度评分公式 $S_{temporal} = \frac{1}{N(N-1)} \sum \exp(-|t_i - t_j|/\tau)$ 排序
- 关键设计：所有检测器输出统一事件schema（timestamp/service/signal_type/severity_score），让下游关联引擎无需关心哪个检测器产生事件；模块化可插拔，统计模型可替换为ML模型
- 实战发现：同一因果链在事故期间会重复播放（上游超时→下游500），重复模式本身是强信号

💡 **关键数据**: Atlassian规模为数百个互联微服务跨多region；聚焦子图通常为几十个服务而非数百个

🔗 **樱桃的调度视角**: 服务拓扑来自OTel的span关系，这比文档里的"应该怎么通信"更真实。多信号关联+拓扑传播对K8s微服务可观测性直接可用，可以集成到K8s事件响应流水线替代纯人工correlation。

### 3. 📦 开发者可观测性「懒人指南」：OpenTelemetry 插桩的痛与解

**原文标题:** The lazy developer's guide to observing your own code
**来源:** CNCF Blog | 2026-08-25
**链接:** https://www.cncf.io/blog/2026/08/25/the-lazy-developers-guide-to-observing-your-own-code/

🎯 **一句话精髓**: 开发者被要求在可观测性上"左移"但阻力重重，文章系统梳理了OpenTelemetry插桩的5个好处、4个痛点和2个核心优势，为零代码插桩铺路。

🔧 **技术栈**: OpenTelemetry / eBPF / Zero-code instrumentation / SDK / SIG

📐 **架构/方法亮点**:
- 5个好处：减少debug时间、加速开发部署、暴露慢路径/隐藏重试/边界case改善代码、理解分布式系统行为、理解vibecoded应用（AI生成代码质量参差，可观测性帮助理清）
- 4个痛点：① 各语言SIG社区贡献不均导致SDK质量差异；② Rust/Elixir缺少zero-code auto-instrumentation需从零手写；③ 选项太多（SDK/eBPF/编译时）且项目成熟度不一；④ API稳定性+metrics高基数（high cardinality）问题
- 2个优势：灵活性（高度可定制可扩展，future-proof）；社区（主流可观测性厂商背书，有专门Developer Experience和Contributor Experience组改善易用性）

💡 **关键数据**: 无具体数字，但指出OpenTelemetry生态"very large"且"many moving parts, not all moving at the same rate"

🔗 **樱桃的调度视角**: 对K8s上的AI推理服务，OpenTelemetry插桩是端到端可观测的基础。Rust缺少auto-instrumentation对用Rust写高性能推理服务（如vLLM周边组件）的团队是真实痛点，需要手动插桩或依赖eBPF方案兜底。

### 4. 📦 Cloudflare BotBase 面向运营者：AI 机器人管理生态的三维分类法

**原文标题:** BotBase for Operators: A clearer path to joining Cloudflare's directory of bots and agents
**来源:** Cloudflare Blog | 2026-08-28
**链接:** https://blog.cloudflare.com/botbase-for-operators/

🎯 **一句话精髓**: Cloudflare为Bot运营者推出Dashboard管理提交全流程，核心创新是用三维行为模型（做什么×内容使用方式×运营身份）替代单一标签，并用自动化审核替代人工判断。

🔧 **技术栈**: Web Bot Auth / Content Signals / robots.txt / Cloudflare Workers / Cloudflare Radar

📐 **架构/方法亮点**:
- 三维分类法：Bot做什么（索引/Agent/训练/SEO），如何使用内容（search/ai-train/use=reference，对应Content Signals模型），谁运营（direct直连 vs intermediary中介平台）
- Content Signals模型写入robots.txt：`Content-Signal: search=yes, ai-train=no, use=reference`，Bot的内容使用声明与此偏好自动校验
- 自动化审核流水线：重复检测→UA模式特异性校验→验证方法自动验证（fetch IP list/确认reverse DNS/验证Web Bot Auth签名），通过即即时上架，需人工看的具体原因已标记
- 提交状态从黑盒变透明：Waiting for review → Accepted/Rejected（附可操作原因和修改建议），支持编辑已有提交

💡 **关键数据**: Bot提交量自2023年增长约7倍；纯人工审核无法支撑该增速

🔗 **樱桃的调度视角**: Content Signals模型和Web Bot Auth签名验证对管理AI爬虫访问K8s托管服务有参考价值。Web Bot Auth比IP allowlist更适合多云/边缘环境，可以作为Ingress层的bot流量治理策略。

### 5. 📦 S3 兼容不等于 S3 级安全：新云对象存储的安全审计

**原文标题:** S3 Compatibility Doesn't Guarantee S3-Level Security
**来源:** InfoQ 中文 | 2026-08-28
**链接:** https://www.infoq.cn/article/xr3L0bkiFZGzYmtZwscB

🎯 **一句话精髓**: Wiz安全研究员测试6家新云的S3兼容对象存储，发现公共Bucket处理、Access Key检测、IAM语义均与AWS S3存在显著差异，S3兼容制造了危险的"可移植性错觉"。

🔧 **技术栈**: S3 API / IAM / Bucket Policy / ACL / MinIO / RustFS / GitHub Secret Scanning

📐 **架构/方法亮点**:
- 6家测试：Nebius、Crusoe、Vultr、Lambda Labs、Cloudflare R2、DigitalOcean，对比维度为公共Bucket处理、Access Key格式与检测、IAM能力和语义
- 公共Bucket处理差异：Crusoe和Lambda Labs不支持公开访问；DigitalOcean支持公开列出Bucket内对象；Vultr同时用ACL和Bucket Policy控制
- Access Key检测黑洞：neocloud密钥缺少AWS的结构化格式特征，GitHub Secret Scanning检测不到这些凭据
- IAM语义陷阱：MinIO有未授权权限提升漏洞；RustFS近期漏洞破坏租户隔离和授权语义；一家服务的`delete-bucket-policy`实际删除了整个Bucket

💡 **关键数据**: AWS S3涉及近300个API、20+年历史、存储万亿对象和数百EB；目前90+家S3兼容服务；Exa未覆盖Backblaze B2/Wasabi/GCS

🔗 **樱桃的调度视角**: 在neocloud上用K8s+MinIO/Rook做对象存储的团队，不能假设"S3兼容=S3安全"。需要逐一审计公共访问控制、密钥检测能力、IAM语义，尤其是`delete-bucket-policy`这类危险API的实际行为。

🎯 **一句话精髓**: Cloudflare推出专为自动化工作负载构建的轻量浏览器Kitesurf，在Workers的WASM/Rust隔离环境运行浏览器组件，用Blitz渲染引擎替代Chromium，资源开销大幅降低。

🔧 **技术栈**: WebAssembly / Rust / Blitz渲染引擎 / Firefox Stylo CSS解析器 / Playwright / Puppeteer / Chrome DevTools Protocol

📐 **架构/方法亮点**:
- 在Cloudflare Workers上隔离的WASM/Rust环境中运行浏览器组件，每个页面/OOPIF在独立Dynamic Worker中运行，拥有独立JavaScript环境与DOM实现环境隔离
- 使用基于Rust的Blitz渲染引擎 + Firefox的Stylo CSS解析器，而非完整Chromium；支持Chrome DevTools Protocol，Playwright/Puppeteer等工具可直接驱动
- 设计哲学：Chromium是为人类设计的浏览器引擎，附带了AI模型根本不需要的性能开销（视频播放、WebGL、真实TLS环境下的bot验证等）
- 当前局限：不支持视频、WebGL、基于TLS的bot验证、长时效已认证会话，不替代Chromium

💡 **关键数据**: 无具体性能数字，但定位为"低于完整Chromium浏览器的资源开销"

🔗 **樱桃的调度视角**: 对K8s上的AI Agent需要网页交互的场景，Kitesurf在边缘Workers上运行比在K8s Pod中跑完整Chromium省资源得多。可以作为Serverless AI Agent的web interaction层，与K8s上的推理服务形成"推理在K8s、网页交互在边缘"的分工架构。

## 📓 樱桃的今日学习总结

1. **「搜索infra」正在成为「模型infra」的共生层** - Keenable和Exa从底层重建Web Index专为Agent服务，揭示了新成本链 Search Quality → Context Quality → Token Consumption → Agent Cost。搜索层不再只返回链接，而是预处理内容、删冗余、只送最相关Passage，同时降低搜索成本和模型推理Token。对K8s上的AI推理平台，搜索调用成本必须纳入总推理成本考量。
2. **可观测性的「左移」从SRE走向开发者，但工具链还不够友好** - CNCF两篇文章从不同角度覆盖可观测性：Atlassian自动化了RCA中最耗时的"多信号关联"步骤（metrics/logs/traces×时间×拓扑），而OpenTelemetry插桩的4个痛点（SDK不均、Rust无auto-instrumentation、选项太多、高基数）说明开发者侧的工具链成熟度仍需追赶。AI生成代码（vibecoded）的可观测性需求进一步放大了这个gap。
3. **AI模型正在从「消耗GPU」走向「优化GPU」** - 腾讯Hy4首次让模型参与自身推理基础设施优化（算子融合+通信优化，+31.8%吞吐），形成递归自我改进闭环。这预示着AI推理平台不仅是调度GPU给模型用，模型本身可以反馈优化调度效率。同时腾讯的算力焦虑（Q2资本开支+176%、自由现金流转负）说明GPU供给仍是最大瓶颈。
