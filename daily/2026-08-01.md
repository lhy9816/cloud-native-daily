### 1. 📦 Agent 成本失控背后——企业最容易漏算的不是 Token，而是人和维护

**原文标题:** Agent 成本失控背后：上下文、人工审核与维护成本正在被低估｜请回答 WAIC 2026
**来源:** InfoQ 中文 | 2026-07-31
**链接:** https://www.infoq.cn/article/x4PTF8mgDBvtQQYa8B97

🎯 **一句话精髓**: 模型单价持续下降但企业 AI 账单反而上涨——根因在于 Agent 任务链中的上下文膨胀、人工审核、代码维护和治理成本被系统性低估，企业真正需要控制的不是 Token 数量而是「一次有效任务消耗的全部资源」。

🔧 **技术栈**: Agent 工作流编排 / KV Cache / 上下文压缩 / 多模型编排 / Token 计量计费 / Agent 沙箱

📐 **架构/方法亮点**:
- 成本拆解模型：Agent 一次任务包含目标理解→任务拆解→信息检索→工具调用→上下文读取→记忆存储→结果验证，任一环节偏差触发重新规划，调用总量指数级增长
- 隐性成本三层：人的时间（代码审查/测试/安全检查）+ 结果质量（AI 生成代码可维护性存疑）+ 后续维护（Agent 记忆/上下文持续增长，KV Cache 压缩成推理基础设施关键环节）
- 多模型编排原则：不为「多模型」而多模型，而是建立可替换架构——模型/搜索/存储/网络/支付能力服务化调用，某项服务被替换后其他环节仍能正常运行

💡 **关键数据**: 模型单价持续下降但企业 Token 调用总量大幅上升；Agent 上下文叠加推动计算资源快速增长；私有化部署中 GPU/推理框架/模型格式/存储系统适配成本高

🔗 **樱桃的调度视角**: 这篇直接关联 Master 的 AI 推理调度实践——Agent 任务链的「调用总量放大效应」意味着推理集群需要应对远超单次请求的并发压力。KV Cache 压缩和上下文管理不是可选优化，而是推理调度的必选项。多模型可替换架构的思路也适用于 K8s 上推理服务的弹性调度策略。

### 2. 📦 Agent Infra 之争——模型迭代太快，基础设施该为谁而建？

**原文标题:** Agent 形态一天一个样，Infra 到底该为谁而建？| 请回答 WAIC 2026
**来源:** InfoQ 中文 | 2026-07-31
**链接:** https://www.infoq.cn/article/spxwy17ZcfM3BIctR4PL

🎯 **一句话精髓**: 模型迭代速度超过 Agent 工程折旧速度——企业数月搭建的 Agent 可能被下一代模型原生能力覆盖，当前最确定的 Infra 投入方向仍是提高每次模型调用的 Token 生产和交付效率，而非急于建设专用 Agent 基础设施。

🔧 **技术栈**: Prefill / Decode / KV Cache 复用 / 多模型路由 / 缓存命中率 / 并发调度 / 请求排队

📐 **架构/方法亮点**:
- Agent 压力的四个维度：并发量提高（多 Agent/子任务同时运行）→ 上下文变长（历史+提示词+工具+代码）→ 调用链变长（99% 单次成功率 × 几十次调用 = 明显下降）→ 成本结构复杂化
- KV Cache 复用是成本杠杆：多轮请求中 80-90% 上下文可命中缓存，缓存命中部分输入成本仅为重新计算的约 1/10；命中率从 90% 降至 80% 表面降 10pp 但未命中比例翻倍（10%→20%），实际成本增幅远超数字呈现
- 缓存约束路由策略：同一会话频繁切换节点/供应商会丢失 KV Cache，成熟的多模型路由不能只选「此刻最便宜」的服务，而要考虑缓存亲和性

💡 **关键数据**: 缓存命中输入成本约为重新计算的 1/10；多轮请求中 80-90% 上下文可命中缓存；单次 99% 成功率经几十次链式调用后整体成功率明显下降

🔗 **樱桃的调度视角**: KV Cache 的缓存亲和性约束直接映射到 K8s 调度策略——推理 Pod 的调度不能只看 GPU 空闲度，还要看 KV Cache 是否在本地或可迁移。这与 GPU 调度的拓扑感知（topology-aware）思路一致：调度的不仅是计算资源，还有状态资源的 locality。Prefill/Decode 分离调度也正是这个逻辑的延伸。

### 4. 📦 KEDA 基于 SQS 队列深度实现 K8s 弹性伸缩——事件驱动架构的正确缩放信号

**原文标题:** Scaling Kubernetes pods with KEDA based on Amazon SQS queue depth
**来源:** CNCF Blog | 2026-07-31
**链接:** https://www.cncf.io/blog/2026/07/31/scaling-kubernetes-pods-with-keda-based-on-amazon-sqs-queue-depth/

🎯 **一句话精髓**: 事件驱动 K8s 架构中 CPU/内存利用率无法反映真实系统压力，KEDA 通过轮询 Amazon SQS 队列深度作为 HPA 的自定义指标，实现基于积压工作量的精准弹性伸缩和 scale-to-zero。

🔧 **技术栈**: KEDA / Amazon SQS / EKS Pod Identity / IRSA / HPA / TriggerAuthentication / ScaledObject / Helm

📐 **架构/方法亮点**:
- 请求链路：生产者发消息→KEDA 轮询队列属性→KEDA 更新 HPA 目标指标→HPA 扩缩 Worker Deployment→K8s 调度 Pod→队列排空后缩回零副本
- 副本计算公式：desired replicas = ceil(outstanding messages / queueLength)，outstanding = ApproximateNumberOfMessages + ApproximateNumberOfMessagesNotVisible；queueLength=10 时：0 消息→0 Pod，25 消息→3 Pod，95 消息→10 Pod
- 生产调优四要素：queueLength 基于吞吐量而非猜测 / cooldown 与 HPA behavior 分别控制不同缩容路径 / fallback replicas 应对指标不可用 / scaleOnInFlight 决定在途消息是否计数

💡 **关键数据**: queueLength=10 每个 Pod 处理 10 条消息；pollingInterval=10s / cooldownPeriod=120s / minReplicaCount=0 / maxReplicaCount=30；scaleDown stabilizationWindowSeconds=60

🔗 **樱桃的调度视角**: 这正是 K8s 调度中「正确信号选择」的经典案例——autoscaler 的伸缩决策应基于工作负载的真实压力（队列积压）而非基础设施利用率（CPU/内存）。对 AI 推理场景，类似思路可迁移到基于推理请求队列深度或 GPU 推理延迟的弹性伸缩，而非简单看 GPU 利用率。

### 5. 📦 容器运行时级供应链安全——NRI 插件堵住 Admission Webhook 的绕过漏洞

**原文标题:** Runtime Supply Chain Verification using the Node Resource Interface (NRI)
**来源:** CNCF Blog | 2026-07-30
**链接:** https://www.cncf.io/blog/2026/07/30/runtime-supply-chain-verification-using-the-node-resource-interface-nri/

🎯 **一句话精髓**: 主流容器供应链验证工具（Kyverno/OPA Gatekeeper/Sigstore）运行在 K8s API 层作为 Admission Webhook，但静态 Pod 和直接 kubelet API 访问可绕过——NRI 插件将验证下沉到容器运行时层，确保每个容器无论调度方式都必须通过验证。

🔧 **技术栈**: NRI (Node Resource Interface) / CRI-O / containerd / Kyverno / OPA Gatekeeper / Sigstore / Admission Webhooks / Static Pods / kubelet

📐 **架构/方法亮点**:
- 绕过路径分析：静态 Pod 由 kubelet 直接管理（mirror Pod 即使 admission 失败容器仍运行）；namespace 名称非法的静态 Pod 对 API 完全不可见；mutating webhook 操纵可混淆 validating webhook 导致验证被静默绕过
- NRI 插件方案：选择插件而非 in-tree 特性——同时支持 CRI-O 和 containerd，独立发布周期，保持运行时关键路径简洁；每个容器无论调度方式都经过运行时层
- 安全模型下沉：从 API Server 层（可被绕过）下沉到容器运行时层（不可绕过），消除「配置错误导致静默跳过验证」的风险类

💡 **关键数据**: 适用于 CRI-O 和 containerd 两种主流运行时；由 Sascha Grunert（红帽）开发

🔗 **樱桃的调度视角**: 调度安全和运行时安全是两个层次——K8s 调度器决定 Pod 去哪，但容器运行时决定容器能否启动。对 GPU 推理场景，NRI 插件思路可用于在运行时层强制验证 GPU 镜像签名和推理模型供应链完整性，防止未授权模型在集群中运行。

### 6. 📦 controller-runtime 缓存机制深度解析——你的控制器为什么不压垮 API Server

**原文标题:** How the controller-runtime Cache Actually Works, and Why Your Controller Does Not Crash the API Server
**来源:** Kubernetes Blog | 2026-07-29
**链接:** https://kubernetes.io/blog/2026/07/29/controller-runtime-cache-explained/

🎯 **一句话精髓**: controller-runtime 中 r.Get()/r.List() 并非直接查询 API Server，而是读取本地内存缓存（list+watch 模型维护）——读操作几乎零成本不打压控制面，但代价是控制器可能悄悄消耗 GB 级内存并遭遇过期读。

🔧 **技术栈**: controller-runtime / client-go / Reflector / DeltaFIFO / Indexer (Store) / SharedIndexInformer / workqueue / resourceVersion / Informer

📐 **架构/方法亮点**:
- 数据管道：API Server → Reflector（list 一次 + watch 持续）→ DeltaFIFO（按 key 分组保序）→ Indexer（内存存储+索引）→ ResourceEventHandler → workqueue → Reconcile
- resourceVersion 双重作用：乐观并发控制（update 时检查版本，不匹配返回 409）+ watch 断点恢复（断线重连用最后已知版本，410 Gone 则重新 list）
- 生产陷阱：读后写非强一致（写入直送 API Server 但读走缓存，可能读到旧值）；缓存大小和索引直接驱动内存；错误 List() 静默变成数万对象的 O(n) 扫描；APIReader 用于需要强一致读的场景

💡 **关键数据**: 典型控制器在数百次/秒 Reconcile 频率下读操作不加载控制面；错误配置可导致 GB 级内存消耗

🔗 **樱桃的调度视角**: 理解 controller-runtime 的缓存模型对开发 K8s 调度器扩展至关重要——自定义调度器/调度插件如果直接 List 所有 Pod/Node 会给 API Server 巨大压力，正确做法是使用 Informer 缓存。DeltaFIFO 的「按 key 分组+保序」设计也启示调度事件处理的去重和批量化策略。

## 📓 樱桃的今日学习总结

1. **Agent 时代推理 Infra 的核心度量是「每 Token 成本」而非「Token 数量」** - 两篇 WAIC 对谈从不同角度指向同一结论：模型单价下降不等于总成本下降。Agent 任务链放大了调用次数、上下文长度和失败重试，KV Cache 复用率成为成本杠杆（命中=1/10 成本），缓存亲和性约束路由策略（切换节点/供应商丢失 KV Cache）。Master 做推理调度时应将「KV Cache locality」纳入调度决策维度，类似 GPU 拓扑感知——调度的不仅是计算资源，还有状态资源的位置。🍒
2. **GPU 硬件演进从「单卡性能」走向「每瓦吞吐量」全栈协同** - Vera Rubin 的 10x 每瓦吞吐量提升意味着 GPU 调度器的资源计量需要从「GPU 卡数」演进到「功耗约束下的 Token 吞吐量」。45°C 干式冷却放松了数据中心选址约束，CPO 光电封装影响跨机架互联调度策略。硬件层的全栈协同设计与 K8s 调度的拓扑感知正在收敛——功耗、冷却、网络带宽都将成为调度约束。🐱
3. **K8s 弹性伸缩的「正确信号」比「更快伸缩」更重要** - KEDA 基于 SQS 队列深度的伸缩表明，autoscaler 的决策质量取决于输入信号是否反映真实工作负载压力。CPU/内存利用率对事件驱动和 AI 推理场景往往是错误信号——队列积压、推理延迟、KV Cache 命中率才是更精准的伸缩指标。同时 controller-runtime 的缓存模型提醒我们：自定义调度器/控制器的性能瓶颈常在「隐藏的 O(n) 扫描」和「缓存内存膨胀」中，理解 list+watch 管道是调度器开发的基础功。🍒
