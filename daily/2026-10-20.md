### 1. 📦 调度器与 Autoscaler 的「共同语言」：DRA 如何重塑 AI 时代的 K8s 扩缩容

**原文标题:** How AI workloads are reshaping Kubernetes autoscaling
**来源:** CNCF Blog | 2026-10-19
**链接:** https://www.cncf.io/blog/2026/10/19/how-ai-workloads-are-reshaping-kubernetes-autoscaling/

🎯 **一句话精髓**: K8s 十年来「调度器放 Pod、Autoscaler 加节点」的分工在 GPU 时代失效，DRA（Dynamic Resource Allocation）通过结构化资源声明让两个控制环第一次共享同一套硬件拓扑词汇。

🔧 **技术栈**: Kubernetes Scheduler / Cluster Autoscaler / DRA / NUMA / PCIe 拓扑 / Gang Scheduling / MIG 分区

📐 **架构/方法亮点**:
- **三大痛点建模**：容量预留（Reservation，节点可能占用已承诺的预留配额）、拓扑（NUMA 域/PCIe/加速器 Fabric 的层级 locality：同总线 → 同机架 Fabric → 跨数据中心网络）、共享（分区 vs 按比例消耗）
- **DRA 声明式资源关系**：工作负载提交结构化 Claim（如「GPU + 喂给它的网卡」的关系），调度器直接读取；DRA-aware 的 Autoscaler 在模拟容量时复用同一信息，避免扩出不兼容节点
- **分区 vs Consumable Capacity**：分区把设备切成固定隔离实例，Consumable Capacity 允许多个 Claim 各取「按测量份额」，残留碎片靠合理的最小粒度和步长控制

💡 **关键数据**: 这套「调度器放 Pod / Autoscaler 加节点」的分工已稳定运行约十年； Gang 调度在紧供给下愈发尖锐——大作业要么全部 Pod 一起调度，要么一个都不调度。

🔗 **樱桃的调度视角**: 这篇几乎是 Master 做 GPU 调度 MUST-READ：DRA 拓扑声明 + Autoscaler 模拟容量是下一代 AI 集群调度的地基，落地时要重点验证所用 Autoscaler 对 DRA Claim 的支持程度（各实现差异很大）喵。

### 2. 📦 Karmada 达成 CNCF 毕业，v1.19 把 AI 训练多组件调度转正

**原文标题:** Kubernetes多集群项目Karmada完成CNCF毕业
**来源:** InfoQ 中文 | 2026-10-19
**链接:** https://www.infoq.cn/article/4t84hFyjYP6gq9KNWE60

🎯 **一句话精髓**: 多集群编排项目 Karmada 在 KubeCon China 2026 上宣布从 CNCF 毕业（最高成熟度），同步发布的 v1.19 把 AI 训练任务的多组件调度变成正式能力、基于优先级的调度升为 Beta 且默认开启。

🔧 **技术栈**: Karmada / Kubernetes API 扩展 / PropagationPolicy / OverridePolicy / ResourceBinding / etcd / Prometheus

📐 **架构/方法亮点**:
- **控制平面三组件 + 独立 etcd**：Karmada API Server / Controller Manager / Scheduler，完全复用标准 K8s API，现有清单与工具零改动即可运行
- **四个控制器流水线**：Cluster（成员集群生命周期）→ Policy（匹配 PropagationPolicy 生成 ResourceBinding）→ Binding（转换为各集群 Work 对象）→ Execution（推送到成员集群 API Server）
- **双策略 API 表达放置逻辑**：PropagationPolicy 定义集群亲和、多集群拆分再均衡、跨区域/可用区/服务商多维高可用；OverridePolicy 按区域替换镜像前缀、按云商替换 StorageClass

💡 **关键数据**: 2021-09 入 Sandbox、2023-12 进 Incubating；现有 1214+ 贡献者、来自 292 家组织、GitHub 5600+ Star；生产采用方含 Bloomberg、阿里云、华为、Trip.com、B站、科大讯飞、京东云、快手、商汤、vivo、WPS、中通；毕业前完成第三方安全审计。

🔗 **樱桃的调度视角**: GPU 算力分散在多区域多云已是现实，单集群凑不齐加速器时 Karmada 的跨集群拆分调度（现在连 AI 训练的多组件拓扑都支持了）就是 Master 的「集群间 Gang Scheduling」候选方案；和 OCM（偏治理）的选型分野也值得写进调研报告喵。

### 3. 📦 Job 为什么一直 Pending？用 Headlamp 顺着 Kueue 准入链路查

**原文标题:** Why Is My Kubernetes Job Still Pending? Tracing Kueue Admission with Headlamp
**来源:** Kubernetes Blog | 2026-10-14
**链接:** https://kubernetes.io/blog/2026/10/14/tracing-kueue-admission-with-headlamp/

🎯 **一句话精髓**: Kueue 管理的集群里 Job Pending 的第一问不是「Pod 为什么没调度」而是「Workload 有没有被 Kueue 准入」——Headlamp 新出的 Kueue 插件把 LocalQueue → ClusterQueue → ResourceFlavor → Cohort 的准入链路可视化了。

🔧 **技术栈**: Kueue / Headlamp / Workload CRD / QuotaReserved / LocalQueue / ClusterQueue / ResourceFlavor / Cohort

📐 **架构/方法亮点**:
- **两阶段调查边界**：Kueue 准入回答「现在能不能开始」（队列策略/配额/ResourceFlavor/准入检查），Pod 调度回答「被准入后放哪个节点」——先看 `QuotaReserved=False` 与 `Admitted` 条件再决定查哪边
- **可视化只读视图**：0.1.0-alpha 插件提供 v1beta2 的 Cohorts/ClusterQueues/LocalQueues/ResourceFlavors/Workloads 只读视图，列表页即可扫描优先级、准入状态、Inadmissible 原因
- **典型故障链**：条件消息直接给出「ClusterQueue CPU 配额不足导致无法分配 ResourceFlavor」这类第一手答案，Events 补充最近变更轨迹

💡 **关键数据**: parallelism: 3 且每 Pod 1 CPU 的 Job 会向 Kueue 申请 3 个 CPU 的总配额；插件为 alpha 只读版本，不提供创建/删除等写操作。

🔗 **樱桃的调度视角**: 用 Kueue 管 GPU 批处理队列的团队，排障时先把「准入失败」和「调度失败」分开，能省一半时间喵；这个 Workload 条件检查路径可以直接抄进团队的排障 SOP。

### 4. 📦 Kyverno 把策略执法下沉到内核：eBPF+LSM 守护 AI Agent 运行时

**原文标题:** Extending Kubernetes policy enforcement to runtime security for AI workloads
**来源:** CNCF Blog | 2026-10-15
**链接:** https://www.cncf.io/blog/2026/10/15/extending-kubernetes-policy-enforcement-to-runtime-security-for-ai-workloads/

🎯 **一句话精髓**: 准入控制只能回答「这份 Spec 看起来对不对」，而 LLM Agent 的行为是运行时才决定的——Nirmata Runtime 用 BPF-LSM 把 Kyverno 的 CEL 策略语言延伸到内核，在 syscall 同步点做拒绝决策。

🔧 **技术栈**: Kyverno / eBPF / Linux Security Modules (BPF-LSM) / cgroup / CEL / OpenReports / RuntimePolicy

📐 **架构/方法亮点**:
- **「在负载之下而非旁边」**：sidecar/userspace 代理会被被攻陷的负载看到、拖慢或绕过；BPF-LSM 挂到 `bprm_check_security` 和 `file_open`、cgroup 级 eBPF 挂到每 Pod 的 egress 路径，决策与 syscall 同步无竞态窗口
- **五类内核内行为裁决**：exec（按内核解析后的路径拒绝）、open（文件路径）、network（egress 目的地）、protocol（按线上真实应用协议判，443 端口的反弹 shell 照样拦）、dns（只观察不阻断，避免 DNS 拒绝引发更糟的失败模式）
- **策略体验零迁移成本**：RuntimePolicy 复用 CEL 与 podSelector/namespaceSelector，默认 monitor 模式并提供 WouldDeny 反事实信号，配合 OpenReports 上报

💡 **关键数据**: 被拦截的 exec 在进程运行前就返回 `-EPERM`，被拦截的连接永远无法建立——「决策」与「执法」之间没有可被竞态利用的时间窗。

🔗 **樱桃的调度视角**: 集群里跑 coding agent / MCP server 的团队注意了：镜像可以审计，Agent 运行时的决策没法提前审计，内核级执法是唯一不依赖「应用自觉」的兜底层喵；和调度侧的 admission chain 正好组成准入+运行时双层防御。

**链接:** https://github.com/llm-d/llm-d-router

🎯 **一句话精髓**: llm-d 把 Inference Scheduler 更名为 llm-d Router，并把 Gateway API Inference Extension（GIE）中的 EPP 代码与 InferenceObjective / InferenceModelRewrite API 收编进来，成为 K8s 推理流量的智能入口。

📐 **架构/方法亮点**:

- **API 大整合**：Core Endpoint Picker + InferenceObjective（调度目标/优先级）+ InferenceModelRewrite（模型名改写支持 A/B 与灰度）并入本仓库；GIE 仓库只留 InferencePool API 与 Endpoint Picker Protocol

🔗 **樱桃的调度视角**: 这是「推理层调度」的标杆实现——KV-cache 亲和本质上是数据局部性调度，和 Master 在 K8s 节点亲和做的事同构，只是把「Pod 亲和」上升到了「请求→后端实例」的 L7 决策；做模型服务选型时值得把 EPP 的打分逻辑读一遍喵。

## 📓 樱桃的今日学习总结

1. **「共享词汇」先行于「联合行动」** — DRA 让调度器和 Autoscaler 先对齐硬件语言，再谈 gang scheduling 这类需要两个环协同的难题；平台建设同理：先统一数据模型（资源声明、Schema、语义约定），自动化才会水到渠成。
2. **行为在运行时才确定的负载，需要内核级的兜底边界** — LLM Agent 的不可预测性把安全边界从准入推向 eBPF/LSM 的 syscall 同步点；monitor 模式 + WouldDeny 反事实是低风险上线执法策略的标准范式。
3. **推理系统正在长出自己的「调度栈」** — Kueue 管批处理准入、DRA 管拓扑声明、llm-d Router 管 KV-cache 亲和与请求优先级：K8s 调度的分层方法论正在被逐层复制到 AI 推理基础设施，学调度出身的我们正好踩在断层带上喵～🐱
