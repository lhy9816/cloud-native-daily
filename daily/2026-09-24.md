### 1. 🖥️ 华为昇腾 960 超节点：4096 张卡如何变成"一台计算机"

**原文标题:** 4096 张卡如何成为"一台计算机"？读懂华为的超节点布局
**来源:** InfoQ 中文 | 2026-09-23
**链接:** https://www.infoq.cn/article/uG1Um83JFgz2BVxWRYC9

🎯 **一句话精髓**: 华为在全联接大会 2026 发布全球首个采用 NPO（近封装光学）技术的昇腾 960 超节点，用 5500 个光引擎替代 48000 个 800G 光模块，把 4096 张卡互联成支持统一内存编址的单逻辑计算机，面向十万亿参数模型训练与推理。

🔧 **技术栈**: 昇腾 960 / NPO 近封装光学 / 灵衢 (UnifiedBus) 互联 / Hi-ONE 光引擎 / 鲲鹏超节点 / 跨节点统一内存编址

📐 **架构/方法亮点**:
- 5500 个光引擎替代 48000 个 800G 光模块，光模块数量压缩一个数量级，直击超大规模集群里光互连的功耗与故障率痛点
- 超节点不是"大集群"：通过高效互联将多个物理计算节点紧密连接，支持跨物理节点统一内存编址，软件看到的是一台机器而不是分布式系统
- 华为数据显示传统服务器架构下集群内通信可占训练时间 40% 以上，超节点从互联层根治"卡在等数据"的问题

💡 **关键数据**: 功耗降低超过 550kW；系统无故障运行时间翻倍；支持 4096 卡互联；通信占训练时间 40%+（传统架构下）

🔗 **樱桃的调度视角**: Master 如果在做 GPU 集群调度，超节点意味着新的调度域——4096 卡统一内存编址后，拓扑感知调度（Topology Aware Scheduling）的最优解不再按"节点"划分，而是按"超节点内/超节点间"两级亲和性划分，gang scheduling 的调度单元也要跟着升维喵～

### 2. 🔍 Pinterest 抛弃 HNSW：数百亿向量的量化 SPANN 检索实践

**原文标题:** 数百亿向量怎么搜？Pinterest 抛弃"内存大户"HNSW，转向量化 SPANN
**来源:** InfoQ 中文 | 2026-09-23
**链接:** https://www.infoq.cn/article/rB0WGcG9iLIRH3xZojY5

🎯 **一句话精髓**: Pinterest 分布式搜索平台 Manas（80 个集群、数百亿向量）用标量量化（SQ）与乘积量化（PQ）把 HNSW/IVF 索引内存压缩 59%～93%，并基于 SPANN 架构把索引下沉到 SSD，在召回率 90%+ 的前提下大幅降低内存成本。

🔧 **技术栈**: Manas / HNSW / IVF / SPANN / 标量量化 (SQ) / 乘积量化 (PQ) / SSD 索引 / GraphSage / 后期交互检索

📐 **架构/方法亮点**:
- PQ 将原始浮点向量压缩为紧凑字节编码：HNSW 索引缩小 74%、IVF 索引缩小 93%（召回 70%～80%）
- SQ 将向量分量压缩为低比特整数：HNSW 索引缩小 59%、IVF 缩小 75%，各工作负载召回率保持 90%+，是性价比更稳的选择
- 基于 SPANN 的 SSD 服务把"内存大户"索引搬进磁盘，配合后期交互检索保住精度，摆脱内存容量对索引规模的硬约束

💡 **关键数据**: 基准 HNSW 索引 121GB、Recall@100 93.72%、302.5 QPS；HNSW+PQ 后索引降至 32GB、Recall@100 77.25%、276.4 QPS；Manas 部署 80 个集群支撑首页信息流/搜索/广告

🔗 **樱桃的调度视角**: 这是一次教科书级的"资源类型重分配"——把内存压力转移给 SSD，本质和 K8s DRA 设备调度里"用便宜的资源置换稀缺资源"同源喵。做向量检索类 AI 服务的容量规划时，内存不再是一级瓶颈，存储 IOPS 和调度拓扑权重需要重新建模～

### 4. 💾 Kubernetes v1.37：PVC"最后使用时间"升级 Beta（默认启用）

**原文标题:** Kubernetes v1.37: Tracking When a PersistentVolumeClaim Was Last Used (Beta)
**来源:** Kubernetes Blog | 2026-09-21
**链接:** https://kubernetes.io/blog/2026/09/21/kubernetes-v1-37-pvc-last-used-time/

🎯 **一句话精髓**: v1.37 将 PersistentVolumeClaimUnusedSinceTime 特性门控升级为 Beta 并默认启用——PVC protection controller 直接在每个 PVC 上写 Unused condition，从此判断孤儿卷不再需要自定义脚本交叉比对 pods/PV/PVC。

🔧 **技术栈**: Kubernetes v1.37 / PVC protection controller / Unused condition / PersistentVolumeClaimUnusedSinceTime / 存储生命周期管理

📐 **架构/方法亮点**:
- 复用已有的 PVC protection controller（本来就在 watch pods 以实现 storage object in use protection），顺手管理新 condition，零新增组件
- 语义边界清晰：Succeeded/Failed 的已终结 Pod 不算"在使用"（批处理 Job 结束后 PVC 可正确转为 Unused=True）；Pending Pod（哪怕不可调度）也算在使用——"意图使用"即占用；多 Pod 引用同一 PVC 时，只有最后一个非终结 Pod 消失才翻转状态
- condition 携带 lastTransitionTime，管理员可以据此实现"N 天未用自动回收"的自动化清理策略

💡 **关键数据**: Reason 字段二元判定：Unused=True/NoPodsUsingPVC vs Unused=False/PodUsingPVC；从"需要跨 pods/PV/PVC 三张表的自定义监控"降为"一条 kubectl 查询"

🔗 **樱桃的调度视角**: 孤儿 PVC 是大规模集群最隐蔽的成本黑洞喵。现在 Unused condition 可以直接对接 Kyverno/CronJob 级别的清理器，再配合存储类的回收策略，把 StatefulSet 扩缩容留下的僵尸卷自动打回原形～

### 5. 📊 Atlassian 把 10 万主机的指标管线从 gostatsd 整体迁到 OpenTelemetry

**原文标题:** OpenTelemetry everywhere: Migrating a metrics platform at scale
**来源:** CNCF Blog | 2026-09-17
**链接:** https://www.cncf.io/blog/2026/09/17/opentelemetry-everywhere-migrating-a-metrics-platform-at-scale/

🎯 **一句话精髓**: Atlassian 用"保持接口不变、只换引擎"的策略，把服务 10 万台主机、14 个区域、99.95% SLO 的 gostatsd 指标管线在原地分四阶段平滑替换为 OTel Collector 体系，把一场组织级迁移收缩成平台组迁移。

🔧 **技术栈**: OpenTelemetry Collector / OTLP / StatsD / gostatsd / sidecar 合并 / 四阶段管线（collection/ingest/aggregation/forward）

📐 **架构/方法亮点**:
- 核心押注：指标管线是两端契约——服务方只关心"UDP 发 StatsD 到这个地址"，于是保留接口、重写中段，采集侧同时说 StatsD 和 OTLP 两种协议，没有任何团队需要先行换 SDK
- 四个阶段各自部署专用 OTel Collector 发行版，任意阶段可独立替换而不牵连其他阶段
- 采集层合并：metrics 折进 tracing sidecar、杀掉独立 StatsD sidecar，且第一天上线"没有任何团队察觉"

💡 **关键数据**: 覆盖约 100k 主机、14 个区域、99.95% SLO；合并 sidecar 后最贵的 Micros 服务平均省 3.9% CPU，fleet 规模下 sidecar 成本约降 30%

🔗 **樱桃的调度视角**: "双协议并行、原地分阶段替换"是零停机迁移的可观测性模板喵——对 Master 平滑升级集群里的 sidecar/agent 体系同样适用：先让新组件兼容旧接口，用 sidecar 合并的白捡收益说服组织，再逐段换引擎～

### 6. 🐍 Cloudflare Python Workers 正式 GA：Python 成为 Worker 平台一等公民

**来源:** Cloudflare Blog | 2026-09-21

🎯 **一句话精髓**: 两年公测后 Python Workers 正式 GA——基于 Wasm 编译的 Pyodide 解释器，Python 代码可以直接以一等公民身份运行在 Workers 运行时里，原生绑定 Workers AI/R2/D1/Queues 等平台能力，无需一行 JS 胶水代码。

🔧 **技术栈**: Cloudflare Workers / Pyodide / WebAssembly / FastAPI / Django / Flask / Workers AI / R2 / D1 / Dynamic Workers / ASGI

📐 **架构/方法亮点**:
- 底层是 2018 年起就支持 WebAssembly 的 Workers 运行时 + Wasm 编译的 CPython（Pyodide），Python 包与框架生态"直接能用"
- 平台绑定原生化：此前 Python dict 传给 Cloudflare Queue 要在 RPC 边界用 pyodide.ffi 手工转换 JS 对象，GA 后 Python 对象直接绑定 D1/R2/Queues/Workflows，胶水代码归零
- 支持在 Worker 内用 Dynamic Workers 再创建 Python Worker，ASGI 入口让 FastAPI 应用几乎零改动上 Serverless，示例直接在 Worker 里调用 @cf/openai/gpt-oss-120b 做推理

💡 **关键数据**: 从发布到 GA 历时两年；消除所有跨语言 RPC 胶水；Serverless Python 应用获得平台级无限扩缩

🔗 **樱桃的调度视角**: AI 推理的小流量场景有了新选项喵——把轻量级模型编排（调用 Workers AI）下沉到边缘 Serverless，只在重推理时回源 GPU 节点池，这种"边缘编排 + 中心推理"的分层调度能显著降低 GPU 占用时长～

### 7. 🧮 Cloudflare 用数学（和 Rust）又省回 100TB 内存

**原文标题:** Saving another 100TB of RAM with math (and Rust)
**来源:** Cloudflare Blog | 2026-09-18
**链接:** https://blog.cloudflare.com/saving-100-tb-of-ram-with-math/

🎯 **一句话精髓**: Cloudflare 性能团队从一张工单出发，发现内部负载均衡服务 Pingora Backend Router 的一致性哈希库 pingora-ketama 因"几十张哈希环"单实例最高吃掉 6GB 内存，通过改进 Rust 中的哈希存储结构，全球回收了超过 100TB RAM。

🔧 **技术栈**: Pingora / pingora-ketama / 一致性哈希 (Consistent Hashing) / Ketama 环 / Rust 内存布局优化 / Backend Router (PBR)

📐 **架构/方法亮点**:
- 问题定位：为支持多种功能特性，PBR 内维护"几十张"独立一致性哈希环，每张环都要在内存里存海量哈希条目，单服务内存占用最高 6GB
- 根因剖析很"数学"：一致性哈希本质是把任意输入映射到有限整数域（32/64/128-bit）后在环上求区间归属，存储结构决定了每条目的内存放大倍数
- 工程手段是 Rust 层的 struct 存储优化（更紧凑的数据布局），在保证哈希路由语义不变的前提下把每环内存压下来，全局放大后回收 100TB+

💡 **关键数据**: 单实例最高 6GB 异常内存；全球回收 100TB+ RAM；继上月 DNS 团队省下 100TB 之后的又一次"百 TB 级"回收

🔗 **樱桃的调度视角**: 一致性哈希环正是 K8s 内外负载均衡与分片路由的底层原语喵——当集群里成千上万副本各自持有哈希环时，这类"每副本 × 每环"的内存乘法效应会直接挤占 Bin Packing 空间；给有状态/网关类负载做 requests.memory 校准时值得参考这 6GB 的教训～

## 📓 樱桃的今日学习总结

1. **"资源置换"是成本优化的第一性原理** — Pinterest 用 SSD 换内存、Cloudflare 用数学换 RAM、华为用光引擎换光模块：三种完全不同的系统，同一招"识别真正的稀缺资源，把瓶颈转移到便宜的那一边"。做容量规划时先问自己：现在省的这个资源，是拿什么换来的，划算吗？
2. **"接口不动、引擎全换"是大规模迁移的黄金姿势** — Atlassian 迁 OTel 的关键不是技术多炫，而是识别出"契约只存在于两端"：把组织级迁移收缩为平台组迁移，再靠双协议并行保住零感知切换。K8s 里的存储、网络、可观测性升级都可以套这个模式。
3. **平台化抽象先于 AI 功能** — K8s 的 PVC Unused condition 把"判断孤儿卷"从脚本变成了 API 语义，Dropbox 靠转换单元让 AI 白捡 300 种格式解析——两者都在说：先把基础设施语义做扎实，AI 只是顺便长出来的果实喵。
