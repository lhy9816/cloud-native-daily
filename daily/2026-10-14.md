### 1. 📦 Uber ServiceScale：把「扩容意图」和「执行动作」彻底解耦

**原文标题:** Uber 在 Kubernetes 平台上将扩容意图与执行操作解耦
**来源:** InfoQ 中文 | 2026-10-11
**链接:** https://www.infoq.cn/article/2SNgaiHoK808v22dl5SJ

🎯 **一句话精髓**: Uber 发布 ServiceScale 控制器，让多个编排器可以安全地操作同一组 K8s 工作负载的扩缩容——把「想要什么」(意图) 与「谁来改副本数」(执行) 分离，从而无需常备闲置容量就能支撑区域故障转移。

🔧 **技术栈**: Kubernetes / ServiceScale 控制器 / Up 平台（集群联邦层） / Uber 部署控制器 UDC / 多云（Oracle Cloud + Google Cloud）

📐 **架构/方法亮点**:
- 意图与执行分离：服务所有者只声明扩缩容预期，UDC 将意图调和（reconcile）为 K8s 原语，多个编排器经 ServiceScale 协调后安全共存于同一组工作负载
- 区域故障转移新思路：从「所有数据中心预留空闲容量」改为「复用低优先级工作负载的容量」——故障时缩容低优、扩容高优
- 内部平台 Up 作为 Kubernetes 集群联邦层，统一管理数据中心与云厂商集群

💡 **关键数据**: 100+ 计算集群（跨数据中心与两家公有云）、约 4000 个服务、300 万核 CPU、每天启动 150 万个 Pod

🔗 **樱桃的调度视角**: 这是「意图式扩缩容」在超大规模下的工业级实证——低优负载兜底容量本质上是集群内的抢占式调度策略，和 Kueue/Volcano 的队列配额思路殊途同归；Master 如果在做多集群或混部容量规划，这篇的意图/执行分层非常值得抄喵。

### 2. 📦 Kubernetes 官方定调：cgroup v1 进入维护模式，v2 成为资源管理主航道

**原文标题:** The Shift to cgroup v2 in Kubernetes: What You Need to Know
**来源:** Kubernetes Blog（官方） | 2026-10-06
**链接:** https://kubernetes.io/blog/2026/10/06/kubernetes-cgroups-v2-shift/

🎯 **一句话精髓**: K8s 官方确认资源管理的代际切换——cgroup v1 自 v1.31 起进入维护模式（只修不增），v2 自 v1.25 起 stable，凭借统一层级成为现代资源隔离与 QoS 的基础。

🔧 **技术栈**: Linux cgroup v2 / kubelet / 统一层级（unified hierarchy） / CPU & Memory 资源管理

📐 **架构/方法亮点**:
- cgroup v2 采用单一统一层级，取代 v1 的多棵独立层级树，接口更一致
- v2 为更精细的资源隔离与现代资源管理特性（如更准确的内存 QoS 划分）提供内核基础
- 官方明确版本节点：v2 支持 v1.25 起稳定，v1 管理自 v1.31 起维护模式——升级路径要提前规划

💡 **关键数据**: 2 个版本分界线——v1.25（v2 stable）/ v1.31（v1 maintenance mode）；对存量集群而言这是「什么时候必须迁」而不是「要不要迁」的问题

🔗 **樱桃的调度视角**: 调度器的所有资源承诺最终都靠 cgroup 落地；GPU/AI 负载对内存 QoS 敏感（显存回收不能靠 OOM 硬杀），v2 的 memory 相关接口是后续资源模型演进的前提，建议把节点镜像和内核版本升级排进 roadmap 喵。

### 3. 🚀 vLLM v0.31.0 发布：DeepSeek-V4.1-Flash 全链路融合 + 秒级引擎重启

**原文标题:** vLLM v0.31.0
**来源:** GitHub Releases（vllm-project/vllm） | 2026-10-05
**链接:** https://github.com/vllm-project/vllm/releases/tag/v0.31.0

🎯 **一句话精髓**: 717 个 commit 的大版本：DeepSeek-V4.1-Flash 在 SM100 上默认启用 FlashMLA + NVFP4 压缩 KV cache 的全链路 kernel 融合，同时 `vllm preload` 权重缓存守护进程让引擎重启不再从磁盘重载权重。

🔧 **技术栈**: vLLM / FlashMLA / NVFP4 & MXFP8 量化 / DeepGEMM / CUDA Graphs / TP 并行 / 权重缓存守护进程（weight-cache daemon）

📐 **架构/方法亮点**:
- DeepSeek-V4.1-Flash 性能线：FlashMLA mega attention + NVFP4 压缩 KV cache 成为 SM100 默认；DeepGEMM sparse MQA logits；Mega-Gate 把 gate GEMM 与 expert selection 融合；解码端融合 TP all-reduce 与 MoE finalize
- 快速重启：`vllm preload` CLI 启动权重缓存守护进程，量化后权重常驻 GPU 显存，跨引擎重启直接映射复用，并支持数据并行、MTP draft 模型、/health 端点与就绪等待
- MXFP8 `wo_b` GEMM 与 sequence-parallel reduce-scatter 融合、SWA bounded replay 把滑动窗口 KV 挡在 prefix caching 之外

💡 **关键数据**: 717 commits / 307 位贡献者（96 位新人）；KV cache 从 FP16 压到 NVFP4 直接腰斩显存占用；权重驻留显存后重启省去磁盘重载环节

🔗 **樱桃的调度视角**: 「权重常驻显存 + 秒级重启」改变了推理服务的调度假设——驱逐代价大幅下降后，Pod 重调度/抢占对 SLO 的冲击更可控，配合 K8s DRA 做卡级调度时可以更放心地做 bin-packing 喵。

### 5. 📦 Meta ZGateway：每秒 10 亿次操作，把 ZippyDB 连接数压缩 19 倍

**原文标题:** Meta ZGateway 在每秒处理超过 10 亿次操作的同时，将 ZippyDB 的连接数减少了 19 倍
**来源:** InfoQ 中文 | 2026-10-12
**链接:** https://www.infoq.cn/article/d5x9BkQ9AoIZq5mf6LN0

🎯 **一句话精髓**: Meta 为分布式 KV 存储 ZippyDB 加了一层无状态代理 ZGateway：客户端只连区域网关（粘性连接），数据库只接受受控网关集群的连接，用「连接汇聚」终结百万客户端的连接风暴。

🔧 **技术栈**: ZippyDB / ZGateway 无状态代理 / ServiceRouter（Meta 服务网格） / C++ 请求引擎 / 读透式缓存（read-through cache）

📐 **架构/方法亮点**:
- 直连模型下单个客户端要连数十万台 DB 主机上的数万个分片，形成稠密多对多连接网格，连接风暴导致文件描述符耗尽与 OOM——ZGateway 在中间做两层收敛
- 客户端 ↔ 区域网关保持粘性连接，网关 ↔ DB 侧连接完全受控；经 ServiceRouter 发现，客户端始终就近接入网关
- 复用 Meta 现有 C++ ZippyDB 客户端作为请求引擎，同时支持纯代理与读透缓存两种形态

💡 **关键数据**: >100 万客户端主机；每秒处理 >10 亿次操作、承担 ZippyDB 约 40% 流量；每主机连接数减少约 97%~98%，持久连接总数降为原来的约 1/19

🔗 **樱桃的调度视角**: 这是「sidecar/代理层拓扑感知」的经典题——连接收敛本质上是把 any-to-any 网状流量改造成 hub-and-spoke，K8s 里用 topology-aware routing + 无状态代理层（Deployment 按区打散）就能复刻同款架构喵。

🎯 **一句话精髓**: 面对「到底能给 Agent 多大权限操作我的 K8s 集群」这个问题，作者给出的设计答案是：Agent 不直接执行，而是产出对系统下一状态的提议，经策略/人类门禁后由既有控制面落地。

- 把「自主系统操作机器」的信任问题转化为控制平面设计问题：审批、回滚、审计全部复用现有 K8s/GitOps 机制
- 作者坦承没有普适答案，权限大小取决于具体场景，但「不给 root」应是默认底线

💡 **关键数据**: 无具体基准数字——本文价值在设计原则：Agent 权限默认为零，一切变更走「提议 → 门禁 → 应用」的显式链路

🔗 **樱桃的调度视角**: 对正在搭 AI SRE / 运维 Agent 的团队，这就是权威边界的画法：让 Agent 写不了 etcd、只能提交 Kustomize patch；调度侧再配 admission webhook 兜底，两层防线各管一段喵。

### 8. ☁️ 高可用 ≠ 弹性：一次 TLS 升级如何让整个区域的流量凭空消失

**原文标题:** 高可用不等于弹性：云系统为何在关键时刻失效
**来源:** InfoQ 中文 | 2026-10-13
**链接:** https://www.infoq.cn/article/CNMCVLwkvFb120huYzr9

🎯 **一句话精髓**: 一个满足合规的 TLS 1.3 升级让 Route 53 健康检查静默失败（它要求 TLS 1.2），CDN 判定区域不健康并把流量甩到数千公里外——数据平面一切正常，坏掉的是「决定流量去向」的控制平面。

🔧 **技术栈**: Route 53 HTTPS 健康检查 / CDN 全局流量调度 / TLS 1.3 / 多区域故障转移 / 合成监控（synthetic monitoring）

📐 **架构/方法亮点**:
- 故障链：仅启用 TLS 1.3 → 健康检查握手失败 → 端点被标记不健康 → 区域被摘除 → 流量透明重路由数千公里
- 区域内部所有指标绿：服务在线、LB 健康、请求持续处理——唯一症状是流量不再流入，内部遥测完全盲区
- 概念澄清：高可用 = 以最小中断应对「预期内」故障；弹性 = 从「设计时未预料」的异常中恢复；健康检查这类依赖要和被检查对象一起纳入变更评审

💡 **关键数据**: 约 40 分钟才定位根因；故障期间受影响区域延迟急剧上升、故障转移区域被动扩容承接未预估负载

🔗 **樱桃的调度视角**: 这正是全局负载均衡（GSLB）作为「跨集群调度器」的盲区案例——健康检查探针本身是控制平面依赖，建议探针的协议约束与业务端点一起进 CI 校验，多集群调度策略里也要给「区域误摘除」设计半开熔断喵。

## 📓 樱桃的今日学习总结

1. **意图与执行分离是调度系统走向多编排器共存的前提** — Uber ServiceScale 和 CNCF「Agent 只提议不执行」本质是同一个模式：把「想要什么」变成可审、可批、可调和的声明，把「怎么做」留给唯一可信的执行层。这套分层在任何多租户/多控制器系统里都成立。
2. **AI 基础设施的经济学正在重塑调度假设** — MiMo 单步 RL 27~37 亿 Token、vLLM 把权重钉在显存里换秒级重启：当「算力成本」和「驱逐代价」变成显式数字，调度器设计目标就从「能跑」转向「每 Token 成本最优」，GPU bin-packing 与权重缓存会成为推理平台的标配。
3. **控制平面是新的故障面** — TLS 健康检查摘除整个区域、连接风暴打爆文件描述符：数据平面越稳，事故越往控制平面和依赖链上游转移；健康探针、代理层、联邦策略这些「调度的调度器」需要与业务同等强度的测试和灰度。
