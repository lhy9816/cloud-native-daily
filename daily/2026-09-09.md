### 2. 🔌 K8s v1.37 DRA 大更新：Extended Resource GA，调度吞吐翻倍

**原文标题:** Kubernetes v1.37: DRA Updates
**来源:** Kubernetes Blog | 2026-09-03
**链接:** https://kubernetes.io/blog/2026/09/03/kubernetes-v1-37-dra-updates/

🎯 **一句话精髓**: DRA（Dynamic Resource Allocation）Extended Resource 支持正式 GA——传统 `example.com/gpu` 式资源请求可以直接由 DRA 驱动满足，存量工作负载零改动迁移到新设备模型；PreQueueingHint 扩展点则把调度器在大规模扩容时的 O(N²) 重队列成本降到 O(1)。

🔧 **技术栈**: DRA / ResourceClaim / DeviceClass / DeviceTaintRule / CEL 表达式 / CDI / PreQueueingHint / ResourceSlice

📐 **架构/方法亮点**:
- Extended Resource GA：扩展资源名直接设在 DeviceClass 上，Pod 按老写法请求 `example.com/gpu`，由 DRA 完成设备匹配，工作负载侧无需 ResourceClaim、也无需再部署 device plugin——1.34 KEP → 1.35 alpha → 1.36 beta → 1.37 stable 三连跳
- 设备染色 GA：DRA 驱动可把故障设备标记为 tainted，新 Pod 调度自动跳过，管理员用 DeviceTaintRule 做集群级染色，已使用该设备的 Pod 若未显式容忍会被自动驱逐——把 node taint/toleration 语义复制到了单个设备粒度（如拔一块 GPU 做维护）
- 标准化 numaNode 属性：`resource.kubernetes.io/numaNode` 成为跨驱动的共享属性名，不同厂商设备的 NUMA 亲和性终于可在同一坐标系比较；Derived Attributes 进一步用 CEL 表达式自定义设备配对规则（GPU+NIC 同 NUMA 组网不用再等厂商统一命名）
- PreQueueingHint 扩展点（alpha）：ResourceClaim 事件到来时，调度器不再全量扫描每个不可调度 Pod，而是用 pod informer 索引直取受影响者

💡 **关键数据**: PreQueueingHint 将大规模扩容场景的重队列路径从 O(N²) 降至 O(1)，早期基准测试调度吞吐量约翻倍；Workload ResourceClaims（Beta）解除单 Claim 256 Pod 的旧上限；DRA Device Compatibility Groups 可在调度期提前拒绝 MIG 与 vGPU 分区的不兼容组合

🔗 **樱桃的调度视角**: 这是 GPU 调度方向今年最重要的一条喵——Extended Resource GA 给了平滑迁移路径（先换后端、不动负载），taint 驱逐 + NUMA 标准化 + CEL 配对则是做 GPU 拓扑感知调度的三块新积木，建议把 v1.37 的 DRA changelog 通读一遍。

### 3. ⚡ FreeToken：RTX 4060 跑 35B MoE 每秒 39 token，CPU+GPU 动态协同调度

**原文标题:** RTX 4060 跑 35B 模型，每秒 39 Token？伯克利、MIT 联手开源 FreeToken
**来源:** InfoQ 中文 | 2026-09-05
**链接:** https://www.infoq.cn/article/tij5T0vJ1Yk0s7Uov7SE

🎯 **一句话精髓**: 伯克利与 MIT 的开源推理引擎 FreeToken 把消费级 PC 重新定义为「可弹性调度的异构计算资源」——用 q* 动态协同调度策略取代静态专家卸载，让 MoE 解码在 PCIe 瓶颈下不再停摆。

🔧 **技术栈**: FreeToken / MoE / q* 协同调度策略 / FTW 快速权重格式 / PCIe / CPU 张量核心协同

📐 **架构/方法亮点**:
- 痛点定位清晰：MoE 解码要在数千亿未激活权重间路由，数据中心靠 NVLink 掩盖传输开销，消费级硬件的 PCIe（16～64 GB/s）和主机内存延迟成为致命瓶颈
- 静态卸载的缺陷：现有边缘运行时把未激活专家权重留在系统内存，激活时同步搬上 GPU，缓存未命中即全流程停顿
- q* 策略：缓存未命中时 GPU 不停等，而是按实时互连吞吐量在 CPU 核心与 GPU 张量核心之间动态分配 token 计算；配套 FTW（快速权重格式）与整层[加载]机制降低传输与转换成本

💡 **关键数据**: RTX 4060（消费级）跑 35B 参数 MoE 模型达到每秒 39 token；PCIe 吞吐典型值 16～64 GB/s；作者阵容含 Matei Zaharia 与 Ion Stoica（Databricks 联合创始人）、Song Han、Kurt Keutzer

🔗 **樱桃的调度视角**: 「按互连实时吞吐量分配计算」本质是把调度决策下沉到了硬件链路层——这套思路对 K8s 上的混合算力节点（GPU 节点同时跑 CPU 侧推理）有直接启发：拓扑感知调度（NUMA/PCIe）不该只在 Pod 放置时考虑，运行时的算力分配同样要感知互连喵～

**来源:** GitHub Trending（Go 周榜）| 2026-09-09 采集

🎯 **一句话精髓**: vLLM 官方生态的语义路由器把「请求该走哪个模型」做成可编程基础设施——基于请求信号、用户偏好与应用策略，在异构 LLM 基础设施上为每个请求选择或组合出最优模型路径。

💡 **关键数据**: 本周 Go 语言趋势榜上榜；2025-09 项目发布至今迭代 3 个大版本；AMD 提供官方 GPU/ROCm 资源赞助

🔗 **樱桃的调度视角**: 这就是「推理层的 K8s 调度器」喵——Pod 调度解决「负载放哪」，Semantic Router 解决「请求发给谁」，两者组合才是完整的 AI 推理资源编排；在多模型服务网格里做流量治理时值得重点评估。

### 5. 🖥️ CPU+GPU：AI 平台工程本质是异构基础设施问题

**原文标题:** CPU + GPU: Why AI platform engineering is a heterogeneous infrastructure problem
**来源:** CNCF Blog（作者 Kasia Hilborne, Vultr）| 2026-09-04
**链接:** https://www.cncf.io/blog/2026/09/04/cpu-gpu-why-ai-platform-engineering-is-a-heterogeneous-infrastructure-problem/

🎯 **一句话精髓**: 平台团队的正确提问不是「这个负载要几张 GPU」，而是「每个阶段需要什么资源、阶段之间依赖是什么」——GPU 利用率低未必是需求不足，可能是加速器在等 CPU 预处理、数据读取或调度。

🔧 **技术栈**: Kubernetes / DRA / 异构资源编排 / CPU 预处理 / tokenization / 检索增强 / 可观测性关联分析

📐 **架构/方法亮点**:
- 全链路视角：典型推理管线「数据 → CPU 预处理 → GPU 推理 → CPU 后处理 → 应用」中，预处理供不上数据加速器就空转，存储送不动模型工件启动就变慢，CPU/内存/网络受限时加 GPU 无济于事
- 阶段差异化：LLM 推理内部 prompt processing 与 token generation 的计算/内存画像不同，为平台按阶段匹配资源（而非整条管线塞进单一资源模板）创造空间
- 可观测性升级：需要把基础设施遥测与应用遥测关联起来，回答「时间花在哪、哪个资源是瓶颈」；目标不是每个资源都跑满 100%，而是整体协同满足性能要求

💡 **关键数据**: 核心论点引用 DRA 的方向——专用计算正在成为与其余应用同一套云原生资源模型的一部分（本文无具体基准数据，属方法论文章）

🔗 **樱桃的调度视角**: 给做 GPU 资源利用率的 Master 提个醒喵：看到 GPU 利用率低先别急着缩容或加卡，用全链路 trace 确认瓶颈在 CPU 侧预处理还是数据管道——调度器侧的对应动作是给 CPU 密集的前后处理 Pod 配置 GPU Pod 的亲和性/反亲和性拓扑。

### 6. 🎙️ OpenAI 首曝 GPT-Live 架构：每会话预留算力 + 上下文可迁移的有状态语音推理

**原文标题:** OpenAI 详解 GPT-Live 架构如何实现了连续的有状态语音交互
**来源:** InfoQ 中文 | 2026-09-08
**链接:** https://www.infoq.cn/article/rdESg5icYIZ71J7xb69K

🎯 **一句话精髓**: GPT-Live 用异步 RPC 边界把延迟敏感的实时路径（媒体管道+推理循环）与应用逻辑解耦，并为每个会话在指定实例上预留计算资源、支持上下文跨实例迁移——实时 AI 服务的基础设施范式样本。

🔧 **技术栈**: WebRTC / WARP（WebRTC Abridged Roundtrip Protocol）/ 有状态推理 / 会话粘滞与迁移 / 异步 RPC / 静默测试（shadow traffic）

📐 **架构/方法亮点**:
- 双路径解耦：实时路径内含媒体处理管道与推理循环，保证对话即使在外部服务可变延迟下依然响应；任务委托、工具使用、数据持久化等应用逻辑全部置于异步 RPC 边界之后
- 会话级资源管理：每个会话在其分配的实例上预留计算资源（类似会话亲和 + 资源独占），资源耗尽或触达上下文上限时，上下文可迁移至另一实例——这是「有状态推理负载」的调度原语
- 传输层优化：坚持 WebRTC 作为媒体传输底座，新增 WARP 协议与即时连接机制压缩服务启动延迟
- 上线前静默测试：处理真实入站语音流量但丢弃生成输出，发现了合成测试覆盖不到的负载相关异常行为

💡 **关键数据**: OpenAI 实时 AI 负责人 Justin Uberti 就架构与运营权衡接受 InfoQ 专访（本文为架构披露型文章，未公布具体延迟数字）

🔗 **樱桃的调度视角**: 会话预留 + 上下文迁移这对组合拳，正是 K8s 有状态负载调度（StatefulSet/拓扑Spread/优雅迁移）在推理层的翻版喵——如果 Master 要做实时推理服务，「会话粘滞 vs 资源均衡」的权衡策略可以直接参考 GPT-Live 的迁移设计。

### 7. 🌊 etcd RangeStream 升级 Beta：大列表读取按字节流式分块，OOM 风险收敛

**原文标题:** Kubernetes v1.37: etcd RangeStream Cuts Memory Use on Large List Reads
**来源:** Kubernetes Blog（作者 Jeffrey Ying, Google）| 2026-09-01
**链接:** https://kubernetes.io/blog/2026/09/01/kubernetes-v1-37-etcd-range-stream/

🎯 **一句话精髓**: etcd v3.7 的 RangeStream RPC 把 apiserver 拉取大集合从「按 key 数分页、整页装配」改成「按字节自适应分块、边流边释放」，两侧内存峰值更可预测，坏组合下的大对象 OOM 得到收敛。

🔧 **技术栈**: etcd v3.7 RangeStream RPC / kube-apiserver watch cache / EtcdRangeStream feature gate / KEP-5966 / Prometheus 指标

📐 **架构/方法亮点**:
- 旧机制缺陷：apiserver 按 key 数分页读取 etcd，但页大小对对象体积无感知——大对象（如 Pods）+ 并发读的坏组合足以触发 OOM；unary Range 要在 etcd 侧整页装配、apiserver 解码期间继续持有，同一份 payload 双侧驻留内存
- 流式改造：RangeStream 接收相同 RangeRequest 返回相同结果集，但按返回值大小自适应调块、以字节为界，内存随流推进逐块释放；watch cache 初始化与 list 回退直读 etcd 的路径全部切换
- 兼容性兜底：apiserver 启动时探测 etcd 能力，运行中调用返回 Unimplemented 自动回退老分页路径——配老版本 etcd 也能安全开 beta gate（v1.37 默认开启）

💡 **关键数据**: 要求 etcd ≥ v3.7 + K8s ≥ v1.37；验证指标：`etcd_request_duration_seconds_count{operation="listStream"}` 计数非零即已生效

🔗 **樱桃的调度视角**: 大规模集群每次节点扩容都会触发全量 Pod list（scheduler/node informer 初始化），RangeStream 直接削平了这个内存尖峰——升级 etcd 3.7 后可以用这条指标确认生效，属于「低风险白捡的稳定性」喵～

### 8. 🛡️ Rootless Kubernetes 进入 Beta：节点组件全面免 root，五年安全长跑结硕果

**原文标题:** Kubernetes v1.37: KubeletInUserNamespace (aka Rootless mode) Graduates to Beta
**来源:** Kubernetes Blog（作者 Akihiro Suda, NTT）| 2026-09-04
**链接:** https://kubernetes.io/blog/2026/09/04/kubernetes-v1-37-rootless-beta/

🎯 **一句话精髓**: KubeletInUserNamespace 升级 Beta 后，kubelet、CRI/OCI 运行时、CNI 插件、kube-proxy 全部节点组件可以非 root 身份运行——容器逃逸漏洞的危害被限制在命名空间内的非特权账户，攻击者甚至无法篡改内核/引导加载器/固件来隐藏痕迹。

🔧 **技术栈**: Linux user namespace / KEP-2033 / kubelet / CRI-O / runc / containerd / seccomp / hostUsers: false

📐 **架构/方法亮点**:
- 威胁模型实证：列举了该模式缓解的真实逃逸 CVE 链——cr8escape（CVE-2022-0811，CRI-O 任意 sysctl 导致 root 执行）、CVE-2023-27561（runc 卷挂载竞态绕过 masked paths）、CVE-2024-10220（kubelet gitRepo 卷 root 命令执行）、CVE-2025-31133（runc bind-mount 写宿主 procfs）、CVE-2026-53488（containerd 镜像 label 注入命令执行）
- 与 Pod 级 user namespace 互补：`hostUsers: false`（v1.36 GA）只把 Pod 放进 user namespace、节点组件仍以 root 跑；两者可叠加实现无需 `privileged: true` 的 K8s-in-K8s 嵌套
- 场景矩阵清晰：生产集群纵深防御、HPC 共享机免 root 部署、笔记本本地集群防误伤宿主机、AI sandbox（给 AI Coding Agent 单独的账户+测试集群，防止被网上恶意信息诱导的 Agent 破坏宿主机）、Cluster API 引导
- 边界诚实：user namespace 不缓解内核本身漏洞，需搭配 seccomp 限制系统调用面

💡 **关键数据**: 2018 年实验起步 → 2021 年 v1.22 alpha（KEP-2033）→ 2026 年 v1.37 beta，历时 8 年；单条 CVE 影响（如 cr8escape）即为主机级 root 代码执行

🔗 **樱桃的调度视角**: AI sandbox 场景简直是为跑 Agent 的 Master 量身定做喵——给本地测试集群开 rootless，再配合嵌套集群做 Agent 的爆炸半径隔离；GPU 驱动对 user namespace 的兼容性仍是落地前需要验证的点。

## 📓 樱桃的今日学习总结

1. **设备资源语义正在完成「计数 → 声明」的迁移** — DRA Extended Resource GA 让新旧资源 API 共存过渡，Karmada 把这套语义抬升到多集群资源池。方法论：平台演进的关键不是替代而是「换后端不动负载」——存量兼容层（Extended Resource）给迁移留时间窗，新能力（taint 驱逐、NUMA 标准、CEL 配对）在新模型上快速迭代。
2. **推理性能的瓶颈从「算」转移到「连」** — FreeToken 按互连吞吐量在 CPU/GPU 间分配 token、vLLM SR 按信号路由异构模型、CNCF 强调全链路资源协同，三条线索指向同一结论：异构系统的效率取决于「数据搬运 + 决策放置」，纯算子优化边际收益递减。做容量规划时要为互连拓扑（PCIe/NUMA/网络）建立一等资源画像。
3. **有状态 AI 服务的调度原语开始成型** — GPT-Live 的「会话预留 + 上下文迁移」、DRA 的设备状态上报、etcd RangeStream 的可预测内存，共同回答「动态负载如何在共享平台获得确定性」——把运维经验（粘滞、迁移、限流、回退）编码成控制面机制，而不是留在 runbook 里。
