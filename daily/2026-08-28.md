### 1. 📦 在 Kubernetes 上构建 AI 工厂：GPU 池化、DRA 与多租户隔离的全栈蓝图

**原文标题:** Building an AI factory on Kubernetes
**来源:** CNCF Blog | 2026-08-27
**链接:** https://www.cncf.io/blog/2026/08/27/building-an-ai-factory-on-kubernetes/

🎯 **一句话精髓**: 这篇文章系统性拆解了在 K8s 上构建「AI 工厂」的完整技术栈——从裸金属 provisioning 到 GPU 分配、租户隔离、推理服务、计费回充，给出了 16 层架构的落地路线图。

🔧 **技术栈**: DRA（动态资源分配）/ HAMi / MIG / vCluster / KAI Scheduler / Volcano / Kueue / vLLM / KServe / llm-d / KubeVirt / Cilium / Multus / SR-IOV / OpenCost / Falco

📐 **架构/方法亮点**:
- GPU 分配双轨制：DRA（K8s 1.34 GA）提供富设备声明模型，但分数级密度来自设备层——HAMi 做软件级 per-pod 内存/算力限制，MIG 做硬件级隔离；信任域内用分区提升密度，跨租户用整卡隔离
- 租户隔离双平面：控制平面用 vCluster 虚拟集群（每个租户独立 API server + CRD + RBAC），数据平面用 DPU（BlueField/Pensando）将隔离和加密卸载到硬件
- 调度分层：KAI Scheduler 和 Volcano 负责 Gang 调度和拓扑感知放置，Kueue 负责排队、准入和配额——调度与资源分配解耦

💡 **关键数据**: AI 工厂的核心衡量指标是 GPU 利用率而非单次 tokens/s；SemiAnalysis 的 ClusterMAX 评分体系将安全隔离（per-tenant 集群、DPU 隔离）权重置于原始吞吐量之上

🔗 **樱桃的调度视角**: 这篇文章几乎覆盖了 Master 关注的所有方向——DRA 如何改变调度器对 GPU 的认知模型、HAMi 如何在共享 GPU 上做软隔离、KAI Scheduler 的拓扑感知放置。特别值得注意是「拓扑感知而非资源感知」的结论：NVLink 域、NUMA 节点、GPUDirect RDMA 路径，调度时不考虑任何一个都会导致集合通信卡在最慢的一跳上。

### 2. 📦 大模型推理加速全链路：从算子优化到异构调度的清华方案

**原文标题:** 大模型推理加速全链路：内存管理、编译优化、量化与并行策略
**来源:** InfoQ 中文（QCon 2026 北京站演讲整理） | 2026-08-27
**链接:** https://www.infoq.cn/article/AN2AuAT58V9fe8KXD2zi

🎯 **一句话精髓**: 清华大学金煜阳团队提出覆盖算子级图层优化、KV Cache 内存管理、混合精度量化、CPU-GPU 异构调度与自适应并行的全链路推理加速方案，并在开源引擎「赤兔」中完成国产芯片适配验证。

🔧 **技术栈**: FlashTensor / KV Cache Paged Attention / Triton / TensorRT / Tensor Core / MoE / Mamba 线性注意力 / vLLM / SGLang / 华为昇腾 / 摩尔线程

📐 **架构/方法亮点**:
- FlashTensor 细粒度图层优化：定义细粒度张量属性描述算子间复杂依赖结构，在最大化并行度条件下重组计算，解决粗粒度融合导致的并行度受限或中间张量访存爆炸问题
- KV Cache 异构内存管理：GPU 显存 → CPU 内存动态转移 + 预取，借鉴操作系统页表机制做动态内存分配（vLLM Paged Attention），减少内存碎片
- 异构调度基础：Prefill 是计算密集型（一次性处理整段输入），Decode 是访存密集型（逐 token 生成，每次需访问全部上下文），两阶段资源需求截然不同，为异构调度和并行策略设计埋下伏笔

💡 **关键数据**: FlashTensor 在 A100/H100 上端到端推理时间提升 1.5-1.86 倍；Sparse Attention 算子在粗粒度处理下计算效率仅 3.45%（正常应 80-90%）；DeepSeek V4 参数已达万亿级

🔗 **樱桃的调度视角**: Prefill/Decode 两阶段资源特性的差异直接影响 GPU 调度策略——如果 K8s 上的推理服务能将 Prefill 和 Decode 分配到不同特性的 GPU 上（类似 disaggregated inference），就能显著提升集群整体利用率。这与今天 CNCF AI 工厂文章中 NVIDIA Dynamo/llm-d 推动的「分离式推理」方向一致喵～

### 3. 📦 懒加载容器镜像的「谎言」：K8s 上模型服务的延迟代价与故障语义

**原文标题:** The Lazy Pod That Lies: Deferred Cost and Failure Semantics of Lazy Container Image Pulling for Model Serving on Kubernetes
**来源:** arXiv cs.DC | 2026-08-19
**链接:** https://arxiv.org/abs/2608.19412

🎯 **一句话精髓**: 这篇论文系统评估了懒加载镜像拉取在 K8s 模型服务场景下的真实表现——冷启动确实变快了，但代价被延迟而非消除，且引入了一种 eager pulling 不可能出现的缓存耗尽故障模式。

🔧 **技术栈**: KServe / eStargz / stargz-snapshotter / AWS SOCI / Kubernetes / fp16 模型权重

📐 **架构/方法亮点**:
- 懒拉取的 headline 成立：冷启动到首次预测时间（cold TTFT）变为与镜像大小无关（16.9-17.6s vs eager 的 24.5-573.0s），但完整读取 14GB 模型通过懒挂载需 105.3s，比 eager 的 72.4s 更慢
- 两种系统代价相反：SOCI 几乎在 Ready 前预取完整镜像，eStargz 将几乎所有延迟到首次读取
- 关键故障模式发现：snapshotter 节点级缓存耗尽后，正在运行的 Pod 开始读取模型文件失败——一个被检测 Pod 在 snapshotter 已记录 196 秒真实故障期间通过了所有 K8s 可见和应用级健康检查；重压下 67-94% 模型文件读取失败

💡 **关键数据**: 2-140GB 模型权重实测；缓存耗尽时模型文件失败率 67-94% 且与残余缓存占用单调相关；snapshotter daemon 重启会导致 Running 状态 Pod 中的文件句柄永久过期

🔗 **樱桃的调度视角**: 这对 Master 的 AI 推理调度直接相关——如果用懒拉取加速模型 Pod 冷启动，必须同时设计缓存容量规划和监控策略。论文揭示了一个调度盲区：K8s 调度器看到的 Pod 状态（Running/Ready）与底层存储实际健康状况之间存在显著时间差，需要 DCGM exporter 级别的存储层监控来弥补。

### 4. 📦 K8s 调度的计算复杂性：Inter-Pod 亲和性约束下 Pod 可部署性是 PSPACE 完全的

**原文标题:** Pod-Deployability in Kubernetes with Inter-Pod Affinity Constraints is PSPACE-Complete
**来源:** arXiv cs.DC | 2026-08-20
**链接:** https://arxiv.org/abs/2608.19822

🎯 **一句话精髓**: 这篇论文严格证明了 Kubernetes 调度器中 Pod 间的 required affinity 约束使得「Pod 可部署性问题」是 PSPACE 完全的——意味着带亲和性约束的调度序列规划在理论上就是指数级复杂度。

🔧 **技术栈:** Kubernetes 调度器 / label-based affinity / anti-affinity / Petri 网可达性 / pebbling 复杂性

📐 **架构/方法亮点**:
- 三层复杂性结果：① 无 affinity（仅 anti-affinity）时可在多项式时间内判定；② required affinity + required anti-affinity 使问题 PSPACE 完全；③ 仅 required affinity 在单节点单一标量资源下也已是 PSPACE 完全
- 下界归约编码：分别用 1-safe Petri 网覆盖性和 bounded black pebbling 证明，隔离了 K8s 调度中状态空间复杂度的两个独立来源——逻辑排斥和资源受限的前置依赖管理
- 现实意义：调度器的「贪心+过滤」策略之所以在实践中可行，正是因为它回避了全局最优的序列规划，但这也意味着某些合法部署序列可能永远无法被贪心策略找到

💡 **关键数据**: 无亲和性时 P 时间可解，有 required affinity 时 PSPACE 完全（即使在单节点单资源约束下）

🔗 **樱桃的调度视角**: 这为 Master 提供了一个理论参照——当集群规模扩大、亲和性规则变复杂时，不要期望调度器总能找到全局最优解。这也解释了为什么 KAI Scheduler、Volcano 等需要 Gang 调度能力：它们通过约束问题结构（如 Gang 的 all-or-nothing 语义）来绕过一般性的 PSPACE 困难。调度策略设计应该关注「约束结构」而非追求通用最优。

### 5. 📦 Flux Mirror 插件：只让可信制品进入 K8s 集群的供应链「二极管」

**来源:** InfoQ 中文 | 2026-08-27
**链接:** https://www.infoq.cn/article/p8qELFuWcdBic11PXG72

🎯 **一句话精髓**: Flux v2.9 推出 Mirror CLI 插件，可在注册表间声明式镜像容器镜像、Helm Chart 和 OCI 制品，结合 Cosign 签名验证和制品最短存续时间策略，构建从公共注册表到私有集群的供应链「单向二极管」。

🔧 **技术栈:** Flux v2.9 / OCI 注册表 / Cosign 签名 / SBOM / Helm Chart / Gitless GitOps / GitHub Actions / Kubernetes CronJob

📐 **架构/方法亮点**:
- 声明式镜像管线：配置文件描述需镜像内容、来源和目标，将注册表内容作为声明式状态编码在版本控制中；选择器管线由正则、语义化版本约束、排序和 Top-N 限制组成，只镜像实际使用的版本
- 供应链二极管设计：Cosign 签名 + 身份策略 + 制品最短存续时间（minimum age）三重验证——新签名制品会被暂缓，直到公开时间长到被视为安全后才镜像

💡 **关键数据**: 针对 Shai Hulud 蠕虫和 Trivy GitHub Action 被入侵事件（恶意制品在线存在数日）的现实威胁设计；覆盖多架构清单列表逐字节复制

🔗 **樱桃的调度视角**: 虽然不直接涉及调度，但供应链安全是 AI 工厂中 GPU Pod 部署的前提——如果模型镜像被篡改，再好的调度策略也无意义。Master 在设计 K8s AI 平台时，应将制品信任链（签名验证 + 最短存续时间）纳入准入控制层，类似 Kyverno 策略在 Pod 创建时强制校验 imagePullSecret 和签名。

### 6. 📦 Netflix 如何扩展实时服务地图：三阶段流处理 + eBPF + 一致性哈希

**原文标题:** Netflix详述如何扩展其实时服务地图
**来源:** InfoQ 中文 | 2026-08-26
**链接:** https://www.infoq.cn/article/T0CGyJc70O4ss6H2OCj9

🎯 **一句话精髓**: Netflix 详细披露了驱动 Service Topology（实时服务依赖地图）的流处理管道重构——三阶段架构、Kafka 回压传播、SSE 取代 gRPC，以及一致性哈希实现无重平衡的实例伸缩。

🔧 **技术栈:** eBPF 网络流 / 分布式追踪 / IPC 指标 / Apache Pekko Streams / Kafka / SSE（Server-Sent Events）/ 一致性哈希 / 图数据库

📐 **架构/方法亮点**:
- 三阶段管道：① 多区域 Kafka 流消费 + 过滤 + 5分钟窗口批处理 → ② 中间跳转解析为应用到应用边（处理 LB/NAT/网关/代理跳转）→ ③ 数据丰富（健康/归属/元数据）+ 图数据库持久化
- 回压设计：用 Pekko Streams 管理回压，当图存储跟不上时压力沿处理阶段向上游传播直到 Kafka 消费者暂停——高负载下出现新鲜度延迟而非数据丢失
- 内部传输优化：管道阶段间用 SSE 取代 gRPC，序列化、连接池管理和流式响应内存压力在高流量下代价过高，SSE 更轻量且兼容反应式回压

💡 **关键数据**: 部分实例在 I/O 密集数据丰富操作时流量可达典型值 100 倍；一致性哈希使实例加入/离开时仅迁移受影响的聚合器到新所有者，无需单独重平衡

🔗 **樱桃的调度视角**: Netflix 的 Service Topology 对应 K8s 中的服务依赖图——调度器做拓扑感知放置时需要这种实时的、基于实际流量（而非文档声明的）依赖关系。eBPF 网络流 + 分布式追踪的融合思路，可以启发 Master 在 K8s 集群中构建调度感知的服务拓扑输入。

## 📓 樱桃的今日学习总结

1. **AI 工厂的衡量标准是利用率而非吞吐量** — 从 CNCF 的 AI 工厂文章到英伟达的 Scale-In，再到清华团队的推理全链路优化，今天的资讯形成了一条完整线索：GPU 调度的核心矛盾是「密度 vs 隔离 vs 成本」的三方平衡。DRA 改变了调度器对 GPU 的认知模型（从标量资源到富设备），但真正的密度来自设备层（HAMi/MIG）；真正的隔离来自硬件层（DPU）；真正的成本来自计量层（DCGM GPU-seconds + OpenCost）。每一层都需要独立设计，组合才是 AI 工厂。

2. **推理调度的阶段感知正在成为新范式** — 清华团队的 Prefill/Decode 异构调度、英伟达 Groq 3 LPX 专攻 Token 生成、NVIDIA Dynamo/llm-d 的分离式推理，都在指向同一方向：推理不再是一个黑箱，而是可分解为计算密集和访存密集两个阶段的流水线，调度器需要感知阶段特性做差异化放置。这为 K8s 上的 AI 推理调度打开了新的优化空间。

3. **调度理论的计算边界是工程实践的安全网** — arXiv 论文证明带 affinity 约束的 Pod 可部署性是 PSPACE 完全的，这不是说调度无解，而是说贪心策略是合理的工程选择——通过约束问题结构（Gang 语义、拓扑域限制）来回避一般性困难。但 Master 在设计大规模调度策略时，需要意识到某些部署序列可能永远无法被贪心策略找到，需要外部求解器（如 OPSche 插件）做全局优化补偿。
