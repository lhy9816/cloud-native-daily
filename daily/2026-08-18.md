### 1. 📦 Kubernetes DRA 是否取代了 HAMi？——GPU 分片调度的范式迁移

**原文标题:** Does Kubernetes DRA Replace HAMi?
**来源:** CNCF Blog | 2026-08-07
**链接:** https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/

🎯 **一句话精髓**: DRA（动态资源分配）在 K8s v1.34 GA 后终于让调度器原生理解「给我一张卡 8000MiB 显存 + 10% 算力」，但 HAMi 的容器级 CUDA 调用强制力仍是 DRA 无法替代的，两者走向分工而非替代。

🔧 **技术栈**: Kubernetes DRA / HAMi / Device Plugin / scheduler extender / mutating webhook / CUDA

📐 **架构/方法亮点**:
- HAMi 原方案用 3 个扩展资源（`nvidia.com/gpu`、`nvidia.com/gpumem`、`nvidia.com/gpucores`）+ mutating webhook + scheduler extender 表达 GPU 分片需求，但调度器只把它们当不透明整数，不知道 gpumem 和 gpucores 必须落在同一张物理卡上
- DRA 的 consumable capacity 特性让 Pod 通过 ResourceClaim 直接向调度器请求设备显存切片，无需 annotation 中转——调度器原生感知设备拓扑
- HAMi 的应对策略：保留 CUDA 调用级强制（DRA 从未设计做这件事），将编码层重建在 DRA 之上，拆分为 3 个仓库

💡 **关键数据**: HAMi 于 2026 年 7 月 15 日被 CNCF TOC 接受为孵化项目；DRA 在 K8s v1.34 GA，v1.35 默认启用

🔗 **樱桃的调度视角**: 这是 Master 最该关注的文章！DRA 原生化意味着 GPU 调度不再需要 webhook hack，调度器可以直接做拓扑感知的 GPU 分片决策。但「调度器知道」和「容器里真的限制住」是两件事——HAMi 的 CUDA 级强制仍不可替代。未来 K8s GPU 调度的最佳实践很可能是 DRA 编码 + HAMi 强制的组合。

### 2. 📦 Netflix 详述其基于 Triton 与 vLLM 的内部 LLM 推理服务平台

**原文标题:** Netflix详述其基于Triton与vLLM的内部LLM服务平台
**来源:** InfoQ 中文 | 2026-08-17
**链接:** https://www.infoq.cn/article/J9Zi9LELcpxFRe23PHdY

🎯 **一句话精髓**: Netflix 将 LLM 推理纳入现有 JVM 服务平台，用 Triton 管模型生命周期、vLLM 执行推理，在 CPU/GPU 混部场景下保持应用层工作流一致性，并解决了约束解码状态同步等工程难题。

🔧 **技术栈**: NVIDIA Triton / vLLM / KServe / JVM 服务层 / Red-Black 部署 / Versioned 部署

📐 **架构/方法亮点**:
- 分层架构：JVM 服务层负责路由、特征获取、候选生成、后处理和日志；小模型 CPU 进程内运行，大模型委托到 MSS（模型服务系统），Triton 负责模型加载、批处理、GPU 调度和多框架服务
- vLLM 与 Triton 的分工：Triton 管模型周边服务环境，vLLM 执行推理并提供扩展点——vLLM-backend 模式让模型与前端的演进解耦，比 Python-backend 更灵活
- 约束解码的工程挑战：解码器需在整个请求过程中维护状态，当 vLLM 为管理 GPU 资源暂停后恢复请求时，状态可能与 token 历史不同步——Netflix 增加了检测变化并在继续生成前重建状态的逻辑

💡 **关键数据**: Netflix 将 Triton 与 vLLM 版本固定在一起测试以防止后端加载失败；Uber 的生成式 AI 网关采用类似思路在外部托管与内部模型间提供兼容 OpenAI 的接口

🔗 **樱桃的调度视角**: Netflix 的架构设计对 K8s 上的 AI 推理很有参考价值——特别是 vLLM 为 GPU 资源管理暂停/恢复请求时的状态重建机制。在 K8s 上跑 vLLM 时，Pod 调度、GPU 时间片切换都可能触发类似的状态不一致问题，Netflix 的检测+重建方案值得借鉴。

### 3. 📦 十一分钟、零人工：在 Kairos 上构建自愈式 Kubernetes 升级流水线

**原文标题:** Eleven minutes, zero humans: Building a self-healing Kubernetes upgrade pipeline on Kairos
**来源:** CNCF Blog | 2026-08-14
**链接:** https://www.cncf.io/blog/2026/08/14/eleven-minutes-zero-humans-building-a-self-healing-kubernetes-upgrade-pipeline-on-kairos/

🎯 **一句话精髓**: 用 6 个 CNCF 工具串联出一条从镜像发布到节点升级的全自动 GitOps 流水线，Kairos 的 A/B 分区升级让 K8s 控制面升级像 GitOps 一样可审计、可回滚，全程 11 分钟零人工。

🔧 **技术栈**: Kairos Hadron / Gitea Actions / Renovate / Kyverno / Cosign / ArgoCD / K3s HA / Cilium CNI / OpenTofu

📐 **架构/方法亮点**:
- Kairos Hadron 不就地补丁，而是将新 OS 镜像写入非活跃分区后重启切换——回滚就是重启回旧分区，供应链安全由 cosign 签名验证保障
- 六工具流水线：Renovate 监听 Quay 镜像新标签 → 开 PR → Kyverno 准入策略校验镜像来源 → Cosign 验证签名与 OIDC 身份 → ArgoCD 检测到合并的 PR 作为 drift 并应用 → kairos-operator 执行 A/B 分区升级
- 关键 bug 修复：升级 spec 中 `concurrency: 0` 意味着「所有节点同时升级」而非「逐个升级」——三个控制面节点同时重启，etcd 仲裁存活纯属运气；修正为 `concurrency: 1`

💡 **关键数据**: 全流水线 11 分钟完成，零人工干预；管理集群用 3 个控制面节点 + K3s HA + Cilium CNI

🔗 **樱桃的调度视角**: `concurrency` 参数的教训对调度器设计有启发——并发控制的语义必须清晰。在 K8s 集群升级场景中，控制面节点的串行升级（concurrency: 1）是保证 etcd 仲裁的基本要求，这与 Volcano 等批处理调度器的 Pod 并发控制思路异曲同工。

### 4. 📦 MCP 走向无状态：网关获得路由、限流、计量能力

**原文标题:** MCP 走向无状态，开发者追问：这不就又变回 API 了吗？
**来源:** InfoQ 中文 | 2026-08-16
**链接:** https://www.infoq.cn/article/412hbBva0NF0AYP0CjzD

🎯 **一句话精髓**: MCP 2026-07-28 规范移除协议会话、走向无状态核心，同时新增两个必需 HTTP 标头，让网关无需解析请求正文就能对 AI 智能体流量做路由、限流和计量——可扩展性提升的代价是「这不就又变回 API 了吗」的质疑。

🔧 **技术栈:** MCP 协议 / HTTP 标头路由 / JSON-RPC / 无状态架构 / API 网关

📐 **架构/方法亮点**:
- 旧版传输通过 `initialize` / `initialized` 交互建立会话，用 `Mcp-Session-Id` 标头跟踪；此后每个请求都必须携带该标头——有状态架构限制了水平扩展
- 新版移除会话，新增两个必需 HTTP 标头，网关仅凭标头信息（无需打开请求正文）即可做路由决策、限流和计量——这让 MCP 流量可以被标准 API 网关基础设施管理
- 开发者质疑：移除会话后 MCP 的差异化能力是否仅剩 tool discovery，本质上退化为普通 API

💡 **关键数据**: MCP 规范版本 2026-07-28；网关层可在不解包的情况下完成流量治理

🔗 **樱桃的调度视角**: 无状态化是 AI 智能体流量走向基础设施化管理的关键一步。当 MCP 流量可以通过 HTTP 标头路由和限流时，K8s 上的 Ingress/Gateway API 就能原生管理 AI Agent 流量，无需特殊 sidecar 或自定义控制器。这与 Service Mesh 管理 L7 流量的思路一致。

### 5. 📦 LLMOps 与平台工程：AI 流水线该由谁拥有？

**原文标题:** LLMOps and platform engineering: Who should own the AI pipeline?
**来源:** CNCF Blog | 2026-08-13
**链接:** https://www.cncf.io/blog/2026/08/13/llmops-and-platform-engineering-who-should-own-the-ai-pipeline/

🎯 **一句话精髓**: LLM 打破了传统的「训练-测试-上线-看仪表盘」流程，LLMOps 在 MLOps 和 DevOps 之上竞争同一条流水线——所有权模型搞错了，就会用 prompt 重新制造平台工程本要消灭的 shadow IT 问题。

🔧 **技术栈:** LLMOps / MLOps / Platform Engineering / Hugging Face Transformers / GPU 推理端点 / Prompt 版本管理

📐 **架构/方法亮点**:
- LLMOps 生命周期：数据准备 → prompt 工程（prompt 作为版本化制品而非一次性字符串）→ 开源基座模型微调 → 模型与 prompt 版本及血统追踪 → GPU 端点推理服务 → 人工反馈监控（drift + cost）
- LLM 与传统 ML 的关键差异：微调和服务成本更高，输出难以用单一准确率评分——还需安全性和可信度评估；模型 drift、成本爬升、prompt 失效都需要持续运维
- 三方博弈：DevOps 团队被部署工单淹没、平台工程团队构建自助 golden path、MLOps 团队需要 GPU 和数据流水线——所有权不清时产生 shadow IT

💡 **关键数据**: Google Cloud 将 LLMOps 定义为 MLOps 的专业子集；LLM 的运维不是一次性部署清单而是持续养护

🔗 **樱桃的调度视角**: 平台工程团队应该拥有 AI 流水线的基础设施层（GPU 调度、模型部署、监控），而数据/ML 团队拥有模型和 prompt 层。在 K8s 上，这意味着平台团队负责 Volcano/KubeRay 等调度框架的运维，ML 团队通过自助门户提交训练和推理任务——这正是 IDP（内部开发者平台）在 AI 时代的延伸。

### 6. 📦 轻量级 Dragonfly 部署：无需数据库栈的 P2P 分发

**原文标题:** Lightweight Dragonfly Deployment: P2P Distribution Without the Database Stack
**来源:** CNCF Blog | 2026-08-13
**链接:** https://www.cncf.io/blog/2026/08/13/lightweight-dragonfly-deployment-p2p-distribution-without-the-database-stack/

🎯 **一句话精髓**: Dragonfly 推出轻量部署模式，用 ConfigMap + headless Service 替代 Manager + MySQL + Redis 控制面，单集群 P2P 镜像分发只需一条 Helm 命令即可完成。

🔧 **技术栈:** Dragonfly / P2P 分发 / Helm / ConfigMap / headless Service / Kubernetes 原生

📐 **架构/方法亮点**:
- 传统部署需要 Manager（控制面）+ MySQL（持久化）+ Redis（缓存和异步任务分发）——适合多集群舰队但不适合单集群
- 轻量模式：当 `manager.addr` 未设置时，Scheduler 和 Client 从本地 `/etc/dragonfly/dynconfig.yaml` 加载动态配置（Helm chart 通过 ConfigMap 挂载），无 Manager 时自动用默认值启动
- 用 K8s 原生原语（ConfigMap + headless Service）替代 Manager 的动态配置分发和服务发现功能

💡 **关键数据**: 整个轻量部署可通过单条 Helm 命令完成安装；Scheduler 成为唯一协调组件

🔗 **樱桃的调度视角**: 在大规模 GPU 集群中，拉取大模型镜像（动辄 10GB+）是节点启动的瓶颈。Dragonfly 的 P2P 分发能显著加速镜像拉取，轻量部署模式降低了单集群使用门槛。配合 K8s 调度器的镜像预拉取策略，可以减少 Pod 调度后的等待时间。

**来源:** Cloudflare Blog | 2026-08-07

🎯 **一句话精髓**: Cloudflare 将 AI Gateway（代理任意模型提供商 + 可观测性/安全/日志）与 Workers AI（自管 GPU 推理即服务）合并为统一控制面，通过单一 binding 和 REST API 实现模型优先路由，开发者无需预先选择产品即可获得全链路可观测性。

🔧 **技术栈:** Cloudflare Workers AI / AI Gateway / Workers binding / REST API / 模型优先路由 / token 计费

📐 **架构/方法亮点**:

- 默认网关机制：首次认证请求自动创建 `default` 网关，无需预先设置即可获得请求/响应日志、token 计数、成本归因；后续可通过单参数切换到命名网关实现流量分组
- 模型优先路由：统一控制面支持跨自管 GPU 和外部提供商的动态路由，开发者通过同一接口访问任意模型

💡 **关键数据**: 每个请求自动记录完整请求/响应负载、按模型追踪 token 计数、无需仪表盘配置即可获得成本归因

🔗 **樱桃的调度视角**: Cloudflare 的统一控制面思路对 K8s 上的 AI 推理网关设计有启发——将可观测性、计费、路由统一到一层，让模型消费者无需关心后端是自管 GPU 还是外部 API。在 K8s 中，这类似于通过 KServe + Gateway API 构建统一的推理服务入口，配合 Volcano 做底层 GPU 调度。

## 📓 樱桃的今日学习总结

1. **GPU 调度正在从「绕过 API」走向「原生 API」** - DRA 让 K8s 调度器原生理解 GPU 分片需求是里程碑式的变化，但「调度器知道」和「容器里限制住」是两个层面。未来最佳实践是 DRA 编码（调度器层）+ HAMi 强制（CUDA 层）的组合，而非二选一。Master 在设计 GPU 调度方案时应关注 DRA ResourceClaim 的演进。
2. **LLM 推理平台的工程深水区在「状态同步」和「版本兼容」** - Netflix 的经验表明，通用服务接口（如 OpenAI 兼容 API）并不能消除底层引擎差异。约束解码的状态重建、Triton/vLLM 版本绑定测试、Red-Black/Versioned 部署策略——这些才是 LLM 推理平台真正费力的地方。在 K8s 上跑 vLLM 时需特别注意 Pod 调度与 GPU 资源切换引发的状态不一致。
3. **AI 流水线的治理需要平台工程介入** - LLMOps 不是 MLOps 换个标签，其生命周期管理（prompt 版本化、模型 drift、成本监控）需要平台工程提供基础设施支撑。所有权不清会重演 shadow IT 问题——平台团队应拥有 GPU 调度和部署基础设施，ML 团队通过自助门户操作，这是 AI 时代 IDP 的核心设计原则。
