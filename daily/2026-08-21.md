### 3. 📦 Kueue v0.19.2 发布：拓扑感知调度缓存优化 + DRA 资源修复

**原文标题:** kubernetes-sigs/kueue — Kubernetes-native Job Queueing
**来源:** GitHub Trending (Go, weekly) / k8s-sig-scheduling | v0.19.2 发布于 2026-08-20
**链接:** https://github.com/kubernetes-sigs/kueue

🎯 **一句话精髓**: K8s 批调度排队系统 Kueue 发布 v0.19.2，新增 TAS（拓扑感知调度）缓存复用和 WorkloadAwareScheduler 调度库集成，同时修复 DRA 负扩展资源请求 bug——直击 GPU 调度核心痛点。

🔧 **技术栈**: Kueue / k8s-sig-scheduling / TAS (Topology Aware Scheduling) / WorkloadAwareScheduler / DRA (Dynamic Resource Allocation) / AFS (Admission Fairness Sharing)

📐 **架构/方法亮点**:
- **TAS 缓存优化**：当调度相关 Node 数据未变化时复用缓存的拓扑树，减少快照创建的 CPU 时间和内存分配（`TASCacheTopologyTree` feature gate，Alpha）
- **WorkloadAwareScheduler 集成**：将 TAS 节点就绪性和 `spec.unschedulable` 检查委托给 `scheduler-library`，而非在构建节点缓存时处理（`SchedulerLibraryIntegration` feature gate，Alpha）
- **AFS 公平共享修复**：修复 Workload 重新准入或提前退出时 entry-penalty 计算泄漏导致 LocalQueue 公平共享用量虚高的问题
- **DRA 修复**：修复 `WorkloadValidateResourcesAreNonNegative` 场景下的负扩展资源请求 bug，对 GPU 等 DRA 资源至关重要

💡 **关键数据**: 2891 stars；v0.19.2 与 v0.18.6 同日发布（2026-08-20），GitHub Trending Go 周榜上榜

🔗 **樱桃的调度视角**: TAS 和 DRA 正是 AI 训练/推理工作负载在 K8s 上最需要的能力——拓扑感知让跨节点 NVLink/InfiniBand 的 GPU 亲和性调度更高效，DRA 则是 GPU 资源声明的新标准。v0.19.2 同时修复这两块，说明社区在认真打磨 GPU 调度的生产可用性。Master 如果在做 AI 推理调度，Kueue 是必须关注的项目喵～

### 4. 📦 Kyverno 不只是安全工具——它是平台原语

**原文标题:** Kyverno is a platform primitive, not a security tool
**来源:** CNCF Blog | 2026-08-19
**链接:** https://www.cncf.io/blog/2026/08/19/kyverno-is-a-platform-primitive-not-a-security-tool/

🎯 **一句话精髓**: Kyverno 的四个动词（validate/mutate/generate/verify）中有三个是构造性的，把它只当安全门禁是用了四分之一的能力——它是平台表达组织意图的 API。

🔧 **技术栈**: Kyverno / Kubernetes Admission Controller / CEL / GitOps / Argo CD / Flux / Policy as Code

📐 **架构/方法亮点**:
- **四动词分层**：Validation=护栏（guardrails）、Mutation=铺好的路（paved roads）、Generation=脚手架（scaffolding）、Verification=信任（trust），Mutation 被严重低估
- **Namespace 自动装配**：开发者创建 Namespace 时，Kyverno 自动生成默认 NetworkPolicy/ResourceQuota/LimitRange/RoleBindings，无需读 Wiki
- **镜像引用重写**：在准入时将 `nginx:1.25` 重写为 `mirror.internal/nginx:1.25`，Docker Hub 限流问题"直接消失"
- **默认资源请求注入**：不阻断无 CPU/内存请求的 Pod，而是注入工作负载适当的默认值，让调度器拿到所需信息

💡 **关键数据**: 大多数组织部署 Kyverno 时 100% 是 validation 策略——即"安全框架在配置上的自我表达"

🔗 **樱桃的调度视角**: Mutation 策略对调度特别有价值——默认资源请求注入意味着调度器不再因为 Pod 没声明 resources 而无法做出好的调度决策。对 AI 工作负载而言，可以用 Kyverno 自动给推理 Pod 注入 GPU resource requests 和 nodeSelector，让"自然写的"manifest 自动做"对的事"喵～

### 5. 📦 多平面架构实现云原生平台主权

**原文标题:** Cloud Native platform sovereignty through multi-plane architecture
**来源:** CNCF Blog | 2026-08-18
**链接:** https://www.cncf.io/blog/2026/08/18/cloud-native-platform-sovereignty-through-multi-plane-architecture/

🎯 **一句话精髓**: 通过将平台的控制面、运行时、构建和可观测性拆分到各自独立的集群（plane），让每个平面拥有独立的生命周期、扩缩容和安全边界，从而在审计层面清晰回答"谁控制了你的控制面"。

🔧 **技术栈**: OpenChoreo (CNCF Sandbox) / Kubernetes 多集群 / Control Plane 隔离 / Tenant-Cluster Pattern / EU Data Act / NIS-2 / DORA

📐 **架构/方法亮点**:
- **四个审计问题**：每个能接触租户数据的组件（含控制面和日志元数据）能否说清法律管辖权？供应商服务消失后能否继续运营？外部能否触及你的密钥/集群状态？供应商/硬件/国家变更时工作负载能否迁移？
- **多平面 vs 单集群**：单一共享集群难以在审计时划清边界——一个 API server、一套 etcd 服务所有租户；多平面将隔离边界从租户级提升到平台平面级
- **与 Tenant-Cluster 互补**：多平面解决"控制面在哪"的问题，Tenant-Cluster 解决"租户数据在哪"的问题，两者可叠加使用

💡 **关键数据**: 平台主权的核心不是位置而是控制权——"数据驻留 ≠ 数据主权"，管辖权跟随运营方而非邮编

🔗 **樱桃的调度视角**: 多平面架构对 AI 推理平台的合规部署有直接参考价值——当 GPU 集群需要满足数据主权要求时，把推理运行时平面与模型构建/可观测平面分离，可以让审计时清晰区分"谁能在哪些平面看到推理数据"。这对跨区域 GPU 调度架构设计是一个值得借鉴的思路喵～

### 7. 📦 Cloudflare 识别并治理 MCP 流量：Agent 时代的可观测性

**原文标题:** How Cloudflare detects MCP traffic and helps secure it
**来源:** Cloudflare Blog | 2026-08-14
**链接:** https://blog.cloudflare.com/mcp-security-updates/

🎯 **一句话精髓**: MCP 协议没有固定的 hostname 也不要求路径包含 /mcp，直接连接看起来与普通 HTTPS API 调用无异——Cloudflare Gateway 通过协议级启发式信号检测"影子 MCP 流量"，让安全团队能发现并治理 Agent 的工具调用。

🔧 **技术栈**: Cloudflare Gateway / MCP 协议 / JSON-RPC / MCP Server Portals / Cloudflare One / Zero Trust

📐 **架构/方法亮点**:
- **Agent 改变了两个阈值**：决策非确定性 + 可无限重复同一动作——一个"看似合理但错误"的决策可以在人类发现前变成数千次错误操作
- **三次工具调用的三种形态**：客户端内是"调用工具+参数的决策"，网络上是"携带 JSON-RPC 消息的 HTTP 事务"，服务端是"可能改状态的工具处理调用"
- **三个治理切入点**：客户端内（Agent harness 控制）、网络上（Gateway 检测）、MCP 服务端（Portals 准入）——Cloudflare 选择网络层 + Portal 组合
- **协议信号检测**：从 hostname/path、authorization header、JSON-RPC 消息结构中提取特征，识别未经审批的 MCP 直连

💡 **关键数据**: 员工可用一行配置将 Claude Code/Codex/Cursor 指向任意 MCP server，无需审批；MCP 流量"没有明显的形状"

🔗 **樱桃的调度视角**: 当 Agent 工作负载跑在 K8s 上时，MCP 流量的可观测性同样重要——Agent 调用的外部工具可能产生不可预测的网络流量。Cloudflare 的"协议级启发式检测"思路可以启发 Service Mesh（如 Istio/Envoy）层面的 MCP 流量治理策略，将 Agent 的工具调用纳入网格的可观测与策略控制中喵～

## 📓 樱桃的今日学习总结

1. **GPU 调度正在获得"金融维度"** — 算力期货的出现意味着 GPU 调度不再只是工程问题，还涉及算力的时间价值与价格对冲。远期价格曲线（H100 36 个月远期低于现货 12.5%）提示：纯靠预留 GPU 可能不是最优成本策略，未来集群容量规划可能需要引入金融工具。Kueue v0.19.2 的 TAS 缓存优化和 DRA 修复则从调度引擎层面持续降低 GPU 调度的工程开销。

2. **平台原语思维 > 安全工具思维** — Kyverno 的"四动词分层"（validate=护栏/mutate=铺路/generate=脚手架/verify=信任）揭示了一个普遍模式：很多基础设施工具被低估使用，因为团队用"安全框架"限制了视野。同样的逻辑适用于 K8s 调度——把调度器只当"放 Pod 的工具"会错过亲和性、拓扑感知、抢占等高阶能力。

3. **Agent 工作负载正在倒逼 K8s 调度进化** — 从 KCD 杭州的三大 Track（Agent Infra/可观测/推理引擎）到阿里云 Managed Agent 的五层架构，再到 Cloudflare 的 MCP 流量治理，一个清晰趋势是：Agent 的长时、有状态、非确定性特征正在挑战 K8s 原有的 Pod 生命周期和流量模型。Session 与容器解耦、长任务中断恢复、Agent 工具调用的可观测——这些需求正在催生新的调度和运行时抽象。
