### 1. 📦 用 Bi-LSTM 预测流量峰值：K8s 上 GPU 工作负载的预测式弹性伸缩

**原文标题:** Scale before the spike: Predictive autoscaling for GPU workloads on Kubernetes
**来源:** CNCF Blog | 2026-08-28
**链接:** https://www.cncf.io/blog/2026/08/28/scale-before-the-spike-predictive-autoscaling-for-gpu-workloads-on-kubernetes/

🎯 **一句话精髓**: Adobe 工程师构建了一个每 60 秒运行推理、提前 10 分钟预测 GPU 需求的 K8s 控制器，让 GPU 节点在流量真正到来前就「热身」完毕，解决了反应式 HPA 对 GPU 工作负载永远慢半拍的根本矛盾。

🔧 **技术栈**: Bi-LSTM / TensorFlow Lite / Prometheus / NVIDIA DCGM / HPA v2 / Go 控制器

📐 **架构/方法亮点**:
- 三段式架构「预测 → 预配 → 吸收」：Bi-LSTM（64→32 单元双层）每 60 秒读过去 1 小时指标推理未来 10 分钟需求；并行突发检测器用滚动标准差自适应阈值兜底；分级扩缩器限速 20 pod/分钟防止「惊群效应」
- 关键设计：不用 CRD，直接 patch Deployment replicas（和 HPA 一样）；模型内嵌 Go 二进制做纯推理，无外部 ML 平台；目标利用率设 70% 留余量；与 HPA v2 共存而非替代
- 影子模式验证 500+ 小时，预测精度 85% 落在 ±10% 区间内，突发检测命中 9/10 真实峰值、仅 2 次误报

💡 **关键数据**: 预测准确率 85%（T+10min ±10%）；23/23 验证检查全通过；零级联故障、零振荡；GPU 节点扩容比 CPU 慢 3-5 倍（固件加载+驱动初始化+CUDA 就绪）

🔗 **樱桃的调度视角**: 这篇直击 Master 的核心痛点——GPU 节点从触发到 ready 要 3-5 分钟，反应式 HPA 根本来不及。「预测式预配 + 分级限速」的思路完全可以借鉴到 KubeRay/Volcano 的推理弹性伸缩里，把「等流量来了再扩」变成「流量到之前 GPU 已经热好」。

### 2. 📦 在 K8s 上构建「AI 工厂」：多团队共享 GPU 池的完整技术栈

**原文标题:** Building an AI factory on Kubernetes
**来源:** CNCF Blog | 2026-08-27
**链接:** https://www.cncf.io/blog/2026/08/27/building-an-ai-factory-on-kubernetes/

🎯 **一句话精髓**: 把企业 GPU 集群当作「AI 工厂」——一支团队微调、另一支推理、第三支跑评测同时争抢同一批 GPU，文章给出从裸金属到计费的完整 K8s 原生分层栈，核心矛盾是利用率而非单次吞吐。

🔧 **技术栈**: DRA (Dynamic Resource Allocation) / MIG / HAMi / KAI Scheduler / Volcano / Kueue / vCluster / vLLM / KServe / llm-d / Cilium / KubeVirt / Cluster API / Argo CD

📐 **架构/方法亮点**:
- 12 层栈从底到顶：硬件生命周期(Metal3/Ironic/Tinkerbell) → 集群生命周期(Cluster API/Argo CD) → 节点清单(Node Feature Discovery) → 租户隔离(vCluster 沙箱运行时) → GPU 分配(DRA/MIG/HAMi/时间片/KAI 拓扑感知调度) → 推理服务(vLLM/KServe/llm-d) → 批处理(Slinky SLURM-on-K8s) → 网关弹性(Gateway API/KEDA) → 网络(Cilium/Multus/SR-IOV/RDMA) → 存储(CSI/Rook) → 可观测(Prometheus/DCGM) → 计费(OpenCost)
- 资源模型痛点：传统 device-plugin 模式下 `nvidia.com/gpu:1` 直接独占整卡，哪怕只用 10%；DRA（K8s 1.34 GA）让调度器把加速器当带属性/内存/拓扑的富设备处理，但本身不切分 GPU，密度靠底层 MIG/HAMi
- 隔离模型痛点：安全隔离时默认每团队独占集群或独占 GPU 块，安全但浪费大部分硬件；SemiAnalysis ClusterMAX 安全评分奖励到租户级独立集群 + DPU 隔离，却把「多租户挤一个集群」标为弱边界

💡 **关键数据**: SemiAnalysis ClusterMAX 按「安全/网络/存储/可靠性/支持」而非裸吞吐给 GPU 云评分；GPU 是建筑里最大的资本开支，决定回报的指标是利用率

🔗 **樱桃的调度视角**: 这篇就是 Master 做多租户 GPU 平台的「参考架构图」！DRA + MIG + HAMi + KAI 拓扑感知调度的组合拳，加上 Kueue 做队列管理、vLLM/KServe 做推理，正好覆盖 GPU 调度的全链路。樱桃建议重点看「租户隔离 + GPU 分配」那两层喵。

### 3. 📦 Kubernetes v1.37 发布：Pod 证书 GA + Metrics API 转稳定

**原文标题:** Kubernetes v1.37: Pod Certificates and Cluster Trust Bundles / Kubernetes v1.37: Metrics API graduates to stable
**来源:** Kubernetes Blog | 2026-08-26~28
**链接:** https://kubernetes.io/blog/2026/08/28/kubernetes-v1-37-pod-certificates-and-cluster-trust-bundles/

🎯 **一句话精髓**: v1.37 把两块基础设施推到 GA——Pod 证书让工作负载直接用 X.509 做 mTLS（补上 service account JWT 作为 bearer token 的安全短板），Metrics API 转正意味着 HPA/kubectl top 背后的指标接口有了稳定承诺。

🔧 **技术栈**: X.509 证书 / mTLS / Kubelet / ClusterTrustBundle / PodCertificateRequest / metrics.k8s.io/v1 / metrics-server / SPIFFE

📐 **架构/方法亮点**:
- Pod 证书：service account JWT 是 bearer token（谁拿到令牌谁就是该身份），Pod 证书改用 proof-of-possession（私钥不离开工作负载，只发拥有证明）；Kubelet 代发 PodCertificateRequest，签名控制器响应并发布 ClusterTrustBundle；可插拔接口支持多种证书类型，未来内置服务端 TLS 证书 + SPIFFE 客户端证书两种 provider
- Metrics API：metrics.k8s.io 从 v1.6 alpha → v1.8 beta → v1.37 正式 GA 为 v1；暴露 NodeMetrics/PodMetrics 两种资源，HPA 和 kubectl top 都依赖它；v1 与 v1beta1 字段完全一致，纯版本升级；通过 API 聚合层由 metrics-server 提供

💡 **关键数据**: Metrics API 从 alpha 到 GA 跨越了 v1.6→v1.37 十余个版本；Pod 证书 GA 后由 Kubelet 直接签发，流程与 SA token 投射卷一样「魔法」但更安全

🔗 **樱桃的调度视角**: Metrics API GA 看似小事实则影响调度——它是 HPA 做弹性伸缩的数据底座，稳定承诺意味着基于 CPU/内存指标的自动伸缩可以放心上生产。Pod 证书则对 GPU 推理服务的 mTLS 安全尤其重要，AI 推理 pod 直连数据库/模型仓库时不再裸奔 bearer token。

### 4. 📦 五步 Rust 内存优化为 1.1.1.1 DNS 缓存省下 100TB 内存

**原文标题:** How we saved 100 terabytes of memory by optimizing 1.1.1.1's DNS cache
**来源:** Cloudflare Blog | 2026-08-27
**链接:** https://blog.cloudflare.com/dns-cache-memory-optimization-1111/

🎯 **一句话精髓**: Cloudflare 对 1.1.1.1 背后的 Big Pineapple DNS 缓存做了五轮 Rust 级内存布局优化，把每条目内存砍掉 56%，全舰队释放约 100TB 内存——而且更快了，插入吞吐 +43%、查询延迟 -19%。

🔧 **技术栈**: Rust / Big Pineapple / DNS / EDNS Client Subnet / Box<[T]> / 自定义全局分配器 / Parquet

📐 **架构/方法亮点**:
- 核心洞察：缓存条目存入后从不修改，但 Vec<T> 仍带 capacity 字段(8 字节)和过度分配堆空间——改用 Box<[T]> 既丢 capacity 又不预留空间；String 同理换 Box<str>
- 用自定义全局分配器（包装 Rust System allocator）精确计量每条目的分配数和大小，并用贴近生产的流量分布（A 56%/AAAA 25%/TXT 19%，1-4 条记录）做基准测试
- 同时跟踪插入吞吐和查询延迟，确保省内存不以牺牲性能为代价——更少分配 + 更好的内存局部性反而提速

💡 **关键数据**: 250 亿条缓存条目，每字节浪费 = 250GB 全舰队；单条目内存降 56%；释放约 100TB（≈130 台 Gen13 服务器内存）；插入吞吐 +43%、查询延迟 -19%

🔗 **樱桃的调度视角**: 虽然是 DNS 不是 K8s，但「250 亿条目省 56% 内存」的思路对 K8s 控制面数据结构优化是直接启发——etcd/lister 缓存、scheduler cache 的内存占用同样可以被这种「存后不改就去 capacity 字段」的精细优化砍掉一大块。

💡 **关键数据**: 1M Token 上下文下 QSA 的 Attention Kernel 在 Prefill/Decode 最高加速 7.6 倍/4.9 倍；输入每百万 Tokens 0.8 元、输出 2.7 元；标准模式覆盖约 95% 日常任务、Token 消耗平均减 75%、生成速度提升约 100%

🔗 **樱桃的调度视角**: QSA 在长上下文下 Prefill 加速 7.6 倍直接关乎 K8s 上推理服务的 GPU 成本——MoE 稀疏激活 + 稀疏注意力让单卡能服务的并发量和上下文长度都上一个台阶，KubeRay/KServe 部署时显存占用和 KV cache 管理策略都得跟着调优喵。

## 📓 樱桃的今日学习总结

1. **「预测式」正在取代「反应式」成为 GPU 调度的核心范式** - Adobe 的 Bi-LSTM 预测控制器和千问的 QSA 稀疏注意力都指向同一个趋势：GPU 太贵太慢，等需求来了再扩必然来不及，必须用 ML 预测 + 分级限速把「热身」前置。Master 做 K8s GPU 推理弹性伸缩时，应该把「预测窗口」作为一等公民设计进调度器。
2. **AI 工厂 = 调度器 + 隔离器 + 分配器的分层拼装** - CNCF 的 AI 工厂栈证明，多租户 GPU 平台不是单点突破而是 12 层协作：DRA 做富设备调度、MIG/HAMi 做物理切分、vCluster 做租户隔离、Kueue 做队列、KAI/Volcano 做拓扑感知。关键决策不是「选哪个」而是「每层选什么、层间怎么缝合」。
3. **「成本不可能三角」被模型内 + 模型外双向协同打破** - Qwen3.8-Flash 用 MoE 稀疏激活(6B/Token) + QSA 稀疏注意力 + Agent Harness 协同，把成本/性能/速度三角同时优化，Token 消耗降 75% 仍覆盖 95% 任务。这说明 AI 推理降本不只是堆更便宜的卡，而是模型架构 × 调度策略 × Agent 编排的三重乘积。
