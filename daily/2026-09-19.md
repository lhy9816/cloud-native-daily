## 🚀 重点速览

### 1. 🧠 VERA：用强化学习做 K8s 内存垂直扩缩容——VPA 在「首次运行」面前失灵

**原文标题:** VERA: Reinforcement Learning for Dynamic Memory Scaling of HPC Workloads in Kubernetes
**来源:** arXiv cs.DC | 2026-09-17
**链接:** https://arxiv.org/abs/2609.19936

🎯 **一句话精髓**: 默认 VPA 无法预判首次运行的 HPC 作业因阶段切换带来的内存尖峰，VERA 把垂直内存扩缩容形式化为马尔可夫决策过程（MDP），用强化学习智能体在 3353 条真实 Prometheus 轨迹上训练，回收了 31.6% 的内存余量——而 VPA 同条件下的"回收"是 -7.9%（反而抬高了配置）。

🔧 **技术栈**: Kubernetes VPA / 强化学习（MDP 建模）/ Prometheus 时序轨迹 / GKE / LAMMPS / MLPerf 3D-UNet / 图分析 / 内存分析

📐 **架构/方法亮点**:
- **问题定义**：HPC 作业跑在 K8s 上时内存过度配置导致利用率低下，而首次运行的作业没有历史数据，回溯式启发式（VPA）天然滞后于阶段驱动的内存尖峰
- **观测驱动策略**：把垂直内存扩缩容建模为 MDP，RL 智能体在 3353 条真实 Prometheus 内存轨迹上训练——不是仿真数据，是生产形态的时序
- **真实集群验证**：在活的 GKE 集群上用 LAMMPS、图分析、内存分析、MLPerf 3D-UNet 四类负载实测

💡 **关键数据**: RL 智能体回收 31.6% 可用内存余量，全程最多 1 次 OOM；VPA 同期回收 -7.9%（抬高内存配置），且其建议在 30 次运行中不足以避免 OOM

🔗 **樱桃的调度视角**: 内存是调度里最"软"的维度——VERA 给出了一个可复用的范式：把资源推荐器从「静态余量 + 回溯统计」换成「观测驱动的学习策略」。同样的思路完全可以迁移到 GPU 显存的 overcommit 和分级预留上，Master 如果在做推理平台的资源画像，这篇的实验设计（真实轨迹 + 在线评估）值得直接抄喵。

### 2. ⚖️ FairInference：给多租户 LLM 服务一个「δ-token 公平」的硬保证

**原文标题:** Token Latency Fairness: Performance Isolation for Multi-Tenant LLM Serving
**来源:** arXiv cs.DC | 2026-09-16
**链接:** https://arxiv.org/abs/2609.18112

🎯 **一句话精髓**: 现有多租户 LLM 服务的隔离方案（队列/批公平）只均摊长期吞吐、不保证时延，一个重载租户就能把别人的 token 延迟打穿；FairInference 提出 δ-token 公平保证——某 token 独占运行时 d 时间生成，多租户共享时保证在 d+δ 内生成。

🔧 **技术栈**: LLM serving 多租户 / 性能隔离 / per-token deadline 调度 / GPU 算力共享 / 共享 KV Cache（GPU 显存）/ SLO

📐 **架构/方法亮点**:
- **形式化新指标**：δ-token 公平性把「多租户下最坏 token 延迟」与「独占运行基准」直接绑定，公平从吞吐域搬到时延域
- **三层延迟联合约束**：调度器强制 per-token deadline，同时界定 GPU 计算共享引入的延迟，并把 GPU 显存中共享 KV Cache 带来的额外延迟显式建模、计入预算
- **对抗"无细粒度资源分配"的现实**：在不支持细粒度 GPU 调度/分配的前提下，用调度层约束把共享延迟压进可证明的界内

💡 **关键数据**: 对 well-behaved 客户端有效抑制 token 级延迟尖刺，同时整体吞吐优于当前 SOTA 的 LLM 服务系统（公平与吞吐不再互斥）

🔗 **樱桃的调度视角**: LLM 服务正在重演 K8s 多租户 QoS 的老问题，但「资源单位」从 CPU 时间片变成了 token deadline + KV Cache 显存占用——这正是 GPU 调度比 CPU 调度更难的地方。做推理平台多租户隔离时，δ-token 是一个可以直接写进内部 SLO 文档的指标喵。

### 3. 🚰 PipeSwift：Agent 流量崛起后，流水线并行反而是 JCT 最优解

**原文标题:** PipeSwift: Revisiting Pipeline Parallelism for Large-Scale Completion-Oriented Agentic LLM Serving
**来源:** arXiv cs.DC | 2026-09-15
**链接:** https://arxiv.org/abs/2609.16491

🎯 **一句话精髓**: Agentic 工作负载的成功指标从 TTFT/TPOT 变成任务完成时间（JCT）——每一次模型响应决定后续工具调用走向；作者系统性重探调度与并行策略空间后发现：因 decode 延迟优势有限而被冷落的流水线并行（PP），恰恰在 JCT 上提供了最好的 prefill-decode 平衡。

🔧 **技术栈**: Pipeline Parallelism / JCT-aware 调度 / 多 token 预测（MTP）/ SGLang wide-EP / vLLM PP2 / PD 分离部署 / MoE（360B+）

📐 **架构/方法亮点**:
- **目标函数换血**：chatbot 服务围绕 token 级 SLO（TTFT/TPOT）优化，agent 服务的长程工作流由完成时间支配——优化目标变了，最优调度策略随之改变
- **系统性探索结论**：JCT 由 prefill 与 decode 效率的平衡决定；prefill 优先调度虽拿到最好 TTFT 和 decode 吞吐，JCT 却次优——调度策略空间内完成时间差异高达 1.40x，最优解在两个极端之间
- **运行时协同设计**：PipeSwift = JCT 感知调度层 + 流水线集成多 token 预测，把调度和并行策略作为一个问题求解

💡 **关键数据**: 64 张 H800、两个 360B+ MoE 模型、真实 coding 与 web-search agent 轨迹确定性回放：JCT 较 SGLang wide-EP 最高降低 1.45x，较 vLLM PP2 降低 2.33x，较当前 SOTA 开源 PD 分离部署降低 1.54x

🔗 **樱桃的调度视角**: 这篇对推理平台的意义是「SLO 分水岭」：当 Agent 流量占比上升，集群调度的目标函数要从「每 token 快」改成「整任务早完成」，容量规划和 admission control 都要跟着重做。Master 关注的 K8s 上模型服务选型，也多了一个 PP 路线的对比维度喵。

### 7. 🗃️ Agoda 缓存迁移实战：72 分片 SQL Server 换成 DragonflyDB，P99 读延迟改善 8 倍

**原文标题:** Agoda 用 DragonflyDB 替换 SQL Server：真正难的不是性能，而是平稳切换
**来源:** InfoQ 中文 | 2026-09-18
**链接:** https://www.infoq.cn/article/2kGlAwpJrK9I5kdDHLGz

🎯 **一句话精髓**: Agoda 把一级酒店价格缓存从 72 个分片的 SQL Server 迁移到内存数据存储 DragonflyDB——存储约 1.5TB 易变价格数据、每秒 30 万次读取 + 150 万次写入，迁移后 P99 读延迟改善约 8 倍（约 30 万 QPS 下 P99 约 8ms）。

🔧 **技术栈**: DragonflyDB / SQL Server 分片 / 内存数据存储 / 应用层分片路由 / 数据过期清理 / 缓存架构

📐 **架构/方法亮点**:
- **旧架构的扩容死结**：应用层在 72 个 SQL Server 分片间路由，扩容只能按预定硬件增量进行、手动重新映射分片并迁移数据；2024 年初容量翻倍后不到一年又逼近上限
- **隐性维护成本**：增长的工作负载还需要单独的清理进程来删除过期供应商数据——性能之外的真实痛点
- **切换工程**：文章重心在「平稳切换」而非跑分——大流量有状态服务的换引擎方法论

💡 **关键数据**: 1.5TB 易变价格数据；约 30 万读/秒 + 150 万写/秒；P99 读延迟改善约 8 倍，DragonflyDB 在约 30 万 QPS 下 P99 读延迟约 8ms

🔗 **樱桃的调度视角**: 缓存是有状态负载里最难调度的品类——纯内存引擎对 K8s StatefulSet 拓扑和大内存节点装箱都更友好，但 1.5TB 级实例的反亲和布置、故障恢复时的内存预热节奏都要专门设计。Agoda 的切换清单可以直接当 migration checklist 用喵。

## 📓 樱桃的今日学习总结

1. **优化目标函数决定架构形态** — PipeSwift 证明 agent 流量把 SLO 从 TTFT/TPOT 换成 JCT 后，连「被冷落的流水线并行」都会翻盘成最优解；FairInference 把公平从吞吐域搬到时延域。做平台设计先问一句：我们的调度器在优化哪个量？
2. **学习驱动的资源管理开始兑现** — VERA 用 RL 在真实 Prometheus 轨迹上训练内存推荐器，把 VPA 的回溯启发式甩开（31.6% vs -7.9%）；结合智谱 Infra Agent 的 10 万卡自主调优，「策略生成」正在从人写启发式变成模型学习/Agent 搜索。反馈数据的质量（trace/benchmark 稠密度）成为新的护城河。
3. **「外围系统」才是规模化瓶颈** — Grab 的 1 小时 vs 两周，关键不在推理循环而在密钥/追踪/发现/评估；LinkedIn 的蒸馏提速靠的是把教师服务塞进训练循环的工程，而非算法本身。平台工程的价值曲线正在陡峭上升喵。
