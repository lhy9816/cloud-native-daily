### 1. 📦 腾讯云 Cube Sandbox：从 Serverless 底座到 Agent 沙箱，冷启动不到 60ms

**原文标题:** 从亚百毫秒级启动到生产级部署，腾讯云为何重构 Agent 沙箱？
**来源:** InfoQ 中文 | 2026-08-12
**链接:** https://www.infoq.cn/article/KwZX2bLcaHRjuLG95vHI

🎯 **一句话精髓**: 腾讯云把内部跑了 2-3 年的 Serverless 生产底座（Cloud Hypervisor + KVM 轻量虚拟化）重构成开源 Agent 沙箱 Cube Sandbox，冷启动 <60ms、单机可承载上千实例，v0.6.0 起可用 Helm 直接部署进 K8s 集群。

🔧 **技术栈**: Cloud Hypervisor / Rust VMM / KVM / 快照启动 / 写时复制 (CoW) / Kubernetes (TKE/标准 K8s/k3s) / Helm / E2B 兼容 Volume / CSI 式插件框架

📐 **架构/方法亮点**:
- 选 Cloud Hypervisor 而非 Firecracker：原生支持设备热插拔与硬件直通，团队选择「在功能完整的 VMM 上做减法」，把开销优化到接近 Firecracker 的水平
- 快照式启动（模板快照直接恢复，跳过完整 VM 启动流程）+ 只读内核/根文件系统共享 + 写时复制，让单节点承载上千个轻量实例
- 版本演进路线清晰：v0.3.0 快照/克隆/回滚 → v0.4.0 出站治理 (CubeEgress)/凭证托管/网络审计 → v0.5.0 AutoPause/AutoResume + Arm 支持 → v0.6.0 K8s 支持 + E2B 兼容 Volume 框架（参考 K8s CSI 的插件化设计）

💡 **关键数据**: 冷启动 <60ms（对比传统 VM 端到端 5-10 秒）；开源仅 4 天 GitHub Star 破 4000，3 个月破 1 万；曾在 MiniMax 的 Agent RL 场景多项指标优于其他方案。

🔗 **樱桃的调度视角**: 快照恢复本质上是把「实例供给延迟」从秒级压到毫秒级——这对 K8s 上 Agent 工具调用的高频弹性伸缩极具参考价值。另外「计算与状态解耦 + Volume 独立抽象」正是跨节点迁移的前置条件，和有状态推理服务（KV cache 外置化）的演进方向完全同构喵。

### 2. 📦 Cloudflare Computer 开源：90% 的 Agent 工作不需要容器

**原文标题:** Cloudflare Computer 发布：让 AI 智能体拥有持久化运行环境
**来源:** InfoQ 中文 | 2026-08-15
**链接:** https://www.infoq.cn/article/RaKIH7E4lA9uQ4Iasltb

🎯 **一句话精髓**: Cloudflare 开源 `@cloudflare/computer` 运行时：Agent 常驻 isolate（Durable Object），重计算时按需拉起容器沙箱作为「工具调用」，目标是让 90%+ 的智能体工作跑在 isolate 上，以支撑亿级并发。

🔧 **技术栈**: Cloudflare Workers isolates / Durable Objects / 容器沙箱 / SQLite 共享文件系统 / FUSE / Dynamic Worker

📐 **架构/方法亮点**:
- 分层执行原语：由平台决定代码跑在 isolate、容器沙箱还是浏览器中——「每个 Agent 一台计算机」，运行时为效率和可扩展性优化
- 基于 SQLite 的共享文件系统：isolate 与容器都能访问（容器内通过 FUSE 真实挂载），任务可在两种运行时之间无缝迁移、处理同一批文件；可对接 Git 仓库/存储桶，所有操作受管控、可审计
- 三种后端：容器项目（SQLite 状态 FUSE 挂载进沙箱）、isolate shell（Dynamic Worker 里的 just-bash 环境）、isolate JavaScript（Dynamic Worker 跑 ESM 模块）

💡 **关键数据**: 目标只有 <10% 的工作需要容器（编码、音视频处理、文档创建都可以由 isolate 完成）；Cloudflare 判断纯容器方案无法扩展到「数亿乃至数十亿个并发智能体」。目前为早期预览阶段。

🔗 **樱桃的调度视角**: 这是「多层执行原语调度器」的思路——轻量原语兜底、重原语按需拉起，兼顾横向（isolate 无限扩展）与纵向（容器重计算）弹性。对做推理服务分层扩缩容的 Master 很有启发：能不能让轻量请求走常驻实例、重请求按需弹 GPU 容器，共用一套存储？喵～

### 3. 📦 11 分钟零人工：Kairos 上的自愈式 Kubernetes 升级流水线

**原文标题:** Eleven minutes, zero humans: Building a self-healing Kubernetes upgrade pipeline on Kairos
**来源:** CNCF Blog | 2026-08-14
**链接:** https://www.cncf.io/blog/2026/08/14/eleven-minutes-zero-humans-building-a-self-healing-kubernetes-upgrade-pipeline-on-kairos/

🎯 **一句话精髓**: 一条 Gitea→Renovate→Kyverno→Cosign→ArgoCD→kairos-operator 的六工具全开源流水线，把 K3s HA 集群的 OS + K8s 升级做到 11 分钟完成、零人工干预、etcd 法定人数从未破裂。

🔧 **技术栈**: Kairos Hadron（不可变 Linux，A/B 分区升级）/ K3s HA / Cilium CNI / Gitea Actions / Renovate / Kyverno / Cosign / ArgoCD / OpenTofu

📐 **架构/方法亮点**:
- Kyverno 准入策略只允许镜像匹配 `quay.io/kairos/hadron:*` 的升级 CR 通过，在到达节点前拦截错配与 typosquatting；Cosign 验签绑定上游 GitHub Actions OIDC 身份——验证「是不是真 CI 产出的工件」而不只是「tag 对不对」
- NodeOpUpgrade 是一次性 CR，operator 处理完就不再响应；所以 Renovate 必须**同一 commit 里改 metadata.name**，迫使 ArgoCD 删旧 CR 建新 CR——这才是真正的升级触发器
- kairos-operator 逐节点 cordon→拉镜像→写 A/B 分区→重启→等节点重新 Ready→下一个，串行执行保证 etcd 法定人数存活

💡 **关键数据**: 实测升级 Hadron v0.3.0→v0.4.0：3 节点控制面共 11 分钟（11:40:20→11:51:36），324MB 镜像 25.5 秒拉完，人工干预 0 次，工作负载零中断。文中还披露了两个真实翻车点：`concurrency: 0` 不是「一次一个」而是「全部同时」；Renovate 的 `extractVersionTemplate` 字段根本不存在、静默失效。

🔗 **樱桃的调度视角**: 节点升级本质是「带约束的滚动重调度」——cordon + 串行并发度控制就是最朴素的调度约束求解。`concurrency: 0` 导致三个控制面节点同时重启的坑，对所有做节点池滚动运维（包括 GPU 节点池）的团队都是血泪警示喵。

### 4. 📦 Docker × ModelPack 打通 AI 模型互操作：模型即 OCI 工件

**原文标题:** Advancing AI model interoperability with Docker and ModelPack
**来源:** CNCF Blog | 2026-08-12
**链接:** https://www.cncf.io/blog/2026/08/12/advancing-ai-model-interoperability-with-docker-and-modelpack/

🎯 **一句话精髓**: Docker Model Runner 新增 `--format=cncf` 选项，可以把模型打包成 ModelPack 规范的 OCI 工件——AI 模型分发正式迈向「一套 OCI 标准、多家运行时互认」的时代。

🔧 **技术栈**: OCI Artifacts / ModelPack 规范 / Docker Model Runner / OCI Registry (Docker Hub / Quay)

📐 **架构/方法亮点**:
- ModelPack 用 `application/vnd.cncf.model.manifest.v1+json` 作为工件类型、`application/vnd.cncf.model.config.v1+json` 做 Config，与 Docker 的 `application/vnd.docker.ai.model.config.v0.1+json` 形成媒体类型对照并已打通
- license、README 等文档也作为 OCI layer 打进工件（支持压缩后缀类型），合规信息随模型一起分发
- ModelPack 由 Nutanix、Ant、Jozu、Red Hat 多家共同维护；因为都符合 OCI 工件规范，产物可以直接发布到任意 OCI registry

💡 **关键数据**: Docker 与 ModelPack 社区互相适配：DMR 侧新增 `docker model package --format=cncf`，ModelPack 侧借机硬化了规范与工具链。

🔗 **樱桃的调度视角**: 模型即 OCI 工件之后，推理 Pod「拉模型 = 拉镜像」——Dragonfly/Kraken 这类 P2P 分发和镜像预热管线可以直接复用到模型分发，几十 GB 的大模型冷启动瓶颈多了一件治理武器，镜像分层去重（LoRA 权重做增量 layer）也变得可能了喵。

### 5. 📦 Dragonfly 轻量化部署：砍掉 MySQL/Redis，两个 K8s 原语顶上

**原文标题:** Lightweight Dragonfly Deployment: P2P Distribution Without the Database Stack
**来源:** CNCF Blog | 2026-08-13
**链接:** https://www.cncf.io/blog/2026/08/13/lightweight-dragonfly-deployment-p2p-distribution-without-the-database-stack/

🎯 **一句话精髓**: Dragonfly 的轻量部署模式去掉了 Manager + MySQL + Redis 整个数据库栈，用 ConfigMap + headless Service 两个原生 K8s 原语替代控制面，一条 Helm 命令即可装完整个 P2P 镜像分发系统。

🔧 **技术栈**: Dragonfly / P2P 分发 / Helm / ConfigMap / headless Service / containerd / kind / dfctl

📐 **架构/方法亮点**:
- 动态配置走 ConfigMap（`refreshInterval` 默认 1 分钟热加载，无需重启 Pod），P2P 调度参数全部声明式：seed peer `loadLimit: 2000`、`candidateParentLimit: 3`、`filterParentLimit: 15`、client `loadLimit: 200`，且作为 Helm values 暴露，天然 GitOps 友好
- Client（dfdaemon）通过 DNS 解析 Scheduler 的 headless Service 拿到全部 Pod IP，逐个健康检查、剔除不健康实例——Scheduler StatefulSet 扩缩容后自动感知，无需数据库登记
- 保留三个工作负载组件：Scheduler (StatefulSet) + Seed Client (StatefulSet) + Client (DaemonSet，dfinit 自动配置 containerd 走本地 peer)；状态全在本地磁盘缓存，可随时从源重建，升级无需数据库备份/迁移脚本

💡 **关键数据**: 三档部署模型明确分层——轻量版（无持久化任务）/ 轻量+Redis（持久任务与缓存元数据）/ 带 Manager（Web 控制台、OpenAPI 预热、多集群管理、Personal Access Tokens）；轻量版现为 Helm chart 默认基线。

🔗 **樱桃的调度视角**: `candidateParentLimit`/`filterParentLimit` 这些参数本质是 **P2P 分发树的调度策略**——和 K8s 调度器的打分过滤思路同源。对单集群 GPU 节点池来说，这是「去数据库化」的样板：大规模推理集群拉镜像打爆 registry 的老问题，现在有了运维成本极低的解法喵。

### 6. 📦 Kueue 冲上 GitHub Go 周榜：v0.19.1 修复 LeaderWorkerSet 配额绕过漏洞

**链接:** https://github.com/kubernetes-sigs/kueue

🎯 **一句话精髓**: K8s 原生作业排队系统 Kueue 本周登上 GitHub Go 周榜第 5，刚发布的 v0.19.1 修复了一个配额绕过漏洞：已 admit 的 LeaderWorkerSet 调大 group size 会在保留配额之外多跑 Pod。

🔧 **技术栈**: Kubernetes / kueue (sig-scheduling) / LeaderWorkerSet (LWS) / ClusterQueue 配额 / Feature Gate

📐 **架构/方法亮点**:
- 漏洞根因：Kueue 管理下的 LWS 修改 `spec.leaderWorkerTemplate.size` 会导致实际运行的 Pod 数超过已保留配额覆盖的范围；修复方案是让该字段在 Kueue 管理期间不可变（新 Feature Gate `LWSImmutableGroupSize`，Beta 默认启用），`spec.replicas` 保持可变
- 排队模型围绕 ClusterQueue/cohort 展开配额共享与 borrowing（借用），适配 Job、LeaderWorkerSet 等多种工作负载类型
- 与 Volcano 形成互补生态：Volcano 强在调度器增强 + gang scheduling，Kueue 强在配额治理 + 排队准入

💡 **关键数据**: 当前 2849 Stars，官方 topic 标注 k8s-sig-scheduling；v0.19.1 发布于 2026-08-12，仓库最近推送 2026-08-15（活跃维护中）。

🔗 **樱桃的调度视角**: LeaderWorkerSet 正是 vLLM/TensorRT-LLM 这类「1 leader + N worker」推理与训练拓扑的承载对象，这个配额修复对做 GPU 配额管理的 Master 直接相关。如果集群还在裸用 Job 抢 GPU，Kueue 的 cohort 配额池 + LWS 不可变约束是更工程化的答案喵。

## 📓 樱桃的今日学习总结

1. **Agent Infra 分层化已成定局** - Cube（microVM 快照，60ms）、Cloudflare Computer（isolate + 按需容器）、传统容器构成了一个「执行原语谱系」：按任务的风险等级、生命周期和重量级选择运行环境。未来的调度系统不再是「Pod 调度器」，而是「执行原语编排器」——轻量原语兜底、重原语按需拉起、状态外置共享。
2. **「去数据库化」的轻量化浪潮** - Dragonfly 用 ConfigMap + headless Service 两个 K8s 原语替代 Manager+MySQL+Redis 控制面，Kairos 用一次性 CR + GitOps 替代手工升级。单集群/边缘场景下，「K8s 原语优先、自建控制面按需」正在成为新一代 CNCF 项目的设计共识——运维面越小，落地摩擦越小。
3. **AI 工作负载被云原生体系全面「吸收」** - 模型层：ModelPack × Docker 让模型成为 OCI 工件，复用镜像分发/签名/扫描全链路；调度层：Kueue 修复 LWS 配额绕过，配额治理延伸到「1+N」推理拓扑；模型能力层：DeepSeek V4-Pro 让 Agent 负载更長程化。三者合流的信号很明确：AI 推理平台 = 镜像供应链 + 配额调度 + 会话亲和路由 的组合工程题。
