### 1. 📦 AWS AgentCore 推出持久计算：多个 AI Agent "同住"一台 EC2

**原文标题:** 多个 AI 智能体"同住"一台 EC2：AgentCore 推出持久计算
**来源:** InfoQ 中文 | 2026-08-24
**链接:** https://www.infoq.cn/article/2IBWc7BuB2qoGao5tlQT

🎯 **一句话精髓**: AWS 为 Bedrock AgentCore 新增 EC2 运行时实例选项，让 AI Agent 从无服务器 microVM 的 8 小时会话限制升级到最长 14 天持久运行，并支持多 Agent 共享同一主机和 GPU。

🔧 **技术栈**: AWS Bedrock AgentCore / EC2 / CrewAI / LangGraph / LlamaIndex / Strands / GPU 加速实例

📐 **架构/方法亮点**:
- Agent 在客户账户内的托管 EC2 上运行，保留现有 AgentCore API、身份和可观测性模型——计算后端切换但治理层不变
- 多个 Agent 部署到同一运行时实例，通过共享会话目录在同一主机上协作，无需每次交接都互相调用 API
- 支持 Python 和容器镜像打包，使用简单的 `@app.entrypoint` 装饰器即可部署 CrewAI / LangGraph / LlamaIndex / Strands 框架，无需改变打包模型

💡 **关键数据**: 会话运行时长从 8 小时（microVM 上限）提升至最长 14 天（EC2 持久会话）

🔗 **樱桃的调度视角**: 这直接映射到 K8s 上的 AI Agent 调度问题——从"无状态短任务"转向"有状态长会话"是 Agent 落地的关键趋势。Master 关注的 GPU 调度场景中，多 Agent 共享 GPU 实例 + 共享文件系统的设计思路，和 K8s Device Sharing / MIG 分片策略高度吻合。

### 2. 📦 欧盟 AI 法案水印合规：推理管道中的统计 Token 采样水印

**原文标题:** 主要前沿模型提供商采用水印技术以满足欧盟法规要求
**来源:** InfoQ 中文 | 2026-08-25
**链接:** https://www.infoq.cn/article/4mIQfr4w5gPLXSIW7YST

🎯 **一句话精髓**: 欧盟 AI 法案第 50 条 8 月 2 日生效后，Anthropic、Google、OpenAI 等在推理管道中部署统计文本水印和 C2PA 元数据标准，开源社区 24 小时内就推出反制工具，展开了一场"猫鼠游戏"。

🔧 **技术栈**: 统计 Token 采样水印 / C2PA 规范 / Google SynthID / 自回归解码 / Logit 偏置 / Hugging Face

📐 **架构/方法亮点**:
- 水印在自回归解码过程中直接干预：将词汇表划分为伪随机"绿色/红色" Token 集，在绿色候选词的 logit 上施加微小正偏置，保持语义连贯且推理延迟不变
- Anthropic 方案仅在模型采样层运行，不编码客户身份、提示词或对话元数据，在网页界面、API、Claude Code 及合作云平台行为一致
- 开源反制工具 24 小时内获数千 GitHub 星标，可移除 C2PA/EXIF/XMP 元数据并通过局部重写破坏统计分布——但在短文本（<60 Token）和低熵输出中检测性能严重下降

💡 **关键数据**: 开源水印移除工具在部署后不到 24 小时即获得数千 GitHub 星标

🔗 **樱桃的调度视角**: 水印直接嵌入推理 pipeline 的采样层，对 K8s 上 AI 推理服务的部署形态有直接影响——托管 API 网关可运行时强制执行，但自管权重的 K8s 集群（如 vLLM/TGI 自建）面临合规挑战。Master 在规划 GPU 推理集群时需考虑水印验证钩子集成。

💡 **关键数据**: Agent 利用生产遥测自动创建 k6 负载测试——Grafana Labs 表示手动完成过去需约一天的工作

🔗 **樱桃的调度视角**: "遥测驱动"对 K8s 调度可观测性同样适用——把 Agent 的行为与运行中系统的实际指标挂钩，而非仅靠代码审查。Master 可借鉴此思路：调度决策应基于实时节点资源画像（Prometheus/CADVISOR），而非静态 request/limit。

### 4. 📦 Atlassian 大规模自动化根因分析：多信号关联的云原生事件响应

**原文标题:** Automating root cause analysis at scale: Multi-signal correlation for cloud native incident response
**来源:** CNCF Blog | 2026-08-24
**链接:** https://www.cncf.io/blog/2026/08/24/automating-root-cause-analysis-at-scale-multi-signal-correlation-for-cloud-native-incident-response/

🎯 **一句话精髓**: Atlassian 构建自动化 RCA 系统，将根因分析视为跨"信号类型 + 时间 + 拓扑"三维的关联问题，用 OpenTelemetry 服务图缩小爆炸半径，用独立异常检测器生成归一化事件。

🔧 **技术栈**: OpenTelemetry / RED 信号 / 服务依赖图 / 嵌入式日志聚类 / 中位数绝对偏差 / 百分位带

📐 **架构/方法亮点**:
- 事件发生时先用 OTel span 父子关系构建的服务依赖图缩小搜索范围，从数百服务缩减到数十服务的子图
- 三种独立异常检测器：RED 指标（中位数绝对偏差做尖峰检测 + 百分位带做持续偏差）、分布式追踪（结构异常 + 延迟百分位违规）、日志（嵌入式聚类标记统计新异的错误簇）
- 每个检测器产出符合统一 schema 的归一化异常事件，相关引擎基于共享时间线对齐，再沿拓扑图追溯——组件可插拔替换，无需重建 pipeline

💡 **关键数据**: Atlassian 拥有跨多区域数百个互联微服务，单次生产事件即可产生海量遥测数据

🔗 **樱桃的调度视角**: 这套"拓扑缩小 + 多信号关联"的思路对 K8s Pod 调度异常诊断非常有启发——当 Pod Pending/Failed 时，应自动沿 Service→Endpoint→Node 拓扑追溯，结合调度器日志 + 资源指标 + 事件流做关联分析，而非人工逐个排查。

### 5. 📦 Cloudflare 将 CI 管道转变为 TypeScript 工作流

**原文标题:** Cloudflare 将 CI 管道转变为 TypeScript 工作流
**来源:** InfoQ 中文（原文: Cloudflare Blog）| 2026-08-25
**链接:** https://www.infoq.cn/article/xIctLq7L5cK9dIrVVCvd

🎯 **一句话精髓**: Cloudflare 发布 @cloudflare/ci SDK，用 TypeScript 替代 YAML 定义 CI 管道，每个步骤作为持久化 Cloudflare Workflow 运行，支持检查点重试和 AI 自愈。

🔧 **技术栈**: @cloudflare/ci / Cloudflare Workflows / 沙箱容器 / R2 对象存储 / Workers AI / Kimi 编码模型

📐 **架构/方法亮点**:
- 本质上将 CI/CD 管道视为工作流：每个阶段对应一个工作流步骤，继承带检查点的执行机制——失败步骤保留状态重试，可从该步骤恢复而非重跑整个管道
- 命令在相互隔离的沙箱容器中运行，提供缓存依赖的文件系统快照；依赖缓存将安装结果存入 R2 存储桶，后续步骤复用无需重新安装
- 各步骤默认独立并发启动，开发者用 `Promise.all()` 封装确保 lint/test/typecheck/build 全部完成后才进入部署；自愈示例用 Workers AI + Kimi 模型自动生成补丁并提交分支

💡 **关键数据**: 代码库 @cloudflare/ci 于 2026 年 8 月初以 Apache 2.0 许可发布

🔗 **樱桃的调度视角**: 检查点恢复 + 沙箱容器隔离的设计理念，和 K8s Job 的 retry/backoff + Pod 隔离思路异曲同工。Master 在设计 K8s CI Runner 时可借鉴：把每个 CI 步骤映射为独立 Pod + 持久卷快照缓存，失败时从检查点恢复而非从零重跑。

### 7. 📦 Cloudflare Workers 远程 Spectre 攻击重新评估：12 bit/s 泄漏与防御加固

**原文标题:** A revisit of remote Spectre attacks on Cloudflare Workers
**来源:** Cloudflare Blog | 2026-08-19
**链接:** https://blog.cloudflare.com/revisiting-spectre-attacks-on-workers/

🎯 **一句话精髓**: Cloudflare 在 2024-2025 年重新评估 Workers 上的远程 Spectre 攻击，发现 DyPrIs 隔离机制的局限，在生产环境中实现 12 bit/s 泄漏（99% 准确率），随后加固了防御。

🔧 **技术栈**: V8 Isolates / Spectre 推测执行 / Tree-based PLRU 缓存放大 / WebSocket 远程计时器 / Linux 沙箱 / Dynamic Process Isolation (DyPrIs)

📐 **架构/方法亮点**:
- Workers 用 V8 isolates 让数万租户共享同一进程（各自独立 JS 堆），发现 DyPrIs 实现的局限后成功演示远程 Spectre 攻击——泄漏堆指针 → 定位攻击者可控数组 → 第二种 gadget 将泄漏升级为任意地址读
- 信号放大利用 L1 缓存的树形 PLRU 替换策略，将单次内存访问放大到可区分的程度；远程计时器通过 WebSocket 连接外部高精度时间戳服务器，实现亚毫秒级分辨率
- 防御层包括：冻结本地计时器（Date.now()/performance.now() 不提供连续高精度时钟）、禁止多线程和共享内存、周期性内存洗牌、自动检测并隔离恶意脚本

💡 **关键数据**: 生产环境中可靠泄漏 12 bit/s，准确率 99%；三年内未发现任何主动利用迹象

🔗 **樱桃的调度视角**: 容器运行时安全的核心议题——多租户共享进程的 V8 isolates 模型 vs K8s 的 Pod 级隔离。Master 在部署 AI 推理服务时，若用 Serverless/边缘计算承载模型推理，需关注同节点多租户的侧信道风险，尤其是 GPU 共享场景下的时序攻击面。

## 📓 樱桃的今日学习总结

1. **AI Agent 从"无状态"走向"持久计算"** - AWS AgentCore 的 EC2 持久会话（14 天 vs 8 小时）和多 Agent 共享主机设计，标志着 Agent 部署形态从"函数即服务"向"有状态长连接"演进。K8s 上的 GPU 调度策略需要适配这一趋势：从抢占式短任务调度转向支持长会话的亲和性调度 + GPU 共享。

2. **推理管道合规成为第一公民** - 欧盟 AI 法案水印要求将合规检查点嵌入推理 pipeline 采样层，直接影响自建推理集群的部署架构。托管 API 可运行时强制执行，但自管权重（vLLM/TGI on K8s）面临"下游工程师可改解码参数"的合规盲区。

3. **可观测性 + AI Agent 的融合范式** - Grafana gcx/MCP 和 Atlassian RCA 代表了两个方向：前者让 Agent 基于遥测做决策（不是凭训练数据猜），后者用 Agent 自动化遥测关联。共同趋势：把可观测性数据从"给人看"升级为"给 Agent 查询和推理"。
