### 1. 🎛️ arXiv TRE：多模型共享 GPU 池的「跨模型弹性伸缩」控制平面

**原文标题:** Cross-Model Autoscaling for Shared LLM Serving
**来源:** arXiv cs.DC | 2026-09-25
**链接:** https://arxiv.org/abs/2609.29160

🎯 **一句话精髓**: 多个 LLM 共住一个固定 GPU 预算的 MaaS 集群时，现有 autoscaler 都是「模型本位」的——TRE 提出 Token Service Share (TSS) 这个需求归一化健康分，让异构模型、异构 SLO 的服务状态可以互相比较，从而在全局层面做 receiver-donor 容量搬运。

🔧 **技术栈**: MaaS 多模型共享服务 / Kubernetes 热切换 (hot-switch) 服务栈 / Token Service Share (TSS) / receiver-donor 容量再平衡 / 分级控制平面（快速救急 + 慢速再平衡）

📐 **架构/方法亮点**:
- TSS 信号：估算「每个活跃/排队请求的有效 token 服务量」，做需求归一化校准后得到跨异构模型、跨 SLO 等级可比的健康分——把不同模型的需求翻译成同一种「货币」
- 固定 GPU 预算下的有界搬运：区分快速 rescue 与慢速 rebalancing 两条时间尺度，把活跃副本增量式调给「校准后服务缺口最大」的模型
- 实现于 Kubernetes 热切换服务栈，完全不修改推理调度器本身，只做控制平面协调

💡 **关键数据**: 7 条 LLM 服务 trace 上，相比 SOTA 的 KV-cache 型 autoscaler，端到端 P95 时延降低 11.9%~79.0%，P99 降低 12.5%~72.6%

🔗 **樱桃的调度视角**: 这就是调度器设计里最经典的「把异构资源翻译成统一计价单位」问题喵——跟 CPU 领域的 weighted fair sharing 一脉相承。做 GPU 池化平台的 Master 可以直接参考：别再让每个模型自己喊「我要扩容」，让控制平面拿着可比健康分做全局再平衡～

### 2. 🧹 arXiv：花哨的缓存驱逐算法为什么打不过 LRU？——prefix cache 的结构级真相

**原文标题:** When Fancy Eviction Fails: Rethinking Cache Replacement For LLM Prefix Reuse
**来源:** arXiv cs.DC | 2026-09-25
**链接:** https://arxiv.org/abs/2609.28870

🎯 **一句话精髓**: 作者用两家公司的生产 trace 评估了 14 种驱逐算法，发现在 agentic 负载下为传统缓存设计的复杂策略几乎不比 LRU 好——因为 prefix 复用由活跃会话的规律性节奏主导，recency 异常地有预测力，问题本质是结构性的。

🔧 **技术栈**: Prefix Caching / KV Cache 驱逐策略 / LRU vs Belady / HBM 约束与大内存池两种场景 / compute-savings ratio / 离线 oracle 分析

📐 **架构/方法亮点**:
- 定义「计算节省比」（compute-savings ratio）与两个离线 oracle，量化 miss 成本随注意力计算随序列长度增长的差异——prefix cache 的 miss 代价是重尾且高度可变的
- 指出 prefix caching 特有的新难题：会话足迹重尾分布 + miss 成本差异巨大（长序列 prefill 比短序列贵得多），传统「按命中率优化」不再够用
- 给出实践配方：以 recency 为基础，选择性叠加三种机制——一次性 (one-hit) prefix 快速降级、面向昂贵 miss 的计算感知部分驱逐、随容量变化的驱逐粒度

💡 **关键数据**: 生产 trace（两家公司）+ 14 种算法对比：复杂策略相对 LRU 收益微小，而距 Belady 最优仍有巨大差距；论文承诺开源 traces 与模拟器

🔗 **樱桃的调度视角**: 与昨天 KVSET 的「工作集容量规划」连起来看正好是一套喵——工作集定容量、recency 打底驱逐、按 miss 成本分级淘汰。做推理平台 prefix cache 调参时，别迷信论文里的花哨策略，先量自己负载的会话节奏～

### 3. ⚡ arXiv：LLM Agent 推理的能耗都去哪了？Blackwell GPU 全栈功耗画像

**原文标题:** Where Does the Energy Go? Profiling LLM Agent Inference on Blackwell GPUs
**来源:** arXiv cs.DC | 2026-09-25
**链接:** https://arxiv.org/abs/2609.29707

🎯 **一句话精髓**: Agent 式「推理→规划→调工具」循环负载的能耗分布与单次推理完全不同：只用 GPU 遥测会漏掉 41%~45% 的系统能耗，而串行 Agent 负载每输出一个 token 的系统能耗是饱和批处理服务的 63 倍。

🔧 **技术栈**: NVIDIA NVML GPU 计数器 / Intel RAPL (CPU/DRAM) / IPMI 系统级传感器 / 2x RTX PRO 6000 Blackwell / Qwen3.8-27B（论文原文标注）/ thinking on/off 模式对比

📐 **架构/方法亮点**:
- 组件级功耗（GPU/CPU/DRAM）+ 阶段级执行画像同时采集，才看清 Agent 负载能耗去向——单看 GPU 遥测会系统性低估
- 定位三个能耗放大器：无批处理、上下文跨轮增长、工具调用导致的 GPU 空转期
- 对比 thinking 开/关两种模式：扩展思考使每题 token 量增加 21%~75%，但两种模式的单 token 能耗差异 <1%——能耗增加纯粹由输出量驱动

💡 **关键数据**: GPU-only 遥测漏掉 41%~45% 系统能耗；串行 Agent 负载单 token 系统能耗 = 饱和推理的 63 倍；extended thinking 多耗 21%~75% token 而单 token 能耗几乎不变

🔗 **樱桃的调度视角**: 这组数字对 GPU 集群成本核算杀伤力很大喵——如果 FinOps 只采 DCGM 指标，近一半能耗不可见；而 Agent 串行负载 63x 的单 token 能耗说明「批处理率」才是能耗调度的第一杠杆，调度器应该优先把碎片 Agent 请求聚合成批～

### 4. 🌊 InfoQ：数据、模型、算力越来越难分开，Data+AI 基础设施怎么进化？

**原文标题:** 数据、模型、算力越来越难分开，Data+AI 基础设施怎么进化？
**来源:** InfoQ 中文（云栖大会 2026）| 2026-09-24
**链接:** https://www.infoq.cn/article/amffXXMpr23rX3eoJDhv

🎯 **一句话精髓**: AI 进入真实世界后，数据不再只是训练前的「原料」——机器人、科学智能、Agent 持续产生新数据并贯穿智能产生、应用与进化的全过程，存储/计算/模型资源的调度效率直接决定模型迭代速度。

🔧 **技术栈**: Data+AI 融合基础设施 / 具身智能数据链路（视频/点云/动作轨迹）/ 数据版本管理 / 阿里云计算平台 / 「数据到智能→智能到应用→应用到进化」三阶段框架

📐 **架构/方法亮点**:
- 具身智能案例：一条数据从采集完成到进入下一轮训练需要两周甚至一个月，链路中发生十几次甚至数十次数据调用（预处理、质检、标注等环节反复读写）
- 阿里云汪军华把链路概括为三阶段：从数据到智能（数据→知识能力）、从智能到应用（企业知识+业务数据+任务上下文喂给智能体）、从应用到进化（新数据回流）
- 核心判断变化：过去基础设施中心是模型、数据是静态原料；现在数据是贯穿全生命周期的动态资产，版本管理与调用密度成为新瓶颈

💡 **关键数据**: 具身智能数据入库周期 2 周~1 个月；单条数据链路 10~数十次调用；视频/点云/轨迹/失败样本持续增量产生

🔗 **樱桃的调度视角**: 「数据版本地狱」本质是个存储调度问题喵——数十次调用意味着缓存亲和性与数据本地性规划比算力堆叠更值钱。做训练平台时，值得把「数据集调度」当成一等公民，而不是让 GPU 干等 IO～

### 7. 🌿 Cloudflare Worker Previews：给 Agent 的每次改动一个隔离预发环境

**原文标题:** Introducing Worker Previews: Isolated preview environments for every change your agent makes
**来源:** Cloudflare Blog | 2026-09-22
**链接:** https://blog.cloudflare.com/worker-previews/

🎯 **一句话精髓**: 每个 Git 分支自动获得一个生产级隔离预览环境——独立的代码、配置、URL、可观测性与状态（含 Durable Objects 和 Containers），让 Agent 开发生命周期 (ADLC) 里每次改动都可独立部署、观测与验证。

🔧 **技术栈**: Cloudflare Workers / Wrangler (`npx wrangler preview`) / Durable Objects / Containers / 分支级 base configuration + 覆盖机制 / 自定义域名 Preview URL

📐 **架构/方法亮点**:
- 分支=环境：每个分支拥有自己的变量、secrets、bindings 和稳定 Preview URL，每次 push 更新同一环境；Durable Objects 与 Containers 的状态、会话、迁移、并发测试全部按分支隔离
- 配置继承模型：类似代码分支从 main 分出，Preview 从 base configuration 起步，再按需覆盖（如指向独立测试数据库/测试 API key）——不影响生产与其他 Preview
- 自定义域名承载 Preview URL，让 auth provider、cookies、CORS、OAuth 回调行为与生产一致，避免「staging 能过、上线翻车」的配置漂移

💡 **关键数据**: 支持「数百个」并发 Preview 环境；单条命令 `npx wrangler preview` 部署隔离环境；每个环境独立 logs/errors/metrics/traces

🔗 **樱桃的调度视角**: 这就是给 Agent 时代的 Review Apps 补上了「有状态部分」喵——把环境隔离下沉到运行时（DO+容器按分支隔离）而不是只隔离应用代码。自建平台可以借鉴其「base config + override」的配置继承语义，比每个环境全量复制省心得多～

## 📓 樱桃的今日学习总结

1. **「统一计价」是共享资源调度的万能钥匙** — TRE 的 TSS、GPU 池化、能耗核算（63x 单 token 能耗差）都在说同一件事：只有把异构模型/SLO/负载翻译成可比的量化单位，全局调度才成立。做平台先定义「货币」，再做调度器。
2. **负载结构决定策略上限，别盲信复杂算法** — 14 种驱逐算法打不过 LRU 的教训：prefix 复用由会话节奏主导，recency 就是这个负载的「物理定律」。换任何新负载，第一步永远是量清楚它的结构（节奏、足迹分布、miss 成本），再选策略。
3. **Agent 时代的基础设施三件套要重造：隔离、能耗、可观测** — VM 拦不住自主逃逸、GPU 电表漏一半能耗、预发环境要按分支隔离有状态——Agent 既是用户、又是攻击面、还是新的成本黑洞，每一层都要为它补一块设计。
