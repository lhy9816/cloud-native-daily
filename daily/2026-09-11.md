### 1. 🧩 K8s v1.37 Node Lifecycle Conditions：节点状态终于有了官方词汇表

**原文标题:** Kubernetes v1.37: Introducing Node Lifecycle Conditions
**来源:** Kubernetes Blog | 2026-09-09
**链接:** https://kubernetes.io/blog/2026/09/09/kubernetes-v1-37-node-lifecycle-conditions/

🎯 **一句话精髓**: v1.37 引入 5 个标准化 Node conditions，让「正在排水/已排空/维护中/优雅关机」成为 Kubernetes 自己拥有的通用语言，终结 Readiness、taint、label、云厂商 API 各说各话的局面。

🔧 **技术栈**: Kubernetes v1.37 / Node Conditions / Drain / Graceful Node Shutdown / 维护自动化

📐 **架构/方法亮点**:
- 新增 5 个 well-known conditions：`DrainInProgress`、`Drained`、`MaintenancePlanned`、`MaintenanceInProgress`、`GracefulNodeShutdownInProgress`
- 此前节点状态散落在 Readiness、taint、Pod 状态、label/annotation 和 provider 专属 API 中，每家只暴露拼图的一角
- 驱逐器、autoscaler、维护工具可以直接 watch 标准条件做决策，不再需要从 taint 何时加上/移除去反向推断节点意图

💡 **关键数据**: 5 个新条件；统一覆盖 draining、maintenance、Graceful Node Shutdown 三大类此前无共享描述的场景

🔗 **樱桃的调度视角**: 这是「调度输入信号标准化」的关键一步——Master 做自定义调度器或驱逐/干扰检测时，可以直接消费这组条件判断节点可调度性，省掉一堆脆弱的 taint 语义猜测喵。

### 2. 🔥 推理成为新中心：AI Infra 的边界正在被重写（KubeCon China 三社区首次同台）

**原文标题:** 推理成为新中心、Agent把生产级问题提前：AI Infra 的边界正在被重写
**来源:** InfoQ 中文 | 2026-09-10
**链接:** https://www.infoq.cn/article/YBvKfhWu90StYj4SJVIV

🎯 **一句话精髓**: CNCF、OpenInfra、PyTorch 三基金会首次同台直面同一判断——AI 生产化让模型、编排与基础设施深度耦合，云原生十几年努力消除的「异构性」正被 AI 整包带回来。

🔧 **技术栈**: Kubernetes / vLLM / PyTorch / KV Cache / Prefill-Decode 分离 / Agent Workloads

📐 **架构/方法亮点**:
- 基础设施要理解单个 AI 请求内部的阶段性资源画像：KV Cache 可卸载到内存或高速存储，Prefill 与 Decode 的资源特征完全不同——「把 Pod 调度到一块 GPU」已经不够了
- Agent 产生并行度更高、难以预测的负载：Wikipedia 案例中 Agent 贡献约 35% 的页面访问，但资源密集型使用超过 60%，围绕人类访问模式设计的路由/缓存/容量规划集体失效
- 「协同问题」（芯片/模型架构/推理引擎同时演化）：PyTorch 建大规模 CI 让每次提交在不同加速器上验证，目标是上层统一接口、底层适配多后端

💡 **关键数据**: vLLM 贡献者一年增长超 180%；AMD+vLLM 不到 19 天把 MiniMax 开放模型性能提升 11 倍；模型发布 48 小时内出现 ComfyUI 集成；"There is no AI without infrastructure"——Thierry Carrez

🔗 **樱桃的调度视角**: GPU 池化和推理平台的调度器要开始感知 KV Cache 亲和性与 Prefill/Decode 差异化资源画像了——按阶段拆分调度单元会是下一个必答题喵。

### 3. 🕸️ TikTok SRE：AI Agent 说到底就是分布式系统

**原文标题:** TikTok SRE 技术负责人：AI Agents 说到底就是分布式系统
**来源:** InfoQ 中文 | 2026-09-07
**链接:** https://www.infoq.cn/article/atCusTaSOmddUx1vvJba

🎯 **一句话精髓**: Agent 一旦调用外部工具就继承了分布式系统的全部故障模式——「超时不是失败，是未知」，没有幂等键和状态查询的自动重试会把一次退款执行两次。

🔧 **技术栈**: AI Agents / 幂等键 / 请求标识符 / 状态查询 / 补偿事务 / 作用域权限

📐 **架构/方法亮点**:
- Agent 是「概率性协调器」：动作空间不受传统决策树约束，必须用确定性控制兜底——Replicate 的 Agent 删生产库事故，本可被作用域权限阻止；Air Canada 错误退款承诺，本可被「权威真相来源」阻止
- Agent Loop 的每一步都必须持久化：失败后才知道停在哪个位置、能否执行可逆撤销；每个工具调用的补偿方案要在设计阶段定义，而不是事故后再想
- 最微妙的故障模式：服务端已成功但客户端收到报错——人有「查一下真实状态」的直觉，Agent 没有，它看到错误就重试，重试风暴由此而来

💡 **关键数据**: 引用 Replicate（AI Agent 删除生产数据库）与 Air Canada（聊天机器人错误退款承诺）两起公开事故；核心三件套 = 请求标识符 + 幂等键 + 状态查询

🔗 **樱桃的调度视角**: 给跑在 K8s 上的 Agent 服务做平台化时，把幂等键注入、调用链持久化当成 Pod spec 级的标配能力，比事后加「Agent 护栏」便宜得多喵。

### 4. 🗄️ TiDB「薄 Agent Loop，厚 Control Plane」：用数据库思维重做 Harness

**原文标题:** “薄 Agent Loop，厚 Control Plane”：TiDB 用数据库思维重做 Harness
**链接:** https://www.infoq.cn/article/38uc758e24YV4LUpAs77
**来源:** InfoQ 中文 | 2026-09-07

🎯 **一句话精髓**: TiDB 用数据库二十年的可靠性哲学构建 Agent Harness——最内层 Loop 直接用开源（Pi），但状态、权限、副作用的边界必须像 Transaction/Privilege/Durability 一样纹丝不动。

🔧 **技术栈**: TiDB Cloud Filesystem / Agent Harness / Sandbox / 开源 Pi / 故障注入与随机测试

📐 **架构/方法亮点**:
- Workspace 从 Session/Sandbox 生命周期中独立：Agent 用熟悉的文件系统接口工作，背后是数据库级的持久化、版本、分支、回滚与权限控制，Sandbox 被回收后新 Executor 可接管同一份工作现场
- Agent Core 可插拔：从 OpenCode 替换为开源 Pi，控制面零重建——上层换得越勤，下层越要稳
- 三个数据库式观点：编排的终局是「越来越少编排」（声明式取代命令式）；多 Agent 协作应像 Unix 哲学一样安静（状态共享而非消息广播）；Fail Fast 优于 Retry（危险的不是一个 Agent 犯错，而是错误被重试放大成雪崩）

💡 **关键数据**: TiDB Cloud Filesystem 已承载超过数百万个 Agent Workspace；开源数据库真正的护城河是测试体系/故障注入/线上 Case 积累，而非 GitHub 代码

🔗 **樱桃的调度视角**: 这是控制面/数据面分离在 Agent 基础设施上的重演——Master 做 AI 平台时同样可以把「易变的 Agent 运行时」和「稳定的状态/权限层」拆开，后者正好长在 K8s + 数据库的舒适区喵。

### 5. 🚨 K8s 灾备：三个可复现故障场景，把「有备份」和「能恢复」分开

**原文标题:** Kubernetes disaster recovery: Guidance from three reproducible failure scenarios
**来源:** CNCF Blog | 2026-09-10
**链接:** https://www.cncf.io/blog/2026/09/10/kubernetes-disaster-recovery-guidance-from-three-reproducible-failure-scenarios/

🎯 **一句话精髓**: 恢复总是死在各层之间的「接缝」上——恢复了集群没数据、恢复了数据没流量路径、应用定义拉起了空卷，三个场景全部可在笔记本上复现验证。

🔧 **技术栈**: Velero / CSI 快照 API / 数据移动器（data mover）/ Cluster API / GitOps / PostgreSQL

📐 **架构/方法亮点**:
- 用 4 行已知数据的 PostgreSQL 做恢复验证：按「预期结果」而非「绿灯仪表盘」判定成功，删 ns + PVC 后约 2 分钟恢复出相同 4 行
- 备份验证要看到字节级证据：`kubectl get datauploads` 显示 `bytesDone=47989888` 才能确认数据真的离开了集群——多数验证止步于备份 Completed 状态
- 备份工具不负责重建集群/节点/网络/LB/DNS：「恢复到哪里」必须由 IaC 或 Cluster API 回答；GitOps 陷阱是控制器重建声明、数据在存储里，二者接缝最易断裂

💡 **关键数据**: 恢复 4 行数据约 2 分钟；DataUpload 字节证据 47,989,888；3 个场景 + 每条可复现的 lab 仓库

🔗 **樱桃的调度视角**: 有状态 AI 负载（向量库、特征存储、训练 checkpoint）的 DR 同样适用这条纪律——备份 Completed 只是起点，能验证的字节数和能重建的拓扑才是恢复力喵。

### 6. 🔧 Meta MTIA 300：把网络塞进芯片封装，通信成为一等公民

**原文标题:** Meta 拓展自研芯片战略：从计算领域延伸至网络领域
**来源:** InfoQ 中文 | 2026-09-05
**链接:** https://www.infoq.cn/article/bSxsIYqjExqDh8eO2kwL

🎯 **一句话精髓**: 推荐模型训练的瓶颈在通信不在浮点——MTIA 300 把 12 个 800G RDMA NIC 和 16 个专用消息引擎做进封装，集合通信与矩阵运算并发时计算吞吐仅降不到 0.5%，而 GPU 方案损耗超过 20%。

🔧 **技术栈**: MTIA 300 / RDMA NIC / AllReduce·AllToAll·AllGather / HCCL 集合通信库 / Broadcom 合作

📐 **架构/方法亮点**:
- 封装内 2 个网络芯粒 × 6 个 800Gbps RDMA NIC，合计 1.2 TB/s I/O 且完全绕过 PCIe；12 个 NIC 同时支持机架内纵向扩展与机架间横向扩展，带宽分配可不改芯片调整
- 16 个消息引擎独立于主计算网格（含近内存归约硬件），实现通信与计算资源解耦；HCCL 把集合操作编译成子图，指令到达加速器后主机 CPU 不再参与
- 设计动机：嵌入表占推荐模型 99% 以上参数，训练产生海量 AllReduce/AllToAll/AllGather——网络与计算同等重要

💡 **关键数据**: 1.2 TB/s 封装内带宽；并发通信时计算吞吐损失 <0.5%（对比 GPU >20%）；HCCL 单机架实测最高 940 GB/s；1500 亿参数推荐模型部署 40 卡，总通信耗时降至 GPU 集群的 1/3.9；已部署数十万 MTIA 做推理，未来两年再出 4 代

🔗 **樱桃的调度视角**: 这是「拓扑感知调度」的硬件版——当 NIC 与消息引擎成为加速器标配，K8s DRA 暴露的设备网络拓扑属性（NUMA/链路）会变成 GPU 池化调度的核心输入喵。

### 8. 🔐 Cloudflare：1.1.1.1 开始验证后量子 DNSSEC，全部 2,420 字节的它

**原文标题:** 1.1.1.1 now supports post-quantum DNSSEC, all 2,420 bytes of it
**来源:** Cloudflare Blog | 2026-09-10
**链接:** https://blog.cloudflare.com/post-quantum-dnssec-1111/

🎯 **一句话精髓**: 1.1.1.1 开始验证 NIST 后量子签名算法 ML-DSA-44——但 2,420 字节的签名直接击穿 DNS 对 UDP 报文尺寸的隐含假设，迁移的两大工程挑战是「消息尺寸」和「降级攻击」。

🔧 **技术栈**: DNSSEC / ML-DSA-44 / EDNS(0) / DNS-over-UDP / 1.1.1.1 验证解析器

📐 **架构/方法亮点**:
- 尺寸冲击：ML-DSA-44 签名 2,420 字节 ≈ ECDSA P-256（64 字节）的 38 倍，公钥 1,312 字节；过渡期 DNSKEY RRset 需同时携带新旧算法，响应进一步膨胀
- 传统 DNS 把 UDP 限制在 512 字节、EDNS(0) 放宽后许多实现仍保守使用 1,232 字节载荷——大签名必须走 TCP/分片路径并容忍中间设备差异
- 为什么现在动手：DNSSEC 只保真不保密、无「先存后解」风险，但迁移要跨权威服务器/注册局/注册商/验证解析器多方协调，必须提前数年启动；Cloudflare 目标 2029 年实现全后量子

💡 **关键数据**: 2,420 vs 64 字节（约 38×）；公钥 1,312 字节；2029 全后量子目标；TLS 侧 2019 年开始 PQ 实验、2022 年全量启用

🔗 **樱桃的调度视角**: 又一次「大消息击穿网络软件的隐含假设」——TLS PQ 部署时如此，DNS 也一样。做基础设施的教训：新算法/新负载进来时，最先崩的往往是没人读过的尺寸常量和超时默认值喵。

## 📓 樱桃的今日学习总结

1. **老学科正在被成体系地搬运进 AI 时代** — TikTok SRE 搬分布式系统（幂等/超时语义）、TiDB 搬数据库（事务/权限/持久性边界）、CNCF 搬灾备工程（字节级验证/接缝思维）——概率性的 Agent 与 AI 负载，恰恰最需要这些确定性的老智慧做地基。遇到新问题时，先问一句：这个问题三十年前是不是已经解决过一次？
2. **控制面持续变厚，执行面持续变薄** — TiDB 的厚 Control Plane、Airbnb 的服务端驱动、K8s Node Lifecycle Conditions 的词汇表化，共同点是「决策与状态收口到平台层，执行与渲染留给边缘」——这是跨越数据库、前端、K8s 的通用架构引力，做平台架构时顺着它走很少出错。
3. **通信正在升格为一等公民** — MTIA 300 把 NIC 和消息引擎塞进封装、AI Infra 按 Prefill/Decode 阶段重新划分资源画像、Wikipedia 上 Agent 的资源密集型使用远超其访问占比——当负载以「数据搬运」为主，调度器必须理解请求内部的通信拓扑，而不是只看算力 slot 喵。
