### 1. 📦 Linkerd 多集群联邦实战：三种模式混合部署实现零停机 K8s

**原文标题:** Federating clusters for zero-downtime Kubernetes
**来源:** CNCF Blog | 2026-07-27
**链接:** https://www.cncf.io/blog/2026/07/27/federating-clusters-for-zero-downtime-kubernetes/

🎯 **一句话精髓**: 在三个 GKE 集群上实战 Linkerd 多集群三种模式（Gateway 镜像 / Flat Pod-to-Pod / Federated 联邦），通过全网格链路拓扑 + 混沌测试验证整集群故障时的自动流量转移。

🔧 **技术栈**: Linkerd multicluster / GKE VPC Peering / mTLS / 服务网格 / Kubernetes 多集群

📐 **架构/方法亮点**:
- 三种多集群模式可在同一组链路上按 Service 粒度通过 label 切换：`mirror.linkerd.io/exported=true`（网关镜像）、`remote-discovery`（扁平网络直连 Pod）、`federated=member`（同名服务联邦负载均衡）
- 全网格 VPC Peering（west↔east↔north 六条方向链路），通过 `--export-custom-routes` 让 Pod CIDR 跨区域可路由，实现扁平网络
- 共享信任锚（root CA）+ 每集群独立 issuer 证书，单集群证书泄露可隔离轮换而不影响其他集群的 mTLS 信任链

💡 **关键数据**: 3 个 GKE 集群 × 3 副本 = 9 个 Pod 参与联邦负载均衡；混沌测试中干掉整个集群后剩余 6 Pod 自动吸收流量，零应用层变更

🔗 **樱桃的调度视角**: 这正是多区域 K8s 调度的核心场景——联邦模式下同名 Service 跨集群负载均衡，本质上是将调度域从单集群扩展到多集群。Master 如果做多区域 GPU 调度，可以参考这种「按 Service 标签选择多集群模式」的思路，让 AI 推理服务在不同区域的 GPU 集群间实现自动故障转移。

### 4. 📦 从 Token 到任务：Agentic AI 正在重新定义基础设施的关注焦点

**原文标题:** 从Token到任务：Agentic AI 如何改变基础设施的关注焦点
**来源:** InfoQ 中文 | 2026-07-27
**链接:** https://www.infoq.cn/article/vhx0VYNXpieSIuq0YIR6

🎯 **一句话精髓**: AI 智能体让推理从「单次 prompt-response」演变为「持续工作流」，性能衡量维度从 Token 吞吐量转向完整任务交付，GPU 不再是唯一关键路径。

🔧 **技术栈**: Agentic AI / GPU 推理 / 任务编排 / 沙箱运行时 / 工具调用 / 上下文检索 / 遥测采集 / 策略系统

📐 **架构/方法亮点**:
- 一条提示词可触发请求解析→任务创建→策略检查→代码库检索→上下文拼接→Token 编码→模型调用→工具验证→沙箱路由→文件编辑→测试运行→遥测采集→结果核验的完整任务图
- 智能体工作流的关键路径不再局限于模型执行：任务规划、上下文检索、状态管理、工具/API 调用、沙箱运行、结果验证等大量协调工作由 CPU 承担
- 推理演变为分布式系统问题：哪些任务在运行、在哪里运行、伴随哪些上下文、允许使用哪些工具、结果是否满足需求

💡 **关键数据**: 传统推理指标（prefill/decode/每秒 Token 数/首 Token 延迟/批处理效率）仍重要，但已不再是系统性能的唯一决定因素

🔗 **樱桃的调度视角**: 这直接关系到 K8s 上的 AI 推理调度策略！当 Agent 工作流涉及大量 CPU 侧编排（检索、沙箱、工具调用）+ GPU 侧推理时，调度器需要同时分配 CPU 和 GPU 资源，而不是只看 GPU 利用率。Master 在设计推理集群调度时，应该考虑「任务图编排」而非「单次推理请求」的资源分配模型。

### 5. 📦 多区域架构决策框架：延迟、成本与复杂度的真实权衡

**原文标题:** 多区域架构中的权衡：延迟与成本
**来源:** InfoQ 中文 | 2026-07-28
**链接:** https://www.infoq.cn/article/i84fFL01baIXa1P6Kqcl

🎯 **一句话精髓**: 作者基于多次跨区域部署经验，提出多区域架构不能简单用「延迟改善收入 > 区域成本」的算术模型决策，需要量化基础设施、服务上线、复制同步和运营四类隐藏成本。

🔧 **技术栈**: 多区域部署 / 同步/异步复制 / 跨区域网络 / 自动扩展 / 服务依赖管理 / 部署管道自动化

📐 **架构/方法亮点**:
- 新增区域总拥有成本四维度：基础设施资本支出（约 25%）、服务上线开销（数百服务×数千依赖问题）、复制同步成本（同步复制增加 ~100ms 写延迟）、运营开销（值班覆盖+部署管道+事件响应）
- 同步复制可能使写入延迟增加近 100ms；异步复制引入最终一致性窗口，需应用层处理
- 自动化部署检查点信号（从服务监控提取健康指标而非人工 TPM 协调），12 个月内使数十个服务团队手动工作量减少 89%

💡 **关键数据**: 基础设施资本支出约占区域总成本 25%；自动化使手动工作量减少 89%；跨区域同步复制写入延迟增加近 100ms

🔗 **樱桃的调度视角**: 这对多区域 K8s 调度有直接参考价值——跨区域调度不仅要考虑延迟，还要量化复制成本和运营开销。Master 在做多区域 GPU 调度时，同步复制 100ms 写延迟可能影响推理模型的参数同步策略，需要权衡强一致性和延迟的取舍。

### 6. 📦 Cloudflare 开源隐私代理 CLI：OHTTP 协议调试的 curl 替代品

**原文标题:** We're open-sourcing our privacy proxy CLI
**来源:** Cloudflare Blog | 2026-07-27
**链接:** https://blog.cloudflare.com/open-sourcing-our-privacy-proxy-cli/

🎯 **一句话精髓**: Cloudflare 开源 pvcli——一个类似 curl 的 CLI 工具，将 Oblivious HTTP（OHTTP）协议的多步骤调试（客户端→中继→网关→源站）简化为一条命令，解决隐私协议调试难的痛点。

🔧 **技术栈**: OHTTP（Oblivious HTTP）/ Binary HTTP / QUIC / HTTP/3 / Rust / Apache-2.0

📐 **架构/方法亮点**:
- OHTTP 通过中继（Relay）和网关（Gateway）两个非合谋方实现隐私保证：中继移除「谁」发出请求，网关解密请求内容，任何一方都无法同时知道身份和内容
- pvcli 按顺序展示协议每一步（获取公钥→加密请求→中继转发→网关解密→源站处理→响应加密→中继回传→客户端解密），精确定位故障环节
- 基于 Cloudflare 百万级 QPS 的 OHTTP 运营经验构建，支持 Apple Private Relay、Microsoft Edge Secure Network 等产品场景

💡 **关键数据**: Cloudflare 在百万级请求/秒规模运营 OHTTP 协议；pvcli 可将多步骤 OHTTP 请求简化为单条命令执行

🔗 **樱桃的调度视角**: 虽然不直接涉及 K8s 调度，但 OHTTP 的多跳架构（客户端→中继→网关→源站）与多集群服务网格的流量路径有相似性。在 K8s 服务网格中调试跨集群 mTLS 流量时，可以借鉴这种「按步骤展示协议链路」的调试思路，快速定位是调度问题还是网络问题。

🔧 **技术栈**: GitLab CI/CD / 碳排放估算模型 / 智能缓存 / 并行执行 / 执行器利用率监控 / 区域电网碳强度数据

📐 **架构/方法亮点**:
- 非直接测量服务器用电量，而是通过管道执行时长 × 执行器利用率 × 计算资源 × 区域电网碳强度的关联模型估算碳排放
- 核心洞察：减少碳排放与提高工程效率天然契合——不必要任务、重复构建、过度配置执行器、冗余测试同时增加成本和碳排放
- 测量结果整合到现有工程仪表盘，可比较不同项目、识别低效工作流、观察架构变更对可持续性的影响

💡 **关键数据**: 碳排放成为软件交付中与构建时长、部署频率并列的可观测指标；智能缓存、并行执行、选择性测试可同时降低成本和碳排放

🔗 **樱桃的调度视角**: 这个思路完全可以迁移到 K8s GPU 调度！GPU 是能耗大户，调度器在做调度决策时可以引入「碳感知调度」——根据区域电网碳强度数据，将非紧急的 AI 训练任务调度到碳排放低的区域或时段。这与 Kubernetes 的拓扑感知调度（Topology Aware Routing）理念一致，只是感知维度从网络拓扑扩展到能源拓扑。

## 📓 樱桃的今日学习总结

1. **多集群调度域正在从理论走向实战** - Linkerd 的三种多集群模式（Gateway/Flat/Federated）通过 Service 标签按需切换，证明多集群联邦不需要「选择一种模式」，而是可以混合部署。这对 Master 设计多区域 GPU 调度有直接参考——不同 AI 推理服务可以根据延迟敏感度选择不同的跨集群策略。

2. **AI 推理基础设施的关注焦点从「Token 吞吐」转向「任务编排」** - Agentic AI 让推理变成分布式系统问题，GPU 不再是唯一关键路径，CPU 侧的编排、检索、沙箱、工具调用成为新的性能瓶颈。这意味着 K8s 调度器需要从「GPU 资源分配器」进化为「任务图调度器」，同时管理 CPU 和 GPU 资源。

3. **可观测性正在成为 AI 工作负载调度的数据基座** - OpenTelemetry 毕业 + GitLab 碳排放可观测，都指向同一个趋势：调度决策需要更丰富的遥测数据。从 GPU 利用率到推理延迟到碳排放强度，调度器的输入信号正在从单一资源指标扩展到多维可观测体系。Master 可以考虑在调度器中引入 OpenTelemetry 语义约定来标准化这些信号。
