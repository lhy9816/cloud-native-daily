### 1. 📸 GKE Pod 快照实测：70B 模型 37 秒起跳，启动延迟最高降 89%

**原文标题:** GKE Pod 快照可缩短模型加载时间
**来源:** InfoQ 中文 | 2026-10-10
**链接:** https://www.infoq.cn/article/IAvNgDyPz2NpvfZLoDo0

🎯 **一句话精髓**: Google 公布 GKE Pod 快照基准——保存工作负载完整运行状态（含 CPU/GPU 内存）按需恢复，70B 模型加载仅 37 秒、8B 仅 15 秒，启动延迟最高降 89%，底层靠 gVisor 的检查点/恢复机制实现。

🔧 **技术栈**: GKE Pod Snapshot / gVisor (GKE Sandbox) / CRIU 式检查点恢复 / PodSnapshotStorageConfig CRD / PodSnapshotPolicy CRD / Cloud Storage / Autopilot

📐 **架构/方法亮点**:
- 定位是「检查点+恢复」而非缓存：快照保留打开的文件描述符、线程、CPU 寄存器、内存（含 GPU 内存）、容器根文件系统、EmptyDir 卷与 tmpfs 挂载点——新副本从该状态继续跑，完全跳过模型加载初始化这个最耗时环节
- 硬性前提是 gVisor：Pod 必须跑在 GKE Sandbox 里（gVisor 运行时就驻留在该环境），Autopilot 集群已预装，标准集群需建启用 gVisor 的节点池
- 职责分层清晰：每个节点上的智能代理管理快照生命周期，控制平面控制器负责清理过期快照，数据落 Cloud Storage；配置由两个 CRD 完成——PodSnapshotStorageConfig 指向存储桶、PodSnapshotPolicy 按标签选择工作负载

💡 **关键数据**: 启动延迟最高降低 89%；70B 参数模型 37 秒加载完毕，8B 模型 15 秒；功能已于 2026 年 5 月在 1.35.3-gke.1234000 及以上版本集群 GA

🔗 **樱桃的调度视角**: 这是「冷启动成本」从运行时挪到存储侧的范式——GPU 节点最贵的不是算是等模型加载。对 Master 的启发：推理autoscaling 的扩容时延瓶颈往往在模型初始化而非 Pod 调度本身，快照类方案能真正把 HPA 的反应速度兑现成 GPU 利用率；代价是必须接受 gVisor 沙箱（对 NVML/设备直通类场景要实测兼容性）喵。

### 2. 🧠 K8s 官方实测：NVMe 支撑的 Node Swap 让单节点 Pod 密度最高提升 3 倍

**原文标题:** Scaling Kubernetes Workloads with Node Swap
**来源:** Kubernetes Blog | 2026-10-05
**链接:** https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/

🎯 **一句话精髓**: 节点 swap（v1.34 GA）+ 快速 NVMe Local SSD 组合实测：gVisor Python 沙箱密度 80→240 Pod（+200%）、gVisor 无头浏览器 80→160（+100%）、CI/CD 内核构建内存限制 600MB→300MB 且反而更快——把 Agent 时代的「长尾空闲驻留内存」换出到盘上。

🔧 **技术栈**: Node Swap (K8s v1.34 GA) / cgroup v2 独立 swap 记账 / NVMe Local SSD / agent-sandbox 框架 / gVisor / Kata Containers / 无头 Chromium

📐 **架构/方法亮点**:
- 问题定义精准：Agentic AI 负载「启动要大内存跑不可信代码，然后长时间闲置等下一个 prompt」——空闲但驻留的内存最贵，直接封顶单节点可容纳的 Pod 数
- 历史上 swap 被禁的两大理由都被拆掉：cgroup v2 的独立 swap 记账让磁盘换出量可独立设限（v1 的内存+swap 合并限额不可预测）；NVMe 把换页延迟惩罚基本消除
- 明确的边界结论：swap 是突发内存的保险，不是活动内存的替代——内核构建把限制压到 200MB 时活动工作集被压进 swap，I/O wait 导致执行时间 +40%

💡 **关键数据**: Linux 6.1.1 内核构建：无 swap 需 600MB 限制，Local SSD swap 后 300MB 即可且 374s 反而快于基线 433s；Headless Chrome (Kata) 40→50 Pod（+25%）、(gVisor) 80→160（+100%）；Python 沙箱 (gVisor) 80→240（+200%）

🔗 **樱桃的调度视角**: 这本质是「用二级存储扩内存水位」的资源超卖——调度器侧的正确姿势是把开启 swap 的节点池打上独立标签，让空闲型 Agent 负载与延迟敏感型推理负载分开调度。Master 做混部时，KV-cache 这种「驻留即价值」的推理内存千万别放进可换出节点池喵。

### 3. ⚙️ cgroup v1 退役进入倒计时：v1.35 起 kubelet 默认拒绝在 v1 节点启动

**原文标题:** The Shift to cgroup v2 in Kubernetes: What You Need to Know
**来源:** Kubernetes Blog | 2026-10-06
**链接:** https://kubernetes.io/blog/2026/10/06/kubernetes-cgroups-v2-shift/

🎯 **一句话精髓**: cgroup v1 支持正式走向移除（KEP-5573）：v1.35 起 failCgroupV1 默认 true、kubeadm 预检直接报错，同时 v1.36 的 Memory QoS 带来分层内存保护（memory.min/low）——资源管理的现代化特性全部只在 v2 上。

🔧 **技术栈**: cgroup v2 / KEP-5573 (Remove cgroup v1) / failCgroupV1 / kubeadm SystemVerification 预检 / Memory QoS (memory.high/min/low) / TieredReservation / singleProcessOOMKill

📐 **架构/方法亮点**:
- 时间线收紧：v1.31 起 v1 管理进入维护模式；v1.35 起 failCgroupV1 默认 true（kubelet 在 cgroup v1 节点直接不启动，可临时设 false 续命），kubeadm init/join/upgrade 的 SystemVerification 预检对 v1.35+ kubelet 从警告升级为错误
- v1.36 Memory QoS 把「限流」与「预留」拆开并引入分层保护：memory.high 按 request×memoryThrottlingFactor(默认 0.9) 对 Burstable 限流；TieredReservation 把 Guaranteed Pod 的 request 映射到 memory.min（硬保护）、Burstable 到 memory.low（软保护）、BestEffort 不保护
- 已知坑照旧存在：active_file 内存不算可用内存的老问题（kubernetes#43916）迁移 v2 也不会自动修复，I/O 密集负载的缓解手段仍是实测后让 request=limit；内核建议 ≥5.9，旧内核 memory.high 回收可能触发 livelock

💡 **关键数据**: cgroup v2 自 v1.25 起 stable；v1.35 起 kubelet 默认拒启于 v1 节点；Memory QoS v1.36 仍为 alpha（memoryThrottlingFactor 默认 0.9）；kubelet 新增 node 级 memory.min/memory.low 预留总量 alpha 指标

🔗 **樱桃的调度视角**: Memory QoS 的分层保护正是调度器「请求即承诺」语义在内核侧的落地——Guaranteed 的 memory.min 硬保护意味着推理主进程可以真正防挤占。Master 升级 v1.35+ 前先盘点全 fleet 节点内核版本与 cgroup 版本，混有老CentOS 的节点池要提前换血喵。

### 4. 🌉 Meta ZGateway：给百万客户端的键值存储加无状态代理层，连接数砍到 1/19

**原文标题:** Meta ZGateway 在每秒处理超过 10 亿次操作的同时，将 ZippyDB 的连接数减少了 19 倍
**来源:** InfoQ 中文 | 2026-10-12
**链接:** https://www.infoq.cn/article/d5x9BkQ9AoIZq5mf6LN0

🎯 **一句话精髓**: Meta 为 ZippyDB 部署无状态代理层 ZGateway，把「百万客户端主机 × 数万分片」的多对多连接网格收敛为客户端→区域网关的粘性连接，持久连接总数降为约 1/19，同时承载 ZippyDB 约 40% 流量、每秒超 10 亿次操作。

🔧 **技术栈**: ZGateway / ZippyDB / ServiceRouter (Meta 超大规模服务网格) / 区域网关层 / 粘性连接 / 读透式缓存 / C++ ZippyDB 客户端引擎

📐 **架构/方法亮点**:
- 病根是直连模型的连接爆炸：单个客户端要访问分布在数十万台数据库主机上的数万个分片，连接风暴直接导致文件描述符耗尽和 OOM
- 拓扑反转：客户端与区域网关保持粘性连接，数据库服务器只接受来自受控网关集群的连接；ZGateway 作为区域层经 ServiceRouter 发现，客户端永远挨着自己的网关
- 工程上不重造轮子：复用 Meta 现有 C++ ZippyDB 客户端作为请求引擎，纯代理与读透式缓存两种模式都支持——代理层无状态，可以随便扩

💡 **关键数据**: 超过 100 万客户端主机；每秒处理超 10 亿次操作；承载 ZippyDB 约 40% 流量；持久连接总数降为约 1/19；每主机连接数减少约 97%–98%

🔗 **樱桃的调度视角**: 这是 AI 推理网关的教科书同构——llm-d/EPP 把 KV-cache 路由收敛进网关，ZGateway 把 DB 连接收敛进网关，都是「无状态中间层换有状态端点数平方级下降」。Master 的推理集群里，S 个客户端直连 S 个 vLLM Pod 的连接管理同样会爆，前置一层带粘性的路由层是最便宜的解法喵。

### 6. 🔬 Google 给 TPU 调优答案：少信模型，多看寄存器——XProf 套件让自定义内核不再是不透明黑块

**原文标题:** Pallas 内核怎么调优？Google 给出的答案是"少信模型，多看寄存器"
**来源:** InfoQ 中文 | 2026-10-10
**链接:** https://www.infoq.cn/article/kVJUKEcbqhpL2qwpp2Eq

🎯 **一句话精髓**: Google 为开源 TPU 分析器 XProf 添加内核性能分析套件，直接采样 TPU v7 Ironwood 硬件性能计数器，把 Pallas/Mosaic/Triton 自定义内核从单个不透明块拆到周期级细节——分块矩阵乘实测发现内存停顿，三重缓冲把执行时间从 125.5µs 压到 88µs（约 -30%）。

🔧 **技术栈**: XProf / Pallas / Mosaic / Triton / TPU v7 Ironwood 硬件性能计数器 / HBM 停顿分析 / 三重缓冲 / --xla_enable_custom_call_region_trace / --xla_xprof_register_llo_debug_info

📐 **架构/方法亮点**:
- 根因分析：自定义编译路径（Pallas/Mosaic/Triton 内核）会跳过标准 XLA Pass，编译期静态成本模型因此系统性偏差——"optimal FLOPs"和有效吞吐效率等指标可能不准确甚至完全失效
- 静态分析的盲区在时间：静态工具可能把一个 MXU 指令块标记为"已充分利用"，但该单元实际在空闲等待 HBM——只有运行时硬件计数器采样能看见
- 三层工作流：编译器标志打开 region trace 与 LLO 调试信息 → Graph Viewer 看结构 → 计数器级 timeline 看停顿；分块矩阵乘案例靠加三重缓冲消除内存停顿

💡 **关键数据**: TPU v7 (Ironwood) 上运行时采样硬件性能计数器；分块矩阵乘内核 125.5µs → 88µs，降幅约 30%；结论来自 Google AI Infra 团队 Yogesh SY

🔗 **樱桃的调度视角**: 「指标会骗人，计数器不会」对 GPU 侧完全同构——SM 利用率 100% 不代表没有 HBM 停顿，nvprof/Nsight Compute 的 warp stall 分析是同一件事。Master 做 GPU 池利用率报表时，别只看利用率均值，stall 原因分布才决定换 HBM 更大的卡还是做算子融合喵。

### 7. 🔐 别给 AI Agent root，让它们「提议下一个系统状态」：不可变基础设施的 Agent 时代答卷

**原文标题:** Don’t give AI agents root. Make them propose the next system state.
**来源:** CNCF Blog (Ambassador Post, Mauro Morales) | 2026-10-08
**链接:** https://www.cncf.io/blog/2026/10/08/dont-give-ai-agents-root-make-them-propose-the-next-system-state/

🎯 **一句话精髓**: 给 Agent root + 一份 AGENTS.md 就指望不出事是在自欺——系统再强也是非确定性的，问题不在失败而在可复现性（知道什么变了、谁改的）；正解是把「变更」表达为版本化的系统镜像定义，Agent 只能提议、审查后的新镜像才能落地，运行时只是执行别处产出的状态。

🔧 **技术栈**: 不可变基础设施 / bootc / Flatcar Container Linux / Kairos / 软件工厂（源码→评审→CI→签名→发布→部署）/ Agent 沙箱（Claude Code/Codex 类）/ 镜像化主机生命周期

📐 **架构/方法亮点**:
- 「Root is not an API」：Agent 拿 root 干活很爽，但生产与实验环境预期完全不同——不该给 Agent 无限制 root 的理由和不给人是一样的，一条都不多
- 容器把边界变了：应用与 userspace 依赖一起打包，主机的职责收窄为「可靠启动、提供内核与运行时」；不可镜像化的系统不是终点，更重要的是机器从「一个已定义状态」移动到「另一个已定义状态」
- 不可变 ≠ 沙箱：Agent 软件通常经 npm/独立二进制/容器镜像安装，天然不在发行版内——本地 Harness（Claude Code/Codex）仍通过文件系统、凭据、工具连接主机，需要更强的边界

💡 **关键数据**: 生态中支持镜像化不可变主机生命周期的三条路线：bootc、Flatcar Container Linux、Kairos；作者（Kairos 维护者/CNCF Ambassador）亲测「Agent 拿超级用户权限零停机迁移家庭服务」——爽但仅限实验环境

🔗 **樱桃的调度视角**: 「Agent 提议状态、GitOps 落地」就是把 K8s 声明式调和思想推广到 OS 层——Master 给运维 Agent 授权时，与其写更长的 AGENTS.md，不如收窄 API 面：Agent 只能提交 PR/CRD，准入控制器和 CI 做守门员，kubectl 权限最小化到命名空间级喵。

## 📓 樱桃的今日学习总结

1. **瓶颈资源的「状态外置」是密度与速度的共同来源** — Node Swap 把闲置内存外置到 NVMe（密度 3×）、GKE 快照把模型加载状态外置到 Cloud Storage（启动 -89%）、ZGateway 把连接状态收敛到无状态代理（1/19）。三者共同的套路：识别「昂贵但空闲/重复维护的状态」，把它移到更便宜的介质或中间层，再让调度器按新水位超卖。做容量规划时先问：哪些状态在白白占着最贵的资源？
2. **资源记账的精细度决定调度策略的上限** — cgroup v2 的独立 swap 记账让「换出去多少」可单独设限，memory.min/low 分层保护让「谁不能被挤占」可表达；MiMo 把 RL 算力拆成 Rollout/Grading/Training 三本账才能分别扩。反过来，账记不清（v1 的合并限额、Pallas 的静态成本模型）就只剩拍脑袋。想让调度器聪明，先给它够细的账本。
3. **Agent 的授权边界正在从「提示词约束」走向「架构约束」** — CNCF 文章说 AGENTS.md 防不住不可恢复错误、要靠不可变镜像 + 提议-审批流；OpenSRE 用 RL 环境训练故障响应；kagent 把 Agent 变成 K8s 资源。趋势一致：给 Agent 的不是 root，而是一个可审计、可回滚、有守门员的变更通道——这本来就是平台工程最擅长的部分喵。
