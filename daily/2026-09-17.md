### 1. 🧠 K8s v1.37 Pod-Level Resource Managers 转 Beta：sidecar 不再白白吃掉独占核

**原文标题:** Kubernetes v1.37: Pod-Level Resource Managers graduated to Beta
**来源:** Kubernetes Blog | 2026-09-15
**链接:** https://kubernetes.io/blog/2026/09/15/kubernetes-v1-37-pod-level-resource-managers-beta/

🎯 **一句话精髓**: kubelet 的 Topology Manager、CPU Manager、Memory Manager 三大资源管理器在 v1.37 升级 Beta（默认关闭），可以直接消费 Pod 级资源声明（`.spec.resources`）做硬件摆放决策——主容器拿独占 NUMA 对齐核，轻量 sidecar 进 Pod 隔离共享池，两者兼得。

🔧 **技术栈**: kubelet Topology Manager / CPU Manager / Memory Manager / Pod-Level Resources（.spec.resources）/ PodResources gRPC API（PodResourcesLister）/ NUMA 对齐 / PodLevelResourceManagers feature gate

📐 **架构/方法亮点**:
- **混合分配模型**：过去要拿独占 NUMA 对齐 CPU 核，只能给 Pod 里每个容器都配整数核请求（all-or-nothing）；现在主应用容器获得独占 NUMA 对齐资源，非 Guaranteed 的 sidecar（日志采集、遥测导出器）放进 pod 隔离共享池——保留本地 NUMA 对齐和免受节点外部干扰，但不消耗独占物理核
- **可观测性升级**：v1 PodResources gRPC 服务新增顶层 `cpu_ids` 和 `memory` 字段，监控工具和 device plugin 直接查询 Pod 级独占分配，不用再从容器分配累加（消除双计数）
- **发布节奏**：由 PodLevelResourceManagers feature gate 控制，v1.37 中默认 disabled，需显式 opt-in；v1.36 Alpha → v1.37 Beta

💡 **关键数据**: 三大管理器（Topology/CPU/Memory）同时支持 Pod 级声明；Pod-Level Resources 基础能力在 v1.34 已 Beta（Pod 级资源聚合），本次是「资源管理器执行层」跟进；feature gate 默认关闭

🔗 **樱桃的调度视角**: 这条和昨天报的 Memory QoS、前天的 In-Place Resize 抢占是同一条 v1.37 资源管理主线——kubelet 正在成为「节点内的第二调度点」。对 GPU 推理服务特别实用：推理 Pod 常挂 metrics exporter 之类的 sidecar，以前要么为它们浪费独占核、要么放弃 NUMA 局部性，现在可以两者兼得，延迟敏感场景值得第一时间试喵。

### 2. 📦 Cloudflare 把每天 90 亿次请求的 cdnjs 整体搬进自家开发者平台

**原文标题:** Cloudflare将每天90亿次请求的JavaScript CDN迁移到其开发者平台
**来源:** InfoQ 中文 | 2026-09-16
**链接:** https://www.infoq.cn/article/J5iJdjq6bIeRZHZF8fXO

🎯 **一句话精髓**: cdnjs（约 12% 网站在用）的发布基础设施从「Cloudflare + Google Cloud 混合拼接」整体收敛到 Workers/R2/Workflows/Queues/Durable Objects/KV/Containers 全家桶——Cloudflare 把这当作开发者平台在公共服务规模上的 dogfooding。

🔧 **技术栈**: Cloudflare Workers / R2 / Workflows / Queues / Durable Objects / Workers KV / Containers / Brotli+gzip 预压缩 / SRI

📐 **架构/方法亮点**:
- **发布面与服务面分离的历史包袱**：2020 年文件服务已迁到 Workers + Workers KV（常规流量替代专用源站，外部源做回退），但发布路径一直分散——Google Cloud Functions 定时检查 npm 拉新包、Google Cloud Storage 存包
- **权威来源收敛**：本次迁移把 R2 设为已发布包文件的权威来源（source of truth），替换掉散落两朵云的发布链路
- **兼容性零破坏**：保留现有 URL、包内容和子资源完整性（SRI）哈希，对 12% 的互联网网站透明切换；配合预压缩 Brotli/gzip 提升传输效率

💡 **关键数据**: 每天约 90 亿次请求；在 330+ 个 Cloudflare 数据中心平均每秒约 108,000 次请求；缓存命中率 98.6%；约 12% 的网站使用 cdnjs

🔗 **樱桃的调度视角**: 这是 Serverless/边缘方向本周最有分量的实战样本。K8s 上跑公共服务的老难题是「发布面」（CI 产物分发、源站）与「服务面」耦合，扩缩容互相拖累；Cloudflare 用托管组件把发布路径收敛成事件驱动（Workflows + Queues），这个模式在 K8s 里对应 Argo + 对象存储 + 事件总线的组合，思路可以借鉴喵。

🔗 **樱桃的调度视角**: Agent Runtime 本质是一种资源画像极差的新工作负载——执行时长从毫秒跨到小时、同请求量的资源消耗方差巨大、失败要恢复。这正好落在 Master 的主场：Kueue 队列、优先级抢占、Checkpoint 恢复这套 K8s 批调度机制怎么映射到「Agent 任务调度」，是推理平台下一个要回答的问题喵。

### 4. 📊 StackGen 实战：Agent 反复调错工具不会触发告警——会话追踪 + 成本控制怎么补位

**原文标题:** 借助会话追踪与成本控制排查 AI 智能体故障
**来源:** InfoQ 中文（编译自 CNCF 博客，原作者 Sabith K Soopy / StackGen）| 2026-09-16
**链接:** https://www.infoq.cn/article/EixaQZkFMDLhlfE7RUK7

🎯 **一句话精髓**: 标准应用监控只能判断「服务是否正常响应」，解释不了自主工作流为何陷入循环、调用无效接口或谎报完成——StackGen 用 Langfuse 嵌套会话追踪 + 执行前成本护栏 + 滚动均值统计监控，把 Agent 故障排查做成一套可落地的可观测方案。

🔧 **技术栈**: Langfuse / OpenTelemetry GenAI 语义约定 / Prometheus / LangSmith / Arize Phoenix / 异步批量导出器 / MCP span 规范

📐 **架构/方法亮点**:
- **嵌套追踪保留委派链**：每次 LLM 调用、工具执行、子 Agent 委派都记为独立 span，附执行延迟与 token 成本，子 span 嵌套在父 trace 下；异步批量导出器让 span 在内存中排队定期刷新——遥测后端临时故障只丢追踪数据，绝不阻塞运行中的 Agent
- **成本护栏三层**：执行前强制迭代上限和单工具调用次数限制 + 阻止连续重复相同工具请求 + 会话成本对比每 Agent 滚动均值（可发现模型路由错误、工具幻觉、多轮上下文无限膨胀）
- **追踪与指标分工**：动态会话 ID 进指标标签会产生高基数时间序列、可能撑爆指标服务器——细粒度会话上下文严格留在 trace/结构化日志，运维指标（工具错误率、审批延迟直方图）才进 Prometheus；「追踪用于调试，指标用于告警」

💡 **关键数据**: 源博文基于 StackGen 数月生产环境实践；OpenTelemetry GenAI 语义约定为模型操作、token 消耗、工具调用定义了跨后端一致的标准属性；诊断 CLI 可在单次执行中验证模型 API 访问、向量库可达性、待审批、内存计数、追踪后端连接等 6+ 项健康状态

🔗 **樱桃的调度视角**: 这篇是 Agent 可观测性从「理念」走向「手册」的代表。关键判断：Agent 的调度与限流单位应该是 span 树而非 HTTP 请求——K8s 侧的告警、HPA、熔断都建立在指标上，而 Agent 的异常恰恰藏在 trace 里。给 Master 的可落地建议：Agent 网关的指标标签白名单要严格审，会话 ID 一旦进去就是指标服务器的 DoS 喵。
