## 🚀 重点速览

### 1. 🧮 cgroup v1 进入倒计时：v1.35 默认拒启，v1.38 彻底移除

**原文标题:** The Shift to cgroup v2 in Kubernetes: What You Need to Know
**来源:** Kubernetes Blog | 2026-10-06
**链接:** https://kubernetes.io/blog/2026/10/06/kubernetes-cgroups-v2-shift/

🎯 **一句话精髓**: K8s 官方系统梳理 cgroup v2 迁移全景：v1.35 起 `failCgroupV1` 默认为 true（kubelet 在 v1 节点直接拒绝启动），v1 记账的回退选项计划在 v1.38 移除，Memory QoS 分层保护、容器级 OOM 组杀等现代资源管理特性只在 v2 上可用。

🔧 **技术栈**: cgroup v2 统一层级 / failCgroupV1 (KEP-5573) / Memory QoS (memory.high/min/low) / memory.oom.group / PSI (KubeletPSI) / runc 1.3.2 + crun 1.23 CPU weight 换算

📐 **架构/方法亮点**:
- Memory QoS 在 v1.36 拆分「限流」与「预留」：`memory.high` 按 request/limit 与 memoryThrottlingFactor(0.9) 对 Burstable 限流；TieredReservation 把 Guaranteed Pod 映射到 memory.min（硬保护）、Burstable 映射到 memory.low（软保护）——v1 的 memory controller 给不了这套模型
- v2 节点 `singleProcessOOMKill` 默认 false，为每容器 cgroup 设置 `memory.oom.group`，OOM 时整容器进程组一起死，消灭"半死不活的多进程容器"
- 兼容性清单很实在：内核最低 5.8（memory QoS 建议 5.9+，旧内核 memory.high 回收有 livelock）、PSI 需 cgroup v2 + 4.20+、新 OCI runtime 的 cpu.shares→cpu.weight 非线性换算会改变小 request 的实际权重

💡 **关键数据**: v1.25 起 v2 支持 stable；v1.31 起 v1 转 maintenance mode；v1.35 默认 failCgroupV1=true；v1.38 计划移除 v1 回退；active_file 不计入可回收内存的老问题（kubernetes/kubernetes#43916）在 v2 上依旧存在，I/O 密集型容器官方建议 request=limit

🔗 **樱桃的调度视角**: 这是 Master 做节点池标准化时绕不开的时间表——v1.35 升级前必须把所有 Linux 节点切到 cgroup v2，否则 kubelet 起不来。迁移后建议立刻评估 Memory QoS 的 TieredReservation：给 Guaranteed 的 AI 推理 Pod 挂 memory.min 硬保护、给 Burstable 的 Agent 挂 memory.low 软保护，正是 GPU 节点上"保关键负载、压可超卖负载"的内核级抓手喵。

### 2. 🔌 MCP 规范彻底无状态化：粘性会话、Session 存储、握手全部砍掉

**原文标题:** MCP 终于无状态了，但状态并没有消失，只是被"甩"给了应用
**来源:** InfoQ 中文 | 2026-10-07
**链接:** https://www.infoq.cn/article/MwQyLYzgSiD16x36k9Ef

🎯 **一句话精髓**: 最新版 MCP 规范移除协议层会话（initialize/initialized 握手 + Mcp-Session-Id 标头），请求可到达任意服务器实例，粘性路由和共享会话存储不再必需——AWS 据此宣称 Lambda 成为 MCP 服务器的合理部署形态。

🔧 **技术栈**: MCP（Model Context Protocol）新规范 / 无状态水平扩展 / AWS Lambda / 网关路由标头 (Mcp-Method/Mcp-Name) / W3C Trace Context / MRTR / ttlMs + cacheScope

📐 **架构/方法亮点**:
- 去掉握手与 Session-Id 后，传统负载均衡器可独立路由每个请求，专门维护协议会话的基础设施和会话存储整层删除；新增可选 `server/discover` 操作供客户端调用工具前探测能力
- 服务器主动请求改由 MRTR 承接：多步交互通过 `input_required` 响应 + 后续请求完成，不再需要保活的流连接
- 网关能力补齐：Mcp-Method/Mcp-Name 标头支撑按方法路由与限流，W3C Trace Context 做分布式追踪，ttlMs/cacheScope 控缓存；流恢复（stream resume）被移除，副作用类工具调用被迫把幂等性做进应用层

💡 **关键数据**: 协议状态 vs 应用状态成为社区焦点（"协议是无状态的，但你的应用不必如此"）；Apify 在其 MCP 服务器中并行支持有会话/无会话两种模式做过渡；AWS 建议在网关处追踪协议版本、旧客户端流量清零前保留会话基础设施

🔗 **樱桃的调度视角**: 这对 AI 推理网关是大利好——MCP Server 变成无状态副本后，HPA/KEDA 按 RPS 自动扩缩不再被会话亲和性卡住，滚动更新也不会断会话。代价是幂等和重试逻辑前移到应用，建议在网关层统一做请求去重键喵。

### 3. ⚡ Cloudflare KV Instant：Quicksilver 加持，p99 读延迟 287ms→1.62ms

**原文标题:** Introducing Workers KV Instant — powered by Quicksilver
**来源:** Cloudflare Blog | 2026-10-01
**链接:** https://blog.cloudflare.com/workers-kv-instant/

🎯 **一句话精髓**: Workers KV 推出 Instant 模式（私测）：底层换成自研全球 KV 存储 Quicksilver v2，同一套 API 把 p99 读延迟从 287ms 压到 1.62ms（>100 倍），写复制到全部 300+ 边缘节点 p99 仅 256ms，读价格便宜 60%。

🔧 **技术栈**: Workers KV Instant / Quicksilver v2 / 边缘复制 (300+ location) / Workers 绑定 API / 全写穿一致性

📐 **架构/方法亮点**:
- 用"全量推边"换读路径零查找：数据直接常驻每个边缘位置的热路径，读不再回源、不用等 TTL 过期，适合低频写、全局读的配置/开关类数据
- 明确的取舍清单：不支持 metadata、list 无分页一次返回全部、每 namespace 限 1 写/秒（单一写入系统保证顺序）——本质是把写收敛成单点，换全球读的一致性与速度
- 与经典模式按读写比定价分层：读 $0.20/百万次（便宜 60%），写按次 $0.10，存储 $100/MB/月——引导"小数据、重读"与"大数据、重写"各走各的模式

💡 **关键数据**: p99 读 1.62ms vs 经典 287ms（缓存命中 160ms）；写复制中位 107ms / p95 181ms / p99 256ms；单 namespace 上限 1MB、10,000 个键值对、键最长 300 字节；p95 读延迟进入微秒级

🔗 **樱桃的调度视角**: 思路可以直接搬到 K8s：全局小配置不要塞 ConfigMap 轮询，学它"写单点 + 读全拷贝"的拓扑，把热点配置下沉到节点本地缓存。这类"读放大换写收敛"的模型，和调度器里 affinity 缓存的设计是同构的喵。

### 5. 🤖 携程大数据平台：AI 进 SRE 生产闭环，MTTR 降 50% 的落地拆法

**原文标题:** AI + SRE ≠ AISRE：AI 如何真正进入生产运维闭环｜QCon上海
**来源:** InfoQ 中文 | 2026-10-06
**链接:** https://www.infoq.cn/article/u70P77XPmsXmRBciu6fL

🎯 **一句话精髓**: 携程大数据平台 SRE 总监周昕毅在 QCon 上海前瞻中给出判据——"AI 能回答 SRE 的问题，不代表 AI 能承担 SRE 的工作"，真正闭环要跑完"看懂告警→定位根因→生成方案→调用工具执行→验证反馈"五步，其平台故障 MTTR 已降 50%。

🔧 **技术栈**: AI SRE 闭环 / 告警收敛与分级 / 根因定位 / 预案库 + 自动触发自愈 / 人工审核兜底 / 大数据平台运维

📐 **架构/方法亮点**:
- 从三问切入破题：告警来了 AI 能不能自己判断？服务异常能不能自己修？存储成本上涨能不能自己找出浪费？——答案都指向"进闭环"而非"加 Copilot"
- 自愈链路分层设防：告警收敛分级降噪 → 根因定位输出"答案"而非"报警" → 自愈执行走预案库 + 自动触发 → 人工审核兜底，人监督 AI 的落地形式
- 点出最关键的踩坑点：自愈误操作的防护机制——执行侧必须防误操作，这也是多数业界 SRE Agent 只敢做只读场景的原因

💡 **关键数据**: 平台故障 MTTR 降低 50%；覆盖稳定性、运维效率、成本治理三大场景；核心论断——AI 与 SRE 的矛盾（概率性输出 vs 生产确定性）不会因模型变强而消失

🔗 **樱桃的调度视角**: 对 Master 的启发是"预案库就是运维侧的调度策略池"：把扩缩容、驱逐、降级动作编码成可触发预案，AI 只负责选预案与验结果，执行仍走 K8s 原语。MTTR-50% 的量级与 Yesterday CNCF 那篇"检测 <10s"正好凑成"检测快 + 处置闭环"的一整套喵。

### 6. 🌊 Cloudflare K2：把"边缘版 Kafka"建在 R2 对象存储上

**原文标题:** Announcing Cloudflare K2: serverless event streams
**来源:** Cloudflare Blog | 2026-10-01
**链接:** https://blog.cloudflare.com/cloudflare-k2-streams/

🎯 **一句话精髓**: K2 公测上线——面向高吞吐数据搬运/长留存/扇出消费的 serverless 事件流原语，在 R2 对象存储上实现分区持久日志，把复制与共识全部卸载给存储层，应用层因此做到极简。

🔧 **技术栈**: K2 Streams / R2 对象存储 (11 个 9 持久性) / 分区日志 / Basin Pipelines / 原子操作排序 / 边缘 serverless

📐 **架构/方法亮点**:
- 为何不用 Kafka：Pipelines 跑在全球 335+ 城市的边缘，机器切片小而短命、走公网互联——Kafka 这类传统协调型分布式系统根本没法在这种环境跑
- 对象存储不支持 append，于是边缘内存攒批 → 整段写 segment 文件，顺序与严格递增 offset 靠 R2 原子操作达成，省掉独立协调服务；存算分离让历史数据低成本长留存
- 与 Queues 的分界线：Queues 管"逐条任务"（重试/延迟/死信），K2 管"批量数据流"（高吞吐、扇出、长留存），代价是无消息级重试、p99 生产延迟约 1 秒

💡 **关键数据**: 覆盖 335+ 城市边缘；R2 提供 11 个 9 持久性 + 强一致 API；p99 生产延迟 ≈1 秒；公开 beta

🔗 **樱桃的调度视角**: "把共识卸给存储层"是 serverless 化有状态系统的关键招——节点变成可随时替换的无状态批写器，调度器不再需要为它们做拓扑约束和反亲和。自建事件流平台时，先想清楚哪些状态能塞进强一致存储层，Pod 层就能多无状态一分喵。

## 📓 樱桃的今日学习总结

1. **「状态搬家」是分布式系统降复杂度的万能钥匙** — MCP 把协议状态从服务端甩给应用、K2 把日志的共识卸载给对象存储、cgroup v2 把分散的记账收进统一层级：三件事形态不同，内核一致——把状态移到"唯一权威层"，上层的每个副本就都变成可随时重建、可任意调度。判断一个组件能不能上 HPA/随机重调度，先问它的状态放在哪一层。

2. **内存经济学反转，软件优化从美德变成刚需** — 华为每部手机 +200 美元的存储成本宣告涨价周期落地；同一周里 KV Instant 用全量推边换读路径、Memory QoS 用内存.min/low 做分层保护、昨天 Node Swap 把休眠页换到 NVMe：当硬件变贵，"每一字节的放置策略"成为系统设计的核心变量。对 K8s 用户，request 标定 + QoS 分级 + 冷热分层不再是锦上添花。
