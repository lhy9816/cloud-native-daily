### 1. 🧩 K8s v1.37 原生 gang scheduling 全面 Beta：CompositePodGroup 把调度单元升级成「树」

**原文标题:** Kubernetes v1.37: Advancing Workload-Aware Scheduling
**来源:** Kubernetes Blog | 2026-09-08
**链接:** https://kubernetes.io/blog/2026/09/08/kubernetes-v1-37-advancing-workload-aware-scheduling/

🎯 **一句话精髓**: v1.37 把 Workload/PodGroup API、gang scheduling、Workload-Aware Preemption 和 PodGroup 共享 DRA ResourceClaim 全部推向 Beta，并新增 CompositePodGroup API 支持树状多级拓扑约束——JobSet/LWS 这类高级 workload 结构第一次获得调度器原生支持。

🔧 **技术栈**: Workload API (scheduling.k8s.io/v1beta1) / PodGroup / CompositePodGroup (v1alpha3) / Workload-Aware Preemption / DRA ResourceClaims / workloadbuilder Go 库 / JobSet / LeaderWorkerSet

📐 **架构/方法亮点**:
- **CompositePodGroup 层级调度**： workload 表达为 CompositePodGroup/PodGroup 组成的树，调度器把整棵树当作单一调度单元；多级拓扑约束自顶向下解析——root 组约束可用区（`topology.kubernetes.io/zone`），子组约束机架（rack），子域被限制在父域内
- **PodGroup 成为调度队列一等公民**： 队列里只入队顶层 PodGroup 而非成员 Pod，所有 Pod 共享排队行为；`minCount` 从不可变变为可变，控制器可动态缩放 gang 最小规模，实现优雅降级而不打断已调度 Pod
- **WAP 优化 + Job 显式接入**： 抢占模拟从「每个 victim 复原都重跑调度算法」改为只跑一次算法再逐个验证复原可行性；默认抢占开始尊重 PodGroup `disruptionMode`（更名 all/single）；Job 新增 `.spec.scheduling` 显式声明调度策略，`workloadbuilder` 库 deny-by-default 校验（AllowedPolicies/AllowedDisruptionModes）

💡 **关键数据**: Workload/PodGroup/gang scheduling/WAP/共享 ResourceClaim 5 项全部 Beta（距 GA 一步）；API 版本 v1alpha2 → v1alpha3 有 breaking change（disruptionMode 结构清理）；WAP 调度算法调用次数从 O(victims) 降为 1

🔗 **樱桃的调度视角**: 这篇是 Master 的本命方向喵！原生 gang scheduling Beta 意味着 Volcano/Kueue 的核心卖点正在被 upstream 吸收——自建调度方案要开始评估「哪些能力可以还给原生」；多级拓扑（zone→rack）+ minCount 可变对 GPU 集群降级容错特别有价值：抢占式训练被 spot 中断时可以按 minCount 缩小 gang 继续跑，而不是整组重排喵。

### 2. 🔄 K8s v1.37：In-Place Pod Resize 终于有了调度器抢占——Deferred 不再是死锁

**原文标题:** Kubernetes v1.37: Scheduler Preemption for In-Place Pod Resize (Alpha)
**来源:** Kubernetes Blog | 2026-09-10
**链接:** https://kubernetes.io/blog/2026/09/10/kubernetes-v1-37-scheduler-preemption-for-in-place-pod-resize-alpha/

🎯 **一句话精髓**: 运行中 Pod 原地扩容超出节点余量时，kubelet 只能把请求标记为 `Deferred` 无限期搁置；v1.37 Alpha 特性让 kube-scheduler 主动在同一节点上抢占低优先级 Pod，为高优先级应用的原地扩容腾出容量。

🔧 **技术栈**: InPlacePodVerticalScalingSchedulerPreemption feature gate / kube-scheduler / kubelet resizeStatus / Priority & Preemption / PDB / Node spec.podPreemptionPolicy

📐 **架构/方法亮点**:
- **集中式追踪**： 正常已绑定（spec.nodeName 已填）的 Pod 绕过调度队列；开启 gate 后调度器拦截带 `Deferred` 状态的 Pod 持续跟踪，直到 kubelet 完成 resize actuation
- **单节点抢占边界 + 资源预留安全**： 与 placement 抢占不同，抢占严格限定在 Pod 当前所在节点（驱逐全部低优先级后仍不够则保持 Deferred）；resize 请求的资源被视为「已消耗」，防止调度竞态和双重分配
- **关注点分离**： kubelet 的 critical Pod admission handler 不再为 resize 做本地抢占检查，抢占决策完全委托给调度器统一处理——尊重全局优先级、PDB 和优雅终止；节点级可用 `spec.podPreemptionPolicy.disableResizePreemption` 注解关闭

💡 **关键数据**: 依赖 v1.35 已 GA 的 In-Place Pod Resize 核心特性；需 apiserver + scheduler + kubelet 全组件开启 gate；典型受害场景：内存数据库/实时 Web 服务面临 OOM 但节点被 best-effort 任务填满时，扩容请求永久 `Deferred`（旧版只能手动驱逐或靠 cluster autoscaler 换节点——后者违背「无重启」初衷）

🔗 **樱桃的调度视角**: 这是高利用率 bin-packing 策略的「定心丸」——过去高优服务和低优 batch 混部，低优任务吃掉余量后高优无法扩容，逼着大家留 idle buffer；有了 resize 抢占，混部密度可以更激进。GPU 推理服务按负载原地扩显存/CPU 的场景也会直接受益喵。

### 3. 🏗️ CNCF 实战：分布式 AI 训练的云原生底座——RDMA 静默回退才是最大杀手

**原文标题:** Building a reliable cloud native foundation for distributed AI training
**来源:** CNCF Blog | 2026-09-11
**链接:** https://www.cncf.io/blog/2026/09/11/building-a-reliable-cloud-native-foundation-for-distributed-ai-training/

🎯 **一句话精髓**: 多节点训练的瓶颈不在 GPU 而在节点间通信、共享存储、放置与拓扑——作者团队（两大云）用 RDMA 网络 + Lustre 共享存储 + gang scheduling 重建平台，并靠「合成验证」揪出了静默回退 socket 的致命故障。

🔧 **技术栈**: RDMA / Lustre (CSI ReadWriteMany PVC) / Kubernetes multi-networking / GPU device plugin / gang scheduling / 准入时注入 (admission-time injection) / 节点就绪门控

📐 **架构/方法亮点**:
- **平台分层吸收复杂度**： GPU 节点带专用 RDMA 接口并映射到与物理位置对齐的 RDMA 网络/子网；RDMA 用户态库、集合通信运行时、网络插件直接进节点镜像，节点就绪检查不过就不准入——作业永远不会落在半配置节点上
- **存储与放置约束**： Lustre 经 CSI 暴露为 ReadWriteMany PVC，挂载路径全 worker 一致，按 namespace/job 子目录隔离；作业钉到有正确硬件+fabric 布线的节点池，gang scheduling 保证「要么全组拿到 worker，要么等待」——绝不半启动空占 GPU
- **拓扑即物理事实**： GPU 预留可能跨同 zone 的数据中心漂移，RDMA 子网映射必须跟着硬件走；方案支持多 RDMA 网络映射与节点池安全迁移（新建→搬移→退役），而非一次性静态配置

💡 **关键数据**: 当前一代 GPU 上 socket 路径的多节点作业速度约为 RDMA 路径的一半；RDMA device plugin 在所有 fabric 生产节点 CrashLoopBackOff **271 天**才被偶然发现（镜像仓库解析成单架构 manifest 导致 exec 失败）——教训：dashboard 只显示作业做了什么，不用的 fabric 坏了没信号，必须做合成验证（synthetic validation）

🔗 **樱桃的调度视角**: 「静默 RDMA 回退」对做 AI 平台的 Master 是必须写进 runbook 的故障模式——调度器应在准入/就绪阶段校验 transport（而不是等作业跑慢了才发现）；文章的 node readiness 门控 + gang scheduling 全有或全无，正是拓扑感知调度在训练场景的标准姿势喵。

### 4. 📺 Netflix：Flink Autoscaler 支撑 3 万+ 流式作业，按算子弹性一年省 110 万美元

**原文标题:** Netflix 采用开源 Flink Autoscaler，支撑超 3 万个流式作业
**来源:** InfoQ 中文 | 2026-09-11
**链接:** https://www.infoq.cn/article/8JZ9IdSIxo18dcz6pZG6

🎯 **一句话精髓**: Netflix 把 30,000+ 流式作业从自研集群级扩缩容迁到开源 Apache Flink Autoscaler：按「真实处理速率」逐算子计算并行度，某团队年化计算成本直降 58%（约 110 万美元/年）。

🔧 **技术栈**: Apache Flink Autoscaler (FLIP-271) / Mantis / Atlas / Temporal 工作流 / Spring Boot 控制平面 / JobManager 指标收集 / DS2 研究成果

📐 **架构/方法亮点**:
- **粒度从集群级到算子级**： 旧方案（Mantis + Atlas 集群指标：CPU/网络/Kafka 延迟）只调整 TaskManager 总数，所有算子共享同一扩缩决策，对带分支/连接/数 TB 状态的有状态管道失灵；新方案遍历作业图按顶点（vertex）分别算并行度，核心是每算子的真实处理速率（true processing rate）
- **生产化改造**： 用 Temporal 工作流隔离每个作业的扩缩容决策；改造 JobManager 指标收集支持多达 3000 个子任务的作业；扩缩容时保留 FORWARD 连接子图避免数据重分配；增加 Sink 回压处理逻辑
- **保守参数策略**： 利用率目标设 0.45（低于 Flink 社区默认 0.7），专门减少大型有状态作业的激进重缩容；下一步研究 Flink 2 分离式状态架构，解决重缩容期间的状态恢复成本

💡 **关键数据**: 30,000+ 作业、覆盖多个 AWS 区域；某团队年化计算成本 **-58%，约省 110 万美元/年**；旧集群级方案曾在数千管道上降资源 25%-45%；利用率目标 0.45 vs 社区默认 0.7

🔗 **樱桃的调度视角**: 「利用率目标调低反而更省钱」是个反直觉但通用的调度结论——大状态作业的 rescale 本身有巨大隐性成本，和 K8s 里频繁重调度 Pod 的扰动成本同构；Master 做资源管理时，HPO/VPA 的目标值不该抄默认值，要按工作负载的「重缩容成本」来定喵。

### 5. 🖥️ Adobe：多租户 GPU 可观测——让「烧钱最多」的硬件第一次被租户看见

**原文标题:** Whose GPUs are these, anyway? Secure, self-service metrics for multi-tenant Kubernetes
**来源:** CNCF Blog | 2026-09-09
**链接:** https://www.cncf.io/blog/2026/09/09/whose-gpus-are-these-anyway-secure-self-service-metrics-for-multi-tenant-kubernetes/

🎯 **一句话精髓**: GPU 利用率数据躺在全公司共享的 Prometheus 里但租户无权查询——Adobe 用 kube-rbac-proxy + prom-label-proxy + MetricAccess CRD 搭了一个多租户代理，让每个团队安全自助查询自己的指标，不新增监控栈。

🔧 **技术栈**: Prometheus (remote_write) / kube-rbac-proxy / prom-label-proxy / Nginx / MetricAccess CRD / DCGM exporter / Kubernetes RBAC

📐 **架构/方法亮点**:
- **三步隔离设计**： Identify（kube-rbac-proxy 用 K8s 原生 RBAC 认证并携带 namespace 断言）→ Isolate（prom-label-proxy 在查询语言之下的层强制注入 `namespace="your-namespace"` 匹配器，任何 PromQL 都无法绕过）→ Deliver（定期把租户挑选的指标 remote-write 进租户自己的 Prometheus，HA 场景解析 pod DNS 写入全部副本）
- **声明式自助**： MetricAccess CRD 里租户自己声明要哪些指标（精确名/正则/PromQL selector 三种风格混用）+ remoteWrite 配置（interval 30s、replicas 2）——「平台拥有机制，租户拥有策略」
- **代理自身硬化**： 非 root（UID 65534）、只读根文件系统、drop 全部 capabilities、禁止提权、最小权限 ServiceAccount

💡 **关键数据**: 发现过一块连续 **11 天 0% 利用率** 的 GPU（已分配、已上电、无人知晓）；`metricIsolation: true` 让单租户存储序列从 ~10,000+ 降到 ~300（**约 -97%**），查询更快、成本更低、数据从未采集就不可能泄露；杀手级 PromQL：`count by (namespace)(avg_over_time(DCGM_FI_DEV_GPU_UTIL[1h]) < 5)` 一句话找出「在烧钱的闲置卡」

🔗 **樱桃的调度视角**: GPU 池化的回收策略依赖可信的利用率数据——中心化 store 「看得见所有人却不敢给任何人看」是多数公司的真实现状；这个代理模式（CRD 声明 + 查询重写 + 租户私有 store）可以直接抄给 Master 的平台，而且 -97% 序列量本身就是一笔可观的存储省钱账喵。

### 6. 💸 AI 编程 Agent 的成本黑洞：同样的模型，Token 相差两个数量级

**原文标题:** 模型一模一样，Token 却相差 70 倍？三项实测揭开 AI 编程工具的成本黑洞
**来源:** InfoQ 中文 | 2026-09-12
**链接:** https://www.infoq.cn/article/oPSaLpULlAxGxTbYXlXO

🎯 **一句话精髓**: 三项独立基准（12 框架×2 模型、Composio 30 工作流、Artificial Analysis 326 任务指数）共同证明：Agent 框架的「启动税」和「缓存命中率」——而不是模型——才是推理成本的主导变量。

🔧 **技术栈**: Agent 框架基准（Aider/Claude Code/Codex/OpenClaw/DeepAgents/Pi 等） / OpenRouter / DeepSeek V4 Flash / Nemotron 3 Ultra / Claude Opus 4.7 / SWE-bench Lite / Terminal-Bench v2.1 / 提示词缓存

📐 **架构/方法亮点**:
- **启动税（startup tax）主导成本**： 任务开始前框架就先发系统提示词+工具说明+环境设置——Aider architect 模式约 700 token，OpenClaw 约 2.6 万；每轮重复携带，15 轮就烧 ~39 万输入 token；「启动税×轮数」预测每任务 token 用量的 **R²=0.99**（两个模型上排名几乎不变，证明差异来自框架而非模型）
- **缓存命中率改写排行榜**： Claude Code 输入 token 仅 1.5% 命中缓存，Codex ~70%、OMP ~57%；新输入价格≈缓存 5 倍——Codex 计费 token 超过 100 万但 77% 是约 1/10 价格的缓存读取，按账单算反而比只用它一半 token 的 Claude Code 便宜；连「自建 Agent 框架」都躲不开，因为钱花在底层推理
- **便宜≠更好，但差距真实存在**： Composio 通过率从 OpenCode 46.7% 到 Pi Agent 66.7%（同模型差 20 个百分点）；每次成功任务成本 $0.028（Pi）到 $0.195（Claude Code）；DeepAgents 通过率与 Claude Code 完全相同但成本仅 1/4

💡 **关键数据**: 每任务 token 从 ~3,500（Aider architect）到 29.2 万（OpenClaw）；上下文增速（每轮几百 token）各框架相近、不是成本差异来源；SWE-bench Lite 十任务四种框架都只解出同一题，Aider 花 80 万 token、Codex 花 1500 万；Artificial Analysis 指数 326 任务×3 次取均值

🔗 **樱桃的调度视角**: 这套方法论可以直接搬到 AI 推理平台：按「会话的脚手架开销×轮数 + 缓存命中率」建模计费与容量，而不是只看模型单价；提示词缓存命中率和路由路径强相关（OpenRouter 的 messages 端点转换就打掉了缓存），推理网关做会话亲和（session affinity）时要把缓存友好性当成一等目标喵。

### 7. 🏖️ 蚂蚁 ARCA：从沙箱到执行边界——数万级日创建、千万级日请求的 Agent 基础设施

**原文标题:** 从沙箱到执行边界：蚂蚁 AI Agent 的大规模企业级实践｜QCon上海
**来源:** InfoQ 中文 | 2026-09-12
**链接:** https://www.infoq.cn/article/hk3WB50fAOMDg55YVaaW

🎯 **一句话精髓**: 蚂蚁把 Agent 沙箱从「跑一个容器」升级为 ARCA 执行边界体系：ARCA Sandbox 管隔离+缓存池+快照恢复+成本治理，Piston 管托管与灰度，Tool Gateway 把高危动作路由进沙箱——支撑数万级日沙箱创建、千万级日请求、万核级资源峰值。

🔧 **技术栈**: ARCA Sandbox（安全容器/checkpoint-restore/镜像预热）/ Piston（Agent 托管）/ Tool Gateway / Agentic RL 环境供应链 / CPU 超卖与混部 / 多集群调度

📐 **架构/方法亮点**:
- **五难拆解**： 隔离难（放开执行能力同时守住租户/身份/网络/内核边界）、启动慢（安全容器+镜像拉取+依赖初始化叠加）、状态重（workspace/依赖/会话要持久化但资源不能空转）、规模大（Agentic RL 批量评测带来镜像风暴、缓存击穿、配额竞争）、治理散（高危动作何时进沙箱不能靠业务代码临时判断）
- **Sandboxed Agent 的分治法**： 计算状态、文件状态、身份状态、网络边界、资源成本分开治理——缓存池热分配缩短冷启动、持久化存储+内存快照（checkpoint/restore）支持长会话恢复、出口网关+办公区/沙箱区网络隔离守住边界；成本治理靠 CPU 超卖、混部、空闲回收、quota 计量
- **Agentic RL = 环境供应链**： 训练/评测环境必须可版本化、可复现、可调度、可观测——沙箱在这里的角色是「批量拉起的可信执行环境工厂」，要同时应对多集群调度与环境一致性

💡 **关键数据**: 数万级每日沙箱创建、千万级日请求、万核级资源峰值；覆盖办公 Agent、Coding Agent、Agentic RL、批量评测四类场景（QCon 上海 10 月 22-24 日演讲提纲披露的生产体系概述）

🔗 **樱桃的调度视角**: Agent 沙箱本质是「高频、短生命周期、状态重」的新型 workload——缓存池热分配 + checkpoint/restore 正是调度器冷启动优化的两个杠杆（预热=预调度，快照=状态外置）；「镜像风暴/缓存击穿/配额竞争」提示 Master：Agentic RL 的集群调度要按「环境」而非「Pod」做配额和亲和设计喵。

- **Gateway API 变成更广的流量管理层**： ExternalAuth 让认证/鉴权在请求到达应用之前完成；TCPRoute/UDPRoute 把非 HTTP 流量也纳入同一 API——还在跑 Ingress NGINX 的团队可以让现有 CNI 直接接管南北向
- **netkit auto（bpf.datapathMode=auto）**： 每个 agent 启动时探测自己主机内核，支持 netkit（内核 ≥6.8）就用、不支持则静默回退 veth——混合内核舰队只需一个配置；Meta 已在数百万容器铺开 netkit，ByteDance 同规模部署并报告 10% 性能提升
- **Datapath 插件（beta，Google 主导）**： 第三方代码以独立进程挂进 eBPF 数据路径（CiliumDatapathPlugin CRD 注册），独立构建/版本/发布，插件崩溃不拖垮 agent——云厂商不再需要维护 fork
