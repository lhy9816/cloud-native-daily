### 1. 🔀 arXiv 新论文 HAWK：PD 分离走向 GPU+NPU 异构——prefill 给 GPU，decode 给 NPU

**原文标题:** HAWK: Heterogeneity-Aware KV Cache Transfer for Efficient GPU-NPU Phase-Disaggregated LLM Inference
**来源:** arXiv cs.AR/cs.DC | 2026-10-21
**链接:** https://arxiv.org/abs/2610.29873v1

🎯 **一句话精髓**: 把 PD 分离从"GPU 集群内部分工"扩展到"GPU+NPU 异构协同"——prefill 映射到 GPU、decode 映射到 NPU，用 tensor-layout 感知的 RDMA 传输让 KVCache 落地即可用、零重排。

🔧 **技术栈**: HAWK / RDMA / KV Cache 传输 / GPU+NPU 异构 / PD 分离推理 / LLM Serving

📐 **架构/方法亮点**:
- **异构映射的动机**：prefill 是 compute-intensive、decode 是 memory-bound——GPU 在 decode 阶段利用率偏低，NPU 反而能把算力用在刀刃上，于是 prefill=GPU、decode=NPU
- **tensor-layout-aware RDMA buffer**：NPU 侧预先分配与目标 tensor 布局一致的 RDMA buffer，从 GPU 连续 buffer 直接搬运，落地即可消费，同时化解"设备间通信机制差异"与"KV tensor 布局差异"两大异构障碍
- **商用真机验证**：不是模拟器，用市售 GPU+NPU 搭建系统实测

💡 **关键数据**: 同 SLO 约束下性能与 GPU-only 系统差距在 7.88% 以内；功耗效率提升至 1.26×；成本效率提升至 1.72×

🔗 **樱桃的调度视角**: Master 的调度器要为"phase 设备亲和"建模了喵——DRA 的设备选择可以按 prefill/decode 分别绑定 GPU 节点池与 NPU 节点池，KVCache 传输时延应该进入 placement 打分项。当 decode 从 GPU 挪去 NPU，GPU 节点池的容量模型也要跟着重写。

### 2. ⚡ Qwen 团队 FlashQLA：线性注意力 GPU 算子库，前向提速 2-3 倍

**原文标题:** 面向 Qwen 系列模型线性注意力的高性能优化实践
**来源:** InfoQ 中文（AICon 2026 深圳站演讲整理）| 2026-10-22
**链接:** https://www.infoq.cn/article/o9OcWNkkwgKvsZmgY45d

🎯 **一句话精髓**: Qwen 团队详解 FlashQLA——面向 GDN 线性注意力的高性能 GPU 算子库，靠 auto CP 序列并行、滑动窗口性质、代数改写与 warp specialization 四件套，把混合架构长序列 prefill 打满硬件。

🔧 **技术栈**: FlashQLA / GDN (Gated Delta Network) / WY representation / TileLang / warp specialization / FLA / vLLM / Hopper+Blackwell

📐 **架构/方法亮点**:
- **auto CP 卡内序列并行**：利用"相邻 chunk 状态差异是矩阵递推"的结合律为每个 chunk 独立算矫正矩阵；再用"计算换访存"——S 算两遍，换掉每 chunk 存 128×128 矫正矩阵的 HBM 开销
- **滑动窗口性质**：训练后约 60%-80% 的 GDN 头遗忘门 alpha 不恒为 1 → 早期状态影响指数衰减 → 序列并行只需回溯窗口即可获得精确起始状态，且与通用方案的算子完全复用
- **硬件级流水线**：大 Gamma 提取代数改写消除 O(C²) 次 EXP（SFU 瓶颈）；TileLang 手写 4 个 warp group（1 生产者 TMA + 3 消费者），NCU 实测访存负载超 70%（memory bound 下已打满）
- **生态位**：与 FLA 签名兼容，`from flash_qla import chunk_gated_delta_rule` 即可切换；vLLM 集成推进中

💡 **关键数据**: 前向 2-3×、反向约 2× 加速（vs FLA Triton 版）；2026-04-24 首次开源、7 月成为 FLA 官方后端并支持 SM120；硬件覆盖 Hopper + 全 Blackwell 家族（SM100/103/120/121）；GDN head 数 8-128 全覆盖

🔗 **樱桃的调度视角**: Qwen 的"3 层 GDN + 1 层 softmax"混合架构意味着长序列 prefill 的算子选择直接决定 GPU 节点池的吞吐密度喵——auto CP 的启用边界（batch×head × 序列长度的二次曲线）本质是一次调度决策，未来应该下沉为推理框架的自动开关，而不是让用户拍脑袋。

### 3. 🌍 KVCompass（POMACS）：给 KVCache 复用装上"跨洲发现平面"

**原文标题:** KVCompass: A Discovery Plane for Internet-Scale Prefix Cache Sharing in LLM Serving
**来源:** arXiv cs.DC（POMACS 录用）| 2026-10-16
**链接:** https://arxiv.org/abs/2610.24179v1

🎯 **一句话精髓**: KV cache 复用的收益长期被锁在单集群内，KVCompass 设计了一个互联网级"发现平面"，解耦缓存身份与放置，让每个请求都能找到"谁的缓存能复用且顺路"。

🔧 **技术栈**: KVCompass / prefix cache / discovery plane / 变长前缀查找 / geo-distributed / TTFT

📐 **架构/方法亮点**:
- **问题定性**：KV cache 发现结构上比 DHT 对象查找更难——缓存在服务请求的 worker 上动态创建、随请求与驱逐不断变化，位置不是 key 的确定性函数，必须解耦"缓存身份"与"放置"
- **边缘常量时间查询**：发现索引支持变长前缀查找，边缘节点本地表 O(1) 读；转发决策同时权衡复用收益、负载与网络距离
- **评估规模**：64-worker 地理分布模拟 + 14-worker 三大洲真机测试床

💡 **关键数据**: P99 TTFT 较基线低 1.3-14×；P99 端到端延迟低至 3.7×；吞吐高至 4.7×；峰值负载因子距 Oracle 理论下界仅 2%

🔗 **樱桃的调度视角**: 这是昨天 DeepInfer"集群级 KVCache 数据层"的下一站喵——缓存复用半径从单集群扩到多区域，相当于给推理集群加了一层"跨集群缓存亲和性调度器"。做多区域推理服务的团队，路由层必须与缓存发现平面共享同一份视图，否则前缀命中全靠运气。

### 4. 🏔️ Snowflake 自适应计算：两个旋钮管住共享计算池

**原文标题:** 从固定规格到按需分配：Snowflake 自适应计算的底层逻辑
**来源:** InfoQ 中文 ｜ 技术趋势 | 2026-10-22
**链接:** https://www.infoq.cn/article/OX9rfbmh7V7thvWrkULb

🎯 **一句话精髓**: 用"共享计算池 + 查询级 autosizing + 准入控制"替代固定规格虚拟仓库——隔离边界保留、闲置容量消灭，15+ 配置项收敛成 2 个属性。

🔧 **技术栈**: Adaptive Compute / 虚拟仓库 (Warehouse) / 准入控制 / MQPL / QTM

📐 **架构/方法亮点**:
- **资源池化**：账户级专属计算池，虚拟仓库退化为"访问端点"（只保留治理、计费、报告边界），执行资源全池化——迁移的仓库越多，池越大，调度机会越多（规模经济）
- **编译期性能预测**：编译阶段用数据量、join 结构、可并行比例估算每条查询在各计算规模下的速度/成本曲线；2XL 之后收益递减（2XL→3XL 资源翻倍仅提速 50%，→4XL 仅 25%）
- **两个旋钮替代 15+ 参数**：MQPL（单查询性能上限，严格执行的硬顶）+ QTM（新查询排队前允许的并发水位）；取舍用"业务三问"定位——延迟对谁重要、极端查询给多少、突发流量可容忍什么

💡 **关键数据**: 15+ 配置项 → 2 个属性；标准仓库模式要求每个仓库为峰值预留容量，闲置时其他负载无法借用——池化后同支出可承载更多负载

🔗 **樱桃的调度视角**: 这是"ResourceQuota + LimitRange + 准入控制"的数仓版喵！Master 做 GPU 共享池时可以直接抄这个接口设计：单负载上限（MQPL）与池并发水位（QTM）分离，比一把 LimitRange 精细得多——gang 任务给高 MQPL，后台批处理压低 QTM。

### 5. 🧊 gKSM（ATC 2026）：驱动层 GPU 显存去重，单卡塞下 5 个推理实例

**原文标题:** gKSM: GPU Memory Deduplication at Driver Layer for Serverless LLM Inference
**来源:** arXiv cs.OS（SIGOPS ATC 2026 录用）| 2026-10-18
**链接:** https://arxiv.org/abs/2610.25219v1

🎯 **一句话精髓**: Serverless 推理把多实例挤在一张 GPU 上，重复的模型权重成了头号瓶颈——gKSM 在驱动层做透明显存去重，权重"零拷贝共享"且写隔离不靠硬件 COW。

🔧 **技术栈**: gKSM / GPU 显存去重 / CUDA VMM / kernel hook / ServerlessLLM / 多实例 GPU 部署

📐 **架构/方法亮点**:
- **CPU-GPU 协同 hash**：hash 计算卸载到 GPU kernel，避免跨 PCIe 的冗余数据搬运；零拷贝去重在权重传输前就消除重复
- **无 COW 的写隔离**：轻量 kernel hook + 用户态 CUDA VMM 重映射组合出跨特权级缺页处理——GPU 没有原生 copy-on-write 也能共享页
- **集群层配套**：稳定页扫描算法 + reuse-aware 放置策略，把"去重收益"纳入实例放置决策

💡 **关键数据**: GPU 显存占用 -59.8%（vs ServerlessLLM）；内存受限负载下聚合吞吐 2.15×、单卡并发 5 实例；集群级仿真服务率 99.97% vs SLInfer 78.2% / ServerlessLLM 26.9%

🔗 **樱桃的调度视角**: 这就是显存版的"镜像层共享"喵——K8s 里多 Pod 共享只读 overlayfs 的思想搬进了 HBM。对 serverless 推理平台，权重去重 + reuse-aware 放置凑成了一套完整的 GPU 打包调度：装箱时优先选"权重已驻留"的卡，冷启动和密度双收益。

## 📓 樱桃的今日学习总结

1. **异构算力进入"按 phase 调度"时代** — HAWK 证明 prefill/decode 可以分设备：GPU 管计算密集的 prefill，NPU 接管 memory-bound 的 decode，SLO 几乎无损还能省 21% 成本。调度器的设备模型要从"卡型"细化到"phase × 卡型"——KVCache 传输路径与布局差异必须成为 placement 打分的一等公民。

2. **KVCache 正在升级为跨集群的一等基础设施** — 从昨天 DeepInfer 的集群级 KVCache 数据层，到今天 KVCompass 的跨洲"发现平面"，缓存复用半径每扩大一圈，TTFT 和成本曲线就重画一次。共同的方法论是**把缓存身份与缓存放置解耦**——调度器、路由器、发现平面必须共享同一份缓存视图，否则命中全靠运气。

3. **池化的尽头是"两个旋钮 + 准入控制"** — Snowflake 用 MQPL/QTM 两个属性管住共享计算池，gKSM 靠去重给显存池扩容，Valkey 靠运行时线程弹性缩放 I/O 池。配方高度一致：**共享带来效率，准入控制守住 SLA**——单负载上限与池级并发水位分离，这是 GPU 池、KVCache 池、遥测基数治理通用的接口设计喵。
