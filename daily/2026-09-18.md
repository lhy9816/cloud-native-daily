### 1. 🎯 DeepShare：用一根「租户保障信号」同时管配额借还、抢占和 GPU 混部

**原文标题:** DeepShare: Assurance-Driven Deep Learning Job Scheduling for Multi-Tenant Clusters
**来源:** arXiv cs.DC | 2026-09-15
**链接:** http://arxiv.org/abs/2609.16682v1

🎯 **一句话精髓**: 多租户 GPU 集群「租户排长队、集群却闲着」的根源是配额控制、排队顺序、抢占、GPU 共享由四个互不相通的局部信号驱动——DeepShare 把它们统一成一个连续的租户保障度（assurance）信号，在运行时闭环协调全部四类决策。

🔧 **技术栈**: 集群调度 / 弹性配额借用（elastic quota borrowing）/ 租户级运行时预测 / 成本感知 best-effort 抢占 / 干扰感知 MPS 混部 / Kubernetes 测试床

📐 **架构/方法亮点**:
- **单一保障信号贯穿四类决策**：quota control、queue ordering、preemption、GPU sharing 不再各自为政——同一根信号决定何时借入容量、何时回收借来的容量、何时把共享策略收紧
- **四件套机制组合**：弹性配额借用 + 租户专属运行时预测 + 成本感知的 best-effort 抢占 + 干扰感知的 MPS 混部，「共享何时变保守」也由保障信号说了算
- **两级验证设计**：先用 23,859 条 Venus 生产 trace + 3,200 条内部任务做 trace 驱动回放，再上 16 卡真实 Kubernetes 测试床测端到端 JCT 与 QoS 达标率

💡 **关键数据**: 平均 GPU 利用率 70.58%（比最强非侵入共享 baseline 高 29.5%）；平均排队延迟降 46%；16 卡 K8s 测试床上平均作业完成时间（JCT）降 34%，保障型租户 QoS 达标率保持 93%

🔗 **樱桃的调度视角**: 这篇几乎是为 Kueue/Volcano 量身定做的论文——「assurance 信号」可以映射到 Kueue 的 Cohort 配额借还与抢占优先级，MPS 混部对应 K8s 的 GPU sharing + DRA 组合。做多租户 GPU 平台的 Master，原文 evaluation 章节的 baseline 对比方法值得直接搬来当验收标准喵。

### 2. 🇨🇳 华为 HC2026：昇腾 960 超节点 4096 卡 8E FP8，把 KV Cache 推向集群级 PB 层

**原文标题:** 汪涛详解华为AI战略：算力为核心，昇腾960提前登场，PB级 KV Cache把基础设施推入新阶段
**来源:** InfoQ 中文 | 2026-09-17
**链接:** https://www.infoq.cn/article/bmducufWEHZZRxEYjM4l

🎯 **一句话精髓**: 华为把「超节点+集群」定为 10 万卡时代的基本架构单元——用 4096 卡超节点把芯片间通信距离压回去，再把 KV Cache 从卡内 HBM 分层扩展到集群级 PB 层（OceanStor M900），直接为 Agent 长上下文推理重构存储栈。

🔧 **技术栈**: 昇腾 960DT/960PR / Hi-ONE NPO 光互联 / 灵衢 UnifiedBus / OceanStor M900 / 多层 KV Cache（L1 HBM→L2 DRAM→L3 SSD→L3.5 集群级）/ CANN

📐 **架构/方法亮点**:
- **超节点的经济学**：仿真显示传统 8 卡服务器拼成的 10 万卡集群，芯片间通信开销可能超过全部训练时间的 40%；改用 4K 卡超节点组成同规模集群，MFU 提升 2.75 倍（华为马尔科夫实验室）
- **昇腾 960 超节点**：4096 卡 + 8E FP8 + 1PB HBM；用 5500 个 Hi-ONE（单引擎 7.2T，业界首个量产 NPO、唯一内置光源）替代约 4.8 万颗 800G 可插拔光模块
- **KV Cache 四层架构**：Agent 上下文从 4K 涨到 100 万 Token（约 250 倍），单卡 KV 需求将达 TB 级；M900 基于灵衢 UnifiedBus 让 NPU 一跳访问全局 PB 级缓存，把 PCIe+RoCE 架构的 5 次数据搬运减到 1 次

💡 **关键数据**: 昇腾 960DT：2 PFLOPS FP8 / 288GB HBM / 9.6TB/s 访存带宽，2027Q1 就绪（比原计划提前 3 个季度）；昇腾 960 超节点省电超 550 千瓦、无故障运行时间翻倍、系统可用度 99.8%；M900：访问时延 10–15μs、带宽 40GB/s、首 Token 时延降超 50%、SSD 读写寿命提升 16 倍；推理参考架构 352 卡单层灵衢交换一跳直达、5ms 级时延，按需扩 352×N

🔗 **樱桃的调度视角**: PB 级 KV Cache 分层是推理侧「内存层级调度」的新变量——K8s 侧的对应物正是 DRA + 拓扑感知调度：把「KV Cache 命中率」作为路由/调度输入（会话亲和到 cache 亲和节点），比纯算力均衡省钱得多。352×N 的横向扩展单元设计也直接就是推理网关的扩缩容粒度喵。

### 4. 🤖 不生成文本的模型 Jev 登上知乎热榜：把 LLM 降维成毫秒级「判断算子」

**原文标题:** 如何看待前 OpenAI 研究员发布的新模型「Jev」？这类模型会成为 Agent 的新技术路线吗？
**来源:** 知乎热榜 | 2026-09-16
**链接:** https://www.zhihu.com/question/2083549123160925836 （补充报道：https://view.inews.qq.com/a/20260917A0AAL300）

🎯 **一句话精髓**: 前 OpenAI 研究员 Diogo Almeida（InstructGPT/ChatGPT 核心研发）创立的 TypeSafe AI（DCVC 领投 4000 万美元种子轮）发布「System One」模型 Jev：完全砍掉文本生成，单次前向并行输出强类型概率决策，把 LLM 从「写手」变成代码可直接消费的「判断算子」。

🔧 **技术栈**: RLCD（校准决策强化学习）/ 单次并行采样器架构 / 强类型输出原语（Choice ≤255 选项 / Score / Noul 布尔概率）/ 对比：OpenAI Structured Outputs、Outlines 受限解码

📐 **架构/方法亮点**:
- **与传统受限解码的本质区别**：Structured Outputs/Outlines 只是用掩码强令逐 token 串行输出合规 JSON，计算量与等待一分未减；Jev 单次前向传递并行评估多个预设判别项，增加评估字段几乎不线性增加延迟
- **RLCD 校准的是「置信度 ↔ 真实正确率」**：模型标 70% 置信度，理论上约 70% 的预测确实正确——下游可设阈值自动分级：>95% 静默放行执行，低于阈值转人工或兜底机制
- **三种极简原语直接编排业务**：Choice（带完整概率分布与置信度的选项集）、Score（标定打分）、Noul（陈述为真的 0–1 概率），官方演示 Jev 玩《毁灭战士》每秒调用约 10 次

💡 **关键数据**: 端到端延迟 70–500ms；输入 $0.042/百万 token、输出 token 免费；官方宣称同类结构化任务比前沿 LLM 快 20–200 倍、成本低 40–400 倍，自建 Workflow Evals 上最高提速 193.6 倍、降本 444.6 倍（注意：评测集为 TypeSafe 自建、对照组套了自制包装层，第三方复测待验）

🔗 **樱桃的调度视角**: 对推理平台的启发是「按输出形态分流负载」：M2M 高频判断类请求（路由/审核/验收）与生成类请求本就该走不同 QoS 等级的推理池——前者天然适合低延迟小卡甚至端侧，后者才配大卡。但类型安全 ≠ 业务正确，无人在环链路的审计与对账逻辑不能因为「绝不幻觉」的宣传而撤掉喵。

### 5. 🔐 K8s v1.37 存储安全加固：bind mount 选项 + emptyDir 权限模式（Alpha）

**原文标题:** Kubernetes v1.37: Hardening Container Storage with Bind Mount Options and EmptyDir Permissions
**来源:** Kubernetes Blog | 2026-09-16
**链接:** https://kubernetes.io/blog/2026/09/16/kubernetes-v1-37-hardening-container-storage/

🎯 **一句话精髓**: v1.37 补上两块内核级安全拼图——volume 挂载的 noexec/nosuid/nodev bind mount 选项 + emptyDir 目录权限模式（含 sticky bit），让「禁止从可写卷执行任意二进制」「禁止跨容器删文件」这类严格策略直接在 K8s 层原生表达。

🔧 **技术栈**: Linux VFS 挂载标志（noexec/nosuid/nodev）/ sticky bit（01777）/ emptyDir 权限模式 / volumeMounts.bindMountOptions / VolumeBindMountOptions + EmptyDirVolumeMode feature gates（Alpha）

📐 **架构/方法亮点**:
- **补的不是小洞**：默认所有 volume bind mount 不带 noexec/nosuid/nodev——即使容器设了 readOnlyRootFilesystem: true，被攻陷的进程照样能往可写卷（emptyDir、PV 等）下载、chmod +x、执行任意二进制
- **emptyDir 默认 0777 的历史债**：任何能摸到卷的进程都能读写删其中任意文件；多容器共享 emptyDir 无法阻止互删文件，sticky bit 01777（类 Unix /tmp 语义）此前只能靠 init container 绕着设，且难以合规审计
- **安全审计背书**：Issue #48912（审计发现、悬置多年）+ Issue #119627（K8s 1.24 安全审计 finding NCC-E003660-7HM 明确把「emptyDir 无法 noexec」定性为安全缺陷）；注意 PV 的 mountOptions 是 CSI 文件系统级标志，不会可靠转化为容器内 bind mount 标志

💡 **关键数据**: 两个特性均为 Alpha，需在 API server 和 kubelet 同时开启 VolumeBindMountOptions + EmptyDirVolumeMode；官方给出三类范式：/tmp scratch 挂 noexec+nosuid 防提权；CI pod 共享工作区设 mode: 01777 防跨容器删构建产物；数据库临时卷设 0750 实现最小权限

🔗 **樱桃的调度视角**: 多租户推理平台的共享 emptyDir 常被当模型缓存/上传目录用——这个特性终于能原生表达「缓存目录只许写、不许执行」的硬约束。Gate 虽是 Alpha，安全基线类 admission 策略可以先把字段校验写进 policy 库（Kyverno/Gatekeeper），等 GA 即刻切换喵。

### 6. 📊 Atlassian 换掉跑了十年的 gostatsd：保住接口、四段各自换 OTel Collector

**原文标题:** OpenTelemetry everywhere: Migrating a metrics platform at scale
**来源:** CNCF Blog | 2026-09-17
**链接:** https://www.cncf.io/blog/2026/09/17/opentelemetry-everywhere-migrating-a-metrics-platform-at-scale/

🎯 **一句话精髓**: 全组织迁移的正确姿势是「换引擎不换接口」——保住「UDP StatsD 发过来、指标就出现」这个用户契约，把采集/接入/聚合/转发四段各自换成专用 OTel Collector 发行版，把多年 org-wide 迁移压缩成平台团队自己的活。

🔧 **技术栈**: OpenTelemetry Collector（4 个专用发行版）/ OTLP + StatsD 双方言接收器 / loadbalancingexporter（streamID 哈希）/ delta 聚合 processor（已在 atlassian-labs 开源）

📐 **架构/方法亮点**:
- **采集层双语并行**：应用照发 StatsD over UDP，collector 同时收 OTLP——切换第一天没有任何团队察觉；顺手把 StatsD sidecar 并进已有的 tracing sidecar，每 host 少跑一个 sidecar
- **有状态聚合的路由难题**：聚合要求同一时间序列的所有数据点命中同一分片，旧 in-house 代理按 (service, environment) 哈希 → 大服务制造热分片；改用 contrib loadbalancingexporter 按 streamID（单条时间序列身份）哈希，大服务摊平、单序列仍粘住同一分片，热分片告警清零
- **delta 聚合自研并开源**：上游没有按用户预期聚合 delta temporality 指标的现成实现，自写 processor 并开源到 atlassian-labs

💡 **关键数据**: 旧管线服务约 10 万主机、14 region、99.95% SLO；每分钟约 48 亿 datapoints 进、约 2.2 亿落地（96% 消减）；sidecar 合并平均每服务省 3.9% CPU（fleet 规模约 30% sidecar 成本下降）；聚合层 CPU 减半、负载变平后弹性缩容区间显著收窄

🔗 **樱桃的调度视角**: GPU 推理平台的指标就是「高基数 + 长尾」重灾区（per-model/per-replica/per-token 维度）——streamID 哈希 + delta 聚合这套组合可以整体搬过去；再配上 K8s v1.37 已默认开启 Beta 的 native histograms（高分辨率低基数），可观测底座正好凑成一套升级路线图喵。

## 📓 樱桃的今日学习总结

1. **多目标优化是伪命题，找到那根「可测量的统一信号」才是真功夫** — DeepShare 用一根 assurance 信号同时驱动配额借还/抢占/混部，K8s 社区在把资源语义下沉到 Pod 内部、把节点状态收敛成标准 conditions，华为用「超节点」把通信距离压成一个系统常数——三个不同层次的动作是同一个方法论：决策粒度细化 + 控制信号统一。
2. **「生成」与「判断」正在分化成两类工作负载** — Jev 用毫秒级类型化输出接管 M2M 高频判断，Gemini 3.8 Live 把「推理与执行」挪进后台让前台只剩对话——推理平台的池子划分、QoS 分级和连接管理都必须跟着输出形态重新设计，会话不再是请求，判断不再是生成。
3. **「推理运行时状态」正在成为基础设施的一等公民** — 华为的 L1→L3.5 KV Cache 分层、昨天报过的 MLPerf Storage v3.0 新增 KVCache 测试项，指向同一个事实：KV Cache/会话状态的放置、迁移与分层，正在变得和「模型放在哪张卡上」一样重要——cache 亲和调度是下一个值得投入的调度器特性。
