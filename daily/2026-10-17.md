### 1. 🌋 Volcano v1.16.0 发布：失败缓存 + Slurm 式公平 + HyperNode 拓扑开放

**原文标题:** Volcano v1.16.0
**来源:** GitHub Releases（volcano-sh/volcano） | 2026-10-14
**链接:** https://github.com/volcano-sh/volcano/releases/tag/v1.16.0

🎯 **一句话精髓**: 批量调度旗舰一次放出三大件——NamespaceQueue + fairshare 插件解决多租户长期公平（借鉴 Slurm 历史用量衰减）、Unschedulable Job Cache 把"调度失败记忆"变成事件驱动状态、HyperNode 拓扑发现/supernode 管理抽成独立控制器开放给其他调度器复用。

🔧 **技术栈**: Volcano / NamespaceQueue / fairshare（Slurm 用量衰减）/ HyperNode controller & API / PodGroup 拓扑反亲和 / Unschedulable Job Cache / DRA scoring / Kubernetes 1.36

📐 **架构/方法亮点**:
- **Unschedulable Job Cache**：记录 Job 被拒的具体原因，配合插件提供的 event hints 决定何时重评——Node label 更新唤醒被亲和性阻塞的 Job、资源释放唤醒资源阻塞的 Job、Queue 更新唤醒配额阻塞的 Job；只有当**所有**拒绝插件都给出安全 hint 时才入缓存，gang 语义与公平性不受影响，其余 Job 照常走逐 session 评估
- **NamespaceQueue 多租户模型**：租户在自己的命名空间内管理队列层级与配额，底层消费管理员授权的资源池；fairshare 用历史用量衰减抑制"昨天抢多的今天继续抢"，改善长期公平
- **HyperNode 生态化**：拓扑发现与 supernode 管理独立成 controller + API，其他调度器可直接接入；PodGroup 拓扑反亲和支持 required/preferred 两档，把工作实例强制打散到不同拓扑域

💡 **关键数据**: 支持 Kubernetes 1.36；调度性能三项优化——评分插件共享节点遍历、缓存更新与队列查找降开销、bulk Pod dispatch 负载估算；同版还加入 DRA 评分、nodegroup 级队列配额与加速器增强

🔗 **樱桃的调度视角**: Unschedulable Job Cache 本质是把调度器的"失败记忆"提升为一等状态——和 K8s 调度器把 unschedulable Pod 移入 backoff 队列同思想，但在 gang/batch 语义上补得更完整，万卡集群积压场景收益最大。NamespaceQueue + fairshare 直接对标 Slurm fair-tree，是 GPU 集群多租户配额博弈的现成答案喵。

### 2. 🧮 QCon 前瞻：算力效率的边界——经典分布式命题在 AI 负载下的物理重塑

**原文标题:** 算力效率的边界：以体系结构量化与分布式工程破局 AI Infra
**来源:** InfoQ 中文（QCon 上海 2026「AI Infra：算力效率决定规模化落地」专场前瞻） | 2026-10-15
**链接:** https://www.infoq.cn/article/JbzA5yvzl2BkuTpkfdrU

🎯 **一句话精髓**: 成本重心已加速转向推理端，竞争核心从"单 Token 标价"变成"端到端任务的有效交付成本"（业界称"斩杀线"）；算力效率是最大的工程杠杆——文章系统梳理了三大系统瓶颈与四大经典分布式命题（资源分配/状态维护/通信协同/效能度量）被 AI 负载物理约束改写的全过程。

🔧 **技术栈**: MoE 动态路由 / PagedAttention / MLA·GQA·低比特量化 / RadixAttention（SGLang）/ Mooncake / PD 分离 / 400Gbps RDMA / BlitzScale 组播加载 / Orca 迭代级调度 / RollPacker

📐 **架构/方法亮点**:
- **CPU 调度三件套在 GPU 上全部失效**：时间片轮转、虚拟内存超卖、微秒级确定性抢占——GPU 显存有严格物理上限且不可超卖（触顶即 OOM，只能靠 MLA/GQA/量化压缩状态体积 + PagedAttention 治碎片 + Token 预算动态批处理），无细粒度硬件抢占（最小调度单位停在算子边界，高优先级任务也必须等在途算子跑完），性能深度绑定 NVLink/交换域拓扑、节点不可等价置换
- **KV cache 复用逻辑重写**：缓存重建开销 = 一次完整 Prefill，且丢 3 万 token 长上下文 vs 丢 50 token 短上下文的重算成本差数个数量级——LRU/LFU 全部失效，必须转向"算力收益驱动"的动态复用（SGLang 用前缀树、Mooncake 用内存+SSD 池化置换计算）
- **PD 分离不是银弹**：Prefill 产出的数 GB KV cache 要实时跨节点同步，400Gbps 以上 RDMA 集群才能"搬迁快过重算"，普通以太网会抵消全部增益；RL 后训练场景还要在 Rollout（KV cache 显存）与 Training（优化器/梯度显存）间高频时分复用，RollPacker 用长尾归并+阶段重叠缓解执行长尾

💡 **关键数据**: 推理实例扩容需搬运数十至数百 GB 权重（冷启动是"数据搬运问题"而非控制面指令）；单任务 Token 消耗以更高阶倍率激增、交付成本不降反升；文章把 GPU 调度挑战归纳为显存不可超卖、冷启动延迟、缺抢占、组调度拓扑碎片、RL 时分复用五大类，QCon 上海 10 月 22-24 日展开

🔗 **樱桃的调度视角**: 这是给调度器工程师的"物理约束清单"——显存不可超卖意味着**准入控制在调度之前**，拓扑绑定意味着调度器必须持有带宽矩阵而非把算力当可加标量。做 GPU 集群调度器设计时，这篇可以当 checklist 用喵。

### 3. 📄 arXiv 新论文：连续批处理下 8 种轻量调度策略的 1152 组实证

**原文标题:** Lightweight Scheduling Policies for Continuously Batched LLM Serving Across GPU Architectures
**来源:** arXiv cs.DC（arXiv:2610.15899） | 2026-10-11
**链接:** https://arxiv.org/abs/2610.15899

🎯 **一句话精髓**: 不改模型架构、不换 kernel、不部署 learned scheduler，仅靠解码期的请求排序策略就能改变 LLM 服务的延迟-吞吐权衡——论文用 1152 组 GPU-模型-调度器-负载组合实验给出实证排名：**Aging shortest-prompt-first（老化最短提示优先）是最强实用基线**。

🔧 **技术栈**: 连续批处理（continuous batching）/ Python·PyTorch 测试台（真实 Hugging Face 执行）/ ShareGPT 衍生流量 / Qwen·Gemma·Mistral 共 6 个模型 / Modal 云 L40S·A100·H100

📐 **架构/方法亮点**:
- 实验设计极其规整：固定模型、GPU、负载、batch size 与 prefill 预算，单变量轮换调度器，8 种策略 × 1152 组跑遍三种 GPU 架构——把"调度策略选型"从玄学变成查表
- 核心发现：调度器选择同时影响吞吐、TTFT、完成延迟与尾延迟；aging shortest-prompt-first 在 L40S 与混合负载下表现最强——用"等待时间老化"补偿最短优先的饥饿问题，实现成本几乎为零
- 反直觉结论：oracle 级"剩余长度已知"调度并没有碾压——**仅知道 job 大小并不足够**，批处理动力学与硬件效应同样塑造性能；数据集已上传 Hugging Face 供复现

💡 **关键数据**: 1,152 组 GPU-model-scheduler-workload 运行；8 种策略；6 个模型；3 种 GPU（L40S/A100/H100）；流量取自 ShareGPT 衍生真实分布

🔗 **樱桃的调度视角**: 推理网关里的请求排序就是"免费的调度杠杆"——这篇论文给了选型基线（aging SPF 起步，再按负载形态调）。它和 llm-d 的 EPP 是同一层的两个视角：EPP 管 KV 局部性放置，SPF 管队内排序，两者正交可叠加喵。

### 4. 🤖 GitHub Go 周榜第一 google/ax：Google 开源"Agent 编排运行时"，K8s 式声明 YAML 调度数十亿 Agent

**原文标题:** AX — Google's open agentic orchestration runtime
**来源:** GitHub Trending（Go 日榜第一，周 +2,919★） | 2026-10-16（在榜数据）
**链接:** https://github.com/google/ax

🎯 **一句话精髓**: Google 把 AI Agent 定义为一种**新的 workload 类型**——"既不是无状态微服务，也不是 run-to-completion 批任务"——用 ax.io/v1alpha1 的 Workspace/Task/Model 三种声明式原语，在 Agent Substrate 沙箱上编排"每集群数十亿级"的自治 Agent 任务，体验刻意做成 `ax apply` 风格的 K8s 平替感。

🔧 **技术栈**: Go / ax.io/v1alpha1 API（Workspace·Task·Model）/ Agent Substrate（沙箱执行基座，ate-system 命名空间）/ Git 仓库与 MCP server 预接线 / ko 部署 / Kubernetes Secret 管理模型凭证

📐 **架构/方法亮点**:
- **Task = 带资源限额的沙箱**：不受信 Agent 代码跑在 CPU/内存限额的隔离沙箱里，支持 `ax ssh` 进运行中 Agent 查看现场、`debug: true` 开调试——Agent 治理从"提示词工程"下沉到"资源隔离"
- **Workspace = 预热的工作区**：把 Git 仓库、MCP 服务器、skill 包提前接线好，让每个 Agent "热启动"；把 Model 凭证收敛进 K8s Secret，平台自用 LLM 与业务 Agent 解耦
- **生命周期原语**：`ax suspend`/`ax resume` 暂停闲置 Agent 并从断点精确恢复（Agent 状态会累积，不能当无状态服务杀掉重拉）——这是 K8s 三个原生 workload 抽象都覆盖不了的

💡 **关键数据**: Go 周榜第一（周 +2,919★）、总 13,701★；仓库 2026-03-30 创建，最后 push 2026-10-15；README 明确定位"run billions of tasks per cluster"，当前处于不稳定期（作者警告核心概念与协议在 1.0 前会有 breaking changes）

🔗 **樱桃的调度视角**: 继 kagent「Agent 即 CR」之后，Google 给出了更激进的版本——自建 substrate 而非直接复用 K8s 调度器，因为 Agent 需要的是**长生命周期状态 + 沙箱隔离 + 成本护栏**的三合一。Master 关注 Agent 平台建设的话，Task 的资源限额与 suspend/resume 语义值得抄进自己的设计喵。

### 5. 🇨🇳 阶跃星辰开放 Step 5 Preview 权重：600B 稀疏 MoE 押注长程 Agent，上下文压缩进训练目标

**原文标题:** 阶跃星辰开放 Step 5 Preview 权重：长程 Agent 的竞争，延伸到上下文管理与训练系统
**来源:** InfoQ 中文 | 2026-10-15
**链接:** https://www.infoq.cn/article/EwqsJX6f03ODRac6Kk4c （权重：https://huggingface.co/stepfun-ai/Step-5-Preview）

🎯 **一句话精髓**: 阶跃星辰 10 月 15 日开源 Step 5 Preview（BF16+FP8 双精度），600B 总参/27B 激活的稀疏 MoE、1M 上下文，面向长程 Agent 任务；最有意思的设计是把**上下文压缩纳入端到端策略训练**——让模型自己学会在上下文预算将尽时整理出可恢复的工作状态。

🔧 **技术栈**: 稀疏 MoE（600B/27B）/ 92 层窄深架构 / 门控滑动窗口注意力 3:1 交替稀疏全局注意力 / Sparse GQA（8-token 索引块）/ FP32 隐藏状态+细粒度梯度截断 / 百万级可验证环境 / vLLM·SGLang 部署

📐 **架构/方法亮点**:
- 注意力工程细节：92 层 Transformer 按 3:1 交替配置门控滑动窗口注意力与稀疏全局注意力；Sparse GQA 把相邻 8 个 token 合并为索引块，索引与 top-k 选择开销降至原来的 **1/8**（注意：是该项开销降 8 倍，不等于端到端推理提速 8 倍）
- 训练稳定性组合拳：隐藏状态及其梯度、归一化缩放参数全部用 FP32，配合细粒度梯度截断；百万级可验证环境显式控制任务难度与多样性，并检查模型是否利用评测漏洞"刷分"
- 上下文压缩即训练目标：与常规"外挂记忆/截断"不同，压缩行为用与任务相同的奖励做端到端强化——Agent 在预算将尽时输出可恢复状态再继续，窗口大小与任务可靠性之间的鸿沟交给模型自己学

💡 **关键数据**: 总参数 600B、每 token 激活 27B、100 万 token 上下文窗口、原生文本+视觉输入；截至 10 月 15 日 OpenRouter 平台 Token 用量周榜与日榜**全球第二**；InfoQ 特别提醒：27B 激活≠27B 部署门槛——未激活的专家权重仍是部署系统必须管理的资源

🔗 **樱桃的调度视角**: 又一个"激活参数≠容量规划参数"的案例——显存里驻留的是全部 600B，调度器做副本放置时只能按 BF16/FP8 全量权重算容量。FP8 版本 + vLLM/SGLang 官方适配意味着推理平台可以立刻做吞吐基准，1M 上下文则会持续推高 KV cache 分层存储的需求喵。

### 6. 🏭 生产级 LLM 平台工程手册：不换模型，把幻觉率从 15% 干到 1.5%

**原文标题:** 生产级大模型平台工程实战手册
**来源:** InfoQ 中文（作者 Aditya Mulik，15793 字长文） | 2026-10-16
**链接:** https://www.infoq.cn/article/xQLd004RGWrzFhwqBOyC

🎯 **一句话精髓**: 大型零售企业的 LLM 库存系统上线首月 15% 输出是幻觉，六个月降到 1.5%——靠的不是换更强的模型，而是把大模型能力**下沉为平台基础设施**：网关 + ADK 根协调 Agent + 专家 Agent + MCP 工具服务分层，用 Schema 强制校验把"模糊的 AI 故障"变成"结构化的可重试事件"。

🔧 **技术栈**: Google ADK（智能体编排）/ MCP（FastMCP 工具服务，按团队隔离）/ LiteLLM 统一模型路由（本地 Ollama llama3.1 ↔ 云端 Gemini/GPT 一键切换）/ Pydantic Schema 强制校验 / JWT 网关鉴权

📐 **架构/方法亮点**:
- **Schema 即幻觉探测器**：输出 Schema 内置 grounded / out_of_scope 追踪字段（生成成本为零），强制模型以机器可读形式承诺"答案是否有工具证据支撑"；校验失败、字段缺失、grounded=false 都成为平台级监控指标而非应用日志里的异常
- **重试编排三分法**：Schema 违规→把校验错误回注提示词重试；幻觉信号→换更强的锚定上下文重试；基础设施故障（429/503）→指数退避——盲目重试有害，直接重跑幻觉提示词只会得到另一个幻觉；每请求硬上限 3 次
- **工具锚定流水线**：专家 Agent 只能以 MCP 工具返回为唯一事实来源，先查 ID 再拉文档，文档没覆盖必须如实回答 out_of_scope——锚定不是提示词技巧，而是"工具取证据 + 提示词约束 + Schema 声明 + 校验重试"四段闭环

💡 **关键数据**: 幻觉率 15% → 1.5%（6 个月）；系统分析数百万 SKU、数十亿条历史库存记录；平台服务数十个应用团队；配套代码库端到端本地可跑（Ollama），零 API 费用；作者的决策心法——**搭平台的时机是第二个 LLM 应用上线时，而不是第十个之后**

🔗 **樱桃的调度视角**: 这篇把"重试风暴治理"讲成了容量问题：无上限重试就是自我 DDoS，故障分类 + 指数退避 + 请求硬上限是 LLM 网关的限流三件套。它也再次验证了第 4 条的趋势——Agent 负载要被平台托管（凭证、配额、可观测），而不是散落在各应用里喵。

### 7. 📉 Cloudflare 数据管道的"反摩尔定律"战役：五年优化推迟两年半硬件扩张

**原文标题:** Rewinding the exponential: How we keep hardware usage down
**来源:** Cloudflare Blog | 2026-10-13
**链接:** https://blog.cloudflare.com/rewinding-the-exponential/

🎯 **一句话精髓**: 承载 20% Web 流量的 Cloudflare 数据管道在约 20 亿 events/秒的量级上对抗"流量指数增长 vs 硬件线性增长"——过去五年三轮架构手术（拆 schema、换压缩、重构复制+分散采样+管道内聚合）累计**推迟了两年半的硬件扩张**。

🔧 **技术栈**: Logfwdr（采集）→ 集中式 receivers → Buftee（缓冲）→ ClickHouse / zstd / 双写→共享接收池 failover / 降采样 / 管道内聚合

📐 **架构/方法亮点**:
- **2022 拆 monolith schema**：把"所有产品字段挤一条流"改为按产品拆分小消息，内部消费者不再全量拉取再丢弃——骨干带宽直接降 35-40%，相当于抵掉约一年的压缩流量增长
- **2024 LZ4 → zstd**：先小规模灰度确认 CPU 无感再全量推开，压缩流量再降约 40%——同尺寸管道承载 1.5 倍流量，约合 10 个月增长
- **2026 复制架构重构**：为容灾而生的"每事件双写两地"在覆盖几乎所有分析流后让 Logfwdr 流量翻倍，改为 Logpush 式"共享接收池 + 机器/机房不可达自动 failover"；配合分散式采样（高频流量降采样、稀有事件全保）与管道内聚合三箭齐发

💡 **关键数据**: 约 20 亿 events/秒（2026 年 5 月）；支撑数万台服务器；五年优化累计 = 2.5 年硬件扩张延期；35-40%（schema 拆分）+ 40%（zstd）骨干带宽削减

🔗 **樱桃的调度视角**: 这是一场跨五年的"容量调度"：采样与聚合本质是**用精度换资源的降级策略**，双写改共享池则是把容灾冗余从"静态复制因子"变成"动态故障转移"——和调度器里"预留 vs 抢占"的权衡同构。指数增长面前，省下的每一个字节都是延迟采购的资本支出喵。

🎯 **一句话精髓**: 绿色软件基金会（GSF）想把 SCI（Software Carbon Intensity）引入 OTel 语义约定——关键不是再出一个能耗指标，而是用 **SCI =（E×I+M）/R** 把碳排放绑定到"功能单元"（每请求/每事务），让碳效率可以像延迟、吞吐一样被对比、被优化、被调度。

🔧 **技术栈**: SCI 规范（GSF）/ OpenTelemetry 语义约定 / Kepler（K8s 能耗指标暴露）/ 碳强度 I（电网因子）/ 隐含碳排放 M（硬件折旧分摊）

📐 **架构/方法亮点**:
- **功能单元 R 是灵魂**：版本 A 总排放 100 kg CO₂e / 100 万事务，版本 B 110 kg / 200 万事务——B 总量更高但每事务 0.000055 vs 0.0001 kg CO₂e，碳强度减半；只看总量的指标会引导出错误优化方向
- **从"孤立测量"到"关联 workload"**：Kepler 等工具已能暴露 K8s 能耗数据，但把能耗归属到具体 workload/服务/操作仍无统一语言——OTel 语义约定负责统一命名、单位与粒度，让跨系统对比成为可能
- **能耗 ≠ 碳 ≠ 效率**：E（能耗）、I（电网碳强度，随时间与区域波动）、M（硬件隐含碳）三个变量独立变化，优化目标必须分开陈述

💡 **关键数据**: 文中算例——A 版 0.0001 kg CO₂e/事务 vs B 版 0.000055 kg CO₂e/事务（总量 100→110 kg、事务量 100 万→200 万）；该方向在 Observability Summit Europe 2026（布拉格）keynote 中提出

🔗 **樱桃的调度视角**: 碳感知调度离落地只差这一层标准化——I（电网碳强度）天然是时变信号，完全可以进调度器评分函数当权重（类似 spot 价格驱动抢占）。对 GPU 集群而言，"每请求焦耳"和 MFU 一样是效率审计指标，Kepler 出数据 + OTel 定语义 + 调度器消费，链路已经隐约可见喵。
