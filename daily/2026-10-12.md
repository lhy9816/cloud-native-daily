## 🚀 重点速览

### 1. 🏗️ Uber 多编排器扩缩容解耦：一个 ServiceScale CRD 让故障转移「抢」容量，省下 100 万核

**原文标题:** Uber 在 Kubernetes 平台上将扩容意图与执行操作解耦
**来源:** InfoQ 中文 | 2026-10-11
**链接:** https://www.infoq.cn/article/2SNgaiHoK808v22dl5SJ

🎯 **一句话精髓**: Uber 发布 ServiceScale 控制器方案——把「谁想扩缩容」（Up/UDC 的稳态意图、故障转移编排器的临时意图）与「怎么落地」（SSC 调和成 K8s 对象）分离，多个编排器安全共存地管理同一组工作负载，区域故障时抢占低优先级容量、彻底告别静态预留。

🔧 **技术栈**: ServiceScale CRD / Service Scale Controller (SSC) / Uber 部署控制器 (UDC) / Up 平台 / Informer 缓存「读己所写」防护 / OpenKruise CloneSet / KubeKind 集成测试 / Karmada

📐 **架构/方法亮点**:
- 刻意不把故障转移逻辑塞进 UDC（它已处在服务生命周期关键路径，回归会波及全部部署），而是新增 CRD 承载多方意图——意图直接物化在 etcd 里，排障时看 ServiceScale 就知道「哪个编排器想要什么」，恢复时也不用从日志重建状态
- 「读己所写」一致性防护：控制器更新下游资源时把资源版本号打成注解，上报状态前先确认本地 Informer 缓存已读到该版本——K8s v1.36 的控制器缓存过期缓解方案采用了同款思路，且正与 controller-runtime 合作推广到全生态
- 多写入者并发陷阱：UDC 与 SSC 同改一个资源时，特定时序会让 ReplicaSet 元数据与规范漂移、破坏滚动更新比例扩缩容——靠全集群可观测检测 + 自动修复程序兜底，并在扩缩容路径上推进长期修复

💡 **关键数据**: 100+ 计算集群（IDC + Oracle + Google 云）、约 4000 个服务、300 万核 CPU、每天启动 150 万个 Pod；统一故障转移架构把稳态冗余从 2 倍降到 1.3 倍、节省超 100 万 CPU 核（arXiv 2026-01 论文）；整个方案上线耗时一年，零客户可感知中断

🔗 **樱桃的调度视角**: 这是「抢占式容量分层」的生产级范本——把低优先级负载当容量缓冲、故障时分钟级让位，比每个区域都留一倍闲置便宜得多。Master 做多集群容量规划时，「意图 CRD 化」比私有 API 更 K8s-native；Karmada 刚从 CNCF 毕业，说明多编排器这条路已是社区主线喵。

### 2. 🚦 llm-d Router 登上 Go 周趋势榜：推理流量的「调度器」正式收敛进一个仓库

**原文标题:** llm-d Router (Inference Scheduler 更名)
**来源:** GitHub Trending (Go, weekly) | 2026-10-11
**链接:** https://github.com/llm-d/llm-d-router

🎯 **一句话精髓**: llm-d 把 Inference Scheduler 更名为 llm-d Router，并把 Gateway API Inference Extension 的 EPP 核心代码与 InferenceObjective、InferenceModelRewrite 两个 API 合并进来——「负载与前缀缓存感知」的推理路由正式成为网关侧一等公民，GIE 仓库只保留 InferencePool API。

🔧 **技术栈**: Endpoint Picker (EPP) / Envoy ext-proc / Gateway API Inference Extension (InferencePool) / InferenceObjective + InferenceModelRewrite API / Istio / AgentGateway / Google Cloud ALB / P/D·E/P/D 分离 Disaggregation Sidecar

📐 **架构/方法亮点**:
- EPP 是路由大脑：综合 KV-cache 局部性、当前负载、请求优先级做放置决策，经 ext-proc 协议把实时信号注入 Envoy 数据面——调度器以网关旁路决策点的形态存在，不侵入每个 Pod
- 请求管理 API 拆出调度语义：InferenceObjective 声明请求优先级与性能目标，InferenceModelRewrite 做模型名重写以支撑 A/B 测试与金丝雀发布
- Disaggregation Sidecar（通常部署在 decode worker 旁）编排 P/D（Prefill/Decode）与 E/P/D（Encode/Prefill/Decode）多阶段生命周期，协调 KV-cache 与 embedding 传输；部署上 Standalone（Envoy sidecar/service 两种拓扑）与 Gateway API 对接两种模式任选

💡 **关键数据**: 本周登上 GitHub Go 语言周趋势榜；仓库 394 stars、Go 实现、topics 覆盖 gateway-api/inference/kubernetes/networking、最近推送 2026-10-11

🔗 **樱桃的调度视角**: Prefill 算力密集、Decode 访存密集，P/D 分离后「网关按 KV-cache 局部性路由」本质就是推理版的数据亲和性调度。Master 选型 GPU 推理网关时，EPP+ext-proc 把调度决策放在 L7 代理旁边，比自研全网格干净得多；InferenceObjective 的优先级语义也正好能对接 Kueue 的队列优先级喵。

### 3. 🎛️ vLLM-Omni 技术报告：语音/图像/视频/机器人生成统一进一套多阶段流水线运行时

**原文标题:** vLLM-Omni Technical Report: A Unified Serving Runtime for Omni-Modality Generation
**来源:** arXiv | 2026-10-07（提交）
**链接:** http://arxiv.org/abs/2610.09307

🎯 **一句话精髓**: 全模态时代的 serving 不再是单一 text decode loop——vLLM-Omni 用「单一 orchestrator + 多阶段流水线」统一准入、跨阶段推进、流式解复用：专用引擎做计算、connector 在数据面搬重负载、会话化控制撑住长连接的世界模型与机器人循环。

🔧 **技术栈**: vLLM-Omni / 多阶段流水线编排 / stage 级 KV 路径 / stage 副本池 / 多硬件平台 / 数据面 connector / 会话导向控制 / OpenAI 兼容 API + OpenPI API

📐 **架构/方法亮点**:
- 病灶拆得准：多阶段自回归（omni/TTS 流水线）、迭代扩散/流匹配生成、跨步带状态的世界模型与机器人循环，三种执行模式互不相容——LLM server 深耕自回归调度与 KV 管理，扩散栈深耕去噪与并行生成，都没给跨引擎流水线留控制面，生产只能 ad-hoc 拼接
- 单 orchestrator 负责请求准入、阶段推进、流式输出解复用；stage 副本池按阶段隔离算力；重负载（音频/图像张量）走数据面 connector，不挤控制面
- 会话导向控制面向长寿命双工、世界模型、机器人工作负载；对外暴露 OpenAI 兼容与 OpenPI 两套 API，覆盖 omni/TTS/图像视频/世界模型/机器人/双工六类负载

💡 **关键数据**: 评测构建在多模态 nightly CI 的 H100 上（TTS 与 MiniCPM-o 场景用 H200），重点负载为 Qwen3-Omni

🔗 **樱桃的调度视角**: 多阶段流水线本质是「异构 DAG 工作流调度」——TTS 偏访存、扩散偏算力，各 stage 资源画像完全不同，stage 副本池就是可独立扩缩容的调度单元。Master 要在一套 GPU 池上混部 TTS+扩散+LLM 时，按 stage 划资源池比整机独占的利用率高得多，而且天然适配 Volcano 的 DAG 作业语义喵。

### 4. 🧩 CoMoE：没有 NVLink 的消费级 GPU 跑 MoE 推理，把主机内存变成路由枢纽

**原文标题:** Democratizing MoE inference on commodity GPUs with CoMoE
**来源:** arXiv | 2026-10-07（提交）
**链接:** http://arxiv.org/abs/2610.09424

🎯 **一句话精髓**: MoE 的专家并行依赖 NVLink 级 P2P 互联，而消费级 GPU 只有主机中介的弱 PCIe——CoMoE 反手把 host 升级为主动路由枢纽重写 token dispatch/combine 通信路径，RTX 5090 上吞吐最高提升 1.46 倍，以 A800 约 23.4% 的硬件成本逼近其 NVLink 性能。

🔧 **技术栈**: MoE / 专家并行 (EP) / host-centric routing / host-backed token multicast / host staging buffers / PCIe / RTX 5090

📐 **架构/方法亮点**:
- 核心洞察：消费级平台的星型、主机中介拓扑不是缺陷而是机会——与其绕不开主机，不如就在主机上路由，从根本上削减通信量并消除全局同步停顿
- Dispatch 侧：host-backed token multicast——共享 token 只写主机一次再分发，消除出口方向的传输冗余
- Combine 侧：用 host staging buffer 做细粒度、token 级聚合，替代刚性全局同步，缓解 straggler（慢节点）拖垮整组的问题

💡 **关键数据**: RTX 5090 上推理吞吐最高 1.46×；硬件成本约为 NVLink 方案（A800）的 23.4%

🔗 **樱桃的调度视角**: 这给「非对称硬件池」调度提供了新选项——没有高端互联的老卡/消费卡节点不再是 MoE 的二等公民，调度器打亲和性标签时应纳入「互联拓扑」维度而不只是卡型号。Master 手里若有闲置 4090/5090 节点想跑开源 MoE（DeepSeek/Qwen 系），这个方案值得实测喵。

### 5. 📋 CNCF：NIS2/DORA 合规别挂在安全团队看板上，把「工件」挂进 sprint

**原文标题:** Who owns NIS2 and DORA on a Kubernetes platform team
**来源:** CNCF Blog (Member Post) | 2026-10-09
**链接:** https://www.cncf.io/blog/2026/10/09/who-owns-nis2-and-dora-on-a-kubernetes-platform-team/

🎯 **一句话精髓**: 欧洲平台团队的通病是把监管条款当工单丢给安全团队，三个 sprint 后集群纹丝不动——解法是「可追溯链」：风险/法务/安全负责把条款解释成控制问题与证据定义，平台团队负责把工件（audit policy、准入策略、SBOM）做进 sprint 并常态化运营。

🔧 **技术栈**: NIS2 Article 20/21/23 / DORA Article 5/9/17/19/28 / Kubernetes audit policy / Kyverno / OPA Gatekeeper / Pod Security Admission / Harbor + Sigstore + in-toto / OpenBao + External Secrets Operator + SPIFFE/SPIRE + cert-manager / Falco + Fluent Bit + OpenTelemetry + Prometheus / SBOM / Backstage

📐 **架构/方法亮点**:
- 两种失败模式互相喂养：安全成为瓶颈 → 团队绕道（break-glass kubeconfig、未经评审的 sidecar、目录外 registry）滋生影子基础设施；平台侧习得性无助 → 为赶发布关掉 admission policy，出事无人认领
- 责任锚点其实在管理层：NIS2 第 20 条与 DORA 第 5 条把 ICT 风险管理责任放在管理机构（可被追责、需受训），CISO 头衔只是指派链中的一个角色——「管理机构不会去 patch containerd」，真空地带正是多数合规计划死掉的地方
- 工件-条款映射表（节选）：加固镜像目录与重建流水线（Harbor/Sigstore/in-toto）↔ Art 21(2)(d)(e)；审计与入口日志进 SIEM（audit policy/Fluent Bit/Falco）↔ Art 21(2)(b)；准入策略（Kyverno/Gatekeeper + PSA，例外写成会过期的对象而非 Slack 消息）↔ Art 21(2)(f)(i)；CI 生成并留存 SBOM ↔ DORA Art 28；事件 runbook + 24 小时事实包 ↔ NIS2 Art 23（24h 早期预警、72h 正式通报）

💡 **关键数据**: 审计期硬指标：NIS2 要求 24 小时早期预警 + 72 小时内正式通报；合格工单的标准是「点名工件、链接控制问题、写明证据、有能把它做完的负责人」——「Security can write the policy. Security cannot merge the Helm chart.」

🔗 **樱桃的调度视角**: 「条款→控制问题→工件→常态化运营」这套映射对国内等保/数据安全合规同样适用。Master 的平台团队可以把 Kyverno 策略、审计日志保留期、SBOM 流水线当成调度器之外的平台一等公民维护——合规证据是持续产出物，不是审计前三天的消防演练喵。

### 6. 🏛️ InfoQ：用 AI 编码智能体守护架构的五种方法——描述目标，别描述实现

**原文标题:** 利用 AI 代码智能体优化软件架构的五种方法
**来源:** InfoQ 中文 | 2026-10-11
**链接:** https://www.infoq.cn/article/soRObi5sjdTTUM95zLJK

🎯 **一句话精髓**: AI 编码快到容易失控，架构是第一个失守的层——只喂功能需求不会得到合理架构，必须把可衡量的质量属性需求（QAR）与权衡显式喂给智能体，再用测试验证；文章给出记录遗留服务、修复架构缺陷、安全审计、提供架构基础、生成可测试 MVA 五种方法。

🔧 **技术栈**: AI 编码智能体 / QAR（质量属性需求）/ DDD 边界检查 / 数据流追踪与安全审计 / MVA（最小可行架构）/ 架构变更案例 / GitHub 模板与技能

📐 **架构/方法亮点**:
- 五法速览：① 梳理遗留服务的数据流与系统设计、扫缺陷、按需重构（消除新架构的关键风险）；② 找 API 设计缺陷与 DDD 边界越界（如服务层直接摸其他领域的内部状态）；③ 安全审计——追踪数据流、跨文件找复杂逻辑缺陷、生成压力测试脚本、产出修复补丁，配三道闸：只读授权、封闭网络、强制人工评审
- 反直觉要点：提示词应「描述目标 + 约束 + 验证方式」而非直接指定实现方案——这会倒逼团队把隐性架构需求显式化、可落地、可测试
- MVA 纪律：最小可行架构必须包含证明 QAR 与功能需求同时满足的全部代码，生成后用可量化测试评估，扩展成本用「架构变更案例」预先评估

💡 **关键数据**: 实战示例：npm 包漏洞评估产出影响分析报告——4 个安全告警中更新 2 个包、替换 1 个包、判定 1 个误报保留；文中判断「编码变简单了，但创建需求变得更难」

🔗 **樱桃的调度视角**: 「只喂功能需求，架构必失守」对平台工程同样成立——Master 让 AI 写 Operator/控制器时，把调度语义（亲和性约束、PDB、驱逐行为）当 QAR 写进提示词并用 KubeKind 集成测试验证，比事后 review YAML 靠谱得多，正好呼应 Uber 用 KubeKind 捕获竞态的做法喵。

### 7. 🧰 Agent = Model + Harness：从一个下午的 Demo 到生产级 Agent 差的那一层

**原文标题:** 从 Demo 到生产：AI Agent 缺的到底是什么？
**来源:** InfoQ 中文 | 2026-10-09
**链接:** https://www.infoq.cn/article/PLEWse6sEviMN99iLE93

🎯 **一句话精髓**: 生产级 Agent 的稳定在线、安全、成本控制、可观测能力几乎都不来自模型，而来自围绕模型的 Agent Harness——记忆、工具访问、模型路由、护栏、成本控制、trace；文章拆解 Harness 的开发/运维两大组成，以及从 Harness-as-a-Service 到自管技术栈的选型谱系。

🔧 **技术栈**: Agent Harness / 记忆管理 / 工具访问控制 / 模型路由 / 护栏 / 成本控制 / trace 可观测 / Harness-as-a-Service

📐 **架构/方法亮点**:
- 公式化定义：Agent = Model + Harness——说法今年才流行，但把工具接起来、反复调 Prompt、补重试和日志这些工作早就在做，变化在于它被当作独立工程层对待
- 两大组成：开发侧（记忆/工具/编排）与运维侧（安全/成本/可观测）；选型谱系从完全托管的 Harness-as-a-Service 到完全自主管理，取决于团队规模与合规要求
- 用两种方式（托管 vs 自管）各实现同一个 FinBot Agent，逐项对比同样能力如何分别落地——「Demo 一个下午就够，生产完全是另一回事」

💡 **关键数据**: 生产底线四件套：稳定在线、足够安全、成本可控、可观测（出问题能翻 trace 定位）——每一项都不是模型自带能力

🔗 **樱桃的调度视角**: Harness 里的「模型路由」就是推理流量的调度器（按成本/能力/负载选模型），与今天的 llm-d Router、vLLM-Omni 是同一件事在不同层的投影。Master 搭 Agent 平台时，路由、护栏、配额这些 Harness 组件可以直接复用推理网关的调度语义，别再造一套平行体系喵。

## 📓 樱桃的今日学习总结

1. **「意图与执行分离」是大厂控制面的共同选择** — Uber 用 ServiceScale CRD 分离扩缩容意图与执行，llm-d 把路由决策（EPP）与流量转发（Envoy）分离，vLLM-Omni 把编排（orchestrator）与执行（专用引擎）分离。多写入者系统里，先把「谁想要什么」物化成可查询的状态（CRD/ext-proc 信号），并发与排障问题才有解——私有脚本里堆 if-else 只会把故障转移的回归扩散到整个部署路径。
2. **推理基础设施正在「按执行模式」重新划分调度单元** — P/D 分离（llm-d）、stage 副本池（vLLM-Omni）、host 枢纽路由（CoMoE）的共同点：不再把「一个模型一个 Deployment」当作调度单位，而是按流水线阶段、通信拓扑切分资源池。调度器必须跟着执行模式走，亲和性标签里「互联拓扑」和「阶段画像」会变得和「卡型号」一样重要。
3. **「显式化」是 AI 时代工程能力的分水岭** — NIS2 把条款显式化为可运营的工件、五种方法把架构需求显式化为 QAR、Harness 把运维能力显式化为组件。AI 越强，人的价值越集中在把隐性要求写成可验证的目标——这句话对集群调度同样成立：调度策略不显式化，就永远在被「临时 kubectl edit」侵蚀。

📌 **樱桃小贴士**: 本周 GitHub Go 周趋势榜被 AI 基础设施刷屏——llm-d/llm-d-router（推理路由）、docker/docker-agent（Docker 官方 Agent Builder & Runtime，4.4k stars）、google/gvisor、ollama/ollama 同榜。Go 生态正在成为 AI Agent 与推理网关的主场，Master 招聘/选型时可以把 Go 的 K8s 控制面经验当作迁移 AI Infra 的杠杆喵。
