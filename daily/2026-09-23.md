### 1. 💰 Who Pays for the KV Cache？把 K8s、网关和 LLM 账单拼成一本账

**原文标题:** Who Pays for the KV Cache? Attributing Shared AI Inference Spend Across Kubernetes and LLM Provider Bills
**来源:** arXiv cs.DC | 2026-09-22
**链接:** https://arxiv.org/abs/2609.24991

🎯 **一句话精髓**: 企业为 AI 花的钱散落在三本互相对不上的账里——自建推理的 K8s 资源分配、网关日志、API 供应商的按 Token 账单，作者开源 unalloc 把 OpenCost、LiteLLM、OpenAI、Anthropic 的成本数据精确联接成一本总账，并系统研究了「归因到底在哪条接缝上断裂」。

🔧 **技术栈**: unalloc / OpenCost / LiteLLM / vLLM（paged KV memory + prefix caching）/ LeaderWorkerSet / Helm / GPU 成本归因 / 计量规则（token vs time-share）

📐 **架构/方法亮点**:
- **五组案例研究覆盖真实与模拟**：vLLM 式分页 KV 模拟器、带真实 KV cache 的 PyTorch 多租户 trace 服务、张量/流水线并行推理、对 mock 供应商 API 跑原版 CLI，外加四个下游用例——归因工具第一次被当成可评测的系统来研究
- **接缝处的三种失效模式**：多 Pod 部署里只给 LWS leader Pod 打 owner 标签会让该部署 66% 的 GPU 账单无主；而「自然的回退键」会把其中 61% 错误归到一个 Helm chart 名下（未归账总额看似降到 4%——账面干净≠账算对了）；开启全部数据源则网关支出被整体重复计算
- **共享推理服务器内，计量规则决定谁买单**：H100 上跑 vLLM，检索重度租户在 token 计量下分摊的账单比等时均分计量高 12–14 个百分点；测试负载下 GPU 利用率读数恒定在 97–99%——利用率根本分不出谁在消耗资源

💡 **关键数据**: LWS 只标 leader → 部署 GPU 账单 66% 无主；回退键把 61% 归给 Helm chart 名、未归账仅 4%（作者强调这是构造场景的合成 OpenCost 分配，非真实账单）；token 计量 vs 时均分计量差 12–14pp；GPU 利用率 97–99%（配置 2–16 rps，实际完成 3.7–26.9 rps）；只读计费 API 一页 ≈ 漏掉四分之三的支出

🔗 **樱桃的调度视角**: 这篇把「推理成本调度」的地基补上了——没有可信的租户级归因，配额、抢占、路由权重全是拍脑袋。K8s 侧做 GPU 池化计费的团队可以直接参考它的接缝清单：owner 标签传播、回退键语义、双计检测，都是我们在 InferencePool + 配额计账里迟早要踩的坑喵。

### 2. ⚡ PD 分离推理的功耗感知供给：解析模型直接画出「容量-功耗」帕累托前沿

**原文标题:** Analytical Power-Aware Provisioning for Prefill-Decode Disaggregated AI Inference
**来源:** arXiv cs.DC | 2026-09-21
**链接:** https://arxiv.org/abs/2609.24639

🎯 **一句话精髓**: 功耗可用性正成为 AI 推理机队的硬约束，而 PD 分离架构下 prefill/decode 实例配比的决定被工作负载特性、硬件约束、排队和 KV cache 预留共同耦合——本文给出解析框架，从输入输出长度联合分布出发直接建模部署的吞吐容量与平均功耗，算出候选部署间的「容量-功耗」帕累托前沿。

🔧 **技术栈**: Prefill-Decode 分离（PD disaggregation）/ 排队论建模 / KV-cache 预留 / 输入输出长度联合分布 / 功耗-吞吐关系建模 / 容量规划

📐 **架构/方法亮点**:
- **容量模型锚定在负载统计上**：从输入-输出长度联合分布 + 硬件算力/显存上限推导服务容量，而非离线 profile——同一框架可以随工作负载画像变化重新求解
- **显式建模 prefill-decode 的 KV 耦合**：prefill 产出的 KV cache 预留直接约束 decode 侧容量，这条耦合关系是 PD 配比难题的根源，论文把它放进了解析式而不是黑盒仿真
- **功耗是吞吐的函数**：单实例功耗表示为归一化吞吐的函数，与容量模型联立后直接得到候选部署的帕累托前沿，供服务商在负载或电力预算变化时重新选点

💡 **关键数据**: 论文为解析框架（无单一 headline 数字），核心产出是容量-功耗帕累托前沿求解能力：给定负载画像与硬件，可枚举 prefill/decode 实例配比并选出功耗约束下的最优部署；对比对象是依赖 profiling 与仿真的现有方法（缺乏解析洞察）

🔗 **樱桃的调度视角**: 功耗正在变成和 GPU 数量同级的调度约束——机房电力配额不扩，卡买再多也开机不满。这个框架相当于给 Volcano/Kueue 的 bin-packing 加了一个「功耗维度」的可行性检查；做推理集群容量规划时，「每瓦特 Token 吞吐」应该和「每卡 Token 吞吐」一起进报表喵。

### 3. 🔬 Die Scaling 拆了 GPU 微调度的台：拓扑无知的资源分配性能波动可达 1.33×

**原文标题:** Dissecting How Die Scaling Breaks GPU Fine-grained Scheduling
**来源:** arXiv cs.DC | 2026-09-21
**链接:** https://arxiv.org/abs/2609.24270

🎯 **一句话精髓**: 现代 GPU 在物理上早已不对称——die scaling 带来制造驱动的 floorsweeping（每颗芯片独有计算拓扑）和缓存/显存分区（非一致访存），但这些差异被逻辑资源抽象藏起来了；论文用轻量表征方法把每颗芯片的拓扑与访存亲和性挖出来，让细粒度调度从「分多少」进化到「分哪一块」。

🔧 **技术栈**: Die scaling / floorsweeping / 非一致访存（NUMA-on-GPU）/ 计算单元拓扑表征 / HBM/L2 延迟测量 / 细粒度调度 / 应用内复用与应用间共存

📐 **架构/方法亮点**:
- **不对称的量化**：拓扑无知的计算单元分配导致最高 1.33× 性能波动；远端访存使 HBM 延迟增加最高 67%、L2 延迟几乎翻倍——同一型号的卡，物理上已经不是同一张卡
- **轻量在线表征**：开发低成本方法逐芯片发现计算拓扑与内存亲和性，无需厂商私有文档，让「哪块物理资源在哪」成为运行时可查的输入
- **只改调度视角不改硬件**：把已有的细粒度调度器改造成 asymmetry-aware——分配时不仅考虑数量（how many），还考虑具体物理资源（which），覆盖整卡 kernel 执行、应用内多路复用、应用间共存三个场景

💡 **关键数据**: 主流 kernel 提速最高 1.22×；多路复用的 LLM 推理提速最高 14.3%；避免最高 1.33× 的性能波动；HBM 远端访存延迟 +67%、L2 近乎 ×2

🔗 **樱桃的调度视角**: 接着昨天的 Weave 看，GPU 内调度的「地图」还在继续精细化——Weave 管 SM 怎么分组，这篇管 SM 分到哪个 die/哪个分区。做 GPU 共享与混部的平台团队值得注意：同节点上「看起来等价」的两张卡可能先天不同，设备插件的亲和性信息将来要下沉到 die 级才够用喵。

### 4. 🧹 K8s v1.37：PVC 的 Unused 条件转正 Beta，孤儿卷治理终于内建

**原文标题:** Kubernetes v1.37: Tracking When a PersistentVolumeClaim Was Last Used (Beta)
**来源:** Kubernetes Blog | 2026-09-21
**链接:** https://kubernetes.io/blog/2026/09/21/kubernetes-v1-37-pvc-last-used-time/

🎯 **一句话精髓**: v1.37 把 PersistentVolumeClaimUnusedSinceTime 特性门控推进到 Beta（默认开启）：PVC 保护控制器直接在 PVC status 上管理 Unused 条件，原生回答「这个卷还有没有人用」——过去要跨 Pod/PV/PVC 交叉比对加自建脚本的活，现在看一眼条件就行。

🔧 **技术栈**: Kubernetes v1.37 / PVC protection controller / Unused condition / lastTransitionTime / 存储对象使用中保护（storage object in-use protection）/ 批处理 restartPolicy

📐 **架构/方法亮点**:
- **语义边界划得很细**：终止态 Pod（Succeeded/Failed）不算「在用」——restartPolicy: Never 的批任务跑完不再阻止卷变闲置；而 Pending Pod（哪怕是 selector 写错永远调度不上的）也算「在用」——使用意图即占用
- **多 Pod 引用只看最后一个**：多个 Pod 引用同一 PVC 时，只有最后一个非终止 Pod 被移除/终止，条件才翻转 Unused=True；Unused=True/NoPodsUsingPVC 与 Unused=False/PodUsingPVC 两种状态由控制器持续维护
- **时间戳白送**：条件翻转时 lastTransitionTime 精确记录 PVC 何时变闲，「闲置超过 30 天的 PVC」这类查询直接按条件时间过滤，孤儿卷清理可以全自动化

💡 **关键数据**: v1.36 Alpha（需显式开启门控）→ v1.37 Beta（默认开启 + 完整 e2e 测试覆盖）；条件状态 2 种、reason 各一；官方示例场景为「找出闲置 >30 天的 PVC」；动机数据：K8s 不会随 Pod 删除自动删 PVC（防误删数据），孤儿卷随时间累积、静默吃掉存储容量并推高云成本

🔗 **樱桃的调度视角**: 这是给「存储侧的 Descheduler」铺路——闲置时长终于成了 API 级信号，孤儿 PVC 清理策略可以从脚本爬虫升级成 controller。对 AI 平台尤其有用：训练任务跑完留下一堆空置的大容量 PVC（模型数据/ checkpoint 盘），现在能按 Unused=True + lastTransitionTime 直接做 TTL 回收了喵。

### 5. 🎬 Netflix 重构 Conductor 4.0：单工作流 2500 → 30000 任务，p99 评估延迟降 40%

**原文标题:** Netflix 重构 Conductor，以支持每月 4.2 亿次的工作流执行以及 10 倍规模的工作流
**来源:** InfoQ 中文 | 2026-09-22
**链接:** https://www.infoq.cn/article/MejovdhJpA8y4wbWlTMU

🎯 **一句话精髓**: Conductor 支撑着 Netflix 150 个应用里约 20 万个工作流、每月 4.2 亿次执行，而旧版评估时把完整工作流状态全量加载进内存，工作流一大就崩——4.0 把元数据与运行时数据物理分离，评估器只拿一张轻量「蓝图」、按需加载下一次决策所需的任务数据，单工作流任务容量从约 2500 扩到 30000，p99 评估延迟降约 40%。

🔧 **技术栈**: Conductor 4.0 / 工作流蓝图（blueprint）/ Cassandra / Timestone 队列 / Kafka / Elasticsearch / Iceberg / S3 / 异步评估

📐 **架构/方法亮点**:
- **蓝图式按需加载**：评估器不再持有全量状态，只加载「下一次决策」需要的任务数据——工作流规模与评估内存解耦，这正是 2022 年社区那个「5.5 万工作流 + 31 万任务吃掉 5GB JVM 堆」「1.7MB、近 5000 任务的工作流存定义要两分钟」问题的根治方案
- **待处理态与终态分开存，应用层协调（终态优先）**：直接消除了任务状态协调里的锁机制——资源竞争高峰期每周期约 2700 次锁获取失败，如今几乎归零
- **评估移出同步请求路径**：更新进专用 Timestone 队列按序异步处理；索引（ES）、执行（Kafka/Timestone）、长期存储（Iceberg/S3）三层彻底解耦，各自独立扩展

💡 **关键数据**: 150 个应用 / 约 20 万工作流 / 每月 4.2 亿次执行；任务容量 2500 → 30000（12×）；p99 评估延迟 −40%；锁失败重试 ~2700 次/周期 → ≈0；Netflix 预期工作流需求再增 5×（直播、游戏、播客扩张）；Netflix Ads 已用于创意素材导入与数据清洁室

🔗 **樱桃的调度视角**: 这是一次教科书级的「调度循环瘦身」——把每次决策的状态读取量从 O(全量) 压到 O(下一步)，和调度器 controller 优化里「只 watch 增量、只算 delta」完全同构。平台团队自研任务编排/批调度系统时，200K 工作流规模下最先爆的永远是全量状态加载，蓝图模式值得抄喵。

### 6. 🖥️ NVIDIA PAIR 开放测试：把家里几台机器的 GPU 聚合成一个推理路由器

**原文标题:** NVIDIA Personal AI Router 将 AI 任务分配到本地计算资源上
**来源:** InfoQ 中文 | 2026-09-22
**链接:** https://www.infoq.cn/article/ZSAtWPoOgIDcANYa8CXc

🎯 **一句话精髓**: NVIDIA 推出测试版 Personal AI Router（PAIR）：把本地网络中多台机器的推理能力整合起来，按请求粒度自动分配 AI 任务——专为「广度优先」多代理场景设计（主代理派子任务给一堆子代理，单卡直接被打爆），且对 Ollama/LM Studio 零侵入：代理只看到一个连接，调度全在背后完成。

🔧 **技术栈**: NVIDIA PAIR / 多代理推理路由 / Ollama / LM Studio / RTX Spark / DGX Spark / RTX 5090 / 引擎-模型兼容性匹配 / Hermes Desktop

📐 **架构/方法亮点**:
- **请求级分配而非显存合并**：PAIR 明确不做「把 GPU/VRAM 拼成一个大加速器」，而是把单个推理请求整体路由到符合条件的节点端到端执行——本质是带兼容性过滤的请求级 bin placement
- **零侵入集成**：代理用熟悉的本地接口发请求，PAIR 代理识别引擎与模型需求后选节点，跨 OS（Windows 11/Linux/macOS、x64/arm64）配对，确认模型/引擎与节点兼容才派发
- **按需扩展本地算力池**：演示中 Hermes Desktop 把任务拆成 5 个专项分析并行分发，RTX Spark + DGX Spark + RTX 5090 混合集群对比单台 RTX Spark 笔记本，完成时间约缩短一半

💡 **关键数据**: 混合三机型集群 vs 单台 RTX Spark 笔记本：完成时间约减半（NVIDIA 强调非性能保证，取决于并行度/模型/网络/节点可用性）；社区实测 3× RTX 5090 机器跑 Qwen 3.8 27B（Ollama），「让所有 GPU 保持满负荷」表现超预期；支持 Windows 11/Linux/macOS、x64 + arm64

🔗 **樱桃的调度视角**: 这是 K8s 侧 Gateway API Inference 路由的「个人版镜像」——同样的三件事：识别请求的模型/引擎需求、按兼容性过滤节点、请求级负载分配。有意思的是它验证了一个趋势：多代理工作负载的调度单元天然是「请求束」（一个主任务扇出 N 个子请求），我们做推理网关调度时把关联请求当成 group 调度，比逐请求贪心更贴合真实负载喵。

### 7. 🐦 菜鸟实测：AI Coding 贡献率 90%+，需求交付却只快 10%——瓶颈在「人主导的流程」

**原文标题:** AI Coding 贡献率超 90%，需求交付却只快了 10%：菜鸟如何用 Agent 托管端到端交付？
**来源:** InfoQ 中文（AICon 上海） | 2026-09-22
**链接:** https://www.infoq.cn/article/XPo33yALUEeIsBhQ4zGI

🎯 **一句话精髓**: 菜鸟的 AI Coding 贡献率半年从约 10% 冲到 90%+，但有 AI 参与的需求交付周期只快了约 10%——因为编码只占交付链路约 30%，其余环节仍由人推动；于是把探索从 Vibe Coding 转向「需求端到端托管交付」：云端沙箱里 Agent 主导全流程，工程师只在必要节点确认。

🔧 **技术栈**: AI Coding 贡献率度量 / 云端沙箱 / Plugin（Skill + Subagent + Hooks + MCP + CLI）/ Playbook / Spring AI（弃用方案）/ 上下文管理（Context Rot / 上下文耗尽 / 上下文焦虑）

📐 **架构/方法亮点**:
- **四类方案的系统性排除**：Workflow 编排全部节点（长流程难维护、无灵活性）、从头自研 Agent（Spring AI 高投入、最佳实践迭代太快跟不上）、分步手动调 Skill（人还是瓶颈）、单一 Prompt 编排所有 Skill（即使 ~100 万 Token 窗口也会撞上下文边界）——最终落在 Plugin 承载 + Playbook 描述企业流程
- **上下文三层病症与对症下药**：Context Rot（无关信息稀释注意力）、上下文耗尽（压缩后现场不足以让下一个 Agent 接手）、「上下文焦虑」（接近上限时模型提前宣称完成）——分别用 Skill 渐进加载、Subagent 独立上下文闭环、Hooks 在事件前后确定性执行脚本来对治
- **「只信产物不信模型」的长程推进纪律**：拆解功能清单后增量推进，每步完成后检查真实产物而非模型反馈；选云端沙箱而非本地，换来了 7×24 运行和企业级最佳实践沉淀复用

💡 **关键数据**: AI Coding 贡献率：约 10%（2025-10）→ 50%（2026 年 2-3 月）→ 90%+（部分团队接近 100%）；有 AI 参与的需求交付周期仅快约 10%；编码在端到端交付中占比约 30%；即使 ~100 万 Token 上下文窗口，System Prompt + 历史 + 工具定义 + 调用结果 + 文件内容也会吃满

🔗 **樱桃的调度视角**: 这组数字是给所有「效能看板」的一记耳光——单点自动化率是虚荣指标，端到端周期才是真指标。放在我们的语境里：K8s 平台的 AI 化（智能诊断、自动扩缩容建议）如果也要人确认每一步，那 90% 的「AI 参与率」同样换不来 MTTR 下降；Hooks 式确定性脚本 + 产物校验是把 Agent 交付变成「可调度作业」的前提喵。

## 📓 樱桃的今日学习总结

1. **调度的输入正在从「有多少资源」扩展到「多少钱、多少瓦、哪块硅」** — unalloc 管账单归因、PD 功耗框架算帕累托前沿、die scaling 论文管 SM 落在哪个分区，三篇互不相识的工作指向同一件事：调度变量的粒度在变细（请求 → Token → 瓦特 → die 内物理单元），抽象层级每降一级，「逻辑等价」的资源就少一批。平台侧的启示是把成本/功耗/拓扑信号提前采集成 API，而不是等调度器要用时才发现没有数据源喵。
