### 1. 📦 Kubeflow 遇上 Cilium：调试 K8s 上 60% 闲置 GPU 的「跨区静默故障」

**原文标题:** When Kubeflow meets Cilium: Debugging 60% idle GPUs in Kubernetes
**来源:** CNCF Blog | 2026-07-23
**链接:** https://www.cncf.io/blog/2026/07/23/when-kubeflow-meets-cilium-debugging-60-idle-gpus-in-kubernetes/

🎯 **一句话精髓**: 分布式训练任务全部 Pod 健康、却有一半 GPU 闲置——根因是 K8s 调度器拓扑无感 + Cilium 网络策略拓扑感知，两个「各自正确」的系统合在一起把训练协调器和工作组放进了互相不可达的可用区。

🔧 **技术栈**: Kubernetes 调度器 / Kubeflow / Cilium / CiliumNetworkPolicy / NCCL AllReduce / nodeAffinity / topologySpreadConstraints / podAffinity / Prometheus / Grafana / kind

📐 **架构/方法亮点**:
- **同一根因三种症状**: 硬阻断（zone 边界网络策略直接拒连，训练永不启动，秒级可见）；跨区延迟（无硬阻断仅距离，NCCL AllReduce 每步付跨区 RTT，吞吐悄降 30–60% 且无报错）；跨 AZ 出口成本（流量跨可用区只体现在云账单上，天级才察觉）
- **不碰 CNI、不打补丁的修复**: 只在 workload spec 上加几行 YAML——nodeAffinity 把整组钉到 GPU zone、topologySpreadConstraints 把协调器与 worker 共置、toleration 让协调器能落到 GPU taint 节点；或用 podAffinity + zone topology key 按「关系」共置，跨集群可移植
- **可观测先行**: GPU 利用率与 Pod-zone 指标在 Prometheus/Grafana 里秒级暴露问题，没有它们可能要排查数天

💡 **关键数据**: 共置后 GPU 利用率从约 **40% 升到约 85%**；跨区延迟场景吞吐静默下降 **30–60%**；作者来自 Adobe 两位 Golden Kubestronaut（Ramkumar Nagaraj、Bingi Narasimha Karthik），附可复现 lab（https://github.com/ram2valar/kubeflow-cilium-lab）与 KubeCon India 2026 演讲录像

🔗 **樱桃的调度视角**: 这是 Master 做 GPU 调度最该收藏的一个 case——「调度器看不到 CNI 的拓扑意见」是一整类故障的源头。做推理调度时，网络策略的 zone 边界必须作为调度约束输入（topologySpreadConstraints + 亲和），否则就是花钱让 GPU 空转喵～

### 2. 📦 NVIDIA 把 GPU 调度推进 K8s 主线：DRA 上游 + KAI Scheduler 进 Sandbox

**原文标题:** The future of AI is community driven and open
**来源:** CNCF Blog | 2026-07-23
**链接:** https://www.cncf.io/blog/2026/07/23/the-future-of-ai-is-community-driven-and-open/

🎯 **一句话精髓**: NVIDIA 以 CNCF 管理委员会身份宣布，把 GPU 动态资源分配（DRA）驱动、KAI Scheduler、AI 一致性认证全部贡献进 K8s 上游与社区治理，要让 GPU 工作负载在 K8s 上「像普通工作负载一样日常化」。

🔧 **技术栈**: Kubernetes SIG-Node / DRA（Dynamic Resource Allocation）/ MIG / Multi-Node NVLink / ComputeDomains / KAI Scheduler / gang scheduling / Dominant Resource Fairness / Kubernetes AI Conformance Program / NVIDIA GPU Operator / Container Toolkit

📐 **架构/方法亮点**:
- **DRA 驱动进 SIG-Node**: 作为厂商中立的 DRA API 参考实现，用「实时按需分配」替代「调度时静态分配」，新增 MIG 设备共享（alpha）、ComputeDomains 让 GPU 跨节点经 Multi-Node NVLink 安全共享内存——一个大 multi-GPU 任务按需拿到所需加速器而非占着静态预留
- **KAI Scheduler 进 CNCF Sandbox**: 面向大 AI 集群的调度器，核心是带预调度模拟的 gang scheduling（避免无谓驱逐）、带 DRF 的分层队列（多团队集群公平）、异步绑定——已在 **1 万+ GPU** 集群上跑过
- **认证体系扩张**: K8s AI Conformance Program 从 18 涨到 31 个认证平台，v1.35 新增 agentic workflow 支持与面向推理 serving 的 in-place pod resizing

💡 **关键数据**: CNCF 2025 年度调查——**82%** 容器用户在生产跑 K8s、**66%** 托管生成式 AI 的组织用 K8s 管推理，但仅 **7%** 每日部署模型、**47%** 只是间歇部署；NVIDIA 承诺未来 3 年向 CNCF 投 **400 万美元**让项目在真实 GPU（而非模拟器）上跑 CI；作者 Erin A. Boyd（NVIDIA Senior Director、CNCF 管理委员会成员）

🔗 **樱桃的调度视角**: 这条几乎就是 Master 工作的技术路线图——DRA 替代静态 GPU 分配、KAI 的 gang scheduling + DRF 分层队列、ComputeDomains 跨节点 NVLink 共享内存，每一个都直击「共享集群上多租户 AI 平台」的调度痛点。从「静态独占」到「按需切分」是这波 K8s GPU 调度的核心范式转移喵～

### 4. 📦 Confidential Containers 升级 CNCF 孵化：用 TEE 给 K8s 上的 AI 推理「数据在使用中」上锁

**原文标题:** Confidential Containers becomes a CNCF incubating project
**来源:** CNCF Blog | 2026-07-22
**链接:** https://www.cncf.io/blog/2026/07/22/confidential-containers-becomes-a-cncf-incubating-project/

🎯 **一句话精髓**: Confidential Containers 获 CNCF TOC 投票通过成为孵化项目，基于硬件 TEE 在计算过程中加密内存数据，让敏感工作负载能在第三方基础设施上运行而基础设施运营商也无法访问——并正在被集成进 KServe 做机密 AI 推理。

🔧 **技术栈**: TEE（Trusted Execution Environments）/ Kata Containers / Intel TDX / AMD SEV-SNP / Trustee（远程证明服务）/ Kyverno / KServe / Helm / Hardware Abstraction Layer

📐 **架构/方法亮点**:
- **四大组件**: Confidential Containers Pods（把硬件安全抽象成标准 K8s Pod，无需改容器即可跨 TEE 部署）、Trustee（可扩展的远程证明服务，验证 TEE 节点与工作负载完整性后才放行密钥）、Helm Charts & Controllers（跨异构 TEE 的生命周期管理）、Hardware Abstraction Layer（对接 Intel TDX 与 AMD SEV-SNP，不锁定单一云厂商硬件）
- **机密 AI 推理落地**: 正被集成进 KServe，把「数据在使用中」保护对齐到 AI 推理 serving 场景，目标是生产级机密 AI 推理
- **治理中性化**: 2021 年由 Red Hat、Intel、IBM 联合发起，经 Kata Containers 运行时集成进 K8s 生态；进入孵化后获得中立治理以设定「隐私保护基础设施」行业标准

💡 **关键数据**: 核心仓库 **1000+** GitHub stars、跨 26 个仓库组 **1200+** 合并 PR、**1500+** 历史/活跃 issue、**150+** 活跃贡献者、**15+** 累计发布；支持方含 Microsoft Azure、Intel、AMD、IBM、NVIDIA、阿里巴巴、Red Hat；同期孵化项目名单里还有 **Volcano**（AI 调度）

🔗 **樱桃的调度视角**: 对 Master 而言，机密容器 + KServe 的组合意味着「推理 Pod 的模型权重与 prompt 可以在内存里加密」——做多租户共享 GPU 推理平台时，这是防「隔壁租户/云厂商偷看权重」的关键一环，和 DRA 的设备共享是互补的两条线喵～

### 5. 📦 Linkerd 2.20：感知限流负载均衡 + 控制平面内存最高降 85%

**原文标题:** Linkerd 2.20 Delivers Smarter Traffic Management and Dramatic Efficiency Gains
**来源:** InfoQ 中文 | 2026-07-23
**链接:** https://www.infoq.cn/article/TJL8TIiuD6Cev0Ig0AAS

🎯 **一句话精髓**: CNCF 毕业项目 Linkerd 发布 2.20，新增能识别 HTTP 限流响应并自动绕开过载实例的「感知限流负载均衡」，并在 Pod 频繁创建销毁场景下把控制平面内存占用最高降 85%，继续走「轻量、低运维」路线对抗 Istio。

🔧 **技术栈**: Linkerd / Rust / mTLS / Rate-Limit-Aware Load Balancing / destination controller / OpenTelemetry / Kubernetes Gateway API / eBPF

📐 **架构/方法亮点**:
- **感知限流负载均衡**: 传统网格按延迟与实例可用性分发，Linkerd 2.20 能识别 HTTP 限流响应（而非直接失败），自动把请求暂时绕开正在主动限流的实例、调度到更健康实例，在维持吞吐的同时降低级联故障风险——尤其适合大量依赖第三方 API 的微服务
- **destination controller 重构**: 针对 K8s 调度频繁变化期间内存占用大幅下降，让更多集群资源留给应用而非基础设施组件

💡 **关键数据**: Pod 大量频繁创建销毁场景下控制平面内存占用最高降低 **85%**；Linkerd 由 Buoyant 用 Rust 开发，主打 mTLS + 流量管理 + 可观测性且避免大型网格的高资源消耗；作者 Craig Risi、马可薇

🔗 **樱桃的调度视角**: 「感知限流负载均衡」本质是网格层做了一次「应用感知的二次调度」——把限流信号反馈进流量路由。对 Master 做推理 serving 的启发是：当推理副本因 GPU 显存压力返回 429 时，网格若能感知并绕开，比单纯重试更能保护集群吞吐喵～

### 7. 📦 Cloudflare 实测：近 70% 的 BGP 路径 ORIGIN 属性被运营商私自改写

**原文标题:** BGP ORIGIN attribute manipulation and its impact on the Internet
**来源:** Cloudflare Blog | 2026-07-25
**链接:** https://blog.cloudflare.com/bgp-origin-attribute/

🎯 **一句话精髓**: Cloudflare 通过全球 BGP Anycast 实验发现，近 70% 观测路径的 ORIGIN 属性被传输运营商为抢流量而私自改写（多改为更优先的 IGP），违反 RFC4271「不应被改」的规定，呼吁在路由选择中废弃 ORIGIN。

🔧 **技术栈**: BGP / ORIGIN 属性 / AS_PATH / BGP Anycast / BGPKIT / MRT dumps / RIPE RIS / RouteViews / BMP / Local Preference

📐 **架构/方法亮点**:
- **实验设计**: 从全球 peering 点用 BGP Anycast 宣告 3 个 IPv4 + 3 个 IPv6 前缀（分别设 IGP/EGP/INCOMPLETE），确认全球传播后撤回触发 path hunting 暴露更多路径，用 BGPKIT 解析 RIPE RIS 与 RouteViews 的 MRT dumps + 本地 BMP 数据
- **改写动机与机制**: ORIGIN 在路径选择中较早被评估，传输商把对手路由的 ORIGIN 改成更优的 IGP 即可在 AS_PATH 等长时抢到流量与收入——这是一场「收入驱动的军备竞赛」，大家不等对手恢复 RFC 合规就先改写以求公平
- **呼吁废弃**: 早期评估位置使 ORIGIN 成为抢流量利器，已有过期 Internet-Draft 建议废弃；Cloudflare 主张在路由选择中弃用 ORIGIN

💡 **关键数据**: 近 **70%** 观测路径的 ORIGIN 与起源 AS 设定不同；全网路由中 **89.8%** 为 IGP、**3.5%** EGP、**6.7%** INCOMPLETE；约 **10%** 直连 peer 把 ORIGIN 改写为 IGP；分析了 **352** 个 IPv4 直连 peer 与 **315** 个 IPv6 直连 peer；James Bensley 在 RIPE 91 首次公开此现象

🔗 **樱桃的调度视角**: 这条偏网络底层，但对 Master 做多区域/多云推理出口选路有参考——BGP 属性被运营商为利益改写意味着「跨云流量路径并非你以为的最优」，做推理 serving 的多地部署与流量调度时，不能盲信 AS_PATH 与 ORIGIN，要靠主动探测与 Anycast 实测验证喵～

## 📓 樱桃的今日学习总结

1. **GPU 调度的「语义翻译」是本周主线** - NVIDIA 把 DRA 推进 SIG-Node、KAI Scheduler 进 Sandbox、ComputeDomains 跨节点 NVLink 共享内存，本质是把 GPU 从「调度时静态独占资源」翻译成「运行时按需切分、可跨节点共享」的 K8s 原生语义。Master 做推理调度，应该把 DRA + gang scheduling + DRF 分层队列当成接下来半年的核心跟踪线。

2. **「两个各自正确的系统合在一起出错」是一类高隐蔽故障** - Kubeflow+Cilium 的 GPU 闲置 case 揭示：调度器拓扑无感 + CNI 拓扑感知，会产生「健康检查全绿但 GPU 空转」的静默故障。教训是——任何拓扑感知组件（CNI、存储、GPU fabric）的意见，都必须显式作为调度约束输入，否则调度器就是在「看不见的墙」之间盲放 Pod。

3. **机密推理 + 设备共享是 AI 基础设施安全的互补双线** - Confidential Containers 进孵化并被集成进 KServe，意味着「推理时模型权重与 prompt 在内存加密」即将生产可用；它与 DRA 的设备共享组合，正好解决多租户共享 GPU 平台「既要切分 GPU、又要防邻居偷看权重」的双重诉求。

4. **多轮 Agent 的成本杠杆在「固定前缀压缩」而非换小模型** - 腾讯 CodeBuddy 把首轮 Token 从 2 万压到 2 千（-90%），核心是认识到系统提示词是每轮都要重发的固定成本。这对推理 serving 成本优化的启发是：prompt 前缀压缩 + 缓存命中率，比单纯路由到小模型更系统、收益更可持续。
