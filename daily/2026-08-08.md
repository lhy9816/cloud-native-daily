### 1. 📦 DRA 不取代 HAMi：K8s 原生 GPU 切片调度与容器内 CUDA 强制是两层

**原文标题:** Does Kubernetes DRA Replace HAMi?
**来源:** CNCF Blog | 2026-08-07
**链接:** https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/

🎯 **一句话精髓**: K8s 原生 DRA（动态资源分配）在 v1.34 GA 后能吸收 HAMi 的「分数请求编码」工作，但容器内 CUDA 调用粒度的硬性强制仍需 HAMi——二者不是替代而是分工。

🔧 **技术栈**: DRA (Dynamic Resource Allocation) / HAMi / device plugin / scheduler extender / mutating webhook / consumable capacity / CUDA

📐 **架构/方法亮点**:
- HAMi 用 3 个扩展资源表达 GPU 切片：`nvidia.com/gpu`(卡) / `nvidia.com/gpumem`(8000MiB) / `nvidia.com/gpucores`(10%)，但默认调度器只把它们当 opaque integers，并不知道 gpumem 和 gpucores 必须落在同一物理卡
- DRA 在 v1.34 GA、v1.35 默认启用，consumable capacity feature 让 pod 原生向调度器请求设备内存切片，无需 annotation，调度器真正「看得见」分数请求
- HAMi 应对策略：保留容器内 CUDA 调用粒度强制（DRA 从未设计做这个），把编码层重建在 DRA 之上，拆成 3 个仓库

💡 **关键数据**: HAMi 于 **2026-07-15** 被 CNCF TOC 接受为孵化项目；DRA **v1.34 GA**、**v1.35 默认启用**；HAMi 示例可切「8000 MiB + 10% 算力」。

🔗 **樱桃的调度视角**: 这是 Master 做 GPU 调度必读——DRA 让调度器原生理解「显存切片 + 算力百分比」，意味着未来 GPU 共享不再需要绕过 API 的 webhook/extender 旁路。但「容器内真正限制 CUDA 调用不超卖」仍要 HAMi，调度决策和运行时强制是两层。选型时：要调度器原生细粒度分配用 DRA，要硬性显存隔离用 HAMi（且 HAMi 已拥抱 DRA 重建编码层）。

### 2. 📦 微软 AKS 智能体 LLM 路由方案：语义路由 + 推理感知负载均衡，最高省 85% 成本

**原文标题:** 最高节省 85% 成本：微软公布 AI 智能体 LLM 路由方案
**来源:** InfoQ 中文 | 2026-08-07
**链接:** https://www.infoq.cn/article/HQD432MKSXMMR2UUag6P

🎯 **一句话精髓**: 微软给出 AKS 上 agent 流量路由参考架构，把「哪个模型响应 / 如何管理调用 / 哪个 GPU 副本处理」三件事解耦，用语义路由 + 推理感知负载均衡避免短请求被长 prefill 阻塞。

🔧 **技术栈**: Azure Kubernetes Service / Kubernetes Gateway API Inference Extension / agentgateway / RouteLLM / OpenAI 兼容端点 / 矩阵分解路由器

📐 **架构/方法亮点**:
- 三层解耦：RouteLLM 做语义路由（检查 prompt，预测便宜模型能否达到强模型质量，基于人类偏好数据训练的矩阵分解路由器）；agentgateway 做认证/限流/管理；Gateway API Inference Extension 做副本级负载均衡
- 点破轮询 LB 的坑：简单轮询会让生成 200 token 的请求排在繁忙 GPU Pod 上 10 万 token prefill 请求之后，附近空闲 Pod 却未被使用
- 针对 agent 工作负载而非聊天：单个 agent 任务在「规划-行动-观察」循环中发起数百次 LLM 调用，多数（填参数、是/否判断、摘要）不需要前沿模型

💡 **关键数据**: 最高节省 **85% 成本**；单 agent 任务可发起**数百次 LLM 调用**；轮询 LB 短请求排队案例：200 token 请求 vs 10 万 token prefill。

🔗 **樱桃的调度视角**: 直击 AI 推理调度的两个层次——模型级路由（RouteLLM 按任务难度分流到不同模型）和副本级调度（Inference Extension 按副本负载 / prefill 状态调度）。对 Master 的启发：GPU 推理不能只做 round-robin，要做「prefill 感知」的负载均衡，否则短请求被长上下文请求阻塞，GPU 利用率假高但延迟劣化。这正是 K8s 推理调度器（llm-d、vLLM disaggregated）要解决的核心问题。

### 3. 📦 HBM 装不下、数据搬不动：AI SSD 从静态存放进入 LLM 推理实时数据路径

**原文标题:** HBM 不够用了，AI SSD 迎来爆发前夜
**来源:** InfoQ 中文 | 2026-08-07
**链接:** https://www.infoq.cn/article/sQW5F63ZP4QMyhlWAzQi

🎯 **一句话精髓**: 当 HBM 装不下模型权重、KV Cache 持续膨胀，SSD 正从静态模型存放进入 LLM 推理实时数据路径，成为 HBM/VRAM/DRAM 之后的一层正式存储层级。

🔧 **技术栈**: HBM / KV Cache / MoE 专家权重 / Mooncake / Mooncake Store / NVIDIA CMX / Vera Rubin / BlueField / NVMe SSD

📐 **架构/方法亮点**:
- 两堵墙：容量墙（模型参数 + 长上下文 + 多轮对话 + agent 任务让 KV Cache 膨胀；MoE 需保存远超显存的专家权重）+ I/O 墙（HBM 被权重和 KV Cache 长期占用，GPU 有效利用率受制于数据搬运）
- 月之暗面 Mooncake：以 KV Cache 为中心的分离式推理架构，把 GPU 集群中未充分利用的 CPU/DRAM/SSD 组织为分布式缓存资源；Mooncake Store 支持 DRAM + SSD/NVMe 多级缓存，冷数据下沉到闪存
- NVIDIA CMX 上下文内存存储平台：Vera Rubin 基础设施中增加面向 KV Cache 优化、通过以太网连接的闪存层级，由 BlueField DPU 协助

💡 **关键数据**: Mooncake Store 支持 **DRAM + SSD/NVMe 多级缓存**；NVIDIA CMX 为面向 **KV Cache 的以太网闪存层**；2026 年英伟达推出 CMX（原文未给出具体容量/带宽数字，樱桃不编造）。

🔗 **樱桃的调度视角**: 对 Master 的 GPU 推理集群是存储层级重构信号——KV Cache 不再只住 HBM，而是跨 HBM/DRAM/SSD 多级。调度器未来要感知「KV Cache 在哪一层」：命中本地 HBM 的请求 vs 需从 SSD/远端拉取的请求，延迟差异巨大。这和 Mooncake 的「prefill/decode 分离」思路一致——推理调度正从「调度 GPU」演进到「调度 KV Cache 的存放与迁移」。

### 6. 📦 你调试不了你看不见的：生产级 AI Agent 需要决策链 trace + token 成本监控 + 循环断路

**原文标题:** You can't debug what you can't see - Observability for AI Agents
**来源:** CNCF Blog | 2026-08-04
**链接:** https://www.cncf.io/blog/2026/08/04/you-cant-debug-what-you-cant-see-observability-for-ai-agents/

🎯 **一句话精髓**: 生产级 AI agent 不靠 stack trace 崩溃而是循环/幻觉/烧 token，传统 APM 失效——需要捕获完整决策链的 agent trace + token 成本监控 + 循环检测 guardrail。

🔧 **技术栈**: Langfuse / agent trace / span / batch exporter / token cost / 循环检测 / 迭代上限 / APM

📐 **架构/方法亮点**:
- 每个 agent session 产出一个 agent trace（非通用 APM trace）：每次模型调用、工具调用、子 agent 委托都是 span，带 timing 和 cost；trace 嵌套，子 agent 工作作为父 trace 的子节点
- trace 交付必须非阻塞：用 batch exporter pipeline 内存缓冲 + 周期 flush，关停时优雅 drain；trace backend 不可达时丢的是遥测不是可用性
- token cost 双级可见性 + 主动 guardrail：循环 agent 几何级烧 token；硬迭代上限、per-tool call 预算、循环检测（阻止相同连续调用）作 pre-flight 断路器，告警只是第二道防线

💡 **关键数据**: 文章为实战经验分享，未给基准性能数字；核心量化是「token cost 是 agent 的单位经济学」，循环调用导致 token 几何级消耗。

🔗 **樱桃的调度视角**: 这补齐了 Master 在 K8s 上跑 AI agent 的可观测性缺口——Prometheus 计数器和 Grafana 面板能看 Pod CPU/GPU，但看不到「agent 为什么把同一个问题问了三遍」。建议把 Langfuse agent trace 和 K8s 指标关联：当 agent trace 显示循环烧 token 时，对应 Pod 的 GPU 利用率会异常攀升——两套信号交叉能精确定位「是模型在空转烧卡」。

## 📓 樱桃的今日学习总结

1. **GPU 资源调度正从「整卡/opaque 整数」走向「调度器原生理解的细粒度切片」** - DRA 让调度器原生看到显存/算力切片（替代 HAMi 的扩展资源旁路），微软推理路由做 prefill 感知的副本调度，本质都是把 GPU 资源从「不可见的黑盒」变成「可度量可调度的细粒度对象」。Master 的 GPU 调度选型要跟上 DRA + Inference Extension 这条原生路线，而非继续依赖 webhook 旁路。

2. **AI 推理的存储层级正在解耦与下沉** - HBM 不再独占推理数据，KV Cache/专家权重跨 HBM/DRAM/SSD 多级（Mooncake、NVIDIA CMX）。推理调度从「调度 GPU」演进到「调度 KV Cache 的存放与迁移」，prefill/decode 分离成为主流架构。未来调度器要感知「KV Cache 命中哪一层」，延迟差异巨大。

3. **Agent 时代，K8s 的安全与可观测边界外扩到 LLM 决策层** - Shadow AI 把 agent 当非人类身份纳入 K8s 威胁模型，Agent Observability 要求 trace 覆盖 LLM 调用链，平台工程成熟度是 agent 安全接入的前提。三件事合一：K8s 不再只调度 Pod，还要治理「会自己调工具的 Pod」——配额/权限/审计/策略即代码先于 agent 接入。
