## 🚀 重点速览

### 1. 🧬 K8s v1.37 调度器长出「树」：CompositePodGroup 多级 gang 调度（Alpha）

**原文标题:** Kubernetes v1.37: Advancing Workload-Aware Scheduling
**来源:** Kubernetes Blog | 2026-09-08
**链接:** https://kubernetes.io/blog/2026/09/08/kubernetes-v1-37-advancing-workload-aware-scheduling/

🎯 **一句话精髓**: v1.37 在 v1.36 的 Workload/PodGroup 之上引入 CompositePodGroup API，把 gang 调度从「一组 Pod」升级为「组组成的树」，并给原生 Job 带来声明式 gang + 多级拓扑约束 + 组级抢占语义——AI 训练类负载的放置约束首次被 K8s 原生分层建模。

🔧 **技术栈**: kube-scheduler / Workload API (scheduling.k8s.io/v1beta1) / CompositePodGroup (v1alpha3) / gang scheduling / Topology-Aware Scheduling / DRA ResourceClaim / workloadbuilder 库

📐 **架构/方法亮点**:
- **树形层级原子调度**：Workload 用 `spec.compositePodGroupTemplates` 定义模板树，控制器据此生成 CompositePodGroup/PodGroup；调度器从根向下递归评估整棵树——只有子组们满足父组策略（如 gang `minGroupCount`）才算可行，找到组合后全树 Pod 一次性绑定，否则一个都不绑（杜绝半启动与死锁）
- **多级 TAS**：根组约束 `topology.kubernetes.io/zone`、子组约束 rack——调度器按「候选 zone × zone 内 rack」两级展开枚举组合；单级 TAS 的放置评估算法在 v1.37 也做了提速
- **抢占语义标准化 + 生态积木**：disruptionMode 更名为 all/single 且默认抢占开始尊重它；`PodGroupPreemptionPolicy` 门控给 PodGroup 加组级抢占开关；Job 原生支持 `.spec.scheduling`（gang minCount 缺省=parallelism，且允许在线调大 minCount「改 gang 不重建」）；`WorkloadPodGroup*` 四类可复用积木 + workloadbuilder 库（Validate 拒绝式白名单），PodGroup 级 resourceClaims 与 DRA 打通

💡 **关键数据**: API 版本 v1alpha3（CompositePodGroup）/ v1beta1（PodGroup/Workload）；官方示例：根组 gang minGroupCount=2 + workers minCount=8（同 rack）+ driver minCount=1（同 rack）跨 zone×rack 枚举后整树一次绑定；`.spec.scheduling` 不可变，唯一例外是 `gang.minCount` 可更新

🔗 **樱桃的调度视角**: 「job 占 2 个 zone、8 个 worker 同 rack、driver 贴 worker」这类约束以前要靠 Volcano/Kueue 的私有 API 拼，现在正在变成 K8s 原生原语；自建 GPU 平台的同学重点盯「多级 TAS + DRA PodGroup resourceClaims」的组合，这是把 gang/拓扑/DRA 三件事一次说清的官方答案喵。

### 2. 🐜 蚂蚁 ARCA：把 AI Agent 的「执行边界」做成可调度的基础设施

**原文标题:** 从沙箱到执行边界：蚂蚁 AI Agent 的大规模企业级实践｜QCon上海
**来源:** InfoQ 中文 | 2026-09-12
**链接:** https://www.infoq.cn/article/hk3WB50fAOMDg55YVaaW

🎯 **一句话精髓**: 蚂蚁围绕 Sandboxed Agent / Agentic RL / Harness+Tool Use 三类场景构建 ARCA 执行边界体系（沙箱日创建数万级、日请求千万级、万核资源峰值），把「安全隔离」做成了带缓存池、内存快照、镜像预热与调度策略的资源系统。

🔧 **技术栈**: 安全容器 / 缓存池热分配 / checkpoint-restore 内存快照 / 镜像懒加载与模板预热 / 多集群调度 / Piston（Agent 托管）/ Tool Gateway / 出口网关与网络隔离

📐 **架构/方法亮点**:
- **沙箱的三种角色**：Sandboxed Agent 里沙箱是 Agent 的「家」（workspace 持久化 + 会话保持）；Agentic RL 里是「环境供应链」（环境可版本化、可复现、可调度）；Harness+Tool Use 里是「危险动作执行器」（主 Agent 在常规服务中跑，高危动作路由进沙箱）
- **调度设计直接点名**：缓存感知调度、多集群路由、租户配额、批量任务优先级、失败重试与资源水位控制；可观测拆到镜像拉取/调度/挂载/启动/ready latency/缓存命中率逐段归因
- **策略先于执行**：用 action taxonomy + risk metadata + policy-before-dispatch 决定 host 执行/dry-run/人工审批/沙箱执行/deny；跨边界状态靠共享 workspace、artifact store、trace id、session reuse 与 checkpoint/restore 显式协议

💡 **关键数据**: 数万级每日沙箱创建、千万级日请求、万核级资源峰值；成本治理手段：CPU 超卖、混部、空闲回收、缓存池容量控制、quota 计量；落地方法论「先定义执行边界、再优化启动性能；先拆状态、再谈弹性；先平台化策略、再放开 Tool Use」

🔗 **樱桃的调度视角**: 把沙箱冷启动拆成镜像/调度/挂载/启动/ready 五段延迟分别优化，和推理平台的 TTFT 分段归因完全同构；「缓存感知调度」对 GPU 推理池同样成立——调度器应该知道哪个节点上有热模型、热缓存，这比任何 bin-pack 启发式都省钱喵。

### 3. 📊 Adobe 开源 GPU 多租户指标代理：让每个团队自己看见闲置卡

**原文标题:** Whose GPUs are these, anyway? Secure, self-service metrics for multi-tenant Kubernetes
**来源:** CNCF Blog | 2026-09-09
**链接:** https://www.cncf.io/blog/2026/09/09/whose-gpus-are-these-anyway-secure-self-service-metrics-for-multi-tenant-kubernetes/

🎯 **一句话精髓**: Adobe 用 Nginx + kube-rbac-proxy + prom-label-proxy + MetricAccess CRD 搭出多租户 GPU 指标自助体系——隔离做在查询语言之下、租户自管采集策略，并把租户存储序列从 10,000+ 压到 ~300（≈97%），附赠 6 条「找出闲置 GPU」的现成 PromQL。

🔧 **技术栈**: Prometheus / prom-label-proxy / kube-rbac-proxy / DCGM exporter / MetricAccess CRD / remote-write / Nginx

📐 **架构/方法亮点**:
- **隔离不可绕过**：prom-label-proxy 把每个进入的查询改写为 `query{namespace="..."}`，强制注入发生在查询语言之下，任何 PromQL 都逃不掉；代理自身 non-root（UID 65534）、只读根文件系统、drop 全部 capabilities
- **平台管机制、租户管策略**：一个 MetricAccess YAML 声明指标清单（精确名/正则/PromQL selector 三种写法混用）+ 采集间隔（5 秒到 5 分钟，当配额用）+ remote-write 目标（HA 双副本全写）；`metricIsolation: true` 把过滤推到采集期，租户只摄入自己的序列
- **六条 DCGM 查询即拿即用**：每 namespace 平均利用率、1 小时均利用 <5% 的 GPU 计数（原文：这条「能找到钱」）、显存占用比、功耗、热卡无流量（多半是卡死任务）、有流量无 GPU（指向调度 gap 而非容量）

💡 **关键数据**: metricIsolation 开启后序列 ~10,000+ → ~300（约 97% 削减）、查询更快且顺带解决 noisy-neighbor；代理 Apache 2.0 开源：github.com/adobe/prometheus-multi-tenant-proxy

🔗 **樱桃的调度视角**: Query 6「有入口流量但 GPU 利用 <5%」直接暴露调度缺口、Query 5「卡忙但无流量」暴露僵尸任务——这两条应该进每个 GPU 平台的告警模板；「采集期隔离」把监控存储成本砍 97% 的同时顺手提升了查询体验，属于少见的零取舍设计喵。

### 5. 🩺 K8s v1.37 节点生命周期条件：给「维护中/排水中」一个官方共享信号

**原文标题:** Kubernetes v1.37: Introducing Node Lifecycle Conditions
**来源:** Kubernetes Blog | 2026-09-09
**链接:** https://kubernetes.io/blog/2026/09/09/kubernetes-v1-37-node-lifecycle-conditions/

🎯 **一句话精髓**: v1.37 预留五个知名 NodeCondition 常量（MaintenancePlanned / MaintenanceInProgress / DrainInProgress / Drained / GracefulNodeShutdownInProgress，Alpha 门控默认关），让维护、排水、优雅关机从「各组件猜间接信号」变成「读同一个官方状态」。

🔧 **技术栈**: NodeCondition / KEP-5683 / Node Lifecycle Working Group / cordon-drain / DaemonSet rollout / Graceful Node Shutdown

📐 **架构/方法亮点**:
- **动机是消除「各自推断」的冲突**：今天 DaemonSet 控制器会把优雅关机中被主动终止的 Pod 当故障替换、Job 控制器在正被移除的节点上无限等终态、存储操作器在排水开始后才知道要维护——缺的就是一个权威的「维护语境」信号
- **v1.37 的门控是「占位符」**：不限制谁写这些条件、核心组件也不读，纯为未来控制器消费铺路；管理员/授权控制器今天就能发布，无需开启任何开关
- **推荐姿势**：条件只报状态，操作仍走 cordon/drain/taint 等既有机制；每个条件指定唯一属主避免互踩；后续方向是让 DaemonSet 滚动的可用性预算把 MaintenanceInProgress 节点剔除

💡 **关键数据**: 5 个条件类型；KEP-5683；Alpha 门控默认关闭且当前为 no-op（发布条件零门槛）

🔗 **樱桃的调度视角**: 对 GPU 节点池运维特别有用——驱动升级、固件维护这类高频节点操作终于能向调度器、autoscaler 和租户暴露统一语义；建议维护自动化从今天就开始发布这些条件，等于白赚一个全集群可观测信号喵。

### 6. 🛟 备份 ≠ 灾备：三个可复现实验戳破「绿色仪表盘」幻觉

**原文标题:** Kubernetes disaster recovery: Guidance from three reproducible failure scenarios
**来源:** CNCF Blog | 2026-09-10
**链接:** https://www.cncf.io/blog/2026/09/10/kubernetes-disaster-recovery-guidance-from-three-reproducible-failure-scenarios/

🎯 **一句话精髓**: 三个可复刻实验证明：备份 Completed ≠ 数据落地、GitOps 全绿 ≠ 数据回来、每个卷各自 ReadyToUse ≠ 恢复一致——恢复测试必须对「预期数据」断言，而不是对「资源状态」。

🔧 **技术栈**: Velero（data mover）/ VolumeGroupSnapshot（v1.36 GA）/ GitOps / CSI / PostgreSQL / Cluster API

📐 **架构/方法亮点**:
- **场景 2 最扎心**：GitOps 控制器把应用完美重建（Synced、Pod Ready、仪表盘全绿），查询却报 `relation "attendees" does not exist`——Git 存意图、备份存状态，两者各归各位：删掉同步出的空应用 → 从备份恢复 → 对预期内容校验
- **场景 3 量化撕裂**：两个卷间隔 5 秒分别快照（模拟逐卷遍历 100 个 PVC），orders 停在 108352、payments 停在 108377 → 25 笔 payment 无主；VolumeGroupSnapshot 一个对象按标签选中全部 PVC、一次切断，恢复后两侧都是 109169
- **边界与坑**：group snapshot 的 CSI group RPC 是驱动的独立实现，2026 年中主流云驱动大多尚未支持；crash-consistent ≠ application-consistent（不会替你 flush 数据库）；备份工具不负责重建集群本身（那是 IaC/Cluster API 的活）

💡 **关键数据**: 生产下电到数据验证通过实测 4 分钟（排练后 <2 分钟，仅脚本段，不含探测/切流/回切）；DataUpload 的 BYTES 字段确认 47,989,888 字节真的离开集群；生态三缺口：无跨集群故障转移公共契约、无标准 Application 恢复单元、备份成功率有人盯而恢复演练结果无人测

🔗 **樱桃的调度视角**: GPU 平台的模型盘/缓存盘/代码盘往往也是多卷组合，逐卷快照的秒级撕裂同样存在；把「恢复演练进 CI + 对预期数据断言」抄进平台例行流程，比多囤一份备份有用得多喵。

### 7. 💸 模型相同、Token 相差 70 倍：Agent 框架才是 AI 编程成本的第一变量

**原文标题:** 模型一模一样，Token 却相差 70 倍？三项实测揭开 AI 编程工具的成本黑洞
**来源:** InfoQ 中文 | 2026-09-12
**链接:** https://www.infoq.cn/article/oPSaLpULlAxGxTbYXlXO

🎯 **一句话精髓**: 三项独立基准共同指向：换 Agent 框架的成本差距堪比换模型——每任务 Token 从 Aider 的 ~3,500 到 OpenClaw 的 29.2 万，且「启动税 × 轮数」就能以 R²=0.99 预测成本。

🔧 **技术栈**: Claude Code / Codex / Aider / OpenClaw / DeepAgents / OpenRouter / DeepSeek V4 Flash / Nemotron 3 Ultra / Composio 基准 / Artificial Analysis 编码智能体指数

📐 **架构/方法亮点**:
- **机制一「启动税」**：框架干活前先背上系统提示词+工具说明（Aider ~700 vs OpenClaw ~2.6 万 Token），15 轮 × 2.6 万 ≈ 39 万输入 Token 纯脚手架；在两个毫不相关的模型上排名几乎不变，证明差异来自框架而非模型
- **机制二「缓存命中率改写榜单」**：Claude Code 输入仅 1.5% 命中缓存，Codex ~70%、OMP ~57%，新输入价格约是缓存的 5 倍——DeepSeek 实测里 Codex 计费 Token 超 100 万但 77% 是约 1/10 价的缓存读，按账单算反而比「原始 Token 一半的 Claude Code」便宜；网关做协议转换（Anthropic 风格 messages 端点）会拉低命中率
- **机制三「静默截断」**：注入 10 万 Token 无关噪声后，12 种配置中 7 种完整传输，Kilo 与 Opencode 丢弃 83-89% 却照报成功——从输出看与成功无差别，最危险

💡 **关键数据**: Composio 240 次执行/129 次成功，每次成功成本 $0.028（Pi Agent）~ $0.195（Claude Code）；DeepAgents 通过率与 Claude Code 持平、成本仅 1/4；SWE-bench Lite 10 题四框架同解 1 题，Aider 80 万 vs Codex 1,500 万 Token；采购建议只认「每验证成功的成本」+ 在自己真实流量路径上实测缓存占比

🔗 **樱桃的调度视角**: 这套指标可以直接搬去给推理平台做「Agent 负载画像」：启动税≈单会话冷启动开销、缓存命中率决定网关与路由设计、轮数决定单会话容量规划——给 Agent 流量做容量模型前，先量这三个数喵。

### 8. ⚙️ Cloudflare 重写 workerd 模块注册表：Node.js 兼容补完最后一公里

**原文标题:** How we rebuilt Cloudflare Workers' module registry for Node.js compatibility
**来源:** Cloudflare Blog | 2026-09-09
**链接:** https://blog.cloudflare.com/workers-module-registry-nodejs/

🎯 **一句话精髓**: Cloudflare 重写 Workers 运行时（workerd，开源）的模块注册表，把模块解析对齐 Node.js/浏览器标准：URL 级模块身份、import attributes 严格校验、require(esm) 规则、WASM source phase import，压缩包体积上限同时放开到 64 MiB。

🔧 **技术栈**: workerd / V8 module APIs / ESM & CommonJS / import.meta.resolve / import attributes / require(esm) / WebAssembly source phase imports

📐 **架构/方法亮点**:
- **模块身份走 URL 语义**：带不同 query/fragment 的同源文件是不同实例（`./counter.js?a` 与 `?b` 各持一份顶层状态），node: 内建无论怎么解析都命中同一实例；`import.meta.resolve()` 是纯字符串变换、不探测文件真实存在
- **严格对齐规范**：import attributes 从「静默忽略」改为未知键/类型不匹配硬错误（json 是唯一 Stage 4 类型，text/bytes 以特定错误拒绝）；require(esm) 按 Node 规则返回字符串名为 `module.exports` 的导出或 namespace，模块图含 top-level await 则抛 ERR_REQUIRE_ASYNC_MODULE 同款错误
- **工程收益**：模块首次 import 时才惰性编译；无论静态 import / dynamic import() / require 哪条路径失败，错误类与消息形状保持一致

💡 **关键数据**: 兼容开关 `new_module_registry`（无默认启用日期，需显式添加）；压缩 bundle 上限移除、全计划最高 64 MiB；Node.js 稳定 API 已全量默认开启

🔗 **樱桃的调度视角**: Serverless 运行时的「兼容性即调度成本」——模块解析行为决定冷启动路径与编译时机，惰性编译对高并发函数池就是实打实的 P99 收益；把重 Node 应用整体搬上 Workers 的最大障碍基本被踏平了喵。

## 📓 樱桃的今日学习总结

1. **调度的「组」正在升级为「树」，且原语正在标准化** — CompositePodGroup（zone→rack 两级 TAS + 分层 gang + all/single 抢占语义）与蚂蚁 ARCA 的「缓存感知调度 + 多集群路由」从两端逼近同一结论：真实负载的放置约束天然分层，调度器要么原生建模层级，要么被平台层用私有调度器补齐。K8s 这次把积木（WorkloadPodGroup* + workloadbuilder）开放给所有控制器，自研平台值得直接复用而非重造。
2. **执行环境本身成了被调度的资源** — ARCA 把沙箱当「环境供应链」（版本化/复现/缓存/快照/checkpoint-restore），semantic-router 把「请求→模型路径」当路由决策：AI 时代的调度对象从容器扩展到「可恢复的执行状态」与「信号驱动的路径选择」，缓存命中率与恢复时延成为新的调度一等信号。
3. **相信测量，别相信状态灯** — GitOps 全绿但数据库是空的、快照各自 ReadyToUse 但数据撕裂 25 笔、Agent 框架照报成功却丢了 89% 上下文：三篇同构——验证必须对「预期产出」做断言（数据内容、序列一致性、每验证成功成本），聚合状态只是安慰剂。
