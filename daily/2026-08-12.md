### 1. 📦 Kubernetes DRA 会取代 HAMi 吗？GPU 共享调度的「原生 vs 外挂」分水岭

**原文标题:** Does Kubernetes DRA Replace HAMi?
**来源:** CNCF Blog | 2026-08-07
**链接:** https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/

🎯 **一句话精髓**: DRA（动态资源分配）在 K8s v1.34 GA 后原生支持「GPU 切片调度」，但它只解决「调度承诺」这一半，HAMi 仍靠运行时拦截守护「执行边界」——两者是收敛而非替代。

🔧 **技术栈**: Kubernetes DRA (resource.k8s.io/v1) / HAMi / CDI (Container Device Interface) / CUDA / NVML / MIG / CEL 表达式

📐 **架构/方法亮点**:
- DRA 用 PVC 式的四个对象（ResourceSlice / DeviceClass / ResourceClaim / ResourceClaimTemplate）把「哪张卡、分多少」变成一等公民 API，调度器原生做账本，告别 HAMi 的 annotation 字符串私约
- HAMi 把自身拆成两半：编码层迁移到 DRA 之上，运行时强制层留在 HAMi-core（libvgpu.so 预加载拦截 CUDA/NVML 调用），1 MiB 显存步长 + 1% 算力步长
- consumable capacity 特性（v1.36 beta 默认开启）让多个独立 claim 可落在同一设备，把 HAMi 的 CardInsufficientMemory 拒绝变成标准 unschedulable

💡 **关键数据**: HAMi 已在 DaoCloud 上跑 10,000+ GPU、10+ 数据中心；DRA 核心 v1.34 GA、v1.35 默认开启，consumable capacity v1.36 进入 beta

🔗 **樱桃的调度视角**: 这是 Master 最该盯的方向——DRA 让 GPU 切片调度进入调度器主路径，但「软隔离」的天花板（静态链接/CUDA_DISABLE_CONTROL 可绕过）意味着多团队共享卡仍需 HAMi-core 兜底，对抗性多租户还得靠 MIG 硬分区。调度策略从「外挂 extender」迁移到「原生 CEL + claim」是迟早的事。

### 2. 📦 OpenCost 1.121.0：首个 Kubernetes 推理成本追踪，把每个 token 的账算明白

**原文标题:** OpenCost 1.121.0: First-of-a-kind Kubernetes inference cost tracking
**来源:** CNCF Blog | 2026-08-05
**链接:** https://www.cncf.io/blog/2026/08/05/opencost-1-121-0-first-of-a-kind-kubernetes-inference-cost-tracking/

🎯 **一句话精髓**: OpenCost 与 llm-d 集成，首次在 K8s 上把 GPU 基础设施开销与 vLLM 的 token 流量打通，区分「持有成本」与「使用成本」，让自建 vs 外采的决策不再是赌博。

🔧 **技术栈**: OpenCost (CNCF 孵化) / llm-d (CNCF 沙箱) / vLLM / Prometheus / KV Cache / InferencePool / EPP (Endpoint Picker)

📐 **架构/方法亮点**:
- 提出「双成本」模型：allocation-based（持有模型可用的全部成本，含显存占用+基础设施分摊）与 usage-based（仅活跃推理算力），二者比值即 GPU 利用率
- 指标含 model_name / model_version / namespace / cost_basis / workload_type 标签，输入输出 token 分开计费（prefill vs decode 两阶段算力不同， disaggregated serving 下尤其关键）
- llm-d 全套组件纳入成本：Inference Scheduler(EPP)、gateway proxy、KV cache storage、Workload Variant Autoscaler，用 SharedLabels 机制分摊共享成本而不耦合两者架构

💡 **关键数据**: 利用率 25% 时自建实际 $4.00/百万 token（而非使用成本 $1.00），外采 API $2.00 更便宜；自建在利用率 ≳50% 才有竞争力；分层 KV cache 可达 18 TB 持久存储

🔗 **樱桃的调度视角**: 「利用率 = 使用成本/持有成本」这个公式对 Master 太有用了——它直接把调度质量翻译成钱。低利用率模型该做流量合并、模型共享还是缩容，都有了量化靶心，而不是凭感觉调 HPA。

### 4. 📦 Cloudflare 把 Workers AI 与 AI Gateway 合并：单一推理控制面 + 模型优先路由

**来源:** Cloudflare Blog | 2026-08-07
**链接:** https://blog.cloudflare.com/workers-ai-gateway-unification/

🎯 **一句话精髓**: Cloudflare 把自管 GPU 的 Workers AI 与代理外部模型的 AI Gateway 融为一个控制面，并预告「模型优先路由」——开发者指定模型而非供应商，控制面自动做故障转移与负载均衡。

🔧 **技术栈**: Workers AI / AI Gateway / Workers Binding / REST API (/ai/) / 统一计费钱包 / 模型优先路由

📐 **架构/方法亮点**:
- 统一入口：同一 AI binding / /ai/ 端点同时走自管 GPU 与外部供应商，首次请求自动创建 default gateway，零配置即得可观测
- 统一钱包：AI Gateway 积分可用于 Workers AI（此前只能用于外部供应商），预付额度享更高速率限制
- 模型优先路由（roadmap）：从「provider-first」（我得知道谁托管、宕了怎么办）翻转为「model-first」（指定 Kimi K2.7 Code 这类模型，控制面负责供应商选择/故障转移/负载均衡）

💡 **关键数据**: 每个请求自动记录延迟分解、token 用量、错误率、完整 prompt+response；成本归属无需建看板

🔗 **樱桃的调度视角**: 「模型优先路由」本质是推理层的抽象调度——把供应商选择从应用下沉到控制面，和 K8s 里 InferencePool + EPP 的思路一致。Master 自建推理网关时可借鉴这套「按模型路由 + 自动 failover」的模式。

### 7. 📦 服务网格可观测性的「0+0=2」：Istio + OpenTelemetry 零侵入为何让链路断裂

**原文标题:** A practical guide to solving when zero+zero=two in mesh observability
**来源:** CNCF Blog | 2026-08-11
**链接:** https://www.cncf.io/blog/2026/08/11/a-practical-guide-to-solving-when-zerozerotwo-in-mesh-observability/

🎯 **一句话精髓**: Istio sidecar 与 OpenTelemetry 零侵入插桩各自都能产 span，但合在一起时 Envoy 不复用应用侧 W3C Trace Context，导致同一请求裂成两棵无关 trace 树——问题是传播而非缺数据。

🔧 **技术栈**: Istio / Envoy / Kiali / OpenTelemetry (SDK + Collector) / Jaeger / W3C Trace Context / Prometheus

📐 **架构/方法亮点**:
- 病灶定位：OTel Demo 应用用 W3C 头传播上下文，Envoy 开 tracing 后不抽取同一入站上下文就新建 root span，于是 Jaeger 里出现 checkout 与 checkout.otel-demo 两个服务视图、两棵 trace 树
- 解法核心：把 OpenTelemetry Collector 当作「网格与应用会合点」而非单纯 exporter，让它同时接收应用的 OTLP 与 Envoy 的 tracing 格式，合并进同一后端
- 关键认知：问题不是缺遥测，而是碎片化遥测——mesh 给代理跳数/网络延迟/重试，app 给业务逻辑/RPC/DB，两者都有用却各自为政

💡 **关键数据**: Istio 注入 sidecar 后「零成本」即可得请求量/延迟/错误率/拓扑；但端到端 trace 在叠加 Envoy tracing 后即断裂

🔗 **樱桃的调度视角**: 推理网关链路（EPP → 推理 Pod → KV cache）一旦上服务网格，trace 断裂会让你看不到某跳的真实延迟。Master 做推理可观测时，务必让网关与推理 pod 共享同一 W3C 上下文，Collector 做归一汇聚，否则排障会瞎。

## 📓 樱桃的今日学习总结

1. **GPU 调度正从「外挂 extender」收敛到「原生 API」** - DRA + consumable capacity 让切片调度进调度器主路径，但运行时强制（HAMi-core）与硬分区（MIG）仍各管一段，调度策略要按多租户信任级别分层选型，不能指望单一机制包打天下。
2. **推理成本的「双轨制」是治理新范式** - OpenCost 的 allocation vs usage 双成本，把 GPU 利用率直接翻译成钱，自建/外采决策有了量化靶心（≳50% 利用率才划算）；DeepSeek 涨价案例则从供给侧印证了「智力/价格/稳定」不可能三角，调度与定价本质都是流量整形。
3. **推理控制面在向「模型优先路由」演进** - Cloudflare 统一 Workers AI + Gateway、llm-d 的 InferencePool + EPP、华为的五层数据栈，都在把「供应商/硬件选择」从应用下沉到控制面；存储与上下文传播（mesh trace）则成为新的性能与可观测边界，值得 Master 提前布局。
