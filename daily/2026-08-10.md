## 🚀 重点速览

### 1. 📦 K8s DRA 是否取代 HAMi？调度器原生 GPU 切片 vs 容器内 CUDA 级强制

**原文标题:** Does Kubernetes DRA Replace HAMi?
**来源:** CNCF Blog | 2026-08-07
**链接:** https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/

🎯 **一句话精髓**: DRA 的 consumable capacity 功能让 K8s 调度器首次原生理解 GPU 分片请求（显存+算力），吸收了 HAMi 的「编码」职责；但容器内 CUDA 调用粒度的资源强制（enforcement）DRA 从未设计来做，HAMi 据此分裂为「DRA 管调度 + 自己管 enforcement」的双层架构。

🔧 **技术栈**: Dynamic Resource Allocation (DRA) / HAMi / ResourceSlice / DeviceClass / ResourceClaim / consumable capacity / libvgpu.so / scheduler extender / CEL 表达式 / K8s v1.34-v1.36

📐 **架构/方法亮点**:
- **DRA 的四对象模型**（类比 PVC）：ResourceSlice（设备驱动发布，描述每节点真实硬件的结构化属性如 model/memory/architecture）→ DeviceClass（集群管理员用 CEL 表达式定义设备类别）→ ResourceClaim/ResourceClaimTemplate（工作负载 owner 按类别+选择器+约束请求设备，template 为每个 Pod 副本戳出独立 claim）→ 调度器在绑定 Pod 前分配具体设备，结果存入 claim 的 status，kubectl 可读、RBAC 可守
- **consumable capacity 是关键拼图**：核心 DRA 的基线共享是「多个 Pod 引用同一个 ResourceClaim」（共享同一分配而非各得切片）；consumable capacity（v1.34 alpha → v1.36 beta 默认开启）新增两件事：驱动可标记设备 `allowMultipleAllocations`（不同 namespace 的独立 claim 可同时落同一设备）+ claim 可携带 capacity request 请求设备上某个命名资源的特定数量——调度器像管理 node memory 一样做 GPU memory 簿记，保证已分配容量之和不超过设备声明值
- **HAMi enforcement 不可替代**：HAMi 在 device plugin 的 `Allocate()` 中读取 annotation，注入 `CUDA_DEVICE_MEMORY_LIMIT_0=8000m` 和 `CUDA_DEVICE_SM_LIMIT=10`，预加载 `libvgpu.so` 拦截 CUDA 调用做硬限制——这是 DRA 从未设计的容器内 enforcement 层；HAMi 的应对是保留 enforcement、在 DRA 之上重建编码（3 个仓库）

💡 **关键数据**: DRA 核心 GA 于 **K8s v1.34**，v1.35 起默认开启；consumable capacity 为 **v1.36 beta**（截至 2026-07 尚未 stable）；HAMi 已被 CNCF TOC 于 **2026-07-15** 接受为孵化项目；DaoCloud 在 HAMi 上跑 **10,000+ GPU / 10+ 数据中心**。

🔗 **樱桃的调度视角**: 这是 Master 必读的一条——它精准定义了 K8s GPU 共享的「调度原生」与「容器内强制」两个职责边界。DRA consumable capacity 意味着调度器终于能像调度 CPU/memory 一样调度 GPU 切片，HAMi 的 mutating webhook + scheduler extender + annotation 这套 workaround 正在被原生 API 替代。但关键洞见是：**调度器能分配 ≠ 容器内能限制**——DRA 解决「这个 Pod 分到哪张卡的多少资源」，HAMi 的 libvgpu.so 解决「这个 Pod 真的只用这么多」。对 Master 的 GPU 推理平台：如果只用 DRA 不加 enforcement，一个声明 8GB 的 Pod 可以实际吃满整张卡——调度层面的公平不等于运行时的隔离。短期最佳实践是 HAMi 的双栈路线：DRA 管调度决策，HAMi 管运行时强制。

### 2. 📦 HBM 不够用了：AI SSD 进入大模型推理的实时数据路径

**原文标题:** HBM 不够用了，AI SSD 迎来爆发前夜
**来源:** InfoQ 中文 | 2026-08-07
**链接:** https://www.infoq.cn/article/sQW5F63ZP4QMyhlWAzQi

🎯 **一句话精髓**: 当 HBM 被模型权重和 KV Cache 长期占用、GPU 有效利用率受制于数据搬运时，SSD 正从模型文件的静态存放设备进入大模型推理的实时数据路径，成为 HBM/VRAM/DRAM 之后的正式存储层级，并分化为「I/O 强化型」和「直接参与推理调度型」两条技术路线。

🔧 **技术栈**: HBM / KV Cache / Mooncake 分离式推理 / NVIDIA CMX / BlueField-4 / MoE 专家权重 / NAND Flash / FTL / aiDAPTIVCache / SPU+iSA / XL-Flash / SLC NAND / NVMe / CXL

📐 **架构/方法亮点**:
- **推理的两堵墙**：容量墙（模型参数扩大 + 长上下文/多轮对话/Agent 任务让 KV Cache 膨胀 + MoE 需保存远超显存的专家权重）和 I/O 墙（HBM 被长期占用，GPU 有效利用率受制于数据搬运）；传统 SSD 面向文件/块存储设计（顺序带宽、随机 IOPS），而 LLM 推理需要严格时序约束的数据供应——KV Cache 在 prefill 集中生成并持续写入、后续按会话/模型层/Token 位置反复读取，MoE 需按路由结果在每层计算前及时取得特定专家权重
- **两条 AI SSD 路线**：第一类「I/O 强化型企业级 SSD」（英韧洞庭 N3X 用 XL-Flash/SLC NAND 降低时延至 1/3、写入吞吐提升 3 倍、DWPD 提升 17-33 倍；华为 OceanDisk 分极致性能盘/高性价比推理盘/245TB 超大容量盘）——仍以块存储为基本形态但围绕 AI 数据路径重排指标；第二类「直接参与推理调度型 SSD」（群联 aiDAPTIV 将超 VRAM 容量的模型权重切块在 VRAM↔SSD 间流式传输、江波龙 SPU+iSA 集成压缩/冷热识别/预取调度、寅谱-联芸联盟贯通 middleware/firmware/controller 做 MoE 专家/KV Cache/数值精度的数据切分与预测式预取）
- **NVIDIA CMX 的产业信号**：2026 年 NVIDIA 推出 CMX 上下文内存存储平台，在 Vera Rubin 基础设施中增加面向 KV Cache 优化、通过以太网连接的闪存层级，由 BlueField-4 负责 NVMe SSD 管理——定义了介于 GPU 内存与共享存储之间的 pod 级上下文层

💡 **关键数据**: 英韧 N3X 相比传统 TLC SSD 访问时延降至约 **1/3**、写入吞吐提升至约 **3 倍**、DWPD 提升约 **17-33 倍**；群联 aiDAPTIV 缓存 SSD 耐久性最高 **100 DWPD**；华为 OceanDisk LC 560 单盘容量最高 **245TB**；月之暗面 Mooncake Store 支持 DRAM + SSD/NVMe 多级缓存。

🔗 **樱桃的调度视角**: 这条直接关联 Master 的 AI 推理调度——当 SSD 从「模型加载前的外围设备」变成「Token 生成中的实时数据层」，调度器的资源模型必须扩展：不仅要调度 GPU 算力和显存，还要调度 SSD 的 KV Cache 容量和 MoE 专家权重的预取带宽。Mooncake 的分离式架构（GPU 集群 + CPU/DRAM/SSD 组成分布式缓存）和 NVIDIA CMX（pod 级闪存上下文层）都在指向同一个方向：**推理调度的资源维度从「GPU 卡」扩展到「GPU + 显存 + 远端 KV Cache 存储 + SSD 预取带宽」的多层协同**。如果 Master 的 K8s 推理平台还在把 SSD 当被动存储，该考虑把它纳入调度决策了——尤其 MoE 模型的专家权重按需加载，SSD 预取延迟直接决定 GPU 空闲率。

### 3. 📦 Shadow AI 威胁建模：从开发者笔记本到 K8s Pod 的全链路攻击面

**原文标题:** Shadow AI in CI/CD: Threat-modeling the path from developer laptop to Kubernetes
**来源:** CNCF Blog | 2026-08-07
**链接:** https://www.cncf.io/blog/2026/08/07/shadow-ai-in-ci-cd-threat-modeling-the-path-from-developer-laptop-to-kubernetes/

🎯 **一句话精髓**: Shadow AI（未经正式审批/归属/风险评估/监控的 AI 工具/模型/agent/扩展）不再是「开发者用聊天机器人」的问题而是「访问控制」问题——一旦 AI agent 拿到 Git token、云凭证或 K8s ServiceAccount，它就成了一个有权限、有爆炸半径的非人类身份，文章对从开发笔记本到 K8s Pod 的交付路径逐阶段做了威胁建模和防御控制映射。

🔧 **技术栈**: Shadow AI / 威胁建模 / gitleaks / Gitsign (Sigstore) / VM 隔离工作区 / K8s ServiceAccount / RBAC / 准入控制 / Kyverno / OPA Gatekeeper / 供应链安全 / prompt injection

📐 **架构/方法亮点**:
- **六阶段交付路径 × Shadow AI 注入点**：开发者笔记本（未批准的代码助手/本地模型插件/公共聊天机 → 源码/密钥/架构泄露）→ 源码控制（AI bot 审 PR/生成 commit → 过度仓库权限/不安全代码变更/无归属）→ CI 流水线（AI 生成流水线逻辑/分析日志/修失败构建 → 构建密钥和云凭证暴露）→ 制品仓库（AI 辅助选镜像/依赖 → 漏洞/恶意/不可追溯依赖入生产）→ CD 平台（AI agent 审批/修改/发布 → 绕过变更控制/未授权部署）→ K8s 运行时（agent 查询集群/修复告警/扩缩容 → 过度授权 SA/破坏性操作/横向移动）
- **从建议到行动的风险跃迁**：提供建议的助手（建议代码片段 → 数据离开边界/错误建议被信任）vs 拿到凭证的 agent（以机器速度创建/修改/删除资源 → K8s 不会区分攻击者和过度授权的自动化身份）——后者是全新的非人类身份威胁，需要 operational 而非 philosophical 的回答
- **防御控制矩阵**：笔记本层提供批准的 AI 工具（让使用可见而非禁止）+ gitleaks pre-commit secret scanning + Gitsign 签名 commit（短期身份证书替代长期 GPG key，让「谁产出了这个变更」可审计，包括 agent 作者）；CI 层隔离 agent 运行环境（VM 隔离工作区，agent 有独立内核和文件系统，宿主 SSH key/云凭证不可达）；K8s 运行时用准入控制（Kyverno/OPA Gatekeeper）限制 agent SA 的资源操作 + 监控实际行为

💡 **关键数据**: Shadow AI 威胁建模覆盖 **6 个交付阶段**；防御工具栈包括 gitleaks（密钥扫描）、Gitsign（Sigstore 签名）、Kyverno/OPA Gatekeeper（准入控制）；OWASP AI agent 和 LLM 应用指南作为失败模式基线。

🔗 **樱桃的调度视角**: 这条对 Master 的 K8s 平台安全有直接操作价值——当 CI/CD agent、运维 agent 开始操作 K8s 集群时，每个 agent 都应该有自己的 ServiceAccount + 最小权限 RBAC + 行为审计，而不是共用一个 cluster-admin 级别的凭证。文章的六阶段模型可以直接映射到 Master 的交付流水线做差距分析。特别值得注意的洞察是「prompt injection 是贯穿线」——agent 读 issue 描述、README、依赖 changelog、构建日志都是不可信内容，任何一个都可以操纵 agent 泄露数据或执行不安全操作，因此 prompt 过滤永远不够，需要 defense-in-depth。

### 4. 📦 Cloudflare 定义 Agentic Internet：可读、可发现、可调用、可支付的四层协议栈

**原文标题:** Building an open Agentic Internet: readable, discoverable, callable, and payable
**来源:** Cloudflare Blog | 2026-08-06
**链接:** https://blog.cloudflare.com/the-agentic-internet/

🎯 **一句话精髓**: Cloudflare 提出「Agentic Internet」愿景——Agent 不是新型软件而是新型 Web 访问者，围绕 readable（Markdown for Agents）、discoverable、callable（WebMCP）、payable（x402）四层构建开放协议栈，配合 Web Bot Auth（密码学身份）、PACT（匿名访问令牌）、Kitesurf（V8 隔离的 agent 浏览器）让 agent 与域名所有者协作而非冲突。

🔧 **技术栈**: Web Bot Auth / PACT (Private Access Control Tokens) / Markdown for Agents / WebMCP / x402 / Kitesurf / V8 isolates / Cloudflare Workers / MCP v2

📐 **架构/方法亮点**:
- **Agent 作为新型 Web 访问者**：数据显示大量良性 bot 流量在重复抓取未变化的页面——数十亿次请求、巨大的机器算力、零结果，这是「为人类构建的 Web 被另一种东西访问」的标志；每个 agent 背后都有付费的人类，每次请求都带着目的和账单——「拦截它就拦截了你的客户，当爬虫对待就失去他们」
- **四层协议栈**：Readable（Markdown for Agents 让 agent 用更少 token 和带宽读网站，每个为人类渲染但 agent 不看的 HTML 标签都是计算浪费和上下文窗口污染）；Callable（WebMCP 给 agent 原生的站点交互方式，无需代码修改，Cloudflare 在页面注入 bridge 注册工具集）；Payable（x402 标准让 agent 直接向商户支付）；Identity（Web Bot Auth 让 bot 密码学自证身份，PACT 让站点匿名背书合法 agent，减少摩擦）
- **Kitesurf 浏览器**：lean 到能在 Workers 上运行的 agent-first 浏览器，按请求 spin up、用完即弃，运行在 V8 isolate 中；所有规范基于开放标准（x402/MCP/Web Bot Auth/PACT），域名所有者选自己的身份提供商/支付处理器/agent 合作伙伴，Cloudflare 是选项之一而非整个栈

💡 **关键数据**: Cloudflare 数据显示 **超过一半的 HTML 页面请求已不再来自人类**；大量良性 bot 流量在重复抓取未变化内容，造成「数十亿次请求、零结果」；PACT 与 Mozilla/Google/Microsoft/Shopify 联合发布。

🔗 **樱桃的调度视角**: 虽然这不是 K8s 原生话题，但「Agent 是新型 Web 访问者」的定位对 Master 有架构启发——当你的推理平台上跑的 agent 需要访问外部 Web 资源时，流量模式会根本改变（高并发、短会话、不渲染 CSS/图片、每次请求有 token 成本）。Markdown for Agents 的思路（给 agent 少消耗 token 的内容格式）可以内化到推理平台的 API 设计：给 agent 调用的工具返回结构化精简数据而非 HTML。Kitesurf 的 V8 隔离 + 按请求 spin up 模式也和 K8s 上 serverless agent 的思路一致——agent 执行环境应该轻量、隔离、用完即弃。

### 5. 📦 技能还是子代理？Azure 给出 Agent 架构的四维决策框架

**原文标题:** 如何在技能与子代理之间做出恰当的选择
**来源:** InfoQ 中文 | 2026-08-06
**链接:** https://www.infoq.cn/article/BjFl6lKjTi2FEZNMxyb5

🎯 **一句话精髓**: Azure 首席工程师指出构建 AI 系统的「第一个真正抉择」不是选哪个模型而是选架构——技能（skill，在持续对话中运行，可读文件/提问/交互，始终考虑整个对话上下文）还是子代理（sub-agent，接收单个提示词独立运行至完成，从干净无污染的上下文窗口开始），用四个维度做决策：迭代模型、语音保真度、人工干预点、任务重复频率。

🔧 **技术栈**: Skills / Sub-agents / Copilot Studio / Planner / MCP / 上下文窗口管理 / 可复用性 / 协调层非确定性

📐 **架构/方法亮点**:
- **四维决策框架**：迭代模型（技能支持持续迭代交互 vs 子代理一次性响应）、语音保真度（技能保持对话连贯 vs 子代理独立输出）、人工干预点（技能让用户全程参与 vs 子代理自动完成）、任务重复频率（**频率是界限最分明的区分因素**——一次性手工制品倾向技能，可重复批量工作倾向子代理）
- **上下文窗口是核心权衡**：子代理始终从干净无污染的上下文窗口开始（避免上下文污染/幻觉累积），而技能始终考虑整个对话内容（保持连贯但可能受无关信息干扰）；技能可在多个代理或对话流中复用，子代理在需要独立上下文/权限/不同知识来源时才有意义
- **分层组合是最成熟设计**：技能与子代理的二分法仅是表面现象，两者可无缝组合——技能可以构建在子代理之上；社区思维模型：代理=导演、子代理=经理、技能=专业工作人员、工具=专用机器、MCP=组织治理规则

💡 **关键数据**: 决策框架基于 **4 个维度**；Copilot Studio 中 Planner 根据描述/上下文/最近对话动态决定何时调用技能/工具/主题/子代理——「并非每个类似提示词都会调用某项技能」体现了协调层的非确定性。

🔗 **樱桃的调度视角**: 这个四维框架可以直接映射到 Master 的 K8s agent 编排平台——技能和子代理在调度层面的区别是：技能是「长期运行、共享上下文」的常驻进程（类似 K8s Deployment），子代理是「一次性任务、独立上下文」的批处理作业（类似 K8s Job）。频率维度最实用：高频可重复任务用子代理（Job 模式，用完即弃，资源可回收），低频交互式任务用技能（Deployment 模式，常驻待命）。上下文窗口的权衡也很关键——子代理的干净上下文意味着每次启动要重新加载必要信息（冷启动成本），技能的持续上下文意味着常驻内存（保温成本）。这和 GPU 推理的冷热模型是完全同构的问题。

### 6. 📦 平台工程成熟度成为 AI 落地关键差异化因素：Perforce + DORA 双报告交叉验证

**原文标题:** 平台工程成熟度已成为企业人工智能应用能否成功的关键差异化因素
**来源:** InfoQ 中文 | 2026-08-06
**链接:** https://www.infoq.cn/article/j0qkf5FqgMfcDqOAWkZD

🎯 **一句话精髓**: Perforce「2026 平台工程报告」（820 名技术专业人士）发现成熟平台工程企业中 73% 认为平台成熟度是 AI 成功的关键因素（低成熟度仅 44%），Google DORA 独立研究将 AI 描述为「放大器」——高质量内部平台把个人 AI 生产力转化为团队交付改进，薄弱平台则让收益损耗在测试/安全/部署瓶颈中。

### 7. 📦 AWS Lambda 取消代码存储配额：别误会，函数大小限制没变

**原文标题:** AWS Lambda 取消代码存储配额，别误会：函数大小限制没变
**来源:** InfoQ 中文 | 2026-08-08
**链接:** https://www.infoq.cn/article/OG03ezJaBkdOd1G3rc1b

🎯 **一句话精髓**: AWS Lambda 推出自管理代码存储，让函数和层直接引用客户自有 S3 桶中的部署包，取消了账户级代码存储配额并将 Lambda 管理存储默认配额从 75GB 提升到 300GB——但单个函数的包大小限制（zip 50MB 压缩/250MB 解压，容器镜像 10GB）完全没变，社区关于「能否打包更大模型到函数」的期待落空。

🔧 **技术栈**: AWS Lambda / S3 自管理代码存储 / 部署包 / Lambda Layers / 容器镜像函数 / 存储配额 / 单一事实来源

📐 **架构/方法亮点**:
- **改变的是存放位置不是大小限制**：自管理存储让部署包存放在客户自己的 S3 桶而非 Lambda 管理空间，取消账户级总量上限，Lambda 管理存储默认配额从 75GB→300GB；但单个函数限制不变——zip 函数压缩后 50MB/解压后 250MB，容器镜像 10GB
- **社区误读与澄清**：AWS 无服务器首席开发者布道师 Julian Wood 在 LinkedIn 称「不再有存储限制」，引出社区关于「能否打包更大模型到函数」的讨论；开发者直截了当回答：不能，原有限制仍适用，且 AWS 还会向你收取 S3 存储和检索费用
- **真正的价值在单一事实来源**：客户可在自己账户建立部署包的单一事实来源，通过现有 S3 指标和生命周期规则获得完全可见性——对大规模函数集群的团队解决了此前需要提交支持工单提高配额的痛点

💡 **关键数据**: Lambda 管理存储默认配额从 **75GB → 300GB**；单函数 zip 限制：压缩后 **50MB** / 解压后 **250MB**；容器镜像函数：**10GB**；自管理存储无账户级上限（受 S3 桶容量限制）。

🔗 **樱桃的调度视角**: 这条对 Master 在 Serverless 上跑 AI 推理有直接参考——250MB 解压限制意味着小模型（如量化后的 7B 以下）可以打包进 Lambda，但大模型仍需走容器镜像（10GB）或外部模型服务。自管理 S3 存储的真正价值是让 Serverless 函数的部署包管理更接近 K8s 的镜像仓库模式——单一事实来源 + 生命周期规则。但 AWS 仍未解决 Serverless AI 的核心痛点：冷启动时加载模型到内存的延迟。对比 K8s 上的推理 Pod 可以常驻 GPU + 预加载模型，Lambda 的按需冷启动对延迟敏感的推理场景仍是硬伤。

## 📓 樱桃的今日学习总结

1. **K8s GPU 共享进入「调度原生」时代，但 enforcement 仍是独立层** - DRA consumable capacity 让调度器首次原生理解 GPU 分片（显存+算力），HAMi 的 mutating webhook + scheduler extender + annotation 编码层正在被 ResourceSlice/DeviceClass/ResourceClaim 替代。但关键洞见是「调度能分配 ≠ 运行时能限制」——DRA 解决 Pod 分到哪张卡的多少资源，libvgpu.so 解决 Pod 真的只用这么多。HAMi 的双栈路线（DRA 管调度 + 自己管 enforcement）是短期最佳实践。Master 的 GPU 平台如果只用 DRA 不加 enforcement，一个声明 8GB 的 Pod 可以吃满整张卡。

2. **AI 推理的存储层级正在从 HBM 向下延伸到 SSD，Token 经济学需要新变量** - 当 HBM 被模型权重和 KV Cache 占满，SSD 从静态存放进入实时数据路径。Mooncake 的 DRAM+SSD 多级缓存、NVIDIA CMX 的 pod 级闪存上下文层、群联 aiDAPTIV 的 VRAM↔SSD 权重流送都在指向：推理调度的资源维度必须从「GPU 卡」扩展到「GPU + 显存 + 远端 KV Cache + SSD 预取带宽」的多层协同。MoE 模型的专家权重按需加载让 SSD 预取延迟直接决定 GPU 空闲率——这和 DRA 的 consumable capacity 一样，都是把更多资源维度纳入调度决策。

3. **Agent 时代的 Infrastructure 正在分化为「身份/协议/治理」和「调度/执行/观测」两层** - Cloudflare 的 Agentic Internet 四层协议栈（readable/discoverable/callable/payable + Web Bot Auth/PACT 身份）、Azure 的技能 vs 子代理四维决策框架（迭代/保真/干预/频率）、Shadow AI 的六阶段威胁建模，共同指向：Agent 基础设施需要一层新的「agent 身份与协作治理」（谁能发现谁、谁能调用谁、协作如何审计），而 K8s 的 ServiceAccount/RBAC 是 Pod 级别的，需要向上扩展。技能=常驻 Deployment、子代理=一次性 Job 的映射也说明 agent 编排和 K8s 调度本质同构。
