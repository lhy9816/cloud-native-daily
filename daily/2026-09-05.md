### 1. 📦 K8s v1.37 DRA 大更新：Extended Resource 支持 GA，设备污点、CEL 派生属性齐上阵

**原文标题:** Kubernetes v1.37: DRA Updates
**来源:** Kubernetes Blog | 2026-09-03
**链接:** https://kubernetes.io/blog/2026/09/03/kubernetes-v1-37-dra-updates/

🎯 **一句话精髓**: DRA（动态资源分配）的 Extended Resource 支持历经三个版本终于 GA——存量 `example.com/gpu` 写法的工作负载零改造即可切到 DRA 后端，GPU 调度正式从「能用」迈向「可运营」。

🔧 **技术栈**: DRA / DeviceClass / ResourceClaim / DeviceTaintRule / CEL 表达式 / MIG / vGPU / CDI / KubeVirt / NUMA

📐 **架构/方法亮点**:
- Extended Resource GA：扩展资源名可直接设置在 DeviceClass 上，Pod 请求时由 DRA 匹配设备，无需 ResourceClaim、也无需 device plugin 旁路部署，存量工作负载无感迁移
- 设备污点与容忍转正（Stable）：管理员通过 DeviceTaintRule 集群级标记设备维护/降级，正在使用污点设备的 Pod 自动驱逐——完整镜像了节点污点机制；ResourceClaim status 新增 devices 字段，驱动可上报网卡接口名/MAC/IP
- PreQueueingHint（Alpha）：DRA ResourceClaim 事件原本触发全量不可调度 Pod 扫描（O(N²) 级开销），改用 pod informer index 精确圈定受影响 Pod，重排队路径降为 O(1)
- Derived Attributes（Alpha）：用 CEL 表达式桥接不同厂商属性命名差异（GPU 驱动叫 `numa`、NIC 驱动叫 `numaNode` 也能配对），还可从长拓扑字符串切片、按容量自定义性能分层

💡 **关键数据**: Extended Resource 三连跳 1.35 Alpha → 1.36 Beta → 1.37 GA；PreQueueingHint 早期基准约 2x 调度吞吐提升；ResourceClaim 跨 PodGroup 共享解除原 256 Pod 上限（Beta）；标准属性 `resource.kubernetes.io/numaNode` 直接以 Stable 落地

🔗 **樱桃的调度视角**: 这篇就是 Master 的主战场喵！Extended Resource GA 解决的是 DRA 最大的落地障碍——迁移成本；Derived Attributes + numaNode 标准化则是拓扑感知调度跨厂商 GPU+NIC 亲和配对的最后一块拼图，值得立刻跟进 WG Device Management 的后续动态。

### 2. 🧠 预测引导的多智能体 LLM 工作流编排：在异构 GPU 池上联合优化放置与模型生命周期

**原文标题:** Latency-Aware Orchestration for Multi-Agent LLM Workflows on Heterogeneous GPUs
**来源:** arXiv cs.DC | 2026-09-03
**链接:** http://arxiv.org/abs/2609.03335v1

🎯 **一句话精髓**: 把「模型加载成本、激活延迟、峰值内存」变成一等调度输入——用工作流预测构建物理执行图，在负载、模型常驻状态随时变化的异构 GPU 池上联合优化放置与执行顺序。

🔧 **技术栈**: Multi-Agent LLM 工作流 / 异构 GPU 池 / 模型生命周期管理 / 物理执行图 / makespan 优化 / p95 延迟

📐 **架构/方法亮点**:
- Predictor 估计设备相关的激活延迟、峰值内存与模型加载成本，再沿工作流依赖边传播，预测未来的激活就绪时间与模型需求
- Constructor 生成语义保持的算子融合与模型生命周期（加载/驱逐/常驻）替代方案，Scheduler 基于实时池状态联合优化方案选择、放置与执行顺序
- 核心抽象分离：逻辑工作流只定义计算需求，物理执行图决定调度单元、生命周期动作与资源排序——与 K8s「声明式意图 + 运行时绑定」思路同源

💡 **关键数据**: 相比 SOTA 工作流调度器，端到端 makespan 最多降低 36.8%，突发到达下整体 p95 完成延迟降低 25.9%，每个会话最多节省 24.63 GPU 秒

🔗 **樱桃的调度视角**: 这篇论文预演了推理调度的下一步——当多 Agent 工作流成为主流负载，「模型换入换出」会像今天的热页换页一样需要成本模型驱动。对 Volcano/Kueue 的 gang scheduling 设计极有借鉴意义喵。

### 3. 🚀 llm-d：K8s 上的分布式 LLM 推理编排栈，GitHub 周榜持续上榜

**原文标题:** llm-d — Achieve state of the art inference performance with modern accelerators on Kubernetes
**来源:** GitHub Trending（Shell 周榜）| 本周持续活跃（最近 push 2026-09-04）
**链接:** https://github.com/llm-d/llm-d

🎯 **一句话精髓**: Red Hat、Google Cloud、IBM Research、CoreWeave、NVIDIA 联合创立的 CNCF 沙箱项目，在 vLLM/SGLang 之上提供 K8s 原生编排层——智能路由、KV-Cache 分层、P/D 分离、SLO 感知弹性一应俱全。

🔧 **技术栈**: Kubernetes / vLLM / SGLang / prefix-cache 感知路由 / KV-Cache 分层卸载 / prefill-decode 分离 / 宽专家并行 / SLO 感知自动扩缩容

📐 **架构/方法亮点**:
- 智能路由：prefix-cache + 负载感知均衡，实验性预测延迟调度降低尾延迟
- KV-Cache 管理：多轮请求的有效工作集通过分层卸载（CPU/磁盘）扩大，配合全局精确索引

🔗 **樱桃的调度视角**: llm-d 就是「K8s 上 AI 推理」的参考实现，和今天第 1 条 DRA GA 形成完整闭环——它的路由与扩缩容信号都构建在 K8s 资源模型之上。Master 做 GPU 调度研究时，它是最好的生产级对照系统喵～

### 4. ⚖️ HPA 原生 Scale-to-Zero 升 Beta：队列型负载省掉最后一个空闲 Pod

**原文标题:** Kubernetes v1.37: Scale Workloads to Zero with HorizontalPodAutoscaler
**来源:** Kubernetes Blog | 2026-09-02
**链接:** https://kubernetes.io/blog/2026/09/02/kubernetes-v1-37-hpa-scale-to-zero-beta/

🎯 **一句话精髓**: v1.37 中 HPA 缩容到 0 副本进入 Beta 并默认启用——队列消费者、批处理这类「能等」的负载不再需要 KEDA 等外部组件，就能把独占 CPU/GPU 的空闲 Pod 也省掉。

🔧 **技术栈**: HPA / External Metrics API / Object Metrics / Prometheus Adapter / ScaledToZero condition / minReplicas: 0

📐 **架构/方法亮点**:
- 只认 object/external 指标：CPU/内存指标来自运行中的 Pod，副本归零后信号消失无法唤醒；API server 直接拒绝纯资源指标配 `minReplicas: 0`——队列长度这类独立于 worker 存在的指标才是正解
- ScaledToZero status condition 消歧：区分「HPA 自己缩到 0」与「人工暂停」——HPA 不会唤醒不是自己缩下去的负载，保留了人工 replicas:0 的暂停语义
- 默认 5 分钟缩容稳定窗口防抖，可通过 `spec.behavior.scaleDown` 调整

💡 **关键数据**: Alpha 最早可追溯到 v1.16，v1.36 加入 ScaledToZero condition，v1.37 Beta 默认开启；官方示例为每 30 个排队任务请求 1 副本（0–10 副本）

🔗 **樱桃的调度视角**: GPU 推理服务的成本敏感场景很适合「队列信号 + scale-to-zero + 冷启动容忍」组合拳；但要记住 HTTP 请求驱动负载需要额外缓冲层（Service 不会缓存请求）——这正是 llm-d 们做流控的理由喵。

### 5. 🔗 CPU + GPU：AI 平台工程本质是异构资源系统工程

**原文标题:** CPU + GPU: Why AI platform engineering is a heterogeneous infrastructure problem
**来源:** CNCF Blog（Vultr 赞助）| 2026-09-04
**链接:** https://www.cncf.io/blog/2026/09/04/cpu-gpu-why-ai-platform-engineering-is-a-heterogeneous-infrastructure-problem/

🎯 **一句话精髓**: 「跟着工作流走，而不是跟着 GPU 走」——GPU 利用率低往往不是需求不足，而是 CPU 预处理、存储或网络在上游卡了脖子，AI 平台工程的优化对象应是整条异构流水线。

🔧 **技术栈**: 异构调度 / DRA / LLM 推理流水线 / 全链路关联遥测 / 平台工程

📐 **架构/方法亮点**:
- 推理流水线拆解：数据 → CPU 预处理 → GPU 推理 → CPU 后处理 → 应用；整体性能取决于完整路径，任一环节供给不足都会让加速器空转
- LLM 推理本身也是异构负载：prompt processing（算力密集）与 token generation（访存密集）特征不同，可差异化匹配资源画像
- GPU 利用率单点指标会骗人：低利用率可能是等 CPU、等数据、等调度——需要 CPU → 数据 → 加速器 → 应用的全链路关联遥测，目标是资源协同高效而非单点 100%

💡 **关键数据**: 无量化基准（方法论文章），核心论断：AI 基础设施不是「一堆 GPU 加配套服务」，而是计算/内存/存储/网络的互联系统

🔗 **樱桃的调度视角**: 这篇与 DRA GA 是一体两面喵——Master 做 GPU 调度时，调度域应覆盖整条流水线（CPU 预处理 Pod 与 GPU Pod 的拓扑亲和），而不是只盯着 GPU 利用率单点优化。

### 6. 🧮 Every Kernel Is a Join：用关系代数全自动切分多 GPU 并行，实测快过 vLLM

**原文标题:** Every Kernel Is a Join: Automatic Multi-GPU Parallelism for AI Computations in Einsummable
**来源:** arXiv cs.DC | 2026-09-03
**链接:** http://arxiv.org/abs/2609.03905v1

🎯 **一句话精髓**: 把每个 AI 算子建模为「张量关系上的 join + 聚合」，优化器在分解空间里全局搜索最小化通信成本的方案，通信代码全部编译期合成——全自动并行超越手工调优。

🔧 **技术栈**: 关系代数 join / join-agg specs / auto-parallelization / exchange 算子 / 编译期通信合成 / 8×A100

📐 **架构/方法亮点**:
- 每个算子通过 join-agg specs 暴露所有可能分解，优化器跨整段计算选取分解组合以最小化通信成本代理——搜索的是分解空间而非「张量/流水线/数据并行」命名策略菜单，能发现 mesh 类自动并行器找不到的方案
- exchange program：Volcano exchange 算子的拓扑感知泛化，负责分解后算子的数据交换
- 不调用任何现成 collective（AllReduce 等），所有通信与聚合在编译期按需特化生成

💡 **关键数据**: LLaMA transformer block 在 8×A100 服务器上几何平均运行时 8.97ms，对比手工调优 PyTorch 13.80ms、vLLM 15.90ms

🔗 **樱桃的调度视角**: 数据库思想反哺 AI 系统的典范（和第 8 条「AI 改写数据库」正好双向奔赴喵）。它预示调度/并行决策正从运行时策略菜单走向编译期全局成本搜索——K8s 调度器的成本模型未来也可能被这类搜索式方法部分替代。

**来源:** InfoQ 中文 | 2026-09-03
**链接:** https://www.infoq.cn/article/yghIuWdN8M9vQyYeGuHl

🎯 **一句话精髓**: 把倒排索引 + 全文检索完整落到可观测性查询路径上——不同数据类型的任意字段都具备建倒排/全文索引的能力，把 Bloom 过滤「可能命中」的块级排除升级为「可组合、可运算的行集合」收敛。

🔧 **技术栈**: 倒排索引 / 全文检索 / Bloom filter / 指标-日志-链路-RUM 统一检索 / 千亿级数据

📐 **架构/方法亮点**:
- Bloom 的根本局限：只保存成员关系、不保存行号，只能排除「不可能命中」的数据块，无法告诉查询引擎值在哪条记录——倒排直接给出行集合，可与其他条件做集合运算
- 「全字段」≠ 无差别全建索引：用户按字段类型和查询习惯自选策略，把每份索引成本花在查询收益最高的地方
- 面向真实故障排查形态设计：服务/环境/地域/状态/追踪标识/文本条件的组合查询 + 排除已知噪声

💡 **关键数据**: 目标场景为千亿级数据点的秒级查询（指标、日志、链路、RUM、事件五类数据统一检索）

🔗 **樱桃的调度视角**: K8s 可观测（Pod 事件、调度器日志、高基数指标标签）本质也是高基数标签检索问题，倒排 vs Bloom 的取舍思路同样适用于调度器诊断与集群画像工具的索引设计喵。

## 📓 樱桃的今日学习总结

1. **DRA 生态闭环成型** — Extended Resource GA 给出教科书级的渐进迁移设计：存量 extended resource 写法零改造即可切后端，加上设备污点做运维、CEL 派生属性做跨厂商拓扑配对，K8s 设备管理完成了「能用 → 可运营」的跃迁；llm-d 这类上层推理栈是直接受益者。
