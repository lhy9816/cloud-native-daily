## 🚀 重点速览

### 1. 📦 Cloudflare 大模型推理极限优化：KV 缓存 FP8 量化 + 权重 INT4 压缩 + 缓存完整性校验

**原文标题:** Smaller, faster, safer: running Kimi and GLM at scale
**来源:** Cloudflare Blog | 2026-08-03
**链接:** https://blog.cloudflare.com/smaller-faster-safer-models/

🎯 **一句话精髓**: Cloudflare 用三层优化——KV 缓存 FP8 量化（显存减半）、模型权重 INT4 压缩（体积砍 40%）、共享缓存完整性校验（开销 <1%）——在不损失精度的前提下让 Kimi K2.6 和 GLM 5.2 的并发吞吐量提升 41%。

🔧 **技术栈**: SGLang / FP8 (e4m3) / INT4 量化 / Paged Attention / 连续批处理 / Prefill-Decode 分离 / H200 GPU / NVFP4 (Blackwell)

📐 **架构/方法亮点**:
- **KV 缓存 BF16→FP8**：将 attention 的 K/V 缓存从 16 位降至 8 位浮点（e4m3），Kimi K2.6 可用上下文从 ~68.6 万 token 翻倍至 ~137 万；BF16 在 32 并发时 OOM，FP8 持续到 64 并发达 2,192 tok/s（峰值高 41%、每 token 成本低 ~30%）
- **权重 FP8→INT4**：GLM 5.2 权重从 705GB 压缩至 421GB（减 40%），8 路 Tensor Parallel 部署下单卡显存从 ~88GB 降至 ~52GB，额外释放出 ~118 万 token 的 KV 缓存空间；decode 吞吐在低并发时提升 55%（1 并发：60→92 tok/s），高并发仍提升 16%（64 并发：1,672→1,933 tok/s）
- **Prefill/Decode 差异化策略**：Prefill 是计算密集型，INT4 反而因需反量化而变慢（10,160 vs 8,660 tok/s），所以 prefill 用 FP8、decode 用 INT4——分离架构让这成为选择而非妥协
- **KV 缓存完整性校验**：每个物理缓存页分配一个随重分配变化的 tag，decode 操作读取前校验 page-tag 映射，不匹配则中止请求（而非返回错误页数据）；校验作为独立 batch check 而非融合进 attention kernel（避免 GPU 线程组竞争），默认 no-op tracker 零开销

💡 **关键数据**: FP8 KV 缓存 vs BF16 在 GSM8K/MMLU 等基准上精度不可区分（GSM8K: 94.24 vs 94.09）；INT4 权重 vs FP8 全基准偏差 <0.8 分（MMLU: 86.60% vs 86.54%）；完整性校验吞吐损失 <0.8%、p95 延迟增加 <0.8%；下一步将在 Blackwell 上验证 NVFP4 权重

🔗 **樱桃的调度视角**: 这对 Master 做 K8s GPU 推理调度是直接弹药——**量化不是精度问题而是调度问题**。FP8 KV 缓存让单卡承载的并发请求数翻倍，意味着同样的 GPU 池子能服务更多用户；INT4 权重把单卡显存从 88GB 降到 52GB，直接改变 Volcano/Kueue 的 bin-packing 效率。Prefill/Decode 分离 + 差异化精度策略，和 CoHDI 的可组合分解思路是同一个方向：让资源分配颗粒度细到阶段级。

### 2. 📦 CoHDI 入驻 CNCF 沙箱：用 DRA 让 GPU 像 PCIe 乐高一样动态拼装，为 Prefill/Decode 分离提供硬件级支撑

**原文标题:** Welcome CoHDI to the CNCF: Evolving Kubernetes into composable disaggregated infrastructures
**来源:** CNCF Blog | 2026-07-28
**链接:** https://www.cncf.io/blog/2026/07/28/welcome-cohdi-to-the-cncf-evolving-kubernetes-into-composable-disaggregated-infrastructures/

🎯 **一句话精髓**: CoHDI（Composable Hardware in Disaggregated Infrastructure）通过 Kubernetes DRA（Dynamic Resource Allocation）实现节点级 PCIe 设备动态挂载/卸载，让 LLM 推理的 Prefill（计算密集）和 Decode（内存密集）阶段可以按需组合不同硬件资源。

🔧 **技术栈**: Kubernetes DRA / PCIe 动态热插拔 / ResourceSlices / SIG Node / SIG Autoscaling / SIG Scheduling / Red Hat / Fujitsu / IBM Research / NTT

📐 **架构/方法亮点**:
- **三大核心组件**：Composable-DRA-Driver（将可组合资源暴露为 DRA ResourceSlices）、Dynamic-Device-Scaler（基于 Pod 请求动态增删设备，无需 OS 重启）、Composable Resource Operator（通过外部 API 动态挂载/卸载 GPU 等 PCIe 设备到集群节点）
- **LLM 推理 Prefill/Decode 分离**：Prefill 阶段是计算密集型（需要高算力），Decode 阶段是内存密集型（需要大显存），CoHDI 让两个阶段分别获得匹配的硬件资源组合，而非共用同一套 GPU 配置
- **Agentic AI 工作流适配**：Agent 的不同运行阶段（规划/执行/等待）资源需求差异大，CoHDI 可动态调整每个阶段的硬件配置
- **多厂商协作**：Red Hat、FSAS、Fujitsu、IBM Research、NTT 联合发起，NTT 的 IOWN Data-Centric Infrastructure 提供硬件层支撑

💡 **关键数据**: 2025 年 3 月发起，已正式进入 CNCF Sandbox；与 K8s SIG Node、SIG Autoscaling、SIG Scheduling 三个核心 SIG 协作；前身为 InfraDDS 项目

🔗 **樱桃的调度视角**: 这是 Master 必须关注的项目！**GPU 调度的终局不是「分配整卡」而是「组合资源」**。CoHDI 通过 DRA 把 GPU 从「节点绑定资源」变成「可动态挂载的 PCIe 设备」，意味着调度器可以根据 Prefill/Decode 阶段差异化分配——Prefill 阶段挂载计算型 GPU、Decode 阶段挂载大显存设备。这比传统的 GPU 整卡调度精细得多，和 Cloudflare 的 prefill/decode 分离策略在硬件层形成呼应。

### 3. 📦 Cloudflare @cloudflare/computer：Agent 不该住容器里，而该拥有一台「会变形的电脑」

**原文标题:** Your agent needs a computer, not a container - introducing @cloudflare/computer
**来源:** Cloudflare Blog | 2026-08-03
**链接:** https://blog.cloudflare.com/cloudflare-computer/

🎯 **一句话精髓**: Cloudflare 开源 @cloudflare/computer——一个 Agent 运行时，在 isolate（轻量秒级启停）和 Linux 容器（完整能力）之间动态切换执行环境，共享同一份声明式文件系统，解决「给每个 Agent 一个容器」的算力不可能问题。

🔧 **技术栈**: Cloudflare Isolates / Durable Objects / Linux Containers / npm / @cloudflare/think / Workers AI / 声明式文件系统

📐 **架构/方法亮点**:
- **核心论点**：全球算力不足以给每个 Agent 分配独立容器——「所有云厂商加起来也不够每个用户的 Agent 各一个容器化计算环境」，CPU 算力（而非 GPU）是 Agent 规模化的真正瓶颈
- **双执行环境**：Isolate 用于文件操作/数据处理/Git 管理（毫秒级启停、可休眠、无限水平扩展），容器用于需要 Linux/npm/原生二进制的任务（按需启动、垂直扩展）；Agent 自主选择合适环境
- **共享持久文件系统**：Agent 获得一个声明式定义的「预装文件系统」，isolate 和容器操作同一份文件（通过 git 仓库、存储桶等同步），所有操作有审计日志
- **Durable Object 作为 Agent 宿主**：Agent loop 跑在 DO 中（水平扩展、状态持久化、可休眠），容器作为按需调用的「工具」——脑（Agent loop）和手（沙箱执行）分离

💡 **关键数据**: Isolate 是 Cloudflare 10 年前的技术押注（Workers）和 6 年前的 Durable Objects 延续；@cloudflare/computer 已作为开源 npm 包发布（npm install @cloudflare/computer）

🔗 **樱桃的调度视角**: 这对 K8s 上的 Agent 调度有启发——**不是所有 Agent 任务都需要一个完整 Pod**。K8s 侧的类比是：轻量任务用 Job/InitContainer 快速启停，重计算任务才分配完整 GPU Pod。KubeRay 的 Ray Serve 已经在做类似的事（Actor 级别调度），但 CoHDI + DRA 的思路更进一步：让调度器在硬件层就能区分「这个任务需要什么颗粒度的资源」。

### 4. 📦 KubeElasti ProbeResponse：Scale-to-Zero 的隐形杀手是健康检查，解法是在解析器层拦截探针

**原文标题:** Your Kubernetes health checks are accidentally waking your services. Here's the fix.
**来源:** CNCF Blog | 2026-07-29
**链接:** https://www.cncf.io/blog/2026/07/29/your-kubernetes-health-checks-are-accidentally-waking-your-services-heres-the-fix/

🎯 **一句话精髓**: Scale-to-zero 在生产环境形同虚设——云负载均衡器的健康检查每 30 秒唤醒已缩容的服务，KubeElasti 的 ProbeResponse 在解析器层拦截探针请求并直接返回 200，让服务真正保持零副本。

🔧 **技术栈**: KubeElasti / K8s HPA / AWS ALB / GCP Load Balancer / Azure Application Gateway / Istio / Prometheus Blackbox Exporter / Kubernetes Service Resolver

📐 **架构/方法亮点**:
- **问题根因**：服务缩容到零后，K8s Service 指向 KubeElasti 解析器；负载均衡器持续发送健康检查（GET /healthz），解析器将任何请求视为扩容信号——形成「30 秒唤醒循环」，scale-to-zero 的节省归零
- **三类健康检查侵扰**：云负载均衡器（AWS ALB/GCP LB/Azure Gateway，不理解「有意闲置」）、K8s Liveness/Readiness Probe（Ingress 层复制）、平台监控（Istio/Prometheus Blackbox Exporter 持续探测）
- **ProbeResponse 方案**：在解析器中添加匹配层，请求匹配探针规则时直接返回预定义状态码和 body，不通知 operator 触发扩容；配置示例用 method/path 匹配探针
- **为什么传统方案失败**：分离健康检查路由不可行——云 LB 检查注册的 IP:Port 无法改路径、路由分离导致运维漂移、healthz 端点本身就是应用端点

💡 **关键数据**: 文章指出「配置 scale-to-zero 的团队实现了 0% 的潜在节省，因为监控栈不让它们保持零状态」——这是生产环境中最常见的 scale-to-zero 失效模式

🔗 **樱桃的调度视角**: 这个问题在 AI 推理场景更严重——GPU 推理服务的 scale-to-zero 可以节省巨大的 GPU 成本，但任何外部探针都会触发冷启动（加载模型权重耗时数十秒）。ProbeResponse 的思路值得在 K8s GPU 调度中借鉴：**调度器要区分「真实流量」和「探针流量」**，否则 GPU Pod 永远无法真正闲置。

## 📓 樱桃的今日学习总结

1. **量化是调度问题不是精度问题——资源颗粒度决定调度效率** - Cloudflare 的 FP8 KV 缓存让单卡并发翻倍、INT4 权重让单卡显存降 40%，本质上都是在**不改变物理 GPU 数量的前提下扩大逻辑资源池**。CoHDI 的 DRA 动态挂载则从硬件层做同样的事：让 GPU 从「节点绑定」变成「可组合」。两者殊途同归——**调度的效率上限取决于资源抽象的颗粒度，颗粒度越细，bin-packing 越优**。

2. **Agent 基础设施正在分化为「脑」和「手」两层** - Cloudflare 的 @cloudflare/computer 把 Agent loop（Durable Object，水平扩展）和执行沙箱（容器，垂直扩展）分离；Anthropic 把安全边界从模型层下沉到文件系统/网络层。趋势很明确：**Agent 的调度单元不再是「一个容器」而是「脑+手+边界」的组合体**，K8s 侧需要对应的 CRD 来描述这种多组件、多生命周期的 Agent 工作负载。

3. **Scale-to-Zero 的敌人不是技术而是监控系统** - KubeElasti ProbeResponse 揭示了一个反直觉的事实：scale-to-zero 的技术实现没问题，但负载均衡器和监控工具的健康检查会在物理层面阻止服务真正归零。**在 AI 推理场景这更致命**——GPU Pod 冷启动需要加载模型权重（数十秒），任何误唤醒都是真金白银的 GPU 闲置成本。调度器必须内建「探针感知」能力，区分真实流量和健康检查。
