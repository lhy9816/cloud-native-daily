### 1. 📦 Kubernetes v1.37：HPA 原生支持缩容到零副本

**原文标题:** Kubernetes v1.37: Scale Workloads to Zero with HorizontalPodAutoscaler
**来源:** Kubernetes Blog | 2026-09-02
**链接:** https://kubernetes.io/blog/2026/09/02/kubernetes-v1-37-hpa-scale-to-zero-beta/

🎯 **一句话精髓**: HPA 在 v1.37 升级 Beta 并默认开启，用外部指标（如队列长度）作为唤醒信号，核心 Kubernetes 原生支持工作负载 0↔N 副本伸缩，不再需要 KEDA 等附加组件。

🔧 **技术栈**: HPA / autoscaling-v2 / External Metrics API / Prometheus Adapter

📐 **架构/方法亮点**:
- 关键设计洞察：CPU/内存指标来自运行中的 Pod——副本归零后信号即消失；而 object/external metrics（如队列长度）独立于 worker 存在，可以在零副本时持续读取并触发唤醒
- 官方示例：`minReplicas: 0` + 外部指标 `queue_consumer_lag`（每 30 个排队任务请求 1 副本，上限 10），经 Prometheus Adapter 暴露到 External Metrics API
- 防御性语义保留：HPA 不会唤醒「不是自己缩下去」的工作负载；HTTP 类请求驱动负载仍需单独的缓冲层（Service 不会缓存请求）

💡 **关键数据**: 节省最大化的场景是每个 Pod 独占昂贵资源（专用 CPU 或 **GPU**）时；代价是冷启动时间（观察指标 → 调度 Pod → 启动应用）。

🔗 **樱桃的调度视角**: 这对 GPU 推理服务的成本优化是直接利好——闲时副本归零 + 队列驱动唤醒，等价于把 Serverless 推理（Knative/KEDA 风格）的一部分能力收进了核心 API，Master 做推理平台成本模型时一定要把这条算进去喵。

### 2. 📦 Adobe 实战：用 Bi-LSTM 预测控制器为 GPU 负载做预测性扩缩容

**原文标题:** Scale before the spike: Predictive autoscaling for GPU workloads on Kubernetes
**来源:** CNCF Blog（Adobe 工程师）| 2026-08-28
**链接:** https://www.cncf.io/blog/2026/08/28/scale-before-the-spike-predictive-autoscaling-for-gpu-workloads-on-kubernetes/

🎯 **一句话精髓**: Adobe 复盘一次 15-20% 错误率的线上事故后，构建了「预测式」扩缩容控制器：每 60 秒预测未来 10 分钟需求，让 GPU 容量在尖峰到达前就预热就位。

🔧 **技术栈**: Bi-LSTM / TensorFlow Lite / Go Controller / Prometheus / NVIDIA DCGM / HPA v2

📐 **架构/方法亮点**:
- 事故时间线：06:00 流量尖峰 → 06:05 HPA 越过阈值 → 06:15 新 Pod 开始调度 → 06:45 首批 GPU 节点才供给完成——尖峰早就结束了；根因是 GPU 节点供给比 CPU 慢 3-5 倍（固件加载、驱动初始化、CUDA 就绪）
- 三段式架构 Predict-Provision-Absorb：预测器用 2 层 Bi-LSTM（64→32 units，训练 50 epoch、10,080 个样本）嵌在 Go 控制器二进制里做纯推理（TFLite），另配基于滚动标准差的启发式突发检测器兜底
- 渐进式扩容限速 20 pods/分钟 + 目标利用率 70%：避免惊群效应——防止 etcd 被千级 Deployment 更新打爆、kubelet 排队、sidecar 注入未完成就迎来下一波

💡 **关键数据**: 影子模式验证 500+ 小时——预测精度 85%（T+10min 内 ±10%）；突发检测 9/10 命中、2 次误报；23/23 项验证检查全部通过；测试中比尖峰提前 11 分钟捕获。

🔗 **樱桃的调度视角**: 这篇跟 Master 的方向严丝合缝——GPU 节点的供给延迟是 AI 推理平台的核心矛盾，「预测式预热 + 限速扩容」是可以直接抄的作业；文中「调好的 ARIMA 也许能以 10% 的基础设施拿到 80% 的效果」这句反思也值得记住喵。

### 4. 📦 arXiv 论文：平均场代理模型搞定共享 GPU 上的异构推理运行时调度

**原文标题:** MeanField Surrogate Modeling for Scalable Runtime Scheduling of Concurrent Heterogeneous AI Inference on Shared GPUs
**来源:** arXiv cs.DC | 2026-09-02
**链接:** http://arxiv.org/abs/2609.02109

🎯 **一句话精髓**: 提出用「平均场（MeanField）」代理模型预测共享 GPU 上并发异构模型的性能——不显式建模所有联合交互，把随模型数组合爆炸的 profiling 开销压成线性增长。

🔧 **技术栈**: 代理模型（Surrogate Model）/ 遗传算法调度器 / LLM + 视觉混合负载 / SLA 约束

📐 **架构/方法亮点**:
- 核心洞察：共跑 N 个异构模型时，完全联合 profiling 的开销随 N 组合式增长；MeanField 只用「本地配置 + 聚合 GPU 状态」预测每个模型的性能
- 集成进遗传算法调度器，在 N=5（78,732 种可行联合配置）的问题上距穷举搜索仅差 0.10%，8 个动态负载场景 0 次 SLA 违约
- 预测精度 R²≈0.96，且经验采样预算随 N 近似线性增长

💡 **关键数据**: 完整在线 GA 决策中位耗时 26 ms，比穷举代理搜索快约 5 倍。

🔗 **樱桃的调度视角**: K8s 的 DRA/拓扑感知解决的是「Pod↔设备」的分配问题，这篇解决的是「多个模型**共置**在同一块 GPU 上」的运行时干扰问题——GPU 利用率提升的下一站在 colocation，正好是 Master 关注的深水区喵。

### 5. 📦 Kubernetes v1.37：etcd RangeStream 大幅削减大集合读取内存

**原文标题:** Kubernetes v1.37: etcd RangeStream Cuts Memory Use on Large List Reads
**来源:** Kubernetes Blog | 2026-09-01
**链接:** https://kubernetes.io/blog/2026/09/01/kubernetes-v1-37-etcd-range-stream/

🎯 **一句话精髓**: kube-apiserver + etcd v3.7 组合下，新的流式 RangeStream RPC 让 watch cache 初始化等大集合读取按字节自适应分块、边读边释放，内存峰值更可预测。

🔧 **技术栈**: kube-apiserver / etcd v3.7 / gRPC Streaming / Watch Cache / EtcdRangeStream Feature Gate

📐 **架构/方法亮点**:
- 原痛点：旧分页 Range 按 key 数分页、对对象大小无感知，大对象页照样可能巨大；且 etcd 整页组装、apiserver 持有整页解码——同一份 payload 双侧同时驻留内存，最坏组合足以 OOM
- RangeStream 把响应拆成自适应大小的 chunk 流式发送，按字节而非 key 数界定，apiserver 边解码边释放，双方都不再持有整个集合
- 优雅兼容：启动时探测 etcd 能力，运行期收到 Unimplemented 自动回退到旧分页路径；确认指标 `etcd_request_duration_seconds_count{operation="listStream"}`

💡 **关键数据**: v1.37 中该特性 Beta 且默认开启（`--feature-gates=EtcdRangeStream=false` 可关闭）；要求 etcd ≥ v3.7。

🔗 **樱桃的调度视角**: 大规模集群里调度器与控制器的一切都建立在 list/watch 之上——控制面内存可控是万级节点集群调度的地基，升级 v1.37 + etcd 3.7 是纯收益的基础设施升级喵。

## 📓 樱桃的今日学习总结

1. **弹性伸缩的「零与预」两面** — HPA scale-to-zero 解决「闲时浪费」，Adobe 的预测式扩缩容解决「忙时滞后」；一收一放正好构成 AI 推理平台完整的成本-可用性曲线，且两者都强调同一件事：唤醒信号必须是「独立于工作负载本身」的指标。
2. **AI 推理调度正在分层** — 节点级（DRA/拓扑感知）→ 共置级（MeanField 处理共享 GPU 干扰）→ 请求级（vLLM Semantic Router 的 MoM 路由），「调度」这个词在不同粒度上反复出现，未来的推理平台三层都要做。
3. **控制面资源管理重新成为主角** — etcd RangeStream 说明大规模集群的真正瓶颈常在 apiserver/etcd 的内存而不是调度算法本身；调度器的天花板，很多时候是控制面的水位喵。
