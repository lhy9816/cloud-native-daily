### 1. 📦 GPU 负载的预测性扩缩容实战：Bi-LSTM 控制器让容量比流量早到 10 分钟

**原文标题:** Scale before the spike: Predictive autoscaling for GPU workloads on Kubernetes
**来源:** CNCF Blog | 2026-08-28
**链接:** https://www.cncf.io/blog/2026/08/28/scale-before-the-spike-predictive-autoscaling-for-gpu-workloads-on-kubernetes/

🎯 **一句话精髓**: 用嵌在 Go 控制器里的 Bi-LSTM 每 60 秒预测未来 10 分钟的需求并提前预热 GPU 容量，解决 GPU 节点供给比 CPU 慢 3-5 倍、反应式 HPA 物理上永远追不上尖峰的根本矛盾。

🔧 **技术栈**: Kubernetes / Bi-LSTM / TensorFlow Lite / Prometheus / NVIDIA DCGM / HPA v2 / Go Controller

📐 **架构/方法亮点**:
- 三段式架构 Predict → Provision → Absorb：控制器每 60 秒拉取过去 1 小时指标，用 2 层 Bi-LSTM（64→32 units，10,080 样本训练）预测 T+10min 需求；模型以 TFLite 形式直接嵌进 Go 二进制做推理，不需要外部 ML 平台和模型服务层
- 并行 Burst Detector 作为模型安全网：基于「预测 vs 实际」滚动标准差的自适应阈值，真实需求超出置信区间时放大扩容激进度——应对营销活动、功能爆红等训练数据没见过的突刺
- Graduated Scaler 限速 20 pods/分钟防惊群：让节点安置、etcd、kubelet 拉镜像、sidecar 注入逐波完成；目标利用率故意设 70% 而非 100%，给预测误差留头部空间

💡 **关键数据**: 500+ 小时影子模式验证；预测准确率 85%（T+10min 时 ±10% 以内）；burst 检测召回 9/10、仅 2 次误报；23/23 项验证检查全部通过；模拟尖峰提前 11 分钟捕获；作者自评「调好的 ARIMA 能用 10% 的基础设施拿到 80% 效果」

🔗 **樱桃的调度视角**: 这篇和 v1.37 的 HPA scale-to-zero 是一枚硬币的两面——缩到零省空闲成本、预测性扩容保尖峰 SLO，都在把「扩缩容时机」从被动阈值变成主动规划。GPU 冷启动 3-5 分钟的物理约束意味着推理平台必须有「时间视野」，这正是自定义调度器插件 / KEDA 自定义 scaler 的设计空间，而且「无 CRD、直接 patch Deployment replicas」的轻量做法对存量集群极其友好喵。

### 2. 📦 在 Kubernetes 上建一座 AI 工厂：从裸金属到推理服务的 16 层参考架构

**原文标题:** Building an AI factory on Kubernetes
**来源:** CNCF Blog | 2026-08-27
**链接:** https://www.cncf.io/blog/2026/08/27/building-an-ai-factory-on-kubernetes/

🎯 **一句话精髓**: AI 工厂的本质是「一池 GPU、多团队同时抽取」（一边微调、一边推理、一边跑评测），文章给出从裸金属生命周期到租户计费的 16 层完整拼图，并断言瓶颈不是模型服务，而是利用率与租户隔离。

🔧 **技术栈**: Metal3 / Ironic / Cluster API / Argo CD / Node Feature Discovery / DRA / MIG / HAMi / KAI Scheduler / Volcano / Kueue / vLLM / KServe / llm-d / KubeVirt / Cilium / Multus / SR-IOV / RDMA / OpenCost

📐 **架构/方法亮点**:
- 利用率的两大杀手诊断：资源模型上 device-plugin 让 Pod 请求 `nvidia.com/gpu: 1` 就独占整卡（哪怕只用 10%），DRA（v1.34 GA）让调度器把加速器视为带属性/显存/拓扑的富设备但切分仍靠底层 MIG/HAMi；隔离模型上「每团队专用集群/专用 GPU 块」安全却浪费大部分硬件
- 调度层全清单：DRA + MIG + HAMi + time-slicing（分配面）× KAI Scheduler（拓扑感知调度）/ Volcano / Kueue（队列与公平共享）——分配与排队是两个正交维度
- 裸金属层细节扎实：节点发现记录 GPU 数量、ECC 状态、InfiniBand GUID 与 NIC MAC；网络启动装带 GPU 驱动 + CUDA + NCCL 的 OS 镜像；按用途设 BIOS（基线/性能/机密计算）；入池前 burn-in 负载测试 + NCCL 全带宽互连验证；NetBox 作事实源兼管 IPAM

💡 **关键数据**: 参考架构共 16 个功能层（硬件生命周期 → 集群生命周期 → 节点盘点 → 租户隔离 → GPU 分配 → 推理服务 → 批处理/HPC → VM → 网关与弹性 → 网络 → 存储数据 → 可观测 → 身份策略 → 密钥安全 → 可靠性 → 自助计费）；SemiAnalysis ClusterMAX 给 GPU 云打分看的是安全/网络/存储/可靠性/支持而非裸吞吐——「包裹 GPU 的那层壳」才是被市场定价的东西

🔗 **樱桃的调度视角**: 这张分层表可以直接当 Master 的 GPU 平台选型 checklist 用。樱桃特别圈出调度行的组合：KAI Scheduler（拓扑感知）+ Kueue（队列/配额）+ DRA/MIG/HAMi（分配）——与 Netflix 生产迁移互相印证「队列 + 拓扑感知」已是 AI 工厂调度层的事实标准拼图；租户隔离选 vCluster + sandboxed runtime 而非硬切集群，是利用率与安全的工程平衡点。

### 3. 📦 arXiv 论文：SemSpot——把竞价实例经济学引入 LLM 推理的语义感知服务模型

**原文标题:** Bridging Agent Semantics with Spot Capacity: An Elastic and Recoverable Service Model
**来源:** arXiv cs.DC（Minchen Yu）| 2026-08-30
**链接:** https://arxiv.org/abs/2608.29581

🎯 **一句话精髓**: 把云计算里「Spot 实例便宜但可被回收」的语义搬进 MaaS 推理平台：厂商按请求发布短期报价（价格/完成概率/失败通知时限），Agent 运行时根据当前任务状态与完成规则动态选择——「可抢占」从基础设施属性升级为可编程的服务契约。

🔧 **技术栈**: LLM Agent / Model-as-a-Service / Spot Capacity / 语义感知调度 / 完成语义 / 推理状态保持

📐 **架构/方法亮点**:
- 请求级 SemSpot：provider 发布 short-lived offers（success price、completion probability、failure-notification deadline 三个字段），agent runtime 结合任务状态与 completion rule 做选择——现有 MaaS 服务模型只在 request/job/endpoint 粒度运作，无法组合瞬时供给与演进中的任务语义
- 对 6 个 agent benchmark、1,535 个案例的审计归纳出 4 类 recurring workflow structure，不同结构下成本/服务时延/降级行为显著不同——语义结构成为定价依据
- token 级 SemSpot：在长请求内部保存 provider 推理状态 + runtime 验证过的语义段，请求被回收后可从语义边界恢复而非从零重放——把「重放成本」这个 agent 特有变量纳入设计

💡 **关键数据**: 审计 1,535 个案例、覆盖 6 个 agent benchmark、归纳 4 类工作流结构；论文同时给出经济边界与跨层研究议程

🔗 **樱桃的调度视角**: 这是樱桃今天最喜欢的一篇——Agent 后台长跑 + Spot 容量的组合可能是推理成本曲线的下一个断崖。若 spot 语义进 MaaS，K8s 调度层面就要新增「完成概率 + 通知时限」两个决策维度，与 Volcano 的可抢占作业队列天然契合；「按语义段恢复」的思路对 GPU 推理的 checkpoint/迁移设计也有直接启发喵。

### 5. 📦 Uber 公开 AI 软件工厂省钱账本：请求量涨 9.4 倍，token 账单却没涨

**原文标题:** 智能体请求暴增9.4倍，token账单却没涨：Uber 公开AI软件工厂省钱方法

🎯 **一句话精髓**: Uber 把智能体会话成本拆成六个相乘因子的公式逐项优化，在周活跃用户涨 7 倍、请求量涨 9.4 倍的同时让 AI 总支出自 4 月起保持平稳——智能体基础设施的成本工程完整方法论。

🔧 **技术栈**: 智能体 Harness / 模型路由 / 提示词缓存 / MCP 统一网关 / 基准测试选型 / Pareto 前沿

📐 **架构/方法亮点**:
- 四层智能体运行模型 + 六项相乘成本公式：采用率 × 参与度（想变大的项）× 自主轮次 × token 单价 × 每请求 token 等中间项（想变小的项），每项独立度量、独立优化

💡 **关键数据**: 70%+ 的 MR 由智能体生成；已构建 3,600+ 智能体技能、日均 3 万+ 次调用；固定模型对照测试下每千次请求成本较峰值降近 34%、每会话成本较 6 月峰值降 52%；统一 MCP 网关管理 1,000+ 内部与第三方 MCP 服务器

🔗 **樱桃的调度视角**: 这套六因子公式就是「Agent 时代的资源模型」——过去优化 CPU/内存利用率，现在要优化 token 利用率，而且每一项都能映射到 K8s 平台概念：模型路由 = 分级调度、提示词缓存 = KV Cache 复用、40 万 token 自动压缩 = 资源回收。Master 做推理平台容量规划时，「token 利用率」应该和 GPU 利用率一起进仪表盘喵。

### 6. 📦 Floatboat 的全栈 Harness 赌注：同一个模型，换套运行时便宜 57 倍还更强

**原文标题:** 自研Runtime、Agent Loop、Infra：一家通用Agent公司的全栈赌注
**来源:** InfoQ 中文 | 2026-08-31
**链接:** https://www.infoq.cn/article/NUGYDLvivgYXMV9u637z

🎯 **一句话精髓**: 一组对照评测给「模型之外的那半个系统」定了价：DeepSeek-V4-Flash（混合价 $0.175/M）在自研 Harness 上五项基准全胜贵 57.1 倍的 Claude Opus 4.8，且任务越长程增益越大——运行时工程的收益可以被基准化。

🔧 **技术栈**: 自研 Agent Runtime / Agent Loop / GUI-Agent 双向协议 / FloatSail 自适应进化系统 / DeepSeek-V4-Flash

📐 **架构/方法亮点**:
- 「不经过 Agent 的最优路径」设计哲学：Workflow、代码、普通桌面操作能完成的任务根本不进 Agent，只有真正出现不确定性时 Agent 才介入——Agent 是能力而非所有任务都要缴的「智能税」，这是成本可控的前提
- GUI-Agent 双向协议：用户能看到、能操作的 GUI，Agent 同样能理解、能修改；UI 不是 Harness 外面的包装而是人和 Agent 共享的 Runtime，控制权在同一工作流中自然交接
- 长程任务的核心是「收敛」而非「多跑几步」：交付标准初始模糊、模型在长链中持续漂移，Harness 在每一步把结果拉回交付标准——该回退时回退、该追问时追问、该自校验时自校验

💡 **关键数据**: 短程任务增益仅 1.9%，长程 DeepSWE 达 23.6%——增益随任务程长递增；HLR（Harness Leverage Ratio，换 Harness 相对换模型的杠杆比）从 0.78 倍一路涨到 3.57 倍；同一模型在 DeepSeek 官方 Harness 上一项未赢、接入 Floatboat Harness 后五项全胜

🔗 **樱桃的调度视角**: HLR 是个聪明的指标——它量化了「运行时/调度层工程」相对于「换更强模型」的边际收益，任务越复杂杠杆越高。Master 做平台 ROI 论证时可以直接借用「同一模型 + 不同 Harness」的对照测试方法论，把调度器的价值从「省了多少 GPU 时」扩展到「提升了多少任务成功率」喵。

### 7. 📦 K8s v1.37：Pod 证书与 Cluster Trust Bundles 毕业 GA——工作负载身份告别 Bearer Token

**原文标题:** Kubernetes v1.37: Pod Certificates and Cluster Trust Bundles
**来源:** Kubernetes Blog | 2026-08-28
**链接:** https://kubernetes.io/blog/2026/08/28/kubernetes-v1-37-pod-certificates-and-cluster-trust-bundles/

🎯 **一句话精髓**: Kubernetes 把 X.509 证书签发直接内建进核心（Pod 私钥不出工作负载、内置 signer 签发、Cluster Trust Bundles 分发信任锚），补上 Service Account JWT「持有即身份」的天然安全缺陷。

🔧 **技术栈**: X.509 / mTLS / Pod Certificates / Cluster Trust Bundles / SPIFFE / Tinycert / SIG Auth

📐 **架构/方法亮点**:
- 动机剖析到位：SA JWT 是 bearer token——你必须把 JWT 副本交给所有要对证的对端，拿到的人也就能冒充你；时间/对象/受众绑定只是部分缓解，完整解法是 proof-of-possession（只出示签名证明，私钥留在工作负载或 HSM 内不出门）
- 设计目标是「像用 SA JWT 一样容易地用 X.509」：保留 K8s 原生身份的易用性（自动签发、kubelet 原生支持）同时升到非对称凭证的强度，而非要求用户自建 cert-manager 工作流
- 与 SPIFFE 生态合流：SPIFFE Filesystem Delivery 草案标准正在评审，目标是让 SPIFFE 证书直接跑在原生 K8s 上；Tinycert 支持自建 signer，SIG Auth 主导后续 signer 演进

💡 **关键数据**: K8s 1.37 中 Pod Certificates 与 Cluster Trust Bundles 的基础能力正式 GA；SA JWT 至今仍是三大云厂商 pod-to-cloud 认证的底座——迁移面越大，原生 mTLS 的价值越大

🔗 **樱桃的调度视角**: 工作负载身份是零信任容器平台的基石。GPU 推理平台里 Pod 间 mTLS（推理服务 → 向量库 → 模型仓库 → 网关）以前要靠 cert-manager + SPIRE 外挂拼装，现在主干内建意味着多租户 AI 集群的信任链配置成本大降；配合 v1.36 已 GA 的 User Namespaces，Master 的容器安全清单又能划掉两格了喵。

📐 **架构/方法亮点**:
- 资源模型扩展：生产 AI 管道天然异构（数据准备/预处理/检索/编排在 CPU，训练推理在加速器），单一工作负载可能同时依赖多种资源类型——调度必须把加速器型号与可用性和 CPU/内存/拓扑放在同一张决策表里，DRA 正是为此演进

- 可观测性的提问方式变了：「GPU 利用率」回答不了「工作负载到底在等什么」——要把加速器利用率/显存、调度与排队时延、推理时延、模型加载时间、吞吐、端点健康与基础设施/应用遥测关联成一张图

💡 **关键数据**: CNCF 2025 年度云原生调查：66% 托管 GenAI 模型的组织用 K8s 跑部分或全部推理负载，但仅 7% 每日部署 AI 模型；2025 State of AI in Platform Engineering：35% 平台团队仍不编排 AI 工作负载

🔗 **樱桃的调度视角**: 「66% 在用 vs 7% 每日部署」的九倍差距正是调度平台的用武之地——每日部署意味着持续的容量规划、滚动更新与模型版本路由，这些都是调度器的本职。Master 做的平台正处在这条鸿沟的桥面上，这两个数字可以直接写进任何平台立项的论证材料里喵。
